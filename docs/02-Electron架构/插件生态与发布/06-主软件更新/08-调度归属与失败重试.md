## 一、调度归属——谁在跑后台检查器

### 1.1 问题从哪来

#57.9d 要「mount 后延迟 30s + 每 4h 检查一次」。挂在壳根组件上，看起来就是「一个窗口一份」。L5.3 开了多窗口之后，#57.9f 担心的是 **N 个窗口 = N 份调度器**（每 4h 检查 N 次、一次更新弹 N 条通知）。

### 1.2 源码实证：壳渲染进程在本应用里**只有一份**

| # | 事实 | 证据 |
|:-:|:--|:--|
| ① | **壳页面（`index.html` → `src/main.tsx` → `src/App`）全仓只有一个加载点**，就在 `createWindow()` 里，即唯一的主窗口 | `electron/main.ts:145`（dev `loadURL(DEV_SERVER_URL)`）/ `:147`（prod `loadFile(.../dist/index.html)`）；`index.html:10` 是全仓唯一 `<script src="/src/main.tsx">`；`vite.config.ts:89` 的 `input` 只有 `main: index.html` |
| ② | **脱出窗 / 漂移窗不挂壳 App**——它们是承载 `WebContentsView` 的宿主窗，池视图加载的是 `pool.html` | `electron/windows/window-manager.ts:205`（dev）/ `:209`（prod）；`pool.html:10` → `src/pool/pool-main.tsx` |
| ③ | **壳崩重建也只会有一份活的壳**——`rebuildShell()` 先 `createWindow()`（新壳起来）再 `oldWin.destroy()`，"旧的"是一个**已经崩掉的**渲染进程 | `electron/main.ts:359-368`；触发点 `electron/windows/crash-recovery.ts:155`（分支 2：壳渲染进程崩） |
| ④ | 🔴 **「主窗口关了、应用还活着」这个状态不存在**——主窗 `closed` 是**无条件 `app.quit()`**（连同脱出窗一起关），不是靠 `window-all-closed` | `electron/main.ts:342-351`（E5.8#43-3 / 2026-08-22 用户拍板）；另有 `:499-502` 的 `window-all-closed` 只是兜底 |

### 1.3 结论两条

**（一）不写 `if (!isMainWindow) return;` 守卫。** 它在本应用里**恒为真**——按仓库「无死代码」规矩不该写。原拍板（2026-09-12「走 (a) 主窗口独任」）的**方向不变**（调度者 = 主窗口那一份壳），只是"守卫"这个实现形式被更硬的证据替代：**独任性由架构保证，不由代码保证**。

**（二）「主窗口关闭 → 副窗口要不要不要接管」是空问题。** 依据事实 ④——主窗一关整个应用就退出，**不存在**"副窗口独自活着、调度器全没了"的时间段。原文（清单 `:2360-2361`）的实据写的是 `window-all-closed` 只在全部窗口关闭时才退出，**与源码不符**；按 E5.8#43-3 的拍板，副窗口期间**从不发生**。

> ⚠️ **仍然要做的**：多窗口**并存期间**（主窗 + 脱出窗同时开着）的**通知面唯一性**——更新条目只在主窗口铃铛面板出现，副窗口铃铛零未读。这条与调度无关，是既有定案（[03-插件市场/18-通知系统全账与设计定案.md](../03-插件市场/18-通知系统全账与设计定案.md) §八㉚）。
>
> ⚠️ **行为代价（记账，不遮）**：壳崩重建后新壳会重新 mount 调度器 ⇒ **30 秒首次延迟重新计时**。不额外补偿（补偿要跨渲染进程持久化"上次检查时间"，成本远大于收益）。

### 1.4 将来若真出现第二个壳——判据

前提 ② 唯一会失效的情况：**有人新增一个加载壳页面的窗口**（或让脱出窗去加载 `index.html`）。届时不补守卫就是真 bug（N 份调度器 + N 份通知）。届时**必须**：

1. **身份判据唯一来源**——判据要在**一处**定义、被调度器与通知面共同消费；**不许**用「窗口数」「是否首个窗口」「是否最后一个窗口」这类间接推断（这条是原拍板的实施注，保留）。
2. **正控 + 负控单测同批落地**：正控 = 主窗口身份下调度器**注册**了定时器；负控 = 非主窗口身份下**一次都不发** `update:checkForUpdates`（`console.warn` 之类不算——要断言通道**零调用**）。

**当前前提的自检命令（可随时跑，一行）**：

```bash
grep -l 'src/main.tsx' index.html pool.html preview.html packages/plugin-sdk/dev-host/index.html
```

**期望输出恰好一行 `index.html`。** 多出任何一行 ⇒ 前提失效 ⇒ 立刻按上面两条补真守卫（本归档 §1.3 的结论随之作废）。

## 二、下载失败重试

### 2.1 现状（已实现的部分）

| 项 | 现状 | 出处 |
|:--|:--|:--|
| 下载腿内的自动重试 | **刻意不做** | 01 §2.4 `:196` |
| 腿自持超时 | **30 秒空闲超时**（判据 = 「还有新字节吗」，不是总时长） | 01 §2.4 `:196` |
| 断点续传 | **不做** ⇒ 重试 = 删 `.part` 重头下 | 01 §2.4 `:196` |
| 手动重试入口 | 通知面条目 `[重试]` + 帮助菜单「检查更新…」 | 01 §2.4 `:196`、03 §2.2 |

**为什么腿里不自动重试（已定案，不复议）**：没有断点续传时自动重下 = 悄悄重复下载几十 MB，且把失败吞掉——与「失败必须出声」直接相反。

### 2.2 本次拍板（2026-09-12）

**本格（#57.9）只兑现「手动 `[重试]`」**；**自动重试立案 = #57.9g，实现未开工**。

### 2.3 🔴 待回答的问题（不许猜——#57.9g 开工前必须逐条有答案）

| # | 问题 | 为什么不是小事 |
|:-:|:--|:--|
| ① | **哪些错误类别可自动重试？** 六类归因（01 §2.3 / 07 §三）里 `network` 与 `rate-limited` 是自然候选；`checksum-mismatch`、404、磁盘满重试无意义 | 分类不生效 = 「全都重试」= 对确定性失败做无谓重下 |
| ② | **重试几次、间隔多少？** 固定间隔还是退避？上限之后怎么办（转手动？出声？） | 决定用户会不会遇到「一直在后台重复下载」 |
| ③ | **要不要出声？** 「失败必须出声」是已定原则 —— 自动重试期间是每次都出声、只最后一次出声、还是静默到放弃才出声？ | 出声多了是噪音，少了是偷偷吞失败 |
| ④ | **和手动 `[重试]` 怎么互动？** 用户手点之后，自动计时器要不要重置/退避？ | 两条路径同时发起会撞并发检查（主进程状态机拒绝，但用户看到的是什么） |
| ⑤ | **无断点续传的代价要不要兜？** 每次重试重下整包（几十 MB） | 要么接受，要么本任务连带做续传（会把任务放大一个量级） |

**候选方向（列出供决策，**未拍板**）**：
- **A** 永久不做自动重试（现状）——用户手点永远有反馈，实现零风险。
- **B** 有限自动重试：**仅** `network` / `rate-limited`，N 次 + 退避，每次都出声。
- **C** 只在「下载**中途**失败」自动重试一次；检查腿失败不重试。

### 2.4 判据草案（#57.9g 落地时必须能过；方向定了照此细化）

1. **单测·序列**——桩一个 §2.3① 判定为「可重试」的失败响应，断言重试序列的字面值：次数 / 间隔 / 出声次数。
2. **负控·分类真的生效**——桩一个**不可重试**类别（如 `checksum-mismatch` 或 404），断言**一次都不重试**。没有这条，① 就是空的（"分类"退化成"全都重试"也能让 1 过）。
3. **负控·上限真的生效**——连续失败到上限后**必须停**，且用户拿到可见出口（`lastError` + `[重试]`）。
4. **断网实测**——下载中途断网 → 恢复 → 观察是否按定案行为走（自动重下 / 或停在错误态等手点）。
5. **出声不吞**——按 ③ 的定案，断言用户可见的提示条数（不许"重试了但用户全程不知道"）。

## 三、失败记账里没有「谁发起的」——「后台静默」这条判据缺数据路径

### 3.1 判据已经这么写了，但路没通

[E6-执行清单](../E6-执行清单.md) **#57.12d** `:2414` 写着：「🔴 **后台（auto）检查失败不打扰**（静默回 `idle` + 记 `lastError`，下周期自试）；**只有手动检查才出这条**」。这句话要求通知面**能分辨**「这次失败是后台发的，还是用户手点的」——**当前分辨不了**：

| 环节 | 现状 | 出处 |
|:--|:--|:--|
| `context` 到检查腿就没了 | 形参**未被使用**（`_context` 前缀即证据） | `electron/services/update-source.ts:103` |
| 失败记账不带发起者 | `UpdateError` 只有 `code` + `message` 两槽 | `src/core/types/ipc/update.ts:84-88` |
| 广播形状 | 两条路都落 `idle + lastError`，**逐字节相同** | `electron/services/update-service.ts`（服务文件头铁律：两条路记账做得完全一致） |

⇒ 后台检查失败与手动检查失败，在壳侧拿到的**是同一个东西**（`src/hooks/useUpdateState.ts` 文件头已登记这条）。

### 3.2 后果——照现判据直写，两条错法各占一头

- 想「只有手动才出声」⇒ 只能**在壳侧猜**（例如用 ref 记「最近一次是谁发的」）——用户在后台定时器到期的同一秒手点，猜法必然错，**错的还是"用户点了但没反馈"那一侧**（最坏的一类）。
- 干脆都出声 ⇒ 用户没点过任何东西，突然收到「检查更新失败」= 噪音，与 01 §2.2「无网检查跳过错、静默」直接相反。
- 干脆都不出声 ⇒ 手动失败被后台规则吞掉，`[重试]` 出口永不出现。

### 3.3 候选方向（列出供决策，**未拍板**）

- **A**：`UpdateError` 加 `source: 'manual' | 'background'` 槽——发起者**随记账一起**落态，通知面直接读（改动面：07 §三 类型 + 服务记账点 + 壳文案分支）。
- **B**：态里加 `lastCheck: { context }`（每次检查都留回执）——语义更宽（成功也能知道是谁发的），改动面更大。
- **C**：后台失败**根本不进 `lastError`**（只写日志）——最省，但违反「下周期自动再试」要有账可依（01 §2.2），且**静默 ≠ 不记账**。

### 3.4 判据草案（#57.12f 落地时必须能过）

1. **正控**：后台检查遇 `network` 失败 ⇒ 通知面条目 **0 条**，且 `idle.lastError` **有值**（静默 ≠ 不记账——两者缺一，这条就是假的）。
2. **负控**：手动检查遇**同一个**错误 ⇒ **恰好 1 条**条目、带 `[重试]`。没有这条，正控在「什么都不做」的实现（后台手动都不出声）上照样能过。
3. **并发**：后台定时器与手点同一刻发起 ⇒ 忙态只跑一次（#57.4 既有判据），且结果按**发起者**归口——不许按「先到的那条」。
4. **前提自检（现在跑必然红，这就是立案证据）**：

```bash
grep -n "_context" electron/services/update-source.ts
```

修完必须让 `context` 在**失败记账路径**上真被读（不是加个 `void context;` 消警告）——判据 = 上面第 1/2 条能过。
