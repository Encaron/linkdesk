## 〇、本批收的对象——先把问题钉死

**这一类问题的定义（后面每一棒都用它）**：一个插件今天能用，明天宿主改了点什么，它就**悄悄坏了或悄悄丑了**。按「谁的名字被引用」分两个面，承诺强度**不一样**：

| 面 | 内容 | 强度 |
|:--|:--|:--|
| **插件能用的面** | `window.linkdesk.*` 的 API、`plugin.json` 的字段、插件自己的名字 | 🔴 **硬承诺，上架后不可拿走** |
| **宿主自己的内部标识** | 宿主 config key 名、宿主 CSS 类名、宿主 id 域 | v0 期可整理，但**有代价**（插件会借用/跟上） |

**为什么两个面都要管**：插件产物里**烘进了宿主与共享组件的名字**——`@linkdesk/ui` 的 JS（`className` 字面量）与 CSS 会被 inline 进插件自己的 bundle（实证：`settings` v1.0.13 的 `ldk-input` 计数 = 6 处自身 ＋ 2 处来自 ui，出现在 `index.bundle.js` 与 `views/SettingsView.bundle.js` 两个文件里）⇒ **宿主改一个类名，插件侧要「升依赖 ＋ 重打包」两件**，少任何一件 = **静默失样式**。

**三次静默丢样式的账（本批的存在理由）**：`.badge` 撞车（`settings` v1.0.9）· `.slider` scoped override 停止匹配（v1.0.10）· `.input → .ldk-input` 输入框丢底色/边框/圆角（v1.0.12 → v1.0.13）。三次都**零报错**，靠人肉发现。

## 一、真根因——三层，不是「谁起错了名」

- **层 1（机制）**：插件产物与宿主**共用同一套名字空间**（进程里扁平），而插件产物是**冻结的快照**——发布那一刻的名字被烘进 bundle，之后宿主怎么改它不会知道。
- **层 2（接口）**：依赖是**内联**的，不是运行时解析的 ⇒ 宿主改共享组件/宿主工具类的名字，插件侧的动作是**两件**（`npm update @linkdesk/ui` **＋ 重打包**），而**今天没有任何机械件提醒作者做这两件**。
- **层 3（守门）**：**没有任何门禁拦「删除或改名插件能用的面」**。实证：`contracts:check` 是 d.ts 生成**字节比对**（管「生成器与产物一致」），`scripts/check-api-contracts.mjs` 只管「文档不指向假命名空间」（防「文档指向一个不存在的命名空间」）——**两条都不拦删除**，今天就靠评审纪律。

**一句话根因（每棒收尾都要能复述这句）**：**宿主手里有一堆插件正在引用的名字，拿走它们没有任何机械阻力，也没有任何尺子量得出拿走之后谁的产物悬空了。**
