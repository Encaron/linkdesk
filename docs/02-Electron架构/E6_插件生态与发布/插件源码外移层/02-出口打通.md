# 7.1 出口打通——插件脱离壳工程可构建

> **任务号：** E6#98 · **前置：** 7.0（判据） · **产物：** 六只发货插件的依赖/构建自足 + `@src` 测试解耦 + JSON 插件的 pack 通道
> **一句话判据：** **在一个没有壳仓的全新目录里 `git clone <插件仓> && npm ci && npm run build` 能出 zip。**

---

## 〇、这一轮在解决什么

搬迁的物理动作很简单（`git filter-repo` + `mv`），**卡住搬迁的是「搬过去之后构建不起来」**。本轮把六只含构建产物的插件从「靠壳仓的安装结果才能构建」改成「自己声明一切」。

### 现状实测（2026-09-14 回源，[总档案 §1.1](00-整理档案.md) 是同一张表）

| 插件 | build 脚本 | import `@linkdesk/ui` | import `@linkdesk/contracts` | **声明了谁** |
|:--|:--|:--:|:--:|:--|
| file-tree | `node ../../packages/plugin-sdk/dist/bin.js build` | ✅ 5 文件 | ✅ 10 文件 | **无** |
| marketplace | 同上 | ✅ 14 文件 | ✅ 6 文件 | **无** |
| settings | 同上 | ✅ 6 文件 | — | **无** |
| editor | 同上 | — | — | `monaco-editor` `monaco-languageclient` |
| python | 同上 | — | — | `pyright` |
| serial-monitor | 同上 | ✅ 11 文件 | — | `@codemirror/{search,state,view}` |

🔴 **三处硬伤：**
1. **build 脚本是相对路径** ⇒ 离开壳仓立刻失效。
2. **`@linkdesk/ui` / `@linkdesk/contracts` 零声明**（`grep` 的命中全在 `description` 字符串里，不是 `dependencies`）——现在能跑**纯粹是靠根 `package.json` 的 `workspaces: ["plugins/*"]` + `"@linkdesk/ui": "file:./packages/linkdesk-ui"` 提升**。
3. **`serial-monitor` 最危险**：它 import `@linkdesk/ui`（11 个文件）却连 `description` 里都没提，**是六只里最不可能被发现的一只**。

## 一、依赖声明改造（六只逐只）

**目标形态**（照 `create-linkdesk-plugin` 模板的现行写法，它是唯一已经在用 npm 通道的样板）：

```jsonc
{
  "name": "linkdesk-plugin-<id>",
  "version": "1.0.0",          // ⚠️ 见 §六——这个字段本轮一并处置
  "private": true,             // 保持 private（不是 npm 包，只经 Release 分发）
  "type": "module",
  "scripts": {
    "dev": "linkdesk-plugin-sdk dev",
    "dev:real": "linkdesk-plugin-sdk dev --real",
    "build": "linkdesk-plugin-sdk build",
    "validate": "linkdesk-plugin-sdk validate",
    "lint": "linkdesk-plugin-sdk lint",
    "publish": "linkdesk-plugin-sdk publish"
  },
  "dependencies": {
    "@linkdesk/ui": "^0.1.4",              // ← 按实际 import 才加
    "@linkdesk/contracts": "^0.1.12"       // ← 同上
  },
  "devDependencies": {
    "@linkdesk/plugin-sdk": "^0.1.13",
    "@types/react": "^18.3.12",
    "typescript": "^5.6.3"
  }
}
```

**逐只清单：**

| 插件 | 加 `dependencies` | 加 `devDependencies` | 保留原样 |
|:--|:--|:--|:--|
| file-tree | `@linkdesk/ui` `@linkdesk/contracts` | `@linkdesk/plugin-sdk` `@types/react` `typescript` | — |
| marketplace | `@linkdesk/ui` `@linkdesk/contracts` | 同上 | — |
| settings | `@linkdesk/ui` | 同上 | — |
| editor | — | 同上 | `monaco-editor` `monaco-languageclient` |
| python | — | 同上 | `pyright` |
| serial-monitor | `@linkdesk/ui` | 同上 | `@codemirror/{search,state,view}` |

> ⚠️ **版本号要现查**，不许照抄本文档：`npm view @linkdesk/plugin-sdk version` / `@linkdesk/ui` / `@linkdesk/contracts`。本文写的是 2026-09-14 的实测值（0.1.13 / 0.1.4 / 0.1.12）。

**为什么用 `^0.1.x` 而不是精确锁**：作者侧要能吃到补丁（对齐 `create-linkdesk-plugin` 模板的 `^0.1.0` 口径）；真正需要锁死的可复现性由各插件仓自己的 `package-lock.json` 提供。

### 1.1 `plugin-sdk` 必须有 `bin` 入口

`linkdesk-plugin-sdk` 这个命令来自 `@linkdesk/plugin-sdk` 的 `bin` 字段。**落笔前先验**：`npm view @linkdesk/plugin-sdk bin` —— 若包在 npm 上**没有** `bin` 映射，那模板写法本身就是错的（模板可能从未在真仓外跑过 build）。**实测方式是本轮的验收动作之一**：在仓外临时目录 `npm i @linkdesk/plugin-sdk && npx linkdesk-plugin-sdk --help`。

## 三、`@src` 测试解耦（**精确到行，只有三处**）

全仓运行时源码**零** `@src` import（所有命中都是注释）。真耦合只有 file-tree 的两份测试：

### 3.1 `__tests__/FileTreeClipboard.test.ts:8` —— 真 import，换成本地最小桩

现状：

```ts
import { ContextKeyService } from "@src/core/registry/commands/ContextKeyService";
// E5#70e: 生产代码用 linkdesk.contextKey.set——测试环境 mock 回 ContextKeyService
function mockContextKey() {
  window.linkdesk = { ...(window.linkdesk ?? {}),
    contextKey: { set: (k, v) => { ContextKeyService.setValue(k, v); return Promise.resolve(); } } };
}
mockContextKey();
// 之后用 ContextKeyService.setValue("explorerResourceCut", false) 清残留
```

**处置：** 这个测试只用到 `ContextKeyService` 的「记 key→value」能力。改为插件内本地桩：

```ts
const ctxKeys = new Map<string, unknown>();          // 测试内最小桩
window.linkdesk = { ...(window.linkdesk ?? {}),
  contextKey: { set: (k, v) => { ctxKeys.set(k, v); return Promise.resolve(); } } };
// 清残留 → ctxKeys.clear()
```

**为什么这是对的（不只是「能跑」）**：插件本来就不该依赖壳的**内部实现**——生产代码走的是 `window.linkdesk.contextKey.set` 这条契约，测试却直连实现，**测试依赖越界了**。换成桩之后测试范围反而更准确：它验的是「插件调了契约」，而不是「壳的实现记住了」。

### 3.2 / 3.3 `__tests__/FileTreeModel.test.ts:28` 与 `:36` —— 疑似死 mock，直接删

```ts
:28  vi.mock("@src/core/services/files/FileService", () => ({ listDir }));
:36  vi.mock("@src/core/services/configuration/ConfigurationService", () => ({ getConfigurationValue, onDidChangeConfiguration }));
```

**同文件自带反证**：
- `:50` 注释：「E5#85 迁移桥接——**FileTreeModel 用 `lk.filesystem.listDir` 而非 `@src/core/FileService`**」
- `:48` 注释：「**E5#85 迁移后不再使用，保留兼容**」，而实际喂数据的是 `:52 window.linkdesk.filesystem.listDir = listDir`

**处置：** 删掉两条 `vi.mock`（连带 `:25` 的 `vi.hoisted` 若因此变孤儿）+ 跑测试。
**判据：** `npx vitest run plugins/file-tree` 全绿。
**若删不掉**（vitest 对无法解析的 mock 路径报错、或某处仍在消费）：说明不是死 mock，**退回 3.1 的同款处置**（本地桩），并在 commit message 里如实记「初判为死 mock 不成立」。

> ⚠️ **不许先删后信**——删完必须真跑一遍。判断「是不是死 mock」的证据是**测试真的过了**，不是注释说它不再使用。

## 四、🔴 十二只 JSON 插件缺一条 pack 通道（本层唯一「先造工具」项）

`bundled-plugins/` 18 个 zip = 6 只 React 型 + **12 只纯 JSON 型**（`lang-defaults` `lang-test-ja` + 10 只 `theme-*`）。

**问题：** 纯 JSON 型**没有 entry、没有 `.bundle.js`、没有 SDK build 步骤**。它们的 zip 现在由壳仓脚本 [`scripts/pack-bundled-plugins.mjs`](../../../../scripts/pack-bundled-plugins.mjs) 直接走目录树打包。

⇒ **它们搬出去之后没有产 zip 的手段**（壳仓的脚本不会跟着插件走）。

**要做（二选一，7.0 轮落笔时定）：**

| 方案 | 内容 | 取舍 |
|:--|:--|:--|
| **甲（推荐）** | 给 `@linkdesk/plugin-sdk` 补 `linkdesk-plugin-sdk pack` 子命令——把 `pack-bundled-plugins.mjs` 的目录树打包逻辑（含 [EOL 归一](../../../../scripts/lib/text-eol.mjs) + 固定 zip 时间戳）收进 SDK | 作者侧一条通道统一；**代价 = 改 npm 包 ⇒ 要走 SDK 的发版线**（bump + `check-npm-release` 基线） |
| 乙 | 12 只留仓内，只搬 6 只 React 型 | **不建议**——用户诉求是全部上架市场（不然 12 只主题/语言照样「卸了就没了」） |

**若取甲，必须同笔处理：** SDK 的 `pack` 与 `scripts/pack-bundled-plugins.mjs` 的**打包行为必须逐字节一致**（否则同一插件「壳内打的 zip」与「插件仓打的 zip」内容不同，内容指纹门禁会互相打架）。**判据 = 同一只插件用两条路径各打一次，指纹相等**（可直接复用 [check-bundled-version-bump.mjs](../../../../scripts/check-bundled-version-bump.mjs) 的指纹算法）。

## 五、LSP 链改造（python 搬走后基准要改）

壳仓有三处 LSP 相关脚本把基准指向 `plugins/python`：

| 文件 | 现状 | 处置 |
|:--|:--|:--|
| `scripts/check-lsp-deps.mjs` | 查 `plugins/python/node_modules/pyright` | 改基准为「当前 python 插件源码树的位置」——**用参数传入，不写死** |
| `scripts/check-lsp-smoke.mjs` | `--base <dir>`，dev 默认项目根 | 同上 |

**判据：** `npm run lsp:smoke -- --base <python 插件新位置>` 绿灯；`npm run check` 里的 `check-lsp-deps` 绿灯。

## 六、两处版本号不一致的处置（搬迁期最容易 bump 错的地方）

**现状：** 六只插件的 `package.json.version` **全是 `1.0.0`**，真版本在 `plugin.json.version`（1.0.6 / 1.0.28 / 1.0.5 / 1.0.9 / 1.0.4 / 1.0.8）。

**为什么本轮必须处理：** 搬成独立仓之后，`package.json` 是新人（和 AI）打开仓库第一眼看到的东西——**两个版本号并存且不一致，必然有人 bump 错那一个**。

**处置 —— ✅ 已定案（2026-09-14 用户拍板 = [09-命名规范.md](09-命名规范.md) 的 N6）**：

> 用户原话：「**关于这个 version 版本号，我建议加上，反正就是能规范就规范一点。**」
> ⇒ **取乙案**：**保留 `package.json.version`，并强制与 `plugin.json.version` 相等**（**不删**）。定位 = 版本号的**第四处锚**（既有三处 = `CHANGELOG.md` 段标题 ↔ `plugin.json.version` ↔ `versions[].version`，见 `09-插件目录规范.md:94`）。

| 方案 | 内容 | 取舍 | 结论 |
|:--|:--|:--|:--:|
| 甲 | 删掉 `package.json.version`（`private: true` 下 npm 允许缺此字段） | 最干净，但要实测 `npm ci` / SDK build 在缺 version 时是否正常 | ❌ |
| **乙** | 保留字段但**补机械门禁**：`package.json.version` === `plugin.json.version`，进 `npm run check` | 漂移**当场红**；无「缺字段会不会炸」的未知；且**给 `package.json` 的读者一条自证**（独立仓里它是新人/新 AI 第一眼看到的东西） | ✅ **取此** |

**规范落点 = [09-命名规范.md §5.1](09-命名规范.md)**（四处同源图 + 「改错那个 = 静默无效」的后果说明；**bump 判据引用 `version-bump` skill，不在此重述**——避免第二份真相源）。

⚠️ **不许「两处都改但靠人记得」**——本仓门禁哲学的原话是「**空喊『不许手抄』做不到，得给一条命令让人抄不了**」（[E6#42e](../E6-执行清单.md)）。

**判据：** 六只插件两处版本号一致；门禁进 `npm run check` 且有**负控**（人为改坏一处 ⇒ 红）；**`09-插件目录规范.md:94` 的「三处的锚」同笔改为「四处的锚」**（属 [10-作者文档族对账.md](10-作者文档族对账.md) 的 B 批——**文档不改 = 规范与实际不符**）。

## 七、🔴 身份显式化（E6#98g）——本轮**必须做**，否则搬迁会静默改掉插件 id

> 📖 完整论证与依据 = [09-命名规范.md](09-命名规范.md)（§二 病灶 / §四 VS Code 实测 / §六 迁移红线）。此处只给「本轮要动什么」。

**病灶一句话：** 插件身份 id 今天来自 `pluginId ??` **项目目录名**（`derivePluginId`，外加 zip 基名与安装目录名两处兜底），**而 `pluginId` 字段根本不在 schema 里**（`!!schema.properties.pluginId === false`）。**仓内 18 只一只都没显式声明**（`grep -l '"pluginId"' plugins/*/plugin.json` ⇒ 零命中），全在吃目录名兜底。

**为什么本轮必须做：** L7 恰好要把源码搬进**名字自由**的仓库与本地目录。身份靠目录名 ⇒ **仓库叫 `linkdesk-plugin-file-tree` 而 id 该是 `file-tree`，构建出的 zip 就把 id 兜底成了新名字**。后果五条、**条条不报错**（安装目录并存两份 / 墓碑对不上 / catalog 出现两个 id / 更新链静默断 / 插件数据看似丢失）。

**本轮动作（四步）：**

| # | 动作 | 注意 |
|:--:|:--|:--|
| 1 | **`pluginId` 进 schema** | `public/schemas/plugin.schema.json` + **三份拷贝同笔同步**（`check-plugin-schema-sync` 管 3 组 7 份，漏一份即红）；同时补进 `PluginManifest` 类型 |
| 2 | **官方 18 只全部显式声明 `pluginId`**（值 = **当前目录名**，逐只核对；12 只 JSON 型同样要写） | 🔴 **不许脚本批量替换**——批量=错位风险，且这批值必须与「用户已装的那份」对得上（老用户身份不能变） |
| 3 | **兜底收窄**：目录名兜底**保留**（向后兼容第三方老插件），但 `validate` 打黄灯提示「建议显式声明 `pluginId`」 | 不许直接删兜底——仓外已有第三方老插件在吃它 |
| 4 | **迁移红线入 [03-逐个迁移.md](03-逐个迁移.md)**：`pluginId` 落地前**一律不许改任何插件的目录名** | 见该档 §2.1 |

**判据：**
- [ ] 18 只 `plugin.json` 都有 `pluginId`，且值 === 原目录名
- [ ] 三份 schema 同步绿灯（`check-plugin-schema-sync`）
- [ ] 🔴 **负控**：把某插件**目录改名**后构建 ⇒ 其 `pluginId` **仍是声明值**（不是新目录名）
- [ ] 反向兼容未破：一个**不声明** `pluginId` 的老插件仍能安装（并收到黄灯提示）
- [ ] 装机后**安装目录名仍是原 id**（老用户身份未变）
