# 快捷键录制：已被壳占用的键录不进去（主进程拦截先于池插件）

> **待抉择池（已定位 · 修法已定 · 待排期）**——设置页「快捷键」里录制组合键时，**凡是壳自己已经占用的键，第一个键怎么按都录不上去**（用户原话：设 `ctrl+k;ctrl+l` 切语言，「第一个这个 `ctrl+k` 怎么都按不上去」），而 `ctrl+s` 这类**壳没占用的键**一按就进。
> 根因不在录制器：**主进程 `before-input-event` 路由命中即 `preventDefault()`，键根本没被送进池 WebView**，录制器的 `keydown` 监听自然一次都收不到。
> 2026-10-05 用户点单排查；2026-10-05 定位到回归点（2026-08-22 设置纯插件化迁移），修法与落点已定，**待 AI-2（第 2 波）提交后执行**。

---

## 定位

| | |
|---|---|
| 类型 | **壳侧真缺陷**（`electron/windows/keyboard-router.ts` 的拦截口径 ＋ 壳侧守卫到不了主进程） |
| 影响面 | **凡「被壳占用的键」都录不进去**——已占用的单键（`ctrl+shift+p`／`ctrl+b`／`ctrl+j`／`ctrl+w`／`ctrl+,`／`ctrl+1..9`…）与**所有双段键的第一段**（`ctrl+k`）。未占用的键（`ctrl+s` 等）正常 |
| 表现 | **静默**——不报错、不提示冲突，录制框就是「不理这个键」；连带的第二段也会被吞（见 §实证） |
| 涉及架构改动 | **零新 IPC 通道 / 零账本改动 / 零插件发版**——需要的信号（`setKeybindingCaptureActive`）**已经在既有代理通道里跑**，主进程只是没听 |
| 谁来修 | 壳源码 ⇒ 需要**一次软件版本更新**（PATCH）；插件侧不用动（源码 2026-09-14 已外移各自独立仓，改插件也只能治症） |

## 实证（2026-10-05）

### 一、复现与现象

| 操作 | 期望 | 实测 |
|:--|:--|:--|
| 设置 → 快捷键 → 编辑某命令 → 按 `ctrl+s` | 第一段进框 | ✅ 进 |
| 同上 → 按 `ctrl+k` | 第一段进框、等第二段 | ❌ **毫无反应**（键没到录制器） |
| 同上 → 按 `ctrl+k` 再按 `ctrl+l` | 落成 `ctrl+k ctrl+l` | ❌ 两键全无；2 s 内连按也一样 |

用户机的 `%APPDATA%\linkdesk\keybindings.json` 里就有 `theme.pick → ctrl+k ctrl+t`——**`ctrl+k` 在这台机器上必然是「前缀键」**（另外壳内置还有 `workbench.action.selectLanguage → ctrl+k ctrl+l`）。

### 二、链路（file:line）

1. 池插件调 `setKeybindingCaptureActive(true)`（录制开始）——**这一步是通的**，走 `IPC.plugins.call` 代理到壳，壳把 `_captureActive` 置位；但它**只活在壳渲染进程里**（见下）。
2. 用户按 `ctrl+k`。键盘事件先到主进程 `before-input-event`（挂在池 WCV 上）：
   - `electron/windows/keyboard-router.ts:116` `const hasModifiers = ki.ctrlKey || …` ⇒ `true`，**绕过**「无修饰键放行」那条（`:154` 的 `if (!hasModifiers) return;` 正是 `ctrl+s` 之外裸键还能用的原因）；
   - `:160-163` `if (keyCache.chordPrefixes.has(keyString)) { event.preventDefault(); …放壳; }` ⇒ **命中 `ctrl+k`（两条内置 chord 的第一段）⇒ 吞键**。
   - `event.preventDefault()` 的语义是 **Electron 不再把这次 keydown 投给聚焦的 WebView**。录制器的 `window.addEventListener("keydown", h, true)`（在设置插件 WebView 里）**从来不会被调用**。这就是「怎么都按不上去」——不是 UI 没画出来，是键没送到。
3. 第二半的伤害：吞键的同时主进程 `_chordState` 进入 pending（`CHORD_TIMEOUT = 2000`，`keyboard-router.ts:34`）并 `firstKey = "ctrl+k"`。随后按 `ctrl+l` ⇒ `:139-151` 命中 `keyCache.chordCombos.has("ctrl+k ctrl+l")` ⇒ 再次 `preventDefault()` ＋转发壳；壳侧 `dispatch.ts:35` 的 `if (_captureActive) return false;` 拦住执行 ⇒ **两键全废**，且录制器一直停在「等第一段」。

### 三、为什么现成的守卫救不了

录制器**确实**调了守卫——发货包里可查（`bundled-plugins/settings.linkdesk-plugin` 内 `SettingsView-CokVB58E.js`：`setKeybindingCaptureActive(!0)` / `(false)`，版本 1.0.31）。链路到壳也是通的（`src/core/services/plugins/IpcBridgeHandler/keybindings.ts:63-66` → `…/KeybindingRegistry/dispatch.ts:18`）。**断在最后一环**：

- `_captureActive` 是**壳渲染进程里一个模块级布尔**（`dispatch.ts:17`），只挡「已经送到壳的键」——壳的监听器 `mountGlobalKeybindings` 加在壳文档上。被主进程 `preventDefault()` 掉的键**压根到不了壳**，更到不了这个守卫。
- `electron/` 里 `setKeybindingCaptureActive` **只有两处 preload 纯透传**（`preload-shell.ts:466`、`preload-pool/namespaces-plugin.ts:102`），**主进程零消费方**。

⇒ 守卫的眼睛在壳里，拦截器在主进程，两者之间没有神经。**这是「单 WebView 时代的分工在多 WebView 时代失效」的又一例**（同族：`src/core/commands/input-bindings/shellKeybindings.ts` 里剪贴板键那段注释——「壳抢不了池的键」）。

### 四、为什么 `ctrl+s` 偏偏能用

全仓取证：`ctrl+s` **在被拦截表里根本不存在**——

| 取证面 | 结果 |
|:--|:--|
| 壳内置声明 `src/core/commands/input-bindings/shellKeybindings.ts` | 无 `ctrl+s` |
| `src/` ＋ `electron/` 全量 grep `"ctrl+s"` | 0 命中 |
| 随包 6 只插件（`bundled-plugins/*.linkdesk-plugin` 的 `plugin.json`） | 无 `ctrl+s` |

于是它走到 `keyboard-router.ts` 末尾「不是已知快捷键 → 放行给插件 WebView」⇒ 录制器照常收到。

⚠️ **这不是「`ctrl+s` 特殊」而是「未占用」**——把用户配置里的 `theme.pick` 改绑到 `ctrl+s`，`ctrl+s` 会**当场变成录不进去的键**。判据一句话：**录不进去 ⇔ 该键在主进程的 `shortcuts`/`chordPrefixes` 表里有位置**（表来自 `KeybindingRegistry` 的 `getKeybindingSyncData()`，`registry.ts:169-191`：`spaceIdx !== -1` 的取第一段进 `chordPrefixes`，其余整串进 `shortcuts`）。

## 建议修法（已定 · 未实施）

### A 案（选）：主进程按「视图」记一个「键盘直通」标志，由既有信号驱动

**核心洞察**：需要的信号**已经在跑**，而且**主进程已经看得见它**——

- 池插件的 `setKeybindingCaptureActive(x)` 走 `IPC.plugins.call`（`preload-pool/namespaces-plugin.ts:102`）⇒ 通道 `IPC.plugins.call` **本来就在 `PROXY_CHANNELS` 里**（`electron/ipc/ipc-bridge.ts:116`）⇒ 主进程在 `registerProxyHandlers()` 的循环里**已经收到**这次调用（`args[0] === 'setKeybindingCaptureActive'`，`args[1] === true|false`）。
- 同文件 `:77-80` 的 `hasNoRequestTimeout` **就是现成先例**：主进程已经在用 `String(args[0])` 嗅同一个通道的方法名。
- **`_event.sender` 正是发起调用的那个池 WebContents** ⇒ 直通标志天然就是**逐视图**的，不用另找身份映射。

⇒ **零新 IPC 通道、零 host-reserved 账本改动、零 contracts／AI 手册改动、零插件发版。**

改动清单：

| 文件 | 改动 |
|:--|:--|
| `electron/windows/keyboard-router.ts` | ① 模块级 `const _passthroughIds = new Set<number>()`；② 导出 `setKeyboardPassthrough(id, active)` / `clearKeyboardPassthrough(id)`；③ `handleBeforeInput` 在 `keyDown`／`isAutoRepeat` 早退之后**立刻**判 `if (_passthroughIds.has(viewId)) return;`（放行，不查表、不动 chord 状态机）；④ `attachKeyboardRouting` 闭包捕获 `view.webContents.id` 并传参；⑤ `view.webContents.on('destroyed')` 清标志 |
| `electron/ipc/ipc-bridge.ts` | `registerProxyHandlers()` 循环里加 `setKeybindingCaptureActive` 特判（照 `contextKey.set` 那段的写法）→ 调 `keyboard-router` 的两个导出 |
| `electron/windows/window-manager.ts` | 宿主窗 `blur` 时清该窗池视图的直通标志（见下「卫生要求 2」）——`registerPool` 里已有 `hostWindow.on('focus', onFocus)` 可并肩挂 |
| `electron/windows/keyboard-router.test.ts`（新） | 见 §任务 |

### 三个卫生要求（否则会以新形态复发）

1. **翻转「开」的同一时刻清掉已挂起的 chord**（`clearMainChord()`）——否则：上一次按 `ctrl+k` 留下的 pending 还在，用户进入录制后第一键就会被当「chord 第二键」吞掉，录制器看到的第一个键仍然不是它按的那个。
2. **两个清理点**：`webContents` 的 `destroyed` ＋ 宿主窗 `blur`。理由：录制器的「点外面取消」是 `document.addEventListener("mousedown", …)`（发货包实证），而 `document` 是**插件自己的文档**——用户点到插件 WebView **外面**（壳区域、别的视图）时它**不会触发**，取消分支的 `setKeybindingCaptureActive(false)` 也就不发 ⇒ **悬挂的 true** 是真实风险（此后该视图的所有快捷键永久失效）。`blur` 是主进程侧能拿到的最接近的兜底。
3. **逐视图隔离**：按 `webContents.id` 记，⛔ 不要用单个模块级布尔——多窗/多池下会把别的视图的快捷键一起放开。

### 排除的替代方案

| 案 | 为什么不选 |
|:--|:--|
| **B 新开一条专用 IPC 通道**（如 `keyboard:setPassthrough`） | 要动**整条账本链**（host-reserved 三账本 → `gen-host-reserved` → contracts → AI 手册 → 通道计数 176→177 那套），而这正是 **AI-2／AI-3 正在改的竞写资源**；而信号**本来就在既有代理通道里跑**（见上）⇒ 纯多余。**这是选 A 不选 B 最主要的现实理由** |
| **C 命中即转发但不 `preventDefault`** | 快捷键会「壳执行 ＋ 键照落池」双跑；池内编辑器/输入框会额外收到该键（键泄漏面更大），且与现有 `shouldDedup`／防抖语义打架 |
| **D 只改插件侧录制器**（录制时绕过壳表） | 源码 2026-09-14 已外移各自独立仓 ⇒ 改在插件里只能治录制器**一处症**（file-tree 行内重命名消费同一信号，同病照旧），且要走插件发版链 |

### 刻意**不做**（超范围，另案）

池 → 主进程的**通用「可编辑焦点」上报**。`shellKeybindings.ts` 里 2026 年就留了这条 TODO（「若未来要为池内控件加剪贴板快捷键，必须让池上报焦点（池→主进程 editableFocused 信号），而非在壳注册——壳抢不了池的键」）。本件**只做「录制/捕获态」这一条既有信号**的接线，⛔ 不顺手扩成通用焦点上报（那是另一件事、另一套影响面）。
