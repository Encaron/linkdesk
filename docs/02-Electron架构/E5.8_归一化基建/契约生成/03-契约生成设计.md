## 0. 背景与问题定式

Phase 4 要解决的不是「没有契约」——`src/core/api/linkdesk-api.ts` + 10 域接口已是**精确到方法签名**的契约（40 命名空间）。真问题是三个：

| # | 问题 | 实证 | 后果 |
|:--|:--|:--|:--|
| **P1** | 契约是**手写**文件，双端实现与它零机械关联——「对齐靠纪律」 | preload 双端 import 的全是 `src/core/types/ipc/*` wire 载荷类型，`linkdesk-api` 只在**注释**里被引用（preload-shell.ts:18「wire 契约归口」注释、contextkey.ts:22 注释） | 漂移 3 处存活/潜伏（D1 env.get 丢 pluginId / D2 clipboard.readText 壳缺 / D3 dialog.openFile 壳缺），无任何检查拦截 |
| **P2** | 插件无合法消费路径——只能偷 `@src/core` 类型 | 违规 import 实测 **10 文件**（7 运行时 + 3 测试，见矩阵 §5） | 违反插件独立铁律；契约消费路径不通 = 第三方作者没法安全地拿到类型 |
| **P3** | 消费形态未定——第三方作者拿什么？ | docs/03-插件制造/01-插件API契约.md 是第二份**手写**真相源（#22 文档面） | E6「10 分钟第一个插件」前置缺失；文档与代码两套真相源漂移 |

**解法定式**：P1 → 双端实现 import 契约类型 + `satisfies`（tsc 即门禁，漂移编译期死）；P2 → 生成单文件 `linkdesk.d.ts` 作唯一对外消费面，插件全改走它；P3 → 文档面收敛为指针。

## 1. 标注语法选型——三路线评估 → 拍板

README 与审视收口要求评估三路线：**标记注释（A）vs 显式注册表（B）vs 契约类型文件为源（C）**。

### 1.1 路线 A：标记注释（dsh Typert 模型）

在契约源上加标记注释（如 `@remote`），生成器解析注释产出 d.ts。dsh 的 Typert 生成器正是这个形态（host 侧 `@Remote` 标注 → 生成 client 声明 → contracts-ready 门禁）。

- **为何否**：我们的契约**已经是精确 TypeScript**——方法签名、泛型、联合类型、可选面全在接口里，tsc 全程检查。再加标记注释 = 在同一层语义上叠加第二层语法，生成器还要写注释解析器（文本脆弱、报错难查）。标记注释的价值在「从实现反推契约」——我们是「契约已经写好、只缺对齐与分发」，恰好不需要反推。dsh 抄纪律不抄形态。

### 1.2 路线 B：显式注册表

另建一个注册表文件，枚举 40 命名空间的方法签名，生成器遍历注册表产出 d.ts。

- **为何否**：若注册表独立于 linkdesk-api.ts → **三份真相源**（注册表 + 契约 + 实现）互相漂移；若注册表**取代** linkdesk-api.ts → 把 40 命名空间用注册表语法重写一遍 = 纯返工，还丢掉接口自带的结构检查、IDE 补全、跨类型引用（`LinkDeskCommand`/`PluginListEntry` 等 13 独立接口 + wire 类型全是接口树，注册表语法表达不了泛型/联合/可选/交叉）。
- **一个有用的碎片要留**：注册表里的「每面必须暴露哪些命名空间」清单是**有用的**——它就是矩阵 §2 的覆盖矩阵。但这只是支撑数据（谁必须有什么），不是签名真相源。落成 `surfaces.ts`（§3.2）。

### 1.3 路线 C：契约类型文件为源（推荐）

**linkdesk-api.ts 已是精确契约，就让它当唯一真相源。** 不重写、不标注、不注册——只做三件事：

1. **双端机械对齐（零生成器）**：preload-pool.ts / preload-shell.ts 的 expose 对象 `satisfies` 契约派生面类型（`PoolExposed`/`ShellExposed`）。**tsc 即门禁**——契约加方法而池漏暴露 → 编译红；壳缺必选面（D2/D3 类型）→ 编译红。
2. **薄生成器只打包**：TS compiler API 沿契约类型图递归收集全部依赖类型（10 域接口 + types.ts 13 接口 + wire 类型 17 源文件），内联成一个**自包含单文件** `contracts/linkdesk.d.ts`（无 `@src/core` 引用，第三方作者拷走即用）。
3. **消费面唯一化**：插件只从 `@linkdesk/contracts`（路径别名 → linkdesk.d.ts）取类型；`@src/core` 在插件内全禁（ESLint 收紧，§7）。

**证据支撑**：

| 判据 | 路线 C 表现 |
|:--|:--|
| 机械对齐成本 | 最低——`satisfies` 两行，纯 tsc |
| 生成器复杂度 | 中——类型图打包 ~150 行，无新依赖（typescript 已是 devDep） |
| 真相源数量 | 1（契约源）+ 1 生成物（d.ts）+ 1 支撑清单（surfaces.ts）——零冗余 |
| 第三方消费体验 | 单文件 d.ts，拷贝 + tsconfig 一行 |
| 与现有代码摩擦 | 契约源原位保留，壳内 17 处消费方（src/pool/hooks/components/global.d.ts）零改动 |
| 过度工程风险 | 最低——不发明语法，不另起注册表 |

> **拍板点 1**：推荐 **路线 C**。

## 3. 契约源治理

### 3.1 linkdesk-api.ts 去留定案

**保留为生成源 + 壳内实现类型。** 理由：

- 17 处壳侧消费方（src/pool/zones/main、hooks/usePoolSync、components/shared/context-menu、global.d.ts、mockLinkdesk 等）**已依赖它**——搬走 = 大爆炸重构，零收益。
- 它已经天然是「壳内实现类型」与「对外契约」的同一文件——拆两份才制造漂移。
- `getLinkDesk()`/`linkdesk` 运行时导出是壳侧便利封装，保留（插件不用它——插件拿 `window.linkdesk` 环境变量直调）。

**唯一新增**：文件头注释加一行「本文件 = 契约生成源，产物 contracts/linkdesk.d.ts；改契约必须跑生成器（check-contracts 强制）」。

## 4. 薄生成器设计（#19 实施）

### 4.1 机制

`scripts/generate-contract.mjs`，用 **TypeScript compiler API**（devDep 已有，零新依赖）沿契约类型图递归收集 → 内联 → 单文件 d.ts。不做语法发明，只做「把接口树打包成可拷走的一份」。

```
输入（契约源 + 其 import 链）：
  src/core/api/linkdesk-api.ts            （聚合器，入口）
  src/core/api/linkdesk-api/*.ts          （10 域接口 + types.ts 13 接口）
  src/core/types/ipc/{serial,keyboard,bridge,dialogs,poolActions,search,tabActions,sidebarActions,events}.ts
  src/core/types/pool/{poolLayout,poolToast,poolQuickPick,poolDialog}.ts
  src/core/types/fileEntry.ts
  src/core/registry/commands/{KeybindingRegistry,MenuRegistry}.ts   （仅取 Keybinding/ManifestMenuItem 及其依赖）
  src/core/services/{files/FileService,layout/WorkspaceService}.ts （仅取 FileChangeEvent/WorkspaceFolder）
        ↓
产出 contracts/linkdesk.d.ts（自包含单文件，零 @src 引用）：
  export type LinkDeskAPI = ...（40 命名空间交叉）
  export type { LinkDeskCommand, LinkDeskTheme, ..., PluginListEntry, ... }  （13 + DialogOpenOptions）
  （内联的全部 wire 类型：OpenPortConfig / FileChangeEvent / PluginStateChangedPayload / ...）
  declare global { interface Window { linkdesk: LinkDeskAPI } }    ← ambient 收口
        ↓
产出 contracts/.contract-hash（源文件内容 hash，check-contracts 比对用）
```

### 4.2 双面签名校验件

`#19` 要求「生成器产出双面签名校验件」——即 §3.2/§3.3 的 `satisfies`（生成器不另产文件，它就是 tsc 门禁本身；surfaces.ts 由生成器负责校验其与矩阵一致，或 #19 时用脚本对拍一次矩阵 §2 清单）。

### 4.3 linkdesk.d.ts 内容规则

- **纯类型**：不含任何运行时实现（无 `getLinkDesk`/`linkdesk` 值导出——那是壳内封装，第三方作者用 `window.linkdesk`）。
- **自包含**：全量内联，无 `import ... from "@src/..."` / `"../src/..."`——第三方作者拷一个文件进项目即完整类型。
- **ambient 收口**：`declare global { interface Window { linkdesk: LinkDeskAPI } }` + `export {}`——作者项目里 `window.linkdesk` 直接有类型，无需额外 global.d.ts。
- **独立可跑通（#19 验收）**：生成物单独 tsc 零错误；改动契约源一处 → 重跑生成 → `git diff contracts/linkdesk.d.ts` 可见。

> **拍板点 3（消费形态）**：生成物落 `contracts/linkdesk.d.ts`（仓库根，与 src/ 平级）；插件消费走 tsconfig `paths: { "@linkdesk/contracts": ["./contracts/linkdesk.d.ts"] }`；第三方作者 = 拷贝该文件 + tsconfig `types`/导入一行（docs/03-插件制造 提供下载指针）；插件模板内置 = E6「10 分钟第一个插件」落地时模板自带。独立 npm 包 `@linkdesk/contracts` 留出版基建成熟后（当前仓库内单文件 + 文档下载已覆盖全部真实场景，npm 包是发布层问题不是契约问题）。
