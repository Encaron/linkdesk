## 0. 判据（三方共识的尺子）

1. **文件夹 = 一种东西**（同性质）；**文件对 = 一个单位**（同名 .tsx + .css 相邻 = 你的 C 里 LCD_1_69/src+inc 的等价物）
2. **宽度阈值 ~15**：一个夹里超过约 15 个单位且性质混杂 → 按语义/职责分组
3. **问题在宽度不在层数**：前端惯例层深 3-4 层是健康的，不要为加深而加深
4. **不建冗余包装夹**：`IconBarZone/IconBarZone.tsx` 这种夹名=文件名的包装盒零信息量（除非该单位要长成多文件模块）
5. **一起改的文件放一起**（co-location）：界面+样式+测试同夹，不搞全局 src/css/tests 三类分离（Codex 强调，Claude/AI-2 同意）

## 1. core/services（✅ 三方共识——23 文件混堆，一次性按子系统分 6 夹）

**现状（2026-08-16 实锤）**：23 个 .ts 平铺，混了真 Service（19 个）+ 引导器 AppInitializer + 引擎 LayoutEngine/ThemeEngine + 工具 toast——四种性质一个抽屉，超宽度阈值。

**目标**：

```
services/
├── bootstrap/       AppInitializer, ErrorService, FactorySlots
│                    （启动管线 + 全局错误入口 + 系统插槽）
├── configuration/   ConfigurationService, ConfigurationApplier, StorageService
│                    （配置三层合并 + 应用管道 + 持久化原语）
├── files/           FileService, FileSearcher, EncodingService, FileAssociationService
│                    （文件 I/O 唯一入口 + 搜索 + 编码 + 扩展名映射）
├── layout/          LayoutEngine, LayoutService, ViewContainerService, WorkspaceService
│                    （布局权威 + 布局持久化 + 侧栏容器 + 工作区状态）
├── plugins/         PluginStateService, ProfileService, IpcBridgeHandler
│                    （插件私有存储 + 场景快照 + 壳侧 IPC 桥）
└── ui/              DialogService, NotificationService, toast, LogChannel, ThemeEngine, ClipboardService
                     （对话框 + 通知 + Toast + 日志频道 + 主题引擎 + 剪贴板）
```

**影响面（已摸底）**：外部 import 约 60 处（relative + `@src/core/services/` 两态混合）；`core/index.ts` barrel 同步更新。纯移动零逻辑改动，tsc×2 + vitest 全绿兜底。

**现状**：8 个组件 + `executePoolCommand.ts`（命令执行）+ `viewDragProtocol.ts`（拖放协议）混堆。

**目标**：

```
pool/

│                     + PoolPluginIcon + PoolSectionStack + PoolStatusBarComponent
│                     + PoolToolbarSlot + ErrorBoundary）——同性质，宽度健康，不建夹

单文件目录符合壳目录规范反模式表「正确目录宁可只有一个文件」——语义正确优先于文件数。

## 3. pool/zones（⚠️ 分歧——三版并排，拍板选一）

**现状**：14 文件 = 6 对 + 2 单文件（FloatingLayerHost、MainZone），8 个单位平铺。

| | A 版：平铺保持（Claude 推荐） | B 版：一次建夹（AI-2） | C 版：渐进建夹（Codex） |
|:--|:--|:--|:--|
| 做法 | 不动。8 对同名排序天然成对 | 8 个 zone 各建一夹（icon-bar/、sidebar/…），tsx+css 入夹 | 存量平铺不动；**新增 zone 一律建夹**；存量哪个 zone 下次要大改（加测试/子组件）时顺手迁 |
| 理由 | 单位=文件对（2 文件一个职责），8 对 < 15 阈值；加 zone 三步法（layout 字段 + 文件对 + Shell div）就是扩展路径；建夹=重复名包装盒 | 与用户 C 心智一致（一界面一夹）；未来 zone 长多文件有位置 | 不为了好看动存量（import 改动风险换不来收益）；新结构从新代码开始自然生长，spec 只需写"新增规则" |
| 代价 | 用户心智上"平铺=没分类"的观感保留 | 移动 14 文件 + 改 ~15 处 import + spec/测试同步（一次机械活） | zones 夹里新旧两种形态并存一段时间（spec 记明"存量平铺/新增建夹"） |

**三方收敛点**：components/ 与 pool/ 的边界漂移另案处理（规范更新决策，未拍板）；本任务只定**内部形态**。

  ```

      SettingsView.css
      SettingsView.test.tsx
      sections/            ← 功能复杂后再拆子目录

- **AI-2 版（建夹）**：存量 13 个单位立即按组件建夹。
