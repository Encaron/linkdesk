# 插件间事件契约（声明式发布/订阅）

> **状态：待抉择**（2026-11-25 立案）· 归属：通用能力底盘（轴二「高频数据流」＋ 轴三「连接/端点登记」）
> **一句话**：让插件之间**声明式地**发布与订阅领域事件（如「打卡数据已更新」「设备已接入」），跨插件联动不再靠外部 AI 轮询搬运。

## 一、证据（实测缺口）

- 本次实机验收里，**AI 能做的联动是编排式**：读 A 插件数据 → 调 B 插件命令（可行，已验证）；
- 但**做不到「A 一变就推给 B」**：没有通用事件面。串口只有自己的 `dir:tx/rx` 推送，属插件私有；
- 因此「打卡数据 → 串口送到物理屏」目前必须由 AI 每一步搬运：延迟、易漏、不可无人值守。

## 二、设计

**声明面（manifest，唯一真相源）**

```jsonc
"contributes": {
  "events": {
    "publishes": [{ "id": "demo.checkin.updated", "returns": [{ "name": "date", "type": "string" }] }],
    "subscribes": [{ "id": "demo.checkin.updated" }]
  }
}
```

- 事件 `id` 全局唯一（约定 `pluginId.eventName`）；
- `publishes[].returns` = 载荷字段表（与命令 `returns` 同一形状/校验口径，⛔ 第二套 schema）；
- 订阅是**声明**，装载时由宿主登记；⛔ 壳里按插件名特判。

**运行面（宿主事件总线，一份）**

- 插件侧 SDK：`emit(eventId, payload)` / `on(eventId, cb)`（类型由 manifest 生成，导出面归 C）；
- 宿主侧：鉴权（发布者只能发自己声明过的 id；订阅者只能收已声明的）、顺序（按订阅登记）、**背压/丢弃策略引用轴二**（定义具名策略，⛔ 每插件自造）；
- 可审计：每次发布/投递进账本（来源、事件 id、条数、丢弃数），`log` 可读。

## 三、判据（对 07 准入表）

- **归一化**：事件总线一份；载荷形状用 `returns` 同一套字段表，⛔ 新 schema。
- **无硬编码**：壳不认识任何业务事件名；全部来自 manifest 声明。
- **无死代码**：未声明订阅的插件收不到事件（默认关闭），不做"影子通道"。
- **高内聚低耦合**：发布/订阅双方只依赖事件 id 与载荷字段表，不互相 import。
- **AI 友好化**：`describe` 输出 `events` 段（可发现）；事件投递进 `log`（可审计）。

## 四、边界（⛔ 越界）

- ⛔ 不是 `stream`：本契约不定义帧格式/分隔符/长度前缀（轴二另案）。
- ⛔ 不做请求-响应语义（那是命令，`exec` 已有）。
- ⛔ 不做跨设备/跨进程广播到外部网络（只在本机插件间）。
- ⛔ 不替代权限轴：订阅仍受插件能力声明约束（与权限系统对齐，⛔ 另造授权）。

## 五、验收

1. **端到端**：打卡插件 `emit("demo.checkin.updated", …)` → 串口插件（或虚拟屏插件）订阅后自动上屏，**外部 AI 不参与搬运**；
2. 未声明订阅的插件**收不到**（负控）；
3. 发布者发未声明的事件 id ⇒ 被拒并有码；
4. `describe` 可见 `events`；`log` 可见投递记录（含丢弃）；
5. 跨领域：换一个非硬件订阅方（如通知/便签）同样成立。

## 六、不做的代价

- 跨插件联动只能靠 AI 逐步搬运 —— 慢、易漏、难无人值守；
- 各插件会自建私有通道（callback/全局变量），形成 N 套真相源。

## 七、依赖与排期

- 依赖 **设备会话契约**（[03](03-设备会话共享契约.md)）：`device.added/removed` 是首批事件之一；
- 与权限系统对齐：订阅/发布是否需要能力声明，实现前一次对齐，⛔ 两套授权。
