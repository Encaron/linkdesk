## 一、一句话账（为什么会有这一件）

**左下角那个齿轮，图标是设置插件的，菜单却是壳的——两件事被一根隐式的线（"谁坐在底部"）糊在了一起。** 用户 2026-09-30 连问四轮把它问穿了；这一夹是把问穿的结果、修法、和它对未来的意义一次归档。

### 1.1 用户四问（2026-09-30）

| 轮 | 用户问 | 查清后 |
|:--:|:--|:--|
| 1 | 「左下角齿轮是谁的？是设置这个插件的吗？」 | **图标是设置插件的**（它唯一的 `appearsIn.iconBar: "bottom"`）；**菜单和菜单里每一条都是壳的**。 |
| 2 | 「为什么齿轮能显示很多菜单项？有的是设置插件的、有的是其他插件的？」 | **纠正：一条都不是插件的。** 齿轮里现有 8 条全是壳（`APP_PLUGIN_ID = "app"`）注册。 |
| 3 | 「难道无脑声明在'设置'这个图标中显示自己的配置项就行？位置/名字都无所谓？」 | **半对**：菜单槽确实是**名字契约**（任何插件可写 `contributes.menus.extensionGear`，与提供者/位置无关——E5.7#64 有意设计）；但**齿轮图标**恰恰相反，是**位置耦合**的。 |
| 4 | 「只要在图标栏底部声明了图标，就会显示这一堆菜单项，对吗？一旦任意插件也想在底部声明就会出问题？」 | **成立**（收窄一个字：**形态一**插件会出问题，形态二不会——判定见 [01-设计 §一 · 1.7](./01-设计.md)）。 |

### 1.2 用户由此看出的设计问题

不在"齿轮该归谁"，而在**"归谁"这件事从来没有被当作一个设计决定**——它是被"谁碰巧坐在底部"偷偷决定的。用户原话的意思是：

> 齿轮是个**集成菜单**（设置、主题、DevTools、将来的配置文件、将来的 GitHub 登录全都是它的条目）。它天然属于壳——条目来自多个来源、要能引用别人才有的东西（配置文件 UI 可能就做成插件）、而且必须恒在（换设置 UI / 换市场都不该动它）。**可现在这个定位没有落到实现里。**

### 1.3 用户举的"会怎么炸"（**尚未实机复现，如实记**）

用户举的场景：「**哪天把设置插件卸了 / 删了，发现那个图标没了**」。

查证结论：**这是隐患，不是已复现的现场**。设置插件是 `core: true` 的出厂件（`bundled-plugins/settings.linkdesk-plugin` v1.0.23，`seed: true`），默认永远在 ⇒ 今天看不出问题。但机制上它必然如此：

- 齿轮图标**只因为**设置插件声明了 `iconBar: "bottom"` 才存在；
- 按 `factoryRole` 换一套第三方设置 UI（**这是明确支持的能力**，见记忆 `settings-plugin-replaceable-ui` / `factory-role-coexistence`），若那套**没声明底部图标** ⇒ **齿轮整个消失**；
- 同理，一旦第二只插件（形态一，不填 `factoryRole`）为正经理由声明 `bottom` ⇒ 它的点击**不开自己**，而是弹出壳的齿轮菜单，底部还会并排出现**两个**齿轮。

> ⚠️ 上一条是**据代码推出的**（`IconBarZone.tsx:178-186` 的 `default → bottom` ＋ `:220-226` 的 `isBottom → 弹齿轮菜单`），**本轮未实机造现场**。接手 AI 动工前，建议先按 [01-设计 §五 · 5.3](./01-设计.md) 的反向对照造一次现场，把"隐患"变成"读数"。

### 1.4 用户拍板的方向（已定，不是待拍）

**齿轮归壳；底部回归成普通位置。** 设置插件终局形态（用户原话）：

> 最后设置插件就变成一个**没有自己图标栏图标**、但**入口在齿轮里**的插件。

⚠️ 一处措辞要拧准（见 [02-概念 §二](./02-概念-插件入口两条道与配置文件插件.md)）：设置插件**不是"把自己声明进齿轮"，而是"不再占位、把入口还给壳"**。前者会把耦合从"位置"搬到"菜单声明"，同一个病换个地方。

### 1.5 为什么这件事值得单独立夹

因为它是**一把钥匙**，不是一个小 bug：

1. **设计档早就写了"归壳"，实现只做了一半**——[`06-E3f-壳UI收尾.md:588-603`](../../../02-Electron架构/E3_多WebView与壳收尾_暂定/06-E3f-壳UI收尾.md) 原话「位置：图标栏底部 ⚙ 按钮。**永远可见——不依赖任何插件**。归属：核心…**换 marketplace 不影响此齿轮**」；[`02-E3b-主题引擎跨进程.md:142`](../../../02-Electron架构/E3_多WebView与壳收尾_暂定/02-E3b-主题引擎跨进程.md) 还专门堵过质疑：「**这是 Encaron 的设计，不是违规。**」⇒ 本件是**把设计补完**，不是改设计。
2. **它决定未来能不能顺畅往齿轮里加东西**——用户 2026-09-30 原话：「处理好设置插件，未来齿轮中显示新东西才会通顺」。通顺的不是"齿轮能塞新东西"（这个今天就能塞，file-tree 正在往壳的 ☰ 菜单里塞），而是**"位置不再暗夺归属"**。
3. **它顺手给"配置文件（Profiles）插件"备好了参考**——用户明确要求本夹把配置文件的概念一起写下来，将来他给做配置文件的 AI 一句话即可：「看看 04 里做设置那部分的那份档，里面对于配置文件有详细描述」。**做这件时另外查出一件重要的事**：配置文件的能力**壳侧早就实现完了却没有入口**（`ProfileService.ts` 399 行 ＋ 五维验证，全仓零消费方），而 `switchProfile` 会**禁用/启用插件** ⇒ 今天**某套 profile 不含设置插件时齿轮就会消失**（[01-设计 §二](./01-设计.md) 前后对照表末行）。本件因此不只是"整理归属"，还**堵住了一条真实可达的齿轮消失路径**。

### 4.1 发版口径（用户 2026-09-30 拍板）

- **软件轴（壳）：攒批，不发版**——用 dev 版跑测试即可，省掉 tag → CI 出安装包 → Release 资产 → 实机「检查更新」装一遍那一整条链。`package.json` 版本号**不动**（`check-changelog-section` 只管「版本号推进必有 CHANGELOG 段」，不 bump 即不触发）；但**改 `src/` 的提交仍必须带 `feat:`/`fix:` 前缀**（`check-version-bump` 只看首行前缀，不看有没有 bump）。
- **设置插件轴：仓内源码与件 1 同批改，「发布」押后到壳发版同批**。理由两条：① 本夹开头那条「两侧必须同批」；② **单独发的两个坏结局**——`minAppVersion` 只能指向一个**还没发布**的壳版本（市场对现有壳全显示「不适配」，发出去没人能装），或者不抬 `minAppVersion`（旧壳用户升级后设置插件**整个加载失败**）。
- **npm 包轴（`@linkdesk/contracts`）：照发**——契约形状变了（`IconBarLayout.owned`），`npm run check` 的 `contracts:check` 是字节比对、必须重生成；`check-npm-release` 现挂**黄灯**（作者面内容自 npm `v0.1.27` 起漂移）⇒ 按「升版本 + `npm publish` + `npm run release:mark`」走。
- ⛔ **不许动 `bundled-plugins/` 种子**（除非插件真发布且被官方目录收录）：`check-bundled-version-bump` = 内容变了必 bump 插件版本、`check-bundled-freshness` = 种子须与官方目录最新一致——动它必红。**dev 验件 2 走 `{userData}/plugins/settings/plugin.json` 手改**：boot 装种子是版本幂等的（同版本跳过、不覆盖），所以手改能存活。
