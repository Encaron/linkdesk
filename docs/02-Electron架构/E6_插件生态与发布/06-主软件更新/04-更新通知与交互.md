## 一、触发时机（何时弹 toast）

| 场景 | 行为 |
|:--|:--|
| 后台发现更新（周期/启动） | 弹发现更新 toast（§二） |
| 下载中 | 更新该 toast 消息为进度（§三） |
| 下载完成 | 更新为「重启」toast（§四） |
| 用户点「立即更新/重启并更新」 | 对应 toast 按钮触发（§二/§四） |
| 用户点 TitleBar 更新按钮 | `update.openUpdateFlow` 按状态分支（available→下载 / downloaded→重启）→ 进度走 toast（03 §4.3 三态：下载更新 → 更新中 → 重新启动，主题按钮色） |
| 手动检查无更新 | toast「当前已是最新版本」 |
| 检查/下载失败 | toast 错误（TOAST_TTL_ERROR） |

## 二、发现更新 toast

**恒全显**（🔴 2026-09-10 修正：初稿写的「默认折叠、点 ⋁ 展开」**已随 `ToastHost` 一起作废**——E6#71h 定案「两态删除、恒全显」，消息与 actions 常驻，用户不必先找展开箭头）：

```
┌──────────────────────────────────────────────┐
│ (⬇图标) LinkDesk 有可用的更新 0.2.0       ✕   │   ← 主行：icon 16px + message
│  来源: 主软件更新    [查看更新内容] [立即更新] │   ← 来源行 + actions（常驻，不再折叠）
└──────────────────────────────────────────────┘
  （通知面板内；面板只此一处，无第二个浮层）
```

**调用：**
```typescript
pushToast({
  message: i18n.t("LinkDesk 有可用的更新 {{version}}", { version: "0.2.0" }),
  severity: "info",
  source: "app.update",   // 生产者身份 id（壳域 app. 前缀，app = 既有 APP_PLUGIN_ID）；人类可读名「主软件更新」不写进 source，由通知面按来源名机制解析（见 E6#73g）
  isCloseAffordance: true,   // 用户点 × → 该版本更新提示不再弹（Don't show again，现成机制）
  actions: [
    { label: i18n.t("查看更新内容"), isPrimary: false, onClick: () => openReleaseNotes("0.2.0") },
    { label: i18n.t("立即更新"), isPrimary: true, onClick: () => downloadUpdate() },
  ],
  ttl: 0,                     // 持久——直到用户选择/下载开始；或长 ttl（TOAST_TTL_INFO）
});
```

**「稍后」语义（用户权利保障）：**
- 点 × 关闭 → `isCloseAffordance` 持久化 → 该版本更新提示不再自动弹（用户想查 → 菜单「检查更新…」手动，恒显）。
- 这就是「用户有权一段时间不更新」的实现——**自动弹一次，尊重关闭，手动入口永在**。
- 想要彻底安静：设置 `app.update.mode = manual`（不自动检查，手动才查）。

## 三、下载进度（一条条目复用，逐帧改写）

> 🔴 **订正（2026-09-12，E6#57.12 实现后回填）**：本节旧文给的调用示例**照抄会做不出来**——
> 进度那条不是「push 一条、之后 `updateToast` 改字」，而是**从发现那条一路 `replaceToast` 换过来**；
> 且 `updateToast(id, message, percent?)` 是 `replaceToast` 的**薄封装**（`toast.ts:330`），
> **只能改 message + percent 两个字段**，装不了 actions、也清不掉 `progress` 旗标。
> 真身 = `src/hooks/useUpdateNotifications.ts`（本格唯一生产者）。下面按实现重写。

```
┌──────────────────────────────────────────────┐
│ (sync图标) 正在下载更新 42%                   │   ← 主行 message 逐帧改写（replaceToast）
│  ▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░  42%                │   ← 4px 真进度条（percent 字段）
│  来源: 主软件更新                 [后台运行]   │   ← 「后台运行」只收掉本条，见下方 🔴
└──────────────────────────────────────────────┘
```

**调用（真进度条能力已于 E6#71i 落地）：**
```typescript
// 进度条目 = 从「发现」那条 replaceToast 过来，**同一个 id**（E6#73f 原子替换；dismiss+push 会闪会换位）
function progressEntry(version: string, percent: number): void {
  ensureEntry(version, {
    ...progressPatch(percent),      // percent >= 100 → { message: t("正在校验…"), percent: undefined }
    source: SOURCE,                 // = `${APP_PLUGIN_ID}.update`，**不是字面量 "app.update"**（见 §八 偏差 5）
    progress: true,                 // 4px 真进度条就靠它；也是「进行中」的定义（见 §八 偏差 6）
    wake: false,                    // 🔴 不可省缺省，见 §八 偏差 1
    isCloseAffordance: false,       // 🔴 不可省：从「发现」替换过来会继承它的 true，见 §八 偏差 2
    actions: [{ label: t("后台运行"), isPrimary: false, onClick: () => { /* 只收本条 */ } }],
    ttl: 0,
  });
}
// 进度事件（独立通道，不跟 stateChanged 走）→ 节流 ≤500ms 逐帧改写
//   非壳环境 / 未挂载 / 条目已被收掉 ⇒ updateEntryIfLive 一律**只改不建**
//   （用户在进度中点「后台运行」就是要它消失，500ms 后自己长回来 = 那个按钮没用）
```

> **进度条 UI 已实现，不再「留未来」**：`percent` 非空时通知面板画 **4px 真进度条**（确定态按 percent 填充 / 不定态扫动）——E6#71i 落地、E6#72c 在宽面板上定型、**E6#73k 由 3px 加粗到 4px**。本档直接用它，**不新造任何进度 UI**。
> 🔴 **阶段切换必须显式传 `percent: undefined`**（进「校验/解压」这种无百分数的段）——**留着上一段的 42% 不动会被读成卡死**（01 §2.4 同款约定）。
> 🔴 **「后台运行」不会收起面板**（旧文 :88 的注释「= 关面板」**是错的**）：全仓 `notif:*` 通道全是**池→壳**单向（`notif:panel` / `notif:dismiss` / `notif:clearAll` / `notif:action` / `notif:cancelJob`），**没有壳→池的关面板通道**。该按钮的真身 = `notif:action` 分发器**无条件** `dismissToast(id)` ⇒ **只收掉这一条**，面板保持打开。要真收起得新开一条通道 + 池侧接线，那是新能力，不在本格。

## 四、下载完成 / 重启

```
┌──────────────────────────────────────────────┐
│ (⬇图标) 更新已下载，重启后生效            ✕   │
│  来源: 主软件更新         [稍后] [重启并更新] │
└──────────────────────────────────────────────┘
```

> 🔴 **订正（2026-09-12，E6#57.12 实现后回填）**：旧文给的 `updateToast(id, t("更新已下载，重启后生效"))`
> **做不出本节这张图**——`updateToast` 只能改 message + percent（见 §三 订正），而完成条目要的是
> **两个 actions + 退出进行中**（`progress: false` + `percent: undefined`，撤掉 4px 条）。
> 且旧文 `[稍后]` 的注释「**状态回 idle**，不重下」**是错的**，2026-09-12 用户拍板：**「稍后」不动状态**。

**调用：**
```typescript
// 完成条目同样是 replaceToast 复用同一个 id——多数时候它就是「进度」那条换过来的
function pushDone(version: string): void {
  ensureEntry(version, {
    message: i18n.t("更新已下载，重启后生效"),
    source: SOURCE,
    isCloseAffordance: false,   // 🔴 本条消息里**没有版本号**，抑制键却是 `${source}::${message}` ⇒
                                //    设了它 = 「关一次，此后所有版本的完成提示全部静音」（见 §八 偏差 3）
    actions: [
      { label: i18n.t("稍后"), isPrimary: false, onClick: () => { /* 只收掉本条，状态原地不动 */ } },
      { label: i18n.t("重启并更新"), isPrimary: true, onClick: () => { void restartToUpdate(); } },
    ],
    ttl: 0,
    progress: false,            // 退出进行中（撤 4px 条 + 放行「清除已完成」与 ×，见 §八 偏差 6）
    percent: undefined,
  });
}
```

**「稍后」= 只收条目，状态原地不动**（2026-09-12 用户拍板，与旧稿相反）：
- 状态**保持 `downloaded`**——安装器已在盘上等着装了，把态降回 `idle` **只会让用户重下一遍**。
- 顶栏按钮**仍显示「重新启动」**，随时可再触发（不是「关掉就没了」）。
- 🔴 由此推出 **#57.12g**（已在 `electron/services/update-service.ts` 落地）：`downloaded`/`ready`
  **免疫检查**——检查腿比的是 `latest > current`，已下好的版本必然还大于当前版本 ⇒ 一查必判
  `available` ⇒ 界面从「重新启动」退回「下载更新」。两个态**必须**被 `checkForUpdates` 的忙碌守卫挡住。

**重启流程（无新 UI——toast 直驱）：**
1. 点「重启并更新」→ `restartToUpdate()` → 主进程 `quitAndInstall()`。
2. 主进程 `app.relaunch` + `app.quit()` → 安装器静默覆盖 → 重启。
3. **无 3s 倒计时弹窗**（那是新造 UI）——toast 点击即执行；误点风险低（「重启并更新」是主按钮，用户主动点）。
4. 重启后首启自动弹发行说明（05 §2.5）。
5. 🔴 **装不上必须自己收住异常**：`notif:action` 的分发器是「`onClick(); dismissToast(id)`」的**同步**调用，
   onClick 返回的 promise **无人 await** ⇒ 漏出去就是一条 unhandled rejection，用户侧是「点了没反应」。
   `restartToUpdate` 因而自带 `try/catch` → `reportError`（通用一句话，不复刻腿的归因句——结构化 `detail`
   过 IPC 后被 Electron 重包成普通 Error，见 §八 偏差 8）。

## 五、手动检查反馈

| 结果 | toast |
|:--|:--|
| 已是最新版本 | `pushToast({ message: t("当前已是最新版本"), source: SOURCE, ttl: TOAST_TTL_SUCCESS, **wake: true** })` |
| 检查失败 | `pushToast({ message: t("检查更新失败：{{error}}", { error: t(err.message) }), severity: "error", source: SOURCE, actions: [{ label: t("重试"), onClick: … }], ttl: TOAST_TTL_ERROR })` |
| 有更新 | 同 §二 发现更新 toast（**但不由本条路出**，见下） |

> 🔴 **`wake: true` 显式写**（2026-09-12 用户拍板）：默认唤醒白名单只认 `severity === "error"` ∨ 带按钮，
> 「已是最新」两者都不是 ⇒ 不显式打开就只会让铃铛数字**悄悄 +1**（而且它 5 秒就没了），
> 用户点了「检查更新…」却像什么都没发生。这是对白名单的**窄口径覆盖**——只此一条，不动
> `defaultWake` 表达式本身（动表达式会把内存墙、一切 warning 一起算重要）。
>
> 🔴 **「有更新」这一格不由本表的路出**：`available` 态无论来自后台定时器还是用户手点，
> 都走**同一个状态迁移** ⇒ 发现条目归**迁移驱动**那条路（`useUpdateNotifications` 的状态 effect）。
> 若发起方也顺手出一条，同一个 `available` 就会出**两条**。被 × 关过的版本也不会因此复活
> （`isCloseAffordance` 抑制在 toast store 里，且发现条目的消息**带版本号**，逐版本生效——见 §八 偏差 3）。
>
> 🔴 **失败/已最新两格的归属 = 发起方自消化**（本格核心设计，见 `useUpdateNotifications.ts` 文件头）：
> `idle + lastError` 在「后台查失败」与「手点查失败」下**逐字节相同**（`UpdateError` 只有 code+message
> 两槽，检查腿实测 `context` 不分支）⇒ 想「后台静默、手动出声」就**不能从态反推**，只能**谁发起谁消化**
> ——发起方（命令 handler / 调度器 / `[重试]` 按钮）天然知道自己的身份，`context` 一个布尔同时管
> 「透传给腿」和「说不说话」两件事，**不许分头判断**。
> 反面同样成立：**不许在壳侧用 ref 记「最近一次是谁发的」去猜**——后台定时器到期与用户手点撞在同一秒时，
> 猜法必错，且错的正是「点了没反馈」那一侧。

### 🔴 两条只在源码里、图上永远看不出来的结构事实

- **`progress` 旗标是「进行中」的定义**（`isPending`）：带它的条目，面板**不画 ×**、`notif:dismiss` 与
  `notif:clearAll` 都**跳过**它。所以「完成」那一步**必须显式 `progress: false`** 退出进行中——
  漏了这一句，用户既关不掉也清不掉那条完成提示。
- **进度帧只改不建**（`updateEntryIfLive`）而**完成帧会重建**（`ensureEntry`）：这不是不一致，
  正是「后台运行要能真的收起」与「完成提示必须能等到」两个要求各让一步的结果。改任一侧都会踩到另一侧。
