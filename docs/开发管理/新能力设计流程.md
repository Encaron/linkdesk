# 新能力设计流程（Design Flow for New Capabilities）

> **适用面**：任何新控件 / 新 API / 新能力 / 新方法 / 新插件——全项目唯一设计前置规范。
> **2026-08-27 用户拍板**：「设计必须有一套流程」——立流程，让未来任何 AI 遵循，搞 skill + 机械审查。
> 根因：每个能力在实现期临时摸索 API/配置/显示/通信 → 总有没想到的维度 → 反复返工。

---

## 一、为什么立这条流程（返工根因）

历史教训：每次立项只写「缺口 + 方案方向」，没有规范流程逼设计期想透以下维度——API 怎么放、配置谁给、显示在哪、通信走哪、插件侧怎么组织、壳侧放哪个目录、有没有保底 UI。实现期临时摸索必然遗漏维度 → 返工。

**流程 = 把设计期该想的问题，变成立任务前的强制检查清单。** 设计与实现分离：先按 8 维度回答完设计，再写代码。

---

## 二、流程阶段（立任务 → 实现 的强制步骤）

```
① 立项     任务条目先写「设计前置」——按 8 维度清单回答（一段设计摘要 + 关键决策）
② 设计审查  AI 调用 design-flow skill 逐维度审查方案（软性但全面）
③ 实现     代码满足硬约束 + 归一化 + 概念键分离
④ 机械审查  npm run check 自动拦截可机械判定的不变量（硬性，见 §五）
```

任何一步没走完就写代码 = 违反本流程。

## 三、8 维度设计清单（设计前置必答）

### ① 能力边界
- 这是**壳能力**还是**插件能力**？（核心准入三条件：多提供方 / 多消费方 / 桌子不知道内容）
- **保底设计**：没有插件时，有没有保底？——主题无插件也有 dark/light 保底、图标无插件也有 codicon 保底。壳能力永远先答这个。

### ② API 设计
- 要暴露给插件吗？什么命名空间/方法？（`window.linkdesk.*`）
- 契约在哪定义？（contracts/linkdesk.d.ts + src/core/api/linkdesk-api/）
- 通用优先：先复用已有 API，缺了才新加（memory `api-preference-existing-first`）。
- 新 API **必须**在 03-插件制造 文档说明（用户明确要求）。

### ③ 通信方式设计
- 插件↔壳走哪条通道？（IPC preload 桥 / 配置注册表 / 事件广播 / 命令）
- 数据流：谁产生、谁消费、谁持久化？
- 铁律：插件通信全走 `window.linkdesk.*`，禁止 import @src/core（memory `plugin-communication-standard`）。

### ④ 壳侧代码设计
- 放哪个目录？（壳目录规范——core/services / components/shared / App/config…）
- **单一权威**在哪？（键清单 / 来源，防两份漂移；概念键分离——不同概念不共用同一键）
- 硬约束合规（颜色走 var / 文字走 t() / 插件 ID 不硬编码 / 路径走 getAssetPath）。

### ⑤ 插件侧代码设计
- 走哪个贡献点？（contributes.*——themes / iconThemes / views / commands / languages…）
- 目录结构、虚构实例怎么组织（测试 fixture 用虚构名，硬约束 21）。
- **插件独立铁律**：第三方作者永远不需要壳改代码（memory `plugin-independence-iron-law`）。

### ⑥ 显示设计
- **在哪里显示**？（哪个 UI 位置——顶栏/侧栏/主区/状态栏/设置页/浮层）
- **怎么显示**？（控件类型——卡片/下拉/滑杆/分段/取色器；壳共享组件优先）
- **显示什么**？（数据来自哪——API / 配置 / 事件）

### ⑦ 配置设计
- 配置项 key？（`app.*` 或插件命名空间）
- 设置页**哪一组**出现？（group 分节）
- **配置是壳给还是插件给？**——壳给 = 保底 UI 必然存在；插件给 = 丰富但可缺（如主题插件给配色、壳给保底配方）。显隐/枚举/默认值/复位语义一并定。

### ⑧ 代码规范 + 验收
- 命名/注释/测试卫生、归一化（同概念单写法）、无死代码。
- 验收：`npm run check` 全绿 + CDP 实机 + 用户视觉验收（高风险必实机门禁）。

## 五、机械审查设计（可机械判定的不变量，进 `npm run check`）

对标 E5.7 静态卫生（--max-warnings 0）+ #130 CSS 审计门禁先例。三项（E5.8#137 已落地，全在 `npm run check`）：

### 5.1 新 API 契约四齐全（audit-api-contracts，对标 ipc-audit）
新增 `window.linkdesk.*` 方法必须**四件套齐全**，缺一红灯：
1. contracts/linkdesk.d.ts 类型声明 —— `contracts:check` 字节比对门禁（#21，已有机）
2. preload 实现（namespaces-*.ts）—— `satisfies PoolExposed/ShellExposed` tsc 形状门禁（#20，已有机）
3. 主进程分发（IpcBridgeHandler）—— 同上 tsc 面约束（已有机）
4. 03-插件制造 文档说明 —— **流程层强制**（设计前置 + design-flow skill）：01-插件API契约.md 是**指针式**（E5#85→E5.8#22 有意决策，方法明细指向 d.ts，不手写第二份真相源），机械无法判「新 API 该不该入文档」；机械管**反向漂移**——文档引用的 `linkdesk.<ns>` 必须真实存在于 live 契约（`check-api-contracts.mjs`，实证抓到 E5.7 残留 `window.linkdesk.data` 陈旧引用）。

### 5.2 新配置项保底（audit-config-baseline）
新增 `app.*` 配置项必须：`registerConfiguration` 声明 + 保底默认值（无插件也成立）+ 设置组归属。机械 = `check-config-baseline.mjs`（appearance.ts + startup.ts 每个 `"app.*": { }` 块必须有 `default:`）。

### 5.3 新贡献点三件套（audit-contributes）
新增 `contributes.*` 必须：plugin.schema.json 字段 + 加载器消费 + 文档说明。机械 = `check-contributes.mjs` 三条不变量：live schema（public/schemas）字段 ⊆ 03-插件contributes规范.md 说明 + docs 拷贝 schema == live（防两份漂移，实证抓到 5 vs 16 陈旧拷贝）+ 字段在 src/+electron/ 有消费方。

## 六、验收总则

1. 每个新能力先交「设计前置」方案（8 维度）再写代码——任务条目可见。
2. skill 与机械审查随清单 Phase 11.21 逐项落地。
3. 未来 AI 立新任务时对照本流程自查；机械层红灯必须修到绿灯才提交。
