## 一、VS Code 对标证据（源码实证）

### 1.1 updateService 状态机（9 态判别联合）

> 来源：`src/vs/platform/update/common/update.ts`（VS Code 源码，WebSearch 实证 2026-08-30）

```typescript
// VS Code 状态机——判别联合（discriminated union），每个状态 = 对象 + 唯一 type 判别字段
export const enum StateType {
  Uninitialized = 1,
  Disabled = 2,
  Idle = 3,
  CheckingForUpdates = 4,
  AvailableForDownload = 5,
  Downloading = 6,
  Downloaded = 7,
  Updating = 8,
  Ready = 9,
}

export const State = {
  Uninitialized(): State { return { type: StateType.Uninitialized }; },
  Disabled(reason: string): State { return { type: StateType.Disabled, reason }; },
  Idle(update: IUpdate | undefined): State { return { type: StateType.Idle, update }; },
  CheckingForUpdates(context: boolean): State { return { type: StateType.CheckingForUpdates, context }; },
  AvailableForDownload(update: IUpdate): State { return { type: StateType.AvailableForDownload, update }; },
  Downloading(update: IUpdate): State { return { type: StateType.Downloading, update }; },
  Downloaded(update: IUpdate): State { return { type: StateType.Downloaded, update }; },
  Updating(update: IUpdate): State { return { type: StateType.Updating, update }; },
  Ready(update: IUpdate): State { return { type: StateType.Ready, update }; },
};
```

关键设计：
- **状态 = 数据 + 判别字段**——UI 只 switch `type`，不 if-else 猜状态。
- `IUpdate` = 版本信息负载（version + commit + releaseNotes URL 等）。
- `Updating` 态是**中间态**：下载完成 → 准备重启 → 发出 `Updating` → 进程重启。

### 1.2 update.mode 配置（VS Code 四档 → LinkDesk 简化两档）

> 来源：`src/vs/platform/update/common/update.config.contribution.ts`（VS Code 源码实证）

VS Code 原版四档：`none / manual / start / default`。**LinkDesk 简化两档（2026-08-30 用户拍板）**：

| mode | 自动检查（启动+周期） | 手动检查 | 说明 |
|:--|:--:|:--:|:--|
| `auto` | ✅ | ✅ | 默认——后台定期检查，发现更新自动 toast |
| `manual` | ❌ | ✅ | 仅手动——用户点「检查更新」才查 |

> **为什么砍 `none`**：用户拍板「检查更新选项永在，若是最新版本就显示『当前已是最新版本』」——一个永在的入口不需要「完全禁用」档。最接近「完全不更新」的档 = `manual`（不自动打扰，想查随时查）。**砍 `start`**：启动检查可并入 `auto`（auto 本就含启动后首查），多档无收益。

### 1.3 检查时机（默认定期后台）

对标 VS Code 默认行为（仅 `auto` 档）：
- 启动后延迟 30s → 首次后台检查（避开启动争抢，对标 VS Code `_autoCheckDelay`）。
- 之后每 4 小时一次（对标 VS Code `_autoCheckTimer`）。
- 有更新时不弹窗打扰——直接 toast（见 04）。

### 1.4 更新 URL 构造（GitHub Releases 直连）

> 来源：`src/vs/platform/update/common/update.ts` `UpdateService` 的 `getUpdateUrl`

```
${updateUrl}/api/update/${platform}/${quality}/${commit}
```

- `platform` = win32 / linux / darwin（+ arch）
- `quality` = stable / insider
- `commit` = 当前 commit 哈希（product.json 注入）——**服务端拿 commit 判断「你比最新落后几个」**
- 无更新 → HTTP 204 空响应
- 响应体：`{ version, commit, timestamp, url, name, productVersion, hash, signature }`

### 1.5 发行说明

> 来源：`src/vs/code/electron-main/app.ts` + `src/vs/workbench/contrib/update/browser/releaseNotesEditor.ts`

- 发行说明按版本号拉取 `https://code.visualstudio.com/raw/v{version}.md`，本地按版本缓存（userData 下）。
- 检测到 `pkg.version !== lastVersion`（首启新版本）→ 自动打开内置发行说明 tab。
- 可关：`Update: Show Release Notes` 设置。
- 失败（离线/404）→ 降级为通知条提示，不打扰。

## 二、LinkDesk 设计——主进程 UpdateService（自研）

### 2.1 状态机（对标 VS Code，简化适配）

```
Uninitialized → Disabled（更新源不可用）
             → Idle
Idle ──checkForUpdate──▶ CheckingForUpdates ──新版本──▶ AvailableForDownload
                     │                                   （无更新 → 回 Idle）
                     └──错误──▶ Idle（带 lastError，UI 显示错误信息）

AvailableForDownload ──download──▶ Downloading ──完成──▶ Downloaded
                                      （失败 → 回 Idle + lastError）
Downloaded ──提示重启──▶ Ready（toast「重启并更新」）
                        ├─ 用户点「稍后」 → Idle（保留 update 信息，不重下）
                        └─ 用户点「重启并更新」 → Updating ──quitAndInstall──▶ 进程退出重启
```

TS 类型（完整见 [07-数据流通格式.md](07-数据流通格式.md) §四）：

```typescript
export type UpdateState =
  | { type: 'uninitialized' }
  | { type: 'disabled'; reason: string }
  | { type: 'idle'; update?: UpdateInfo }
  | { type: 'checking' }
  | { type: 'available'; update: UpdateInfo }
  | { type: 'downloading'; update: UpdateInfo; progress: { transferred: number; total: number; percent: number } }
  | { type: 'downloaded'; update: UpdateInfo }
  | { type: 'updating'; update: UpdateInfo }
  | { type: 'ready'; update: UpdateInfo };
```

### 2.2 检查频率（内置常量，不暴露配置项——2026-08-30 拍板）

| 时机 | 行为 | 说明 |
|:--|:--|:--|
| 启动后 | 延迟 30s 首次后台检查 | 避开启动争抢（对标 VS Code `_autoCheckDelay`）；仅 `auto` 档 |
| 每 4 小时 | 后台检查一次 | 对标 VS Code `_autoCheckTimer`；仅 `auto` 档 |
| 手动 | 帮助菜单/齿轮菜单「检查更新」 | 即时检查（`checkForUpdate(context: true)`）；两档都有 |
| 无网 | 跳过，静默 | 不打扰；下次周期自动再试 |

### 2.3 更新源（GitHub Releases 直连）

**更新源 = 官方 GitHub Releases**（`encaron/linkdesk` 仓库的 Releases）。不造第二套存储——与 E6#29 插件市场同基建（同是 GitHub Releases），但**轨道独立**（壳更新 ≠ 插件更新）。

> 🔴🔴 **2026-09-12 补——本节的可行性前提：仓库必须是公开的。** 上面这个 URL 与下面的 asset 下载，**在私有仓库下一律读不到**（GitHub 对未认证调用方返回 404；错误类别还会被归成误导性的 `not-found`——明明只是私有，报的却是「仓库不存在」）。**令牌不是解法**：令牌得随安装包发到每个用户手里，等于把能读全部私有代码的钥匙公开。**用户 2026-09-12 拍板：`Encaron/linkdesk` 转 PUBLIC**（同型先例 = 插件侧的公开仓库 `Encaron/linkdesk-marketplace`）。⚠️ **转公开前必须扫凭证**——已扫（2026-09-12）：跟踪的 `.npmrc` 仅 registry/mirror 配置、零字面量令牌，全树 `ghp_`/`npm_`/`_authToken`/私钥特征串零命中，全分支历史无 `.env`/密钥文件 ⇒ 干净。清单落点 = [E6-执行清单.md 第 5.4 轮前置](../E6-执行清单.md)。

```
更新元数据 URL（对标 VS Code /api/update 接口，自研轻量版）：
https://api.github.com/repos/encaron/linkdesk/releases/latest
```

响应 → 提取 `tag_name`（SemVer，如 `v0.2.0`）→ 与当前 `app.getVersion()` 比对：

| 比对结果 | 行为 |
|:--|:--|
| `latest > current` | 有更新 → `AvailableForDownload` → 发现更新条目（04 §二） |
| `latest <= current` | 无更新 → Idle（手动检查时条目「当前已是最新版本」） |
| 请求失败（见下表六类） | Idle + lastError；**只有手动检查才出声**，后台静默仅记账 |

> 🔴 **2026-09-11 扩写——失败必须分类，不许塌成「未知错误」**（第 3.5 层教训：报错指向错误的方向 = 用户和 AI 都找不到真因）。原稿只写「离线/仓库不存在/超限」三类，且把「asset 缺失」和「tag 不是 SemVer」两件**完全不同**的事漏掉了——这两类恰恰在发布侧出事时最常见：
>
> | code | 触发 | 文案要点 |
> |:--|:--|:--|
> | `network` | 不可达 / 超时 / 代理未生效 | 提示检查网络（⚠️ 本腿**必须走 `electron/services/main-fetch.ts`**——全局 `fetch`(undici) 不读 Windows 系统代理，Chromium `net.fetch` 才读。E6#76） |
> | `rate-limited` | GitHub API 403/429（`x-ratelimit-remaining: 0`） | 「稍后自动重试」，**不要**说成网络故障 |
> | `not-found` | 仓库不存在 / 无 Release（404） | 指向发布侧配置问题 |
> | `invalid-response` | JSON 结构非法 / 缺 `tag_name`/`published_at` | 响应格式异常 |
> | 🔴 `asset-missing` | **Release 拿到手了，但找不到匹配 asset**（命名漂移，如实际叫 `LinkDesk-Setup-0.2.0.exe`） | **「找到新版本但安装包缺失」**——**不许报成 network** |
> | 🔴 `version-unparsable` | `tag_name` 不是合法 SemVer（`v1.0`、`release-0.2.0`） | **与「无更新」分开报**——静默忽略会让发布事故隐形 |

**Release asset 约定**（发布流程沉档）：

```
Release tag:       v0.2.0
Asset 命名:        linkdesk-setup-0.2.0.exe     ← NSIS 安装器（Windows 首个目标平台）
附加元数据:
  - 发行说明正文（Markdown）→ 05-发行说明.md 数据源   ← 进 Release body
  - 校验值 sha256 → 下载后校验                          ← 🔴 不额外附：读 asset.digest（GitHub 服务端自动算）
```

> 🔴 **2026-09-12 订正（E6#57.15b 落笔时实证）**：上面那行原写「**附加元数据（Release body 或 asset 旁）: checksum sha256**」——**已作废**，发布侧**无事可做**。GitHub 为每个上传的 asset **服务端自动算** `digest` 字段（`sha256:<64hex>`），直接读即可；**API 里没有 `checksum` 字段**（实读 `repos/electron/electron/releases` 的 asset 键集）。唯一真值表见 [05-文档与发布/02-发布流水线.md §1.5](../05-文档与发布/02-发布流水线.md)，**那条陷阱（照字段名取 `asset.checksum` ⇒ 恒 `undefined` ⇒ 校验静默失效）写在 §1.5.1**。

> ⚠️ **`asset-missing` 的根因就是上面这行约定被漂移**——asset 名一旦大小写/分隔符变了，判定那一侧（`linkdesk-setup-{version}.exe` 精确匹配）就找不到。**两侧必须引用同一份约定**：发布侧（#57.15b）与消费侧（#57.5a）的命名规则**只能有一处真值**，不许各写一份字符串。

### 2.4 下载与校验

- 下载器：主进程流式下载 → 落 `{userData}/update/linkdesk-update-{version}.exe.part`。
  - 🔴 **出网实现必须读得到 Windows 系统代理**——走 **Chromium `net` 模块**（`net.request`/`net.fetch`），**不要**用 Node `http`/`https` 或全局 `fetch`（undici 不读系统代理 ⇒ 用户开代理时「检查更新看得见、下载必失败」）。元数据腿走 `electron/services/main-fetch.ts`（E6#76），**二进制流这条腿用同一套代理语义**，别两套。
- 进度上报：`Downloading` 态带 `progress`（transferred/total/percent）→ IPC 广播 → 壳渲染 `updateToast(id, msg, percent)` 循环改文字 + **4px 真进度条**（04 §三；E6#71i 落地 / E6#73k 加粗）。
  - ⚠️ **阶段切换时 `percent` 必须显式传 `undefined`**（进「校验/解压」这种无百分数的段）——留着上一段的 42% 不动会被读成卡死。
- 校验：下载完成后按 **`asset.digest`**（GitHub 服务端自动算的 sha256，**先剥 `sha256:` 前缀**）校验，不符 → 删除 + 报错（Idle + lastError，code `checksum-mismatch`）。⚠️ **不许写成 `asset.checksum`**——API 里没这个字段，照名字取会恒 `undefined` ⇒ 每次都降级放行、校验静默失效（05-文档与发布/02-发布流水线.md §1.5.1）。
  - **边界（2026-09-11 补齐）：Release 未附 checksum 时怎么办** —— 定为 **记 `checksum-unavailable` 并降级放行**（理由：Release 是我们自己发的，缺 checksum 是发布侧疏漏，不该让用户装不上更新；同时记账，发布侧能看见）。**此决定与 #57.15b（checksum 附 Release）配对**——发布侧漏附 = 消费侧降级，两侧都能发现。
    - 🔴 **这笔账落 `downloaded.warning`（2026-09-12 用户拍板 ⇒ 三选一取 (a)「给状态加 warning 槽」）**。⚠️ 本行原先写「同时 **lastError** 记账」——**落不了地**：带 `lastError` 槽的态只有 `idle`，而放行时状态走的是 `downloaded`；用户直接点「重启并更新」根本不经过 `idle` ⇒ 照旧类型实现这笔账**必然被无声丢掉**（发布侧永远看不见自己漏附了校验值 = 拍板想要的效果归零）。语义分界：`lastError` = 这次**没成**，`warning` = **成了**但有件事该让发布侧知道。
- 完成：rename 为正式 `linkdesk-update-{version}.exe` → `Downloaded`。

**残留清理（2026-09-11 从一条扩成两条——原稿只管 `.part`，`.exe` 无人管）**：

| 扫什么 | 处置 | 为什么 |
|:--|:--|:--|
| `{userData}/update/*.part` | **删除** | 下载中退出不留垃圾（对标 01-GitHub-Releases方案.md §四·五 插件下载临时文件惯例） |
| 🔴 `{userData}/update/linkdesk-update-*.exe` | **按版本方向三分支**：<br>① 版本 **≤ 当前运行版本** → **删除**<br>② 版本 **> 当前** → 保留（正常 `Downloaded`）<br>③ 解析不出 SemVer → **删除** | 🔴 **原稿完全缺失**。真因：用户升到新版后，磁盘里还躺着上一轮下好的**旧安装器** ⇒ 点「重启并更新」会**把自己降级**。这就是插件侧「装旧版覆盖新版」的主软件版——判据**复用** `electron/ipc/handlers/plugin-install-handlers.ts` 的锚① 语义（**同版恒拒 / 旧版默认拒**），**不许各写一份** |

**失败重试语义（2026-09-11 定案）**：第一版**不做断点续传**——重试 = **删 `.part` 重头下**。重试入口 = 通知面条目 `[重试]` + 帮助菜单「检查更新…」（回 `Checking` 重走全流程）。**实现口径（2026-09-12，#57.6）**：重试一律由**用户/调度**发起 ⇒ **下载腿内部不做自动重试**（没有断点续传时自动重下 = 悄悄重复下载几十 MB、还把失败吞掉，跟「失败必须出声」相反；将来若要自动重试，归调度层 #57.9 统一决定，不在腿里各写一份）。腿自持 **30 秒空闲超时**（判据 = 「还有新字节吗」，**不是**总时长——按总时长掐会把慢网上的健康下载判死，同插件侧 E6#73e）。

**`Downloading` 态不在重启后复活（2026-09-11 定案）**：启动时若持久化状态是 `Downloading` —— 磁盘**有**完整 `.exe` → 落 `Downloaded`；**无**（只有 `.part` 或空）→ 落 `Idle` + `lastError{code:'interrupted'}`。**不许停在 `Downloading` 假装有进度**（UI 会显示一个永远不动的 42% = 卡死且无出口）。

### 2.5 重启安装（Windows 首个平台）

`Ready` 态 → 用户点条目「重启并更新」（04 §四）：

1. 进程退出前，把安装器路径 + 参数写进临场调度：
   ```
   app.relaunch({ args: ['--update-install', '<installer-path>'], execPath: <installer> })
   ```
   或 Windows 上常用先起 `spawn` 一个解耦安装进程再退出。**实现时二选一并实测**（本机 Windows，直接测）。
2. `app.quit()`。
3. 安装器（NSIS）跑 `--updated` 静默模式 → 覆盖安装 → 重启 LinkDesk。

> 🔴 **实测重点不是「参数对不对」，是「文件锁」**——安装器启动时旧进程若没退干净，NSIS 覆盖 `LinkDesk.exe` 会失败（弹「请先关闭 LinkDesk」或静默半装）。**二选一的判据就是这一条**：`--updated` 路径下安装器要能等旧进程退出（NSIS 侧 `nsProcess`/重试宏，或主进程等 `app.quit()` 后再延迟 spawn）。退出前把 `updating` 态**落盘**（下次启动要知道自己是「正在装」而非「崩了」）。

> **依赖关系（执行序）**：E6#57 执行序依赖 **E6#37**（安装包构建完成后实机验证更新链路——没有安装包就没有「重启安装」可测）。
> ✅ **2026-09-11 起这条依赖不再是悬空的**：用户拍板把 **E6#37 从 L4 整颗迁进 L5 第 5.0 轮**（排在本层 5.4 之前）⇒ **顺序天然满足，不必再「到实机格前先请示」**。注意迁的是**执行点**，档案仍在 [04-端到端验证/02-生产安装验证.md](../04-端到端验证/02-生产安装验证.md) §二。
> 🔴 **唯一不变的铁律：不许拿 `electron:dev` 冒充安装版**（`packaging-run-sop`）。研究/设计（#57a/#57b）本来就可先行。

### 2.6 更新通道（stable / preview）——已拍板：只 stable

VS Code 有 `quality = stable/insider`。**LinkDesk 第一版只做 stable 一条通道（2026-08-30 用户拍板）**：

- **稳定版 = 检查只认 GitHub Releases 正式版（忽略 prerelease 标签）**；`app.update.quality` 配置项**留位但不实现**（schema 不提前占，第二版要 preview 时再加，避免发布侧「一版双发」运维负担）。
- 若要双通道（留位备忘）：`app.update.quality`（`stable` 默认 / `preview`），更新 URL 带 quality 参数，preview 通道指向 `encaron/linkdesk` 的 prerelease 标签（GitHub Releases `prerelease: true`）。
