### 层 2：压缩导航控制器

| VS Code | LinkDesk 当前 | 差距 |
|:--|:--|:--|
| `CompressedNavigationController` 类（~120 行） | `getCompactedPath()` + `findLeaf()`（~35 行） | **根本性差异** |
| 树模型层处理（`CompressedObjectTreeModel`） | 数据层外 `flattenTree` 预处理 | 压缩态/展开态切换由树模型保证——我们靠手动 `return` 跳过 |

**这是今天三个 CompactFolder bug 的根因——我们不应该在 `flattenTree` 层做压缩。** 压缩应该是一个树模型层的概念：压缩节点 → 展开 → 树模型自动解压缩并展示子节点。VS Code 把这个逻辑封装在 `CompressibleAsyncDataTree`（平台层，不在 explorer 里）。

### 层 6：视图容器架构 🔴 圆形大厅的桌子

VS Code Explorer 不是一个"文件树组件"，而是一个**视图容器（View Container）**。

**证据——为什么不同的配置文件打开同一个文件夹显示不同？**

```
C/C++ 配置文件打开 D:\123：          Claude Code 配置文件打开 D:\123：
> 123        ← FOLDERS（内置）        > 123        ← FOLDERS（内置）
> 大纲        ← C/C++ 扩展提供
> 时间线      ← Git 扩展提供
```

**VS Code Explorer 是 ViewContainer——插件可以往里面贡献视图。** C/C++ 扩展注册了 OUTLINE，Git 注册了 TIMELINE。Claude Code 配置文件没装这些扩展 → 只看到 FOLDERS。

**这是圆形大厅的一张新桌子：**

```
            ┌──────────────────────────────────────┐
            │  ViewContainer (核心提供)              │
            │  "放视图的桌子"                         │
            │                                        │
  file-tree │  ┌──────┐ ┌──────┐ ┌──────┐          │ C/C++扩展
  ─────────→│  │FOLDER│ │OUTLIN│ │TIMELI│←─────────│ (提供视图)
  (注册视图) │  │  S   │ │  E   │ │  N  E│          │
            │  └──────┘ └──────┘ └──────┘          │
            │                                        │
  Git-插件   │  核心准入标准三条全满足：               │  AI-插件
  ─────────→│  ① 多提供方——file-tree/lang/Git/AI    │←─────────
  (提供视图) │  ② 多消费方——侧栏渲染引擎              │ (提供视图)
            │  ③ 桌子不知道视图内容                   │
            └──────────────────────────────────────┘
```

**设计约束——sidebar 不能写死 file-tree：**

```
❌ 当前：sidebar.tsx 直接 import FileTree + WelcomeView
   → 硬写死了"侧栏=文件树"

✅ 将来：sidebar 是 ViewContainer——渲染注册到 "explorer" 容器的所有视图
   → FileTree 只是一个注册到 "explorer" 的视图贡献者
   → 大纲/时间线/任何插件都可以注册到同一个容器
```

**核心需要提供的 API：**

```typescript
// plugin.json 贡献点
"contributes": {
    "viewsContainers": {
        "explorer": { "id": "explorer", "title": "资源管理器", "icon": "$(files)" }
    },
    "views": {
        "explorer": [
            { "id": "fileTree",    "name": "",            "when": "true" },
            { "id": "outline",     "name": "大纲",         "when": "hasOutlineProvider" },
            { "id": "timeline",    "name": "时间线",       "when": "hasTimelineProvider" }
        ]
    }
}

// 核心 API（新的桌子）
interface ViewContainerService {
    registerViewContainer(id: string, container: ViewContainerDescriptor): void;
    getViews(containerId: string): ViewDescriptor[];
    onDidChangeViews: Event<ViewDescriptor[]>;
    setViewVisibility(viewId: string, visible: boolean): void;
}
```

**优先级：E4 内实现。** 核心需要新增 `ViewContainerService` 桌子。`sidebar.tsx` 重写为视图渲染循环——不再直接 `import FileTree`。对标 `filetree-preview.html` L389–430 的三段结构（OPEN EDITORS / FOLDERS / OUTLINE / TIMELINE）。执行清单：E4V#32–E4V#36。

每种子视图是独立的 `ViewPane`，有独立的：
- context key（`FoldersViewVisibleContext` / `OpenEditorsFocusedContext`）
- 可见性切换（右键视图标题→显示/隐藏）
- 菜单贡献（`MenuId.ViewTitle` 的 when 条件区分不同视图）

## 六、🔴🔴🔴 数据损毁级 Bug——OS 拖入递归嵌套

> 2026-07-29 发现。**严重度：最高——直接破坏用户文件系统。膨胀至 1.85GB。**
> 已修复 `afc9bb6`。

**根因：** `FileTreeDnD.ts` OS 拖入分支（`dataTransfer.files`）只做了 `FileService.copy`，没有 `isAncestorOf` 祖先检查。树内拖拽（`text/plain`）有祖先检查，但两分支不一致。

**复现：** 从 Windows 资源管理器拖 `D:\工具软件\` 到树内子目录 `工具软件\串口助手\` 上→ `copy(根, 子/根)` → `串口助手\工具软件\串口助手\工具软件\...` 无限递归嵌套。每次操作指数膨胀。

**实际影响目录：** `工具软件/工具软件/`（10 层）、`串口助手/串口助手/`（10+ 层）、`FlyMcu程序烧录软件/FlyMcu程序烧录软件/`（10+ 层）、`串口助手-工程源码/串口助手-工程源码/`（5+ 层）

**修复：** `afc9bb6`：OS 拖入加 `normalizedTarget.startsWith(normalizedSrc + "/")` 祖先检查，6 行。

**教训：** VS Code `FileDragAndDrop` 对 OS 拖入有完整 `ITreeDragAndDrop` 接口验证。我们写 #99 时没读 VS Code 源码——两分支只给一个加了约束。
