> 对应清单：**E6#57**。本档回答用户第三问（更新前能否查看更新了什么、去哪看、怎么看）+ 载体决策（标签页 vs 浏览器）。

## 一、VS Code 对标证据

- **自动弹**：`pkg.version !== lastVersion`（首次启动新版本）→ 自动打开内置「更新说明」tab。
- **数据源**：`https://code.visualstudio.com/raw/v{version}.md` 按版本拉取（独立静态文件，按版本 URL 直取）。
- **缓存**：本地按版本缓存（userData 下），同一版本不重复拉。
- **可关**：设置 `Update: Show Release Notes`（首启自动弹的开/关）。
- **失败降级**：拉取失败（离线/404）→ 通知条提示，不打扰、不阻塞启动。

## 二、LinkDesk 设计——发行说明 = 壳内标签页

### 2.1 载体决策（标签页 vs 浏览器）

| 维度 | 壳内标签页（推荐 ✅） | 浏览器新开 |
|:--|:--|:--|
| 体感 | 对标 VS Code 内置 tab，不离开软件 | 跳出软件，断裂 |
| 主题 | 跟随 LinkDesk 主题（玻璃态/深色） | 浏览器样式，不跟随 |
| 可交互 | 可后续接「从发行说明一键安装」等 | 纯静态 |
| 离线 | 缓存在本地，离线可看历史版本说明 | 无网打不开 |
| 实现 | 复刻欢迎页模式（壳直渲染 view） | 壳 api openExternal |
| 标签页哲学 | 「标签页 = 通用表面容器」——发行说明只是又一张表面 | 不占用 |

**结论：壳内标签页。** 符合「标签页 = 通用表面容器」记忆（任何新表达形式 = 加一个标签页）+ 对标 VS Code 内置 tab。

| 入口 | 行为 |

| 更新通知面条目「查看更新内容 →」 | 打开发行说明标签页（新版本）+ 滚动到该版 |
| **首次启动新版本** | **自动打开**（对标 VS Code，见 §2.4） |

### 2.3 标签页实现（复刻欢迎页模式）

- 载体：**壳直渲染 view**，`appearsIn.tabBar: true` + `tabBehavior.singleton: true`（对标 `WelcomePoolView.tsx` 的 `tabBehavior.isFallback` 模式，但**发行说明不是 fallback**——是普通单例标签页）。
- 组件：`src/pool/views/release-notes/ReleaseNotesView.tsx`（壳组件，非插件——对标欢迎页 `src/pool/views/welcome/` 先例，按「UI 功能域 = 文件夹」建夹；不是 `src/components/`）。
- 样式：`var(--*)` 主题 token + 壳组件（硬约束 16，落地走设计 skill）。
- **布局（2026-08-30 定稿）**：发行说明 = **主区标签页**（对齐插件详情页 [01 竞标 A](../03-插件市场/mockups/01-插件详情页-竞标.html) 骨架：头部集成 + 主体）。主体 = **左窄栏版本历史 220px（配角导航）+ 右主区更新内容（主角）**——**版本历史不是主角，不占一半**（用户 2026-08-30 指示「一个区区的版本历史占了标签页的一半？它是主角吗？」，按 skill 设计后定：Developer Tool 文档专注，VS Code 基准窄列表）。**内容不占声明式侧栏**——LinkDesk 侧栏 = 声明制专属面板、与标签栏不同时开，为发行说明搞侧栏容器（title/toolbarslot…）很麻烦（用户 2026-08-30 指示「把信息集成进一个主区标签页，不放单独侧栏」）。mockup 03 外层画出**完整软件框架**（图标栏 / 应用侧栏 / 状态栏）示意——那是软件本身的框架，发行说明只是主区其中一个 tab。
- 内容结构：

```
发行说明标签页（主区 tab，对齐插件详情页 01 A 骨架）
├─ 头部版本区：v0.2.0 + 发布日期 + 通道（stable）+「在 GitHub 查看全部」
├─ 主体：左窄栏 220px（配角导航）+ 右主区（主角）
│  ├─ 左：版本历史（git 历史列表，倒序）——选中即渲染该版 body
│  └─ 右：更新内容（Release body Markdown 渲染 + 首启自动弹横幅）
│     每版一个 Release body（GitHub 拉取/缓存）
└─ 尾部：「所有版本 → GitHub Releases」链接（浏览器打开全历史）
```

### 2.4 数据源与缓存

- **数据源 = GitHub Releases API**（与更新检查同源，不造第二套存储）：
  ```
  https://api.github.com/repos/encaron/linkdesk/releases?per_page=30
  ```
  （分页最多 30 条历史；每条含 `tag_name` / `published_at` / `body` / `html_url`）

- 🔴 **数据源通道（2026-09-11 定，清单 E6#57.8e）——谁去拉？走哪条 IPC？**

  原稿只写了 URL，**没写谁发起这次网络请求**。两条腿必须当场挑一条，不挑就等于交给执行者临场发挥：

  | 选项 | 判据 | 结论 |
  |:--|:--|:--|
  | **(a) 主进程拉**（✅ 选它） | ① 缓存要落 `{userData}`——**只有主进程有**；② 主进程出网走 `main-fetch.ts`（E6#76），**自动继承 Windows 系统代理**；③ 与更新检查（同在主进程）**共用同一份代理语义与失败归因**，不会出现「检查更新能连、发行说明连不上」 | **选定** |
  | (b) 渲染进程拉 | 渲染进程写不了 `{userData}`，代理行为另说，且要新造一套失败归因 | 否 |

  ⇒ **通道名 `update.getReleaseNotes`**（`update.*` 命名空间，主进程处理）。
  ⚠️ **默认不进 `PROXY_CHANNELS` 只读白名单**——发行说明是壳自己的面，第三方插件没有读它的理由；将来要开放再单独过一遍白名单评审（对照 `update.getState` 是唯一已白名单的 `update.*`）。
  ⇒ **必须同步登记到 [07-数据流通格式.md](07-数据流通格式.md) 的通道表**，否则本档与 07 对不上。

- **缓存**：`{userData}/update/releases-cache.json`，24h 过期刷新（对标插件目录缓存惯例）。
  - 🔴 **路径订正（2026-09-13 落地 `#57.8e` 时）**：原文写的是 `updates/`（**复数**），实现改为 `update/`（**单数**）——与安装器、待续安装记录**同一个目录**（`updateDownloadDir()` 这个唯一拼接口）。理由：`{userData}` 下摆一个 `update` 再摆一个 `updates`，每个后来者都要停下来问「这俩什么区别」。安全性已核：启动清理（`cleanupUpdateResidue`）只删 `.part` 半截文件与**版本号解析得出且方向是降级**的安装器，一个 JSON 文件名解析不出安装器版本，被直接跳过。
  - 🔴 **失效判据是两条，不是一条（同日订正）**：`24h 过期` **＋「所请求的那一版不在缓存里 ⇒ 视为失效」**。原文写的「键 = 版本列表 hash」在本文件里**没有比对物**（缓存里存的就是列表本身，拿它自己算 hash 再跟自己比恒相等）⇒ 存一个 hash 字段纯属装饰；那句话的真意思（**由版本列表决定这份缓存还算不算数**）落成第二条判据。它救的是**刚更新完的首次启动**：缓存可能是升级前拉的、根本没有你刚装上的那一版，而 §2.5 的首启自动弹正是这个场景。
  - 🔴 **第二条判据的前提（2026-09-13 订正，清单 E6#57.13i）**：这条判据**只在「发起取数时点了名」时才成立**——而首启自动弹那条路原本**发起时那一格是空的**（`primeReleaseNotes({ banner: true })` 没带 `version`）⇒ `wanted === undefined` ⇒ **判据短路、一次都没上过场**，缓存（升级前拉的、根本没有你刚装上的那一版）照旧命中。**落地口径**：自动弹**必须把 `app.getVersion()` 带下去**（`openReleaseNotesTab({ banner: true, version })`）。<br>🔴 **本条要记的不是「改了一行」，是这个形态**：判据要连「**谁会触发它**」一起写——只写「满足 X 则 Y」而不写「X 由哪个入口置入」，等于在文档里放了一条**永不运行的尺子**。本条判据的原文甚至已经写明了它救的就是首启自动弹那个场景，**仍然没生效**。
  - **兜底走缓存时 `fetchedAt` 不刷新**——否则一次断网就把「24h」无限续命，缓存永远不会因为过期被替换（静默变成永久陈旧）。
- **渲染**：Release body 是 GitHub Flavored Markdown → **消费壳共享 MarkdownView 组件**（react-markdown + remark-gfm + DOMPurify sanitize，E6#54 分发 @linkdesk/ui；2026-08-30 拍板「md 渲染唯一组件」）。与插件详情页 README 同一渲染器（见 [03-插件市场/04-详情页设计.md §4.1](../03-插件市场/04-详情页设计.md)），跟随主题，网络内容统一过 sanitize。
- 🔴 **三态，不是两态（2026-09-11 明确，对应 mockup 03 Frame 1/2/3）**：

  | 态 | 判据 | 画面 |
  |:--|:--|:--|
  | **加载中** | 请求已发、未回来 | **骨架屏**（标题条 + 几条骨架行，**无微光动画**——`prefers-reduced-motion` 下微光本就是噪音）｜Frame 3 |
  | **有内容** | 拉到 / 缓存命中 | 左窄栏版本列表 + 右主区 body｜Frame 1 |
  | **空态** | 拉取失败 **且** 无缓存 | 「无法加载发行说明」+ 重试按钮 + 「在 GitHub 上查看」｜Frame 2 |

  缓存命中时**不经过加载态**（直接渲染，避免每次打开闪一下骨架）。
- **失败降级**：拉取失败 → 缓存兜底；无缓存 → 空态 + 重试 + GitHub 链接（上表第三行）。

### 2.5 首启自动弹（对标 VS Code）

- 判断：`app.getVersion() !== lastSeenVersion`（存 `lastSeenVersion` 到壳存储，随启动写入当前版本）。
- 首次启动新版本 → 自动打开发行说明标签页（只开一次；此后该版本不再弹）。
- 可关：设置 `app.update.showReleaseNotes`（boolean，默认 true）——关了首启不弹，但「显示发行说明」菜单始终可用。
- 失败（离线）→ 不打扰，下次启动再试。
- 🔴 **首启横幅的判据是两条，不是一条（2026-09-13 订正，清单 E6#57.13i）**：自动弹时页顶画一条「**检测到新版本 {{version}}**，已自动打开本页」。两条判据**同时成立才画**：
  1. **`bannerPending`**——这次取数是「**宣告**」，不是用户自己点开看。**只有首启自动弹会上这个闩**；左窄栏点某一版 / 通知面条目定位到某一版走的是「**换一版重新取数**」那条路（`selectReleaseNotesVersion`），它会**先撤闩**再取数。
  2. **`notes.version === announced`**（`announced = version ?? notes.version`）——**取数真把要宣告的那一版拿回来了**。

  ⇒ **取数回落**（离线走缓存兜底 / 那一版压根不在列表里）⇒ **不画横幅**：宁可少说一句，不说错一句。<br>⚠️ 判据 2 原先写的是 `version === undefined`（「只有取最新一版才配叫新版本」）——那个写法挡得住「用户点历史版本」，**挡不住真正会出事的另一路**：首启自动弹点名的就是你刚装上的那版，而取数**可能回落**，`notes.version` 就成了列表头那版（多半正是你刚替换掉的那版）⇒ 横幅会写「**检测到新版本 0.1.54**」。**同一句话从真话变成假话。**

### 2.6 历史版本表示（用户第一问落地）

发行说明标签页 = **当前软件内看历史版本的地方**：

- 版本选择器 = GitHub Releases 列表（倒序），选中即显示该版 body。
- 「所有版本 → GitHub Releases」= 浏览器看完整历史（含 0.x 时代全量）。
- 与 [02-产品身份与版本.md](02-产品身份与版本.md) §2.4 呼应：**历史版本 = GitHub Releases 列表**，软件内提供前 30 条精选，浏览器提供全量。
