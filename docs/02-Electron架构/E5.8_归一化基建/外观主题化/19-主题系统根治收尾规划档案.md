## 一、用户质疑与诚实归因

用户功能诉求全是手机主题软件的成熟功能：自由调圆角 / 自由换肤 / 自由调字体 / 玻璃质感 / 混搭（5 个主题用 a 的图标 + b 的壁纸 + c 的锁屏 + d 的字体）。需求描述清楚，功能非新事物。**难不在「功能」和「需求」，在 LinkDesk 的历史架构**。

### 根本差异：安卓是基建自带 token，LinkDesk 是盖好楼后装修

- **安卓/iOS**：Material Design 第一天就把颜色/圆角/字体定义成 token，系统 UI、组件库、主题引擎**一体设计**。换肤 = 换参数，消费面天生统一。
- **LinkDesk**：组件（顶栏/侧栏/主区/状态栏/浮层）E4-E5 用 CSS 一砖一瓦写起，**大量硬编码颜色、局部变量、各自枚举**。E5.8 才给已盖好的楼做主题系统 = 装修。

> 类比：老房子装中央空调——需求清楚（每间都凉快），施工要穿墙打孔；新楼盘从设计图就预留空调位。**安卓是后者，LinkDesk 是前者。**

### 「同一个 bug 多次出现」的真相：不是复发，是同一反模式逐面漏网

| 反模式 | 表现（用户感知为「同一 bug 多次出现」） |
|---|---|
| 枚举漏项 | 浮层磨砂枚举 10 选择器漏 3 → 每加新浮层，同样的「没磨砂」换个表面再来 |
| 参考系错锚 | ratio 换算 / 玻璃 wash 与 label 矛盾 / panorama 永不实——同一根因三个表现 |
| 多路径不一致 | recipe/mix/override/播种四路各写各的，改一条漏一条 |

根因：**系统性的全局改造被拆成「修这一处」的局部补丁**，补丁盖住已知面，盖不住未知面。

### 新 bug 为什么总出现：消费面隐式 + 组合验证盲区

- **CSS 变量消费是隐式的**——任何组件都能 `var(--xxx)` 或漏掉，**没有任何机械检查能告诉你哪个表面没迁移**（安卓有类型系统保证组件必须声明用哪个 token）。
- 组合空间巨大（6+ 主题 × 14 覆盖键 × 混搭来源 × 玻璃参数），单测只能测 token 计算逻辑（recipe/mix/seeds），测不到渲染层每表面实际消费。

### 为什么「描述清楚却难」

用户描述的是「**要什么**」（功能需求，准确清晰）；难在「**在 LinkDesk 实现时的工程成本**」（消费面迁移 / 跨进程 token 契约 / 隐式 CSS 消费）。需求理解 ≠ 改造容易。

### #131 层级/状态规则图先行（#128 前置——新增，2026-08-27 补）

> 2026-08-27 另一份 AI 分析校准，比初版表述更准确：**「代码收敛 ≠ 视觉行为收敛」**。代码层反模式在逐个消灭（#128-#130 的目的），但用户可感知的「玻璃 0→1 时背景/主表面/右键菜单/弹窗/分区图是否每次按同一规则变化」尚未稳定——玻璃链条（语义重定义 → 镜像 → 镜像失败 → 删镜像 → 分区图不淡出 → 补 #125）证明**基础语义在改、每次修复只覆盖当时看见的一层**。根治前提不是直接 token 化，而是先把「什么层负责什么」定成**不可变规则图**并用真实画面验证。

- **目标**：立一张层级/状态规则图，覆盖以下不可变规则：
  1. **玻璃透明度控制哪一层**——合成层语义（#125 教训：zone 图/主表面/浮层各自是否参与透明度合成）

  3. **合成边界**——浮层 / 脱出窗 / 插件注入 DOM 在合成器里的位置（#93 缝系统、浮层权威）
  4. **优先级图**——用户覆盖 / 混搭来源 / 播种 / 主题配方，谁压谁（#88 生命周期归一）
  5. **概念键分离**——主题配方（审美）/ 配色变体（themeColor 选择）/ 混搭来源（域来源）三个产品概念不共用同一键；现状 colors 域来源并入 `app.themeColor`（E5.8#82 有意决策「配色域来源统一」，UI 已按外观模式动态切描述缓解）→ 落地时按此规则重审是否拆键；**若复用，须把「按当前模式解释」写死**：followTheme 下 `app.themeColor` = 当前配方内 colorway id；custom 下 = colors 域来源 recipe id；切换模式 / 切主题 / 重启恢复 / 复位 / 跨主题配色全走此解释、逐面测试（第三方 AI 校准，2026-08-27）
  6. **跨窗契约**——主窗口 / Pool / 脱出窗口的 CSS 变量所有权（谁写谁清）
- **验证**：真实画面回归——CDP **截图级**对比「玻璃 0→1」时全部表面一致变化（不只 token 几何）。
- **交付**：规则图沉档 + 每条规则映射到消费面代码。
- **前置关系**：#128 token 化依赖此图。

##### 规则 1｜玻璃透明度控制哪一层——合成层语义

- **规则**：用户玻璃透明度（`app.glassOpacity`）只作用于**合成层**——`synthesizeGlassSurfaces` 把 `SURFACE_COLOR_KEYS`（8 个 `--bg-*` 键）color-mix 缩 alpha 成半透明 `--<key>-solid`。一切 surface 底色、zone 图淡出（`--glass-surface-bg-opacity`）、浮层保底磨砂均**从合成结果派生**，不存在第二条独立透明度路径。`--glass-opacity`（配方面 tint 盖片不透明度）是**残留消费**——#112 已摘除用户直写，只随配方面材质缩放。
- **稀疏合成语义（#131 CDP 实测修正）**：`synthesizeGlassSurfaces` **只合成当前 token 集里存在**的 `SURFACE_COLOR_KEYS` 键（tokens.ts:332 设计注释「主题没写的表面色 = CSS :root 壳默认，不碰」）。主题 colorway 未写的 `--bg-*` 键不进 token 集 → 该表面玻璃激活时**保持 `:root` 默认不透明**。「玻璃 = 系统表面层」设计意图（全部 8 键半透明）与稀疏实现存在**真差距**——2026-08-28 CDP 实测：mint-soda 不写 `bg-titlebar` → 顶栏成不透明岛；aurora-glass 写全 8 键 → 整窗玻璃。**follow-up 归属 #151 生产者 alpha（批次 5，待用户裁决）**。
- **消费面映射**：
  - 生产者：`src/core/services/ui/ThemeEngine/tokens.ts:337` `synthesizeGlassSurfaces`（SURFACE_COLOR_KEYS × glass-surface-alpha → `--<key>-solid`）+ `seeds.ts:191` `getGlassSurfaceSpec`（active = 任一玻璃键显式配置；alpha 默认 `GLASS_SURFACE_DEFAULT_ALPHA=0.5`，constants.ts）+ `seeds.ts:207` `getAppearanceOverrides`（`app.glassOpacity` 只写合成层）
  - 消费端：`src/index.css:618-640` 玻璃 `::before` 层（`background: var(--glass-tint)` + `opacity: var(--glass-opacity, 1)`——配方面材质）；`src/index.css:653-690` 影像 `::after` 层（`:670` `opacity: var(--glass-surface-bg-opacity, var(--surface-bg-opacity, 1))`——#125 玻璃激活读合成透明度）
  - 六表面统一形态：`src/index.css:422-436`（`border-radius: var(--surface-radius,0px)` / `box-shadow: var(--surface-shadow,none)` / morph 过渡）
- **一致性验证点（2026-08-28 CDP 实测修正）**：玻璃 0→1 时，**主题写了**的表面（icon-bar/side-panel/main-zone/panel-zone/status-bar）底色**同步**变半透明、zone 图**同步**淡出、blur 按 surface-scale 缩放（icon-bar 0.44× / panel-zone 1.11× / 其余 1×）；**主题没写的键**（如 mint-soda 的 `bg-titlebar`）保持 `:root` 不透明 → **顶栏岛**（实测 titlebar `rgb(221,221,221)` 玻璃激活不变）；浮层保底磨砂**恒 16px 地板**（玻璃 0/1 均不变，规则 3 实证）；0 时全表面回主题原生值零变化。

##### 规则 2｜渲染分层——z 从底到顶 + 谁采样谁

- **规则**：层序固定：`--bg-window` 底座（html/body/#root/pool-root）→ BackgroundLayer 全窗图（z0）→ zone 表面（z1）→ `::after` 影像/切片（z:-2）→ `::before` 玻璃磨砂（z:-1）→ 内容（z auto 锐利）→ 浮层 `#ld-float-layer`（z2000+）。**镜像机制已废（#117）**：zone 图不再 filter blur 作磨砂采样源；`::before` backdrop-filter 直接采样兄弟 `.background-layer` 全景图（cp114 证据）——blur 的语义是「图上的玻璃」，不是「玻璃后的图」。
- **消费面映射**：
