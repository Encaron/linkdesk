## 二、代码诊断（逐条回应 —— 结论：4 条现象 = 2 个机制；用户的居中推测不成立）

### 2.1 先答一个总问题：为什么"到处都在上方"

`HintTipRenderer.tsx:69`：

```ts
placement: (PLACEMENTS.includes(rawPlacement) ? rawPlacement : "top") as TipPlacement,
```

**不写 `data-hint-placement` 就是 `top`**。全仓检索（2026-09-27 复核）：这个属性只有四处「声明/读/单测」——`hintAttrs.ts:25` 声明常量 · `HintTipRenderer.tsx:65` 读它 · `HintTip.tsx:55` 有个 prop 可写 · `HintTip.test.tsx:55` 与 `HintTipRenderer.test.tsx:92-95` 在单测里赋过值；
业务侧 `placement=` 传参 **0 处**，池里也只挂了渲染器本身（`src/pool/PoolZoneShell.tsx:135`）——
⇒ **壳侧 43 处提示全部走默认 `top`**，插件侧同样没写过。这就是「图标栏、标签栏、状态栏一律在部件上方」的总来源。
并且 `placement.ts:9-14` 拍板过「不要小箭头，就是一个框型」⇒ 归属感**全靠 `GAP_PX = 6` 贴紧锚**这一条机制承担。

### 2.2 3.1 图标栏「悬空 15px」——用户说得对，是尺子错了

| 事实 | 出处 |
|:--|:--|
| `.ib-item` 命中盒 **42×42** | `src/pool/zones/icon-bar/IconBarZone.css:40` |
| 里面的 `.glyph` 只有 **24×24** | 同上 `:73` |
| 条与锚的间距 `GAP_PX = 6` | `src/components/shared/hint-tip/placement.ts:18` |

锚取**命中框**时，条的下边到**看得见的字形**上边 = `GAP 6 + (42−24)/2 = **15px**`（参考图 `p-icon` 卡实测 **15px**）。
用户那句「图标肯定比显示它的看不见的框小一点的」= 精确命中根因。**修正方向有两条（不互斥）**：① 锚改取**可见字形**（参考图勾「贴锚基准＝可见字形」，实测回落 6px）；② 方案③ 跟随鼠标，绕开"锚形状"这件事。

### 2.3 3.2 标签栏「一会儿上一会儿下」——是同一个判据的三副面孔

`placement.ts:87` 的翻面条件是**全-or-无**，且**两个轴一起判**：

```ts
if (!fits(primary, tip, viewport) && fits(rawPlacement(anchor, tip, opposite), tip, viewport)) { … }
```

```ts
// fits()：上/左 都要 ≥ EDGE_PX，且 右边/下边 都要 ≤ 视口 − EDGE_PX（placement.ts:69-71）
```

标签文案越长 ⇒ 条越宽 ⇒ 副轴（横向）越早为假。**窗口越窄，副轴越早出局**：

- **窗口化**：长文案的 top 贴不下 → 想翻 bottom，但 bottom 的横向也越界 ⇒ **翻面被否决** ⇒ 夹紧把条拉回来 → 出现「一半盖在标签栏」；
- **全屏**：横向富余 ⇒ top 放得下 ⇒ 就一直留在上方；放不下的那条翻到下方 ⇒ 用户看到「全屏时正常显示在下方」；
- **普通短标签**：top 一直放得下 ⇒ 永远在上方。

参考图实测（窗口化）：长标题标签 → `top → bottom`（落在标签栏下方、不压锚）；普通标签 → `top → top`。

### 2.4 3.3 ✕ ——不是"居中失败"，是"翻面被否决 ＋ 夹紧把条拉回锚身上"

🔴 **用户的推测不成立**：`placement.ts:55-66` 是**边对齐**（`left: anchor.left`），**从来没有"居中"这一步**，所以不存在"居不了中就坐标乱了"。
真实机制是三步（参考图诊断面板会逐字打印这条推理链）：

1. 首选 `top` 的 `raw top = anchor.top(0) − 条高(29) − 6 = −34` ⇒ **贴不下**；
2. 翻面要求对方位**完整**放得下：✕ 在窗口最右缘 ⇒ `left(1211) + 条宽(143) > 1250 − 8` ⇒ **副轴越界，把唯一可用的退路（翻到下方）否决掉了**；
3. 于是 `resolved` 仍是 `top`，最后的夹紧把 `top` 从 **−34 拉到 8** ⇒ 条正好铺在 titlebar 上、**盖住 ✕**。

实测（参考图，窗口 1250×720）：✕ 命中框 `y 104..134`，条 `y 112..141`、`x 1114..1257` ⇒ **压锚 = 是**。
一句话：**不是坐标写错，是"翻面"这条退路被副轴挡住了，剩下的夹紧只能把条拉回锚身上。**

## 六、边界与已知风险（先说清，免得拍板后才撞上）

- 🔴 **DOM 条不可能出窗口**。用户提到原生 tooltip「超出软件 webview 外边缘都没问题」——那是因为 Chromium 由**系统层在页面之外**画它。HTML 元素做不到；唯一的做法是**另开一个透明 always-on-top 的 BrowserWindow**（新窗口 ＋ IPC ＋ 焦点管理），而池层是**哑渲染器**，不建议为一条提示破这个结构。
  ⇒ 「贴窗口边缘时：要么翻面、要么夹紧」是**物理约束**，本件只能在两者之间挑更好看的那个。
- 🟡 **贴右缘会被压窄（机制已定、实机未验）**：`.ldk-hint-tip` 是 `inline-flex` 且只给 `left` ⇒ 绝对/固定定位的「缩至可用宽度」上限 = 包含块宽 − `left`，贴右缘时条会先被压窄，再由 `useLayoutEffect` 的重算逐帧**收敛回自然宽**。参考图里已按**收敛态**锁 `width: max-content`（否则实测被压到 89px、文字逐字换行，几何不可判）。
  ⚠️ **待实机确认**：实机是否有肉眼可见的「先窄后宽」抖一下。若确认，解法就是给条加 `width: max-content`。
- 🟡 参考图的诊断数字由页面内**同值移植**的纯函数算出（`GAP 6 / EDGE 8` 与 `placement.ts` 逐字同值），**不是真实组件渲染**⇒ 落点结论要在壳里复验一次再落实现。
