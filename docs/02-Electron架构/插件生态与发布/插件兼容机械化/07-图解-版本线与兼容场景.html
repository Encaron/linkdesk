0这篇要解决的，是一个具体的绕不出来

用户（2026-09-18）连着问了十几轮，核心始终卡在同一个地方：把四条互不相干的版本线当成了一条—— 以为「ui 包版本」和「壳版本」是同一把尺子上的前后刻度（ui 2.3.5 ↔ 壳 1.0.88、ui 2.3.6 ↔ 壳 1.0.89）， 于是推出「用旧 ui 的插件在旧壳上能用、用新 ui 的插件必须装新壳」。

结论先放这（后面每一节都在证明它）

ui 包的版本只决定两件事：① 插件构建时能不能拿到它；② 插件想不想用上新零件。
它不决定：用户能不能装这只插件、市场里显示哪个词。

2三个误解 → 正解（就是这几天走过的弯路）

误解 ①

ui 包会声明「我适配哪些壳版本」（如 ui 2.3.6 适配壳 1.0.89+）

正解

包只有代码，没有这张表。装不装得上的门槛是 minAppVersion，由插件作者手写

误解 ②

插件声明了 ^0.3.0，ui 包一出补丁（0.3.1），所有插件就自动享受新体验

正解

装了哪个版本由插件仓的清单（lock）钉死；而且零件是焊进插件产物的，包升级不会改变已装在用户机器上的插件

误解 ③

插件用的 ui 版本老（如 1.9.11）⇒ 不可使用

正解

ui 版本完全不参与可用性判断。老零件在新壳上照样跑（因为壳根本不认它）

3为什么「包升级 ≠ 用户拿到」：零件是编译期焊进去的

STEP 1
零件源码 壳仓 src/components/shared/（单一副本）→ 经 @linkdesk/ui 对外分发
STEP 2
构建时焊进产物 插件跑 vite build，共享件源码被内联进插件自己的 bundle
STEP 3
用户机器上的插件 装完之后，这只插件自带一份它构建时的零件拷贝
STEP 4
包再更新也没用 npm 上把包更新一百次，改不了用户机器里那份

实测证据（拆开随包的市场插件 zip 看到的）

  • 产物里 5 个视图 bundle 都能搜到共享件自己的实现痕迹：views/DetailView.bundle.js · SearchView · InstalledListView · BuiltinListView · ConfirmInstall（命中 overlay-root / data-overlay-wrapper / ldk-badge）。
  • SDK 的「由壳提供、插件不许自己打」名单只有六个：react · react-dom · react-dom/client · react/jsx-runtime · react-i18next · i18next（packages/plugin-sdk/src/vite-config.ts:55）。@linkdesk/ui 不在里面，也没有 import-map。
  • 设计文档原话（E6 07-共享组件独立分发设计.md 第 28 行）：「@linkdesk/ui 属"其它皆内联"——组件源码编译进各插件 bundle」。 ⚠️ 2026-09-19（L9「UI 集中供给」起）该结论已翻转：@linkdesk/ui 已进 SDK 的 external 名单、由壳池 vendor 单实例供给——本行是**当时的实测快照**，读现状请看 [UI集中供给/00-整理档案.md](../UI集中供给/00-整理档案.md)。

这是有意选的路线，不是疏忽——两条路线的取舍

对比项打捆（本仓今天的选择）运行时共享（external + import-map）
零件代码在哪每只插件产物里各带一份壳提供一份，插件运行时去取
包修了 bug每只插件各自重新发版才生效包一改，全体立刻受益
壳与插件版本互不依赖：老插件在新壳上照跑必须对齐，否则可能崩
插件产物体积每只各多一份（重复）更小
作者要配什么零配置，装 SDK 即达要管版本对齐

⇒ 本仓选了左边，换来的是「插件产物自洽、作者零配置」（代价：修复要各自发版）。这也是为什么这块面要尽量稳、尽量少改。

4三个问题，三套判据（别混）

① 用户能不能装这只插件？

唯一判据

插件自己写的 minAppVersion vs 用户装的壳版本。
不满足 ⇒ 装不上（不适配）。
实现：src/pluginLoader/resolution/runtime.ts:202-218 ——既有硬机制，本批只把它显示出来。

② 市场里显示哪个词？

三条依据（详见第 6 节）

宿主有没有把插件还在喊的名字拿走（悬空名）＋ minAppVersion 够不够 ＋ 插件发布日 vs 这只壳的构建日。
ui 版本不参与。

③ 插件能不能用上新零件？

全靠插件作者自己动手

进货（刷 ui 依赖）→ 重新构建（新零件焊进去）→ 发一个新版插件。
三步缺一，用户那边什么都不会变。

5^0.3.0 管什么、不管什么

^0.3.0 的全部含义 = >=0.3.0 <0.4.0（实测 semver@7.8.5 展开）。它是一句「允许范围」，不是「已经装上的版本」。

它管它不管
零件厂出 0.3.1 时，插件的声明不会失效、不会构建红、不用改文件 插件不会自动装到 0.3.1（钉死它的是插件仓的清单）
所以「没有任何插件被迫适配」——不改也不会坏 插件不会自动用上新零件（要重新构建 ＋ 重新发版，用户更新后才生效）
如果是 0.4.0（跳代）⇒ 声明立刻失效、必须齐步改 —— 那才叫被迫适配 跟「显示哪个词」「能不能装」都没有关系

一句话：^0.3.0 保证的是「你不被逼着干活」，不是「你自动拿到新东西」。

插件一 能装兼容 没写门槛 ⇒ 装得进；发布日早于这只壳的构建日 ⇒ 兼容。

这张表最值钱的两条

  • 同一只插件，在两个用户那里显示的词可以不一样（因为两只壳的构建日不同）——所以「显示哪个词」是插件 × 这只壳的联合结果，不是插件的固有属性。
  • 想推任何一格，缺的那个数永远是「插件自己写的门槛」；ui 版本推进去也算不出来。

7一次修复，怎么传到用户手上（四步，缺一不可）

拿「ui 0.3.55 有个 bug，作者修好发成 0.3.56」走一遍。发 0.3.56 那一刻，全世界什么都没变。

①
零件厂发 0.3.56只有 npm 上多了一个新版本
②
每只想要它的插件：进货刷清单 0.3.55 → 0.3.56（声明 ^0.3.0 不用改）
③
重新造车 + 发新车重新构建（新零件焊进去）→ 插件自己升版本发新版
④
用户更新插件市场推新版 / 用户点更新，修好的那份才到用户手里

所以：不是「所有插件通通不用动就享受」，而是「每只想要它的插件，各自重新发一次版才能享受」。 没去进的那只，继续带着 0.3.55 的 bug 照跑——不坏，但也没修。

8回本行：五个状态词的真实判据

五个词不是评分、不是人评的，每一条都是「两个事实比大小」，唯一真相源 = 00-整理档案.md §〇d。 本批读数由格 4 E6#117 算格 5 E6#118 只负责显示

用户面词机械判据说明
正常 无悬空名 ＋ minAppVersion 满足 ＋ 插件发布日 ≥ 壳构建日 与当前版本一致
兼容 无悬空名 ＋ minAppVersion 满足 ＋ 插件发布日 < 壳构建日 更早适配、仍可用；不判老、不判差。壳构建日拿不到时也落这里（保守且是真话）
部分不适配 悬空名 > 0（插件还在喊宿主已经没有的名字） 能装能用，个别界面可能显示不正常
不适配 minAppVersion 高于当前壳 装不上——既有硬机制，本批只把它显示出来
— 读数缺失（离线 / 尺子没跑） ⛔ 不许显示成「不适配」

附：这两个日期分别从哪读（2026-09-18 追问「是不是 GitHub 上的」）

答案两边不一样：壳那个不在 GitHub（壳自己随身带着），插件那个在（GitHub 上的目录文件里）。

谁写的存在哪怎么读拿不到时
壳的构建日 壳发布脚本 scripts/write-product-json.mjs——发布那一刻的机器时间 壳自己的身份文件 electron/product.json 的 date 字段，随安装包一起打进去 运行时读它 → 随 app:getProductInfo 下发界面 · 离线可得 仓库/开发期恒为空（发布脚本跑完还会还原成占位）⇒ 显示 — ⇒ 判「兼容」
插件的发版日 插件发版时由 SDK 写（publish 命令；同一动作里先建 GitHub Release，再写这个时间） 官方目录：GitHub 仓 encaron/linkdesk-marketplace 的 marketplace.json，每个条目的 publishedAt（第三方源同形状，写在自己那个源里） 从目录读（联网或已有缓存） 离线 / 本地侧载插件没有目录来源 ⇒ —

两个连带事实（都会影响「怎么算」）

  • 插件包自己身上没有日期——拆开产物里那份清单（plugin.json）实测只有 pluginId / name / version / icon / description / author / entry / contributes …，没有任何日期字段。所以「看看插件文件本身就知道它哪天发的」这条路走不通，发版日只能问目录。
  • 本地确实有一个日期，但它不是发版日：安装账本里记着 installedAt = 我哪天把它装上的（首次装记一次，以后升级不改）。它晚于作者发版日，拿它顶替会把「兼容」误判成「正常」。

这样分工是有意的：壳的构建日放自己包里 ⇒ 离线也能判，不受 GitHub 通不通影响；插件的发版日放目录 ⇒ 目录本来就是「谁发了什么」的登记处。

这套机制今天还没落地：第 8 层 6 格判据（E6#114–E6#119）2026-09-18 立案，全部未勾；壳里 grep compat 零命中。（同日该层另立第 7 格 E6#120＝把那张悬停卡从插件自有件抽成壳的共享件，与本图讲的口径无关。） 落地后两个连带事实要提前知道：

  • 「兼容」的日期比较跟 ui 包无关，比的是插件发布日与这只壳的构建日。
  • 尺子第一次跑起来，会把既存的旧账照亮（宿主过去改名留下的悬空名）⇒ 上线时可能有一批插件被标「部分不适配」。 那不是新伤，而是第一次被看见；且后果被设计得很轻：标不改按钮行为，装不上的判定仍归 minAppVersion。

9口诀：四行，换任何说法都不跑偏

  1. 能不能装 → 看插件自己手写的 minAppVersion 对壳版本（跟 ui 版本无关）。
  2. 显示哪个词 → 宿主有没有拿走你喊的名字 ＋ 门槛够不够 ＋ 插件发布日 vs 这只壳的构建日。
  3. 能不能用上新零件 → 插件自己去进货 → 重新构建 → 发新版；三步缺一，用户那边什么都不变。
  4. ui 包版本 → 只管第 3 条。前两条它一个字都说不上。

再加一句时间账：包发新版的那一刻，全世界什么都没变——变化只会发生在「某只插件重新发版、且用户更新了它」之后。
