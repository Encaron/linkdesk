> **2026-10-05 用户点单立案**——触发点是一次**真机实证的事故**（用户安装版 `v0.2.41` 上的设置插件彻底不可用，而插件详情页照旧显示「正常」，详见 [01](01-事故复盘-真机实证.md)）。

> **一句话**：`plugin.json` 的 `minAppVersion` 今天**靠作者手写，全仓没有任何机械件核对它撑不撑得住插件本身** ⇒ 插件可以声明一个过低的地板、装到旧壳上**当场整只崩**，而市场拒装腿、加载器、兼容读数**一律照旧说「正常」**。本件把那个数字改成**由工具从「插件实际用了什么」算出来**，并补齐作者面说明、脚手架默认值、读数腿与第一方流程腿。
> 🔴 **产品决策权不在本件**——本件只保证「声明为真、读数不撒谎、作者知道该下哪个壳」。**要不要让某只插件在旧壳上"优雅降级"是产品/作者的选择，不是门禁的义务**（[02 §六](02-设计-账本与门禁.md) 有专节说明为什么）。

## 一、缘起（用户 2026-10-05 原话要点）

1. 市场插件详情页显示「正常／兼容模式」之类；起效规则是**插件自己声明适配哪个软件版本**。
2. 质问：**这个东西是不是根本没有门禁？** 设置插件 changelog 明明写了「要求 LinkDesk 0.2.48 或更高」，装 `0.2.41` 的机器上插件详情页**照旧显示「正常」**。
3. 结论诉求（用户原话收敛）：**「插件侧写 `minAppVersion` 能不能有个机械门禁，而不是仅仅在 changelog 提到，结果仍旧显示正常」**。
4. 第二诉求：方案必须经得起 **归一化 · 插件独立化（自由插件）· 高内聚 · 低耦合 · 无硬编码 · 无死代码 · AI 友好性** 七项检验。
5. 第三诉求（环境不对称，**方案的地基**）：我们（第一方）与第三方作者**环境不同**——见 §三。

## 二、根因（一句话）

**`minAppVersion` 是"作者的声明"，不是"工具的结论"。** 全仓唯一的机械件只检查「**你声明了没有、够不够一个历史常量**」，它**从不检查你声明的地板撑不撑得住你实际用的东西**。于是「声明」与「事实」之间没有任何东西桥接——changelog 里那句真话进不了机器，`plugin.json` 里那个假数字也没人反驳。

机制层根因（真机取证）：插件入口 **顶层静态具名导入**了壳池 vendor 的 `@linkdesk/ui` 里**旧壳不存在**的组件 ⇒ **ESM 链接期失败** ⇒ **整只插件模块图死掉**，不是"某个功能不出现"（[01 §二](01-事故复盘-真机实证.md)）。

## 三、地基：两套环境不对称（🔴 方案必须站在第三方那一侧）

| | 我们（第一方） | 第三方作者 |
|:--|:--|:--|
| 手上有什么 | 壳源码 ＋ **未发布的 dev 壳**（可拿来 build/测） | **只有下载下来的已发布壳**；不碰壳源码、不读壳仓、无壳的 git tag |
| 造插件的基准 | 可以（也会）拿 dev 壳当基准 | **他下载并测过的那个壳版本** |
| 发布节奏 | 壳攒批（发一次 20–30 分钟）；插件快（1–2 分钟）⇒ **随手发** | 自定 |
| 因此特有的病 | **能把"依赖未发布壳"的插件发出去**（本次事故） | 结构上不犯这一条 |

**三条硬推论（写死在方案里）**：

1. **判据必须自足**：账本随 **SDK npm 包**下发，第三方 `npm i` 之后**离线**可判——⛔ 绝不能让作者去读壳仓／壳的 tag／任何只在我们机器上的东西（否则插件就不独立了）。
2. **门禁只判一个方向**：软件方承诺**向前兼容**（新壳跑旧插件没问题）⇒ 唯一失败方向是「**插件要的壳比用户的新**」⇒ 门禁只需判 **introduced-in**（组件首次随哪个壳提供），不需要管反向。
3. **「插件跑到壳前面」是第一方特有的洞** ⇒ ⛔ **不许塞进 SDK／作者面**，那是我们发布链的家务事（G5，落点在壳仓）。

> 🔴 **措辞纪律**：官方插件与壳**不是同仓**——它们是 `E:/linkdesk-plugins/{official,third-party,linkdesk-marketplace}` 下各自独立的仓，与壳仓只是**同一块硬盘上的邻居**。壳仓里的 `bundled-plugins/*.linkdesk-plugin` 是**构建产物（出厂种子下料）**，不是源码。**官方插件享受的等级与第三方完全一致**（硬约束 11）。——这条是"万物皆可插件"的禁忌，方案里任何"因为是我们自己的插件所以可以怎样"的口子都是错的。

## 六、边界（⛔ 不做什么）

- ⛔ **不去禁 `@latest`**（禁 = 拿风格绑住插件，违反插件独立化）。`@latest` 造成的错，由门禁判**声明**来兜。
- ⛔ **不许把"优雅降级（动态 `import()`）"写成门禁要求**——那是**风格约束**。门禁只保证「声明为真」；降级与否是作者/产品选择（[02 §六](02-设计-账本与门禁.md)）。
- ⛔ **不许把 G5（第一方发布顺序）塞进 SDK**——污染第三方契约、违反低耦合。
- ⛔ **本件不铺 `window.linkdesk.*` 宿主 API 的同类腿**（调不存在的 API = `TypeError`，mock 宿主**同样源自 `@latest`、同样会藏住它**）——同账本思路可扩展，但**先把 `@linkdesk/ui` 这条腿做扎实**，API 腿另立（见 [02 §七](02-设计-账本与门禁.md)）。
- ⛔ **不引入版本阈值/日期阈值类新发明判据**（照兼容读数既有纪律：时间只做事实展示）。

## 十一、大白话：`since` 到底是什么、为什么要回溯

**要解决的问题只有一个**：怎么知道「这个组件是壳的**哪一版**才开始有的」？

**`since` 就是那个答案本身**——`@linkdesk/ui` 里每个组件都随壳的某一版"出生"。`PluginCard` 这张卡片是壳 **0.2.44** 那版才有的，0.2.41 的壳里**根本没有它**。所以只要一只插件用了 `PluginCard`，它就**不可能**跑在 0.2.41 上。`since` = 「这个组件是壳哪一版开始有的」这个戳。

**有了它，地板就不用作者写了**：把插件用到的**所有**组件的 `since` 取**最大值**，就是这只插件的真实地板——机器算出来的，不是人写的。

**那为什么非要"回溯"？** 因为要算的是**过去已经发布过**的插件（比如 settings 1.0.35），它们用的都是老组件；而今天的 `ui-surface.json` 只记「**有哪些**组件」，**不记「哪一版起有」**。想让门禁当场抓住 settings 这个事故，就必须把**每一个已有组件的 `since` 补齐**——唯一的来源是**壳仓的历史**（每个版本 tag 里存着当时 `ui` 的导出清单，两版一对比就知道谁是新来的）。

**"回溯"具体就是**：翻壳仓的版本标签，从最老的开始，一版一版比对「这版比上版**多导出了哪些组件**」，给新出现的组件打上这一版的号，一路比到最新。这样 `PluginCard` 会被自动打上 **0.2.44**。

**三个选项的区别（一句话）**：
- **A** ＝ **去翻壳仓历史**，把每个组件的"出生版本"补齐 ⇒ 能算出 `PluginCard → 0.2.44`，**本次事故当场抓住**；
- **B** ＝ 不翻壳仓历史，改去翻 **npm 上已发布的 `@linkdesk/ui` 包**做同样比对 ⇒ 绕开 git，但 ui 包号与壳号**已不再一一对应**（E6#166），容易对错；
- **C** ＝ **不补历史**，老组件一律记 `0.2.13`，只有今后新加的才记真号 ⇒ 最省事，但 `PluginCard` 会被记成 `0.2.13`，**这次事故照样抓不住**，等于白做。

**为什么说它是"唯一关卡"**：方案的其余部分（门禁、脚手架、读数腿）全都站在「账本已经有了」这个前提上干活；账本能不能真补出来，取决于壳仓的历史够不够用。**历史补不出来，全案就得换设计。**

## 十二、大白话：D6 问的是「哪些 import 写法算进地板」

**背景**：门禁是**拿正则（文本匹配）扫源码**的，不是真跑一遍 JS。所以要先定：插件代码里"用 `@linkdesk/ui`"有**好几种写法**，**哪些要算进地板**？

### 四种写法长什么样、会不会崩

| # | 写法 | 例子 | 会不会崩 |
|:--:|:--|:--|:--|
| 1 | **静态具名导入**（出事的就是这种） | `import { PluginCard } from "@linkdesk/ui";` | **必崩**——插件一加载这行就必须解析成功，组件不在 ⇒ 整只插件死 |
| 2 | **动态 `import()`** | `const { PluginCard } = await import("@linkdesk/ui");` | **看写在哪**——写在函数/分支里，执行到才解析；写在顶层直接 `await`，就等于第 1 种 |
| 3 | **`require()`** | `const ui = require("@linkdesk/ui");` | 同第 2 种（看写在哪） |
| 4 | **side-effect 导入** | `import "@linkdesk/ui/styles.css";` | **会崩**——不要名字，但加载时一样要去解析这个包/子路径；旧壳上没这个子路径照样炸 |

### 两个选项各是什么意思

**A · 四种写法全计**——只要源码文本里出现**任何一种**指向 `@linkdesk/ui` 的写法，就把它用到的组件算进地板。
- 👍 **不会漏**。门禁只看"文本里有没有"，**不猜"运行时会不会走到"**——因为猜不准。地板宁可抬一点，也不放一只带着旧壳没有的依赖的插件溜出去。
- 👎 **可能"假红"**。例：插件写 `if (高级功能开了) { const { FancyThing } = await import("@linkdesk/ui"); }`，而 `FancyThing` 是 0.2.44 才有的。即使作者认为"旧壳上根本走不到这行"，门禁**照样**要求他把 `minAppVersion` 抬到 0.2.44 ⇒ **他想做"旧壳上优雅降级"，门禁会拦住他**。

**B · 只算顶层静态导入**——只认第 1 种，第 2/3 种出现也不计入。
- 👍 **不误伤**。作者真写了降级（动态 `import()` ＋ `try/catch`），门禁不会硬逼他抬声明，**尊重"插件独立化"**（作者有权让旧壳上少一块功能）。
- 👎 **会漏，而且漏就是漏红**。① side-effect 导入（第 4 种）被漏掉——它一样会在加载时解析、一样会崩；② 作者若把 `await import("@linkdesk/ui")` **写在顶层直接 await**（构建产物里很常见），它跟第 1 种一样**必然执行、必然崩**，B 却看不见 ⇒ **该抓的没抓住**。

### 我的建议：A

理由：本次事故的教训就是**「漏报比误报贵得多」**——误报只是让作者把数字抬一点（多打几个字），漏报是**整只插件在用户机器上静默全崩**。而且 A 与**现有采集器是同一套正则**，属于"不新造东西"（高内聚）。

诚实补一句：将来若作者普遍反映"我明明做了降级、门禁还逼我抬声明"，那时**可以考虑**给"带 `try/catch` 的动态 `import()`"开口——但那是后续的事，而且必须极其小心，别把本次事故的口子又开回来。这正是 **D4 已拍"零豁免"** 的原因。
