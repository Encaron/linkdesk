## 〇、上架是两步，不是一步

| 步 | 动作 | 结果 | 谁做 |
|:--:|:--|:--|:--|
| **①** | `npm run publish`（= `linkdesk-plugin-sdk publish`） | 条目写进**插件自己仓**的 `marketplace.json` + 该仓 Release 带 asset | 插件（自动） |
| **②** | 条目并进 **官方目录** | **所有用户默认可见** | 今天手工（PR / 手工 PUT） |

**只有第一步的后果**：东西在网上，但**只有「手动加了这个源 URL 的人」能找到它**。⇒ 用户卸载后想装回来，得记得那个 URL。

**这正是你「一个都不敢卸」的解药**——只有进了官方目录，卸载才是安全的。实查官方目录（`Encaron/linkdesk-marketplace` 的 `marketplace.json`）当前**只有两条**：`hello-linkdesk` 与 `first-run-setup`。**18 只发货插件一只都没进去。**

> 📖 机制依据：[01-GitHub-Releases方案.md §6.7 官方目录收录](../03-插件市场/01-GitHub-Releases方案.md)（2026-08-30 混合模型定案）。**官方收录 + 多源并存**：不收录 = 只在自己仓发布，用户/AI 手动加源可见。作者可以先自仓发（立即可用）→ 想扩大影响再收录官方。

## 二、第二步：官方目录收录（今天手工，需补工具）

### 2.1 现状与风险

**现状**：把条目并进 `Encaron/linkdesk-marketplace` 的 `marketplace.json`（发 PR 或手工改）。

**风险（这是本轮必须造工具的理由）**：18 只逐条手敲，**一定会把那个 json 改错**——而它一坏，**所有人默认可见的货架全坏**（该文件是内置默认源，用户零操作就会拉它）。

### 2.2 要造的东西（建议）

`scripts/sync-official-catalog.mjs`（**放壳仓 `scripts/`**，因为它维护的是「我们发布的这批插件」的集合账）：

```
① 读壳仓的 bundled-plugins.lock.json（7.4 轮产出）→ 得到 18 只的 owner/repo
② 逐仓 fetch raw.githubusercontent.com/<owner>/<repo>/main/marketplace.json
③ 合并成一份官方目录（同 id 取版本高者；保留既有第三方条目不动）
④ 输出到临时文件 + 打印 diff（新增/变更/删除各几条）
⑤ 由用户过目后手工落进 linkdesk-marketplace 仓（PR 或直推）
```

**边界（不越界的地方）：**
- 🔴 **脚本只生成、不推**——写的是另一个仓库，推送照 memory `push-wait-for-user` 办（用户点头）。
- 🔴 **不许删既有第三方条目**：官方目录里可能有非官方作者的插件（§6.7 的收录路径）。合并逻辑必须是「**只增改自己这批 + 不动别人的行**」，**禁止整文件覆盖**。
- 🔴 **不许把 18 个 id 写死在脚本里**（硬约束 10）：清单来源 = `bundled-plugins.lock.json`（数据文件），不是代码字面量。理由见 [05-出厂种子保鲜.md §五](05-出厂种子保鲜.md)。

### 2.3 为什么第二步本身没法全自动

**它是「官方货架」的编辑权**，天然要人过一眼（§6.7 的早期形态就是「作者给官方仓库发 PR」——**轻量审核是设计的一部分，不是没做完**）。工具的价值在于**把「18 条手敲」降成「看一眼 diff」**，不是取消这一步。

### 7. 🔴 本轮抓到一个**壳侧真缺陷**（不在本层改动面内，如实登记）

**现象**：干净 profile 里点图标栏「设置」**不切换侧栏**；往复操作后，布局里出现**坏标签**：

```json
"id": "[object Object]-2",
"type": { "type": "settings" },
"pluginId": { "type": "settings" },
"label": "[object Object]"
```

**当场日志**（`Runtime.consoleAPICalled`）：

```
[error] [PluginComponent] pluginId 非法（期望非空 string，收到 object），拒绝加载。完整值： { "type": "settings" }
[EXCEPTION] Error invoking remote method 'plugins:resolveEntry': TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received an instance of Object
[error] [wire-guard] 🔴 channel=pool:layout 载荷形状失配: payload.groups[0].tabs[2].pluginId: 期望 string，实收 object
```

**已定位的链路**（三处都读得到）：

1. **一个对象被当成 `type` 传进 `tabs.create`** ⇒ `src/core/services/plugins/IpcBridgeHandler/tabs.ts:24` 的 `const [type, opts] = args as [string, ...]` **是位置解构、无运行时类型校验**，对象原样往下走；
2. 往下经 `shellEvents.emit("tab:create", { type })` → `src/App/tabActions.ts:61-63` 的 `createTab(type, opts)` → `reduceCreateTab(..., type, ...)` 把**对象**当 tab 身份 ⇒ 落盘成 `"[object Object]-2"`；
3. `src/pool/shared/plugin-component/PluginComponent.tsx:48` 的守卫**早已在防这一类**（源码注释自陈「累计日志里 `[object Object]` 被当插件 id **六次**——写入者未定位」）——本轮**第一次把写入现场抓成可复现**（`type: {type:"settings"}` 这个确切形状）。

**归属判定**：涉事三处代码的 git 历史分别停在 **2026-08-19**（`ccf1ce933`，池 UI DTO 迁 `types/pool/`）与 **2026-09-09**（`2af05898e`，E6#62e 纯贡献激活），**L7 一个字没动**；`settings` 插件 1.0.6 相对 1.0.5 **只有 `plugin.json` 元数据差异、零源码改动**（`git diff HEAD~1 HEAD --name-only` 无 `src/`）。⇒ **pre-existing 缺陷，不是本轮引入**。

**⚠️ 但它的表现有一层「设计使然」，别改错方向**：`settings` 的 `contributes.viewsContainers.settings.location = "auxiliarybar"`，而 LinkDesk **无该区域渲染**（`floatingPanelDeclarers.test.ts:101` 与 `loader.test.ts:288` 两处单测**明确钉住这个语义**）——设置**本就该以浮动面板打开**（`floatingPanel.viewId`，走 `revealFloating`），**不是**侧栏视图。所以「点设置图标切侧栏」**本来就不该成功**。真缺陷只是**那个坏标签**：某条路径把一个对象当 `type` 送进了 `tabs.create`，落盘成坏身份并让 `PluginComponent` 拒绝加载。

**处置**：不在 7.3 顺手修（越层且非本轮改动面）。**登记归 7.5/后续**——建议修法写在下面「留给下一轮的账」第 3 条。
