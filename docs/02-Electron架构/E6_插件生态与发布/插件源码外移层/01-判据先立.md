## 〇、为什么必须先做这一轮

本层要动的是**「源码住在哪」这条从没被写下来的规矩**。全仓现状：

- `docs/03-插件制造/09-插件目录规范.md` 规定了插件源码目录长什么样，但**一个字都没说「源码该住在哪个仓库」**；
- `docs/03-插件制造/04-插件分发格式.md` 写了「安装目标 `{userData}/plugins/<id>/`」「源码树 vs 已安装是两个代码根」——**但「源码树」在哪，它默认就是壳仓**；
- `docs/05-插件更新/00-README.md:10` 有一句「单个插件的新版本**在仓外独立工程目录开发**」——**这句是未来的设想，不是现行规范**，而且没写「源码本身搬出去、壳仓那份删掉」。

⇒ 不先立这条，"搬出去"在执行层就永远能被理解成「复制一份到外面」（双真相源，无门禁可发现分叉）。

## 一、落点一：插件目录规范补「源码位置与分发物关系」

**文件：** `docs/03-插件制造/09-插件目录规范.md`

**要做：** 新增一节（建议放在现有「分发物 = SDK 构建的单文件 zip」那条之后，紧挨着，因为它们是同一条链的两端），写死五条：

1. **源码真相源 = 插件自己的仓库**（`github.com/<owner>/<repo>`），**不是壳仓**。壳仓内的 `plugins/<id>/` 只允许存在两类东西：**夹具**（不发货的 demo）与**构建产物**（`bundled-plugins/<id>.linkdesk-plugin`）。
2. **壳仓 `bundled-plugins/<id>.linkdesk-plugin` 的语义** = **出厂发货用的种子快照**，其版本由 7.4 轮的 `bundled-plugins.lock.json` 记账。它**不是**源码的第二份拷贝——源码改了必须回插件仓改，改完走发布链路刷种子。
3. **插件源码目录与分发物的关系** = 源码仓 → `npm run build` → `<id>.linkdesk-plugin`（zip）→ GitHub Release asset → catalog 条目。**从源码到用户桌面没有一步经过壳仓。**
4. **插件身份（`plugin.json` 的 id）永不可变**；显示名（`name`）可改；仓库名可改。
5. **插件内有且只有一处版本号真源** = `plugin.json.version`；`package.json.version` 不是真源（7.1 轮 §六 处置它）。

**判据：** 该节里每一条都能在 7.1–7.4 轮里找到消费它的任务；**没有一条描述与 `publish.ts` 的实际行为相反**（逐条对源：[publish.ts](../../../../packages/plugin-sdk/src/publish.ts) 的「目标仓库 = origin」「写仓库根 marketplace.json」「readmeUrl/changelog 自动写」三处）。

## 二、落点二：新建作者面文档「多仓开发与本地工作区」

**文件：** 新建 `docs/03-插件制造/15-多仓开发与本地工作区.md`

> 📌 编号 15 是建议——**落笔时先 `ls docs/03-插件制造/` 取实际下一个空号**（当前最大是 14）。

**要做：** 覆盖四件事，**每件都要有「为什么」**（这份文档的读者包含未来的 AI，只写「怎么做」它会在下一个会话里按自己的理解改掉）：

1. **本地目录约定（D6）**
   - 推荐容器 `E:\linkdesk-plugins\`，内部按**归属**分 `official\` / `third-party\`，**不要按功能分类**（归属稳定，功能分类会随插件增加不断重划；且 catalog 里的 `category` 已经在做功能分类，本地再分一遍是重复）。
   - 🔴 **容器目录本身绝不建仓。** 理由写清楚：一旦容器被 `git init`（IDE 的「初始化仓库」提示、在错层级敲 `git init`、从父目录 `git add .` 都可能触发），每只插件的 `.git` 变成嵌套仓、父仓把它们记成 gitlink——**静默坏掉且极难看出来**；更要命的是它会**把脚手架的「已在 git 仓内 → 不 init」规则反转成灾难**（每只新插件都不建自己的仓，全变成容器子目录 = 你要避开的 monorepo）。
   - **容器里放一张说明**（`README.md` 或 `不要在这里建仓.txt`）——防的不只是作者本人，还有以后进场读目录的 AI。
2. **插件仓命名（D5）**：仓库名**完全自由**，不强制任何前缀。给出**建议但非强制**的惯例，并写明**改仓库名的代价**：已发布 catalog 条目里的 `downloadUrl` / `readmeUrl` 内嵌 `owner/repo`，改名会断链（源码不受影响）。
3. **身份 vs 显示名 vs 仓库名（D5）**——照 VS Code 实测口径写（§五 引用块）。⚠️ **这一条不止两行**：它牵出「插件身份今天靠目录名兜底」这个结构问题 ⇒ **完整展开与落地在 [09-命名规范.md](09-命名规范.md)**，本落点只负责把结论落进作者面文档（**引用而非复制**）。
4. **本地目录位置与插件身份无关**（这是本层最重要的一条性质，也是 `hello-linkdesk` / `first-run-setup` 平铺在外的正当性）：插件仓是自足的，`git clone` 到哪都能构建；壳只认 Release URL 与 catalog，**不认本地路径**。⇒ 目录结构随时可重排，零风险。
5. **发布链路上的四个名字不许手改**（`<id>.linkdesk-plugin` / `v<version>` tag / 版本号格式 / `pluginId`）——它们参与安装裁决与更新对账，**手改即身份漂移或更新链断**（[09-命名规范.md §一/§五](09-命名规范.md) 的规则表）。

**判据：** 一个没参与过本轮讨论的人只读这份文档，能回答「我的插件工程该放哪、仓库该叫什么、怎么改显示名」。**自测方式：让 AI 在无上下文的情况下读它并回答这三问。**
