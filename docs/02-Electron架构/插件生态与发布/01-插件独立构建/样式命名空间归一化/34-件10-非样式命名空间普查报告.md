# 第 1.30 轮 · `#109r`：**非样式命名空间普查**（件 10·评估）——同一个形状，不止样式一处

> **一句话**：CSS 那一类问题的**形状**是「**一个共享的扁平名字空间 ＋ 多方都能往里写 ＋ 没有归属校验 ＋ 冲突只 warn 不报错**」。本格把它做成一把尺子，量遍**非样式**的所有同族面。
> **🔴 用户猜的一半对、一半不对**：**数据通信**（他猜「应该不会有问题」）—— **对，最要紧的一条已有真门禁**；**声明的东西** 与 **命令类**（他猜「应该也不会有」）—— **都错，这两片问题最多**。另外自查出两条他没点名的，其中 **上下文键是全仓最危险的一条**。
> **编号**：`#109r` · **执行序**：1.29 之后、1.20 之前（**1.20 恒最后**）
> **本格性质**：**评估轮 ⇒ 零代码改动**（只读 `src/`＋`electron/`；只写本档与新档）。**落地另立轮次。**
> **非新能力声明（`check-design-flow` §8.4 ③）**：本档是**既有命名空间的普查与判据设计**，不新增用户能力、不改任何机制。⇒ 无需新能力设计前置。

## 〇、立项与定位

**用户原话**：「**那你感觉除了 UI 这部分外，其余部分有没有类似的问题？如数据通信部分？我想这个应该不会有吧？又或者声明的东西，又或者命令类。**」＋「**不仅仅是我提到的，你还可以自己再找一找。**」

**同形判据（四条全中才算同形）**：

| # | 判据 | 说人话 |
|:--:|:--|:--|
| 1 | 名字空间是**扁平的** | 名字里没有天然归属（`format` 不告诉你它是谁的） |
| 2 | **多方都能写入** | 宿主 ＋ 官方插件 ＋ 第三方插件都能往里写 |
| 3 | 写的时候**没有归属校验** | 不检查「这名字是谁的」 |
| 4 | 🔴 **冲突静默** | 不报错；最好也只是 `console.warn` —— 而 warn **对用户不可见、对「被覆盖的那一方作者」也不可见**（他在自己机器上没装对方插件，一切正常） |

⇒ **第 4 条是关键**：**「被覆盖」这件事，受害方永远收不到通知。** 这正是 CSS 那一类难查的物理原因，也是本格排严重度的唯一尺子。

**🔴 本格定位（2026-09-16 用户拍板）**：本轴**不是一个轮次做得完的**——命令 id / 设置键 / 主题·图标·语言 id / 上下文键 / i18n 键 / `pluginState` / 快捷键 chord **每一个都至少一格** ⇒ 本格只做**点名轮**（立判据 ＋ 普查 ＋ 挂账带 file:line ＋ 建议轮次表），**深查与派工交给新系列第 0 格**（由 1.20 收口那棒交棒）。⛔ 本格**不定案落地、不派具体格**。

## 三、严重度排序（🔴 **按「受害方能不能察觉」排——不许按技术严重性排**）

> **这是本格的核心判据**：CSS 那一类之所以难查，就是**受害者看不见**。同一把尺子量下来：

| 档 | 判据 | 条目 | 为什么在这一档 |
|:--:|:--|:--|:--|
| 🔴 **S1 最高** | **受害方收不到任何信号**（连 `console.warn` 都没有） | **④ 上下文键** · **⑥ `pluginState`** · **⑤ i18n**（连 warn 都没有，但跨仓不可判） | ④ 改的是**宿主菜单/快捷键的可用性**（**行为**，不是外观——「界面没变」让你根本不会怀疑）；⑥ 是**越权读写**（能碰宿主 `"app"` 桶）；⑤ 静默换措辞 |
| 🟠 **S2 中** | 有 `console.warn`，但 warn **只在「覆盖发生的那台机器」**上打印 ⇒ 用户看不见、被覆盖的作者也看不见 | **① 命令 id** · **② 设置键** · **③ 主题/图标/语言 id** · **⑦ 快捷键 chord** | ① 的后果是**功能级**静默（点「格式化」执行别人的 handler）；⑦ 是**按键行为**变了；②③ 是配置/外观被顶替 |
| 🟡 **S3 低** | 有 UI 提示或用户可感知 | **⑧ 视图 id**（复合键共存 ＋ 开发期 error）· **⑨ 容器 id**（首主保有）· **⑩ 插槽**（追加而非覆盖） | 都**不覆盖**，只是共存/污染 ⇒ 用户最多看到多一项 |

🔴 **S1 与 S2 的分界不在「技术严重性」，而在「有没有一行 warn」**——① 命令 id 的技术后果其实比 ⑤ i18n 更重（功能级 vs 文案级），但因为它**至少有一行 warn**，受害方作者在复现环境里**有机会**看到；而 ④⑥ **连机会都没有**。

## 四、逐条选修法与理由

> 四条候选修法（照 [22 号档](22-收口总方案-跨方样式污染九件套.md) 的[宽容度模型](22-收口总方案-跨方样式污染九件套.md)）：
> **(a) 归属前缀**（`<pluginId>.` / `<pluginId>-`）—— 与 CSS 同款，**结构性、零表** · **(b) 首撞者保留 ＋ 后来者降级不覆盖 ＋ 明确提示** · **(c) 只黄灯 ＋ 文档**（跨仓不可判的） · **(d) 宿主键保护区**（插件不得占用 `app.*` / 宿主 context key）

⚠️ **先回应 [30 号档 §三.3](30-任务-非样式命名空间普查.md) 的顾虑（本档必须正面回答）**：`ConfigurationRegistry.ts:120-121` 注释自述 ——

> 「**parseContributions 没有 try/catch，抛错会导致整个插件加载失败。待 E2c #19b 审计后改 fail-fast。**」

⇒ **「冲突即拒绝加载」太狠**（一个第三方插件的重名会让**整只插件废掉**，用户侧表现为「装不上」）。**本档六条 🔴 一条都不选「抛错」**，理由逐条见下。

| # | 面 | 修法 | 理由（为什么是它、不是别的） |
|:--:|:--|:--:|:--|
| ① | **命令 id** | **(a) ＋ (d)** | `(a)` 前缀最直接（`<pluginId>.command`），与 CSS 同款结构性、零表；`(d)` 补一条「插件不得占用宿主命令前缀（`app.` / `workbench.`）」——宿主命令今天就用这两个前缀（`shellMenus.ts` 全篇 `workbench.action.*`），**天然现成的保护区**。⛔ 不选 (b)：命令是**功能性**的，降级不覆盖会让「我注册了命令但点不动」，比 warn 更难查 |
| ② | **设置键** | **(a) ＋ (d)** | 同上；⚠️ **(a) 会用得上「插件本来就有 pluginId 前缀」这个既有事实**——只需把 `app.*` 划为宿主保护区即可（今天 3 个宿主注册点用的正是 `"app"`/`"appearance"`/`"update"`，见 `appearance.ts:55`·`update.ts:22`·`startup.ts:94`）。⛔ 不选抛错（[30 号档 §三.3](30-任务-非样式命名空间普查.md) 的顾虑）；⛔ 不选 (b)：配置项被顶替后**设置面板显示的是别人的 schema**，比缺失更坏 |
| ③ | **主题/图标/语言 id** | **(a) ＋ (d)** | 🔴 这一条**比 ①② 更该用 (a)**：id 会被**用户配置持久化**（`app.theme` 记的就是 id）⇒ 卸载/顶替后**指向谁更隐蔽**（用户下次开软件发现「主题变了」却找不到原因）。`(d)` 保护区 = `theme-defaults`/`lang-defaults` 这类**出厂种子**的 id |
| ④ | 🔴 **上下文键** | **(d) 为主 ＋ (a) 为辅** | **(d) 是第一优先**：宿主自己读 5 个键（`sidebarPosition` · `settingKey` · `settingModified` · `settingResetsToDefault` · `settingFollowTheme` · `updateActionable` · `activeEditor`）⇒ **必须把这些划为宿主保护区**，插件写它们 = 拒绝 ＋ 提示；`(a)` 要求插件键带 `<pluginId>.` 前缀。⛔ **注意 `when` 是跨方契约**：插件**读**宿主键是合法的（`when: "activeEditor == 'xxx'"` 是官方特性）⇒ **只禁写、不禁读**——这条边界必须写进落地任务书，否则会做出假红 |
| ⑤ | **i18n 字典键** | **(c) 只黄灯 ＋ 文档** | ⚠️ **沿用记忆 `plugin-repo-gate-model` 的既有结论，不重开**：键**可以合法住在应用级字典**（插件翻译宿主文案是正当需求）⇒ 跨仓硬判必出假红，**而假红会让真红失效**。⚠️ 但本档**新增一条可机械的事实**：`i18nResources.ts:10-11` 的注释自己写明「两个插件共用顶层键时会误删对方子键」⇒ **这条可以进作者面文档**（把既有的隐式知识显式化） |
| ⑥ | 🔴 **`pluginState`** | **(d) 为主（sender 校验）** | 🔴 **这一条的病根与别条不同**：它不是「命名空间没前缀」，而是 **`pluginId` 由调用方传入、跨 IPC 零校验**（`data.ts:36-44`）⇒ **修法必须是「从 sender 反查真实 pluginId」**（主进程已有 `getWindowIdByWebContents` 这套 sendar 映射，`ipc-bridge.ts:211-214` 是现成先例）。(a) 在这里**没用**——因为攻击面不是名字，是**身份**。⚠️ 这条**优先级与 ④ 并列第一** |
