## 〇、一句话总览（大白话）

**#69 把「插件身份图」这件事做通了一半——本地那一半。**

插件装在本机时，市场行/详情页/标签栏读的都是**包里那份 `plugin.json`**，于是彩色身份图（`marketIcon`）显形正常。
可插件**没装**的时候，市场只能读**目录条目**（网上那份 `marketplace.json`），而那条链路上**从来没有人搬过 `marketIcon`**——`publish` 只搬 `icon`。对图标栏那 4 只插件来说，`icon` **按设计就是那张白色线稿剪影**（图标栏专用）。于是：

- 市场「探索插件」列表 → 白线剪影（串口那只 = 一条心跳线，即 codicon `pulse`）
- 已装列表 / 详情页 → 彩色身份图

**同一个插件，两张脸。** 用户 2026-09-14 实机一眼看出来：

> 「我插件市场里面……像文件树、串口监视器、还有设置，他们都是那种画的线条形状的图标……如果我把它删除之后它就没了，然后本地也没了，然后我把它重新下载之后本地这个就是有图标的这个样子彩色图标的这个样子……为什么上传到网上之后显示的图标它和下载到本地里面图标不一样。」

用户当时的记忆是准的——他确实定义过两类图标（图标栏图 / 市场展示图）。**缺的不是定义，是上传那条腿的接线。**

## 一、根因三条（带 file:line 证据）

### ① 主因：`marketIcon` 从没进过发布链路

身份图只声明在 `plugin.json`，而把它送上网的整条链路**逐环都没有它**：

| 环节 | 位置 | 现状 |
|:--|:--|:--|
| SDK 发布视图 | `packages/plugin-sdk/src/publish.ts:238`（`ManifestView`）· `:255`（`collectManifestView`） | 只有 `icon` / `iconSource`，**无 `marketIcon`** |
| SDK 条目构造 | `packages/plugin-sdk/src/publish.ts:283`（`buildCatalogEntry`） | 只写 `icon` / `iconSource` |
| 各插件仓产物 | `市场容器/<id>/marketplace.json` | 18 只**全部**零 `marketIcon`（实证扫描） |
| 官方目录 | `Encaron/linkdesk-marketplace` 的 `marketplace.json` | 20 条**零** `marketIcon`（api.github.com 实读） |
| 市场侧契约 | 插件仓 `marketplace/src/services/marketCatalog/types.ts:14`（`CatalogEntry`）· `parse.ts:38`（逐字段白名单） | 无该字段（白名单文件自带警告「漏字段 = 静默丢，务必同步」） |
| 市场行裁决 | 插件仓 `marketplace/src/views/sidebar/ExploreView/CatalogRow.tsx:47` | `pickIdentityArt(entry)` —— 只有目录条目一个候选 |

**而下游这几处明明是通的**（说明数据本身有、只是没走这条路）：

- SDK 打包：`packages/plugin-sdk/src/vite-config.ts:564-567`（`marketIcon` 资产同 `icon` 待遇拷进 `.linkdesk-plugin`）
- 壳 list()：`src/core/services/plugins/IpcBridgeHandler/pluginManager.ts:64-71`（`icon` + `marketIcon` 双对随行）

⇒ **断点精确定位在「publish 写目录条目」这一处。**

### ② 并发缺陷：目录条目里的图标是**包内相对路径**，未装即打不开

目录里存的是 `"icon": "resources/icon.svg"`。`resolvePluginIcon`（`src/components/shared/plugin-icon/iconUtils.ts:59-67`）把它拼成 `linkdesk://<id>/resources/icon.svg`，而该协议只在本地插件根里找文件（`electron/plugins/protocol.ts:36-42`：prod = userData 安装家；dev = 源码树 + userData）。

⇒ **插件没装 = 404 = 空图。** 这正是用户说的「删掉之后它就没了」。
线上 20 条里，**只有手写的 `first-run-setup` 用了绝对 URL + `iconSource:"url"`**——它是唯一一条未装态也能显形的条目（也证明这套形态本来就是对的、能用的，见 [01 方案 §3.2](01-GitHub-Releases方案.md) 已登记的「`icon` url 形态」）。

### ③ 归一化缺口：列表行与详情页的裁决顺序不一致

| 位 | 代码 | 候选序 |
|:--|:--|:--|
| 详情页顶 | 插件仓 `DetailView.tsx:146` | `pickIdentityArt(info.manifest, entry)` —— **已装优先** ✅ |
| 已装列表行 | 插件仓 `ExtensionItem.tsx:81` | `pickIdentityArt(plugin.manifest)` —— 已装 ✅ |
| 市场目录行 | 插件仓 `CatalogRow.tsx:47` | `pickIdentityArt(entry)` —— **只有目录** ❌ |
| 禁用列表行 | 插件仓 `DisabledListView.tsx:59` | `pickIdentityArt(catalogById.get(id))` —— **只有目录** ❌ |

`pickIdentityArt` 的签名本意就是「候选按序、先到者先供字段」（`iconUtils.ts:96`，注释写着「已装 manifest 优先于目录条目」）。行组件少传了第一个候选。

🔴 **这条不是美化项、是防回归项**：把目录 `icon` 改成绝对 URL 之后，已装/禁用行若不接本地 manifest，就会**静默转去拉远程图**——既破 [06-图标.md](06-图标.md)「已装不读远程目录图标」这条边界，又**断网即裂图**。所以 #106c/#106d 是必做。

### ④ 上一轮（#69）为什么没抓到——以及一句必须删掉的错注释

- #69 收官提交 `e47a14358` 的验收记录写的是「官方目录 22 行 Type-2/默认插头块」——**剪影那 4 行被漏过去了**（当时验的是「不再是 📄 / 不再是几何符号」，而剪影确实不是这两样）。
- 4 天后 market 插件拆分（#86b）时，`CatalogRow.tsx:9-11` 留下一句：

  > 「目录条目本无 marketIcon 字段（**架构三图模型：目录只存 icon；marketIcon 只在已装 plugin.json 内**）」

  这句话**同时与两份设计文档相反**——[06-图标.md](06-图标.md) 字段机制表写的是「Type-2 身份图 = 市场侧栏行 + 详情顶**同一张**」，[14 档案 §三.2](14-市场图标系统任务档案.md) 更明写了「未装展示图来自 catalog……**两条分发路（打包 zip 内 + 目录 json 内）**」。**它不是任何一次拍板，是拆分时顺笔写下的事后合理化**（`git log -S` 可证首次出现在拆分子件那次提交里）。

  ⇒ 与硬约束 11「代码注释中禁止发明 schema 里没有的分类名词」同型：**一个 bug 被一句注释包装成了架构定论**。本轮必须订正，否则下个 AI 会照它继续错。

## 二、全量核对（2026-09-14 实测，逐只读 manifest + svg 本体）

市场行的显示结果由「目录条目的 `icon`」决定；身份图由「包内 `marketIcon`」决定。二者只有**非图标栏插件**时才碰巧同源。

| 插件 | 包内 `icon`（图标栏位） | 包内 `marketIcon`（身份图位） | 目录条目 `icon` | 市场行实际显 |
|:--|:--|:--|:--|:--|
| **file-tree** | `icon-bar.svg`（白剪影 `#F8FAFC`） | `icon.svg`（7 色渐变） | `resources/icon-bar.svg` | ❌ 剪影 |
| **serial-monitor** | `icon-bar.svg`（codicon `pulse`，即「心跳线」） | `icon.svg`（6 色渐变） | `resources/icon-bar.svg` | ❌ 剪影 |
| **settings** | `icon-bar.svg`（白剪影） | `icon.svg`（4 色渐变） | `resources/icon-bar.svg` | ❌ 剪影 |
| **marketplace** | `icon.svg`（currentColor 字形 = 白线） | `icon-brand.svg`（5 色渐变） | `resources/icon.svg` | ❌ 白线 |
| 其余 12 只（editor / lang-defaults / python / theme-aurora-glass / theme-mint-soda / theme-terminal / theme-zones …） | 即身份图（彩色渐变） | 无（设计如此，非图标栏插件 `icon` 兼 Type-2） | `resources/icon.svg` | ✅ 彩色（但**未装时 404**，见根因 ②） |
| 其余 4 只（lang-test-ja / theme-defaults / theme-iconset-pastel / theme-panorama / theme-pill / theme-songti / theme-twilight-forest） | 无 | 无 | 无 | ✅ 统一默认彩色块（零图可发契约） |

**受影响面（精确）**：

- **显错**：4 只图标栏插件（正是用户点名的三只 + 他当时正站在里面的 marketplace）。
- **未装即空**：11 条带图标的条目里，**11 条全是包内相对路径**——插件没装的市场行/详情顶都是 404 空图。用户本机 20 只全装着（`%APPDATA%\linkdesk\plugins` 实测），所以这一半**还没被他的视角暴露出来**。

## 三、修法五步

> 🔴 **核心判断：这件事只能在发布端修。** 只有 `plugin.json` 知道「身份图是 `icon.svg` 而不是 `icon-bar.svg`」；市场端再聪明也变不出这个信息（它能解决「够不够得着」，解决不了「选哪张」）。

### 第 1 步｜SDK：目录条目带身份图，且一律 URL 形态（#106b，治根因）

- `ManifestView` / `collectManifestView` 增 `marketIcon`(+`marketIconSource`)；`buildCatalogEntry` 写入。
- 值转换规则：已是 `http(s)://` → 原样带；**包内相对路径 → `https://raw.githubusercontent.com/{owner}/{repo}/v{version}/{相对路径}`**——与既有 `readmeUrl` **同一拼法、同一 tag**（`publish.ts` 里现成那套），**URL 规则只此一处**（防两份漂移）。
- 缺省仍**不写键**（沿用本仓「缺省即不写该键」纪律）。
- `icon` 同样 URL 化（否则未装的 6 只非种子插件图标照旧是空图）。
- 单测：URL 化 / 已是 URL 原样 / 缺省不写键。

### 第 2 步｜市场插件：契约补字段 + 行裁决归一 + 永不空白（#106c）

- `CatalogEntry` 类型 + `parse.ts` 白名单补 `marketIcon` / `marketIconSource`（白名单文件自己就写着漏字段会静默丢）。
- `CatalogRow` 改走 `pickIdentityArt(已装 manifest, entry)`——与详情页同序（`useMarketplacePlugins().all` 已在手）。
- `<img>` 加 `onError` → 落 `DEFAULT_PLUGIN_IDENTITY_URI`（今天 `linkdesk://` 404 就是一片空白，不该这样）。

### 第 3 步｜禁用子集图标通道（#106d）

- `PluginInfoEntry`（`contracts/linkdesk.d.ts:1195`）补四字段；`getDisabledPluginInfo`（`src/pluginLoader/lifecycle/lifecycle-ops/query-projections.ts:80`）投影随行——**照 E6#65a 给 `list()` 补图标通道的同一先例**（同一个「缺数据通道」的坑，这是第二处）。
- `DisabledListView` 已装优先消费。

### 第 4 步｜回填 18 只插件仓（#106e/#106f）

- 各仓 `marketplace.json` **只改条目元数据**：URL 化 `icon`、补 `marketIcon`。
- 🔴 **不动 Release、零版本 bump**：`publish` 以 `plugin.json.version` 为 tag，tag 已存在会被拦；纯元数据回填用壳仓工具直接改 json 更干净。工具须**可复跑 + `--check` 空跑核验**，且数据一律**读各仓 `plugin.json` 声明**（不手抄——手抄 18 只必错）。
- 官方目录用 `npm run catalog:official` 重生成（其自身纪律见脚本头注：只生成不推、禁整文件覆盖、不许写死 18 个 id）。
- 收敛性：修好后的 `publish` 写出的值 = 回填写进去的值，故**下一次真发布不会把回填结果改回去**（`publish.ts:325` 的「保历史字段」分支会保留同值）。

### 第 5 步｜文档 + 门禁（#106g/#106h）

- 文档：[06-图标.md](06-图标.md)（补「目录条目字段」+ 未装读目录 / 已装读包内两条路）· [14 档案 §三.2](14-市场图标系统任务档案.md)（补记「落地漏了 publish 一环」）· [01 方案 §3.2](01-GitHub-Releases方案.md)（新增字段表补 `marketIcon` url 形态）· 作者面中英两棵树（`icon`/`marketIcon` 三档契约）· `CatalogRow` 头注错定论订正。
- 门禁：插件仓 CI「声明自洽」腿（脚手架模板 `scripts/ci-verify.mjs:347-351` 已有「`icon`/`marketIcon` 文件必须存在」）**扩一条**：目录条目里出现的图标字段必须是**可远程解析的绝对 URL**——**纯字段形态断言，不引入「谁是图标栏插件」的 ID 知识**（守硬约束 10）。

## 四、边界与不做

1. **不做市场端「相对路径 → 远程 URL」推断**。看似能自愈存量，但它会在市场里长出**第二个 URL 构造点**（归一化违规），且把「目录条目是否自足」这件事变得含糊。存量由回填解决（用户 2026-09-14 拍板「所有插件都更新」）。
   - 代价（如实记）：**用旧 SDK 发布过的第三方条目**，在作者重新发布前，未装态会落统一默认彩色块（不再是空图——`onError` 兜底）。当前线上无此类条目（20 条 = 自家 18 + 手写 2）。
2. **不动 `appearsIn.iconBar` 的「4 只」判据**。「谁是图标栏插件」仍由各插件 `plugin.json` 声明涌现（硬约束 10），本轮不引入任何插件 ID 字面量。
3. **不动三图模型的语义**（Type-1 / Type-2 / 场景封面）。本轮只补「Type-2 怎么上网」这一条腿。
4. **已装读包内**这条边界继续守：已装插件的图标只从包内取（作者换图随版本更新获得）——故必须做 #106c/#106d 的「已装优先」。
5. **零 bump**：18 只插件仓不升版本（只改目录元数据）；壳侧走软件 PATCH；marketplace 因源码变更需 bump + zip 重建 + 种子刷新。

## 六、后继：发版路上暴露的机制缺口（E6#107，2026-09-14 同日收口）

本轮把「图标修好并推上去」这条路真走了一遍，于是**顺带撞出两个与本 bug 无关、但更贵的机制缺口**——
两个都不是外部因素，是自家流程的真空。用户当晚问「一直红的 bug 是我们的问题吗」→ 结论是，已分别收口：

### 6.1 CI 从 7.6 轮起必红，而本地全绿（→ `check-lockfile-sync`）

- **形态**：`Build and Release` 自 `2dbf87dcc`（L7 第 7.6 轮升 `create-linkdesk-plugin` 0.1.2→0.1.3
  **未刷根 lockfile**）起，每一次 `electron` 推送都死在 `npm ci`（13 步里只剩前 6 步跑过）。
- **为什么没人拦**：`npm run check` 的 50 来项门禁**没有一条**看 lockfile，而本地 `node_modules`
  一直在 ⇒ 怎么跑都是绿的。**这是全项目唯一一条「本地绿 ≠ 云端绿」的东西。**
- **代价**：`Release` 步骤全 skipped ⇒ **Release 从未产出**，版本号一路往上走而网上一片空白。
- **收口**：`scripts/check-lockfile-sync.mjs`（离线秒级，挂 `npm run check`）——四条红（根版本 / 依赖键集 /
  workspace 版本名 / workspace 整只缺失）+ 一条黄（孤儿条目，npm 容忍，判红 = 假红）。
  自测 6 例，**负控第一例就是「7.6 那一笔」的复现**。
- **孤儿条目已一次性清掉 18 条**（`plugins/*` 里已搬走的 18 只，lock 里带 `extraneous: true`），当前仓 **0 黄 0 红**。
  ⚠️ 顺带订正一句**本档与门禁脚本初版都写错**的话：「跑一次 `npm install` 就清了」——**实测不成立**：
  `npm install --package-lock-only` 不清；但**手工删条目后重跑也不会写回来**，所以可以一次性清理。
  （教训同型：**门禁/文档里那句「怎么修」必须自己跑一遍**，否则它就是在教人一个无效动作。）

### 6.2 「流程绿」不等于「东西发出去了」（→ 工作流末尾的 Release 核验步）

- **形态**：本地 `npm run publish` 全绿、tag 也推成功、推送也成功——**而线上什么都没有**。
  流程文档写「推 tag 后 CI 负责建 Release 并上传安装包」，但**没有任何环节回头确认过 Release 真存在**。
- **收口**：`.github/workflows/build.yml` 末尾新增 `Verify the Release really exists (E6#107)`——
  回头问 GitHub 三件事：tag 与 `package.json` 同源 / Release 真存在 / 安装包真挂在 asset 里。
  **把静默失败变成同一个 job 的红**（复用既有信号面，不新建告警通道）。

### 6.3 留给下一位的两句话

1. **升 `packages/*` 任一只包的版本号后，必须重跑 `npm install` 并把 lock 一起提交**——现在有门禁盯着了，
   但门禁只能拦，不能替你做。
2. **看到 CI 红，先看死在第几步**：死在 `npm ci` = lock 问题（本档）；死在 `Check` = 代码/文档门禁问题；
   死在 `Release` 之后 = 见 6.2 的核验步。**「本地全绿」不是「能发出去」的证据。**
