## 一、改名执行器

| 项 | 值 |
|:--|:--|
| **路径** | `scratch/rename-nonnaming.mjs`（**不进仓**——`scratch/` 已在根 `.gitignore:52`） |
| **用法** | `node scratch/rename-nonnaming.mjs --plugin <仓目录名> [--space <空间>…] [--base <sha>] [--write] [--root <根>]` |
| **缺省** | **dry-run**（只报告）；`--write` 才落盘。⛔ 无 `--force`、无交互确认 |
| **映射来源** | 🔴 **只读** `src/core/services/configuration/renameMigrations.ts` 的 `RENAME_ROUNDS`（**唯一真相源**） |

**五个空间**（`--space`，缺省 = 全空间）：`setting` · `command` · `flag` · `recipe` · `colorway`

**为什么用 `import` 而不是手抄表**：本脚本用 `pathToFileURL` 直接 `import` 那个 **`.ts`**（Node ≥ 22 原生剥类型；本机实测 **v24.16.0**）。
宁可要求 Node 版本，也不要第二份表——**第二张表必漂移**，那正是本轴 1.15 的病根。

## 二、形状证明

| 项 | 值 |
|:--|:--|
| **路径** | `scratch/prove-rename-shape.mjs` |
| **用法** | `node scratch/prove-rename-shape.mjs --plugin <仓> --base <改名前 sha> [--changed <清单>] [--self-check]` |
| **判据** | 把工作区内容**逐条逆映射**回旧名后，与 `--base` 的 **git blob** 逐字节相等 |
| **退出码** | `0` = 全等 · `1` = 有差异 · **`2` = 没验到任何东西 / 负控未红** |

### 🔴 为什么是「逆映射」而不是「剥前缀」

本轴同一文件里有**多类面**（设置键／命令 id／旗子／配方／配色）。剥前缀只验了前缀；**逆映射验了每一条**——更严。

### 🔴 四条纪律（**写死在代码里，不是注释里的君子协定**）

| # | 纪律 | 落地 | 不遵守会怎样 |
|:--:|:--|:--|:--|
| ① | 基线**必须显式 `--base`** | 缺 `--base` 直接抛错；且**当场 `rev-parse --verify` 解析成 sha** | 默认 HEAD 被中途 amend 悄悄换掉 ⇒ 证的是别的东西 |
| ② | **比 git blob 不比工作区字节** | 一律 `git show <sha>:<path>`，绝不 `readFile` 基线 | 本机 CRLF 检出态与仓库字节天然不等 ⇒ 全是假红 |
| ③ | **负控要自证真的变异了** | `--self-check`：把一条逆映射反转再验，**没红就 `exit 2`** | 1.40 的假负控：「看起来迁移了」≠「迁移了」 |
| ④ | 本轴**多两类面** | 逆映射表含 `flag` 与 `command` 两个空间 | 旗子/命令改了但没验 ⇒ 漏账当绿 |

### 🔴 负控逼出来的两个真 bug（**首版是假的**，留档）

| 症状 | 根因 | 修法 |
|:--|:--|:--|
| `--base UPDATE_REF`（不存在的 ref）时**报了「✅ 通过」** | `git show` 抛错被 catch 成「基线没这个文件 ⇒ 跳过」⇒ **93 个文件全跳过，却报绿** | ① `--base` 当场解析成 sha，解析不了 `exit 2`；② **`compared === 0` 打印「这不是通过，是判据压根没执行」并 `exit 2`** |
| 负控红了但 `EXIT=0` | `| tail` 之后取的是管道尾的码 | 复核用 `${PIPESTATUS[0]}` |

> **教训（与 1.40 同源）**：**「基线解析不了」与「文件是新增的」绝不能共用同一个返回值**——一个 `null` 表示两件事，就必然有一件事被当成好事。

### 已实测（真跑，非声明）

```
$ node scratch/rename-nonnaming.mjs --plugin file-tree --space setting --root /tmp/proofprobe --write
✅ 已写入 18 个文件
$ node scratch/prove-rename-shape.mjs --plugin file-tree --base HEAD --root /tmp/proofprobe --self-check
比对 93 个文件。
✅ 形状证明通过——只改了名字。
✅ 负控红了（3 个文件报差异）——判据确实在跑，上面的 ✅ 才作数。
EXIT=0
```

**第三方独立复核**（不信脚本自报，另用 `git diff --numstat` 算）：

```
$ git diff --numstat HEAD   # 18 个文件
总 +80 / -80                 ⇒ 每个文件都是 +N/-N 相等（纯替换，零增删）
```

人工抽看 `flatten.ts` 的 diff：**连注释里的 `E4V#34b: explorer.compactFolders` 都同步改了**，行数不变、无夹带。

## 三、映射表格式与位置

| 项 | 值 |
|:--|:--|
| **位置** | `src/core/services/configuration/renameMigrations.ts`（**进仓**——运行时迁移要读它） |
| **导出** | `RenameRound` / `RENAME_ROUNDS` / `flattenRenameRounds()` / `selfCheckRenameMaps()` / `settingNewToOld()` |
| **形状** | `{ round, plugin, command: {旧→新}, setting: {…}, flag: {…}, appearance: { recipe: {…}, colorway: {…} } }` |

### 🔴 它是**一次性迁移数据**，**不是登记表**（本轴禁区 #4）

| 判据 | 跑法 | 期望 |
|:--|:--|:--|
| **不是登记表** | `grep -n "renameMigrations" scripts/check-*.mjs` | **命中 0** —— 门禁不得引用它 |

**为什么分得这么死**：登记表是**运行时查询**用的（注入/隔离靠它）；本表是**一次性搬家**用的（搬完就没用了）。
把一次性数据混进登记面 ⇒ 编号会被当成「已注册」⇒ 后加的仓误判冲突。

### 命名形状：**只换第一段，词干零变化**

```
新名 = pluginId + "." + 旧名去掉第一段后的全部
       explorer.confirmDelete  →  file-tree.confirmDelete
       files.exclude           →  file-tree.exclude        （跨命名空间的还回）
       terminal.external.windowsExec → file-tree.external.windowsExec
```

### `selfCheckRenameMaps()` 的四条自检（**入口必跑**）

| # | 判据 | 为什么 |
|:--:|:--|:--|
| ① | 旧名 ≠ 新名 | 空转条目 = 假账 |
| ③ | 两个旧名不得映射到同一新名 | 逆向有歧义 ⇒ 迁移会丢一个值 |
| ④ | 新名不得又是另一条目的旧名 | **轮次耦合** ⇒ 改名顺序会影响结果 |
| — | 逐空间重复检查 | 同一空间内不许重名 |

> 形状证明脚本另有**第二道**逆映射歧义检查（`inverse` Map 撞键即抛）——**故意的双保险**：这道要挡住「迁移数据自检过了但证明有歧义」的缝。

## 四、🔴 三条实证跑法（**改完必跑，逐条留读数**）

> 上位约束是**操作体验零变化**（名字可变，取值与功能不许变）。下面三条是**这条约束的可执行形式**——
> 单元测试证明「代码写对了」，这三条证明「**用户那一侧真的没变化**」。

### 实证 ① 设置项切换（验**设置键**迁移）

```
1. 改名前：把待改的键各设一个**非默认值**（如 file-tree.confirmDelete=false、exclude="**/x"）
   ⚠️ 必须是**非默认值**——默认值在盘上可能压根没写（presence 门控），测了个空
2. 关应用 → 改仓改名 → 打开应用
3. 到设置界面看这些项：**值还在**（不是回默认），且**拨动后立刻生效**（说明新键真被读）
4. 同时看 settings.json：**旧键已消失、新键在**（旧键残留 = 删那一步没执行）
```

### 实证 ② 快捷键触发（验**命令 id**迁移 —— 🔴 本格最易漏的一格）

```
1. 改名前：给一个待改命令**设一个自定义快捷键**（写进 keybindings.json，不是默认表）
   ⚠️ 这条**不在 settings.json 里、没有枚举兜底** ⇒ 漏了就**静默变死键**（按了没反应，也不报错）
2. 关应用 → 改仓改名 → 打开应用
3. 按那个自定义快捷键：**命令照常触发**
4. 看 keybindings.json：command 字段已换成新 id，**自定义键位没丢**
5. ⚠️ 再验一条带 `when` 子句的：子句里的**旗子名**也要跟着换（本轴多出来的第 ⑤ 类面）
```

### 实证 ③ 主题跟随（验**外观 id**迁移）

```
1. 改名前：选一个待改名的主题/配色（非默认那个）
2. 关应用 → 改仓改名 → 打开应用
3. **外观没跳回默认**——颜色/图标仍是改名前选的那个
4. 看 settings.json：外观键的值已换成新 id
```

### 三条的**共同前置**与**共同禁忌**

| 项 | 要求 |
|:--|:--|
| 前置 | 每次都必须**从改名前状态起**（还原 ≈ 干净用户数据），不能拿已经改过一轮的盘接着测 |
| 🔴 禁忌 | **别用「全新安装」测**——全新盘上旧键压根不存在，三条全绿也证明不了任何事（**假绿**） |
| 🔴 禁忌 | **别只看界面**——三步都要**回读磁盘文件**：界面读的是内存缓存，落盘失败了界面照样好看 |
