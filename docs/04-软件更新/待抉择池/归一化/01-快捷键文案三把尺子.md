## 〇、现象（用户原话）

> 「为什么顶部菜单栏……是大写，软件左下角齿轮的快捷键显示是小写」

**今天就能看到的最小对照**（三条命令都带绑定、都在两处同时出现）：

| 命令 | 顶部菜单栏 | 左下角齿轮菜单 |
|:--|:--|:--|
| 设置 `core.openSettings` | `Ctrl+,` | `ctrl+,` |
| 主题 `theme.pick` | `Ctrl+K Ctrl+T` | `ctrl+k ctrl+t` |
| 选择语言 `workbench.action.selectLanguage` | `Ctrl+K Ctrl+L` | `ctrl+k ctrl+l` |

⚠️ **一处与用户举例的出入（如实记，⛔ 别当没看见）**：用户举的例子是「命令面板」，但**齿轮菜单里没有「命令面板」这一项**——它挂的七条是 设置／重置为内置设置／主题／语言／快捷键列表／检查更新／关于（`src/core/commands/shell/settingsCommands.ts:582` 起）。命令面板自己那条命令 `workbench.action.showCommands` 只出现在「查看」下拉里，走的是**已格式化**那条路（⇒ `Ctrl+Shift+P`，正确）。
⇒ 用户当时看到的大概率是上表三项之一。**若确在齿轮里见过「命令面板」，说明还有第四处渲染点没找到**——动工前先复现确认一次。

## 一、根因：同一条命令，三处格式化

| # | 通路 | 落点 | 输出（以 `ctrl+k ctrl+t` 为例） |
|:--:|:--|:--|:--|
| ① | **布局快照**——壳序列化好随 pushLayout 下发，池哑渲染 | [`titlebar.ts:80`](../../../../src/hooks/usePoolSync/titlebar.ts)：`shortcut: formatKeyLabel(kb.key)` | `Ctrl+K Ctrl+T` ✅ |
| ② | **IPC 实时查询**——池 `lk.menu.getItems()` → 壳 `menu:getItems` | [`ui.ts:131`](../../../../src/core/services/plugins/IpcBridgeHandler/ui.ts)：`shortcut: kb?.key`（**注册表原始串原样透传**） | `ctrl+k ctrl+t` ❌ |
| ③ | **命令面板列表**——自带第三套写法 | [`commandPalette.ts:33`](../../../../src/core/commands/palette/commandPalette.ts)：`.split("+").map(首字母大写).join("+")` | `Ctrl+K ctrl+T` ❌ |

③ 对**单键**恰好正确（`ctrl+shift+p` → `Ctrl+Shift+P`），对 **chord** 必然错：`"ctrl+k ctrl+t".split("+")` 切成 `["ctrl", "k ctrl", "t"]`，中间那段只把首字母变大写 ⇒ `Ctrl+K ctrl+T`。池侧 [`QuickPickHost.tsx:92`](../../../../src/pool/floating/quick-pick/QuickPickHost.tsx) 的 `renderKeybinding` 是**零变换**哑渲染（按 `+` 切键帽），壳给什么就画什么。

**一句话判定**：`<ContextMenu>` **传了 `items` ⇒ 走①快照（已格式化）**；**不传 ⇒ 回落 `lk.menu.getItems()`（②原始串）**（判据 = [`ContextMenu.tsx:76`](../../../../src/components/shared/context-menu/ContextMenu.tsx) 的头注释 + `:152` 的实现）。

## 三、实证读数（2026-10-06 · node 逐串验算）

```
raw            = "ctrl+k ctrl+t"
① formatKeyLabel = "Ctrl+K Ctrl+T"   ← 目标形态（VS Code 同款）
② ui.ts 现状     = "ctrl+k ctrl+t"   ← 全小写
③ 命令面板现状    = "Ctrl+K ctrl+T"   ← 中间段漏改

单键 ctrl+shift+p：① "Ctrl+Shift+P" ／ ③ "Ctrl+Shift+P"（③ 侥幸正确，故此 bug 只在 chord 上现形）
```

③ 的写法不是「另一种风格」，是**同一判断实现两遍**（memory `two-rulers-one-caliber`：两把尺子迟早漂移）——它今天已经漂了。

## 四、修法（已拍板：收敛到单权威）

| 步 | 落点 | 改动 |
|:--:|:--|:--|
| 1 | `src/core/services/plugins/IpcBridgeHandler/ui.ts:131` | `shortcut: kb?.key` → `shortcut: kb?.key ? formatKeyLabel(kb.key) : undefined`（与 `titlebar.ts:80` **逐字同一条链**） |
| 2 | `src/core/commands/palette/commandPalette.ts:33-36` | 删掉自造的 `.split("+").map(大写).join("+")`，改调 `formatKeyLabel`（③ 归并） |
| 3 | 契约注释收紧 | `src/core/api/linkdesk-api/types.ts:403` 今天写「已解析快捷键 `"ctrl+shift+p"` 形式」——**举例是小写形态，正是误读之源**；改写成「**显示串**（`formatKeyLabel` 后，如 `Ctrl+K Ctrl+T`）」。改完 **同笔重跑 `npm run contracts:gen`**（`contracts/linkdesk.d.ts` 是生成物、`contracts:check` 逐字节比对） |
| 4 | 机械锁 | 见 §五 D3 |

⚠️ **`formatKeyLabel` 住 `src/core/utils/`（壳侧）、`ContextMenu` 住 `src/components/shared/`（共享件）**——后者**不许** import 前者（门禁腿 `check-shared-components-zero-shell-deps`）。⇒ 格式化**只能**落在壳侧②这条路（`ui.ts`），这既是设计约束也是本修法的位置依据。

### 排除的替代方案

| 案 | 为什么不选 |
|:--|:--|
| **把 `formatKeyLabel` 搬进 `@linkdesk/ui`，让 `ContextMenu` 自己格式化** | 把「显示文本铁律（壳侧解析、池哑渲染）」打成两处判断——两把尺子又回来了；且②的消费方不止池（插件也读 `menu.getItems()` 的返回值） |
| **改注册表键位串为大写** | 键位串是**功能面**不是文案：`normalizeKey` 比对、主进程键表、用户 `keybindings.json` 全吃它。改大小写＝引火烧身 |
| **只改齿轮一处（`iconbar.ts` 里预格式化）** | 治标：②那一整列（右键菜单 ＋ 两个自造槽）照旧小写，只是把病灶藏起来 |
| **给 `ContextMenu` 加 `formatShortcut` 开关** | 又要池侧判断「这条要不要格式化」——同样是第二把尺子 |
