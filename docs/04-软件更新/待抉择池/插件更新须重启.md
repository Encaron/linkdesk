# 插件更新须重启（池按 URL import 不 cache-bust）——含一件「建议先做」的小件

> 🔴 **给未来做任务的 AI——先读这段。本档记的是两个不同的点，别当成一件事。**
>
> | | 点 | 性质 | 本档的主张 |
> |:--|:--|:--|:--|
> | **①** | **卸载 → 装更高版本「静默不生效」** | 🔴 **错**（不是不便） | **建议至少做一做**（§二）——**修它不动缓存机制**，只让那条路如实提示重启。**动手前先花五分钟验真伪**（§二 末给了步骤） |
> | **②** | **更新须重启** | 不便，但**诚实**（toast 明说要重启） | **留池、不排期**（§五 给了触发条件） |
>
> **① 比 ② 更该做，判据只有一条**：**② 用户知道该做什么**（点一下重启就好了）；**① 用户不知道**——界面显示旧版、一个字都不提示、且**无法自查**。静默的错，比明说的不便糟。

## 一、机制：两层缓存的键里都没有版本号

**现象（用户实机）**：同一只插件——**卸载后重装** ⇒ 图标出现、视图当场可用，零重启；**不卸载直接更新** ⇒ 必须点 toast 的 [立即重启]。

**根因**：

| 层 | 键 | 出处 |
|:--|:--|:--|
| 池侧模块表（Chromium module map） | 表面 URL：prod `linkdesk://<pluginId>/...`、dev `/@fs/<abs>/...` | [contributions.ts](../../../src/pluginLoader/contributions/contributions.ts) 的 `resolveRuntimePluginRoot`（`:321-326`）——两个分支都不带版本 / hash / 时间戳 |
| 池侧 `_lazyCache`（**两份**） | `renderPath \|\| pluginId`（视图面）／ `renderPath`（状态栏面） | [PluginComponent.tsx](../../../src/pool/shared/plugin-component/PluginComponent.tsx) `:32` 定义 · `:153` 取键 · `:189` set，**全部 `delete` 只有 `:171`（模块为 null）与 `:185`（import 失败）** ｜ [PoolStatusBarComponent.tsx](../../../src/pool/shared/pool-status-bar/PoolStatusBarComponent.tsx) `:27` 定义 · `:38` 取键 · `:56` set，**唯一 `delete` 是 `:51`（import 失败）** |

⇒ **同一个 URL 永远命中同一份模块**：同版本重装时缓存里那份与盘上**内容相同**，所以"恰好还对"、看不出问题；换版本更新时缓存里是**旧版**、盘上是新版 ⇒ 会话内无手段驱逐 ⇒ 只有整机重启。

这就是 [update.ts](../../../src/pluginLoader/lifecycle/update.ts) `:225`「bundle 模块缓存无法 in-session 破除」的真身。⚠️ 同文件 `:101` 的旧注释写「壳+池双 realm module map」——**壳侧这条已不成立**：壳 bundle 已零插件 JS 源码（[state.ts](../../../src/pluginLoader/resolution/state.ts) `:57-72`），组件加载唯一执行者是池，真正阻塞的只剩池里那一份。

## 二、① 卸载 → 装更高版本「静默不生效」（🔴 建议先做）

**症状（可自查）**：把一只插件**卸载**、再从市场装**更高版本** ⇒ 图标与贡献项都正常出现，**但界面还是旧版的样子**；重启一次才变新版，且**全程没有任何提示**。

**为什么会静默**：那条路上 `needRestart` 只在 `loadPlugin` **抛错**时才置位（[install-ops.ts](../../../src/pluginLoader/lifecycle/lifecycle-ops/install-ops.ts) 的 catch 支 `:170-179`）——而这条路**不抛错**（文件落盘成功、注册也成功），于是既不提示、也不生效。

**为什么自绘状态栏的插件「必然」中招**（最强的触发面，值得单独记）：

- 自绘状态栏的组件要常驻显示，**在启动过程里就被挂载** ⇒ 它的 `statusBar.bundle.js` **从开机起就进了池的缓存**；
- 而**状态栏那份缓存连"模块为 null"的清理都没有**——唯一 `delete` 点是 import 失败（`PoolStatusBarComponent.tsx:51`）；
- ⇒ 卸载 → 装新版 ⇒ 状态栏**必然**渲染缓存里的旧版，一个字都不提示。
- 视图面同理，只是门槛稍高：要在**本会话打开过**那个视图，它的 bundle 才在缓存里。

**修法（不动缓存机制）**：把 `needRestart` 的判据从「`loadPlugin` 抛错」**扩到**「**该表面在本会话已被加载过**（缓存里已有同 URL）」——只在那条真会旧的路上如实补一次重启提示。代价是那条路多一次提示，换来的是**不再骗人**。

> 更笨但更保险的备选：**非首次安装一律提示重启**（判据退化成"盘上原来有没有"）。选哪一档是拍板题。

**⚙️ 动手前先花五分钟验真伪**（本条的定位 = **据代码推出的可达路径，未实机验证**）：

1. 装一只**带自绘状态栏组件**的插件（`contributes.statusBar` ＋ 自绘 render）；
2. **卸载**它；
3. 从市场装**更高版本**（或手工把上一版包内的版本号改高再装）；
4. **不重启**，看状态栏——**显示旧版样子 ⇒ 本条成立**；已是新版 ⇒ 本条不成立（那就把本节划掉，只留 ②）。

## 三、② 为什么算「缺口」而不是「设计」

E6 台账的措辞已经把它定性了——**它是在否认一个归类，不是在陈述一条规则**（[12 号档 §六](../../02-Electron架构/插件生态与发布/01-插件独立构建/12-多表面共享状态塌缩-立案.md)）：

> ⛔ **不是**「壳加载器的 cache-bust」题：池按 URL `import()` 表面 bundle、**同 URL 不随磁盘替换重载** ⇒ 插件升级须重启才生效。这是**另一个**已知面…**归加载器优化域，不并案**。

配套两条边界：E6#159（多表面共享状态塌缩）明确**不并**本案；`E6-执行清单.md:768` 记「chunk 用**内容哈希名**、**升级须重启这条既有前提不变**」——构建侧**有意保留**。

**设计之内的是「形态」，不是「必须重启」**：

- **是设计的**：更新走用户点击而非自动 reload（[P4-设计.md:1351](../../01-Tauri_P1至P5.5/P4-插件系统/P4-设计.md)：安装→通知 + [立即重启]…不自动 reload，不自动跳转）＋ 常驻可攒批（`ttl:0`，E6#73j G3/G7）。这一层还翻过一次面——Tauri Phase 4.7 选的是自动（1.5s 后 `window.location.reload()`），后收敛到 VS Code 的按钮式；
- **不是设计的**：「更新这一步非重启不可」是机制后果，**从未被设计过** ⇒ 它没有设计档，只有一条挂账行。

## 四、② 的候选修法（未拍板）

| 案 | 做什么 | 成本／风险 |
|:--|:--|:--|
| **A**｜给缓存键加版本维度 | 表面 URL 与两份 `_lazyCache` 的键纳入版本（或内容指纹） | 改动面小；**样式自动跟着换**（`<link>` 的 href 由 `cssUrlForRenderPath(renderPath)` 派生，同 `PluginComponent.tsx`）；但"版本键够不够"（同版本重装要不要也换）与 dev `/@fs` 轨的等价性都要先定 |
| **B**｜给池加重建通道 | `pool:` 通道块补一条「重载池」入口，更新收尾改走它而非 `app.relaunch()` | 可复用崩溃恢复既有的 `rebuildPool()`（`electron/windows/window-manager.ts:522`）；⚠️ `getPoolView()` 只覆盖**主池**（`:603`），脱出窗走 `getAllPoolViews()`（`:608`）——只修主池会出现**主窗新版、脱出窗旧版**的混版，比现状更糟 |

两案都不覆盖 `needRestart` 归零（还剩多窗、主进程运行时注册、热退出三面），但都比现状小。**半修的风险高于不动**——漏掉状态栏孪生缓存 / CSS `<link>` / 脱出窗任一处，产出的都是「静默的错」（即 ① 的形态），这正是 ② 排在 ① 后面的理由。

## 五、现状

- **① 建议至少做一做**：判据与修法见 §二；**先花五分钟验真伪再动手**（那条是代码推论，未实机验证）。
- **② 留池、不排期**——三条理由：**（a）** 现状是「诚实的不便」，而**半修会变成「静默的错」**（漏状态栏孪生缓存 / CSS / 脱出窗任一即中），且这个加载器正是 `lifecycle.ts:7` 自述的「**80 个 commit 修同一个伤口**」之地；**（b）** 触发频率低，今天已能攒一批再点一次重启、成本被摊平；**（c）** 收益 = 省一次点击，代价 = 三面专门回归。
- **② 的触发条件**（满足其一再动）：**a)** 要建「**只重建池**」这个能力服务别的场景时——顺带解决、边际成本最低（**最划算的时机**）；**b)** 插件数量 / 更新频率上去，「每次更新要重启」从偶发变高频摩擦；**c)** A 案被证明风险可控（只认 URL 键、不扩散到别的机制）。
- 建档只记账：**不动机制、不 bump、不发版**；发版时机随攒批统一定号。
- ⚠️ **勿与下列混案**：E6#158/#159（多表面共享状态塌缩）走 SDK / 作者面，SDK 0.1.58 已发——按 12 号档 §六「**不并案**」。
- 📌 **同族但与本档无关的一件（另册待立）**：「每次更新重启都复位窗口几何 / 最大化态」——壳窗口无几何持久化（`electron/main.ts:520-526` 硬编码 1400×900、启动不恢复最大化），而基建已在（[windows-state.ts](../../../electron/windows/windows-state.ts)）。**它不属本档**（不碰加载器、惠及全部重启场景含软件更新），此处只留一句指针防遗忘。
