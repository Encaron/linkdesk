## 一、根因：兜底那一行**不认轴**

`computeTipPosition`（[placement.ts](../../../src/components/shared/hint-tip/placement.ts)）的判定次序是：**首选方位够放 ⇒ 采用** → 不够 ⇒ 翻主轴反面 → 反面也不够 ⇒ 取**空间最大**的一侧 → 最后若"离锚太近"（`tooClose`：夹紧把条拉回了锚上、尖角会插进锚里）⇒ **换空间最大的一侧重落一次**。

最后那一行的兜底按几何挑方位，**不认"条属于锚的哪一侧"这个语义**。标签栏现场把它踩实了：

```
标签贴在窗口顶部（标题栏 30px ＋ 标签 4px 上边距 ⇒ 锚上缘实测 37~42）
  ↓ 请求 placement = "top"
名义放得下：space.top(=39) ≥ 条高(31) + GAP(6) = 37
  ↓ 落点 pos.top = 39 − 37 = 2 ⇒ 贴视口上缘，被 EDGE_PX=8 夹紧 ⇒ 抬到 8
条覆盖 y∈[8, 39]，**下缘正好蹭到锚上缘 39** ⇒ tooClose 成立（连 GAP 都没保住）
  ↓ 旧兜底：roomiestSide(space) —— 宽窗口里 W−right(≈1716) ≫ H−bottom(≈1371)
  ↓ 选中的是「右」⇒ 条被甩到旁边轴上，横着盖住下一个标签
```

**触发带恰是 `EDGE_PX` 那 8px**：`条高 + GAP ≤ 锚上缘 < 条高 + GAP + EDGE_PX`，即本例 **37 ≤ top < 45**。标签栏的锚正好落在带内（用户实测那一档），所以**每只标签都触发**——只是触发之后落到哪由"哪边空间大"决定，这才是"前两只 vs 第三只起"的分界的真身：

```
roomiestSide 只可能在上/下/左/右里挑空间最大的
  左/右 的空间 = 窗口宽 − 锚的水平位置     ← 越靠左越大
  下   的空间 = 窗口高 − 锚下缘            ← 对同一排标签是常数
⇒ 窗口够宽时，前几只（靠左）"右"最大 ⇒ 跨轴到右边；靠右的那几只"下"最大 ⇒ 看起来"正常"
```

于是症状成串：**头两只与"只有一只"**都跳到右边（最左的那只 `W−right` 最大，必然选右）；**第三只起**只是因为 `W − 锚右缘` 掉到了 `H − 锚下缘` 以下，兜底恰好又挑回"下"——**不是第三只走对了逻辑，是它的偶然**。窗口再宽一点，分界还会往后挪。

**为什么"上次修过 hint tip"没覆盖这里**：2026-09-27 那次返工修的是**翻面路径**——`space[placement] < need` 时"副轴越界不许否决翻面"（病灶在 `computeTipPosition` 的**第一个**分支，见 [HintTip-落点与尺寸返工/00-README](./HintTip-落点与尺寸返工/00-README.md)）；本次是**夹紧兜底路径**（`tooClose` 之后的**第二个**分支），两条分支几何上互不相干。上一版把"要不要换方位"写对了，**"换到哪"没规定轴的忠诚度**——同一个决定又只写了一半（同族记法见 memory `hint-tip-geometry-close-judge`）。

**为什么单测没拦住**：既有那条「夹紧会吃掉 GAP ⇒ 换空间最大的一侧重落」用的是 1000×800 视口、锚在正中（`space.bottom = 742 > space.right = 440`）——**兜底恰好选中"下"**，于是它与"轴忠实"的期望值重合，把缺陷盖住了。测试的几何取值本身把病灶路径遮成了一片绿。

只此两处；`placeOn` / `tooClose` / `roomiestSide` / 五条几何约定（`GAP_PX`、夹紧、尖角…）**一律未动**。

把兜底临时改回旧形态（跳过同轴对面那一步）单跑新用例，**4 例判红**——全部是"跨轴"现场，正是用户看到的那几只：

| 用例 | 旧形态读数 | 新形态读数 |
|:--|:--|:--|
| 第 1 只标签（1920×1440，条 200×31，锚上缘 39） | `placement = "right"`（**跨轴**，压住下一个标签） | `"bottom"`，`top = 75`（= 锚下缘 69 ＋ GAP 6） |
| 只有一只标签（最左） | `"right"` | `"bottom"` |

| 横向同病（700×1200，请求 left、左缘夹紧） | `"bottom"`（**跨轴**：870 > 290） | `"right"`，`left = 416`（= 锚右缘 410 ＋ GAP 6） |

既有两条用例（「✕ 贴窗口右上角」「夹紧会吃掉 GAP」）**仍绿**：前者根本走不到兜底（第一次翻面就得到 `bottom`），后者的同轴对面正是它原本断言的 `bottom`。

**⏳ 真机读数（待用户实机验收，三项）**

1. 标签栏**第一只／只有一只**标签悬停 ⇒ 条出现在标签**下方**（原报障场景）；
2. 一排标签逐个悬停 ⇒ 全部下方、**无一遮挡相邻标签**；
3. 原生窗口按钮（菜单栏右侧那一排）与面板工具条等**贴窗口上缘**的提示点 ⇒ 同样落下方（同一条触发带的同族现场）。

## 五、边界与遗留

- **同轴对面不可用时仍会跨轴**：窗口高度不足以在锚下方放下条（本例约需 `69 + 31 + 8 ≈ 108px`，正常窗口远够）时，兜底照旧退回"空间最大的一侧"——**这是有意的**（宁可跨轴也不压锚）；真机上只有"窗口被拖到极扁"才会遇到。
- **触发带仍在**（`EDGE_PX = 8` 那条带以 `tooClose` 的形式存在）：本件没动它——它只是**触发**兜底，兜底现在忠于轴；改 `EDGE_PX` 会牵动全部四向落点，不在本案范围。
- **不做的**：不给标签栏写"专属方位"（`data-hint-placement="bottom"` 那种调用侧打补丁）——病灶在**通用兜底**，调用侧逐个打补丁会把同一个缺陷留在其它贴边锚上（原生窗口按钮排、面板工具条…）；也不动尖角（`computeTailOffset` 只依赖最终 `placement`，跨轴改掉后尖角自动指对）。
