# 新能力设计流程（Design Flow for New Capabilities）

> **适用面**：任何新控件 / 新 API / 新能力 / 新方法 / 新插件——全项目唯一设计前置规范。
> **2026-08-27 用户拍板**：「设计必须有一套流程」——立流程，让未来任何 AI 遵循，搞 skill + 机械审查。
> 根因：每个能力在实现期临时摸索 API/配置/显示/通信 → 总有没想到的维度 → 反复返工。
> **2026-08-27 扩展**：任务组织（清单/档案分离 + 颗粒度 + 回勾语义）、Bug 修复任务规范、10 条软件核心理念并入本流程（E5.8#138-#140）。

---

## 一、为什么立这条流程（返工根因）

历史教训：每次立项只写「缺口 + 方案方向」，没有规范流程逼设计期想透以下维度——API 怎么放、配置谁给、显示在哪、通信走哪、插件侧怎么组织、壳侧放哪个目录、有没有保底 UI。实现期临时摸索必然遗漏维度 → 返工。

**流程 = 把设计期该想的问题，变成立任务前的强制检查清单。** 设计与实现分离：先按 8 维度回答完设计，再写代码。

---

## 二、软件核心理念（10 条设计判据）

> **2026-08-27 用户逐字版**。一切设计 / 任务 / 代码的最终判据——设计审查、实现、回勾时对照。
> 与 memory `quality-commandments`（序章 11 条原话 + 十条平级戒律详解）互相印证；本表 = 用户原话，戒律 memory = 逐条解读。

1. **精益求精、慢工出细活、完美软件、低耦合高内聚、AI 友好度、归一化（不会发生 v2.6 / 一个 bug 不会多个地方出现）、插件自由化、vscode 化程度相似、禁止硬编码、时刻注意声明式、易操作**
2. **有利于未来插件生态**
3. **插件独立性**——第三方作者不必为每个新插件来改壳代码
4. **没有死代码，代码整洁**
5. **未来容易拓展新区域、新功能**
6. **没有硬编码**
7. **低耦合、高内聚**
8. **符合归一性**
9. **符合 AI 友好性**——三层：① 代码对 AI 可读（类型即文档 / 命名即意图）② 运行时 AI 可编辑（不改工程不重 build 热生效）③ AI 按框架规则生成任意插件（详见 memory `quality-commandments` §四 + `ai-friendliness-three-layers`）
10. **软件健壮性好、生存力强**

**用法**：设计审查 ② 步逐维度过完后，最后把方案对着 10 条过一遍——不符合的说明理由并记录。**方向性指引，非每功能逐条达标**（用户原话：「虽然很多可能不符合某一个新功能、某一个新插件的要求，但总体方向肯定是对的」）。

## 三、流程阶段（立任务 → 实现 的强制步骤）

```
① 立项     任务条目先写「设计前置」——按 8 维度清单（§六）回答：一段设计摘要 + 关键决策
② 设计审查  AI 调用 design-flow skill 逐维度审查方案（软性但全面）→ 对着 10 条核心理念（§二）过一遍
③ 实现     代码满足硬约束 + 归一化 + 概念键分离；一个任务一事一义（颗粒度见 §四 4.2）
④ 机械审查  npm run check 自动拦截可机械判定的不变量（硬性，见 §八）
⑤ 回勾     ✅ 只在「实现 + 验证通过」后打；完成描述规范见 §四 4.3
```

任何一步没走完就写代码 = 违反本流程。

## 四、任务组织规范（清单 vs 档案分离 + 颗粒度 + 打勾语义 + 完成描述）

> **2026-08-27 用户拍板**：「任务清单和任务档案要分开，有指向性，不要把所有东西都塞入任务清单；具体任务清单怎么打勾、完成时该描述什么，都要明确」。
> 铁律源头：memory `checklist-concise-pointer-set`（清单 = 指向档案的指针集）+ `checklist-slim-preserve-links`（链接是保留指针）。

### 4.1 清单 = 指向档案的指针集，两行制

- **清单只写两行**：标题行 + ✅ 结果行。现象 / 根因 / 方案步骤 / 修复细节全下沉对应档案文档或 commit，**禁止塞进清单**。
- **有指向性**：结果行末尾必须带档案文档锚点链接（`.md`），不是只写 commit——commit 不可导航，档案才是可读载体。
- **新增任务（bug 修复 / 审计类）立案时直接开档案文档**（Phase 子目录编号 md，如 `外观主题化/12-主题缺陷修复档案.md`），清单只写标题行 + 档案锚点。
- 范例：E5.8-执行清单（`linkdesk/docs/02-Electron架构/E5.8_归一化基建/E5.8-执行清单.md`）。

### 4.2 颗粒度——一个任务一事一义，任务量过大必须拆

- **拆任务判据**：一个任务预估超 ~150 行改动，或跨多个不相关文件 / 多个概念，或同时做「修 A + 顺带加 B」→ 拆成多个任务，各配独立 commit。
- **每 commit 只做一件事**（quality-commandments §二 小批快走：每批 ~150 行，交一个验一个；一口气干完一个 Phase = bug 满天飞）。
- 拆任务用小数线性插入（`#NN.m` / `#NN.NN`），**不清洗重排**。

### 4.3 打勾语义 + 完成描述

- **`[ ]` → `[x]` 只在「实现 + 验证通过」后打。** commit ≠ 完成；高风险改动必实机门禁（memory `task-list-first-real-machine-gate`）。
- **✅ 结果行该描述什么（一句到两句）**：
  1. 做了什么（一句）
  2. 关键 commit（`hash`）
  3. 验证结果（`npm run check` 全绿 + 计数 / CDP 实机关键断言 / 用户视觉确认）
  4. 档案锚点链接（有档案时）

## 五、Bug 修复任务规范（修前必答三件事）

> **2026-08-27 用户拍板**：bug 类任务「往往是做完某个 phase 后才发现的，因此要在修这些 bug 之前有原因、代码怎么改之类的，同时保证可执行性」。

**Bug 修复类任务立案时，任务条目必须先写清三件事（先写再改）**：

1. **原因**——根因定位（`file:line` + 机制解释），不是现象描述。参考 memory `bug-fix-protocol`：确认现象在哪层 → 对比历史（V2/旧版怎么做）→ 推演完整时序（mount → event → cleanup → re-mount）。
2. **代码怎么改**——具体改哪个文件哪个函数、怎么改。**写得出才能动手**；写不出 = 还没理解根因，先侦察再立任务。
3. **可执行性**——改动有明确验证路径（单测断言 / CDP 实机复现 / 回归场景）。**没验证路径的修复不可执行**，先定验证法再立任务。

**回勾时描述**：根因（一句）+ 修复 commit + 验证（回归 + CDP + 用户确认）。细节沉对应档案文档（§四 4.1）。

## 六、8 维度设计清单（设计前置必答）

### ① 能力边界
- 这是**壳能力**还是**插件能力**？（核心准入三条件：多提供方 / 多消费方 / 桌子不知道内容）
- **保底设计**：没有插件时，有没有保底？——主题无插件也有 dark/light 保底、图标无插件也有 codicon 保底。壳能力永远先答这个。

### ② API 设计
- 要暴露给插件吗？什么命名空间/方法？（`window.linkdesk.*`）
- 契约在哪定义？（contracts/linkdesk.d.ts + src/core/api/linkdesk-api/）
- 通用优先：先复用已有 API，缺了才新加（memory `api-preference-existing-first`）。
- 新 API **必须**在 03-插件制造 文档说明（用户明确要求）。

### ③ 通信方式设计
- 插件↔壳走哪条通道？（IPC preload 桥 / 配置注册表 / 事件广播 / 命令）
- 数据流：谁产生、谁消费、谁持久化？
- 铁律：插件通信全走 `window.linkdesk.*`，禁止 import @src/core（memory `plugin-communication-standard`）。

### ④ 壳侧代码设计
- 放哪个目录？（壳目录规范——core/services / components/shared / App/config…）
- **目录组织尽量减少平铺**——feature-folder / 子目录按能力分组（壳目录规范 §4，preload-pool 13 子模块聚合先例）；平铺例外需用户拍板（memory `directory-flat-exception`）。
- **单一权威**在哪？（键清单 / 来源，防两份漂移；概念键分离——不同概念不共用同一键）
- 硬约束合规（颜色走 var / 文字走 t() / 插件 ID 不硬编码 / 路径走 getAssetPath）。

### ⑤ 插件侧代码设计
- 走哪个贡献点？（contributes.*——themes / iconThemes / views / commands / languages…）
- 目录结构**尽量减少平铺**（feature-folder / 子目录按能力分组；平铺例外需用户拍板）、虚构实例怎么组织（测试 fixture 用虚构名，硬约束 21）。
- **插件独立铁律**：第三方作者永远不需要壳改代码（memory `plugin-independence-iron-law`）。

### ⑥ 显示设计
- **在哪里显示**？（哪个 UI 位置——顶栏/侧栏/主区/状态栏/设置页/浮层）
- **怎么显示**？（控件类型——卡片/下拉/滑杆/分段/取色器；壳共享组件优先）
- **显示什么**？（数据来自哪——API / 配置 / 事件）

### ⑦ 配置设计
- 配置项 key？（`app.*` 或插件命名空间）
- 设置页**哪一组**出现？（group 分节）
- **配置是壳给还是插件给？**——壳给 = 保底 UI 必然存在；插件给 = 丰富但可缺（如主题插件给配色、壳给保底配方）。显隐/枚举/默认值/复位语义一并定。

### ⑧ 代码规范 + 验收
- 命名/注释/测试卫生、归一化（同概念单写法）、无死代码、符合 §二 10 条核心理念。
- 验收：`npm run check` 全绿 + CDP 实机 + 用户视觉验收（高风险必实机门禁）。

## 八、机械审查设计（可机械判定的不变量，进 `npm run check`）

对标 E5.7 静态卫生（--max-warnings 0）+ #130 CSS 审计门禁先例。三项（E5.8#137 已落地，全在 `npm run check`）：

### 8.1 新 API 契约四齐全（audit-api-contracts，对标 ipc-audit）
新增 `window.linkdesk.*` 方法必须**四件套齐全**，缺一红灯：
1. contracts/linkdesk.d.ts 类型声明 —— `contracts:check` 字节比对门禁（#21，已有机）
2. preload 实现（namespaces-*.ts）—— `satisfies PoolExposed/ShellExposed` tsc 形状门禁（#20，已有机）
3. 主进程分发（IpcBridgeHandler）—— 同上 tsc 面约束（已有机）
4. 03-插件制造 文档说明 —— **流程层强制**（设计前置 + design-flow skill）：01-插件API契约.md 是**指针式**（E5#85→E5.8#22 有意决策，方法明细指向 d.ts，不手写第二份真相源），机械无法判「新 API 该不该入文档」；机械管**反向漂移**——文档引用的 `linkdesk.<ns>` 必须真实存在于 live 契约（`check-api-contracts.mjs`，实证抓到 E5.7 残留 `window.linkdesk.data` 陈旧引用）。

### 8.2 新配置项保底（audit-config-baseline）
新增 `app.*` 配置项必须：`registerConfiguration` 声明 + 保底默认值（无插件也成立）+ 设置组归属。机械 = `check-config-baseline.mjs`（appearance.ts + startup.ts 每个 `"app.*": { }` 块必须有 `default:`）。

### 8.3 新贡献点三件套（audit-contributes）
新增 `contributes.*` 必须：plugin.schema.json 字段 + 加载器消费 + 文档说明。机械 = `check-contributes.mjs` 三条不变量：live schema（public/schemas）字段 ⊆ 03-插件contributes规范.md 说明 + docs 拷贝 schema == live（防两份漂移，实证抓到 5 vs 16 陈旧拷贝）+ 字段在 src/+electron/ 有消费方。

### 8.4 设计流程机械门禁（audit-design-flow，E5.8#145）
设计流程自身的三条不变量（2026-08-27 用户拍板「不走不放行」——memory/skill 是软层靠自觉，机械层才是真拦截）。**存量豁免：#0a-#144 一律跳过（实证 216/323 无档案链接、59 条超 360 字符 = 指针集铁律在历史清单从未被机械执行）；从 #145 之后严格**。机械 = `check-design-flow.mjs`，三条不变量（全过才绿）：
1. **清单条目 = 指针集**（治「把一堆东西塞执行清单」）：`E5.8-执行清单.md` 中**任务号 ≥ #145** 的条目必须 ≤ 2 物理行 + 含 ≥1 档案链接 + 单行 ≤ 400 字符——细节沉档案，禁塞清单（§四 4.1 的机械化）。
2. **档案链接存在性**：#145+ 条目引用的档案路径必须真实存在于磁盘（防悬空指针），相对清单所在目录解析。
3. **新能力文档必带设计前置**（治「不按 8 维度走」）：git 未提交（`??`/`M`）的 `.md` 位于 `docs/02-Electron架构/`（排除 `*执行清单*` / `README`），含新能力标记（`window.linkdesk.` / `contributes.`）且无「设计前置」或「非新能力」声明 → 红灯。新 `app.*` 配置键由 8.2 覆盖，不在此列。

**L2 调用时拦截**（同立案，用户拍板「只拦 commit」）：`.claude/settings.json` PreToolUse 钩子——`git commit` 前先跑本检查，红灯直接 block commit。

## 九、验收总则

1. 每个新能力先交「设计前置」方案（8 维度，§六）再写代码——任务条目可见。
2. 设计前置过完后对着 10 条核心理念（§二）检查，不符合的说明理由。
3. 任务组织遵守 §四（两行制指针集 + 颗粒度 + 打勾语义 + 完成描述）。
4. Bug 修复遵守 §五（原因 + 改法 + 可执行性）。
5. skill 与机械审查随清单 Phase 11.21/#138-#140 逐项落地。
6. 未来 AI 立新任务时对照本流程自查；机械层红灯必须修到绿灯才提交。
