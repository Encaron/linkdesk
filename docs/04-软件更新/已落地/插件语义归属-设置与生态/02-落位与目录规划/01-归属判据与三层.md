# 01 · 归属判据与三层拆分

> 起因（用户 2026-11-24）：改「背景图片选择默认目录」时，AI 同时改了壳和**设置插件**。
> 设置插件是可整套替换的普通 UI 插件——为什么改一个打开目录要动它？
> 这跟当年的翻译问题同构：**呈现者掌握了语义**。

---

## 一、判据：语义归属律

> **一个行为的「默认值 / 约束 / 权限 / 路径」由能力的所有者声明；UI 插件只做呈现与触发。**
> **验证方法（替换测试）**：把该 UI 插件整套换成第三方实现，这个行为还在不在？不在 ⇒ 住错了层。

它与判据 A 互补：判据 A 管「控件住哪层」，本条管「语义住哪层」。

---

## 二、三问（判任何一条能力）

```
Q1 换掉这个 UI 插件（设置/市场/文件树…）后，行为是否消失？
    └ 消失 ⇒ 语义被插件把持 ⇒ 必须上移（壳声明 / 壳 API / 壳命令）
Q2 这条知识是不是宿主域？（路径 / 配置键 / 资产域 / 权限 / 系统调用）
    └ 是 ⇒ 归壳；插件只拿结果
Q3 第三方 UI 不看第一个作者的源码，能不能做对？
    └ 不能 ⇒ 语义没有被声明出来（藏在代码里）⇒ 先补声明，再谈 UI
```

---

## 三、三层拆分（每条能力都拆成三行）

| 层 | 归谁 | 背景图例子 | 主题例子 |
|:--|:--|:--|:--|
| **语义/数据** | 宿主声明（配置 schema / 资产域） | `app.backgroundImage` 声明 `assetDomain:"appearance"` | 主题配方/分节/来源键由 schema 声明 |
| **动作** | 壳 API / 壳命令 | `appearance.pickImage()`（壳决定起始目录、过滤、拷贝入库） | `theme.pick` / `theme.reset*`（已有） |
| **呈现** | UI 插件（可替换） | 只画「选择图片」控件 | 只画主题卡/下拉 |

> ⛔ 反例：插件传 `defaultPathKind:"appearance"`，壳再按这个字符串拼路径——语义的一半在插件、一半在壳，换 UI 就断。

---

## 四、归属判据表（可直接查）

| 能力性质 | 该住哪 | 反例 |
|:--|:--|:--|
| 打开/选择宿主资产目录 | 壳命令/API（路径由主进程解析） | 插件拼 `userData/appearance` |
| 配置项的默认值/枚举/分组/依赖 | 配置 schema 声明 | 插件里 `if (key==="app.themeColor")` |
| 资产域（背景图属于哪一域） | schema 的资产域字段 | 插件传域名字符串 |
| 系统对话框的起始目录/过滤器 | 壳（一个动作一个 API） | 插件传 `defaultPathKind` |
| 宿主能力的权限判定 | 壳 | 插件自己判「能不能」 |
| 纯展示布局/图标/文案排版 | 插件私有 | — |
| 纯函数（解析/格式化） | 壳 core 或共享包一处定义 | 插件抄一份 |

---

## 五、本档不做什么

- ⛔ 不是「把所有逻辑都搬进壳」——**长什么样的脸**仍归插件私有（硬约束 28）。
- ⛔ 不追求「插件一行代码没有」；只搬**语义**（默认值/路径/权限/域）。
- ⛔ 不与插件权限系统合并（那档管「许不许」，本档管「谁拥有语义」）。
