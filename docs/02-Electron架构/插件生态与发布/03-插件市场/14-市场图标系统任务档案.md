## 〇·六、图标管理系统·一处一图总表（2026-09-09 午后用户点名「系统管理要做好」）

> **用户新拍三点（叠加 §〇·五）**：① 样张方向点头 + 侧栏彩色小框**放大一档**；② **标签栏每个标签旁的小图标 = Type-2 彩色图**——理由「不是所有插件都有图标栏图标」，标签不依赖图标栏 icon；③ **文件标签**（editor 开的 .c/.h/.py…）显示**该文件类型的图标**，与文件树**同一套**（用户亲见：同 .c 文件在文件树有类型图标、在标签栏是 📄 文档占位 = 乱）。

**一处一图总表（消费端统一裁决点）**：
| 出现位置 | 显示 | 取图规则 |
|:--|:--|:--|
| 壳最左图标栏 | 插件线稿小图 Type-1 | 仅 4 只（插件市场/串口/文件树/设置）自备；单色滤镜强制 |
| 市场列表行 小框 | 插件彩色图 Type-2 | 每插件一张；缺省统一默认块 |
| 市场详情页 顶 | 插件彩色图 Type-2（与列表同一张） | 同上 |
| 标签栏·插件/视图标签 | 插件彩色图 Type-2 | 同上（图标栏 icon 非前提） |
| 标签栏·文件标签（editor 文档） | **文件类型图标** | 与文件树同一套（FileIconResolver / 图标主题数据） |
| 文件树行（folder/file by name/ext） | 文件类型图标 | FileIconResolver 数据驱动（E5.8#133 双形态 + 主题可换） |

**两个图标域（分开管，别混）**：
- **插件身份域** = plugin.json `icon`/`marketIcon`（Type-1 线稿 / Type-2 彩色）。凡「代表这个插件」的位（图标栏/市场列表/详情顶/该插件的视图标签）用它。editor 这类文件型插件同样有一张自己的 Type-2 彩色图（市场/详情用），与它文件标签的类型图标是两码事。
- **文件类型域** = 文件图标主题（data 驱动，现住 file-tree `services/FileIconResolver` + `utils/icon-mappings` + core IconThemeMappings 契约，主题可整体替换）。凡「代表一个文件」的位（文件树行 / editor 文件标签）用它。**一个文件在任何入口（树、标签、搜索行）必须同一张**。

**接线缺口（批次内探清再定，属实现细节）**：标签栏图标现由壳 windowLayout.ts:96-106 **按标签所属插件**解析（editor 无 icon → 全 📄）；文件标签要出「文件类型图标」需：① 标签携带文件路径/扩展（现 sourceId 即绝对路径）；② 一处**共享文件图标服务**——壳不得 import file-tree 插件内部（插件独立性硬约束），走图标主题核心注册表 / linkdesk API 服务面；③ 判定「文件标签 vs 视图标签」用声明字段而非 pluginId 硬编码（硬约束 10，现无该声明 → 批次立档讨论，可能加 tabBehavior 维度如 `document: true`）。

**🔥 合规红线（2026-09-09 立项自检——实现批不得破坏，四道坎逐条对齐）**：
- **归一化（一处裁决）**：插件身份图裁决链（`marketIcon ?? icon ?? 默认块`）必须是**共享 util 一处**——壳标签栏 / 市场列表 / 市场详情同调，**禁止各消费方复制这条链**（现状已有漂移风险：#67c 市场 display.ts 一份、壳 windowLayout 只读 icon 不认 marketIcon → 一旦壳标签要显 Type-2 就会写成第二份）。**文件类型图标的数据 + 解析同样须归一为共享图标主题服务一处**（file-tree 行 / editor 文件标签 / 搜索行同消费）——FileIconResolver/icon-mappings 现住 file-tree 插件内，若 editor 标签各自实现/import file-tree = 跨插件 import 或复制双源，两处都不许。
- **无硬编码**：图标栏「4 只」由各插件声明决定（emergent，壳零 ID 字面量，硬约束 10）；「文件标签 vs 视图标签」判定走声明/数据字段（sourceId 有路径），禁 `pluginId==="editor"` 之类；任何位置显示哪张图只从 manifest 字段解析，不写「某插件恒用某图」。
- **无死代码**：默认图换型 = **替换** #66 A 家族 640 默认（defaultCoverArt data-URI 删除，不留两套）；marketIcon 从 cover.svg 改指 Type-2 后 cover.svg 资产**仍被 README 引用**（非死）；#67c「展示位/行内位分治」函数收回后**删旧分支**不留死支；icon.png 已 git rm（#68b）不复活。
- **AI 友好**：语义全走 plugin.json 声明字段 + schema 三副本 + contracts:gen（additive）+ [06-图标.md](06-图标.md) 同步（E6 清单 #69h）；新声明字段先立档（contributes-schema-versioning 纪律）再落码；清单任务行 = 指针 + file:line 锚 + 可勾（本清单仓库纪律）。

**插件作者视角（第三方自由制造 + 可拓展——对齐 E6「10 分钟第一个插件」验收）**：
- **最小契约 = 越小越好**：作者**可以完全不配图**（没图 = 统一默认彩色块自动兜底，市场照常有脸）；**配了就一张 `icon` svg** → 市场列表/详情/自身插件标签全链路自动显，壳零开关零特判。`marketIcon` 只是「想给市场一张更讲究门面」时的可选进阶，缺省回退 `icon`——作者不需要懂字段分工那套。
- **图标栏不进第三方**：图标栏 = 壳 chrome，仅内置 4 插件占位；第三方插件**无法也不需要**进图标栏 → Type-1 线稿那套对作者永远不可见，作者永远不用写第二个图标字段。
- **文件图标必须 = 公开贡献面 + 公开只读 API**：#69g 提共享服务时同时满足——① 作者开新文件类型可**声明式贡献**该类型图标（整套换 = 图标主题插件；对标 VS Code `fileIconThemes`），**禁止靠改中央表**（改中央表 = 不可拓展）；② 编辑/文件类第三方插件要渲染「与树一致」的标签图 → 经 `linkdesk.*` 只读 API（additive + guard/契约对齐纪律），不 import 壳内部。
- **判定全在壳、作者零了解**：文件标签 vs 视图标签、取哪张图，全由壳按标签自带数据 + 共享解析器自动裁决——作者声明里没有开关、没有 pluginId 被消费；**新插件落地即自动有图，永不需要改壳**。

## 一、双图标模型设计定案（用户 2026-09-09 亲口归档）

1. **不是所有插件都是视图向/有界面图标**：功能式插件（如 python 语言插件、翻译插件）没有自己的简化图标，**但市场展示页仍须显示一张图标**——内容不限。
2. **有简化图标的插件可拥有两枚**：图标栏/界面的「简化单色小图标」**≠** 详情页/市场的「正常介绍图标」。双视图类插件拿简化图标当展示图不理想 → 分开声明。
3. **市场展示图标优先用彩色 SVG**：尽量给每个插件绘制一张市场介绍 SVG，届时每个插件 plugin.json **小改一次**（声明或补声明）。
4. **默认图标**：没画展示图的插件，市场统一显示一张**规定好的默认图标**——取代现在的 📄 emoji / codicon-symbol-misc 兜底。
5. **🔥 一律矢量 SVG（2026-09-09 用户加定）**：插件图标统一矢量图——**不要 lucide 图标名、不要 png 位图、不要 emoji 当图标**。简化界面图标与市场展示图都应是 SVG 资产文件。现有 lucide（如 file-tree `FolderTree`）、png（serial-monitor/settings）在逐插件批次一并转 SVG；`icon`/`marketIcon` 落点都指向 `.svg` 文件（iconSource 恒 `svg` 或省略自动按文件名推断）。「lucide/codicon 名 descriptor」自本定案起对**新插件图标**不再作为推荐形式；壳内 UI 装饰性小图标（齿轮/删除/下载这类 codicon）是否一并去留 = 另一盘范围问题，用户另行点名（本档案不扩）。
6. **🔑「市场展示图」是展示框/封面美术，不是图标（2026-09-09 用户定义）**：市场详情/列表那个「图标」位，本质是插件的**展示框（cover art）**——SVG 可以画得非常讲究、非常复杂，**不受「小图标要简洁」约束**。它是一张给插件做门面的美术图，跟界面里那枚单色小图标是两码事（同见定案 2 双图标模型）。市场位语义 = 「展示图（cover art）」；界面位语义 = 「图标（icon）」。本档案凡写「市场展示图 / 展示图标」均按此理解。
