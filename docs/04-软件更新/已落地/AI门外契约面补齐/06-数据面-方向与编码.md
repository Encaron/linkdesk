## 一、D1 · 收发方向 ＋ 原始字节（🥈）

### 问题

B2-6：「发送与接收混在一行流里」。插件收到纯文本流，不知道哪句是自己 `send` 出去的、哪句是设备主动上报的。

### 为什么插件补不了

- 设备回显可能**分块**、可能**改格式**（加 `\r\n`、回 `OK` 而不是原样）；
- 并发/多会话下「记住我发了什么再扣掉」扣不准；
- 每个插件都得实现同一套猜法 ⇒ **同一个 bug 多处出现**（违反归一化）。

⇒ 方向必须在**壳的读写边界**打标：方向是事实，不是推断。

### 设计

`SerialDataPayload` 改为「**载荷 + 方向**」，壳不再产出文本：

```ts
// @linkdesk/contracts —— 唯一定义
interface SerialDataPayload {
  portName: string;
  dir: "rx" | "tx";        // 壳在读写边界打标：写出去 = tx，收到 = rx
  data: Uint8Array;        // 原始字节；解码归插件
  at: number;              // 时间戳（已有语义，保留）
}
```

| 层 | 改动 | 判据 |
|:--|:--|:--|
| `@linkdesk/contracts` | 类型改 `{portName, dir, data}`；**删 `text`** | 唯一定义 |
| 壳 `electron/services/serial-service.ts` | 写口 → `dir:"tx"`；读口 → `dir:"rx"`；**不再 decodeBuffer** | 一处实现 |
| SDK | 透传，⛔ 二次解释 | 零逻辑 |
| 插件 | 自己解码（见 D2） | 零推断方向 |

### 归一化

- 方向判定**只有一处**（壳的写口/读口边界），⛔ 插件侧再猜。
- 字段进 contracts，⛔ 插件自定义 `isEcho` 之类平行字段。
- `text` **直接删除**（内测免兼容，决策 #10）——⛔ 保留 `text` 当兼容，否则又出现两套真相。

### 不做

- ⛔ 不做「按内容匹配即 tx」：分块即失效（01 案已证）。
- ⛔ 不让壳也顺手给一份 `text`「方便插件」：那会让解码策略悄悄回到壳，违反底盘最小面。

## 二、D2 · 编码：策略住插件，解码原语共享（🥈）

### 问题

B2-7：「同一屏既有 GBK 乱码又有正常中文」。设备 BOOT 段是 GBK、后续日志是 UTF-8，单档解码必然一半乱码。

### 分层（这是与底盘的裁决点）

| 层 | 住哪 | 内容 |
|:--|:--|:--|
| **解码原语** `decodeBytes(data, coding)` | **共享**（`@linkdesk/plugin-sdk` 或共享工具，一处定义） | 纯函数：字节 + 编码名 → 文本；⛔ 不含「选哪个编码」的策略 |
| **编码档位清单** | 共享（同一处，随原语） | 一份规范列表；⛔ 插件各抄一份 |
| **会话的编码策略**（当前选哪档、「自动」的回退顺序） | **插件**（会话级属性） | 归插件；壳完全不知道 |
| **解码时机/缓存** | 插件 | 插件自己决定 |

> 判据：解码是**纯函数工具** ⇒ 按落位表「一处定义」；选档是**业务策略** ⇒ 归插件。

### 设计

**在串口插件原有的「接收编码」下拉里新增「自动」档**（决策 #3）：

| 档位 | 行为 |
|:--|:--|
| UTF-8（现有） | 严格 UTF-8 |
| GB2312（现有） | 严格 GB2312 |
| Shift-JIS / Latin-1（现有） | 不变 |
| **自动（新增）** | 先按 UTF-8 严格解码；**解不出**（非法序列）再按 GB2312 解 |

- **四个手动档全部保留**（⛔ 不许用自动档替换它们——自动档在混合流里仍可能猜错，手选是权威）。
- 切换档位即时生效，对**已收到但未渲染**的数据不追溯（UI 明示，⛔ 假装能重解）。
- 自动档的回退顺序是**插件策略**，写成可读常量，⛔ 藏在 if 链里。

### 归一化

- 解码**只有一处**（共享原语）；编码列表**只有一份**（共享常量）。
- ⛔ 不做全局开关：编码是**会话级**属性，全局会串台。
- ⛔ 插件不得自己写 `new TextDecoder` + 手写 GBK 分支——那就是第二份解码器。

### 回归（四类样本，缺一不可）

| 样本 | 期望 |
|:--|:--|
| 纯 ASCII | 五档（四手动＋自动）结果一致 |
| 纯中文 UTF-8 | 自动 = UTF-8 |
| GBK 混合（BOOT + 日志） | 自动 能同时解出两段（B2-7 的判定样本） |
| 二进制（含 0x00/0x80+） | 自动 **不崩**、不乱码扩散；显示策略与现有二进制提示一致 |

## 三、判据（对着 07 过一遍）

| 判据 | 本条要求 |
|:--|:--|
| 归一化 | 方向一处判定；解码原语一处；编码列表一份；`text` 删除不留第二真相 |
| AI 友好化 | `dir` 让 AI 区分「我的请求」与「设备主动上报」——自动化闭环的前提 |
| 无硬编码 | ⛔ 插件写编码列表副本；⛔ 壳写死某插件名 |
| 无死代码 | `text` 删干净；四档全部有用；⛔ 自动档留下无人走的分支 |
| 高内聚低耦合 | 壳只管字节与方向；⛔ 壳不知道「BOOT 段」是什么、也不选编码 |
| 文件禁止平铺 | 两主线住本一档 |

## 四、验收

1. **D1**：插板子 `send "AT"` ⇒ 流里该条带 `dir:"tx"` 与原样字节；设备回的 `OK` 带 `dir:"rx"`；分块回显也正确。
2. **D2**：GBK＋UTF-8 混合样本选「自动」两段都正常；选「UTF-8」复现原乱码（证明手动档仍有效）。
3. **回归**：四类样本 × 五档全部跑一遍，无崩溃、无乱码扩散。
4. **消费方**：[01](01-消费方-设备文件系统.md) 的 `list/get/put/remove` 在 D1 到位后可用。
5. **跨插件**：任何用串口的插件都自动获得 `dir` 与字节（⛔ 需逐插件适配方向）。
6. **边界**：壳侧搜索不到任何编码策略（无 `decodeBuffer` 的选档逻辑、无 `SERIAL_CODINGS`）；插件侧搜索不到 `TextDecoder` 第二实现。
7. `npm run check` 全绿 ＋ `ui:build`（若动了共享 UI）。
