## 一句话账（为什么会有这一件）

用户 2026-09-27 实机发问：**图标栏汉堡菜单上悬停出来的那个"菜单"小方框，叫什么、是不是 Electron 自带的、是不是我们画的？**

查清的结论是：**它是 Chromium 原生 tooltip**（HTML `title` 属性白送），外观由系统决定、**CSS 碰不到、不跟壳的主题/字号/模糊**——等于**一个不属于我们的控件长在我们的软件里**。而软件里同时还有**壳自己的玻璃提示卡 `HintCard`**（E6#120，2026-09-19），两套长相完全不同、且**全软件只有 1 个地方用了后者**。

普查（本次实测）：壳侧 **43 处**、官方插件容器 **95 处**（粗测）悬停提示，**全是原生小方框**。

用户当轮追加三条要求：① 提示要能**自动带出快捷键**（对标右键菜单）② 要有**机械门禁**，既管第三方插件仓、也管壳自己新增的组件 ③ **独立一件、先进池子、设计方案先行**（本子夹即其落点）。

**好消息**：① 的机制**已经存在**——壳已在做"命令 → 快捷键文本"解析（`src/hooks/usePoolSync/titlebar.ts:89` 的 `formatKeyLabel`），右键菜单正在用；提示条只是**同一份数据的第二个消费方**，不是新能力。

## 与「菜单补全」的交界（同区先看清楚）

[`../菜单补全.md`](../菜单补全.md) 与本报同属"壳 chrome 一次收口"这一族，且有**共享数据源**：

- 菜单项要带快捷键 ⇒ 走 `titlebar.ts` 的命令映射；提示条要自动带快捷键 ⇒ **必须复用同一份**（两把尺子必然漂移）。
- **建议次序**：菜单补全先做（它本来就在"下一批"推荐位），提示条后做，**直接吃菜单已推的那份数据**，不重复造。
- 若两件同批，则命令映射**一次性设计到位**，两边共用。

## 依赖与边界

- **不改 API 面**：不加新 `window.linkdesk.*`、不加新 IPC、不加新 `contributes.*`——走**属性式声明**（`data-hint` / `data-hint-command`）＋ 组件门面。这是刻意的设计选择，省掉整套契约四齐全。
- **不改浮层通道**：必须复用 `OverlayPortal` → `#overlay-root`（E5.8#107 单一门）；⛔ 不新建 overlay 目录。
- **不替代 `HintCard`**：说明卡继续归它（有标题/注脚/长文案/玻璃）；本件是**轻提示条**——`HintCard` 文件头自己划出的那个"别的件"。
- **插件源码外移（E6 第七层）**：插件侧改动 = 跨仓批次；本档引用插件内文件一律写作 `<插件 id>:<仓内相对路径>`（真相源 = 各插件独立仓，本机克隆 `E:\linkdesk-plugins\official\<id>\`）。
- **第三方仓 `geme-tihu-bicycle`**：⛔ 不代改，转达作者。
- **流程**：按 04 README §一——拍板要做才立项（攒批模式下不定版本号）；本子夹在被拍板前**不占版本号**。
