## 〇、🔴 安装包文件名唯一真理源（2026-09-11 补——本档原稿埋了 `asset-missing` 的雷）

**问题实锤（2026-09-11 实测 + 读 electron-builder 26.15.3 源码查实）**：同一个安装器，本仓**四个名字**在流通，而且**其中一个由打包器自己偷偷翻译出来**——

| 出处 | 写的名字 | 后果 |
|:--|:--|:--|
| `E:\linkdesk-build\` 磁盘上的真文件 | `LinkDesk Setup 0.1.47.exe`（**带空格**） | 实际产物（07:51 构建） |
| 同目录 `latest.yml` 的 `path`/`files[].url` | `LinkDesk-Setup-0.1.47.exe`（**空格换连字符**） | 🔴 **指着一个磁盘上从不存在的文件** |
| 本档 §2.2 下载入口 | `LinkDesk-Setup.exe`（无版本号） | 死链 |
| [01 §2.3 Release asset 约定](../06-主软件更新/01-更新机制设计.md) | `linkdesk-setup-{version}.exe` | **更新器精确匹配它** |

🔴 **`latest.yml` 那个名字是打包器翻译出来的，不是谁手误**——链条如下（每一步都在 `node_modules` 现场验过）：

| # | 环节 | 出处 |
|:--|:--|:--|
| 1 | 本仓 git remote 指向 github ⇒ electron-builder **自动推定** publish provider = github（**仓里连一个 `publish` 配置都没写**） | `PublishManager.js:217-222` |
| 2 | 不写 `artifactName` ⇒ NSIS 默认名 = `LinkDesk Setup 0.1.47.exe`（含空格） | `NsisTarget.js:303` |
| 3 | 空格不在 GitHub 允许的 `[0-9A-Za-z._-]` 内 ⇒ 判不安全 ⇒ **只把空格换成连字符**得 `LinkDesk-Setup-0.1.47.exe` | `platformPackager.js:690` |
| 4 | provider 是 github 时，把它写进 `latest.yml` 的 `path` / `files[].url`——**但磁盘文件不改名** | `updateInfoBuilder.js:100` |

⇒ **更新器读 `latest.yml` 的 `path` 去找 asset，Release 上躺的却是磁盘那个带空格的名字** ⇒ 检查更新能成功、下载永远失败，报 `asset-missing`。这就是 [01 §2.3](../06-主软件更新/01-更新机制设计.md) 自己预警的那个 bug——**它在本仓已经是活的了，不是预警**（CI 那条 `files: <产物>/*.exe` 原样上传磁盘文件，正好撞上）。

**定案 —— 唯一真理源 = `electron-builder.yml` 的 `artifactName`**（清单 **E6#42e**）：

```yaml
# electron-builder.yml（本轮新增）
artifactName: "${name}-setup-${version}.${ext}"   # → linkdesk-setup-0.1.47.exe（name 小写，见下）
```

- `${name}` 取 `package.json` 的 `name`（`linkdesk`，全小写）——**不是 `productName`（`LinkDesk`，大写 L/D）**。大小写差异同样是 `asset-missing` 的成因（Linux/URL 场景大小写敏感）。
- ✅ **为什么这一行就够**：`linkdesk-setup-0.1.47.exe` 的每个字符都落在 `[0-9A-Za-z._-]` 内 ⇒ 上表第 3 步的安全名判定直接通过 ⇒ `safeArtifactName` 返回 `null` ⇒ **`latest.yml` 不再被改写** ⇒ 磁盘名 / `latest.yml` 的 `path` / Release asset / 下载链接**四处同名**。不是「靠人自觉统一」，是**结构上只剩一处可能**。
- **所有消费方一律从这一处取真值，禁止再手抄字符串**：下载入口（§2.2）、CI 上传与 Release（§1.1）、更新器匹配（[01 §2.3](../06-主软件更新/01-更新机制设计.md) `linkdesk-setup-{version}.exe`）、Release 页眉文案。
- 🔴 **验收硬判据（#42e）**——已落成 [scripts/assert-installer-name.mjs](../../../../scripts/assert-installer-name.mjs)，并挂在 `npm run electron:build` 尾部（每次打包自己先量一遍）。三条独立判据：

  1. **配置层**——`electron-builder.yml` 顶层 `artifactName` **逐字符等于** `${name}-setup-${version}.${ext}`；
  2. **产物层**——`directories.output`（= `../linkdesk-build`，**在仓库外**，E6#15e 定案）顶层**有且只有一个** `.exe`，名字**逐字符等于** `linkdesk-setup-{package.json version}.exe`；
  3. **元数据层**——同目录 `latest.yml` 的 `path` 等于那个 `.exe` 的**实际**文件名（🔴 更新器读的就是它；只查文件不查它，等于漏掉本档这半条命）。

  ⚠️ **「有且只有一个」与第 3 条都是刻意的**：0 个若判过，偷懒写法就是「什么都没找到 ⇒ 什么都没错」= 恒绿假门禁；只比配置与产物、不比 `latest.yml`，则「文件改了名、元数据还指着旧名」这类事故照样漏网。**判据 3 与判据 2 的两侧是两条独立证据**（磁盘 vs 产物元数据）。
- 🔴 **CI 不再手抄任何路径**：`node scripts/assert-installer-name.mjs --print-exe` 在全过后把安装包**绝对路径**打到 stdout（人读状态行改走 stderr）⇒ §1.1 的 Release / 上传步骤直接 `files: ${{ steps.installer.outputs.path }}`。**输出目录与文件名两件事都只剩一处真值。**
- 🔴 **门禁必须证明自己会红**：`npm run assert:installer-name:selftest` 内置 **11 例负例/正例自测**（纯内存、不落任何文件）——删掉 `artifactName`、产物被改名、`latest.yml` 写歪、目录空、多产物，**全都验过确实会红**。**恒绿的门禁不是门禁**（memory `snapshot-shadows-truth-bug-class`：判定挂在「期望从现场读」上 = 断言恒真 = 假门禁）。
- 🔴 **姊妹门禁（#57.15a①，2026-09-12 建成）**——[scripts/check-packaging-files.mjs](../../../../scripts/check-packaging-files.mjs)：产品身份 `electron/product.json` 必须**真的进 asar**。它防的是同属「静默降级」那一类的事故——缺文件 ⇒ `electron/product.ts` 的 `loadProduct()` 把 `readFileSync` 的异常 catch 吞掉 ⇒ `updateUrl` 退成空串 ⇒ **更新器没有更新源，且一个字都不报**。两层：① **配置层**挂 `npm run check`（`files:` 逐项解析后必须覆盖它，含 glob 与 `!` 取反）② **产物层 + 内容层**挂 `npm run electron:build` 尾部（真打的 asar 里真有该条目、内容能解析、`updateUrl` 非空）。**②刻意不挂 `check`**——提交时磁盘上多是上一次的 `win-unpacked`，拿旧产物判新配置就是常态假红。自测 **16 例**；负控拿**真实产物**验过会红（删掉那一行 ⇒ 真打一次包 ⇒ ①②③全红），不是内存造假。⚠️ 其**目标路径现场从 `electron/product.ts` 抽**（活消费方是真值），抽不出才退回契约字面量并**出声**——与上面 `artifactName` 那条「契约写死」的取舍刻意相反，两种都在防同一件事：断言跟着现场一起变 ⇒ 恒真 = 假门禁。
- ⚠️ **别把两个名字看成一个（这是两个概念，不是一个拼错）**：

  | 名字 | 在哪 | 是什么 |
  |:--|:--|:--|
  | `linkdesk-setup-{version}.exe` | **GitHub Release 上的 asset** | 发布侧产出的文件（本文档管的就是它） |
  | `linkdesk-update-{version}.exe` | **用户机 `{userData}/update/` 里** | 更新器校验通过后**本地改名**保存的待装包（[01 §2.4](../06-主软件更新/01-更新机制设计.md) 管） |

  ⇒ 两者**故意不同名**（远端 asset 名 vs 本地暂存名），**不是笔误，不要「统一」它们**。真正要求一致的是：更新器要按 `linkdesk-setup-{version}.exe` 精确匹配去 Release 上找 asset——**这一条只跟 §〇 的 `artifactName` 对齐**。

### 1.2 触发条件

| 事件 | 干什么 |
|:--|:--|
| push 到 `electron` 分支 | build + check + 上传 artifact |
| push tag `v*` | build + check + 发布到 GitHub Releases |

### 1.3 Release 步骤

```
push tag v0.2.0
  → CI 跑 check + CHANGELOG 段门禁（#57.15d）+ 安装包名门禁（#42e）
  → 产出 linkdesk-setup-0.2.0.exe（名字由 artifactName 唯一决定，§〇）
  → 创建 GitHub Release v0.2.0
  → 上传 .exe + latest.yml + .blockmap 三件（路径由门禁脚本 --print-exe 给出，**不手抄**）
  → Release body 必须写入本次 CHANGELOG 正文（不是 GitHub 自动罗列的 commit 列表）
```

> 🔴 **Release body 的正文来源（2026-09-11 定，与 #57.15d / #57.8e 配对）**：
> 更新器与发行说明页读的是 **Release body**（[05 §2.4](../06-主软件更新/05-发行说明.md)），**不是 GitHub 的 `generateReleaseNotes` 自动列表**——自动列表是 commit 流水，用户看不懂，也不是人写的那份说明。
> ⇒ CI 的 Release 步骤要把 `CHANGELOG.md` 里 **`## v{version}` 那一段正文**灌进 body。**`generateReleaseNotes: true` 保留但不作为正文**（可退化为「首次贡献者名单」之类的附加区）。
> ⇒ **这就是 #57.15d 那条门禁存在的理由**：缺段 ⇒ body 空 ⇒ 用户点「查看更新内容」看到一片空白。

### 1.4 覆盖安装方向（🔴 E6#42d——发布前必测，别省）

**测试 = 双向往返**，不是只测「装新版」：

| 方向 | 期望 | 不过怎么办 |
|:--|:--|:--|
| 旧版 → 新版（更新器正路） | 覆盖成功、版本号变新、插件与设置全在 | 红灯，修 |
| 🔴 **新版 → 旧版**（手工跑老安装器） | **NSIS 应当拒绝或至少不静默降级** | **如果 NSIS 不拦，则必须在应用层加方向守卫**——判据复用插件侧 **E6#33c 锚①**：`electron/ipc/handlers/plugin-install-handlers.ts` 的**同版恒拒 / 旧版默认拒 / 只有显式 `allowOlder:true` 才放**，比对函数就是 [`src/core/utils/plugin/semverUtils.ts:88`](../../../../src/core/utils/plugin/semverUtils.ts#L88) 的 `updateTargetDirection()`（返回 `upgrade`/`downgrade`/`same`）。**直接复用它，不许各写一份判断**（[01 §2.4 残留清理](../06-主软件更新/01-更新机制设计.md) 那条陈旧 `.exe` 清理用的是同一套语义） |

> ⚠️ **为什么单列一条**：插件侧在第 3 层为「装旧版覆盖新版」这事反复修过好几轮（第 3.5/3.6/3.7 层都有回响）。**主软件侧是同一个病、不同的载体**，不要在第五层重新踩一遍。判据必须是**实测出来的**，不许以「NSIS 应该会拦」结案。

#### 1.4.1 🔴 实测结论（2026-09-12，E6#42d 收口）

**结论一：NSIS 默认不拦，已经实测确证（源码 ＋ 实测双证）。**

- 源码侧：逐份读 `app-builder-lib/templates/nsis/` 全部模板，**没有任何版本比较逻辑**；`version` 只出现在 BrandingText（纯外观）与 `include/installer.nsh:125` 的 `WriteRegStr … DisplayVersion`（**只写、从不读、从不比对**）。
- 实测侧：拿 **0.1.47 的旧包**覆盖已装的 **0.1.49** ⇒ **静默装上**：退出码 **0**、`DisplayVersion` 由 `0.1.49` 掉回 `0.1.47`、安装目录文件 mtime 全部回退。用户 2026-09-12 的真实遭遇（装 0.1.47 时双击 0.1.48 **毫无提示**）也是同一条。

**结论二：因此补了守卫——但补在「安装器层」，不是原文写的「应用层」。**

- 载体 = `build/installer.nsh`（electron-builder 自动 include 约定，**未动 `electron-builder.yml`**）；挂点 = `customInit`；比对源 = 卸载项 `DisplayVersion`。
- 口径（用户 2026-09-12 拍板）：**本包更新 ⇒ 一个字都不问**；**同版 / 更旧 ⇒ 问一句，默认「否」**。静默 `/S` 下不弹窗，按「用户取消」办 ⇒ 退出码 **1602**（`ERROR_INSTALL_USEREXIT`）。
- 六路实测见 [E6 执行清单](../E6-执行清单.md) E6#42d 反向格；弹窗截图 `E:\linkdesk-build\scratch\dlg-same.png` / `dlg-older.png`。

**结论三 🔴 两层不是二选一，各管各的（本条是实测逼出来的新认识）。**

- **安装器守卫管不了已经发出去的老包**——守卫是**编进包里**的，0.1.47 / 0.1.48 的安装器里没有这段代码，双击它们照样直接覆盖（上面那条实测就是这么发生的）。⇒ **安装器层只能保护「从这一版起往后构建的包」**。
- **「本机被老包降级了」这件事，只有应用层看得见**。要覆盖这段缺口，得在主软件里加一条「启动时发现版本比记录过的低 ⇒ 提示一句」——**尚未实现，待拍板**。
- ⇒ 修正原文口径：**「判据复用 `semverUtils.ts` 的 `updateTargetDirection()`」在安装器层做不到**（NSIS 跑不了 TypeScript，改用 NSIS 自带的 `${VersionCompare}` ＋ 三行策略）。但**「方向决策只许有一处」这条规矩不撤**——它管的是**更新器该不该动手**那类决策，仍然只在 `semverUtils.ts` 一处；安装器层不做方向决策，只做「覆盖前问一句」的第二道闸。

## 二、下载入口——GitHub 承载（E6#43）

> 🔴 **2026-09-11 用户拍板改向——「官网 + 域名」方案整条作废。**
> 原话：「**关于那个域名那个东西，就先不要了，GitHub 能不能就是暂时用着？就是说我不要自己的官网了。**」
>
> **本节原稿（2.1 站点结构 / 2.2 落地页 HTML / 2.3 自定义域名）写的是一个不存在的站点**：域名 `linkdesk.io` 从未购买、GitHub Pages 从未启用、DNS 从未配置——**三件都是「待办」，不是「现状」**。现已全部撤除。
> 🔴 **撤的是「自己建站」，不是「下载入口」**：Release 资产本来就由 CI 传到 GitHub（§一 #42b/#42c），**下载入口落在同一处 = 少维护一个站点、少一个会漂的第二真值源**。**「不做官网」≠「下载链接不用管」**——README 入口、Release 正文、更新器抓的资产名，三件事一件都没少。

### 2.1 方案

**两个入口，都在 GitHub 站内，零自建资产。**

```
github.com/encaron/linkdesk          ← 仓库 README 顶部放下载入口
  └── README.md → 指向 releases/latest

github.com/encaron/linkdesk/releases/latest   ← 真正的落地页（GitHub 生成）
  └── Release 正文 + 资产列表（linkdesk-setup-{version}.exe）
```

### 2.2 入口内容

**① 仓库 README 顶部**——放一个指向 `releases/latest` 的下载入口。

> 🔴 **指向 `latest` 这个别名，不要写死版本号。** 写死 ⇒ 每次发版都要回来改 README ⇒ 迟早漏一次 ⇒ 出现「README 说 0.1.47、最新其实是 0.1.52」的第二真值源（本档 §〇 那条病根的同型）。

```markdown
## Download

**[Download for Windows](https://github.com/encaron/linkdesk/releases/latest)** — Windows 10/11 · 64-bit

> 版本号与文件名见 Release 页；安装包文件名唯一真理源见 `electron-builder.yml` 的 `artifactName`（本档 §〇）。
```

**② Release 正文**——每次发版（#42c 自动打 tag → Release）正文模板：

```markdown
## LinkDesk v{version}

**下载：** [`linkdesk-setup-{version}.exe`]({Release 资产直链})
**发布日期：** {date} · **系统需求：** Windows 10/11 · 64-bit

### 变更
{从 CHANGELOG 或 commit 生成}
```

> ✅ **2026-09-12 已落地（E6#43a）**——上面两个模板不再是设想：
> ① **仓库 README** = 根 `README.md`（🔴 **实测：本仓此前根本没有根 README**，本条实为**新建**而非编辑；原任务措辞「README 顶部」隐含已存在）。
> ② **Release 正文** 由 CI 的 `Prepend download block to Release body` 步**自动拼** = 下载信息块 ＋ CHANGELOG 段正文，**三处值全取真值零手抄**（文件名 ← 门禁脚本 `--print-exe`；版本号 ← `package.json`；发布日期 ← CHANGELOG 段头，同段同源）。唯一真理源 = [`.github/workflows/build.yml`](../../../../.github/workflows/build.yml)。

> 🔴 **2026-09-11 订正（原 HTML 块的两个错，改写时保留教训）**：
> ① 原写 `LinkDesk-Setup.exe`——**无版本号 + 大小写错**，与实际产物不符 ⇒ 死链。名字唯一真理源见本档 §〇。
> ② 原写**带版本号的硬编码链接** `…/download/linkdesk-setup-0.1.47.exe`——**版本号会变，硬编码必然过期**。⇒ 要么用 `latest` 别名，要么由发布脚本生成。
> ③ 原稿的 `<a href="/marketplace">Browse Plugins</a>` 一并删除——那是**设想中的官网路由**，插件市场在**软件里**（状态栏/图标栏入口），不在网页上。
