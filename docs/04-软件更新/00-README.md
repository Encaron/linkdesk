## 一、版本号规则：CHANGELOG 是唯一真相源

软件更新点**不按本目录顺序走，也不按预设版本号走**——用着用着发现哪里不好，那个点就该更新，可能插队到任何规划点之前。流程（**攒批发版**，2026-09-26 用户拍板）：

```
发现更新点 → 进「待抉择池」（不占版本号）
          ↓ 拍板要做
立项（§三 已立项表挂行；攒批模式下【不定版本号】）
          ↓ 做完
dev 版测试（npm run electron:dev，秒级热更新）→ 用户点头
          ↓ 攒 2~3 个都点头的
统一定版本号 → CHANGELOG.md 落版本段（版本号唯一真相源）→ 打包发版 → 本 README 划销 + 档案 git mv 进「已落地/」
```

> **为什么攒批**：一次发版（打包＋上传＋tag）约 10 分钟，一个功能发一次太碎；dev 测试是秒级的，攒批把发版成本摊平。**别攒太久**——攒多了那次发版的回归测试面就大，2~3 个一批正好。
> **例外**：只有打包态才见效的改动（启动过场、程序图标等）dev 测不了，攒批发版时用正式安装包补测。

MINOR/PATCH 颗粒、MAJOR 触发条件沿用 [CHANGELOG.md](../../CHANGELOG.md) 既有口径；本目录只管「点什么、做没做」，不管「号排到几」。
