### 2.2 归属表语义的裁决（**核心产出 1**）

现状是「**记归属 → 打印 warn → 照旧归后注册者**」。候选：

| 路线 | 形状 | 要回答的硬问题 |
|:--|:--|:--|
| **(甲) 首撞者保留 ＋ 后来者降级不覆盖 ＋ `console.error`** | 异 pluginId 同 key ⇒ **先者的 properties 留下**，后来者**被拒**并**出声点名双方** | **被拒的插件会怎样？** 它的配置项**在设置页消失**——这算「可见变化」吗？（判据：**今天的行为是"值互相串"，那是更坏的"可见变化"**）· **同插件多次注册的 merge 语义必须继续合法**（`:133-137` 的注释明写「如 `contributes.configuration` + 自动注册的 statusBar 配置」） |
| **(乙) 只保宿主保护区，插件间维持 last-wins ＋ warn** | 加「宿主保留键账」；插件间不动 | 最省，但**两个第三方插件撞键**这条真害没治 ⇒ **按 §〇c 已否决**（规则要零例外） |
| **(丙) 甲 ＋ 乙** | 保护区判红 ＋ 插件间首撞保留 | 逻辑上最完整；**要论证不违「不许改机制」**（改的是**仲裁结果**，不是数据结构） |

🔴 **必须回应**：`ConfigurationRegistry` 自述的「**待 E2c #19b 审计后改 fail-fast**」——**本格的结论就是对这条欠账的正面回答**：**fail-fast（抛错）永久否决**（理由见 [00 档 §2.7](00-整理档案.md)：`parseContributions` 无 try/catch ⇒ 抛错 = 整只插件装不上），改为**降级 ＋ 出声**。**这条要写进结论，并同笔订正那段注释**（注释陈旧 = 下一个人还会照它做）。

⚠️ **仍然要核实/登记的两件事**（但**不改变"要改名"这个结论**）：
1. **设置页主标签显示的就是键名**（实测 `SettingRow.tsx:65` 的 `{configKey}`）⇒ 改名后**标签文字会变**。**这是明文接受的取舍**（§六.2）；本格要**实测并写进迁移说明**（作者面与用户可见处说明一次）。
2. **同一键多声明者**仍要一条结构性判据（**这条独立于改名，是运行时那层的事**）：「**同一个键只有一个声明者**」——不查名字、只看"有没有第二个声明者" ⇒ 归 §2.2 的仲裁路线。

⇒ **本格结论（照 §〇c）**：**判改名 ＋ 写迁移**；`explorer.*` / `files.*` / `terminal.external.*` **一律带上自己的插件 id**；**「语义是全局概念」这条不再成立为豁免理由** —— 真正的全局概念名只有三类（**文件关联扩展名 / 语言定义扩展名 / 语言包语言码**，[00 档 §〇c.2](00-整理档案.md)），**设置键不在其中**。

### 10.6 迁移设计（§2.3 第 3 条 —— 机制已在，本格只定形状）

**机制现况**（`src/core/services/configuration/schemaMigrations.ts`，E5.8#85 建）：`registerConfigMigration({ version, name, migrate })`；版本标志 = `app.schemaVersion`（未注册内部键，UI 不可见）；现有版本 **2/3/4/5**（`src/App/config/appearanceApplier.ts:156,176,198,224`）⇒ **本次迁移用 `version: 6`**。

**形状**（照模块头注释的三条硬约束，逐条落到本家族）：
```ts
registerConfigMigration({
  version: 6,
  name: "E6#111n-2 tree-settings-ownership",   // 1.42 落地时取真名
  migrate: async (ctx) => {
    // ① presence 自查：旧名**有 userValue 才**搬（没设过 = 零变更零写）
    // ② 目标名已有值 ⇒ 不覆盖（用户已在用新名 ⇒ 新名赢）
    // ③ 幂等：搬完 deleteMany(旧名) ⇒ 重跑时空操作
    for (const [oldKey, newKey] of TREE_SETTING_RENAMES) {
      const old = inspectConfiguration(oldKey).userValue;
      if (old === undefined) continue;
      if (inspectConfiguration(newKey).userValue === undefined) ctx.setMany({ [newKey]: old });
      ctx.deleteMany([oldKey]);
    }
  },
});
```
- 🔴 **幂等 + presence + 原子**三条都要落在代码里（原子由编排保证：任一迁移抛错 ⇒ 本次不落盘不提升，`runPendingConfigMigrations` 已实现）。
- 🔴 **表只有一份**：19 对映射**写在一个常量**（建议落 `src/App/config/**` 内的新文件，理由见下），**迁移函数与改名轮都读它**（⛔ 不许在迁移里再手抄一遍）。
- 🔴 **落点必须在账生成器的扫描集内**（本格定的口径把 `src/App/config/**` 包在内）⇒ 改名完成后，**19 个旧名会自动进「保留面」**（退役键语义，§9.2）——**这是有意的**：旧名一旦退役，别人再占它 = 迁移会把他的用户值删掉（真害）。⇒ 两条对账（①实况→账 ②账→实况）**都仍然绿**，且 SDK 腿会拦住「有人重新声明旧名」。
- ⚠️ **迁移归属**：**执行方是 1.42 / 1.43**（与改名**同笔**，`提交轴 = 插件仓 ＋ 壳`）；**1.34 只落判据与保护区，不动这 19 个键**（理由：1.34 的提交轴 = 壳 ＋ SDK，**不含插件仓** ⇒ 它改不了插件侧的声明与消费点）。
