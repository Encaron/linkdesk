## 一、用户质疑与诚实归因

用户功能诉求全是手机主题软件的成熟功能：自由调圆角 / 自由换肤 / 自由调字体 / 玻璃质感 / 混搭（5 个主题用 a 的图标 + b 的壁纸 + c 的锁屏 + d 的字体）。需求描述清楚，功能非新事物。**难不在「功能」和「需求」，在 LinkDesk 的历史架构**。

### 根本差异：安卓是基建自带 token，LinkDesk 是盖好楼后装修

- **安卓/iOS**：Material Design 第一天就把颜色/圆角/字体定义成 token，系统 UI、组件库、主题引擎**一体设计**。换肤 = 换参数，消费面天生统一。
- **LinkDesk**：组件（顶栏/侧栏/主区/状态栏/浮层）E4-E5 用 CSS 一砖一瓦写起，**大量硬编码颜色、局部变量、各自枚举**。E5.8 才给已盖好的楼做主题系统 = 装修。

> 类比：老房子装中央空调——需求清楚（每间都凉快），施工要穿墙打孔；新楼盘从设计图就预留空调位。**安卓是后者，LinkDesk 是前者。**

### 「同一个 bug 多次出现」的真相：不是复发，是同一反模式逐面漏网

| 反模式 | 表现（用户感知为「同一 bug 多次出现」） |
|---|---|
| 枚举漏项 | 浮层磨砂枚举 10 选择器漏 3 → 每加新浮层，同样的「没磨砂」换个表面再来 |
| 参考系错锚 | ratio 换算 / 玻璃 wash 与 label 矛盾 / panorama 永不实——同一根因三个表现 |
| 多路径不一致 | recipe/mix/override/播种四路各写各的，改一条漏一条 |

根因：**系统性的全局改造被拆成「修这一处」的局部补丁**，补丁盖住已知面，盖不住未知面。

### 新 bug 为什么总出现：消费面隐式 + 组合验证盲区

- **CSS 变量消费是隐式的**——任何组件都能 `var(--xxx)` 或漏掉，**没有任何机械检查能告诉你哪个表面没迁移**（安卓有类型系统保证组件必须声明用哪个 token）。
- 组合空间巨大（6+ 主题 × 14 覆盖键 × 混搭来源 × 玻璃参数），单测只能测 token 计算逻辑（recipe/mix/seeds），测不到渲染层每表面实际消费。

### 为什么「描述清楚却难」

用户描述的是「**要什么**」（功能需求，准确清晰）；难在「**在 LinkDesk 实现时的工程成本**」（消费面迁移 / 跨进程 token 契约 / 隐式 CSS 消费）。需求理解 ≠ 改造容易。

## 二、三条根治方向（把「装修」翻新成「基建自带」）

> 目标不是「修好当前 bug」，是让「这一类 bug 不再能产生」——把隐式消费变机械可检查。

### #128 消费面全量 token 化（核心改造）

- **现状**：组件 CSS 残留硬编码颜色/局部枚举；主题引擎统一广播但消费面有历史遗留。
- **目标**：审计全部组件 CSS，消灭残留硬编码，全部改走主题 token；**一次做完，不留补丁**。
- **范围**：顶栏/图标栏/侧栏/主区/状态栏/浮层/浮层内所有表面 + 组件库。
- **验收**：`grep` 硬编码 hex/rgba/hsla 只命中 token 定义处（零残留）；每表面消费主题 token，切主题全表面一致。

### #129 主题文件 formal schema（契约保护）

- **现状**：`appearance`/`colorways` 主题 JSON 契约**无 formal schema 校验**——只有类型推断 + 文档约束，格式错无机械拦截（运行时 API 类型在 contracts 里齐全，主题文件契约缺）。
- **目标**：主题 JSON 立 JSON Schema（对标 `plugin.schema.json`），格式错当场拦。
- **验收**：schema 校验脚本覆盖所有 `contributes.themes` 指向的 JSON 文件；错误主题文件加载时报错不静默。

### #130 CSS 消费面机械审计进 check（长期门禁，防回潮）

- **现状**：硬编码颜色无机械拦截 → 新代码随手写 `#xxx` → 同类 bug 重新埋雷。
- **目标**：硬编码颜色/枚举的 grep 审计进 `npm run check` 作门禁（对标 E5.7 静态卫生 `--max-warnings 0`）。
- **验收**：check 增加审计步骤，硬编码 hex 即红灯；新代码无法回潮。

**三者关系**：#128 是核心改造，一次性翻新；#129 是契约保护，格式错当场拦；#130 是长期门禁，**从机械层保证「同一 bug 不再回来」**。

## 三、为什么现在不做（用户拍板暂缓）

用户 2026-08-27 明确「先别做」。理由记录在案：
- 三方向是 E6 级跨全组件改造，工作量大，需要专门排期，不搭当前 E5.8 收尾的车。
- 当前 E5.8 仍有余量收尾任务，按「一次一个小任务」节奏执行。
- 本档案即为任务入口——未来排期时从清单 Phase 11.19 直接开工，无需重新调研。

**暂缓 ≠ 放弃**：这是用户拍板的结构性安排，不是 AI 的「当前够了/未来再做」话术。
