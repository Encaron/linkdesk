## 二、根因（死代码 + 一个从未兑现的 TODO）

| 环节 | 事实 | 证据 |
|:--|:--|:--|
| 恢复分支被掏空 | `if (detail.layout?.tabs?.groups?.length) { /* workspace:restore 事件由 useTabManager 接管 */ }`——**分支体是空的** | `src/App/lifecycle.ts:133` |
| 承诺的事件从未存在 | 注释说的 `workspace:restore` 事件**全仓只出现在这条注释里**，从无派发者、从无订阅者 | grep 全仓（2026-09-13） |
| 导入侧只 dispatch | 只派发 `RESTORE_WORKSPACE` 自定义事件；既不写 `LayoutService`，也不通知 `useTabManager` | `src/core/commands/shell/coreCommands.ts:85` |
| 启动恢复不覆盖导入 | 标签页布局恢复只发生在启动（读 `getTabLayout()` → `restoreLayout`） | `src/App/tabActions.ts:84-100` |

**🔴 精确口径（免得后人搜错方向）：** 不是「事件没人监听」——`RESTORE_WORKSPACE` **有**监听者（`lifecycle.ts:140` 注册、`:149` 注销）；断的是 ① **监听器里的恢复分支被掏空**，② 注释里那个**从未被创建**的 `workspace:restore` 事件。

## 五、待拍板项

1. **修法与范围：** 布局写回 + 触发重建 + toast 反馈（最小集）；面板/侧栏/脱出窗矩形是否一并接（多十几行，否则那部分重启才生效）；导入作用域 = 仅主窗口（池窗不受影响）——第一版可只做标签页+设置+提示，其余写成已知边界。
2. **覆盖确认：** 导入会瞬间整表替换当前全部标签页（等价于"关掉重开成导入的样子"）——是否加「导入将覆盖当前布局」确认框（AI 建议加，一行事）。
3. **健壮性边界（本次复核新增）：** 导出带了 `version: 1` 字段，但**导入侧不校验版本、也无 schema 校验**——建议最小校验（版本不认识就明确报错，不静默）。
4. **可选门禁（治本思路，做不做待拍板）：** 静态检查「空条件分支 + TODO 占位注释」这类"接线承诺"，或要求布局恢复入口**单一化**（见 §六）。

## 八、验收（用户视角）

1. 导出 → 改动布局（开关标签页/分屏/换主题）→ 导入 → **标签页布局与设置都回来**。
2. 导入一个坏文件（改坏 JSON）→ **明确报错**，不静默。
3. 导入成功 → **有提示**（toast）。
4. 启动/重启后导入结果仍在（走 `saveWorkspaceLayout` 落盘）。
