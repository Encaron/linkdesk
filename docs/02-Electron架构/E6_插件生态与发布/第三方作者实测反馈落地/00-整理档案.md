## 〇、前因后果——这一批为什么会被提出来

**时间线**：

1. **2026-09-19**：用户在**独立工程**里让一个**全新 AI**（与 LinkDesk 工程零接触、未读一行壳代码）用 `create-linkdesk-plugin` 脚手架从零造出游戏插件 `geme-tihu-bicycle`（鹈鹕骑车）——照着网上的「Pelican Riding a Bicycle」agent 能力测试梗。该 AI 全程只靠四份公开契约干活：脚手架全套、`file-tree` 参考仓、在线文档只读 **2 篇**（00-readme 总纲 + 17-region-map 区域映射）、本地 node_modules 里的 schema 与 SDK dist。当日走完 publish + 官方目录收录（第 22 员）。
2. **2026-09-20**：该 AI 提交 **12 个坑 + 4 条脚手架建议**的实测反馈。用户转入本工程，由核对会话逐条对照 SDK 源码、作者面文档树、脚手架模板、dev 宿主实现与 E6 清单，得出四分类结论（见 §〇b 总表）。
3. **2026-09-20**：用户拍板立案（原话见上），本批成立。

**为什么值得立案（三层价值，不是「客人提意见我们礼貌回应」）**：

- **官方仓自己也在同一条线上**。核对会话对 18 仓做了 keydown 摸底：**官方仓自己命中 3 处 `window.addEventListener("keydown")`**（`serial-monitor` SearchBar 两处、`settings` 快捷键录制器一处）——这正是作者面文档 [05-ui-conventions.md §4.2](../../../03-plugin-authoring/05-ui-conventions.md) 点名的反模式。第三方作者踩的坑，官方仓一样在踩 ⇒ 这些不是「第三方要求」，是**工程自己的欠账**被人用一次真实制造过程照了出来。
- **「只读两篇文档就动手」的作者行为模式首次有了实测样本**。四条「坑」其实是工程早已写明的规约或现成 token，只是不在他的阅读动线上（详见总表「已有」行）⇒ 本批的文档面改的是**动线与矩阵**，不是补写大段文档。
- **若干修复是一行级高性价比**（css-hardcode 提示语），拖着不修则每个游戏类作者都会重演「删光阴影」。
