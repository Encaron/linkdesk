# 插件视图样式隔离——四条隔离路线皆不采用

> **本记录回答一个问题**：插件视图与宿主是否应当引入**渲染隔离**（`@layer` / Shadow DOM / CSS Modules / 动态注入）？
> **答案 = 否**（`@layer` 单独裁为「不做」，见 §决策 4）。**这是折中，不是「不需要」。**
> 四条轴的设计与实测见 [样式命名空间归一化专项](../../02-Electron架构/E6_插件生态与发布/01-插件独立构建/样式命名空间归一化/00-整理档案.md)；残余边界权威清单见 [22 号档 §六](../../02-Electron架构/E6_插件生态与发布/01-插件独立构建/样式命名空间归一化/22-收口总方案-跨方样式污染九件套.md)（**只互指、不复制**）。

- **日期**：2026-09-16
- **状态**：rejected
- **背景**：池文档里**宿主 CSS ＋ 共享组件 CSS ＋ 所有已加载插件的 CSS 同处一张扁平全局表**（实机读数 **27 张样式表**）。类名、`@keyframes` 名、自定义属性名、顶层元素选择器在此表里各是一个全局标识符 ⇒ 一方「定义」、他方「渲染」，样式就落到同一个元素上，**不报错、只是长得不对**（真案 `.badge`：主题卡片徽标文字被自己的背景吞掉）。本仓隔离手段用量实测 **全为 0**：`@layer` 0 · `attachShadow` 0 · `*.module.css` 0 · 插件视图 iframe/webview 0（复跑命令见下）。收口走的是另一条路：**四条标识符轴靠约定 ＋ 静态门禁 ＋ 运行时探针三层覆盖**。本记录把那句话从「某处档案提过」升级为**可被仓库外的人读到的决策**，并写死**什么情况下重新评估**。

## 决策

1. **不做渲染隔离**——`@layer` / Shadow DOM / CSS Modules / 动态注入**四路皆不采用**。改用**「命名空间约定（四条轴）＋ 静态门禁 ＋ 运行时全表断言探针」三层替代**（实测读数见「三层替代的机械底座」）。

2. **`@layer` 单独裁决 = (a) 不做**（三选一里的 (a)）。⚠️ **别把「`@layer` 能解决」当结论**——**它只解决「谁赢（优先级）」，不解决「谁命中（选择器匹配）」**。见下方最小实验。
   - 它另有一处价值：把「宿主 > 插件」的次序**显式化**（今天靠源码顺序，隐含且脆弱）。但代价是**全库级联变更**，视觉回归面 ＝ 10 主题 × 18 插件 × 全部表面，**风险等级与本系列其余各件不在同一档**。
   - ⇒ 那点价值**进触发条件**（T3），不在此刻付代价换。

3. **第三方插件作者必须遵守命名空间与作用域规则**——`ldk-` 归宿主与共享组件、`<pluginId>-` 归插件（含 `@keyframes`）、token 定义作用域受结构性约束、顶层无锚选择器受限。作者面正文见 [05-插件UI写法规约 §12](../../03-插件制造/05-插件UI写法规约.md)。**跨方 scoped 调优仍是合法特性**（门禁管形态、不管意图）。

4. **本决策不改变任何用户可见行为**，也不改变已发布插件的运行方式。

## 三条路线的逐条评估

> 每条给 **能解决什么 / 不能解决什么 / 代价 / 适配性** 四栏。⛔ 不许写成「都挺好但代价大」——**每条都要说清它对本仓的哪一条约束不成立**。

### 路线 1 · `@layer`（级联层）—— **不采用**

| 栏 | 内容 |
|:--|:--|
| **能解决** | 「**谁赢**」——用层序把「宿主 > 插件」的级联次序从「源码顺序」这个隐含变量里拿出来，变成显式声明且稳定。 |
| **不能解决** 🔴 | 「**谁命中**」——**这是本决策的核心**。插件的 `.badge` 规则**照样匹配**宿主元素，只是丢掉级联。一条 `button { border: none }` 也照样命中宿主与其他插件的按钮（**连名字都不需要相同**）。⇒ **它不能替代命名空间**，只能叠在命名空间之上做次序保障。 |
| **代价** | **全库级联变更**：引入层序会改变**所有**现有样式表的胜负判定（今天赢的明天可能输）。回归面 = 10 主题 × 18 插件 × 全部表面 ⇒ **需要自己的实测/回归/发版链**，风险等级与本系列其余各件（纯标识符改名、机械证明零视觉变化）**不在同一档**。 |
| **适配性** | ⚠️ 与「跨方 scoped 调优是合法特性」**直接冲突**：插件按设计可以覆盖共享组件外观，而层序会把这类覆盖一律压到宿主之下——**要保留这个特性就得给插件层开豁免口**，等于把今天的隐患换成一套新的层序约定。 |

**🔴 最小实验（可复跑 · 本决策的实证依据）**

装置：一个元素上挂 `.badge`，两方各写一条同名规则；分两部分——**第一部分查「谁赢」，第二部分查「谁命中」**。

```bash
# 装置与运行器（住 scratch/，不进仓；重写照下面注释即可）
node scratch/rt-129/run-edge.cjs      # 用 Edge（Chromium 引擎）headless 跑，读回 computed 值
```

**第一部分：`@layer` 确实解决「谁赢」**（同一份源码顺序，只差「有没有层」）

| 组 | 装置 | 实测 |
|:--|:--|:--|
| P1 | 无层 · 宿主先写 / 插件后写 | `rgb(255,0,0)` ⇒ **插件赢**（谁后写谁赢） |
| P2 | 有层 `@layer host2, plugin2` · **源码顺序故意倒成** 插件先写 / 宿主后写 | `rgb(255,0,0)` ⇒ **插件赢** |
| P3 | 无层 · **与 P2 完全相同的源码顺序**（对照） | `rgb(0,128,0)` ⇒ **宿主赢** |
| **结论** | P2 与 P3 源码顺序相同、只差有没有层 ⇒ **结果从「宿主赢」翻成「插件赢」** ⇒ **层序压过了源码顺序** ✅ |

**第二部分：`@layer` 不解决「谁命中」**（🔴 本决策的核心读数）

| 组 | 装置 | 实测 |
|:--|:--|:--|
| Y1 | 有层。一个**只属于宿主**的元素（不在任何插件子树里）挂 `.badge`；插件层写 `outline: 3px solid red` | 该元素 `outline` = **`3px rgb(255,0,0)`** ⇒ 🔴 **插件规则仍然命中宿主元素**；它的 `background` 仍是宿主绿 ⇒ **只是输掉级联** |
| Y2 | 有层。插件层写整元素选择器 `button { border: … }`（**连名字都不同**） | 宿主 `button` 的边框 = **`4px rgb(255,0,0)`** ⇒ 🔴 **照样命中** |
| **结论** | 层只改「赢家」，**不改「命中集合」** | ⇒ `@layer` **不能替代命名空间**；本仓要治的是命中，故它解决不了主要矛盾 |

> 🔑 **一句话**：`@layer` 让插件「输得更体面」，**没有让插件「打不到」宿主**。

### 路线 2 · Shadow DOM—— **不采用**

| 栏 | 内容 |
|:--|:--|
| **能解决** | ✅ **真隔离**——**唯一能从构造上消灭这一类问题**的手段（样式不再跨 root 命中）。这一点本记录**如实承认**：如果从第一天就这么设计，本系列的四条轴都不需要存在。 |
| **不能解决** | 不解决**宿主自身与共享组件的样式需要到达插件元素**这一需求——`ldk-` 共享组件是**宿主提供、插件消费**的，得靠 `adoptedStyleSheets` / `<link>` 逐 root 注入或 `::part()` 显式开口，**等于把今天的「全局免费」换成「逐 root 显式接线」**。 |
| **代价** 🔴 | **要做就得改渲染模型**，且**本仓的实现形状让这件事从"加一层"变成"重做一条链"**：<br>· **插件 CSS 进不来**——今天 CSS 由 `src/pool/shared/plugin-component/bundleCss.ts` 以**文档级 `<link rel=stylesheet>`** 注入池文档（一插件一份、引用计数、URL 解析相对 `url()` 以保字体/图片）。**`<link>` 是 document 级的，按构造进不了 shadow root** ⇒ 必须重做注入机制（`adoptedStyleSheets` 或逐 root `<link>`），且每个 shadow root 各带一份 ⇒ **样式表份数从「一插件一份」变成「一插件 × 每 root 一份」**。<br>· **主题 token 要穿透**——`ThemeEngine/tokens.ts` 写 `documentElement.style.setProperty`（97 个契约 token）＋ `preload-pool/events.ts` 的 `theme:changed`；CSS 自定义属性**能**穿透 shadow 边界，但 `[data-theme="light"]` 这类**属性选择器作用在宿主文档根上**，需要额外的 root 内属性同步。<br>· **codicon 要重注入**——`@vscode/codicons` 是 651 个类名的**外部契约**（60+ 图标靠它），每个 root 都得有。<br>· 连带：事件冒泡/委托、布局量测、a11y、DevTools 体验，以及**全部 18 仓 ＋ 所有第三方**的适配。 |
| **适配性** | ⇒ **量级远超本系列全部件之和**——它不是「加一个机制」，是**换渲染模型 ＋ 重做样式分发链 ＋ 重验 10 主题 × 18 插件**。**收益（构造上不可能）确实最高，但今天付不起**，故进触发条件（T1/T2）。 |

### 路线 3 · CSS Modules—— **不采用**

| 栏 | 内容 |
|:--|:--|
| **能解决** | 构建期把**自家源码**的类名改哈希 ⇒ 宿主与共享组件自己的源码不再产出可撞的名字。 |
| **不能解决** 🔴 | **管不到第三方插件仓**——插件各自独立构建、各自 bundle（L7 之后**源码在仓外**，一插件一仓）。而这一类问题的**另一半恰恰在插件侧**（插件写裸名打到宿主元素）。⇒ **只解决一半，且是已经解决的那一半**。 |
| **代价** | 源码里 `className="badge"` 全部改 `styles.badge` 形态 ⇒ 大范围改写 ＋ 每个用到的文件都要 import；**且与「插件按设计可 scoped 调优共享组件」冲突**（哈希名无法被外部选择器命中 ⇒ 有意消费也断）。 |
| **适配性** | ⛔ **射程根本对不上**：它作用于「本仓源码」，而本仓的问题面是「**多方在同一个运行时文档里相遇**」。构建期改名**改不了运行时相遇这件事**。 |

### 路线 4 · 动态注入隔离（每插件一张 `<style>` ＋ 运行时重写/scope 包裹）—— **不采用**

| 栏 | 内容 |
|:--|:--|
| **能解决** | 理论上能把每个插件的 CSS 选择器**运行时加前缀/包裹作用域**，做到「插件规则只在自己的子树里命中」。 |
| **不能解决** 🔴 | · **不解决 `--x` 与元素选择器**：重写只对能解析到的选择器生效，`@keyframes` 名、`@property`、内联 `style` 属性、`@import` 进来的第三方 CSS（含 `@vscode/codicons`）都在射程之外或被改写后仍可能命中。<br>· **不解决绕过**：动态拼出的名字（`theme-${variant}`）、`element.style` 直写、`shadowRoot`/`iframe` 内的样式，重写器看不见。 |
| **代价** | 运行时要**解析并重写别人构建好的 CSS**（含 minify 后的产物）⇒ 脆弱（选择器语法边界多）、有启动与内存成本、**且每次插件加载都要跑一遍**；一旦重写器有偏差 = **静默改错样式**，比不做隔离更危险。 |
| **适配性** | ⛔ 与「**量尺必须能机械判定**」的项目原则相悖：它把「样式正确性」寄托在一个运行时改写器上，**而这个改写器本身没有可靠的验收方式**（改写前后视觉等价无法机械证明）。本仓已有更便宜的等价物——**静态门禁 ＋ 运行时探针**（见下）。 |

## 触发条件（**什么情况下重新评估**——重新立项的门槛）

> 🔴 **这是本记录最有价值的一段。** 每条都写成**可判定**的（能观测的量 ＋ 判定方式 ＋ 谁在什么时候复核）。⛔ 「等需要时再说」不算。
> **复核人 = 本项目的维护者 ＋ 他的 AI**（下一轮进场时读本档）；**复核时机 = 每次「新插件上架」或「新 SDK 轮」立项时顺手核一遍本表**；任一条**成立 ⇒ 立刻为隔离另立一格**，不塞进别的轮次。

| # | 触发条件 | 判定方式（可观测） | 谁来复核 · 什么时候 |
|:--:|:--|:--|:--|
| **T1** | 🔴 **出现第一次「门禁绿却出事故」**——不是门禁报红，而是**四条轴的判据全绿、探针也全绿，仍然发生了用户可见的跨方样式错位** | 立案时须**指认出是哪条轴漏了**（用探针 dump 证明碰撞存在而门禁没报）⇒ 说明有轴未被覆盖。**这是唯一能直接推翻本决策的信号** | 维护者；**事故发生时立刻**（不等轮次） |

| **T4** | **第三方插件占比过半**：官方目录里**非官方作者**的插件数 > 官方插件数 | `npm run catalog:official` 条目按 author 分类计数。**理由**：官方 18 仓由同一套 CI ＋ 脚手架 ＋ 同一批维护者产出，**约定能靠工具链兜住**；第三方**用谁的脚手架、跑不跑 `npm run verify` 都不确定** ⇒ 约定对他们约束力弱得多 | 维护者；**每次目录收录后核** |
| **T5** | **插件间冲突的用户报告成为常态**：同一**季度**内收到 ≥ 3 次「装上 A 插件后 B 插件的样式坏了」类报告（含用户实机立案） | 报告计数（issue / 会话立案都算，须能指认到具体插件对）。**判定口径**：3 次/季度 = 「不是偶发个案」 | 维护者；**每季度末核一次** |

> ⚠️ **「不做」的措辞纪律**（本决策的**全部价值所在**）：本记录说的是「**今天不做的折中**」，**不是「不需要隔离」**。四条轴的规则**必须继续被遵守**——触发条件成立只是「该重新评估了」，**不解除任何一条现有纪律**。
