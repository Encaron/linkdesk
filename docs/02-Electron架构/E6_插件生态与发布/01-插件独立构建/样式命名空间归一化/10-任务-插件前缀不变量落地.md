## 一、无论选哪条路线都适用的硬要求（**纪律，不是建议**）

1. **单一真相源不许变成两份**：新规则若需要一份清单/前缀表，它必须**长在 SDK 包里、随包下发**（照 `reserved-class-names.json` 的先例），**不许**在壳仓与 SDK 各写一份。⚠️ **棘轮基线是例外且是刻意的**——它按**仓**存在（`<插件仓>/css-namespace-baseline.json`），因为「本仓的存量」只有本仓知道；它**不是**公共面清单，不得进 SDK 包。
2. **判据必须能从机器事实推出**：能机械校验的才写进门禁（「裸定义类名的首段 === `pluginId`」）；靠人看的写进作者面文档。
3. **负控要真跑红**（照 `#109e` 的做法）：往一只真插件仓塞一条违规 ⇒ 该仓 `npm run verify` **当场红**，报点含**文件 ＋ 行 ＋ 类名**；还原即绿（记 sha256 → 改 → 跑 → 还原 → 复核字节相同）。**自测通过不算判据。**
4. **fail-closed，且已实测确认**：插件仓 `scripts/ci-verify.mjs` 的 ① 段 = 「**除报表档外的全部腿**」判红（`ADVISORY_LEGS` 只豁免 `check-font-scale` / `check-spacing-grid`）⇒ 新增/收紧的腿**自动进严格档**。落地时**实测确认**新判据在 `strictLegs` 里（打印 `strictLegs.map(l => l.label)` 对一眼），**别只读代码**。
5. 🔴 **`plugin.json` 是 JSONC**（可注释、可尾逗号）：任何读 manifest 的新代码**必须用 JSONC 解析器**（SDK 已依赖 `jsonc-parser`；`validate.ts:172` 是现成先例）。用 `JSON.parse` 会在脚手架的注释上直接抛。**另**：schema 顶层 `additionalProperties: true` ⇒ **别指望 ajv 校验替你拦住字段**，腿必须自己读。
6. 🔴 **18 仓的 SDK 依赖是 `^0.1.19`**（caret 上界 `<0.2.0`）⇒ 新 PATCH **会被 18 仓自动吃到**。**含义**：腿一收紧，各仓下次 `npm install` 后 CI **当场红**。⇒ **基线的生成与提交必须排在新腿可被拉到的同一批里**（否则等于让 5 仓红着上班，见 §四 顺序）。

## 三、推荐路线的作业面（(d)「id 派生 ＋ 存量棘轮」）

**规则（落地后作者面写这一句）**：
> **插件 CSS 里给自有元素起的类名，必须以你的 `pluginId` 加一个连字符开头**（例如 `settings-*`、`editor-*`）；本仓基线里已有的旧名字暂时豁免，**但不许再加新的**。

**棘轮的三条机械属性**（照壳仓 `check-css-namespace` 判据⑤ `registry-stale` 的**同款先例**）：
1. 基线里的名字**必须真实存在**于本仓 CSS ⇒ 名字消失而基线没摘 ⇒ **红**（表烂即红）；
2. **不许加行**（新名字要进基线 ⇒ 红）——这是「只减不增」的机械形态；
3. 基线**按仓**存在（`css-namespace-baseline.json`），**不进 SDK 包**、不是公共面。
