# 02-可逆注册设计——一切注册返回 disposer，卸载逆序回滚

> E5.8#8（2026-08-19）。Phase 2 细节设计。**写完用户过目拍板再动工**（拍板点 §9 汇总）。
> 范围：`#7 注册点矩阵.md` 全量注册面。目标：插件卸载/禁用 = 注册的**逆序**回滚，重装契约（"可卸载 ⇒ 可重装"）的机械保障。
> 对标：dsh `ctx.effect`（execute 立即跑，disposer 逆序跑）+ Fiber 状态机。抄纪律不抄形态。

## 0. 现状盘点（#7 矩阵实锤，本设计的出发点）

**两形态注册表并存**——这是本设计要统一的核心事实：

| 形态 | 代表 | 清理机制 | 问题 |
|:--|:--|:--|:--|
| **类注册表**（extends RegistryBase） | Icon / Language / ClipboardProvider / ViewContainer | `markPlugin` + `PluginLifecycle.onWillUninstall` 自动 `unregisterAll` | 仅 4 个；粒度 = per-plugin 全清，无单个条目 disposer |

**旧 unregister\* 外部消费方实锤（grep 全仓）**：仅 lifecycle.ts 消费端 2b + 各自测试——**插件/linkdesk.\* API 零消费**。⇒ 删旧 API 无外部双轨成本，可一步到位。

**已返 disposer 样板 7 处**（零成本、可作 v2 对照）：`ConfigurationApplier.registerOnApply` / `QuickPickService.onChange` / `Emitter.event` / `events.on`（preload 双侧）/ `useIpcEvent` ×2 / StatusBar item。

## 1. RegistryBase v2 路线——统一追踪器，两形态共用

### 1.1 核心决策：v2 不是"升级类"，是**抽模块级追踪器**

RegistryBase v1 的 `markPlugin/unregisterAll` 只有**类**形态能用。但 11 核心注册表中 7 个是**模块函数式**——v2 若只改 RegistryBase，函数式注册表够不着。

**设计**：新建模块级 `registrationTracker.ts`（单例），类注册表与函数注册表**共用同一套逆序回滚**。

```ts
// src/core/registry/registrationTracker.ts（新建）
const _layers = new Map<string, Array<() => void>>();  // pluginId → LIFO disposer 栈

// 模块加载时订阅一次——任何有登记的插件卸载/禁用自动逆序回滚
PluginLifecycle.onWillUninstall.event(({ pluginId }) => rollback(pluginId));

/** 登记一个 disposer——返回可单独调用的幂等 disposer */
export function trackRegistration(pluginId: string, disposer: () => void): () => void;

/** 逆序回滚一个插件的全部登记——单 disposer 抛错不中断后续，错误入诊断面（#9） */
export function rollback(pluginId: string): void;

export function hasRegistrations(pluginId: string): boolean;
```

**RegistryBase v2**（类形态）变薄——归并 markPlugin 机制：

```ts
export abstract class RegistryBase {
  protected track<T>(pluginId: string, disposer: () => void): () => void {
    return trackRegistration(pluginId, disposer);
  }
  // markPlugin / hasPlugin / unregisterAll 三方法归并：
  //   markPlugin(pluginId)        → track(pluginId, noop) 语义废弃，由 disposer 登记替代
  //   hasPlugin(pluginId)         → hasRegistrations(pluginId)
  //   unregisterAll(pluginId)     → rollback(pluginId)（幂等）
}
```

**每个 register() 的 disposer 语义**：注册时把条目入表后，返回"**删这一条**"的 disposer——不再是 per-plugin 全清。示例（CommandRegistry）：

```ts
export function registerCommand(pluginId: string, command: Command): () => void {
  if (_commands.has(command.id)) {
    // 重注册分支：只更新 handler/title，未新增条目 → 返 no-op disposer
    // （原有条目的 disposer 仍是第一个注册时登记的——保证卸载时能删掉）
    existing.handler = command.handler;
    existing.title = command.title;
    existing.placeholder = command.placeholder;
    return () => {};
  }
  _commands.set(command.id, command);
  const pluginSet = (_pluginCommands.get(pluginId) ?? new Set());
  pluginSet.add(command.id);
  _pluginCommands.set(pluginId, pluginSet);
  // 核心：登记 disposer——卸这一条
  return trackRegistration(pluginId, () => {
    _commands.delete(command.id);
    _pluginCommands.get(pluginId)?.delete(command.id);
  });
}
```

### 1.2 卸载时自动回滚——消费方零感知

disposer 由 `register()` **内部** `trackRegistration`——所以 **loader/插件消费方不需要保存 disposer**：卸载触发 `PluginLifecycle.onWillUninstall` → tracker 逆序回滚，机械保证。

消费方适配只剩三种情况：
1. **需要单个条目注销**（非卸载场景）——保留 register 返回的 disposer（如池侧运行时命令 unregister）；
2. **需要主动全清**（测试）——`rollback(pluginId)` 或保留 `clearX()` 测试专用；
3. **其他**——调用面不变（register 返回 void→`() => void`，TS 忽略返回值合法）。

## 3. loader 生命周期状态机（#11 设计级定案）

### 3.1 状态图

```
 PENDING ──loadPluginRuntime──▶ LOADING ──runtime 求值 + 注册全量生效──▶ ACTIVE
    ▲                              │                                        │
    │                              │ 加载抛错                                │ 卸载/禁用
    │                              ▼                                        ▼
    └────────────── FAILED ◀──记录 failureReason ──                 UNLOADING
    （重试回 PENDING 或保持 FAILED 供诊断）                          │ rollback 完成
                                                                   ▼
                                                                 DISPOSED
```

### 3.2 状态 ⊥ 现有三方（#11 审视立案映射）

| 概念 | 归属 | 消费方 | 说明 |
|:--|:--|:--|:--|
| **LoadState**（本状态机） | loader 新增 | 诊断面 | "插件为什么没激活" |
| **CachedPluginMeta.status** | loader 元数据缓存 | marketplace（installed/disabled/uninstalled） | 安装态，**不进**本状态机——disabled 插件停在 PENDING |
| **PluginStateService** | 插件私有存储 | 插件自身 | 非状态，无映射 |

### 3.3 诊断面

`getLoadDiagnostics(pluginId)` → `{ loadState, failureReason?, registeredEffects: number }`。
挂载点：#11 执行时定（候选：dev 面板 + marketplace 插件详情）。

## 4. 主进程侧注册面机制定案——**保持全清全重扫（推荐）**

`electron/ipc/registry-handlers.ts` 三表（LangDef/Protocol/FileAssociation）数据源 = plugin-manifest-loader 预加载 → `plugins:rescanManifests` **全清全重扫**（声明式清单重建，天然无残留）。

**边界规则（成文）**：
> **命令式运行时注册（插件代码逐条注册）→ 可逆注册 disposer 逆序回滚。**
> **声明式 manifest 派生表（loader 读 plugin.json 全量重建）→ 全量重建。**
> 两者各自天然无残留——disposer 化管不住 manifest 表（无"逐条注册"动作），全量重建也不需要 disposer（无增量状态）。**不给声明式重建装 disposer 基建。**

理由：#10 的 disposer 化目标 = 增量注册的局部失败可回滚；manifest 表一次重建无增量无失败窗口。主进程三表跟随 disposer 化 = 给不存在的问题加复杂度。

## 5. ContextKeyService.registerExternalGetter 归置——返 disposer，不跟踪 plugin

`registerExternalGetter` 是**全局**值源 hook（壳服务生命周期 = 应用生命周期，非插件作用域）。

- 返回 `() => void`（删这个 getter）——保持"**一切注册返回 disposer**"不变量统一；
- **不 `trackRegistration`**——无插件作用域，卸载回滚不适用；
- 归置：属于"非插件作用域的全局注册"，不列入 #10 的 13 Registry 逐项，单独一条小适配。

## 8. 风险与边界

| 风险 | 缓解 |
|:--|:--|
| CommandRegistry 重注册分支（ID 已存在）不新增条目——若误登记 disposer 会把别的插件命令删掉 | 重注册分支返 no-op disposer；单测钉"重注册 → dispose 只删自身条目，不动他人" |
| 双回滚（disposer + 旧 unregister\* 并存期） | 过渡窗口 = #10→#12 的 commit 序列，一次性；disposer 幂等（done flag）兜底 |
| `unregisterPoolCommands`（池运行时命令）是独立生命周期（视图 unmount 非插件卸载） | 保留；#10 改挂 register 返回的 disposer，池侧 unregister 改收 disposer 或逐条 |
| 回滚中断容错 | #9 单测：单 disposer 抛错不中断后续 + 错误入诊断面 |
