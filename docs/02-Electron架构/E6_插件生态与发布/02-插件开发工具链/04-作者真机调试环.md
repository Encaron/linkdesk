## 一、Context——为什么要有真机环

**动机源（Encaron，2026-09-07 讨论）：**
1. 万物皆可插件 + 目标 = 插件作者能制作**任意插件**（文件树 / Eclipse、Monaco 类编辑器 / CAN-bus / 示波器 / 愤怒的小鸟游戏），并享受**便利 ≥ 内部开发便利**——内部改 serial-monitor 只需重启 `npm run electron:dev` 即可验证。
2. WPF serial-monitor v2 创伤：只靠每次 AI 生成可执行 exe 双击——慢、后期 150MB、git 膨胀 15GB。**绝不给 LinkDesk 插件作者封死快捷调试通路**——作者不应被逼每次完整封包才能看效果。
3. E4 体量级 bug（见下）证明：**没有便利的真实调试，不可能顺利**；作者端还想要像内部一样的 **CDP/AI 全自动调试**（"pcd"）。
4. 纯浏览器 mock dev 对「需要真 IPC 的插件类」**不够**——这类插件必须真有壳 + 真 IPC 才能显形其 bug。

**为什么浏览器 mock 替代不了真机（E4 bug 家族实证，memory e4-complete / e5.5-7-editor-multi-webview-bugs / monaco-addcommand-global-trap）：**
- Monaco R17 = 5 失败 → 1 正确路径（standalone `monaco.editor.create()`，非 monaco-vscode-api）；worker 初始化时序 / IPC channel 碰撞 / singleton 跨 JS heap 隔离 / `addCommand` 全局动态键绑定陷阱（→ `editor.addAction`）——**只在真壳 + 真 IPC 下复现**。
- 文件树 sticky（E4V#57 弃）、monaco 字体/不启动——无便利真机调试不可能趟平。
- 结论：**真机环是必需，不是可选**（第三方作者尤其——没有内部壳源码/构建）。

## 六、A 的实现要点（执行期参考，非本轮代码）

1. **watch** 作者源码（`dev --real` 复用 vite dev server 之外的第二态，或独立 chokidar）→ 变更触发**隔离单插件 build**（复用 #25/#15 已建：vite-config `defineLinkdeskPluginConfig` → index.bundle.js + css/i18n 资源）。
2. **直写** `{userData}/plugins/<id>`（平台 %APPDATA%/linkdesk；`LINKDESK_USER_PLUGINS_DIR` 可覆盖）——产物 = 完整物化目录（plugin.json + bundle + 资源 + i18n），不经 `plugins:extract`（存在即拒）、不碰 #15n boot 门禁。
3. **reload**：作者以 `--remote-debugging-port=9222` 启动 LinkDesk（Chromium 原生 switch）→ SDK 经 CDP 刷新池窗口（目标 "LinkDesk Pool"）。**刷新 = `Network.enable` + `Network.clearBrowserCache` + `Page.reload` 顺序发**（2026-09-07 实证：单发 `Page.reload` 被 Chromium 对 `linkdesk://` 的启发式缓存遮蔽——见 §二 事实#1；清缓存后 reload 重 import 落到磁盘逐请求 `readFileSync`）。CDP/AI 调试 = 同一 9222 入口。
4. **sourcemap**（执行期细化）：build 产物带 sourcemap 供 CDP 源级断点，非阻塞。

**风险与边界：** 直写覆盖不备份原插件（真机环针对作者自研 dev 插件，非用户市场已装插件——文档要写明作用域）；多插件工程并行 dev 需各自独立（一个 `dev --real` = 一个 dev 插件目录）；CSS 热更走整窗口 reload（秒级，非亚秒 HMR——那是 B 的卖点，B 门控后定）。

- **零手动封包**——watcher 自动触发隔离单插件 build（~1s）
- **零重装**——直写 dist，非 zip 重物化
- **插件改动不碰主进程**——renderer 侧 reload，不重启 electron

### 8.1 坑 1——源码树宿主发旧代码（Vite 模块图缓存）

**现象（作者视角，最迷惑的形态）：** `dev --real` 下改码 → **重启后第一下生效、之后每次改都不动、再重启又好**。三条反证实验全部指向"中间那层在发存货"：强制清缓存+重载仍旧、换 URL（加时间戳）仍旧、软件内部直接取那个 js 文件拿到的是**新**内容。

**机制（本仓代码复核）：**

| 环节 | 事实 | 证据 |
|:--|:--|:--|
| ① 直写是「先删再建」 | `rmSync(targetDir, { recursive: true, force: true })` → `copyTreeOverwrite(...)` ——**这一删把 Vite 对该目录的 watch 打断了线** | `packages/plugin-sdk/src/dev-real.ts:240` |
| ② 通知链 | 更新完发 CDP：`Network.enable` + `Network.clearBrowserCache` + `Page.reload(ignoreCache)`，目标窗口 "LinkDesk Pool" | `dev-real.ts:122-155`、`:184` 头注 |
| ③ 缓存有两层，通知只接了一层 | 清的是**浏览器缓存**（当年为治 `linkdesk://` 无 `Cache-Control` 的陈旧缓存——本文 §二 事实#1）；**Vite 模块图缓存**没清 | §二 事实#1 + §六.3 |
| ④ 宿主决定吃哪层 | 安装版走 `linkdesk://` → 逐请求 `readFileSync` = **每次现读磁盘** ✅；源码树 `electron:dev` 走 Vite `/@fs/` → 命内存副本 ❌ | `vite.config.ts:63-67`（`fs.allow` 注释：dev 经 `/@fs/` 服务、prod 走 `linkdesk://`） |

**🔴 反直觉结论（要写进作者心智模型）：** **安装版宿主反而比源码树宿主新鲜** —— 真机环的质量 = 安装版的质量。别把作者往 `electron:dev` 上引。

**🔬 未定项 + 区分实验（动手第一步）：** 本仓 E5.8#116（2026-08-27）已删掉 `plugins/` 的 watch 忽略（当时实证：忽略 → 模块图缓存永不失效），所以"Vite 无条件发旧"不成立与否**必须实验区分**：**不删目录、只覆盖一个已存在文件**，看是否立即生效。

- **生效** ⇒ 病根 = `rmSync` 打断 watcher ⇒ 修法可很便宜（改成只覆盖不删，`copyTreeOverwrite` 现成）。
- **仍 stale** ⇒ 必须让 Vite 端失效模块图（或源码宿主改协议），成本上一台阶 ⇒ 转 A/B/C 里的 B/C。

**三选一修法：**

| 路 | 做法 | 成本 | 定位 |
|:--:|:--|:--|:--|
| **A·真修** | SDK 侧不再 `rmSync`（只覆盖）+ 必要时通知 Vite 失效该模块；或源码宿主改走 `linkdesk://` | 中（SDK 轴，可能半截壳侧） | 彻底，但先看实验结论 |
| **B·止血** ⭐ | `dev-real` 检测到 CDP 目标页面来自 Vite（1420 / `/@fs/`）→ 打印醒目警告「当前宿主是源码树 dev，真机环会发旧代码——请改用安装版 / win-unpacked」 | 十几行 | **性价比最高**；把"静默骗人"降级为"明确边界" |
| **C·文档** | §四 表上方已补缺格说明 + 作者文档写明「源码树宿主不支持真机环」 | 一行 | 必做（本轮已落） |

### 8.2 坑 2——`dev --real` 无互斥锁

**现象：** 开第二个 `dev --real`（忘了自己开过——极常见）→ 两实例抢同一 `dist/` → `✗ EPERM, Permission denied: dist\<id>.linkdesk-plugin`；**报错后旧产物原样不动** ⇒ 作者看到的现象**仍是"改了没反应"**，与坑 1 症状完全重合（现场两个 AI 都误判过两轮）。

**根因：** `dev-real.ts` 无 pid/锁文件（2026-09-13 grep `lock`/`pid` 确认，文件内只有 CDP 端口相关逻辑，无互斥）。

### 9.3 两条路线比较（#28.7a 正题）

#### 9.3.1 先说最硬的一条机制结论（它把两条路线合并成一堵墙）

**源码级 HMR 的前置条件不是「谁唤壳」，而是「壳必须是 dev 态构建」。**
依据：源级 URL 由**编译期** `import.meta.env.DEV` 选择（9.2 第 4 条）；生产壳里 Vite dev server 根本不存在、`DEV` 在打包时被烘成 `false` ⇒ **装好的 LinkDesk 无论加什么开关都不可能源级 HMR**。

⇒ **两条路线的真实分野 = 「壳从哪来」，不是「谁点启动」：**
- 路线 ①（SDK 唤 dev 态壳）：SDK 手上没有壳 ⇒ 要么作者 clone 壳仓（+ `npm i` + tsc/build，重环境），要么 **SDK 带一份 dev 态壳产物**（第二分发件）。
- 路线 ②（复用 #28 壳侧 dev 推广第三方）：`dev-plugin-mode` 的 `!app.isPackaged` 守卫 + `fs.allow` 白名单在同一层挡住 —— **推广到第三方 = 同样要回答"壳从哪来"**。

#### 9.3.2 路线 ② 有一个被忽略的低档形态——机制本体已在，只差三处闸

壳侧 dev **已经支持源码轨**（9.2 第 5 条：无 `index.bundle.js` 即回退 `manifest.entry`）。因此把门控目录指向**作者源码目录**（而非物化 dist）时，池窗会自动 `import('/@fs/<作者目录>/src/index.tsx')` → **壳自己的 Vite 即时编译 + HMR = 真壳内亚秒循环**，**不需要新写加载器**。缺的只有三处闸：

1. `fs.allow` 放行「当次 dev 的那个插件目录」（不是整个作者工程根——见 9.3.4 ③）
2. react 系裸 import 回指范围（否则双 React ⇒ hooks 崩，E4 bug 家族同源）
3. `dev-plugin.mjs` 加「源码模式」分支（现在恒先 build，且无产物直接报错）

**覆盖谁：持壳仓者**（维护者 + 18 只官方插件作者）。**成本：2-3 天**（壳侧 3 处 + 脚本一个分支 + 实测/负控）。**零新分发产物。**
⚠️ **一个 L7 之后才成立的新事实**：18 只官方插件源码已全部搬出壳仓（E6 第 7 层）⇒ 这些人**今天在壳仓里已经指不到自己的插件**（`fs.allow` 只白名单仓根 + userData），只能退回 A。即：**这条残账是 L7 造成的，且到今天无人承接**（`02-本地预览环境.md:145` 那句「残余：仓库外目标需 vite fs.allow 推广 + 外部化（#62f 承接点）」——而 **#62f 已于 2026-09-08 按「协议收单一 userData 根」口径收官，没含 fs.allow**）。

#### 9.3.4 安全面——「真壳里跑第三方源码意味着什么」（任务点名项）

**先定基线：第三方代码本来就在真壳里跑**（装插件 = 跑作者 bundle，这是产品前提）。⇒ **源码 vs 产物在权限面上同级，不构成新的越权。** 真正变化的只有三处：

① **路 (b) 会让装好的生产壳接受外部注入**：任何本地进程都能让用户的 LinkDesk 从任意目录加载代码，绕过安装台账与装卸语义 ⇒ **与 L6（安全加固 #48-52）正面冲突**。**建议否决 (b)**——`!app.isPackaged` 那道守卫是现在的正确形态，别为省一个产物把它拆了。
② **(a)/(c) 引入未签名、未审计的 dev 态壳**：它能挂用户真实 userData 跑 ⇒ 必须**默认隔离 profile**（`LINKDESK_DEV_USER_DATA_DIR` 已有先例，`dev-plugin.mjs:373-375`）+ 文档写明「dev 壳不承诺安全边界」。

#### 9.3.6 B 的第二重收益——不是只有「更快」（2026-09-15 用户问询后补）

原门控只把 B 的价值写成「**亚秒 HMR**」（速度）。复核 reload 的作用范围后，**还有一重收益被漏掉了：不会打断。**

| | A 今天（`dev --real`） | B（源级 HMR） |
|:--|:--|:--|
| reload 打在谁身上 | **pool 那个 WebContentsView 的整篇文档**——`cdpReloadPool` 找 title `"LinkDesk Pool"` 发 `Page.reload({ignoreCache:true})`（`packages/plugin-sdk/src/dev-real.ts:127-159`）；pool = 宿主窗内的 `WebContentsView`（`electron/windows/window-manager.ts:153-235`） | 不重载文档：Vite 模块热替换 = **组件级 patch** |
| 范围 | 🔴 **视觉上 = 整个可见工作台面重绘**（2026-09-15 订正——本行原写「不是全屏」，**错**）：池文档 = `PoolZoneShell` 一个根，里面装着 **TitleBar / IconBar / Sidebar / Main / Panel / RightSidebar / StatusBar** 全部 zone（`src/pool/PoolZoneShell.tsx:63-90` 逐个 import）⇒ title-bar 也是池的一格，**它跟着一起重建**。**不参与** reload 的只有**主窗口那份文档**（`index.html → src/main.tsx → App.tsx`）——壳侧布局/标签状态住在那里 | 只有被改模块及其边界内重算 |
| 壳侧状态 vs 池内状态 | **壳侧的活**：主窗口文档不重载 ⇒ 标签列表/布局由 `usePoolSync` 在池重新 ready 后**重新推下去**（`src/hooks/usePoolSync.ts:313-314` 遍历 ready 窗推 fullLayout）⇒ **不丢**。**池内的死**：池里所有插件视图（不只你改的那个）一起重挂载 ⇒ 视图内瞬态状态丢（滚动位置这类）。⚠️ **别读成「一定丢内容」**：编辑器脏内容有 Hot Exit / pluginState 这类落盘兜底，逐个插件是否扛得住池重载**本轮未逐条核查** | **两侧都保留**（react-refresh 状态保留是它的设计语义） |
| CSS 改动静默吗 | 否——**也走这条路**（本文 §六 原文自陈「CSS 热更走整窗口 reload（秒级，非亚秒 HMR——那是 B 的卖点）」）；且每次 reload 前还清了一遍浏览器缓存 | 是——patch `<style>`，不重载 |
| 肉眼会不会「闪」 | **整面重绘 ⇒ 有可见的空白期是可预期的**（作者现场体感即「整个屏幕闪一下」）；⚠️ 但**时长无实测读数**（池重建耗时决定观感），本轮不替读者断言 | 设计目标 = 不闪（同样待实测） |

**但 B 也不是「永远不重载」——三类改动仍会升级成整页 reload**（要写进预期，否则又是一个「静默骗人」）：① 改 `plugin.json`（发现层要重扫 manifest）；② 改**非组件模块**或导出形状变化（react-refresh 找不到可接受的刷新边界时，Vite 自行升级 full reload）；③ i18n 资源等非组件产物的改动。

**⚠️ 还有一条本项目**自己踩过**的 HMR 语义坑要给 B 记上**：HMR 只替换模块导出的函数，**不重跑已执行的模块启动副作用**——修「启动时捕获数据」那类 bug 后，HMR 会给出「新代码已激活、老数据还在」的**混合态**（memory `bug-atlas` B2：本仓 #133.5 实机验证时为此排查约 1 小时，根因 = `loadIconThemeContributionData` 在插件加载时把 glyphCss 捕获进 IconRegistry；结论 = 修完这类 bug **必须杀进程重启**，不能只 `location.reload()`）。⇒ B 买到的是「不打断」，代价是 **reload 语义变 HMR 语义**——两者对「启动副作用」的处理不同，作者文档必须写明这条边界（A 的整篇 reload 反而没有这个陷阱）。

**⚠️ 待实测（Tier 1 开工第一步，不是既成事实）：** Fast Refresh 要在「插件源码经**壳自己的** Vite 服务（`/@fs/<作者目录>`）+ react 经 `resolveUserDataBundles` 回指壳 node_modules = **单实例** + 池侧 `import(/* @vite-ignore */ url)` 动态边界（`PluginComponent.tsx:61`）」这个组合下真的接上才算数——尤其动态 import 边界上的 `import.meta.hot.accept` 自接受性。**本轮是设计轮，这一层没有读数。**

**⇒ 对作者日常的含义（一句话，防最容易被脑补错的那格）：B 不是「把安装版升级成热更」，而是「多开一条开发内环」。**

|:--|:--|:--|:--|

🔴 **所以「在装好的安装版里做局部热更」这个组合机制上不成立**（依据 9.3.1：源级 URL 由编译期 `import.meta.env.DEV` 选，装好的壳里 `DEV=false` 且没有 Vite dev server）。想在安装版里做热更只有三条路：① **甲-2** 另发一份 dev 态壳产物；② 自研——把「编译 + 热更协议」搬进壳里（esbuild 变换 + 自研 HMR 运行时），那正是本文 §三/§10.3 否决过的**「工具链变半个壳」原形**；③ 拆掉 `!app.isPackaged` 守卫让安装版接受注入（安全回归，**建议否决**，见 9.3.4 ①）。

### 9.5 呈现拍板——两个明确选项（#28.7b）

#### 选项甲：造（拆正式任务卡）

- **甲-1（推荐形态）= 档 1**：拆一张卡「**壳侧 dev 认仓外插件源码目录（真壳内亚秒循环 + 状态保留，持壳仓者）**」——判据与工作量见 9.4 档 1 行；落在「插件开发工具链」段（#28 系列旁）。**收益是双条**：亚秒 + 「改码不打断」（组件级 patch、状态保留、不重挂载——见 9.3.6）。
- **甲-2 = 档 2**：拆一张卡「**第三方 dev 实例（dev 态壳第二产物 + SDK 拉起）**」——判据与工作量见 9.4 档 2 行。**建议留到**出现真实外部作者、或维护者明确要"无壳仓也能跑"时才开（今天这个人群实测为 0，且 9.1 显示需求信号是推演的）。

- 无论甲-1 还是甲-2，**都建议同笔把 §八 两条补立案**——它们与 B 无关，是独立的实测痛点。

#### 选项乙：不造（档案记 conscious 否决，非 deferral）

写进档案的依据四条（拍板后照抄）：

1. **触发信号从未出现**（9.1）：门控写死的触发 =「秒级不够快的真实体感」，全库检索零命中；L4 走的是产物链合并代验，不是 dev 环长跑。

3. **收益面与成本面倒挂**：档 1 只够持壳仓者（而他们的替代路径 A 已是秒级）；档 2 的唯一增量人群（真第三方）**实测为 0**，代价却是第二条分发链 + 安全边界重划 + dev==prod 在壳轴破一次。
