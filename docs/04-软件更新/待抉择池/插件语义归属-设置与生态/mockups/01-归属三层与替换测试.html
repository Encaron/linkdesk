点下面的开关切「现状 / 归一后」，再点两边的「选择图片…」：看同一动作在「官方设置插件」和「最小第三方 UI」上是否一致。

Frame 1 · 一条能力拆三层：语义 / 动作 / 呈现语义归壳，动作归壳，插件只画

现状 语义被劈成两半

设置插件（可替换）知道字符串 "appearance"
▼ defaultPathKind
壳 dialog-handlers把令牌翻成 userData/appearance
▼
结果换掉设置插件 ⇒ 令牌没人给 ⇒ 起始目录丢

归一后 语义单源

设置插件（可替换）只调 appearance.pickImage({domain,target})
▼ 不带路径/域字符串
壳 hostAssets/appearance/defaults.ts起始目录、过滤器、入库
▼
结果换任何 UI ⇒ 同一命令 ⇒ 行为不变
判据（语义归属律）：一个行为的默认值/约束/路径/权限由能力所有者声明；UI 插件只做呈现与触发。验证：换掉该 UI 插件，行为还在不在？

Frame 3 · 四仓盘点（已完成 · 15 条）详细 file:line 见 01-盘点/01–04
仓条数主要形态最高危的一条
settings6背景目录令牌、settings.json 路径、app.* 键特判、缺 pickTargetV6：自拼宿主设置文件路径
file-tree3路径工具整套自写、跨属主读最近目录、字号/行高双写F2：跨命名空间读 app.recentFolders

判读：多数不是「插件写坏」，而是壳 API 没暴露（settings 去 getFilePath、marketplace 拼资产 URL、serial 没有保存框）⇒ 插件只能绕。 任务里对应补 6 项壳 API（A1–A6），再把插件改回调壳——这才是归一化，不是骂插件。
正例也在同一批仓里：file-tree 的打开方式/定位/终端已全部委托壳命令；marketplace 的安装/位置全走壳； serial 的端口枚举走壳。⇒「搬语义」不是空想，这些仓已经做对过一部分。
