## §一 现状读码

### 1.1 齿轮今天是一坨「三合一」——三个身份挤在一个位置上

用户看到的是「左下角一个齿轮」。代码里它是**三件东西叠在一起**：

| 身份 | 归属 | 落点 | 今天成立的方式 |
|:--|:--|:--|:--|
| **齿轮这个图标（长相 + 位置）** | ❌ **设置插件**（唯一来源） | `settings.linkdesk-plugin` 的 `plugin.json` → `appearsIn.iconBar: "bottom"` | 设置插件在图标栏底部声明了一个图标——**出厂件里唯一一个 `bottom`**（实测三只有声明的：`file-tree` / `marketplace` 都是 `top`） |
| **齿轮点开的菜单（8 条）** | ✅ **壳** | `src/core/commands/shell/settingsCommands.ts:503-515`（6 条）＋ `src/core/commands/shell/developerCommands.ts:71-74`（1 条）＋ `src/core/commands/shell/coreCommands.ts:60-68`（命令面板 1 条） | 壳用 `APP_PLUGIN_ID` 往 `MENU_SLOTS.ExtensionGear` 注册菜单项 |
| **「点底部图标 = 弹齿轮菜单」这条规则** | ✅ **壳（池侧实现）** | `src/pool/zones/icon-bar/IconBarZone.tsx:220-234` | 池按 `location === "bottom"` 判——`bottom` 图标不 emit `icon:selected`，改弹齿轮菜单 |

**结论：`bottom` 这个位置值，今天同时承担了两个语义**——「图标放在底部」（几何）和「这个图标是齿轮」（身份）。齿轮菜单是壳的，齿轮图标却是设置插件的，两边靠「恰好设置插件是全软件唯一一个 `bottom`」这条**没人写下来的巧合**黏在一起。

### 1.5 设置插件的现状（`bundled-plugins/settings.linkdesk-plugin` → 源仓 `Encaron/linkdesk-plugin-settings` v1.0.23）

> ⚠️ `bundled-plugins/*.linkdesk-plugin` 是 **zip 包不是目录**（`ls` 会报 Not a directory）。读 manifest 用 `unzip -p bundled-plugins/settings.linkdesk-plugin plugin.json`，`grep` 打上去只会得到 0 命中（无意义）。

`plugin.json` 关键字段：
```json
"icon": "resources/icon-bar.svg",
"marketIcon": "resources/icon.svg",
"core": true,
"factoryRole": "settings",
"appearsIn": { "iconBar": "bottom", "tabBar": true },
```
- 要拆的只有 `appearsIn.iconBar` 这一行。
- **`icon` 必须留着**——它不止图标栏在用（见 1.6），`icon-bar.svg` 这个名字虽然叫 icon-bar，但删了 `iconBar` 之后它仍是标签栏/悬浮面板的图标源。本次**不动它**（改文件内容是另一件，别顺手改）。
- `factoryRole: "settings"` ⇒ 它属于**形态二（进槽可替换）**：`iconbar.ts:45-48` 的 `slotActive` 过滤保证同角色只渲染激活那一套。**这意味着 1.7 描述的坑对它自己其实不成立**——但齿轮图标今天由它提供，本身就不该。

### 1.6 设置插件的 `icon` 还有谁在用（❌ 不能跟着 `iconBar` 一起删）

`src/hooks/usePoolSync/windowLayout.ts:33` 用 `resolvePluginIcon` 给标签栏算图标 ⇒ 设置标签页的图标读的是 `manifest.icon`。
`src/pool/shared/group-tab-bar/GroupTabBar.tsx:353` `{tab.icon && <PoolPluginIcon icon={tab.icon} … />}` 就是它的渲染处。

⇒ **件 2 只删 `appearsIn.iconBar` 一行**，`icon` 原样保留。删错了的后果 = 设置标签页变成一个没图标的空白标签（用户一眼能看见）。

### 1.7 隐患：为什么「任意插件声明 bottom」会出事

这条链是**今天就已经生效的**，不是假想：

1. 某只**形态一**插件（没声明 `factoryRole`，`iconbar.ts:45-48` 的 `slotActive` 不拦）声明 `appearsIn.iconBar: "bottom"`；
2. `buildIconBar` 照单全收 → `icons` 里出现第二条 `location: "bottom"`；
3. `IconBarZone` 把两条都放进 `.ldk-icon-bar-bottom`，并且 `renderIcon(item, true)` ⇒ **两只图标各自都是一颗齿轮**——点哪只都弹同一份 `ExtensionGear` 菜单；
4. **新插件自己的标签页打不开了**（`isBottom` 分支提前 `return`，永不 emit `icon:selected`）。

形态二插件（声明 `factoryRole`）**不受影响**——`slotActive` 只渲染激活套。所以准确说法是：**「任意插件」应窄化为「任意形态一插件」**。

用户这一问（「一旦哪天任意插件也想在底部声明，就会出问题，对吗？」）的答案是**对，但只在形态一**。而且按用户 2026-09-29 的口径（参考 [00-README.md](00-README.md) §一），将来底部真可能长出别的图标（GitHub 登录人头），**所以这不是「等出事再说」的理论风险**。

### 1.8 设计档早就写了「齿轮归壳」——只落了一半

- `docs/02-Electron架构/E3_多WebView与壳收尾_暂定/06-E3f-壳UI收尾.md:588-603`：「3.2 齿轮 #1——全局左下齿轮（ExtensionGear）… **永远可见——不依赖任何插件** …归属：核心 coreCommands.ts 注册到 MenuId.ExtensionGear。**换 marketplace 不影响此齿轮**」。
- 同文件 `:730-745` 的四齿轮对照表：「菜单项由谁注册 = 核心」。
- `docs/02-Electron架构/E3_多WebView与壳收尾_暂定/02-E3b-主题引擎跨进程.md:142`：「全局齿轮 → 核心登记到 ExtensionGear 分区。…**这是 Encaron 的设计，不是违规。**」

## §二 目标态

### 2.1 一句话

**把「齿轮」从「一个带 bottom 位置的插件图标」改成「壳自带的图标栏按钮」**；`bottom` 从此退回它唯一的本义——**几何位置**。

### 2.2 前后对照

| | 今天 | 目标 |
|:--|:--|:--|
| 齿轮图标来源 | 设置插件 `appearsIn.iconBar: "bottom"` | **壳**（`buildIconBar` 里自带一条，`IconBarLayout` 新字段） |
| 齿轮可见性 | 设置插件装了才有；`factoryRole` 槽空/停用则**消失** | **恒可见**（不依赖任何插件，对齐设计档） |
| 点底部插件图标 | 弹齿轮菜单（标签页打不开） | **正常开标签**（`emit("icon:selected")`，与顶部图标一致） |
| `location: "bottom"` | = 齿轮（身份） | = 底部（**纯几何**） |
| 设置插件 | 有图标栏图标 + 标签页入口在齿轮 | **没有图标栏图标**；标签页入口仍在齿轮菜单（`core.openSettings`） |
| 齿轮菜单 | 8 条，全壳注册 | **不变**（8 条，仍全壳注册，一件不改） |
| 谁能弹齿轮菜单 | 恰好那个唯一 bottom 图标 | 只有壳自带那条（`owned` 字段里的 gear），**位置无关** |
| **切 Profile 之后** | 齿轮随设置插件的启用状态变——`switchProfile` 会启用/禁用插件（`ProfileService.ts:312`、E3d §一「切换 Profile 时自动：禁用不在列表中的插件 → **图标栏图标消失**」）⇒ 某套 profile 若不含设置插件，**齿轮整个消失** | **齿轮恒在**（壳自带，与 profile 无关）——本件顺带修掉的一条真实可达路径 |

#### 1.6 齿轮图标跟不跟「图标主题」（📋 拍板点 ①，理由与代价）

[00-README §四 拍板点 1](00-README.md) 建议「**不**跟图标主题」，理由是**代价不对称**：

- **不跟**（推荐）＝ 齿轮图标写死成一个 codicon（`{ kind: "codicon", name: "codicon-settings-gear" }`）。**零新增解析链、零新增配置项**，且与 VS Code 的实际行为一致（VS Code 的 Manage 齿轮**不随文件图标主题变**，它是个 workbench 内置 codicon）。
- **要跟**＝ 让齿轮也吃 `IconRegistry`（图标主题）的解析结果。**代价**：`IconRegistry` 的解析链是**为插件图标设计的**（输入是 pluginId / manifest，见 `src/core/registry/appearance/IconRegistry.ts`）——齿轮**没有 pluginId**，得**新造一套「壳自带图标的解析入口」**（要么给 `owned` 条目编一个伪 id 进注册表（⛔ 别做，就是 §四 否掉的假数据问题），要么给 `IconRegistry` 加一条「按名字取图标」的公开面）。而且**图标主题数据里根本没有「齿轮」这个名字**——第三方图标主题作者不会知道要给 `linkdesk.gear` 画一个图标 ⇒ 绝大多数主题下它只能**回退到同一个 codicon**，等于白做。
- ⇒ **结论**：本件按「不跟主题」写（写死 codicon）。**若将来真要跟**，那是**另一件**（给 `IconRegistry` 开壳图标解析面 + 定主题里的名字契约），**别在本件里顺手改**。

## §四 为什么不用「往 `icons` 数组里塞一条合成齿轮」（另一个更省事的方案，被否）

有个更省事的做法：`buildIconBar` 里直接 `icons.push({ pluginId: "__gear__", icon: 齿轮, label: "管理", location: "bottom" })`，`IconBarZone` 里对 `pluginId === "__gear__"` 特判弹菜单。**否决，三条理由**：

1. **`icons` 整条数组都在拖拽与持久化路径上**。`IconBarZone.tsx:76-94` 用 `localIcons` 镜像它、`:143-167` 的 `mouseup` 会 `emit("icon:reordered", ids)`、壳把序持久化成 `iconOrder`（`iconbar.ts:23-39` 按 `iconOrder` 重排、`:24` 读 `getPluginStateValue(APP_PLUGIN_ID, "iconOrder")`）。合成条目一旦进这条链：**能被拖、位置能被持久化、还可能被写进 `iconOrder` 变成脏数据**（插件卸载后残留一条 `__gear__` 之类的幽灵 id 在状态里）。
2. **`findTarget`（`:107-122`）按 `[data-plugin-id]` 找落点** ⇒ 合成齿轮会被当成合法拖拽落点，用户把插件图标拖到齿轮上会算出一个「插到齿轮前后」的序——语义污染。
3. **`pluginId` 这个字段的语义是「哪个插件的图标」**。塞一个假 id 进去，等于让下游每一处 `getViewPlugin(i.pluginId)`（如 `:66-70` 的激活判定）都要考虑「这可能不是个真插件」——**一个假值污染整个 DTO 的契约**。

**结论**：「壳自带的」与「插件贡献的」是**两类东西**，DTO 上就该是两个字段。多一个字段的成本是三个构造点各补一行（tsc 强制），远低于让一条假数据在拖拽/持久化/激活判定三条链上长期潜伏。

## §七 不做清单（接手 AI 明确别做的）

2. ⛔ **不给设置插件加 `contributes.menus`**——插件往齿轮注册条目是另一条道（[02](02-概念-插件入口两条道与配置文件插件.md)），本件不引入、不示范。

5. ⛔ **不给底部插件图标新造右键菜单**——今天 bottom 图标右键弹齿轮菜单（`:230-234`）；本件把这段删掉后，底部插件图标右键**与顶部一致（无菜单）**。`MENU_SLOTS.IconBar`（`MenuRegistry.ts:48`「图标栏右键」）**今天没有消费方**，要不要启用它是**另一件**，本件不顺手开。

## §八 残余风险与未验证项

1. ⚠️ **未实机复现**：§一 1.7 的隐患链（形态一插件声明 bottom ⇒ 双齿轮 + 打不开标签）是**读码推出的**，本次未实机验证。§五 5.3 已把它列为**动手前的必跑项**——若跑不出来，读码结论需要修正。
2. ⚠️ **件 3 的 `when` 可达性未验证**：`settingsSlotFilled` 这个 context key 由谁同步、ContextMenu 的 `when` 求值路径能否在齿轮菜单（`context: {}`，见 `IconBarZone.tsx:312`）拿到它——需要落件 3 时先读 `ContextKeyService` + ContextMenu 的求值链。**这是件 3 的第一件事，不是最后一件事。**
3. ⚠️ **`location` 的 `default` 兜底**（`IconBarZone.tsx:184`）：未知位置值会掉进 bottom 组。今天 `getIconLocation` 的类型是 `"top" | "bottom" | undefined`，「未知值」只可能来自池侧数据被手改。本件**不改**这条兜底（改了要动 switch 的穷尽性），但记一笔：将来若新增位置值（如 `"bottom-pinned"`），**必须先改这里**，否则静默进 bottom。
4. ⚠️ **en 下的「管理」（件 1.4）**：不做跨仓词条的话，英文界面齿轮 tooltip 是中文。**已知的、可接受的降级**，别在验收时当 bug 报。
5. ⚠️ **`icon-bar.svg` 这个名字的误导**：设置插件删了 `iconBar` 之后，它的 `icon` 仍指向一个叫 `icon-bar.svg` 的文件（现在只给标签栏用）。**名字不准但功能正确**——改文件/改名是插件仓的另一件小事，本件不顺手做（§七 4）。
