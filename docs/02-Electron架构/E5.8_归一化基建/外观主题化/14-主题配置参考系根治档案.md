## 零、一句话核心思想

> **系统标尺是唯一真相源。主题只是标尺上的一个预设点，用户覆盖是标尺上的另一个点。**
> **任何外观控件必须锚定系统标尺（绝对、有单位、跨主题稳定）；主题值只是该标尺的初始填充，被 clamp 进标尺。绝不锚定主题当前值。**

用户 2026-08-25 定性（原话要义）：「调整圆角不应该是跟着设置的主题的基础值走，而是根据系统给出的基础值走；最大圆角是系统可以承载的最大值，插件作者给再大也不超系统阈值。」查证后确认这不是圆角一个问题——**glass 一族、背景清除、播种显示、主题切换残留全部同源**。

## 〇.1 用户真正要的三件事（2026-08-25 用户补述，「还要思考我究竟要的是什么」）

> **① 主题 = 配置预设，覆盖面 = 主题的全矩阵镜像**
> 「对于设置项已有的，主题更多是更改一下配置项；没有独立设置项的（如各个区域详细颜色），则是通过 app.themeColor 进行配置。」
> → **原则：主题可表达的一切属性，设置面必须有对应的覆盖槽。** 主题 = 标尺上的预设点，配置 = 另一位置，两套完整镜像。现状缺口：**文字族**（`text-primary/secondary/muted`）正是「主题设了、设置面没槽」的典型——这就是需求 ③ 的根源。这条同时把 C1 天平推向策略 A（§六 3）：主题=改配置项 ⇒ 切主题 = 重播种配置值。

> **② 更底层的 light/dark 基底可自选**
> 「现在可以自己搭配图片了，必定有的图片较暗……我希望更底层的 light 和 dark 也是可以选择的（不是 Light 这个主题，而是 light 模式）。」
> 图片明度不受主题控制 → 需要一个不依赖主题 `type` 的文字极性控制。

> **③ 背景与字体不可过近（对比度底线）**
> 「要解决背景（无论是 zone 内或后面的背景）颜色和字体过于接近的问题。」
> 无论背景来自主题色板还是用户图片，文字必须可读。用户已预警：**别做成「light 模式 = 黑字」这种半吊子**——深色主题 + 黑字 = 深底深字黑屏翻车。

> ②+③ 合流为一个设计：**文字极性标尺 `app.fontTone`**（§三 新行 + §四 归一 7）。

## 一、为什么现在的系统会犯这个病——「补丁叠加」架构

当前主题引擎的架构是 **主题优先 + 覆盖补丁**：

```
主题配方 → mergeTokens 算出 token 集 → :root + 广播
                 ↑
用户外观覆盖 = 在主题 token 上打补丁（乘 / 洗 / 存在性门控）
```

这个「补丁打在主题值之上」的架构是**一切缺陷的母体**，每一个补丁特性都必然派生出一种病：

| 补丁特性 | 派生缺陷 | 实例 |
|---|---|---|
| 补丁需要一个**基准** | 参考系锚定主题值 | 圆角 ×倍数、glass wash |
| 补丁可**存在/消失**（presence 门控） | 清除 = 回主题值，非绝对无 | 背景图/字体「清除」残留 |
| 补丁**相对或绝对**取决于键 | label 承诺语义 ≠ 行为 | 「1 不透明」实为 ×0.5 wash |
| 补丁**一次性捕获**（播种） | 切主题不重基线 → 残留 | 上一主题值跟过去 |
| 补丁按**域**分散 | 一个属性多主人 | 透明度 split / 圆角两轴 |

**根治方向 = 翻转架构**：以**系统绝对标尺**为基底，主题负责给标尺填默认值，用户覆盖也是标尺上的一个点。「打补丁」消失，变成「这条标尺当前用谁的值」。

## 三、系统标尺定义表（设计草案）

以系统绝对标尺为基底。**主题 = 标尺默认位置；用户覆盖 = 标尺上另一位置；控件坐标永远在标尺上。**

| 属性 | 系统标尺 | 单位 | 主题（默认位置） | 用户覆盖 | 关键决策 |
|---|---|---|---|---|---|
| 界面圆角 | 0 → **32** | px | 各 token clamp 进标尺 | 滑杆绝对值 | 已定案（skill 交叉验证，见 §四 归一1） |
| 玻璃模糊 | 0 → 32 | px | 主题 blur（**无每表面倍率**） | 滑杆绝对值 | A5 要消：去掉 0.44×/1.11× 或改为声明式每表面系数 |
| 玻璃透明度 | 0 → 1 | — | 主题 rgba 基准 | 滑杆绝对值 | B1 合并：单一「表面透不透」 |
| 玻璃叠加色 | 色值 + alpha 0→1 | — | 主题 tint | 色块 + 透明度 | A4 要消：去掉「颜色 alpha 再降」 |
| 背景图 | 空 / 受控路径 | — | 主题图 | 选图 | A6 清除语义：**清除 = 跟随主题（来源徽标显示）**；要绝对无 = 显式「无背景」选项 |
| 字体 | 族名 | — | 主题字体 | 族名 | A7 同背景图 |
| **文字极性** | 跟随主题 / 亮字(深底) / 暗字(浅底) | — | 主题 `type`（dark→亮字预设，light→暗字预设） | 显式选极性 | 〇.1 ②③ + 归一 7 新；系统双字系标尺（稳定跨主题） |
| zone 背景 | 空 / 受控路径 | — | 主题 zones 图 | 选图 | A9 同背景图 |

> **清除语义统一决策**：三个背景/字体键统一为「清除 = 跟随主题」。用户此前误判「清除=残留」，根因是 UI 没显示来源。配合来源徽标（§四 归一5），「清除后看到主题图」就变成「合理」而非「bug」。

## 四、解决方案：六归一

### 归一 1 · 锚点归一（消灭参考系错误）

**原则**：每个可调属性定义系统绝对标尺；滑杆/色块以标尺为坐标；主题值 = 标尺默认位置；主题值 render 侧 clamp 进标尺。

- **圆角（已定案）**：两轴滑杆改绝对 px 0→32；发射边界统一 `min(v, 32)` clamp 所有绝对 px radius token（`radius-xs~2xl` + `surface-radius` + `radius-pill`）；**`radius-full`(50%) 排除**（相对几何值，消费方全圆形控件）。上限 32px 来源：high-end-visual-design「液态玻璃」定稿圆角 = `rounded-[2rem]`；ui-ux-pro-max Enterprise radiusCard 16 = 壳当前 2xl 现值 → 32 = 2× 壳现有最大值（极限预览档）；Material 3 最大标准 28dp。pill 999 → clamp 32 = 「系统最大圆角预览」（gallery ⑦ 本意）。
- **glass 一族（✅ 已执行 2026-08-25，见 §五 #86）**：glassOpacity → 系统绝对透明度 0→1（0=全透见背景图，1=全不透明，去掉 ×0.5 wash 隐藏乘数）；glassTint = 不透明时的颜色（去掉颜色 alpha 再降）；glassBlur → 绝对 px，去掉每表面隐式倍率（改声明式每表面系数）。
- **播种（新挖 A8）**：进 custom 播种改**绝对标尺值**（显示当前有效 px/透明度），非主题比值。

### 归一 2 · 归属归一（一个属性一个主人）

- **透明度**（B1）：合并「主题 rgba + glassOpacity wash」为单一「表面透明度」标尺。主题 rgba 语义重新对齐；用户一个旋钮控制透不透。
- **圆角**（B2）：`surface-radius` 移入 radius 域（或明确两轴命名——组件圆角 vs 分区圆角，label 讲清谁管谁），消灭「surface/glass 域偷偷产出圆角」。
- **背景**（B3）：全窗 vs zone 双通道保留（语义不同），但每槽来源徽标 + 名字讲清（「窗口背景」「分区背景」）。
- **强调色**（B4）：accentMode 并入统一外观模式轴（见归一5）。

### 归一 3 · 生命周期归一（状态随主题/模式一致演进）

- **主题切换重基线策略（C1，✅ 已定案 = 策略 A）**：
  - 策略 A（已定案）：切换主题 = **重新播种**（覆盖键按新主题反推填标尺，用户显式改过的值保留并显示「已修改」徽标）。
  - 策略 B（不采用）：切换主题 = 保留全部覆盖（现状），但来源徽标把「主题值」实时标出。
- **播种时机统一（C2/C4）**：播种仅在「进自定义」与「切主题（策略 A）」两处；所有模式枚举同一播种哲学。
- **复位对称（C3）**：resetAppearance/resetMix 一律「清键 + 拉回模式默认值」，壳命令与插件 API 同语义。

### 归一 4 · 语义归一（label 永远匹配行为）

- 去隐藏乘数/封顶（A3 A4 A5 的 ×0.5、alpha 再降、0.44×/1.11×）。
- label 直述行为：「玻璃透明度——0 全透见背景，1 全不透明」「圆角——0 直角，32 最大圆角」。
- **预览方块（用户方案 1.2）**：滑杆旁加实时预览方块（对标 ColorPicker 预览），玻璃/圆角改动的真实效果先见后点（可配「实时应用 / 确认应用」二选一）。

### 归一 5 · 模型显性化（单一外观模式轴 + 来源徽标）

- **合并三枚举为一轴（D4，用户「不知道混搭和自由调配关系」的根治）**：吸收 appearanceMode + mixMode + accentMode → 单一「外观模式」开关：**跟随主题** / **自定义**。自定义下每个槽位可独立指定「跟随主题 / 用某主题的值（域来源）/ 手动值」——用户直觉的单开关模型。
- **每槽来源徽标（D3/A6/A7/A9 根治）**：每行显示当前值来源（主题 🎨 / 用户覆盖 ✏️ / 域来源 🔀），清除后「回主题」一眼可见为合理行为。
- **enumDescriptions 补齐**：三枚举在 UI 里讲人话。

### 归一 6 · 性能归一（滑杆拖拽不劣化）

- **滑杆防抖**（E1）：input 期间节流，松手再触发 apply；或本地乐观渲染 + 异步持久化。
- **测量解耦**（E2）：measureSurfaceZones 只在 zone 图/窗口尺寸变化时触发，**不随玻璃/圆角 tick**。
- **持久化降频**（E3）：拖拽期间批量写（同 #59 批量 API 先例）。
- **层级定案**（E4）：zone 图应在**玻璃之下**（backdrop-filter 盖图）——语义 = 「图上的玻璃」，既让 blur 可见又省合成。用户方案 1.2 预览方块同样可缓解体感。

### 归一 7 · 文字对比度归一（〇.1 ②③，新）

**缺口（〇.1 ①）**：主题能表达文字族（`text-primary/secondary/muted`），设置面却无对应槽 → 用户无法覆盖文字，也无法对自配图片救场。补槽：**`app.fontTone`**——这就是「主题设了、设置面没槽」原则缺口的直接修复，也顺便补完「主题=改配置项」的全矩阵镜像。

**标尺（〇.1 ②）**：`app.fontTone: 跟随主题 | 亮字（深色背景用）| 暗字（浅色背景用）`。极性是**系统绝对标尺**——亮字系/暗字系由壳定义（亮字 ≈ `#FFFFFF` / `#FFFFFF.82` / `#FFFFFF.60`；暗字 ≈ `#1A1A1A` / `#1A1A1A.75` / `#1A1A1A.55`，三级文字同比例保层级），**稳定跨主题，不锚任何主题值**（防再犯参考系错）。

**对比度保证（〇.1 ③ 警告）**：label 直述「深底用 / 浅底用」+ 每档实时预览方块（见归一 4）——用户按自己**实际背景**（主题色板或自配图）选极性，选错当下肉眼可见，无「深色主题+暗字」黑屏翻车。不做自动亮度检测（图片背景不可靠计算，给用户自由度 + 预览兜底）。

**备选（〇.1 ② 的另一读法）**：整体 `baseMode: followTheme | light | dark`（整壳翻转，含各分区底色）——大锤，需主题双变体（light+/dark+），仅当用户要「整套明暗翻转」而非只保文字可读时才值得。

4. **壳侧无闪**：两条广播同 JS 任务内连发，壳自身 :root 两次 `setProperty` 同帧完成 → 不落中间值。
5. **池侧闪**：两条广播 = 两条独立 IPC = 池侧两个 macrotask → **浏览器可在两次任务间渲染一帧**。`theme:changed` 落地 → `--accent=紫` 画一帧 → `accent:changed` 落地 → `--accent=红`。`.toggle.on { background: var(--accent); transition: background 150ms }`（index.css:210-215）每次翻转都**重启 150ms transition** → 拖滑杆高频 tick = 动画永不完结 = 连续来回闪。
6. **为何「文件树正常」**：非不闪，而是无人在文件树旁拖滑杆——广播全池生效，停手即无广播、恒红。

## 九、缝系统——宿主所有 zone 留缝归一（Phase 11.8：#93，✅ 已执行 2026-08-26）

> 用户实机定性（2026-08-26）：**「统一都是 4px，然后直角就贴死」** + 4px 可拖拽 resize handle 需在留缝**正中**（「在空隙的 1/2 处」）+ 窗口控制**「跟随顶栏表面（推荐）」** + 窗框边境**「2px 或者别的更符合软件的最好」**（桌面应用非 Android，8px 触摸下限不适用）。核心裁决：**缝=宿主所有（space），非主题所有（material）**——Content vs Space Ownership 铁律的布局侧落地。

### 现象（用户挑出的系统性缺陷，非单点 bug）

主题各自声明 `--surface-inset`（ThemeSurface.inset），与 `app.zoneRadius` 圆角开关**两个独立来源同时持有同一视觉属性**——正是簇 B「归属分裂」的又一实例：
- pill-bubble 配方 `inset:8`：**圆角关（直角贴死）时 zone 间仍留 8px 缝**，与「直角贴死」语义矛盾；
- songti 等配方无 inset：**圆角开时 zone 贴死**，圆角悬浮形态无留缝可容纳阴影/光边，玻璃漂浮不成立；
- 用户开关 `app.zoneRadius`（唯一开关）**只影响圆角、不影响缝**——两轴解耦 = 用户预期（圆角↔留缝）被撕裂。

### 根因（簇 B 归属分裂——一个属性被两个来源同时持有）

- `--surface-inset` 由**主题数据**（配方 inset 键 → surfaceVariables 写变量）与**宿主圆角开关**（`app.zoneRadius` → radius 变量）双源驱动，无单一主人。
- `.pool-grid-cell { overflow:hidden }` 使 100% 高表面在 margin 内缩时被裁剪（#50.7 留缝依赖 cell padding 绕过），限制缝只能走 padding 一条路。
- resize handle 每 zone 各自实现（sidebar/right-sidebar/panel 三份），几何各写各的，与缝无关——缝开时 handle 不居中、缝闭时 handle 跨格悬空。

### 定案（归属归一：缝=宿主所有，与圆角开关耦合）

**① 缝法则（ThemeEngine applyOverrides ③，宿主派生终值赢）：**

```
SURFACE_SEAM_INSET_PX = 2   // 每格半缝
--surface-inset = (--surface-radius ?? 0px) === "0px" ? "0px" : "2px"
```

- 放在 applyOverrides **② 循环之后、return 之前** = **最终值赢**——主题/overrides 任何旧 inset 数据都无条件覆盖（主题 inset 已废弃，见 ②）。③ 在 applyTheme（:342）/mergeDomains（:416）/mix（:604）三路径全走，覆盖全部应用入口。
- **圆角开**（radius ≠ 0）→ 每格半缝 2px，相邻格 = 2×2 = **4px 内部缝**；**直角贴死**（radius 0px / 缺省）→ 0px。与 `app.zoneRadius` 开关**单向耦合**（圆角关必贴死，圆角开才留缝）——用户语义「统一 4px + 直角贴死」达成。
- **窗框边境 = 2px 边缘缝**：grid 格走 `cell padding`，titlebar/status-bar 走 `margin`（.pool-grid-cell 外直接子），同变量派生。

**② 主题 inset 数据废弃（ThemeSurface 删字段）：**
- `ThemeSurface.inset` 删（theme.ts）+ 4 配方删 inset 键（pill-bubble/aurora-glass/image-zones/paper-zones）+ 契约 linkdesk.d.ts 重生成（−2 行）。零迁移——旧配方 inset 键被 ③ 无条件覆盖（向后兼容）。
- surfaceVariables 不再写 `surface-inset`（只写 radius），注释标注「inset 不再由主题数据决定」。

**③ 共享 resize handle（归一化结构性重复，三 zone 接驳）：**
- 新增 `.zone-resize-handle`（index.css 全局层——pool-css 门禁禁池内 @import，几何必须共享）+ `z-index: var(--z-sticky)`（Z_INDEX.panelResizeHandle=200）。
- **居中几何**：handle `position:absolute` 锚 cell 边界（= 缝中心），偏移 `calc(-1 * var(--surface-inset, 0px))`：
  - 缝开（inset=2）→ 边界 ±2 = **[boundary−2, boundary+2] 恰好填满 4px 缝且居中**（用户「空隙 1/2 处」）；相邻格零重叠。
  - 贴死（inset=0）→ [boundary−4, boundary] = 4px 带在**己侧** cell 边缘内（对齐现状贴边视觉），不越界不悬空。
- 三 zone 接驳：sidebar `.vertical.right`、right-sidebar `.vertical.left`、panel 四向 `.vertical/horizontal + top/bottom/left/right`（handlePosition 复用）；**useResizeDrag 拖拽逻辑零改动**（只换视觉类）。
- `.pool-grid-cell` 移除 `overflow:hidden` → 表面必须**自裁剪**（`.side-panel`/`.panel-zone`/`.main-zone` 已有，补 `.icon-bar`/`.titlebar`/`.status-bar`）；窗口级 `.pool-root`/`.pool-body` 仍裁剪窗缘。

**④ 窗口控制跟随顶栏表面（#46.18 声明化遗留的跟随问题）：**
- `.window-controls` `position:fixed; top:0; right:0` → **流内 flex**（titlebar 末位自然右对齐）——顶栏 margin 内缩 2px 时按钮随表面一起动（fixed 早于悬浮表面时代，顶栏留缝时按钮脱离表面）。菜单 portal 到 `#context-menu-root`（ContextMenu renderer）→ titlebar 加 `overflow:hidden` 安全。

### 验证（npm run check 1233 绿 +5 缝法则单测 + CDP 实机 8 项全绿）

## 十一、主题设置域驱动重组超算（2026-08-26，删死键 + 9 分节 + 文字合并组 + surfaceTexture 槽）

### 现象（用户亲诉，非单点 bug）
主题组原来「**外观覆盖 13 键 + 域混搭 6 键**」两列平行清单，描述同一 5 域——同一视觉属性的键（圆角 3 键、玻璃 4 键）散在两组，用户来回扫才看得全。用户原话：「我感觉整个『外观覆盖』下面东西太多太乱了，分类也不好」「**符合广大群众使用习惯的，别人一眼就知道怎么调配**」。→ 重画 mockup（`mockups/02-设置页-主题区-重构-mockup.html`）→ 拍板「实施」。

### 根因（簇 B 归属分裂的 UI 残留）
1. **分组按「机制来源」而非「视觉域」**——「外观覆盖」（用户 override 层）与「域混搭」（recipe 来源层）是两个*机制*分组，同一视觉属性被两组同时描述。普通用户关心的是「圆角去哪调」「玻璃去哪调」，不是「这个值来自用户覆盖还是混搭来源」。
2. **mixRadius/mixGlass 是 #85/#86 圆角/玻璃绝对化后的死键**——圆角/玻璃已被系统标尺绝对化（设置层表达单一系统标尺数值，如 surfaceRadius=8），域混搭语义 =「掺另一个配方的多键集合」，对单一标尺数值无消费对象。保留它们 = 一个用户永远调不出区别的假槽。

### 定案（用户拍板）
1. **删 `app.mixRadius`/`app.mixGlass` 两死键**——`MIX_DOMAIN_KEYS` 6→4 域（colors/font/background/surface）；`MIX_DOMAIN_ORDER` 仍 6 域（base recipe 的 radius/glass token 经 fallback 仍合并，归属归一不破坏）；`MIX_SOURCE_KEYS`/`MIX_RESET_DISABLED_WHEN`/followTheme 复位批三处 import 自动收缩，零手工同步。
2. **域驱动重组 9 分节**（一次一域一眼可见）：
   `整体配方`(theme/appearanceMode) → `配色`(themeColor) → `强调色`(accentColor) → `圆角`(surfaceRadius/zoneRadius/zoneRadiusScale) → `玻璃`(glassBlur/glassOpacity/glassTint/glassSaturate) → `背景`(mixBackground/backgroundImage/backgroundOpacity/backgroundMask/zoneBackgroundImage) → `文字`(fontTone/mixFont/fontFamily/fontFamilyMono) → `表面`(mixSurface/surfaceTexture) → `复位`(mixReset)。
   - **资产域来源键保留并入域小组**（mixFont/mixBackground/mixSurface）：它们是配方捆绑资产唯一入口——字体选择器选不了 `__ld_` 前缀 @font-face 资产（ThemeEngine L1114 #50.20），删了用户就永远碰不到配方资产。
   - **数值域来源键删除**（mixRadius/mixGlass）：圆角/玻璃绝对化后无混搭语义（见根因 2）。
3. **fontTone 并入文字组**——四字体键同节（fontTone/mixFont/fontFamily/fontFamilyMono）；fontTone 恒显（无 dependsOn），三字体行 custom 门控（partial bucket 逐键可见性，SettingsView L224-253 既有机制）。
4. **surfaceTexture 槽（#97）**——`app.surfaceTexture` 表面纹理图片路径：空=跟随主题、`__none__`=绝对无纹理（写 `surface-bg-image:none` + `surface-bg-zones:0` 停 zones 量测）、路径=repeat 平铺（写 url + repeat + zones:0）。镜像 theme `surface.texture` 机制，与 zoneBackgroundImage 冲突靠落点靠后取胜。并入 `APPEARANCE_OVERRIDE_KEYS` 14 键（播种/复位/切主题重播种三路径自动覆盖）。

### 分组机制（grouping.ts first-appearance 归桶，无物理搬移即正确）
整体配方(theme@1/appearanceMode@4)、配色(themeColor@2)、强调色(accentColor@3) 物理顺序无需搬动即归对节——appearanceMode 是第 4 位却并回第 1 节。**仅资产来源键前移需要物理重排**（mixBackground 插到 backgroundImage 前、fontTone/mixFont 插到 fontFamily 前）。

### 设计偏差（mockup 静态色板 → 真实图片路径）
mockup 显示静态纹理色板（纸纹/磨砂/无纹理），真实实现用 **uiHint "image" 图片路径选择器**（与 backgroundImage/zoneBackgroundImage 同构）——配方纹理是任意资产路径（paper.png/tex.svg…），静态预设表达不了。`__none__` = 显式「无纹理」，空 = 跟随主题。
