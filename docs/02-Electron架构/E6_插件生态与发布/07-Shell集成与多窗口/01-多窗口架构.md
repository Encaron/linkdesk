## 二、架构决策

### A. 单实例锁保留，second-instance 接管（订正 #47a 原文）

`requestSingleInstanceLock()` 的工作机制：第二个实例启动 → 拿不到锁 → **它必须退出**，同时第一个实例收到 `second-instance`（携带第二个实例的 argv）。这个机制**就是** D1 路线（单进程多窗）的实现载体——把它拆了才会出现多 app 实例。所以：

- `!gotLock → app.quit()` **保留原样**；
- 改的是第一实例的 `second-instance` 响应：从「聚焦主窗」改为「解析 argv → 路由」（文件 → 焦点窗 intake，文件夹 → 开新窗）。
- ⚠️ 与 `#57.7` 订正 `app.relaunch` 用法同类教训：**任务书原文与 Electron 机制不符时，以机制为准订正任务书**，本节即为订正记录。

### B. mainWindow 从「唯一的窗」变为「焦点窗」

`main.ts` 的模块级 `mainWindow` 被 SerialService/file-service 等直接消费（main.ts:51 注释）。多窗后的语义改为：

- **`mainWindow` = 当前聚焦的 workspace 窗**（`BrowserWindow` focus 事件跟随更新），不再是「永远只有一个」；
- 广播类推送（serial/file/LSP 走 `IpcBridge.broadcast`）**维持广播语义不变**——脱出窗时代数据已经广播到所有池，「设备层跨窗共享」是既有既认行为（memory `detached-window-main-only-paths`），本轮不改；
- 定向类动作（对话框 parent 反查、窗口控制按钮）已按 sender 反查宿主窗（`registerDialogHandlers(windowManager)`，main.ts:116 注释 E5.8#62 审计#4）——多窗后沿用 sender 反查，不用改。
- 🔴 焦点窗为空（全部失焦）时保持最后一个聚焦值，不置 null——推送类消费方依赖它非空。

### C. workspace 状态每窗一份

- 每个新窗创建时由主进程分配 `workspaceWindowId`（格式 `ws-<n>` 递增，与脱出窗 `detached:` 前缀同风格，见 window-manager.ts:427 的 poolWindowId 惯例），随创建流程传给该窗壳；
- 壳侧 `WorkspaceService` 的持久化 key 加窗维度：`workspace-folders` → `workspace-folders:<workspaceWindowId>`，`activeWorkspace` pluginState key 同理；
- **迁移**：首次多窗启动读不到带维度的 key 时，回落读全局 key `"workspace-folders"`（老数据归第一窗），读完不删全局 key（降级兼容：老版本回滚后仍能读到自己的状态）；
- 每窗独立壳渲染进程 = `WorkspaceService` 模块级单例天然每窗一份（内存不用改，**只有落盘 key 要加维度**）——这是 #47c「每窗口独立渲染进程 = 天然隔离」的准确含义。

### D. 冷启动恢复最后活跃窗（D7 拍板）

- 主进程维护 `userData/windows-state.json`：`{ lastActiveWindow: { workspaceFolder: string | null } }`（对标 VS Code storage.json 的 `windowsState.lastActiveWindow.folderUris`，只取我们需要的一个字段）；
- 写入时机：窗口 focus（成为焦点窗）与关闭（降级为「关窗时它是焦点窗才写」）两处；
- 无参数启动：读该文件 → 有记录且文件夹仍存在 → `createWorkspaceWindow(folder)`；无记录/文件夹已删 → 空工作区窗（现状行为）；
- 有参数启动（右键/命令行带路径）：**不读恢复记录**，直接按参数开窗。

### E. 关窗清理

- 关窗（OS × 或壳侧关闭）→ 该窗池 WCV 销毁（`registerPool` 既有销毁路径）→ 该窗 workspace 状态**留在盘上**（下次从「最近」可达，对标 VS Code 关窗不清 workspace 数据）→ 主进程从窗口集合摘除；
- 最后一个窗关 → `window-all-closed` → quit（现状 main.ts:501，不改）。

## 三、分步实施

> 每步 = 清单一个格子。做完一步 `npm run check` 全绿 + commit，再下一步（工作法 §1.1/§1.8）。
> 步骤按依赖排：intake 源（Step 1）→ 每窗状态（Step 2）→ 多窗创建（Step 3）→ 隔离验证（Step 4）→ 恢复（Step 5）→ intake 路由收口（Step 6，#46a 的收尾格）。

### Step 1（#47a）second-instance 路由骨架 + argv 解析

- **改 `electron/main.ts`**：
  1. 新建 `electron/windows/launch-args.ts`：`parseLaunchPaths(argv: string[]): { files: string[]; folders: string[] }`——过滤 Electron 自身开关（`--` 开头，含 dev 的 `--user-data-dir` 等），对剩余项 `fs.existsSync` + `fs.statSync` 分类（isDirectory → folders，否则 files）；解析不出的项**静默丢弃但 console.warn**（不弹窗——启动路径失败不该打扰用户）；
  2. `second-instance` handler（main.ts:522）改为：`parseLaunchPaths(argv)` → folders 逐个 `createWorkspaceWindow(folder)`（Step 3 之前先 console 占位，避免悬空引用）→ files 交给 intake 路由（Step 6 前先聚焦行为保留）；
  3. 启动路径（`app.whenReady` 里现 `createWindow()` 调用点）同款：argv 有 folders → 逐个开窗；有 files → 缓存到 `pendingOpenFiles` 数组待壳就绪后消费（Step 6）；都没有 → 走恢复逻辑（Step 5 之前保持 `createWindow()` 现状）。
- **验收**：`npm run check` 全绿；dev 下开一个实例，再从命令行 `npm run electron:dev -- D:\某文件夹` 触发 second-instance，主进程日志能看到分类结果（此时窗行为还是聚焦，不算完）。
- **风险**：dev 模式 argv 里混着 vite/electron 开关——`parseLaunchPaths` 必须先过滤再 stat（用真实路径测试，别拿假路径糊弄）。

### Step 2（#47e）workspace 状态每窗一份

- **改 `src/core/services/layout/WorkspaceService.ts`**：
  1. `initWorkspaceService` 增参 `workspaceWindowId: string`；`_persistFolders`/`getPluginStateValue(APP_PLUGIN_ID, "activeWorkspace")` 两处 key 加 `:<workspaceWindowId>` 后缀（决策 C）；
  2. 迁移回落：带维度 key 读不到 → 读全局 key（老数据归第一窗）；写迁移标记 pluginState（`workspace-migrated:<id>`）防每次启动重复回落读到老数据；
  3. 🔴 每窗壳是独立渲染进程，`workspaceWindowId` 由谁告诉壳？→ 主进程 `createWorkspaceWindow` 时通过 `process.env` 不行（同进程共享）——走 **query parameter**：壳页面 URL 带 `?wsWindow=ws-1`（`loadURL`/`loadFile` 拼接），壳启动早期读 `location.search` 存入常量。池窗 windowId 已有同款「创建时下发」先例（`CreatePoolWindowRequest`），渲染进程侧先例照抄；
  4. 硬约束 13：`initWorkspaceService` 已有 `_initialized` guard——加参后确认第二次调用返回同一 Promise（多窗各自进程内只调一次，但 StrictMode 双调防线必须保持）。
- **验收**：check 全绿 + 既有 WorkspaceService 单测改造后全过（测试 fixture 用 `ws-test-1` 虚构值，硬约束 21）+ dev 实测重启后文件夹列表恢复如旧（迁移回落正控）。

### Step 3（#47b）多窗创建与销毁

- **改 `electron/main.ts`**：`createWindow()` 参数化 → `createWorkspaceWindow(workspaceFolder?: string)`：
  1. BrowserWindow 构造段原样抽出（frame:false、icon、backgroundColor 等全部保留）；`mainWindow = win` 改为「窗口集合登记 + 设为焦点窗」（决策 B）；
  2. **IPC handler 注册块整体留在首次创建**（幂等注册已是现状，main.ts:81-120 各 `register*Handlers()` 都有 guard）——多窗不重复注册；`WindowManager`/`IpcBridge` 单实例保留（它们已按 windowId 管理多池窗）；
  3. `windowManager.createMainPool()` → 改调池创建按窗版（`registerPool(win, wsWindowId, 'workspace:<id>')`，沿用脱出窗 L427 的第三参命名风格）；
  4. `workspaceFolder` 非空 → 窗口加载后推给壳（`webContents.send(IPC.workspace.openPath, folder)`，通道名按 `channels.ts` workspace 组惯例新增）；壳收到后调 `WorkspaceService.addFolder`。
- **改 `electron/windows/window-manager.ts`**：
  1. `mainWindow` 引用语义改焦点窗（决策 B）：加 `focus` 事件挂钩（创建处统一挂）→ 更新焦点引用 + 写 windows-state.json（Step 5 的钩子，此处先留空函数位）；
  2. closed 处理沿用 `shellClosingWindows`/`notifyShellWindowClosed` 既有模式（L364-380）——workspace 窗关 = 从集合摘除 + 池销毁；**不**走脱出窗的「通知壳按策略处理 tab」（workspace 窗的 tab 归自己壳管，壳进程随窗销毁，无需转交）。
- **验收**：check 全绿；dev 下命令行先后带两个文件夹路径 → 两个窗各自文件树只显示自己的文件夹；关一窗另一窗不受影响；全关进程退出。
- 🔴 **最大风险点**：`mainWindow` 单例的消费方（SerialService/file-service/缩放因子 `_lastZoomFactor` 重放/crash-recovery）——逐个 grep `mainWindow` 消费处，按「焦点窗 or sender 反查」归类改造。改造期间每完成一组消费方就跑一次 check + dev 冒烟，不攒。

### Step 4（#47c）每窗隔离验证（dev 半）

- 多窗下逐项核对：文件树根不同 / 展开状态不串（`expandedUris` 也要加窗维度——Step 2 同款处理，`plugins/file-tree` 的 `useExpandPersistence.ts:18`）/ 设置改动互不影响 / 标签页布局互不干扰（LayoutService 落盘 key 检查——同 Step 2 逻辑，`LayoutService.ts` 的布局持久化 key 若为全局也要加窗维度，**实施时先核它的 key 形态再动手**）。
- 验收 = 一张 dev 实测清单跑完（对标 `code C:\projectA` + `code C:\projectB`），结果记入清单 #47c 行。

### Step 5（#47f）冷启动恢复最后活跃窗

- **改 `electron/windows/launch-args.ts`**（或独立 `windows-state.ts`，实施时按壳目录规范定）：读写 `userData/windows-state.json`（决策 D）；写入挂点 = Step 3 的 focus 钩子 + 关窗钩子；
- 启动分支接回 Step 1 的「无参数 → 恢复」：文件夹存在性校验（`fs.existsSync`）失败 → 空工作区窗 + 不清记录（VS Code 语义：文件夹暂时插着 U 盘走了不等于用户不要它）。
- 验收：开窗 A → 开窗 B → 全关 → 重启 → 只恢复 B；删掉 B 文件夹 → 重启 → 空工作区窗。

### Step 6（#46a 收尾）intake 路由接通

- 文件（`pendingOpenFiles` 与 second-instance files）→ 焦点窗 `webContents.send` → 壳侧 intake 消费 → `fileAssociation.getPluginFor`（见 02 文档 §三）；文件夹 → Step 3 的 `createWorkspaceWindow`。
- 验收与 #46a 整格验收合并（02 文档 §四）。
