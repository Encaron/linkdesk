# 插件规范化层——总档案（L3.7）

> **立案：2026-09-11，用户四问（marketplace 更新日志为何在 plugin.json / 首次配置为何标准 / marketplace 是否历史遗留 / settings 空目录 + editor 图散落）→ 审计交付 → 用户拍板「同意你的想法，但是要立文档，加任务，同样放在第四层前面」。**
> **一句话：** 3.6 层把**文件**理干净了（谁多长、谁该拆）；这层理**元数据**——写的地方和读的地方**从来没对上**，中间还躺着三个「声明了、写了文档、填了类型、就是没人用」的死字段。**文件干净 ≠ 账目对上。**
>
> **定位：** 插在 L3.6（文件整理层）与 L4（端到端验证）之间。**L4 是拿真插件在安装版里跑通全链路——而「详情页读不到更新日志」「未装插件看不到说明」正是全链路上的一段。地基建完先对账，再跑车。**
>
> **🔖 非新能力文档（2026-09-11 判定）：** 本层**不新增任何 `window.linkdesk.*` 壳 API、不新增 contribute 贡献点**。改动只在三处：① `plugin.schema.json` **减两个字段**（changelog / readme）；② `@linkdesk/plugin-sdk` 的 `publish` **增加行为**（读工程内 `CHANGELOG.md` / `README.md` 自动写目录条目）——这是**作者工具链**，不是壳 API；③ 官方插件的**内容补齐**（补 `README.md` / `CHANGELOG.md` / 挪图）。故**无需 8 维度设计前置**，也**不需要在 03-插件制造 里新增 API 章节**（已在 [02 号档案 §六](02-元数据链路归一.md) 逐条核过「要不要新 API」，结论 = 不要）。

## 〇、本层做什么、为什么做

### 做七件事

| # | 动作 | 说明 |
|:--|:--|:--|
| ① | **规范先立** | 把「插件该不该有 README.md / CHANGELOG.md、放哪、和详情页什么关系」写进 [09-插件目录规范](../../03-插件制造/09-插件目录规范.md)——现在**一个字都没有** |
| ② | **元数据真源归一** | `plugin.json` 的 `changelog` / `readme` 两字段**删除**；`CHANGELOG.md` / `README.md` 是唯一真源 |
| ③ | **接通断链** | SDK `publish` 从工程内两个文件**自动写**目录条目的 `readmeUrl` / `versions[].changelog`——未安装的插件也有说明可看 |
| ④ | **官方插件补齐** | **9 只**插件补 `CHANGELOG.md`（**49 条记录搬家，不是重写**）；marketplace 补 `README.md`；settings 修两处 i18n 键错位 |
| ⑤ | **资源与目录归位** | editor 散在插件根的三张图归位 `resources/`；`theme-mint-soda` 补 `icon` 字段；资源随包规则盘清 |
| ⑥ | **脚手架换代** | `create-linkdesk-plugin` 模板补 README / CHANGELOG / resources / .gitignore / publish·lint——**生成出来的插件必须长得像官方插件** |
| ⑦ | **门禁扩域** | 空目录红灯 + 可疑 `t()` key 黄灯 + 脚手架形状红灯——**让这层修的东西下次不会再犯** |

### 为什么现在做——四条实打实的理由

**① 一条链路断成三截，每一截单独看都「没问题」。**

更改日志这条链路：

| 段 | 现状 | 单独看 |
|:--|:--|:--|
| **写** | 9 只插件把 **49 条**更新记录写进 `plugin.json` 的 `changelog` 数组（marketplace 一只 27 条） | 「有更新记录 ✅」 |
| **中间** | SDK 打包器**会**把 `CHANGELOG.md` 拷进 zip（[vite-config.ts:556](../../../packages/plugin-sdk/src/vite-config.ts)） | 「路修好了 ✅」 |
| **读** | 详情页「更改日志」页签**只读包内 `CHANGELOG.md`**（[ChangelogTab.tsx](../../../plugins/marketplace/src/views/detail/DetailView/ChangelogTab.tsx)） | 「有渲染逻辑 ✅」 |

**三段都「有」⇒ 净结果是一条都通不了。** 全仓 **0 个插件**带 `CHANGELOG.md` ⇒ 每只官方插件的「更改日志」页签都显示「**该插件未附带更改日志**」，**49 条记录一条都看不见**。

**② 三个死字段——「声明了、写了文档、填了类型、就是没人用」。**

| 字段 | 谁声明它有 | 谁读它 | 实况 |
|:--|:--|:--|:--|
| `plugin.json.readme` | [plugin.schema.json:85](../../03-插件制造/plugin.schema.json) + [06-plugin.json规范.md:225](../../03-插件制造/06-plugin.json规范.md) | **无人** | publish **读了又丢掉**——[publish.ts:251](../../../packages/plugin-sdk/src/publish.ts) 收进 `ManifestView.readme`，`buildCatalogEntry` 从不用它；**0 只插件填** |
| `plugin.json.changelog` | schema:219 + 06 规范:237 | **无人** | 49 条内容写进了一个没有任何读取方的数组 |
| catalog `versions[].changelog` | [select.ts:115](../../../plugins/marketplace/src/services/marketCatalog/select.ts)（读者在）+ publish.ts:45（类型在） | marketplace（**未装**分支） | publish **从不写**（[publish.ts:268](../../../packages/plugin-sdk/src/publish.ts) 只发 version/downloadUrl/publishedAt） |
| catalog `readmeUrl` | marketplace parse.ts:47（读者在） | marketplace（**未装**分支） | 只有官方目录手写才有，SDK publish 不产 |

**这直接踩用户原则第 4 条「没有死代码」。** 四个字段，四个都是「有类型、有文档、有注释、没读取方/没写入方」。

**③ 根因不是疏忽，是「两套机制从没对上」。**

一边设计成**文件**（`CHANGELOG.md` / `README.md`，对标 VS Code），一边实现成**清单字段**（`plugin.json.changelog` / `.readme`）。两边各通半截、各能自圆其说，**合起来一条也不通**。

判断「哪边对」的锚点不是偏好，是**一件事实**：详情页的读取代码**已经按文件写好了**（`readPackageFile(id, "CHANGELOG.md")`）。⇒ 文件是真源，字段是死路。**本层就是把实现往已经写好的那一侧收。**

**④ 唯一两边都对的样板，是手写的，脚手架造不出来。**

`first-run-setup`（「首次配置」，E6#73p）全仓**唯一**同时有 `plugin.json.changelog` **和** `CHANGELOG.md` 的插件——也是唯一「更改日志」页签真有内容可显示的。

但它**不是脚手架生成的**：它的 `resources/` / `CHANGELOG.md` / `src/{views,services,components,styles}/` / `publish` script **模板一个都没有**（见 [05 号档案 §一](05-脚手架换代.md) 对照表）。

⇒ **「上一个 AI 手写了一只标准插件」不等于「脚手架能造出标准插件」。** 这层的第 ⑤ 件事就是把这个差值补平。

## 三、判据（本层拿它量东西）

**M1｜一个概念一处表达。** 同一件事（更改日志 / 说明文档）**只允许一个真源**——允许「文件 + 字段」并存即等于允许两套真相。

**M2｜声明必须有消费者。** schema 里出现一个字段 ⟺ 有代码读它**且**有代码写它。否则**删**（不是「留着以后可能有用」——那是 memory `no-deferral-future-excuse` 明令禁止的）。

**M3｜删字段必须给迁移出口。** 删 `plugin.json.changelog` 不能只说「已废弃」——49 条内容**必须搬进 `CHANGELOG.md`**（内容零丢失），且 SDK `validate` 对旧写法给**可读提示**（[02 §五](02-元数据链路归一.md)）。

**M4｜官方插件 = 教具。** [09 规范](../../03-插件制造/09-插件目录规范.md) 开篇原话「**官方插件模板——第三方开发者看任一官方插件，目录结构一致**」⇒ **脚手架生成物、官方插件、规范文档三者必须同形**。任何一处不一致都算本层的账。

**M5｜接通优先于砍掉。** 设计已存在、读取方已写好、只差写入方一段纯函数 ⇒ **接通**（②号拍板的判据）。只有「读也写也都没有、且不打算做」才砍。

## 五、待拍板项（研究时冒出来、不属四条已定范围的）

### ① 已装 / 未装的「更改日志」版式要不要归一？

- **现状**：已装分支把包内 `CHANGELOG.md` **全文**渲染成一整个 Markdown 块（[ChangelogTab.tsx:86](../../../plugins/marketplace/src/views/detail/DetailView/ChangelogTab.tsx)），块头却写 `v{已装版本}` + 「已安装」——**底下其实是全部历史**；未装分支按 `versions[]` **逐版本**渲染。
- **为什么现在冒出来**：接通前未装分支基本是空的，**不对称看不出来**；接通后两个分支都有内容，一眼就能看出「同一个文件，两种切法」。
- **建议**：**先不动**。已装读全文是「本地权威」的设计（装的是哪个版本看哪个版本的说明），改它 = 改 UI 行为，要有自己的实机证据。**本层只把它记成已知不对称**，需要归一另立轮。
- 🔴 **须用户点头才动。**

### ② `first-run-setup` 源码不在本仓——样板怎么维护？

- 现状：全仓唯一标准样板，**源码躺在 `E:\linkdesk-build+scratch\first-run-setup`**（用户 2026-09-11 提供的位置），仓里只有 `dev-fixtures/first-run-setup.linkdesk-plugin` 成品。
- 问题：**样板改了没人知道、没人验**；本层想同步删它 `plugin.json.changelog` 也**够不着**。
- 建议（三选一，**须用户拍板**）：
  - **(a)** 源码收进 `plugins/first-run-setup/`（像其余官方插件一样在本仓构建）——**推荐**，样板才能被门禁和 `npm run check` 照到；
  - **(b)** 保持现状，只在文档里写明「样板源码在仓外」，接受它不受门禁保护；
  - **(c)** 把样板能力**吸收进脚手架模板**（本层第 ⑤ 件事本来就做一半），`first-run-setup` 降级为历史产物。
