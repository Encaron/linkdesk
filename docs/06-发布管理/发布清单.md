# 发布清单——每次发版照着勾

> **用途：** 主软件每次发版（打 tag → CI → Release → 发布后回验）的逐条检查单。**照勾，不凭记忆。**
>
> **🔴 本档是指针集，不是真理源**——凡下面写了「见 §X」的，**去那边读，别在本档抄第二份**。抄第二份 = 造一个会漂的真值源（这正是本仓栽过的跟头，见 §〇）。
>
> | 要知道什么 | 去哪读 |
> |---|---|
> | 安装包叫什么名字 | [02-发布流水线.md §〇](../02-Electron架构/E6_插件生态与发布/05-文档与发布/02-发布流水线.md)（唯一真理源）＋ 门禁 `npm run assert:installer-name` |
> | 当前版本号是多少 | `package.json` 的 `version`（**唯一真值**，全仓不写第二份） |
> | 下载入口在哪、长什么样 | [02-发布流水线.md §二](../02-Electron架构/E6_插件生态与发布/05-文档与发布/02-发布流水线.md)（GitHub 承载，无自建站点） |
> | CI 各步干什么 | [`.github/workflows/build.yml`](../../.github/workflows/build.yml)（**唯一真理源**；文档里的 YAML 是设计稿） |
> | 版本号怎么往上走 | [02-发布流水线.md §四](../02-Electron架构/E6_插件生态与发布/05-文档与发布/02-发布流水线.md) ＋ [.claude/skills/version-bump/SKILL.md](../../.claude/skills/version-bump/SKILL.md) |
> | 进度/实况记录 | [E6-执行清单.md](../02-Electron架构/E6_插件生态与发布/E6-执行清单.md)（E6 阶段唯一进度真相源） |
>
> 🔴 **文件名里不许出现版本号**（用户 2026-09-11 拍板：**不进 1.0，继续在 `v0.x.x` 游荡**）——本档因此叫 `发布清单.md`。
> 🔴 **E6 结束也不自动跳 1.0**；要不要进 1.0 须用户另行点名。

## 一、发布前（这些没过完，不许打 tag）

```
[ ] npm run check 零错误（双工程 tsc + ESLint 0 警告 + 全量测试 + 各道门禁）
[ ] E5.8 全量回归矩阵场景通过
[ ] E6 全链路验证通过（E6#39 终极验证）
[ ] 安装包名门禁绿：npm run assert:installer-name（三判据：配置层 / 产物层 / latest.yml 元数据层）
[ ] CHANGELOG.md 里有 `## v{本版版本号}（{日期}）` 段 —— 缺段 ⇒ Release 正文为空 ⇒
    用户点「查看更新内容」看到一片空白（E6#57.15d③ 门禁）
[ ] electron-builder 配置正确（appId / productName / icon / artifactName）
[ ] NSIS 实测：安装 ✅ 卸载 ✅ 覆盖安装 ✅
[ ] 🔴 NSIS 覆盖安装**双向往返**实测（E6#42d）——
    尤其是「**已装新版，再去装旧版**」那一向：拦不拦？拦在哪一层？结论写进发布流水线档 §1.4
[ ] 打包后所有路径不 404（dist/ / bundled-plugins / icon）
```

> ⚠️ **改动过打包配置（`electron-builder.yml`）就必须重打包再验**——改完配置不重打包 = 你验的是上一版产物（第 3 层的老坑）。
> ⚠️ **不许拿 `electron:dev` 冒充安装版**——注册表写入、覆盖安装、卸载这三条路径在 dev 上根本不存在。

## 二、发布（打 tag → CI → 检查）

```
[ ] 版本号已 bump 且同笔写了 CHANGELOG 段（死规矩，3.7.3 立）
[ ] git tag v{版本号}   ← tag 名 = package.json 的 version + `v` 前缀
[ ] git push origin v{版本号}
[ ] 等 GitHub Actions build 完成（两道门禁要过：CHANGELOG 段 / 安装包名）
[ ] 检查 Release 资产有**三件**：`.exe` ＋ `latest.yml` ＋ `.blockmap`
      · 功能上**必需的只有 `.exe`**——本仓自研更新器读 Releases API、按 asset 名匹配，
        **不读 `latest.yml`**（别把「没传 latest.yml 就没有新版」当成理由，那是错的）
      · 另两件是为了给安装包名门禁的第三判据留现场 ＋ 发布惯例
[ ] Release 正文非空，且**是 CHANGELOG 正文**（不是 GitHub 自动罗列的 commit 流水），
    且带下载信息块（文件名 / 版本号 / 发布日期 / 系统需求）——由 CI 自动拼，禁手写
[ ] 🔴 **Release 正文的写法（2026-09-14 用户拍板）**：**面向所有用户的正式发布说明，不是工程日志**——
    按分类组织（✨ 新功能 / 🐛 问题修复 / 📄 说明），**一眼看懂这版改了什么**。
    **禁止出现**：① 内部任务号与轮次（`feat:E6#57.x`、「第 N 轮」）② 版本策略注记（「0.x 向后兼容走 patch 位」）
    ③ 对话腔与第二人称（「不让您再干等」「念给您听」）④ 门禁/负控/如实记账等工程过程叙述。
    这些留给提交记录与执行清单；CHANGELOG 段本身就是 Release 正文（同源），写的时候就按这个口径写。
[ ] Release 页上的 `.exe` 文件名与 tag 版本号对得上
[ ] 下载入口：README 的 `releases/latest` 链接**通常不用动**（别名自动跟随）；
    ⚠️ **一旦发现要手改 README 里的版本号，就是写错了**——那说明你把 `latest` 别名写成了死版本号
```

## 三、发布后（从 Release 页当一次真用户）

```
[ ] 从 Release 页下载安装包 → 装到干净环境
[ ] 启动 → 全功能正常（无白屏 / 各部件齐 / 无启动报错）
[ ] 市场装一个插件 → 正常
[ ] 🔴 旧版实机点「检查更新」→ 发现新版 → 下载 → 重启安装 → 版本号**真的变新**
    （E6#57.16 全链路；依赖 E6#37 的构建产物）
[ ] 建维护分支（分支名随实际版本，别写死 v1.0.x）
```

> 🔴 **判据不是「脚本全绿」，是「货架真新」**——脚本绿只证明基线被标记过。
> 同理：`npm run check` 绿 ≠ 发布成功；**能下载、能装、能起来、版本号真变了**才算。
> （这条在 npm 作者包那侧已经用血换过一次，见 L3.7：脚本绿灯装上才发现货是旧的。）

## 四、这份清单什么时候改

- **新增一道门禁** → 在「一、发布前」加一行，并写明**判据**（不是「注意一下」）
- **改了打包/发布机制** → 同步改指向的真理源，本档只改指针
- ⚠️ **本档不许写死版本号、不许写死文件名**——两者都有唯一真理源，写进来就是第二份
