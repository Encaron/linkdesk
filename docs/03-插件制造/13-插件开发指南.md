## 开写前——三条铁律

违反这三条，插件**装得上但会坏**（甚至带崩壳）。先记住，比写完再改便宜得多：

1. **只走 `window.linkdesk.*`**——禁止 `import` 壳内部（`@src/core/...`）。ESLint `noCoreImportInPlugin` 是 error 级，写下去就红。
2. **颜色走 CSS 变量 `var(--xxx)`**——禁止硬编码 hex，否则主题切换时你的插件不跟随。
3. **文案走 `t()`**——key 就是原文（中文插件用中文 key，中文自带兜底，英文译文放 `i18n/en.json`）。

> 全八条 + 适用范围 → [00-README §硬约束](00-README.md#硬约束写任何一行插件代码前)。

## 第 1 步：生成项目骨架

**做什么**

```bash
npm create linkdesk-plugin@latest my-cool-plugin    # 名字必须 kebab-case（小写字母/数字/连字符）
cd my-cool-plugin
npm install
```

不带参数运行 `npm create linkdesk-plugin@latest` 会交互式问插件名。

> 🔴 **`@latest` 别省。** 不带版本锚时，npm 的 npx 缓存可能**一声不响**给你一份几个月前的脚手架拷贝，而 CLI 从不打印自己的版本号——唯一的症状是生成出来的工程**少了文件**（没有 git 仓、没有 `AGENTS.md`、没有 CI，只有 7 个文件而不是 16 个）。已经中招的人：`npm cache clean --force`，再重跑。

**怎么知道做对了**
新目录里出现 `plugin.json` + `src/index.tsx`，且 `plugin.json` 里的 `{{pluginName}}` 之类占位符**已替换成你的真实插件名**（还有 `pluginId` / `name` / `description` / `author` 已填好，`author` 默认取 `git config user.name`）。CLI 会打印一行告诉你**建没建 git 仓**：建了的话 `git log` 里有一笔「初始骨架」提交、分支叫 `main`。

**细节点哪一篇**
[02-插件开发工具链/01-create-linkdesk-plugin脚手架.md](../02-Electron架构/E6_插件生态与发布/02-插件开发工具链/01-create-linkdesk-plugin脚手架.md)——生成产物的**逐文件契约**（每个文件为什么存在、占位符规则、16 个模板文件的角色）。**项目结构不要在这里找**，那篇是唯一真相源。

> ✅ **建仓（2026-09-14 已落地）**：脚手架**代建 git 仓**——照 `cargo new` 的三条语义，**不是「一律 `git init`」**：
> - 工程目录**不在任何 git 仓里** ⇒ 自动 `git init -b main` ＋ **一次初始提交**（模板自带 `.gitignore`，所以你第一步看到的不是满屏 untracked）；
> - 工程目录**已经在某个 git 仓里** ⇒ **不建**（防嵌套仓——比如你把插件生成在另一个已有仓库的子目录下）；
> - **`--no-git`** ⇒ 一律不建（逃生口，对标 `cargo new --vcs none`）。
>
> CLI 会**明确打印**它到底建没建、为什么，别自己猜。🔴 **前提是脚手架的版本 ≥ 0.1.3**——旧版
> 既不会建仓、生成的工程也没有 CI。CLI 没有 `--version` 旗标，它自己说不出拿到的是哪一版；这正是第 1 步那条命令必须带 `@latest` 的原因。
> 工程该放哪、仓该叫什么 → [15-多仓开发与本地工作区](15-多仓开发与本地工作区.md)。

## 第 3 步：写你的第一段 UI

**做什么**
改 `src/index.tsx` 里 `default export` 的那个 React 组件。壳就是这么渲染它的：

```tsx
export default function HelloPlugin({ isActive }: { isActive: boolean }) { … }
```

- `isActive` = 本标签页当前是否聚焦。**keep-alive 架构下所有标签页始终挂载**——别用 `isActive` 整块 blank 掉内容，它只配用来 gate「聚焦才该跑的副作用」（如自动保存、轮询）。
- `tabId` / `sourceId` = 本标签 id / 上下文数据（编辑器类插件靠 `sourceId` 知道用户打开了哪个文件）。

**怎么知道做对了**
预览宿主里 UI 随你改。**并且**：界面里没有任何裸 hex 颜色、没有硬编码中文（用 `t()`）——这两条肉眼可查，也是后面 `npm run lint` 会拦的。

**细节点哪几篇**
- 视图契约细节 → [05-插件UI写法规约](05-插件UI写法规约.md)（右键菜单/浮层/持久化/快捷键两轨道）
- 想放进侧栏或底部面板 → [08-ViewContainer-视图容器API](08-ViewContainer-视图容器API.md)

## 第 4 步：调一个 API

**做什么**
`window.linkdesk.` 后面能接什么，看**速查表**（45 个命名空间 / 242 个方法，从契约自动生成）：

- 👉 [plugin-sdk README §API 速查表](../../packages/plugin-sdk/README.md#api-速查表)
- 完整签名与逐方法说明 → `node_modules/@linkdesk/contracts/linkdesk.d.ts`（IDE 里能直接跳转）

例：读一个配置项、订一个变更。

```ts
const theme = await window.linkdesk.theme.getCurrent();
const dispose = window.linkdesk.configuration.onChange("my-plugin.greeting", (v) => { … });
```

**怎么知道做对了**
TypeScript 编译通过就是对的——`window.linkdesk.*` 的类型随 SDK 注入（`tsconfig.json` 的 `types` 已配好），**方法名拼错、参数类型不对，`tsc` 当场红**。这是契约给作者的免费防线。

**细节点哪几篇**
- 哪些面在池/壳哪一侧可用、`?` 标法什么意思 → [01-插件API契约 §三 唯一真相源](01-插件API契约.md)
- ⚠️ **速查表里带 `°` 的方法**（契约标 `?`）只在一侧 preload 注入，**多数是壳侧独有**——你的插件跑在池里，调之前先判存在。

## 第 6 步：用共享组件（别自己造右键菜单）

**做什么**

```bash
npm i @linkdesk/ui
```

**怎么知道做对了**
切换主题时你的右键菜单外观跟着变（自造的实现通常不会）。仓库硬约束 3 明确：手写右键菜单是违规的。

## 第 9 步：上架市场

> 🔴 **先破一个最常见的误解：上架是「两步」，`npm run publish` 只是第一步的半程。**
>
> | 步 | 做什么 | 做完之后谁看得见 |
> |:--:|------|------|
> | **①** | `npm run publish`——发布到你**自己**的 GitHub 仓（Release 资产 ＋ 仓库根 `marketplace.json`） | **只有手动把你的仓库地址加进「市场源」的人**。默认用户**看不见** |
> | **②** | **把你的插件收录进官方目录** `Encaron/linkdesk-marketplace`（往目录的 `marketplace.json` 提一个条目 PR） | **所有默认配置的用户**——这一步才是真正的「上架」 |
>
> 「我跑了 publish，怎么市场上搜不到」= 卡在第二步。完整口径（含官方目录收录怎么提）→ [04-插件分发格式](04-插件分发格式.md)。

**做什么**

```bash
npm run publish      # = linkdesk-plugin-sdk publish —— 第 ① 步
```

**前置——工程必须已是推到 GitHub 的 git 仓库**

publish 的目标仓库 = 你工程的 git remote `origin`（发布到**你自己的** GitHub 仓：Release 资产 ＋ 仓库根 `marketplace.json`；多市场源模型）。跑之前 `git remote -v` 确认 origin 指向你的 GitHub 仓。

> ✅ **现状（2026-09-14 已落地）**：脚手架**已代建 git 仓**（`main` 分支 ＋ 一次初始提交，见第 1 步）⇒ 推到 GitHub **只剩两条**，别人常说的三条里 `git init` 那条已经不需要了：
>
> ```bash
> git remote add origin git@github.com:<你>/<仓>.git
> git push -u origin main
> ```
>
> 什么时候仍需自己 `git init`：生成时带了 `--no-git`，或工程被生成在**另一个 git 仓里**（那时脚手架按 `cargo new` 语义刻意不建嵌套仓）。

**在 CI / 非交互终端里发布（AI 代理同理）**

交互跑发布有两步要你碰键盘——各有非交互解法：

| 交互步骤 | 非交互解法 |
|:--|:--|
| GitHub token 掩码输入 | 设环境变量 `LINKDESK_GITHUB_TOKEN`（见下） |
| 「发布以上内容？[y/N]」确认 | 带 `--yes`（或先 `--dry-run` 预览） |

token 的取值顺序：**①** 环境变量 `LINKDESK_GITHUB_TOKEN` → **②** SDK 配置档（你系统配置目录下的 `linkdesk-sdk/config.json`——第一次在交互终端跑 publish 时自动写入）→ **③** 交互式掩码输入。非交互终端里找不到 token 时，publish **立即报错**并提示设环境变量——不会挂住干等。

```bash
LINKDESK_GITHUB_TOKEN=ghp_xxx npm run publish -- --yes   # 脚本里一次性用
```

```yaml
# GitHub Actions——把存的 secret 注入该步骤
env:
  LINKDESK_GITHUB_TOKEN: ${{ secrets.LINKDESK_GITHUB_TOKEN }}
```

> 🔔 **401 多半是「到期」，不是「填错」：** publish 走 GitHub REST API，用**经典 PAT**（repo 权限）。如果发布突然 401 而机器上别的一切正常，头号嫌疑是 **PAT 过期**——新造一个，更新环境变量或配置档。

**怎么知道做对了**
第一步：GitHub Release 上出现你的 `.linkdesk-plugin` 资产；第二步：官方目录出现你的条目后，**在一台干净机器（默认配置、不加任何市场源）**上市场里搜得到、能装、能更新——这才是「上架完成」的判据。

**细节点哪几篇**
- 完整链路（本地 → GitHub → 用户电脑）→ [03-插件发布流水线.md](../02-Electron架构/E6_插件生态与发布/02-插件开发工具链/03-插件发布流水线.md)

## 插件仓里的测试怎么写

不用配任何东西——但「这段该不该测」值得一个直给的回答。

- **工具链已预装**：`vitest` / `jsdom` / `@testing-library/react` 都在 `devDependencies` 里，写 `src/__tests__/<同名>.test.ts`，然后 `npm run test`。
- **共享测试地基由 SDK 提供**：`window.linkdesk` 的最小 mock 住在 `@linkdesk/plugin-sdk/vitest-setup`，你仓里的 `vitest.setup.ts` 是指向它的**一行指针**。⛔ **不要在自己仓里再抄一份**——抄来的那份会与共享版**无声漂移**。
- **纯逻辑最值得测**：`src/**/*.ts` 里既不碰 React、也不碰 `window.linkdesk` 的单元，应该配上测试。视图与交互**划得来时再测**——今天没有任何东西在量它。
- **插件专属桩住本仓**：你的代码调了共享 mock 没覆盖的东西（比如 `window.linkdesk.serial`）？在需要它的那个测试文件里用 `vi.fn()` 补上——别指望共享 mock 为你的插件长一条分支。
- **声明式插件**（纯 JSON／主题／语言包）**没有可测单元**——它的门禁是 `npm run verify`（结构与声明）。**「没有测试」在那里不是缺陷。**
- **老仓什么时候迁都行**：把整份 mock 换成一枚一行指针 ＋ 一次 `npm install`，就是全部动作（好处：mock 升级从此跟着 SDK 走）。

**怎么知道做对了**

```bash
npm run test     # vitest run——空测试集**故意**判过（passWithNoTests）
```
