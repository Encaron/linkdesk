# 08 — 多 WebView vs ExtHost 开销对比

> 2026-07-24。冷冰冰的数字——两种插件隔离模型的进程拓扑、内存、启动时间、调试复杂度逐项对比。
> **不讨论哲学、不讨论原则——只算账。原则和决策见 `02-插件隔离模型.md` 和 `03-插件入口方案.md`。**

---

## 一、两种模型的进程拓扑

### 模型 A：独立 WebContentsView（本方案）

```
┌─ Main Process (Node.js, ~30MB) ──────────────────────────┐
│  SerialService  FileService  ConfigService                │
│  WindowManager  IpcRouter                                 │
└───────────────────────────────────────────────────────────┘
        │                │                │
        ▼                ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ 壳 BrowserWindow │ │ 终端 WebContentsView │ │ 设置 WebContentsView │
│ ~150MB          │ │ ~70MB               │ │ ~70MB               │
│                 │ │                      │ │                      │
│ 图标栏+侧栏+    │ │ React 组件           │ │ React 组件           │
│ 标签栏+分屏     │ │ 逻辑+UI 在一起        │ │ 逻辑+UI 在一起        │
│                 │ │ 一个调用栈            │ │ 一个调用栈            │
│                 │ │                      │ │                      │
│ 非 view 插件加载  │ │ 崩了 → 只崩自己      │ │ 崩了 → 只崩自己      │
│ (protocol/theme/ │ └──────────────┘ └──────────────┘
│  language/resource)
└──────────────┘

标签页关闭 → WebContentsView.destroy() → Chromium 进程 kill → 内存回收
未打开的 view 插件 → 不创建进程 → 0 内存开销
```

**每个 view 插件 = 一个 Chromium 渲染进程。逻辑和 UI 不分离。关闭即销毁。**

### 模型 B：共享 ExtHost + WebviewViews（VS Code 方案）

```
┌─ Main Process (Node.js, ~30MB) ────────────────────────────────┐
│  SerialService  FileService  ConfigService                     │
│  WindowManager  IpcRouter                                      │
└────────────────────────────────────────────────────────────────┘
        │                  │                       │
        ▼                  ▼                       ▼
┌──────────────┐  ┌────────────────────┐  ┌──────────────────────┐
│ 壳 BrowserWindow │  │ ExtHost (Node.js)    │  │ WebviewView 终端    │
│ ~150MB          │  │ ~50-80MB            │  │ 进程级: ~70MB       │
│                 │  │                      │  │ iframe 级: ~10MB    │
│ 图标栏+侧栏+    │  │ 终端 activate()      │  │                      │
│ 标签栏+分屏     │  │ 设置 activate()      │  │ 只有 UI 层            │
│                 │  │ 市场 activate()      │  │ 逻辑在 ExtHost        │
│ 侧栏按钮渲染    │  │ 工作台 activate()    │  │ postMessage 通信      │
│                 │  │ ...N 个插件的         │  └──────────────────────┘
│ webviewView 也  │  │ activate() 全部加载   │
│ 可在壳内以      │  │                      │           │
│ iframe 跑       │  │ 始终运行——不随        │           ▼
└──────────────┘  │ 标签页关闭而回收       │  ┌──────────────────────┐
                  └────────────────────┘  │ WebviewView 设置    │
                                          │ 进程级: ~70MB       │
                                          │ iframe 级: ~10MB    │
                                          └──────────────────────┘

ExtHost 始终在运行——所有已安装插件的 activate() 都加载在里面
WebviewView 在标签页关闭时可以销毁——但 ExtHost 不能
```

**每个 view 插件 = 两个部分。** 逻辑在共享 ExtHost（一个 Node.js 进程），UI 在 WebviewView（独立进程或壳内 iframe）。

## 二、核心差异——一个参数决定一切

WebviewView 有两种隔离模式，这个选择直接决定方案 B 的内存表现：

| 模式 | 隔离强度 | 每个 WebviewView 内存 | 插件间 UI 安全 | Web 能力限制 |
|---|---|---|---|---|
| **进程级**（独立 Chromium 渲染进程） | 强——独立进程 | **~70MB** | ✅ 互相隔离 | 无限制 |
| **iframe 级**（壳进程内 `<iframe>`） | 弱——同进程 DOM | **~5-10MB** | ❌ 同进程，跨 iframe 访问可能 | 跨域限制、部分 API 受限 |

VS Code 两种都支持，从 2019 年开始默认往进程级迁移（安全原因）。iframe 模式有跨域限制——`<iframe sandbox>` 默认禁止 `allow-same-origin`，这意味着 iframe 内的 JS 不能用 `window.top`、不能访问父页面的 DOM、某些 Web API 行为不同。

**重要：如果你选 iframe 级来省内存，等于放弃了"插件 UI 之间互相隔离"——因为它们在同一个 Chromium 进程中，共享同一个 JS 堆。**

## 三、内存算账——逐场景

### 3.1 你的 4 个插件（全有 UI）

| 场景 | 模型 A<br>独立 WebContentsView | 模型 B<br>ExtHost + 进程级 WebviewView | 模型 B<br>ExtHost + iframe 级 WebviewView |
|---|---|---|---|
| 空壳启动 | **150MB** | 150 + 50 = **200MB** | 150 + 50 = **200MB** |
| 只开终端 | 150 + 70 = **220MB** | 200 + 70 = **270MB** | 200 + 10 = **210MB** |
| 终端 + 设置 | 150 + 140 = **290MB** | 200 + 140 = **340MB** | 200 + 20 = **220MB** |
| 4 个全开 | 150 + 280 = **430MB** | 200 + 280 = **480MB** | 200 + 40 = **240MB** |

**进程级 WebviewView 的方案 B 比方案 A 更费内存。** 每个 WebviewView 的 Chromium 进程和 WebContentsView 是一样的东西——都是 Chromium 渲染器。方案 B 额外多一个 ExtHost 进程（50MB）。

iframe 级方案 B 确实更省——但代价是插件 UI 在同一进程里，隔离弱。

### 3.2 真实场景：50 个已安装，3 个打开

| 场景 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 已安装 50 个，打开 3 个 view 插件 | 150 + 3×70 = **~360MB** | 150 + 80 + 3×70 = **~440MB** | 150 + 80 + 3×10 = **~260MB** |
| 其余 47 个插件（非 view） | 加载在壳进程里，不额外创建进程 | 逻辑在 ExtHost 里（含在 80MB 中） | 同左 |
| 其余 47 个中若有 view 插件未打开 | 0 内存——不创建 WebContentsView | 逻辑在 ExtHost 里占少量内存，UI 不创建 | 同左 |

**ExtHost 的 80MB 包含所有 50 个已安装插件的 `activate()` 及其依赖——无论用户是否打开。** 方案 A 里，未打开的插件不创建进程，非 view 插件加载在壳进程里（和壳共享内存）。

### 3.3 两者都有的开销（与模型无关）

以下开销两种方案都一样——都是 Electron：

| 开销项 | 大小 | 说明 |
|---|---|---|
| Electron 框架自身 | 120MB 安装包 | 一次性 |
| Main Process (Node.js) | ~30MB | 串口/文件/配置服务 |
| 壳 BrowserWindow | ~150MB | 图标栏/侧栏/标签栏/分屏 |
| 每个打开的 view 插件的 Chromium 渲染 | ~70MB | 不管叫 WebContentsView 还是进程级 WebviewView——同一个东西 |

## 四、启动时间

| | 模型 A | 模型 B |
|---|---|---|
| **冷启动过程** | 壳渲染 → 用户看到界面 | 壳渲染 + ExtHost 启动 + **加载所有已安装插件的 activate()** → 用户看到界面 |
| **10 个插件** | ~2-3s（壳渲染时间，与插件数无关） | ~3-5s（需初始化 10 个 activate） |
| **50 个插件** | ~2-3s（**不变**——未打开的插件不加载） | ~5-10s（加载 50 个 activate 及其依赖） |
| **100 个插件** | ~2-3s（**仍不变**） | ~8-15s |
| **打开终端标签页** | ~1-2s（创建 WebContentsView + 加载 React） | ~0.5-1s（WebviewView 创建较快——逻辑已在 ExtHost 中运行） |

方案 A 的壳启动时间与安装的插件数量无关——只创建壳自己的 BrowserWindow。**方案 B 的启动时间随安装插件数量线性增长。** 这是 VS Code 用户熟悉的体验——装了很多扩展后启动变慢。

打开单个标签页时，方案 B 略快（因为逻辑层 `activate()` 已初始化）。但这是用更慢的冷启动换来的——类似"启动慢但开标签页快"vs"启动快但开标签页稍慢"的取舍。

## 五、插件崩溃影响面

| 场景 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| **终端插件 JS 死循环** | 终端 WebContentsView 卡死<br>其他插件不受影响<br>关闭终端标签页 → 进程 kill → 恢复 | WebviewView 卡死<br>**ExtHost 不受影响**（ExtHost 是独立进程）<br>关闭 → UI 恢复 | iframe 卡死<br>**壳进程也被卡死**<br>整个软件无响应 |
| **终端插件内存泄漏** | 泄漏在终端进程<br>关闭标签页 → OS 回收 | 泄漏在 WebviewView 进程<br>关闭 → OS 回收 | 泄漏在壳进程<br>整个软件内存持续增长<br>**无法单独回收** |
| **恶意插件读其他插件数据** | **读不到**——独立进程，独立 heap | **读不到**——独立渲染进程 | **能读到**——同进程 heap，可跨 iframe 访问 DOM |
| **ExtHost 崩溃** | 无 ExtHost | **所有插件的逻辑层重启**<br>UI 层（WebviewView）不崩但逻辑断了 | 同左 |

**iframe 级方案 B 的致命问题：** 一个坏插件拖垮整个软件。用户不知道是哪个插件导致的——只知道 "LinkDesk 崩了"。

## 六、为什么进程级 WebviewView 的方案 B 没有意义

进程级 WebviewView = 独立 Chromium 渲染进程 = 跟 WebContentsView 是同一个东西。

```
模型 A:   WebContentsView   = Chromium 渲染进程 (逻辑+UI 在一起)   = ~70MB
模型 B:   ExtHost 进程       = Node.js (纯逻辑)                    = ~50MB
         + WebviewView       = Chromium 渲染进程 (纯 UI)            = ~70MB
                              ─────────────────────
                              总共 ~120MB + 两个调用栈
```

**方案 B 进程级 = 用两个进程做方案 A 一个进程做的事——贵一倍，多一个调用栈，多一层 postMessage。** 唯一的"优势"是逻辑和 UI 分离——但对 UI 插件来说这不是优势，是负担。

## 七、场景推演——50 个插件 vs 200 个插件

### 7.1 50 个插件——中等规模

假设：30 个 view 插件 + 10 个 protocol + 5 个 theme + 5 个 language

用户日常打开 3 个标签页。

| | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 冷启动 | ~2-3s，150MB | ~5-8s，230MB | ~5-8s，230MB |
| 日常使用 | 150 + 3×70 = **360MB** | 230 + 3×70 = **440MB** | 230 + 3×10 = **260MB** |
| 崩溃隔离 | ✅ 每个插件独立 | ✅ UI 独立，逻辑共享 ExtHost | ❌ 所有 UI 共享壳进程 |
| 调试 | 一个 DevTools | DevTools + Node 调试器 | 一个 DevTools（都在壳里） |

### 7.2 200 个插件——生态繁荣

假设：100 个 view 插件 + 60 个 protocol + 20 个 theme + 20 个 language

用户日常打开 5 个标签页。

| | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 冷启动 | ~2-3s，150MB | **~15-30s**，280MB | **~15-30s**，280MB |
| 日常使用 | 150 + 5×70 = **500MB** | 280 + 5×70 = **630MB** | 280 + 5×10 = **330MB** |
| ExtHost 稳定性 | 不存在此问题 | **200 个 activate() 共享一个进程——任一个崩 → 全部逻辑重启** | 同左 |

**200 个插件时 ExtHost 冷启动需加载 200 个 `activate()`——这是 VS Code 级别的启动时间。** 方案 A 的启动时间与安装插件数量无关。

## 八、综合对比

| 维度 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| **4 个 UI 插件内存** | 430MB | 480MB ← **更差** | 240MB ← 更好但... |
| **50 安装/3 打开内存** | 360MB | 440MB ← **更差** | 260MB ← 更好但... |
| **200 安装/5 打开内存** | 500MB | 630MB ← **更差** | 330MB ← 更好但... |
| **冷启动（50 插件）** | ~2-3s ✅ | ~5-8s ❌ | ~5-8s ❌ |
| **冷启动（200 插件）** | ~2-3s ✅ | ~15-30s ❌ | ~15-30s ❌ |
| **插件 UI 进程级隔离** | ✅ | ✅ | **❌** |
| **插件逻辑进程级隔离** | ✅ | **❌** try/catch 级 | **❌** try/catch 级 |
| **一个插件崩 → 影响面** | 只崩自己 | UI 崩自己，逻辑崩全部 | **全崩** |
| **调试调用栈** | 1 个 | 2 个 | 1 个（都在壳里） |
| **写插件文件数** | 1 个 | 3+ 个 | 3+ 个 |
| **AI 训练数据密度** | React——极高 | ExtHost API——低 | ExtHost API——低 |

## 九、结论

**进程级 WebviewView 的方案 B 在所有内存场景下都不如方案 A。** 每个 WebviewView 和 WebContentsView 是同一个底层东西（Chromium 渲染进程）——方案 B 在此基础上多一个 ExtHost 进程。

**iframe 级方案 B 在内存上确实更省——但牺牲了三件事：**
1. **插件 UI 隔离**——同进程，iframe 之间的隔离远弱于进程隔离
2. **崩溃容错**——一个坏插件的 iframe 死循环 → 整个壳进程卡死
3. **Web 能力**——iframe sandbox 限制部分 API

**这三点中的任何一点对 LinkDesk 都是致命的。** 尤其是第二点——LinkDesk 的插件来自第三方，你无法假设它们都写得好。

**独立 WebContentsView（方案 A）在几乎所有维度上都是最优解——包括内存（与进程级 WebviewView 对比时反而更省）。**
