> 当年缺的不是「解耦意识」，是**归属判据**。解耦管住了 import 方向，**没管住「这份能力该住哪一层」**；没有第二个实现者，就没有人问「换一台插件谁来画」。

### P2 · 调用面没有壳级入口——唯一跨插件路径是**硬编码命令 id**

- ⇒ **能力被一台插件托管**：插件对插件的字符串耦合，且与铁律②「壳不认识任何插件 id」擦边（认识它的是 settings，不是壳）。

### P3 · 声明面只认扩展名（无 mime）

- **纠正形态**：若第三方插件出现「无扩展名／多形态」需求（如剪贴板片段、`.md.txt`），需扩声明面（另案）。

### P4 · `contributes.fileAssociations` 的 `command?` 是**死字段**

- `FileAssociationService.ts:27` 注释写「可选——打开时执行的命令（默认 `workbench.action.openFile`）」，但**全仓 grep `workbench.action.openFile` 只在注释里命中**（另一处 `docs/02-Electron架构/E2_底层加固与侧栏扩展_暂定/03-E2c-基础设施缺口.md:179` 是同一句的设计稿）；实际打开走的是 `tabs.create(pluginId, …)`。
- **纠正形态**：删字段（诚实）或补实现（写进作者面文档与 schema）。

### P5 · 壳侧持有插件命令 id 清单（`renameMigrations`）

- `src/core/services/configuration/renameMigrations.ts:70-102` 有约 33 行 `explorer.* → file-tree.*`（含 `explorer.openWith → file-tree.openWith`）。
- **定性（我的判断）**：这是**用户配置的一次性改名账**（explorer 从壳抽成插件时，旧用户的自定义快捷键要跟着改），**可辩护**，甚至把借来的 `editor.*` 还了回去（`:93-95` 注释）。
- 但它确实意味着**壳代码里存在插件命令 id 清单**——登记为「已知擦边」。**纠正形态**：不动；若要动，改由插件自报迁移表（成本高，未必值）。

### P6 · 判据 A 与 D10 的口径紧张（**需用户裁决**）

- 判据 A 说「消费宿主声明的控件必须住双方都取得到的层」——选择器消费的是宿主数据（`listHandlersFor`），且**声明者（任意插件）≠ 渲染者（file-tree）**⇒ 严格按判据 A 它**该**在共享层。
- D10 律说「**≥2 家真实消费者**才准入」⇒ 它**先**留在 file-tree。
- 两条判据打架时，本案用 D10 判了「先留」。**该裁决只在「第二消费者是假想的」时成立**；一旦 ①真出现第二个消费者（见 §三）或 ②认定「文件管理器」这个**角色本身可替换**（如设置插件那样可整套替换），判据 A 立刻要求搬家。
- ⚠️ 而 `07-插件侧适配-文件树与编辑器.md:41` 现在的口径是：「**UI 住文件树（呈现归插件）**……**换一套文件树插件，选择器跟着走**」——这等于同时承认「角色可替换」＋「选择器随插件复制」，与滑块案判词「第二个使用者出现之日就是复制粘贴之日」**同构**。这条口径要不要改，是 P6 的实质。

## 三、缘起：用户新提的需求（P1/P6 的触发条件可能就是它）

用户 2026-10-05 原话要点：**「很多的插件都需要这种特殊功能」**——例：一个「每日日记」插件把日记存成 markdown，插件**自己内部**有个「打开这篇日记」按钮，右键可选「用编辑器插件／记事本／以 VS Code 形式打开」；「**如果说这个功能存在于文件树的话，那么其他的插件怎么样才能够用到这个功能？**」

**今天第三方插件的能力矩阵**（证据：`contracts/linkdesk.d.ts:1941-1953` `LinkDeskAPI.fileAssociation`；通道 `electron/ipc/channels.ts:84-93`；声明面 `electron/plugins/plugin-manifest-loader.ts:89-110`；打开用法 `file-tree/src/views/FoldersView.tsx:126-134`）：

| 它要做的事 | 今天 | 缺口 |
|:--|:--|:--|
| 声明自己是某类文件的打开者 | ✅ `contributes.fileAssociations`（每个 manifest 都注册） | 只认扩展名（P3） |
| 编程问「该用谁打开／列出全部 handler」 | ✅ `lk.fileAssociation.getPluginFor` / `listHandlersFor` | — |
| 写默认／恢复自动 | ✅ `setDefault` / `setDefaultBulk` | — |
| 编程真打开 | ✅ `lk.tabs.create(pluginId, {filePath,…})` | — |
| **弹出同一个「选择打开方式」面板** | ❌ **只能自己重写** | **缺共享件 `OpenWithPicker`（P1）＋ 缺壳级调用面（P2）** |

⇒ 结论：日记插件今天要做「我自己的按钮 → 选打开方式」，除了判定/声明/打开已开放，**面板与入口都得自造**，且拿不到共享的「当前默认／恢复已动」语义。
