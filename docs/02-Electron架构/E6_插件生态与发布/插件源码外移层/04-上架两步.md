# 7.3 上架两步——publish 只是半程

> **任务号：** E6#100 · **前置：** 7.2（该插件已在独立仓、可构建） · **产物：** 18 只发货插件在官方目录里可被**默认发现**
> **🔴 本轮要纠的一个误解：** 「跑一遍 `publish` 就上架了」——**不是**。`publish` 只做第一步。

---

## 〇、上架是两步，不是一步

| 步 | 动作 | 结果 | 谁做 |
|:--:|:--|:--|:--|
| **①** | `npm run publish`（= `linkdesk-plugin-sdk publish`） | 条目写进**插件自己仓**的 `marketplace.json` + 该仓 Release 带 asset | 插件（自动） |
| **②** | 条目并进 **官方目录** | **所有用户默认可见** | 今天手工（PR / 手工 PUT） |

**只有第一步的后果**：东西在网上，但**只有「手动加了这个源 URL 的人」能找到它**。⇒ 用户卸载后想装回来，得记得那个 URL。

**这正是你「一个都不敢卸」的解药**——只有进了官方目录，卸载才是安全的。实查官方目录（`Encaron/linkdesk-marketplace` 的 `marketplace.json`）当前**只有两条**：`hello-linkdesk` 与 `first-run-setup`。**18 只发货插件一只都没进去。**

> 📖 机制依据：[01-GitHub-Releases方案.md §6.7 官方目录收录](../03-插件市场/01-GitHub-Releases方案.md)（2026-08-30 混合模型定案）。**官方收录 + 多源并存**：不收录 = 只在自己仓发布，用户/AI 手动加源可见。作者可以先自仓发（立即可用）→ 想扩大影响再收录官方。

---

## 一、第一步：`publish`（链路已通，逐只跑）

### 1.1 前置条件（逐只自查）

| 条件 | 现状（2026-09-14 实测） |
|:--|:--|
| 工程是 git 仓且 origin 指向 GitHub | 🔴 **待 7.6 轮**——脚手架代建之前，靠 `publish.ts:226` 的报错引导作者手敲 |
| `plugin.json.version` 已 bump 且**未被发布过** | 逐只确认（`publish` 有「tag 已存在 → 拦」守卫） |
| 工程根有 `README.md` | ✅ **18/18 全有** |
| 工程根有 `CHANGELOG.md` | ⚠️ **17/18**——`theme-iconset-pastel` **缺**（见 §三） |
| `CHANGELOG.md` 内有 `## v<plugin.json.version>` 段 | ⚠️ **逐只确认**——切不到该版本 ⇒ 目录条目的 `versions[0].changelog` 不写键（不报错，静默少一块） |
| 分发件 `<id>.linkdesk-plugin` 已 build | 7.2 §3.2 已产 |
| GitHub PAT（`LINKDESK_GITHUB_TOKEN` 或本地配置档） | 逐台机器一次性 |

### 1.2 命令与产物

```
cd <插件仓> && npm run publish          # 有 --yes / --dry-run
```

产物（三样，全在**插件自己仓**上）：
1. GitHub Release，tag = `v<plugin.json.version>`
2. Release asset = `<id>.linkdesk-plugin`
3. 仓库根 `marketplace.json`（`publish` 自动建/合并）——含 `readmeUrl` 与 `versions[0].changelog`（**作者零声明，publish 自动写**）

### 1.3 🔴 逐个闭环，不许攒批

**上与搬必须成对**（[7.2 §〇](03-逐个迁移.md) 铁律）。逐只完成的判据：

- [ ] 插件仓有对应 tag 的 Release + asset（**人肉打开看一眼**——`publish` 的直链是拼出来的，不读响应）
- [ ] 插件仓根有 `marketplace.json` 且条目字段正确（`downloadUrl` / `readmeUrl` / `repository` / `versions[]`）
- [ ] 把该仓源 URL 加进市场（设置里「添加市场源」）⇒ **能看到、能装、能更新**
- [ ] 装到安装版 ⇒ 功能正常
- [ ] **卸载 ⇒ 再从市场装回来**（这一步是「卸载安全」的实证，不是可选项）

## 二、第二步：官方目录收录（今天手工，需补工具）

### 2.1 现状与风险

**现状**：把条目并进 `Encaron/linkdesk-marketplace` 的 `marketplace.json`（发 PR 或手工改）。

**风险（这是本轮必须造工具的理由）**：18 只逐条手敲，**一定会把那个 json 改错**——而它一坏，**所有人默认可见的货架全坏**（该文件是内置默认源，用户零操作就会拉它）。

### 2.2 要造的东西（建议）

`scripts/sync-official-catalog.mjs`（**放壳仓 `scripts/`**，因为它维护的是「我们发布的这批插件」的集合账）：

```
① 读壳仓的 bundled-plugins.lock.json（7.4 轮产出）→ 得到 18 只的 owner/repo
② 逐仓 fetch raw.githubusercontent.com/<owner>/<repo>/main/marketplace.json
③ 合并成一份官方目录（同 id 取版本高者；保留既有第三方条目不动）
④ 输出到临时文件 + 打印 diff（新增/变更/删除各几条）
⑤ 由用户过目后手工落进 linkdesk-marketplace 仓（PR 或直推）
```

**边界（不越界的地方）：**
- 🔴 **脚本只生成、不推**——写的是另一个仓库，推送照 memory `push-wait-for-user` 办（用户点头）。
- 🔴 **不许删既有第三方条目**：官方目录里可能有非官方作者的插件（§6.7 的收录路径）。合并逻辑必须是「**只增改自己这批 + 不动别人的行**」，**禁止整文件覆盖**。
- 🔴 **不许把 18 个 id 写死在脚本里**（硬约束 10）：清单来源 = `bundled-plugins.lock.json`（数据文件），不是代码字面量。理由见 [05-出厂种子保鲜.md §五](05-出厂种子保鲜.md)。

### 2.3 为什么第二步本身没法全自动

**它是「官方货架」的编辑权**，天然要人过一眼（§6.7 的早期形态就是「作者给官方仓库发 PR」——**轻量审核是设计的一部分，不是没做完**）。工具的价值在于**把「18 条手敲」降成「看一眼 diff」**，不是取消这一步。

## 三、前置缺口（本轮内清掉）

| 缺口 | 处置 |
|:--|:--|
| 🔴 `theme-iconset-pastel` **缺 `CHANGELOG.md`**（18 只里唯一） | 补一份（照同批主题插件的最小体例）。**不补的后果**：该插件详情页「更改日志」永远空——不报错，静默少一块 |
| ⚠️ 各插件 `CHANGELOG.md` 是否都有 `## v<当前 plugin.json.version>` 段 | **逐只机械核对**。`publish` 切不到该版本时**不报错**（按设计「缺省即不写键」）⇒ 只能靠事前核对发现 |
| ⚠️ 条目的 `icon` / `iconSource` | 复核 18 只的实际形态（带 URL 图标的走 `iconSource: "url"`，对标官方目录里 `first-run-setup` 那条的写法） |

> ⚠️ **不要为「统一好看」去改插件的显示名或描述**——那是插件自己的内容，本轮只补**发布必需**的缺口。改内容 = 改插件 = 要 bump + 重打 zip，会与本轮的「搬迁不是内容变更」原则打架。
