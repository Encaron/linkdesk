# 入口与数据归一——怎么进 Store，侧栏主区怎么共用一份数据

> **为什么存在**：入口决定「Store 在不打开时怎么被发现」，数据归一决定「侧栏与 Store 是不是同一个市场的两扇窗」。这两题都是结构性拍板，先于一切 UI 设计。
> **上游**：[02-病灶与目标](02-病灶与目标.md)（§三 目标形态 1/2 条是本文两题的由来）；**下游**：[04-分类体系](04-分类体系.md)（分类页住 Store 里）、[05-卡片与动作槽](05-卡片与动作槽.md)（Store 页内容）；**事实底座**：[01-插件侧现状](01-插件侧现状.md)。

## 一、入口行为（拍板：A+B 都要）

### 1. 先立住不该变的东西：图标 ≠ 直接跳主区

**用户场景**（2026-11-19 口述）：主区正看着某个插件的内容，此时只想侧栏搜一下、装一个插件——图标点击若直接把主区跳成商店页，就毁了「侧栏快速操作」这个核心场景（02 §三·1）。

**现状核对**：这**正是现状默认行为**——点 🧩 → 侧栏切到市场，主区保持当前标签页不动（插件仓 `src/index.tsx` 头注原话：「点 🧩 → 侧栏展示列表，主区保持当前标签页不动」）。所以这条不是要实现的新东西，是**要保住的现状**；实施期若有任何改动威胁到它（包括 Store 落地后顺手「优化」图标行为），一律回到本条拦住。

### 2. 方案 A：侧栏常驻入口（先做，零壳改动）

- **是什么**：市场侧栏 toolbar 段加一个显眼入口（「进入 Plugin Store」）→ `window.linkdesk.tabs.create(...)` 开商店标签页。
- **为什么放 toolbar 段**：它是唯一永远展开、永远在视口顶部的段（order -1，见 01 §一）——入口的可见性天花板。
- **为什么零壳改动**：`tabs.create` 是现成通道（侧栏目录行点开详情今天就在走，01 §三·1），插件自己开自己的标签页，壳无感知。
- **为什么「常驻」**：它是商店的**发现性**——哪怕设置开关关着、哪怕用户从没进过商店，门永远看得见。方案 B 只服务老用户，A 服务所有人。

### 3. 方案 B：偏好开关（✅ 2026-11-19 拍板：做，走壳改）

- **是什么**：市场插件在 `contributes.configuration` 声明布尔设置项「点击市场图标时同时打开商店页」，**默认关**；开着时点图标 → 侧栏 ＋ 商店标签页一起来。
- **为什么做成开关且默认关**：A+B 是两种使用习惯（快速操作派 vs 商店直入派），不该替用户选；默认关 = 不改变任何现有用户的既有习惯，开关只做增量。
- **🔴 实现路径（拍板：改壳，不走「插件订阅事件」）**：
  - 配置键约定 **`{pluginId}.openTabOnIcon`**（布尔，缺省 false），插件在自己的 `contributes.configuration` 里声明——设置页照常自动出现，无需壳里写 marketplace 特判。
  - 壳侧 `src/App/tabActions.ts` 的 `icon:selected` 处理器：现有逻辑是「tabOnly 插件直接开标签」；**扩展为**——非 tabOnly 且 `getConfigurationValue(pluginId + ".openTabOnIcon") === true` 时，也 `createTab(pluginId)`；否则维持只切侧栏。
  - 为什么不用「插件订阅 `icon:selected`」：该 push 是否广播到插件窗口**未证实**（探针没做），而拍板已选改壳；壳改动小且**通用**（任何 sidePanel 插件声明同一键即可用，不是市场专用）。
  - **守卫**：默认关时行为必须与本条 1（图标 ≠ 直接跳主区）完全一致——开关关着就有零行为差异，任何情况下不得把「跳主区」变成默认。

## 二、数据归一（拍板：中央订阅，视图纯订阅者）

### 1. 为什么：两起事故（不是理论洁癖）

| 事故 | 现象 | 根因 | 当时的修复 |
|---|---|---|---|
| **1.1.6 多表面塌缩**（插件仓 `docs/01-多表面共享状态塌缩/`，2026-09-30） | 「检查更新」后侧栏行翻新了、主区详情页不翻新，要重启软件 | SDK 多表面打包把模块级单例在表面间**各复制一份**，模块级变量不是跨表面唯一真相 | 整份状态搬进 `realmSlot` 全局槽（01 §一） |
| **用户实测裂缝**（2026-11-19 口述） | 详情页卸载了插件，侧栏列表没跟着变（反之亦然） | **刷新触发点散落在各视图**——每个面自己订阅 lifecycle、自己调 refresh，任何一面漏订阅或时序错开就裂缝 | 未修（本次任务修） |

两起事故是同一个病在不同部位发作：**状态与刷新逻辑没有单一属主**。realmSlot 修掉了「状态的唯一性」，没修「刷新的统一性」——本次归一化把后半也收掉。

### 2. 方案（本次实施的结构约束）

1. **唯一 store**：已装/禁用/目录三个投影，全住 realmSlot 槽（地基已有，沿用不重造）。
2. **中央订阅**：lifecycle 事件（装/卸/启/停）订阅收敛到 `marketplaceShared` **一处**；事件到 → 刷新 store 一份。
3. **视图纯订阅者**：侧栏五段、Store 大屏、详情页、角标，全部只做三件事——订阅 store、渲染、发动作。**⛔ 禁止自建刷新逻辑；⛔ 禁止本地留状态副本；⛔ 禁止绕过 store 直接读壳 API 拼列表。**
4. 效果：卸载发生在任何一面，store 一份刷新，所有面自动收敛——裂缝从机制上不存在。

### 3. 验收判据（实施期测什么）

- 任意一面发起卸载/禁用/安装/更新，其余所有面在下一帧收敛到真值（纯逻辑单测 + 视图冒烟）。
- 代码评审 grep 判据：视图文件里不得出现独立的 lifecycle 订阅或 `refreshData` 调用（中央那处除外）。

## 三、与侧栏退位剧本的衔接

本文的归一化是 02 §五可删除性的**技术前提**：因为视图只是订阅者，删掉侧栏视图不伤数据层；因为 store 单属主，把「分类浏览」从侧栏挪到主区（或反向）只是容器声明搬家。**本文每一条禁止项，都是在为将来的删除铺路。**
