06 · 思路总览——「装了就归它，卸了就退回」是怎么成立的 （布局抽象图：概念/数据流/主权，非高保真）

mockup 仅示意，真实实现走 var(--xxx) + ThemeEngine。四条铁律 → 一次解析的完整旅行 → 两处去硬编码 → 主权三层。对应 00 §四/§五。

一、四条铁律全案的宪法——每个任务都能回溯到其中一条

①
判定归壳，呈现归插件
「这是不是二进制」「.pdf 谁能开」由壳一处回答；「弹什么、画什么」由拿到文件的插件自己画。壳永远不画文件内容。
②
壳不认识任何插件 id
现在壳里刻着 DEFAULT_TAB_TYPE="editor" —— 换掉编辑器墙上的名字就指向空屋。改成角色挂牌：谁声明谁参选，壳只认牌子不认名字（T7）。
③
插件只声明，不耦合
抢默认 = 声明 fileAssociations；做右键项 = 声明 menus.fileContext＋命令。装/卸/换任何一只，壳与别的插件零改动。
④
主权三层（D7）
壳持用户覆盖表＝户口本；插件只有提名权；文件树只有执行权。插件永不自封默认——微软/Adobe/第三方的 N 只 PDF 阅读器和平共存的前提。

二、一次解析的完整旅行点「下一步」看每步发生在哪一层 —— 三入口（文件树/搜索/OS 双击）走的是这同一条路

OS 层 / 入口

Windows 右键 · 双击 · 文件树 · 搜索（拖拽不在归一范围，02 E18 改判）
安装器静态关联（随包文本类） 运行期同步（装/卸阅读器时增撤，T6）
➜

声明面（插件 plugin.json）

插件的「报名表」——纯数据
fileAssociations: [{extension, displayName, role?}] menus.fileContext: 右键贡献项＋when
➜

判定面（壳 · 一处真相）

resolveOpenTarget —— 三入口同吃
① 覆盖表 workbench.fileAssociations（D1） ② 声明表：激活序优先＋字典序 ③ 角色兜底：role="text-fallback"（T7） isBinary 判定（T1）也在这层
➜

呈现面（各插件自己画）

壳只给 tab，内容归插件
阅读器：自己的视图 editor：文本 ／ 二进制提示块＋toast（T1） file-tree：选择器 UI（T2）

三、两处去硬编码——before / after

✕ BEFORE —— 壳里刻着插件名
DEFAULT_TAB_TYPE = "editor" tabs.ts:14
syswrite.cpp: 13 个手写扩展名 vs editor 声明 45 个——已经漂移
卸载/替换 editor ⇒ 兜底指向空屋；清单与声明两张皮，全靠人肉对账（违反归一化）。
✓ AFTER —— 壳只认牌子与声明
resolveFallbackTabType() = 查 role:"text-fallback" 挂牌者
构建期收割随包件 fileAssociations → 生成安装器清单
第三方编辑器挂牌即可参选兜底（用户挑中才接管）；清单从声明机械生成，漂移在机制上不可能（T7/T6）。

四、主权三层——为什么插件不能自己抢默认

壳＝户口本持有者

用户覆盖表 workbench.fileAssociations 住在这里——它背后是用户的意志。
✓ 仲裁、记录、兜底、toast 提醒

插件＝报名者（N 家并存）

声明 fileAssociations = 把名字写进候选名单；声明 role = 举手说「我也愿意兜底」。
✓ 提名、出现在选择器、被用户挑中
✗ 自封默认 · 改覆盖表 · 顶替别人

文件树＝快递员（执行者）

单击文件 → 查解析 → 开标签。它不裁定任何事，换一套文件树插件机制照跑。
✓ 调解析、渲染右键菜单与选择器
✗ 决定谁是默认 · 私藏第二套规则
frame-note——VS Code 对标：微软/Adobe/第三方的 pdf 插件谁都能装，但默认永远是用户的 workbench.editorAssociations 设置——插件没有「自封默认」的 API，这正是 N 家共存不打架的原因（D7 的原型）。两只编辑器同时挂牌不写新规则：激活序优先＋提示＋选择器并列（E3），极客单机替换场景被同一机制天然覆盖。牌＝提名不是夺权——这是「万物皆可插件」与「插件绑架用户」的分界线。
