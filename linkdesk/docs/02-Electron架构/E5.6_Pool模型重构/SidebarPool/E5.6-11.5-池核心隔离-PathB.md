# E5.6#11.5 池核心隔离——Path B 根治

> **状态：** 设计完成，待执行。
> **父任务：** Phase 3 SidebarPool 迁移（E5.6#11 的后续——根治性重构）。
> **依赖：** E5.6#11（侧栏容器搬迁已完成，fix7/fix8 补丁已打）。
> **目标：** 池不 import `@src/core/*` 任何模块。所有核心服务走 `window.linkdesk.*`。壳是唯一真相源。池是纯布局渲染器。

---

## 0. 由来——为什么有 #11.5

E5.6#11 落地后，SidebarPool 可以渲染侧栏容器。但池侧代码（`pool-main.tsx` + 插件）大量 import `@src/core/*` 模块——这些 import 在池的独立 WebContentsView JS 堆里创建了**模块级单例的独立副本**，与壳侧真相源完全脱节。

这个偏离被 4 个 bug 暴露出来：

| Bug | 现象 | 根因 | 临时补丁 |
|:--|:--|:--|:--|
| fix7 | 图标点击坍塌 ≠ ◀ 按钮坍塌 | 池渲染依赖 `isSidebarVisible`（壳状态），两条坍塌路径改壳状态的 side effect 不同 | `lastSidebarViewRef` + width-based collapsed |
| fix7 | marketplace 卸载命令找不到 | 池侧 CommandRegistry 是空实例——命令只在壳注册。`executeCommand` 返回 `undefined`（不抛错）→ preload `.catch()` fallback 死代码 | `hasHandler` 检查 → 手动抛错 |
| fix8 | "待安装"永远 0 | 池侧 `onPluginLifecycleChange` 是独立 Emitter 实例——壳 fire 不触发池订阅 | `events.on("plugin-lifecycle:changed")` → 手动 fire 本地 emitter |
| **当前** | 卸载串口监视器→重启→侧栏仍显示 | 池侧命令路由路径 args 对齐问题（`token` 吞掉 `ctx`）+ 清理可能不持久化 | **未修——Path B 自然消灭** |

**这四个 bug 的表面原因各不相同，但根因是同一个：壳和池各有 `@src/core/*` 模块的独立实例。** 不是巧合——是架构偏离。每个新 plugin import 新 core 模块都可能踩坑。

## 1. 根因分析

### 1.1 模块级状态双重存在

```
壳 JS 堆                                    池 JS 堆 (独立 WebContentsView)
┌──────────────────────────────┐           ┌──────────────────────────────┐
│ CommandRegistry (真)         │           │ CommandRegistry (空)          │
│  ├ "explorer.rename" ✅     │           │  ├ (空——命令只在壳注册)        │
│  ├ "marketplace.uninstall" ✅│           │  │                             │
│  └ ...                       │           │  └ 依赖 hasHandler+throw→IPC   │
│                              │           │                              │
│ ConfigurationService (真)    │           │ ConfigurationService (半空)   │
│  ├ _userSettings: {...} ✅  │           │  ├ _userSettings: {} ❌        │
│  └ _changeListeners: Set ✅ │           │  └ 依赖 applyRemoteConfig      │
│                              │           │                              │
│ WorkspaceService (真)        │ ╳ IPC ╳  │ WorkspaceService (空)         │
│  ├ _folders: [...] ✅       │           │  ├ _folders: [] ❌             │
│  └ _onDidChangeFolders ✅   │           │  └ 依赖 triggerFoldersChanged   │
│                              │           │                              │
│ onPluginLifecycleChange (真) │           │ onPluginLifecycleChange (空)  │
│  ├ 壳 fire → 消费者执行 ✅   │           │  ├ 无人 fire → 消费者死 ❌    │
│                              │           │  └ 依赖 events.on bridge       │
└──────────────────────────────┘           └──────────────────────────────┘
```

**本质：两份"真相"。壳是真，池是空的仿品。** 桥（`events.on` + 手动 fire 本地 emitter）是在这两份之间手工同步。

### 1.2 为什么偏离了 E5.6 的设计本意

E5.6 设计文档 [01-Pool模型设计.md](../01-Pool模型设计.md) 明确：

> "池被动渲染——不知道'世界为什么长这样'，只接收布局快照。"

但落地时：
- `pool-main.tsx` import 了 5 个 `@src/core/*` 模块
- 池的 `PluginComponent` 通过 `import.meta.glob` 加载插件——插件又 import `@src/core/*`
- 池没有专用的 preload——复用了 `preload-plugin.ts`，继承了 20+ 个不需要的 API 命名空间

## 2. Path B 方案——"池是真正的哑渲染器"

### 2.1 核心原则

```
Pool 的唯一职责：接收 PoolLayout JSON → 渲染 React 组件。
Pool 的唯一 API 入口：window.linkdesk.pool（布局）+ window.linkdesk.events（事件）+ window.linkdesk.commands（命令）。
Pool 不 import 任何 @src/core/* 模块——这些模块在池的 JS 堆里不存在。
```

### 2.2 对比

| | E5.6#11 落地（偏离） | Path A（桥接——whack-a-mole） | Path B（这一次） |
|:--|:--|:--|:--|
| 池 import @src/core | 5 个模块 | 5 个模块 + 每个新 bug 可能新增 | **0 个模块** |
| 池 preload | 复用 preload-plugin.ts（20+ API） | 不变 | **专用 preload-pool.ts（3 API）** |
| 命令执行 | 本地先查 hasHandler → 抛错 → IPC | 同上 + 新桥 | **一律 IPC 到壳** |
| 配置同步 | useEffect bridge | 同上 + 新 key 的桥 | **不存在——池不读配置** |
| 生命周期同步 | useEffect bridge | 同上 | **事件走 preload 自动桥接** |
| 归一化 | ❌ 两套机制 | ❌ 桥就是第二套机制 | ✅ **一套机制：window.linkdesk.*** |
| 新插件安全性 | ❌ import 新 core 模块可能静默失败 | ❌ 需要加新桥 | ✅ **不存在就抛错——fail-fast** |
| 死代码 | 池侧 4 个空模块实例 | 更多 | **0** |

### 2.3 架构全景

```
┌─────────────────────────────────────────────────────────────────────┐
│                          主进程 (main)                               │
│  ipcMain: commands:execute, config:get, plugins:call, ...           │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │ IpcBridge: 中转站。收池的 IPC → 转发到壳。                     │  │
│  │   池调 lk.commands.execute("foo", args)                       │  │
│  │     → ipcRenderer.invoke('commands:execute', 'foo', args)     │  │

│  └──────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
          │                                    │
    ┌─────▼──────┐                      ┌─────▼──────┐
    │ 壳 (shell)  │                      │ 池 (pool)   │
    │            │                      │            │
    │ 真相源：    │    PoolLayout JSON   │ 哑渲染器：  │

### 2.4 数据流——两种方向

**壳→池（布局推送）：**
```
壳 usePoolSync → poolApi.pushLayout(zone, layout)
  → preload-shell pool.pushLayout()
  → 主进程 pool:push-layout handler

## 4. 详细设计

### 4.1 `preload-pool.ts`——池专用 preload

**设计原则：** 插件是完整应用程序——在池内运行时仍需完整 `window.linkdesk.*` API。池 preload 暴露与 `preload-plugin.ts` **相同的 API 命名空间**，仅移除 per-tab 概念（`pluginInstance`/`pluginViews`/`notifyReady`）。安全边界不在 API 表面——在每个调用走 IPC 到壳校验执行。

```
暴露的 API 命名空间（= preload-plugin.ts − per-tab 概念 + 池专属）：
  window.linkdesk.pool            — onLayout(cb), ready(), sidebarAction(action)  [池专属]
  window.linkdesk.events          — on(channel, cb), emit(channel, data)
  window.linkdesk.commands        — registerCommand(id, handler) [🆕 池侧注册], unregisterCommands(pluginId), executeCommand(id, ...args), getCommands()
  window.linkdesk.configuration   — get(key), onChange(key, cb)
  window.linkdesk.workspace       — getFolders(), getActive(), setActive(uri), openFolder(), addFolder(path), removeFolder(path), onDidChangeFolders(cb), onDidChangeActiveWorkspace(cb)
  window.linkdesk.filesystem      — listDir, readTextFile, readBinaryFile, writeTextFile, createDir, exists, copy, remove, watch, stat  [文件树大量使用]
  window.linkdesk.tabs            — create, openOrFocus, close  [文件树→编辑器]
  window.linkdesk.dialog          — confirm, open  [删除确认/打开文件夹]
  window.linkdesk.contextKey      — set(key, value), getValue(key)  [explorer context keys]
  window.linkdesk.clipboard       — writeFileList, readText, writeText  [复制文件路径]
  window.linkdesk.pluginState     — get(pluginId, key), set(pluginId, key, value), onChange(pluginId, key, cb)  [持久化展开URI]
  window.linkdesk.menu            — registerItems(menuId, pluginId, items)  [上下文菜单+菜单栏]
  window.linkdesk.shell           — showItemInFolder, openInTerminal  [系统操作]
  window.linkdesk.path            — normalize, basename, dirname, join  [路径工具]
  window.linkdesk.fileAssociation — getPluginFor(ext)  [🆕 扩展名→插件ID——IPC到壳]
  window.linkdesk.search          — searchFiles(opts)  [🆕 文件搜索——IPC到壳/主进程]
  window.linkdesk.decorations     — getDecoration(uri), onDidChange(cb)  [🆕 Git状态装饰]
  window.linkdesk.encoding        — detect(buffer), decode(buffer, encoding), encode(text, encoding)  [🆕 编码检测]
  window.linkdesk.notifications   — show(opts)  [通知]
  window.linkdesk.viewContainer    — registerView(pluginId, containerId, descriptor), getView(viewId)  [🆕 归一化——池侧no-op]
  // 注：lk.viewContainer 在池 preload 中是 no-op（池不注册视图——壳的 loader.ts 做）。
  // 在壳 preload-shell 中直接调 ViewContainerService。插件代码完全相同——无 _isShell 守卫。

不暴露的 API（仅 per-tab 概念——E5.6 已废弃）：
  pluginInstance, pluginViews, notifyReady, getFilePath
```

**命令注册——Path B 关键设计：**

池内插件需要注册 ~30 个命令（file-tree ~20 + marketplace ~5 + serial-monitor ~5）。这些命令的 handler 引用池侧 DOM/React state——不能在壳执行。因此池 preload 在自身 contextBridge 隔离世界内维护 `Map<string, Function>`：

```typescript
// preload-pool.ts — 池侧命令注册表
const _poolCommands = new Map<string, Function>();

const commandsObj = {
  // 注册池侧命令——handler 来自 renderer（React 代码），
  // contextBridge 自动代理函数引用
  registerCommand: (id: string, handler: (...args: any[]) => any) => {
    _poolCommands.set(id, handler);
  },

  // 注销某插件的全部命令
  unregisterCommands: (pluginId: string) => {
    for (const [id, h] of _poolCommands) {
      // 约定：命令 ID 格式为 "pluginId.commandName"（如 "explorer.rename"）
      if (id.startsWith(pluginId + ".")) _poolCommands.delete(id);
    }
  },

  // 执行命令——先查池侧注册表，未找到则 IPC 到壳
  executeCommand: (id: string, ...args: any[]) => {
    const handler = _poolCommands.get(id);
    if (handler) {
      return Promise.resolve(handler(...args));
    }
    // fallback——壳侧 CommandRegistry
    return ipcRenderer.invoke('commands:execute', id, ...args);
  },

  getCommands: () => [..._poolCommands.keys()],
};
```

**为什么池侧需要命令注册表：**
- 文件树的 20 个命令（explorer.rename/delete/newFile...）操作池侧 DOM/fileTreeModel/React state
- 命令 handler 是函数闭包——引用池侧 React refs/DOM。壳无法执行
- 壳侧命令（marketplace.uninstall 等）仍走 IPC——executeCommand 的 fallback 路径

**事件系统——双向：**

```typescript
// preload-pool.ts — events：emit 走 IPC 广播，on 收壳转发
const _eventHandlers = new Map<string, Set<Function>>();

const eventsObj = {
  on: (channel: string, cb: Function) => {
    if (!_eventHandlers.has(channel)) _eventHandlers.set(channel, new Set());
    _eventHandlers.get(channel)!.add(cb);
    return () => { _eventHandlers.get(channel)?.delete(cb); };
  },
  emit: (channel: string, data: any) => {
    // 池→壳：IPC 到主进程→广播到壳+其他 Pool
    ipcRenderer.send('events:emit', channel, data);
  },
};

// 接收壳广播（模块顶层——防竞态）
ipcRenderer.on('pool:broadcast', (_event, channel: string, data: any) => {
  _eventHandlers.get(channel)?.forEach(cb => { try { cb(data); } catch {} });
});
```

**壳侧需广播的事件频道（IpcBridgeHandler 发送到 poolView）：**

### 4.7 🔧 PaneSash 卡位 1/4, 1/2——独立 bug 修复

**现象：** 侧栏 section 拖拽时卡在 1/4、1/2 位置，拖不到预期高度。

**根因：** `PoolSectionStack.tsx` 中 `handleSashDrag` 两处缺陷：

1. `offsetHeight ?? 200` fallback——当 `offsetHeight` 为 0 或 undefined 时，200 的硬编码 fallback 导致高度跳变到一个"卡位"值。1/4 窗口 ≈ 200px、1/2 窗口 ≈ 200px+。

2. `setViewHeights` 不展开前值——`setViewHeights({ [idx]: newValue })` 替换整个对象→其他 view 的高度丢失→下次拖拽时前值已错。

**修复：**

```typescript
// PoolSectionStack.tsx handleSashDrag

// 修复 1：offsetHeight 为无效值时拒绝更新——不用 200 硬编码 fallback
const handleSashDrag = useCallback((idx: number, deltaY: number) => {
  setViewHeights(prev => {
    const currentHeight = prev[idx] ?? containerRef.current?.children[idx]?.offsetHeight;
    // 修复：无效高度→拒绝更新。不 fallback。
    if (!currentHeight || currentHeight <= 0) return prev;
    
    const newHeight = Math.max(
      viewMetas[idx]?.minHeight ?? 60,  // effectiveMinHeight
      currentHeight + deltaY
    );
    
    return { ...prev, [idx]: newHeight };  // ✅ 展开前值——其他 view 高度不丢
  });
}, [viewMetas]);
```

**验收：** 拖拽 PaneSash 到任意高度都平滑跟随，无卡位。重启后高度持久化正确。

### 4.8 串口监视器卸载残留——Path B 自然消灭

**现象：** 卸载串口监视器→重启→侧栏仍显示串口监视器。

**根因分析（三层）：**

1. `loader.ts` `uninstallPlugin()` (lines 1178-1234)：`filesystem.copy(src, dest)` → `filesystem.remove(src)`。Windows Vite 文件锁可能导致 `remove` 静默失败→文件同时存在于两处→重启时 loader 在原始位置找到插件→重新加载→视图注册→侧栏显示。

2. `lifecycle.ts` `initLifecycleConsumers()` (line 111-113)：`ViewContainerService.unregisterAll(pluginId)` 通过动态 `import()` + `.catch(() => {})` 调用。若动态 import 失败→ViewContainerService 永不清理→视图残留。

3. 池侧命令路由：池调用 `executeCommand("marketplace.uninstall", undefined, ctx)` → 池侧 CommandRegistry 空→查 hasHandler→抛错→preload .catch()→IPC 到壳。但 args 对齐问题（token 吞 ctx）可能导致壳侧 handler 收到的参数错误→部分清理步骤跳过。

**Path B 为什么自然消灭：**

- **原因 1+3：** 池侧命令一律走 `lk.commands.executeCommand()` → preload 检查池侧注册表（marketplace.uninstall 不在池侧）→ fallback IPC 到壳。壳侧 CommandRegistry 收到完整 args→执行 `uninstallPlugin(pluginId)` → 壳的完整清理流程（copy → remove → cachePluginMetadata → onWillUninstall.fire → unregisterViewPlugin → loadedPluginIds.delete → onDidUninstall.fire）。**一切在壳侧执行——不存在池侧空注册表/args 对齐问题。**

- **原因 2：** `ViewContainerService.unregisterAll()` 在壳侧执行（壳的 lifecycle.ts 消费者）——动态 import 在壳的 JS 堆中，不涉及跨上下文。`.catch(() => {})` 仍存在但影响面不同——壳内动态 import 失败概率远低于跨 WCV。

- **原因 1 的文件锁问题：** 和隔离无关。若 `filesystem.remove()` 在 Windows 上静默失败→文件残留。**需单独加固：** `uninstallPlugin` 中 `remove` 失败时 toast 警告用户手动删除。但这不属于 #11.5 范围——是 loader 独立 bug。

**🔥 结论：** 串口监视器卸载残留的 3 个根因中，2 个是隔离问题（Path B 自然消灭），1 个是 filesystem 鲁棒性问题（另修）。
