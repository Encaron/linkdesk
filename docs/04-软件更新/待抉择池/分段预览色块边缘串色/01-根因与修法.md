# 01 · 根因与修法（机制推导 ＋ 实测证据）

> 本件回答「**为什么**会这样」与「**改成什么**」。所有读数出自无头 Edge（151.0.4129.86 · DPR 1）对**真身 CSS** 的截屏取列均值，口径见 §五。

## 一、结论（一句话）

色块的渐变**按内边距盒（50×28）铺**、却被**铺进边框盒（52×30）**，而 `background-repeat` 默认是 `repeat` ⇒ 左右各被补上一条**平铺环绕列**（左＝图样末列、右＝图样首列）。内置主题的 `separator` 不透明，这两列被边框盖死；极光玻璃的 `separator` 是 `rgba(255,255,255,0.06)`，盖不住 ⇒ 环绕**透出来**，看着就是「最外两条竖条像素换了位置」。修法＝**让铺贴区等于边框盒**（基类加 `background-origin: border-box`）。🔴 **但「加 `background-origin`」这件事只有用长手才作数**：变体若用 `background` **简写**，会把 `background-origin` 一并重置回 `padding-box` ⇒ 那行白写。2026-10-06 实测的第一版正是这么白写的（与修前**逐像素相同**，见 §六）⇒ **真修 = 基类 `background-origin: border-box` ＋ 变体全部改长手**。

## 二、盒子几何：一个盒子，两个尺寸

产品链条上每一个环节都是**默认值**，四个默认值叠起来才成灾：

| 环节 | 值 | 出处 |
|:--|:--|:--|
| `box-sizing: border-box` | 全局 | `src/index.css:197`（`*,*::before,*::after`） |
| ⇒ 写 `width:52px; height:30px` ＋ `border:1px` 时 | **边框盒 52×30**、**内边距盒 50×28** | 色块规则 `.ldk-segment-preview` / `.settings-segmented-swatch` |
| `background-origin` | **默认 `padding-box`** ⇒ 铺贴区＝内边距盒 **50×28** | CSS 默认值，产品里没写 |
| `background-size` | **默认 `auto`**，渐变无固有尺寸 ⇒ 铺贴块尺寸＝铺贴区＝**50×28** | CSS 默认值，产品里没写 |
| `background-repeat` | **默认 `repeat`** ⇒ 50×28 的图样**平铺**填满整块绘制区 | CSS 默认值，产品里没写 |
| `background-clip` | **默认 `border-box`** ⇒ 绘制区＝边框盒 **52×30** ⇒ 比铺贴区宽 2px、高 2px | CSS 默认值，产品里没写 |

⇒ 净效果：图样在水平方向被复制成 `… k=−1 | k=0 | k=+1 …`，而 **x=0 那一列**落进 `k=−1` 的最后一列、**x=51 那一列**落进 `k=+1` 的第一列。竖直方向同理（被补上 1 行上、1 行下）。

## 三、为什么只有左右两列、上下看不出来

渐变是 `linear-gradient(90deg, …)`——**水平**渐变：

- **竖直方向**补出来的行与本体同色（第 0 行与第 27 行的颜色一样，往上往下补也还是它）⇒ **零视觉差**，所以上下边缘正常；
- **水平方向**补出来的列是**对侧的颜色**：左补的是「末列＝浅」、右补的是「首列＝深」⇒ 唯一可见的两条，正好是你说的「最边上两个竖条」。

## 四、为什么 `light` 看着正常：不透明边框就是遮罩

那两列画在**边框底下**（`background-clip: border-box`），再由边框上一层：

| `separator` 的 alpha | 结果 |
|:--|:--|
| **1.0（不透明）** | 边框把底下那两列盖死 ⇒ 四边都是一条均匀边框色 ⇒ **看不出来**（内置 light/dark 等 12 个配色） |
| **0.06 ~ 0.12（半透明）** | 边框＝「透出底下的渐变」⇒ 四边本该都透出渐变本色（看不出），**唯独左右两条透出的是对侧颜色** ⇒ 露馅 |

所以病根**不是玻璃**，是 **separator 的透明度**：任何写半透明 `separator` 的主题都会露，第三方主题同样。

**官方主题仓 15 个配色全表**（判据只有一条：不透明⇒盖住、半透明⇒露）：

| 主题配方 | 配色 | `separator` | 判定 |
|:--|:--|:--|:--|
| `theme-aurora-glass` | aurora | `rgba(255,255,255,0.06)` | 🔴 **会露** |
| `theme-panorama` | moonlight | `rgba(255,255,255,0.12)` | 🔴 **会露** |
| `theme-pill` | bubble | `rgba(214,51,108,0.10)` | 🔴 **会露** |
| `light`（内置） | light / dark | `#E8E8E8` / `#474747` | ✅ 被盖住 |
| `theme-mint-soda` | ×4 档 | `#EDE5DD` / `#DCE8ED` / `#E4DED6` / `#DCE8DC` | ✅ 被盖住 |
| `theme-songti` | paper | `#E8E2D6` | ✅ 被盖住 |
| `theme-terminal` | phosphor | `#162A24` | ✅ 被盖住 |
| `theme-twilight-forest` | ×4 档 | `#5A5646` / `#364540` / `#3E3648` / `#354A38` | ✅ 被盖住 |

⇒ **15 个配色里 3 个会露**（恰是 3 只玻璃型主题）。

## 六、修法（真修 CSS 原文 ＋ 已否决的 B 案 ＋ 四条禁令）

**真修（已落地 · `@linkdesk/ui` 0.2.50）**——基类加声明（加在**拥有 `border` 的那条规则**上，⛔ 不是加在 `--split` 变体上）＋ **变体全部改长手**：

```css
.ldk-segment-preview{       /* 壳/共享件：src/components/shared/segment-preview/SegmentPreview.css */
  /* …原有声明一字不动… */
  background-origin: border-box;   /* 铺贴块＝边框盒 52×30，无环绕列 */
}
/* 🔴 本件所有变体一律用长手，⛔ 不许用 `background` 简写：
 *   简写会把 background-origin 一并重置回 padding-box ⇒ 基类那行白写。 */
.ldk-segment-preview--split{
  background-image: linear-gradient(90deg, var(--tone-surface-deep) 50%, var(--tone-surface-light) 50%);
}
.ldk-segment-preview--accent{
  background-color: var(--accent);
}
```

**为什么加在基类**：**背景铺设几何是「盒子」的属性，不是某一种变体的属性**。加在基类上，`--split`（渐变）与 `--accent`（纯色）同时正确（纯色无边距差、加了也无影响）；加在变体上则将来任何新的渐变变体都会重新踩坑。
🔴 **而「加在基类」能成立的前提是变体不写简写**——简写的重置作用与「声明住在哪条规则」无关，它只认**顺序**：产品里基类在前、变体在后 ⇒ 变体简写抹掉基类那行。⚠️ 本夹 05 图里那枚 `.fix` 之所以当年看着有效，是因为它在页面样式表里排在 `--split` **之后**（后写者胜）——**同一份 CSS、不同顺序，结论相反**。故：**声明住基类 ＋ 变体用长手，两条一起才成立**。

**B 案（对照，⛔ 不推荐）**：`background-repeat: no-repeat`——环绕列没了，但边框那 1px **没有内容可铺** ⇒ 露出底下的面板色（实测 `#1e252d`，浅底上更明显）。脏边不是消失，是**换了个颜色**。

**⛔ 不许的四种改法**：

1. ⛔ 改 `separator` 的透明度/颜色来「盖住」它——那是把玻璃主题的设计意图拿去填坑；
2. ⛔ 改成 `background-size: 100% 100%` 之类去「凑」——`background-origin` 才是那个语义正确的开关，用 size 凑会留下 `background-position` 的隐式依赖；
3. ⛔ 在变体里用 `background` **简写**（`background: linear-gradient(…)` ／ `background: var(--accent)`）——它会静默重置 `background-origin`，**修了等于没修**（0.2.49 的前车之鉴，逐像素证据见 §五之二）；
4. ⛔ 只改一处、漏掉另一处——修前共有**两份拷贝**（壳共享件 ＋ 插件私有）。✅ 归一化后插件私有那份**已整删**（1.0.40），今天只剩共享件一处；**⛔ 别再去找第二份源文件**（`packages/linkdesk-ui/dist/index.css` 是编译产物，`ui:build` 自动重生）。

## 七、落位判据（为什么这件不该拖成「归属」问题）

按 [《新能力设计流程》§十](../../../开发管理/新能力设计流程.md) 的**判据 A / 三问 Q1–Q3** 对本案：

| 问 | 本案答案 |
|:--|:--|
| **Q1 它消费的是不是宿主声明？** | 是——这枚色块是**宿主 schema 里 `app.accentSource` 选项的视觉语义**（「跟随主题配方」长什么样由主题 token 决定），不是插件自有的业务数据 |
| **Q2 消费宿主声明的控件该住哪？** | 住**壳或 `@linkdesk/ui` 共享件**（判据 A）——共享件 `SegmentPreviewSwatch` **早已存在**（随 `@linkdesk/ui` 发 npm） |
| **Q3 那插件为什么自己有一份？** | ✅ 已查明（2026-10-06 实测）：这枚原子正是 2026-10-03《设置控件-词表正典与共享化》**阶段 3.2 从 `toneControls.tsx` 抽出来的**（`SegmentPreviewText` / `SegmentPreviewSwatch` 进 `@linkdesk/ui`，已发 npm；`ui-surface.json` 记 `since: "0.2.40"`），该案 01 §112-113 的**终态表**也写明 tone 两件「只搬预览原子、handler 留设置仓**薄绑定**」。⚠️ 但**插件全仓零引用这两枚原子**（grep 为空）、`toneControls.tsx` 仍自画 `settings-segmented-swatch` ⇒ **抽的那半做了、接的那半没做**，而该案未清尾账只剩 4.2／5.3（宿主解好面＋删 fallback）⇒ 这一步**谁也没登记**。🔴 当时没换的候选原因是兼容面：两枚原子要**壳 ≥0.2.40／ui ≥0.2.37**，而插件 `minAppVersion` 那时是 `0.2.32` ⇒ 静态具名 import 会在旧壳上 link-time 崩（该案 5.1 正是为此走了 `sharedUi.ts` 的 `pick()` 双轨） |

⇒ **✅ 本案已按你的第 2 条令收口（D1＝B）**：插件改吃共享件、私有 CSS 两族整删（1.0.40）；上一条担心的兼容面**今天两条前提都已不成立**——
1. 插件地板已抬到 **0.2.52**，而所用共享件导入名的 `since` 最高 `0.2.52` ⇒ **静态具名 import 天然安全**（`check-ui-min-app-version` 按静态具名导入算地板，这正是官方示例插件该有的形状）；
2. `pick()` **双轨已整层删除**——而且它本身就是错的：按**变量键**取值（`ns[name]`）会**逃过**地板账本，把插件真正依赖的共享面藏起来。

🔴 一并认账：**这不是「顺手归一」，是接一件已宣布完成的迁移的尾巴**（原子抽了、发了 npm、账上 3.2 ✅，插件却从未消费）——尾巴总账与「换插件不退化」验收见 [06](06-尾巴总账与验收.md)。
