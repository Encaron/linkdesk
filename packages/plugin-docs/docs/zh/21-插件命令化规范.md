# 21 — 插件命令化规范（让 AI、快捷键、命令面板走同一条路）

> 2026-09-28 · **一句话**：**界面上能做的每一件事，都该有一条命令**。
> 命令不是"给高级用户的快捷方式"，它是**动作的统一入口**——命令面板、快捷键、右键菜单、自动化与 AI 都从同一条路进来。
> 本文是**规范 ＋ 作者检查清单**；字段级细节在 [03-插件contributes规范](03-插件contributes规范.md) §3.1，运行期签名在
> [01-插件API契约](01-插件API契约.md)（`commands` 命名空间）。

---

## 一、为什么（壳只认命令）

**壳对插件零知识。** 壳不知道你是串口监视器还是便签板，它只知道"**有插件注册了这些命令**"。

所以「让 AI 能操作我的插件」不是一份申请、也不是一次接入——而是**你注册了命令，就自动被支持**：

| 你做的事 | 自动长出来的入口 |
|:--|:--|
| `contributes.commands` ＋ 池侧 `registerCommand` | 命令面板里多一项 · 快捷键可绑 · 右键菜单/顶栏/区块按钮可引用 · **AI 面（命令清单）里多一条可调命令** |

**反面**：只活在界面上的动作（悬停才出现的按钮、右键菜单项、双击行）**没有任何命令**——
对人没问题（他有手），但对快捷键、对自动化、对 AI 都是**不存在**：它们只能去模拟鼠标，而模拟鼠标有位移阈值、时序、坐标依赖，
换台机器、换个分辨率就可能静默失效。**一条命令是一行 JSON，一次鼠标模拟是一段不可靠的代码。**

---

## 二、两条腿（缺一不可）

| 腿 | 写在哪 | 写什么 |
|:--:|:--|:--|
| ① **元数据** | `plugin.json` → `contributes.commands` | id / title / category / when / **description** / **params** —— 这是**清单**，AI 读的就是它 |
| ② **真 handler** | 池侧代码（视图组件 `mount` 时） | `window.linkdesk.commands.registerCommand(id, handler, meta)` —— 这是**执行**，只存在于池渲染进程 |

```json
{
  "contributes": {
    "commands": [
      {
        "id": "demo-notes.addNote",
        "title": "新建便签",
        "category": "便签",
        "description": "新建一张便签并返回它的 id",
        "params": [
          { "name": "title", "type": "string", "description": "便签标题（省略 = 未命名）" }
        ]
      }
    ]
  }
}
```

```typescript
// 池侧：真 handler（组件 mount 时注册；unmount 时 unregisterCommands(pluginId)）
useEffect(() => {
  window.linkdesk.commands.registerCommand(
    "demo-notes.addNote",
    (title?: string) => createNote(title), // ← 与界面按钮调用**同一个**动作函数
    { description: "新建一张便签并返回它的 id" },
  );
}, []);
```

> ⚠️ **只声明不注册 handler** = 命令面板里有、点了没反应（no-op ＋ 诊断 warn）。
> 声明面给出的是**元数据**（placeholder），handler 才是真的能跑。
>
> ⚠️ **注册在视图 `mount` 里的命令（"视图态命令"）照样要写进 `contributes.commands`。**
> 没开过那个视图时，这类命令在壳注册表里**根本不存在** ⇒ 外部 AI 的 `describe` 看不到、`exec` 调不了；
> **声明面是壳侧唯一的可发现性来源**：壳从清单算出"已声明、尚未注册"那批，单列给 AI
> （`describe` 的 `commandsPending`，每条带"先开哪个视图"那一步），撞上时 `exec` 的 `EUNKNOWN`
> 正文也给同一步。⛔ 别指望 AI 自己"先撞一次报错 → 猜要开视图 → 再试"。（2026-09-29 壳侧落地）

---

## 三、命令要写全的四件事

1. **`id` 带自己的前缀**：`<pluginId>.<动作>`（如 `demo-notes.addNote`）。
   AI 与用户都靠**前缀**一次列出"这只插件能做什么"——不带前缀的 id 会被算到别人头上。
2. **`description` 写意图，不复述 id**。AI 选哪条命令**就看这一句**：写「清空当前会话的全部收发记录」，
   别写「clearSession 命令」。缺这一句，你的命令在 AI 眼里只剩一个 id。
3. **`params` 逐位写清**（`name` / `type` / `required` / `description`）。
   调用方照 `params` 拼 `executeCommand(id, ...params)`，**不必读你的源码猜参数**。
   ⇒ 也可以给**一个具名对象**（键名照 `name`）——壳侧在命令桥上按声明顺序展开（生长格 `AI#52` 已落地）。
4. **状态要能读回来**。命令改了状态之后，另有一条读的路（列表/查询命令，或 `configuration.get()`）——
   "做完验一遍"是自动化与 AI 的基本动作，没有读的路它只能盲目重试。

---

## 四、四条别做（都是真踩过的坑）

1. **⛔ 别让调用方绕开插件**。命令的 handler 必须落在**插件自己的状态链路上**（走你既有的 store/service）——
   绕过它直调底层 API，会出现「命令跑了、界面不知道」的不一致（侧栏灯不变、列表不更新）。
2. **⛔ 别把命令写成界面函数的复制品**。抽一个公共动作函数，按钮的 `onClick` 与命令 handler **调同一个**；
   复制一份的下场是两份行为慢慢分叉，而没有任何灯会亮。
3. **⛔ 别只留手势路径**。悬停按钮、右键菜单、双击**都要保留**（人用着顺手），但每一条背后要有命令——
   手势是**手感**，命令是**入口**，两者并存，不是替换关系。
4. **⛔ 别把隐式前置塞进命令**。前置条件用 `when` 表达、并在 `description` 里说清（"先有打开的串口"这类），
   不要依赖"当前正好选中了某个视图"——调用方看不见你的焦点状态。

## 五、作者检查清单（照着勾）

- [ ] 我把插件里**用户能做的动作**列了一遍（含只出现在悬停按钮/右键菜单/双击行上的那些）
- [ ] 每一条都有 `contributes.commands` 条目（`id` ＋ `title` 必填，`id` 带自己的前缀）
- [ ] 每一条都写了 `description`（一句人话，写意图——AI 就靠它选命令）
- [ ] 带参数的都写了 `params`（`name` 照 handler 实参名、`type` 四值、必填标 `required`）
- [ ] 每一条都在池侧注册了真 handler（`registerCommand`），且 `unmount` 时 `unregisterCommands(pluginId)`
- [ ] **视图态命令**（在视图 `mount` 里才注册的那些）也写进了 `contributes.commands`——没开视图时 AI 只能从声明面看到它
- [ ] 按钮/菜单项与命令 handler 调**同一个**动作函数（不是两份实现）
- [ ] 改了状态的东西，另有**读回来**的路（列表/查询）
- [ ] 自测：装进软件 → 命令面板里搜得到 → 命令清单里看得见 `description`/`params` → 调一次生效**且界面同步变化**
- [ ] 我在**没有鼠标**的情况下走过一遍这些动作（键盘/命令面板），确认每一步都到得了

## 六、边界（这份规范的射程）

- **本文治新插件**，不追溯已有插件：存量插件补不补、补到什么程度，**由各插件作者自己定**。
- 插件要不要业务动作命令化，**取决于作者**——本规范保证的是「**想被 AI 操作时，有标准做法**」，
  不是"所有插件必须命令化"。
- 生成新插件时脚手架会**自带命令注册样板**（见 [13-插件开发指南](13-插件开发指南.md) 的三档入口），
  本规范是它背后的判据；两者互补：一个是**默认就带**，一个是**写的时候知道该写什么**。
- `when` 只决定**命令在菜单/面板里出不出现**（以及快捷键是否触发），**不拦 API 调用**——
  别用 `when` 当权限控制。

## 七、常驻纪律（2026-09-29 立 · `AI#49`）

- 🔴 **这不是一次性交付**：此后**每个新功能 / 新插件**都必须满足「**① 每个用户动作至少一条非鼠标路径；② 业务动作注册为命令，且注册 meta 带 `description` ＋ `params`**」——壳侧的同一句话已进**壳仓库的硬约束 26**（内部工程规范，此处不指向）。理由：**破洞会随迭代重生**（AI 友好化系列的缘起，就是一个老功能里的隐藏门控卡住了 AI）。
- **机械自查两条**（写完跑一遍，⛔ 别肉眼过）：`npm run audit:plugin-commands`（**只报不拦**——报「有视图声明却零命令」与「整批缺 description」）· `npm run manual:build`（宿主命令手册索引的逐字节漂移门禁；插件命令**不需要**进它，运行期 `getCommands()` 查得到即可）。
- **验收同样与物理指针无关**：测命令走命令 / API（或 CLI / MCP），⛔ 不拿「截图 → 猜坐标点击」当验证手段；**只出现在指针下的面**（悬停按钮那类）用「**先取元素、再落到元素自身**」的元素锚定方式验——⛔ 不按窗口位置推算坐标（推算出来的坐标换个窗口设置就错位）。
- ⚠️ **三条实录坑**（2026-09-29 会话 13 验收踩到，写在这省后人一轮）：
  1. **注册时机**——在**视图组件挂载时**才 `registerCommand` 的插件，**没开过视图时外部 AI 在命令清单里看不到你的命令**（调了报 `EUNKNOWN`）⇒ 能在 activate 期注册就别拖到 mount（账 = 生长格 `AI#54`）。
  2. **参数形状**——`params` 是**具名**的，执行面**原先**只按**位置**透传 ⇒ 调用方照「具名对象」调会**静默无效**（`ok=true` 却没做事）。**已修**（生长格 `AI#52`）：命令桥那条缝（`exec` 与池内 `executeCommand` 共用）现在把**单个具名对象**按 `params` 声明顺序展开——位置平铺照旧可用，两种写法都对。⚠️ 展开的窄口：**恰好 1 个对象实参** ＋ 该命令**声明了 ≥2 个 `params`** ＋ 键名**至少命中一个**；`params` ≤1 的命令不展开（那个对象本就是它的合法实参）。
  3. **返回值**——handler **什么都不回**时，外部只看得到信封的 `ok:true`，于是「**跑了但没做事**」（目标不存在 / 前提不成立 / 参数缺失）与「**真做了**」在 AI 眼里**同形**，只能靠截图与反复试探去猜。**规矩**：命令要做事就**回一张回执**——做成了 `{ ok: true }`；**没做事但不是故障**回 `{ ok: true, noop: true, reason: "<字面量>" }`（例如 `"single-tab"` / `"max-depth"` / 目标不存在）；**这次调用本身有问题**回 `{ ok: false, noop: true, reason }`（例如缺参数 / 宿主没注册）。`reason` 必须是**可分辨的字面量**，⛔ 不用「其它」兜底。壳内置的两条分屏命令已按此立样板（生长格 `AI#55`）——**你的 handler 返回值就是 AI 读到的答案**。
