## 1. 为什么是"归一化基建"

用户的 10 准则去重后是 6 个轴：**归一化 / 低耦合高内聚 / AI 友好三层 / 插件独立·生态 / 整洁无死代码 / 健壮生存**。dsh 可借鉴清单 v2 的四大支柱全部命中这些轴，且互为正交：

| 支柱 | 归一化对象 | 一句话 |
|:--|:--|:--|
| 契约生成 | 壳↔池 wire 协议 | 每个 API 只有生成的契约一种写法——漂移在编译期死 |
| 可逆注册 | 生命周期 | 每个注册只有 disposer 一种退路——卸载必拆净 |
| 依赖编排 | 加载顺序 | 每个依赖只有 `requires` 一种声明——顺序框架算，不靠约定 |
| 工程纪律 | 门禁 | 重复/死代码/供应链风险有机械哨兵——不靠人眼 |

**共同主题 = "AI 不需要追踪"**（AI 友好第 3 层公式：你要的不是 AI 更聪明，是代码不给 AI 犯错的机会）。

## 2. 四大支柱设计总览

### 支柱 1：契约生成层——linkdesk.d.ts（Phase 4）

- **现状**：`window.linkdesk.*` 双面（preload-pool.ts / preload-shell.ts 的 exposeInMainWorld）+ `linkdesk-api.ts` 契约面 + IPC channel 双端 handler + mockLinkdesk.ts 第四面（dev preview）——两侧各自 typecheck，漂移靠文档约定抓。E5.7#97 已把 ambient any 收窄为 LinkDeskAPI 精确类型（欠账已还），但真问题仍在：① 契约是手写文件，双端实现对齐靠纪律无机械校验；② 插件作者无合法消费路径（插件侧 6 处运行时 + 1 处测试违规 `@src/core` 类型 import 实锤 2026-08-17）——本支柱就是这两个缺口的落地。
- **dsh 做法**：Typert 生成器——host 侧 `@Remote` 标注 → 生成 client 侧声明 → contracts-ready 门禁（契约未生成，client 编译不过）。双 ts.Program 互斥，契约包是唯一共享叶子。
- **E5.8 方案要点**：
  - 标注语法选型：装饰器不可行（TS 装饰器在 preload 上下文受限）→ 标记注释或显式注册表，Phase 4 开工时定
  - 生成物：`linkdesk.d.ts`（插件作者 import 获得编译期安全——VS Code `vscode.d.ts` 同款，第三方作者不必惊动壳作者）+ 两侧 handler 签名校验
  - 门禁接线：生成物纳入 tsc 链路，契约漂移编译期死
- **不做**：双 ts.Program 完全照搬（我们是三进程，不是 dsh 的双面）；Typert 的 Remote 运行期 codec 全套（E5.8 只做编译期契约 + **轻量运行期校验 #22.5**——2026-08-17 总体审视拍板：版本错配真实存在〔用户升级壳而 plugins 目录保留 / dev 热更新双端瞬时不一致〕，dev 断言 + 诊断面，非完整 codec 框架）。

### 支柱 2：可逆注册升级（Phase 2）

- **现状**：`RegistryBase` 已有"登记注销自动对称"（markPlugin + unregisterAll，插件卸载自动清理）——E4 Emitter Pattern 的 Registry 面。但：①事件订阅/定时器/useIpcEvent 等非 Registry 注册点无统一退路；②无逆序回滚；③无"为什么没加载"诊断面。
- **dsh 做法**：`ctx.effect()`——一切注册返回 disposer，卸载按注册**逆序**回滚；插件 Fiber 状态机 PENDING→LOADING→ACTIVE→UNLOADING→DISPOSED。
- **E5.8 方案要点**：
  - `RegistryBase` v2：register() 返 disposer + effect 登记器（逆序回滚）——markPlugin 机制归并
  - loader 生命周期状态机：加载失败/依赖缺失的原因可诊断（"插件为什么没激活"不再靠猜）
  - 卸载 = disposer 全量回滚——插件重装契约（"可卸载 ⇒ 可重装"）的机械保障
- **不做**：Cordis 的 Service/inject 跨进程解析（我们是 Electron 多进程，注册面各自归位）；HMR 热重载等价物（vite watch 有意排除 plugins/ 是既有决策）。

### 支柱 3：依赖编排（Phase 3）

- **现状**：插件间依赖无声明机制。加载顺序靠 loader 扫描序 + 零散约定。
- **dsh 做法**：`inject: ['tools']` 按名声明依赖（不 import 具体实现），依赖未就绪挂起 PENDING，依赖消失连带卸载、依赖回来自动重载；坏配置 fail-loud。
- **E5.8 方案要点**：
  - `plugin.json` 加 `requires` 字段（+ plugin.schema.json + PluginManifest + 文档）
  - loader 依赖解析：循环依赖检测 fail-loud；依赖未就绪 → PENDING 挂起（对齐支柱 2 状态机）
  - 依赖消失连带卸载 + 自动重载（对齐卸载契约）
- **不做**：运行时服务注入（我们是声明式贡献 + Registry 查询，不是构造器注入）；用户 patch 层（E6 约束，见档案第二梯队）。

### 支柱 4：工程纪律（Phase 1，先行）

- **jscpd**：重复检测入 check（60 token 起报 + `jscpd:ignore-start/end` 注释块豁免）——"一个 bug 多处出现"的土壤是复制粘贴，AI 生成代码的高发病。
- **knip**：死依赖/死导出/孤儿文件检测入 check——单人+AI 最易积累"改了一处另一处没人记得删"。
- **lefthook**：postinstall 自动装（不靠文档要求装）；pre-commit staged lint --fix + whitespace；pre-push typecheck。原则照抄 dsh："local checkpoints fast; CI owns the full matrix"——无 CI，pre-push 是最后防线。
- **供应链纪律（npm 适配版）**：dsh 的 allowBuilds 是 pnpm 10+ 专属——LinkDesk 用 npm，等价物 = `engines` + `.npmrc` `engine-strict=true`（锁 Node 版本带）+ package-lock 钉死 + 原生模块清单审视（serialport/electron install scripts 记录）。pnpm allowBuilds 记入"若切 pnpm"备注，不现在切。
- **顺带吸收（第三梯队）**：pushLayout 两条规则入协议注释；`docs/decisions/` 决策记录目录 + "非平凡改动必须落一篇"。
- **IPC 广播归一化（2026-08-16 E6#14 搬入，E5.8#6.5）**：serial/lsp/file 三 handler 改走 `IpcBridge.broadcast` + `ipc-audit.ts` 审计脚本入 check——消灭"新推送事件漏发"（E5.5 对照审计发现：手动遍历模式忘写 = 插件静默收不到数据）。与 jscpd/knip 同属"不靠人眼"门禁家族。
- **归一化全景审计（2026-08-17 总体审视立案，E5.8#6.6）**：5 唯一方式（`var(--xxx)` / `t()` / plugin.json 声明 / Registry / `getAssetPath()`）grep 实证清零——jscpd/knip 抓不到硬编码 hex/裸字符串，AI 友好第 3 层表格需机械审计闭环。

## 3. 边界——保留与不抄

**保留（身份）**：React 自由渲染、单 Pool（1 BrowserWindow + 1 WCV）、壳想池画、插件自由化、remember 权限模式（dsh 都没有）、Hot Exit 文件版备份。

**不抄**：日志派生 UI 全形态 / 每文件 100% 覆盖率 / Wine 门禁 / 双语 i18n 全家桶 / run-gates DAG 调度器（理由见档案 §3）。

## 4. Phase 依赖

```
Phase 0：归档与基线（串行——文档 + 分支）
Phase 0.5：用户补充修复（串行——目录归一化先行：Phase 1 门禁配置路径依赖归一化树；#0d.8 先于 Phase 1.5）
Phase 1：工程纪律（串行——先行，零架构风险，保护后续重写期）
Phase 1.5：IPC 广播归一化 + 归一化全景审计（E6#14 搬入——Phase 1 后）
Phase 2：可逆注册升级（串行——Phase 1 后；最大推翻）
Phase 3：依赖编排（串行——Phase 2 后，状态机之上）
Phase 4：契约生成（Phase 2 后即可，与 Phase 3 可并行；最大新建）
Phase 5：全量回归（最后）
```

> 🔥 **编号铁律**：计划任务用整数；用户后续补充用小数后缀（#45.6 同款）插在相关任务之后——线性插入，不清洗重排（E5.5 任务执行铁律）。
