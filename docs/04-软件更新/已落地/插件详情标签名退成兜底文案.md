# 已落地 · 插件详情页标签名退成壳兜底文案「插件详情」

> **已落地（2026-09-30 用户实机立案 → 当日查清 → 拍板「治本」→ 当日实现 ＋ 6 条回归用例；⏳ 未发版**——用户拍板「先不发版，到时候再攒几个更新点」，改动先在 dev 累积，随下一批一起 release）。
> **立案（用户实机提问，原话按大意记述）**：插件市场里，有些插件详情页的标签名是插件自己的名字（如某串口插件显示「Serial Monitor」），有些却退成壳文案「插件详情 / Plugin Details」——问是哪一侧、哪个方面的原因，并且「是和壳有耦合的插件才会显示吗」。
> **拍板**：**治本 = 壳侧补「第二名称来源」**（详情页标签名此前只有 viewRegistry 一条来源，而那条来源有登记门）；⛔ 不立刻发版，攒批。
> **归属**：软件本体（壳侧 `src/core/utils/tabIdentity.ts` 一处 ＋ 单测）——不涉任何插件、不涉 SDK、不涉契约、不涉配置；**插件侧零改动**。

## 一、根因：标签名只有一条名称来源，而那条来源有登记门

详情页标签名 = 创建那一刻算一次、之后落盘在 `tab.label`（`defaults.ts:32` → `getDefaultLabel`）。判定链只有一条来源：

```
getDefaultLabel(type, opts)                    src/core/utils/tabIdentity.ts
  └─ targetPluginId = opts.detailPluginId ?? opts.pluginId
  └─ plugin = getViewPlugin(targetPluginId)     ← 唯一名称来源：viewRegistry
       ├─ 命中 → t(plugin.manifest.name)        ✅ 真名
       └─ 未命中 → t(getMeta("plugin-detail").fallbackLabel) = 「插件详情」   ❌ 用户看到的那个
```

而 viewRegistry 有**登记门**（`src/pluginLoader/resolution/runtime.ts:272-278`）：只有 `manifest.entry`（有代码要跑）**或** `hasSidebarContainers(manifest)`（有侧栏容器）的插件才被登记。于是三类插件不在册：

| 不在册的一类 | 为什么 | 用户怎么撞上 |
|:--|:--|:--|
| **纯数据插件**（主题 / 语言包） | 它们的贡献点注册进 `ThemeRegistry` / `LanguageRegistry`，**根本不进 viewRegistry** | 市场「已装列表」/「随包列表」点一只主题或语言包 → 标签名是「插件详情」。全新安装最明显：六只出厂种子里 `lang-defaults`（1.0.37）与 `theme-defaults`（1.0.7）**都没有 `entry`、没有 `views`/`viewsContainers`**（实测包内 `plugin.json`），点开即「插件详情」，另外四只（editor / file-tree / marketplace / settings）有 entry，名字正常 |
| **本会话内被禁用** | 曾经在册，禁用时由 `registrationTracker.rollback(pluginId)` 回滚出册（`PluginLifecycle.onWillUninstall`） | 市场「已禁用列表」点任意一只 → 「插件详情」 |
| **上一次会话就已被禁用** | 同上，且**重启后连名字都不在索引里**（见下）| 禁用某插件 → 重启 App → 「已禁用列表」点它 → 「插件详情」 |

**壳本来就记着这些名字**（两处，按「离盘上真相多近」排）：

1. **manifest 索引**（`getManifestById`）——启动时 `readAllManifests` 水合，来源 `listAllPlugins` → `listPluginDirs`（逐根直扫 + **跳过隐藏名 ⇒ 跳过 `.disabled/` 坟场**）⇒ 覆盖**全部已安装插件**，纯数据插件在内。加载/装卸路径另会 `setManifestInIndex`（装）/ `forgetPluginIndex`（卸）。
2. **元数据缓存**（`getMetadataCache`，持久化 `app.pluginMetadataCache`）——`.disabled/` 坟场里的插件与已卸载插件都靠这份。它是 B2 fix 立的（卸载后市场仍要能浏览详情），`forgetPluginIndex` **刻意不碰它**。⚠️ **禁用不改住所**（只记名单、目录原地不动）⇒ 重启后该插件不在索引里，只在缓存里；而市场「已禁用」列表（`getDisabledPluginInfo`）正是**优先读缓存**、索引只作兜底。

**为什么以前没暴露（commit 考古，给「是早期考虑不周吗」一个交代）**：结论是**未覆盖的组合**，不是早期决策错误——详情页标签取插件名的分支（`146a4e3c6`，2026-09-08 E6#30.7b）与壳兜底文案（`0f434ec19`，2026-08-18）**各自都成立**，写的时候「详情页的主体」默认就是有代码的视图插件（当时种子里的插件确实都有 entry，纯数据插件虽然 2026-07 就存在，但它们的详情页当时没有入口）；2026-09-14 种子表改版（`1ed067788`，E6#101）把语言包与主题摆进「已装」页之后，这条组合才第一次有用户可见的入口。**同类前科**：图标栏也曾只收有 `entry` 的插件（E5.8#37.9.2.3 修，见 memory `entryless-view-plugin-icon-gap`）——「viewRegistry 是唯一来源，而来源有门」这个形状在本仓出现过不止一次。

## 二、改法（已落地）

| # | 改了什么 | 位置 |
|:--:|:--|:--|
| 1 | 新增第二名称来源 `lookupKnownName(pluginId)`——先 `getManifestById(pluginId)?.name`，再退 `getMetadataCache()[pluginId]?.name`，头注写清两处各覆盖谁、以及为什么必须两处 | `src/core/utils/tabIdentity.ts` |
| 2 | `getDefaultLabel` 在 viewRegistry 分支之后、`idValue` 兜底之前插一条：**仅 `isPluginDetailView(type)` 且 `targetPluginId` 有值**时问第二来源，命中即 `t(name)` | 同上 |
| 3 | 优先级注释重写（5 条：opts.label → viewRegistry → 壳已记的名字〔仅详情页〕→ identityField 值 → fallbackLabel）＋ `fallbackLabel` 字段注释改为「两条名称来源都没命中」 | 同上 |
| 4 | **作用域刻意收窄**：只有详情页吃第二来源。其余类型注册表未命中意味着「不是本插件」，拿 `type` 串当名字是语义污染——**有回归用例钉住** | 同上 |
| 5 | 6 条回归用例（驱动**真索引 / 真缓存**——`setManifestInIndex` / `forgetPluginIndex` / `cachePluginMetadata`，不 mock 模块）：数据插件命中真名 ／ `detailPluginId` 同路 ／ **viewRegistry 命中优先于索引** ／ 跨会话被禁用插件走缓存 ／ 两条来源都不认识 ⇒ 仍「插件详情」 ／ 非详情页不吃第二来源 | `src/hooks/useTabManager.test.ts` |

**⚠️ 自查发现并当场补上的一处漏洞（值得记）**：初版只补了 **manifest 索引**，并写了一条自认为成立的判据「禁用插件也在索引里（`listPluginDirs` 不跳 `.disabled/`）」——**这条判据是错的**：`listPluginDirs` 的循环明确 `entry.name.startsWith('.') → continue`，坟场整目录被跳过。所以初版只能修好「本会话内被禁用」的那一档，用户「禁用 → 重启 → 从已禁用列表点开」照样退「插件详情」。核对市场侧消费方（`getDisabledPluginInfo` 优先读元数据缓存）后补上第二步来源，覆盖面才真正闭合。**教训**：断言「某份索引覆盖 X」时，去读扫描函数本身，别读它某条注释的措辞。

**为什么不做别的**：

- **不改插件侧**（让纯数据插件也去写 `entry` / 声明侧栏容器来挤进注册表）：那是为壳的实现细节污染插件面——纯数据插件按设计就不该有代码与容器，改法是拿作者的合规换壳的方便。
- **不换兜底文案**（把「插件详情」改成别的字）：还是没答用户的问题（「这是谁的详情页」），只是把同一缺陷换个说法。
- **不给未安装插件补来源**：三处入口（已装/随包/已禁用）覆盖到的插件名字壳都有；未安装插件在壳内没有详情页入口（「探索」页的行点击自带 `label: name`，走的是 `opts.label` 优先，本来就对），不为不存在的路径加分支。

## 三、验收（dev 手测）

1. 市场「已装列表」点一只**主题**（`theme-*`）或**语言包**（`lang-defaults`）→ 标签名 = 该插件名，不再是「插件详情」。
2. 全新安装/清空用户数据后，点「已装列表」里的 `lang-defaults` / `theme-defaults` → 插件名（这条是原始报障场景：种子里的两只数据插件此前必退「插件详情」）。
3. 禁用某插件 → 不重启，从「已禁用列表」点它 → 插件名。
4. **重启 App 后**再从「已禁用列表」点它 → 仍是插件名（走元数据缓存那一档）。
5. 点一只**有 entry 的插件**（如某串口插件）→ 标签名不变（仍走 viewRegistry，优先级更高）。
6. 「探索」页点一只**未安装**插件 → 标签名 = 目录里的名字（它是插件自己传的 `label`，与本次改动无关，回归确认没被碰坏）。
7. 语言切到 en → 详情页标签名随 `t()` 解析（与既有行为一致，未改）。

## 四、边界与遗留

- **已卸载插件**：缓存里通常还有它（`status: "uninstalled"`），若将来给「已卸载」列表加详情入口，标签名直接正确，无需再改。
- **池侧 `<title>` 不做二次解析**：详情 tab 的 `pid = tab.pluginId ?? tab.type = "plugin-detail"`（详情页刻意不设 `pluginId`，避免污染 IconBar 高亮），`getViewPlugin("plugin-detail")` 未命中 ⇒ `resolvePoolTabTitle(label, undefined, t)` 原样返回 label。而 label 落盘时已 `t()` 过真名 ⇒ 显示正确；**语言切换后已存在的详情标签名不重解析**（与身份派生名同类，属既有行为），本次未动。
- **名称来源现在共三处**（viewRegistry → 索引 → 元数据缓存 → fallbackLabel），壳内再需要「某个已装插件的名字」时问 `lookupKnownName` 那两处，别各写一份名单。
