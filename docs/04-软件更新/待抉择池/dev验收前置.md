## 一、现象（2026-09-28 实测，两次代价）

1. **假阴性误判**：CDP 驱动改完一处壳侧逻辑后，`plugin-states.json` **已更新**（`collapsedViews = ["file-tree:search"]`）而池快照仍为 `[]`、点击毫无变化 ⇒ 判「修了没用」，回头又查一轮才发现真因是**运行中 dev 实例的 HMR 吃不到壳侧非组件模块的改动**；硬 reload 两个页面后同一操作立刻生效。
2. **一次性脚本爆炸**：这一件折叠验收写了 **17 个** scratch 驱动，每个只验一个方向，且各自都带「找 page target ＋ 走 React fiber 读 props」的前戏；换下一件又从头写。

## 二、根因

- ① 验收回路**缺「代码是否已生效」这一维**：只看现象，而现象的变化源有两个（我的改动 / 构建没更新），当场分不开 ⇒ 误判的代价是整轮白查。
- ② CDP 驱动**没有沉淀层**：每次都从零写脚本。「连哪个 target、怎么读池 props、菜单怎么弹」这套知识每次都重学一遍——对照记忆 `cdp-ui-automation` 有坑表，但那是**知识**，不是**可复用代码**。

## 三、修法（三件，全在开发侧）

1. **硬 reload 前置**：driver 第一步对所有 page target `location.reload()` 并等就绪——先把 HMR 的不确定性剥掉。
2. **构建握手**：验收开始时打印/校验构建哈希或时间戳（dev 服务可读），与现象读数并排记录 ⇒ 假阴性当场可辨。
3. **driver 库固化**：把一次性脚本收敛为一组语义助手（`openSection` / `collapseSection` / `readSections` / `readLayout` / `readPoolSnapshot`），放固定位置（`scratch/` 或 `scripts/dev/`；**是否入库待定**）。✅ **2026-09-28 裁决：入库**（`scripts/dev/`，进 git）——判据 2 要的正是**跨会话复用**，`scratch/` 易失（仓里就躺着 `_cleanup-manifest-*.txt` 这类随手产物），且有先例（`audit-nonnaming` 2026-09-17 从 `scratch/` 搬进 `scripts/`、同笔删原件）。
