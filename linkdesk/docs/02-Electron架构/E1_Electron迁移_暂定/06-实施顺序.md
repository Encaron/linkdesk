## 一、前置条件——迁移的唯一门槛

**满足以下全部条件后，下一个 commit 就是迁移。**

| # | 前置 | 内容 | 理由 |
|:--:|------|------|------|
| 1 | Phase 5.5 剩余 bug | 步 15 + G 类关键 bug 全部修完 | 迁移前代码必须稳定——带着已知 bug 迁移 = 新框架上旧 bug 叠加新 bug |
| 2 | `tsc --noEmit` + `vitest run` | 零错误 + 全测试通过 | 迁移前基线——确保迁移过程中能区分"原来就是坏的"vs"迁移搞坏的" |
| 3 | 旧 Phase 6（原计划底层加固）**尚未开始** | 一行旧 Phase 6 代码都没写 | 此时 Rust 投资最小（751 行）、插件最少（4 个）、无 add_child 代码、无 Rust 插件化代码。延迟一天，Tauri 耦合只增不减 |

**为什么不等旧 Phase 6 做完再迁移：** 旧 Phase 6a-c 会改 `StorageService.ts`、`useSendData.ts` 等文件——里面全是 `invoke()` 调用。先做旧 6a-c 再迁移 = 改了这些文件 → 迁移时每个 `invoke()` 再改一遍 `window.linkdesk.*` = 同一批文件碰两次。**先迁移再做 = `invoke` → `window.linkdesk` 在 E1 一次性改完 → 然后 E2 的新代码直接在正确的 API 上写，只碰一次。**

## 十、执行纪律

### 每步执行模板

```
1. 读相关代码（3 分钟 max）
2. 改（小步，尽量 < 30 行）
3. npx tsc --noEmit  → 零错误
4. npx vitest run    → 全过
5. git diff --stat   → 确认只动了该动的文件
6. git commit         → 一条 commit 只修一个概念
7. 告诉用户测什么    → 用户验证
8. 用户确认          → 下一步
```

### 不做的事

- ❌ 一口气修多个概念——一条 commit 只做一件事
- ❌ 跳过 tsc/vitest 直接 commit
- ❌ "顺手"加新功能——E1/E2 零新功能（E1 行为不变，E2 纯加固）
- ❌ E2 做完前开始 E3（多 WebView 需要 ErrorBoundary + 终端干净 + FileService 就绪）
- ❌ E3a 做完前开始 E3b/E3c（主题/语言跨进程广播需要多 View 底座）
- ❌ 在单 WebView 里先写文件树再迁 IPC——双倍工作量

## 十一、支线预案

| 触发条件 | 支线 |
|:--|------|
| E1 步 4 `window.linkdesk.*` 调用签名与 Tauri `invoke` 不兼容 | 逐文件对比参数格式——serial.openPort 的 `{portName,baudRate}` vs Tauri 的结构体 |
| E2 步 7 SerialContext 搬迁后 tsc 报循环依赖 | 先解耦再迁移——提取接口层到 `src/core/types.ts` |
| E2 步 13-14 FileService/WorkspaceService 时序冲突 | 比照 Phase 5f "懒加载时序歧义"修复——`setWorkspaceRoot` 在 App.tsx 最早同步代码中调用 |
| E2 步 16 Chord 和现有 KeybindingRegistry 冲突 | 单键绑定不受影响——Chord 是独立状态机 |
| E3 步 24 WebContentsView 创建失败 | 检查 Electron 版本 ≥ 30 + preload 路径正确 + contextIsolation: true |
| E3 步 25 IPC 性能瓶颈（串口数据高频推送） | 评估批量模式——多个数据包合并为一次 IPC 推送 |
| E3 步 29/34 主题浏览器和旧 ThemeEngine 冲突 | 先建 Registry → loader 兼容旧格式 → 再删旧代码 |
| E3 步 39 Profile 切换时五维验证失败 | 逐维独立 try/catch → toast 报告失败维度 → 回退到切换前状态 |
| 任何步 tsc 报错 | 停下来先修类型错误——不改逻辑 |
| 任何步 vitest 失败 | 停下来先修测试——可能是测试本身需要更新 mock |
