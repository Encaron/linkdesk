## 〇、一句话

**发现 = 拉目录 + 比版本，不轮询。** 作者发新版时更新 `marketplace.json` 目录条目，软件拉一次目录 + 一次 semver 比较就知道「谁有新版」。发现 ≠ 下载——发现零流量，下载只在用户点更新或自动更新勾选时才发生。

## 一、发现机制（软件如何捕获到插件新版本）

### 一·一、本质——目录式发现

不是逐个探测 GitHub Releases，也不是推送订阅。marketplace.json 就是「谁有新版本」的**单一索引**：作者发布 v1.1.0 → 更新自己目录里该插件的 `version` + `versions[]` → 软件下次拉目录，比对本地版本，捕获到差异。

### 一·二、数据流（发现全链路）

```text
┌─ 本地（已装现状）                          ┌─ 远端（权威目录）
│  PluginInstallService.getInstalled()       │  fetch marketplace.json（多源合并，01 §六）
│  → 每条 plugin.json.version               │  → 每条目 versions[0].version / 顶层 version
│     （localVersion）                      │     （remoteLatest）
└───────────────┬───────────────────────────┘
                ▼
        semver.gt(remoteLatest, localVersion)   ← 唯一判定
                │
        ┌───────┴────────┐
      true → 有更新      false → 无更新
                │
        ┌───────▼──────────────────────────────┐
        │  更新列表 → 三处去向（E6#33a/b）        │
        ├─ 通知中心铃铛           推一条「有新版本」通知（一次性 + 未读红点，非常驻计数）
        ├─ 市场内已装项「可更新」徽标  + 「禁用/卸载」旁升级入口（常驻，更新完成才消）
        └─ 详情页升级入口
```

### 一·三、比对判定（唯一规则）

| 项 | 规则 |
|:--|:--|
| 本地版本 | 已装插件 `plugin.json.version`（PluginInstallService 读出） |
| 远端最新 | `versions[0].version`（最新在前）；旧条目无 versions[] → 顶层 `version`（兼容，01 §三.2） |
| 判定 | `semver.gt(remoteLatest, localVersion)` → 有更新 |
| 版本相等 | 不提示（本地已是最新） |

### 一·四、触发时机（什么时候跑一次发现）

| 时机 | 行为 | 依据 |
|:--|:--|:--|
| 启动后延迟 ~10s | 后台拉目录 + 比对，幂等一次 | E6#33a |
| 手动刷新（市场内「检查更新/刷新」入口——铃铛点击 = 打开通知历史，非刷新动作） | 立即拉 + 比对 | E6#33a |
| 打开市场页 | 顺带检查——**受缓存 TTL 5 分钟节流**（01 §四），不是每次打开都拉 | 01 §四 |
| 自动更新插件（#33d 已勾） | 发现新版 → 直接自动下载替换（不经用户） | E6#33d |

**发现延迟 ≈ 分钟级**：作者更新 marketplace.json → GitHub raw CDN 缓存 → 本地 5 分钟 TTL。对「捕获新版本」场景足够，不需要秒级。

### 一·五、发现 ≠ 下载（边界）

- 发现：只比版本号，零网络下载、零文件写。
- 下载：用户点「更新」（E6#13c `update-download`）或插件勾自动更新（E6#33d）才发生。
- 所以「发现到更新」不消耗流量，铃铛/徽标只是提示。

## 二、细节决策（2026-08-29 定案——发现机制的完整逻辑）

### 二·一、幂等——不重复打扰（lastNotifiedVersion）

**问题**：发现 v1.1.0 后用户不点更新，是不是每次启动都响铃？
**定案**：`installed-plugins.json` 条目加 `lastNotifiedVersion`（可选字段，纯增量，PluginInstallService 唯一 owner，与 `autoUpdate` 同处）。发现逻辑：

```text
有更新（gt 成立）→ 比对 lastNotifiedVersion
  ├─ lastNotifiedVersion === remoteLatest → 已提醒过该版本 → 不响铃（幂等）
  └─ 否则 → 提示（通知中心铃铛推一条 + 市场内徽标）→ 写 lastNotifiedVersion = remoteLatest
更新成功 → 清 lastNotifiedVersion（插件本地版本已追上）
```
**「响铃/提示」载体 = 两条路各管各的（§一·二前注记）**：通知中心铃铛 = **每版本一次性推送**（未读红点 +1，看后清、消息留历史可关）；市场内徽标 = **常驻状态**（亮到更新完成才消）。`lastNotifiedVersion` 幂等管的是铃铛那条——同版不重复打扰。

### 二·二、多源冲突——取高者，回退不提示

**基准**：发现基于**合并后的 catalog**（E6#30c 多源合并产物），不是每个源单独查。同 id 冲突取版本高者（01 §六.4 已定）。
**补充**：源变化导致 remoteLatest **回退**（如源 A 删了高版本条目）→ 与本地版本比较仍成立时**按现 catalog 比对，不制造额外提示**——发现只看「现在目录里谁更高」，不记忆历史峰值。

### 二·三、无「内置排除」——出厂种子与第三方同规则（2026-09-06 塌平语义回扫改写，原 2026-08-29 二·三按旧 builtin/user 二类废弃）

出厂制造插件也会上架（E6#26b，市场真实条目）——**插件只有一类，无 core:true 排除更新之谓**（2026-09-05 塌平重定义：core:true 唯一语义 = UI 层无卸载入口，不定义任何更新/版本行为）。marketplace 更新检查覆盖**全部已装插件**——塌平单根 `{userData}/plugins/<id>`，**无 user/ 目录**。

- **「内置插件」不是类**：随壳带的那几只 = **首启种子**（boot 只在「无账本记录且目录缺失」时物化一次——此后任何不见了都 respect → removed 墓碑，永不自动复活，**2026-09-07 #18 种子一次化**），身份与第三方同格，可更新可降级；`core:true` = 纯 UI 藏钮（详情页无卸载入口，防误删——API/命令层可卸可禁，#18a）。
- **防铃噪不靠排除类**：出厂种子不勾 autoUpdate（§五 默认关）即静默——原定案「对标 VS Code 内置扩展不单独提示」要防的「一装收一堆铃」由此承担，无需按来源/类排除。
- **出厂种子内容随壳升级如何到达已装用户**（boot 同步 vs 走更新流）→ **#15n 判据**（E6 清单，未拍板；判据不看 core、看用户有无版本意图）。

### 二·四、prerelease / beta——默认忽略

**问题**：marketplace.json 放 v1.1.0-beta 时，`semver.gt("1.1.0-beta.1", "1.0.0")` = true 会提示 beta。
**定案**：发现**默认只比对稳定版**——`versions[]` 过滤掉 prerelease 版本（对标 VS Code 稳定渠道默认只看稳定版）。**自动更新（#33d）同样只看稳定版**，不自动装 beta。beta 走手动安装（版本下拉可选）。

### 二·五、条目消失 / 下架——不提示、不动本地

marketplace.json 删了某插件（作者下架）→ 本地还有 → 不提示更新，按旧版管理，**不卸载不降级**（尊重已装状态）。
**UI 反应（缝隙 G9/A1）：**
- 未装 → 从「探索」列表自动消失，无残留。
- 已装 → 「已安装」组照常保留（数据源 = 本地 pluginManager），无更新入口；详情页 marketEntry 缺失 → 显示本地信息 + 市场数据区隐藏。
- 卸载后想重装但已下架 → 探索列表无条目，**详情页历史记录保留**（「已下架」标识 + 此前目录信息），不给用户「凭空消失」的困惑。

### 二·六、更新失败回滚（G5）——原子切换

**更新 = 下载到 temp 目录 → 校验 → 原子 rename 替换 → 重载**。任一步失败 → 旧版保留不动 + error toast [重试]（09 §二）。**不存在「替换到一半崩了插件损坏」**——替换是整目录原子操作，失败即回滚。

### 二·七、自动更新运行中（G6）——照常替换，重启生效（2026-09-08 锚③改注）

插件正在被使用（有打开的标签页）→ **autoUpdate 照常 stage + 原子替换 + toast「重启生效」，不因开着跳过**。用户手动点更新不受此限（同机制）。

**改注理由（原「有标签页开着就跳过、下次启动补做」废止）**：① 更新引擎 `needRestart` 恒 true——更新从不即时生效，旧代码在内存里照常跑到重启，没有「打断用户」可言；② 原子替换（target→.bak→staged→rm .bak，同卷 rename）1.2-5 实机已证插件标签页开着也能成功替换——原要防的「文件占用冲突」在 Chromium 读后即关 + 同卷 rename 语义下不成立；③ 「跳过」反而造成死循环：用户一直开着该插件标签页 → 自动更新永不到达。被替换目录里正在跑的旧代码在重启前不受影响（05 §二·八 配置天然在外，更不碰）。

### 二·八、更新配置保留（G7）——配置由壳管，天然不丢

**插件配置/用户数据由壳统一管理**（config 注册表 + 插件专属存储，**不进插件安装目录**）→ 更新替换插件目录**天然不碰配置**。此契约由「可卸载⇒可重装」铁律支撑（重装后配置仍在）；更新更不丢。

### 二·九、选旧版 vs 自动更新（B3）——手动意图优先

用户版本下拉手动选了非最新版本 → 记 `pinnedVersion` → **自动更新跳过该插件**（尊重「停在旧版」的意图）；用户手动点「更新到最新」或版本下拉选最新 → 清除 pinned，自动更新恢复。

### 二·十、禁用插件点更新（F1）——状态保持

已装+禁用 → 用户点更新 → 更新完成后**保持禁用态**（更新只换文件，不改变禁用状态）。

### 二·十一、版本回退配置不兼容（F2）——装旧版确认

目标版本 < 当前已装版本（版本下拉选旧版）→ 确认弹窗「此版本较旧，配置可能不兼容」。**不拦，只提示**（用户有主动降级的自由）。`core:true` 的插件同规则可更新/降级——无内置排除（§二·三），仅 UI 不可卸载。

## 三、更新徽标（点 4 第一段）
- 已装插件有新版 → 「禁用/卸载」旁升级入口（图标 + 更新按钮）。
- 检测时机沿用 §一·四（启动 10s / 打开市场 / 手动刷新）。发现结果去向：**市场内升级入口 + 「可更新」徽标**（常驻，更新完成才消）+ **通知中心铃铛推一条**（一次性，§一·二树）。铃铛点击 = 看通知历史，不是刷新入口。
- 徽标计数走 `marketplace:updateBadge` 广播（已有，11-API §一 #11）。

## 四、版本下拉（点 4 第二段）
- `versions.length > 1` → 升级/安装按钮旁下拉列出历史版本（最新默认）。
- 作者保留旧版本 → 用户可装任意旧版（覆盖到 `{userData}/plugins/<id>`——塌平单根，无 user/ 目录，同 §二·三）。
- **选中机制**：下拉每条 = `{version, downloadUrl, publishedAt, changelog?}`——**选中哪条就拉哪条的 `downloadUrl`**（不是只下最新）。作者没在 `versions[]` 留旧版 → 下拉只有一条/不显示 → 用户装不了旧版（声明制，跟 GitHub 文件在不在无关）。
- **两场景**：未装插件 → 下拉 = 「装哪个版本」；已装插件 → 选最新 = 更新，选旧版（目标 < 当前）= 降级（F2 确认，§二·十一）。
- 无版本历史 → 不显示下拉（纯增量兼容）。

## 五、自动更新勾选（点 4 第三段）
- 插件级 **Opt-IN，默认关**——用户不勾，壳绝不自动动。
- `installed-plugins.json` 条目加 `autoUpdate: boolean`（PluginInstallService 唯一 owner，与 `lastNotifiedVersion` 同处）。
- 开启后：更新检查发现新版（§二·四 只看稳定版）→ 自动下载替换 + toast 通知（11-API §三 映射表「自动更新完成」）。
- 位置：详情页 action 区 + 已安装行。
- **勾选只在已装态显示**（G2，2026-08-29 定稿）：未装/挂起态**不显示**——`autoUpdate` 是已装条目属性，装完进入已装态才出现且**默认不勾**；mockup 帧 1「未安装」行已同步修订。
