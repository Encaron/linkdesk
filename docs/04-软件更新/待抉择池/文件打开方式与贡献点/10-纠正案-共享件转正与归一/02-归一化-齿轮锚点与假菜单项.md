## 一、事实：管理器里有**两处**齿轮，载荷形状本来就不一样

| 齿轮 | 谁渲染 | 载荷怎么传 | handler 读什么 | 位置 |
|:--|:--|:--|:--|:--|
| **竞争行齿轮** | 管理器自己弹 | 管理器建 items 时写 `commandArgs: [row.exts]`；`ContextMenu` **没传 `context`** | `args[0]` = 类型数组（或 `{exts}`） | `settings/…/FileAssociationsManagerView.tsx:161-169`，`<ContextMenu …:215-223>` |
| **插件卡齿轮** | 共享件 `PluginCard` 渲染 | 共享件**固定**送 `context={{pluginId}}`（管理器管不着） | `args[0]` = `{pluginId}` | `src/components/shared/plugin-card/PluginCard.tsx:150-157` ＋ `settings/…/fileAssociationsGearCommands.ts:86-118` |

**载荷机制（已核实，是设计而非巧合）**：`ContextMenu` 执行时走
`executeCommand(item.id, undefined, ...(item.commandArgs ?? []), context)`（`ContextMenu.tsx:309` / `:329`），
壳 handler 收到的 `args` = `[...commandArgs, context]`；`MenuItemDescriptor` 只有 `command` 字段（`contracts/linkdesk.d.ts:1320-1341`），
`ContextMenu` 内部把它映射成 `ResolvedItem.id`（`:189`）。⇒ **per-item 身份必须走 `commandArgs`，`context` 是整菜单共享的。**

这条口径**目前只散落在三处注释里**（`ContextMenu.tsx:100-103`、`MenuItemDescriptor` 文档串、`fileAssociationsGearTarget.ts:4-8`）。

## 二、任务卡 C2.1：把载荷律上升为**共享契约**（⛔ 不再靠口口相传）

- **改哪里（三处，缺一不可）**：
  1. `packages/plugin-docs/docs/22-menu-contribution-points.md` ＋ `docs/zh/22-菜单贡献点.md`（作者手册 · 中英同笔）——新增一节「载荷：`commandArgs` vs `context`」；
  2. `packages/plugin-docs/docs/05-ui-conventions.md` ＋ `docs/zh/05-插件UI写法规约.md`——共享组件消费侧写法（「共享件会固定送自己的 `context`，你的 handler 必须按它的形状读」）；
  3. 主案 `03-组件规格-按插件浏览-插件卡.md` §齿轮——把 `PluginCard` 的固定 context 写成**对外契约**（现在是实现在硬编码，文档没写，第三方作者踩坑）。
- **写什么**（照抄这条，逐字用）：
  > **菜单载荷律**：`ContextMenu` 的 `context` 是**整菜单共享**的；每一项的身份必须走 `MenuItemDescriptor.commandArgs`。
  > 壳 handler 收到 `args = [...commandArgs, context]`。共享件（如 `PluginCard`）会固定送**它自己的** `context`
  > （`PluginCard` = `{pluginId}`）⇒ 消费共享件齿轮的插件，handler 必须同时容忍 `args[0]` 是自己的载荷、
  > **末尾**是共享件的 context——⛔ 不要假设 `args[0]` 一定是你的数据（除非该槽位无共享 context）。
- **怎么验**：文档中英两版同笔改（翻译腿）；`grep -n "commandArgs" packages/plugin-docs/docs/22-menu-contribution-points.md` 命中。

## 三、任务卡 C2.2：「竞争（contested）」口径入档（用户第 5 条）

用户看到的「绿灯」是**竞争判定**的标记。口径必须落成文字，避免下个 AI 再解释一遍：

> **竞争判定**（唯一真相源 = 归一化扩展名）：
> ① 扩展名先归一（`normalizeExt`：去空白、转小写、去前导点；含空白 / `/` / `\` ⇒ 非法丢弃）；
> ② **同一归一化扩展名**上有 **≥2 个已启用插件**声明 ⇒ 该类型为**竞争类型**（管理器的绿灯 / 竞争区聚合格）；
> ③ 只有 1 个处理器 ⇒ **不算竞争**（E29 口径：单选自动，不打扰用户）；
> ④ **不存在「类别」概念**——判定键就是扩展名字符串本身 ⇒ **结构上不可能误判**（没有「同类别不同类」的模糊空间）；
> ⑤ 真正的风险只有两条：**声明不足**（插件没声明 ⇒ 永远碰不上）与 **扩展名粒度**（P3：mime/glob 未支持，`a.b` 与 `b` 类问题）。

- **改哪里**：主案 `02-边缘情况清单.md`（新增一条 E 编号，正文即上表）＋ 用户手册/设置页文案若有「竞争」字样，回指该 E 号。
- **怎么验**：`grep -n "竞争" 02-边缘情况清单.md` 命中且带判据；设置页 UI 里「竞争」处 tooltip 指向同一段（⛔ 不新造第二套说法）。

## 四、任务卡 C2.3：**已定位的空转项**——「在文件树中打开选择器」

### 4.1 为什么它点了没反应（已核实，file:line 为证）

```
items 里这一项：{ command: OPEN_WITH_COMMAND_ID, label: "在文件树中打开选择器" }   ← FileAssociationsManagerView.tsx:167-169
    ⛔ 没有 commandArgs
父级 ContextMenu：<ContextMenu menuId="fileAssociationsRowGear" anchor={anchor} items={items} onClose variant="non-modal" />
    ⛔ 没有 context 属性                                                          ← 同文件 :215-223
执行：executeCommand("file-tree.openWith", undefined)          ← ContextMenu.tsx:309（commandArgs 空 ⇒ 只余 undefined）
handler：args[0] === undefined                                   ← navigation.ts:50-110
    ↓ 无 uri ⇒ 回退 h()?.getFocusedUri()
    ↓ 仍无 ⇒ toast「没有选中的文件——请先在文件树中选中一个文件」
```

**结论**：这一项**在设置页语义上不可能正确**——设置页那一行的身份是「一个/一组**类型**」（`.pdf`），
而 `file-tree.openWith` 的入参是「**一个文件**」。现在它的行为是：要么去开文件树里**碰巧聚焦的那个文件**（与用户点的那一行无关），
要么弹一句「没有选中的文件」（用户报的「点了没反应/是假的」）。

### 4.2 修法（推荐 ＋ 备选，**待用户拍板**）

| 方案 | 内容 | 评价 |
|:--|:--|:--|
| **A（推荐）改按类型开** | 待 [01](./01-住错层纠正-选择器转正与壳级打开面.md) 的壳命令落地后，本项改 `commandArgs: [{ ext: row.exts[0] }]`，label 改「打开方式…（.{{ext}}）」；面板按类型列出处理器（**不需要文件**） | 保留入口且语义正确；**这正是把面板归壳换来的新能力**（旧契约要求一个真文件路径，所以旧方案本就不可能对） |
| **B 直接删项** | 删掉这一项，入口只留文件树右键 + 编辑器 | 最省事、零风险；但设置页少了「按类型试开」的便利 |
| **C 暂留但置灰** | ⛔ 不采纳 | 灰项＝死钮的变体，违反 E17/E39 |

> 🔴 **要用户拍板的那一句**（实施时问，带上推荐）：*设置页竞争行齿轮里的「在文件树中打开选择器」——推荐改成「按该行类型打开选择器」（需要一个 pdf 阅读器才显示处理器），也可以直接删掉这一项。你要哪个？*

### 4.3 无论选 A/B，本格都要做的

- **改哪里**：`FileAssociationsManagerView.tsx:167-169`；
- **怎么改**：A ⇒ 补 `commandArgs`（并用 `SHELL_COMMANDS.openWith` 常量替代 `OPEN_WITH_COMMAND_ID`，见 [01](./01-住错层纠正-选择器转正与壳级打开面.md) C1.4）；B ⇒ 删除该项与 `OPEN_WITH_COMMAND_ID` 常量＋ `openWithAvailable` 探测（⛔ 不留死代码）；
- **怎么验**：点该项必有可见结果（面板升起 or 项不存在）；⛔ 不许出现「点了什么都不发生」。

| 剪贴板面 | `window.linkdesk?.clipboard?.writeText?.(...)` | ⚠️ 见 5.3 |

### 5.2 复现清单（⛔ 先复现再改，别盲改）

1. 打开设置页「文件关联」→「按插件浏览」，**展开**任一插件卡；卡头右侧齿轮**是否出现**（`gearItems` 非空条件：`copyPluginId` 恒在 ⇒ 应恒有）；
2. 点齿轮 ⇒ 菜单**是否弹出**、有没有「复制插件 id」；
3. 点击后**剪贴板里到底有没有**内容（用记事本粘贴验证，⛔ 别靠 toast 判断）；
4. 有无 toast「已复制：<id>」；
5. DevTools Console 有无 **Unhandled Promise Rejection**；
6. 同页「竞争行齿轮」的「清除该行默认覆盖」是否正常（对照组：同一套命令注册面，若它也坏 ⇒ 问题在注册/IPC 面；若它好 ⇒ 问题只在这条 handler）。

### 5.3 头号嫌疑人（无论复现结果都要修 —— 属「回执不可达」缺陷）

```ts
// fileAssociationsGearCommands.ts:113-118（现状）
reg(copyPluginId, async (args) => {
  const target = readPluginCardGearTarget(args);
  if (!target) return;
  await window.linkdesk?.clipboard?.writeText?.(target.pluginId);   // ⚠️ 若这句 reject/面不存在
  toast(i18n.t("已复制：") + target.pluginId);                        // ⚠️ 这句就永远不执行
});
```

`?.` 只挡「面不存在」（返回 `undefined`，`await undefined` 无害），**挡不住 promise reject**：
剪贴板 IPC 失败 / 权限问题 ⇒ 抛出 ⇒ 后面的 toast 不执行 ⇒ 用户看到的就是**「点了没反应」**（与报告症状一致）。

- **怎么改**：`try { await …; toast(成功) } catch (e) { toast("复制失败：…" , "error") }`；并且**先探测面**：
  `const write = window.linkdesk?.clipboard?.writeText; if (!write) { toast("剪贴板不可用", "warning"); return; }`；
- **写什么**：同一修法**一并施于** `clearRow`/`clearCard`（现状已有 try/catch，核对面探测即可——它们已经这么写了，照它们的写法对齐，保持三条 handler 同构）；
- **怎么验**：单测（见 §七）＋ 实机第 3/4/5 条；
- **若复现出「面不存在」**：那是壳侧暴露面缺口 ⇒ 记入 [04](./04-契约API与文档连锁.md) 的「顺带发现」栏，别在本格私接。
