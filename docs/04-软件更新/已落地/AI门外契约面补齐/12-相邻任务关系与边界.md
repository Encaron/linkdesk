## 二、与 [通用能力底盘](../../待抉择池/通用能力底盘/00-提案.md)

### 2.1 总关系：**正交的两条轴**

| | 通用能力底盘 | 本档 |
|:--|:--|:--|
| 管 | **能动手**：进程 / 流 / 连接 / 能力声明 | **能确认**：回执 / 错误码 / 描述面 / 可达性 / 自检 |
| 关键产物 | `capabilities: string[]`（插件级） | `risk`（命令级）· `activation` · `returns` |
| 判据 | 止损线：壳能力须有两个领域消费者 | 判据 A：语义归谁就住哪层 |

### 2.2 轴四 `capabilities` vs 本档 S7 `risk`（⛔ 不许合并）

| 维度 | `capabilities` | `risk` |
|:--|:--|:--|
| 粒度 | **插件**（装了有没有这项能力） | **命令**（这一条调用多危险） |
| 何时判 | 安装时人授权（一次） | 每次调用按 AI 档位判 |
| 拒绝码 | `EPERMDENIED` | `EPOLICYDENIED` |
| 谁维护 | 插件清单 ＋ 权限系统 UI | 插件清单 ＋ `policy/risk.ts` |

**关系**：`capabilities` 是**门**（能不能进这个房间），`risk` 是**台阶**（进了房间，这一步要不要扶一把）。两者都过才执行。
**归一化要求**：两份表都必须**从同一份 manifest 读**，⛔ 各自维护一份「插件能干什么」的副本；门禁可共用一条腿，但判据分开。

### 2.3 串口最小面 vs 本档 D1/D2（🔴 已裁决，最要紧）

底盘 §五 决策 #5（2026-11-12，用户已定）：
> 串口是壳的通用传输能力之一，**壳只留「枚举 / 开 / 关 / 读写 / DTR·RTS」**；会话·暂停·缓冲·日志·**编码策略**全部住插件。

本档据此裁决：

| 概念 | 住哪 | 说明 |
|:--|:--|:--|
| 枚举 / 开 / 关 / 读写字节 / DTR·RTS | **壳** | 底盘最小面 |
| **收发方向 `dir`** | **壳**（读写边界打标） | 传输事实，不是策略 |
| **原始字节 `data`** | **壳透传** | 最小面「读写」的自然产物 |
| **编码策略**（选哪档、自动回退顺序） | **插件** | 底盘明定 |
| **解码原语** `decodeBytes` | **共享包**（SDK） | 纯函数工具，按落位表「一处定义」 |
| 会话 / 暂停 / 缓冲 / 日志 | **插件** | 底盘明定 |

⇒ **D1/D2 的前置是「底盘串口最小面落位」**。它没落之前，D1/D2 顺延（[06](06-数据面-方向与编码.md) 已写）。
⇒ ⛔ **不许在 `{text}` 上打补丁**：那会把编码策略留在壳，与已拍板决策正面冲突。

### 2.4 轴二 `stream` vs 本档 D1

- `dir`（rx/tx）是**串口语义**，⛔ 不要推广到通用 `stream`（字节流没有必然方向）。
- `stream` 是**帧**的世界（长度前缀/分隔符/定长）；本档不碰。
- 若将来某插件把串口包成 stream，方向由该插件自己在其帧头里表达。

### 2.5 轴三 `connections` vs 串口会话

- 串口通道的「同一块板子换了 COM 号」属于底盘的**设备身份握手**；本档不解决。
- 本档只保证：命令的 `returns` 能被 AI 读懂（例如会话列表里带 `connectionId` 时，声明其含义由插件负责）。

## 三、与 [万物皆可插件-表现层可替换化](../../待抉择池/万物皆可插件-表现层可替换化/00-提案.md)

### 3.1 总关系：**它把命令面升格为唯一稳定契约**

那档的愿想是「皮是第三方的，内容是官方的；更新不碰皮，替换不碰内容」。推论：

> **皮可以随便换，命令不能换。** ⇒ 命令面必须是**完整、可信、与视图解耦**的。

所以本档不是「顺便相关」，而是**那档的地基**：

| 那档需要 | 本档提供 | 若缺失的后果 |
|:--|:--|:--|
| 替换体只调数据命令取数（铁律 A） | `describe` 的 `returns` 准确（S3b） | 替换体拿不到稳定结构，只能猜 |
| 替换体的动作命令任何 UI 都能调 | 命令不寄生视图（S4） | 换掉原 UI ⇒ 动作命令一起消失 |
| 槽位「列出/切换/回退」命令可被 AI 发现 | `activation`/`risk`/`returns` 齐全 | AI 找不到、不敢调 |
| 逃生舱命令在崩坏时可用 | 命令不依赖被替换的视图 | 皮崩了连逃生舱都进不去 |

🔴 **结论**：**S4 是表现层可替换化的前置条件**——先让命令脱离视图，再谈换皮。⛔ 反过来做（先换皮）会把「动作命令寄生视图」这个债原样带进新架构。

### 3.2 命令分类：两套维度，不是两套体系

那档 §三 分「数据命令 / 动作命令 / 状态命令」——这是**语义分类**（谁消费）。
本档有「`activation`（entry/view）/ `risk`（0–3）」——这是**机械属性**。

| 那档的类 | 典型 `activation` | 典型 `risk` |
|:--|:--|:--|
| 数据命令（`app.getWelcomeData`） | entry（必须无视图可用） | 0–1（只读） |
| 动作命令（`lpm.updateItem`） | entry（任何 UI 都能调） | 2（有副作用） |
| 状态命令（`commands.getCommands`） | entry | 0 |

⛔ **不要把那档的三类做成 manifest 字段**——那会变成第二套分类体系；用语义分类指导作者，用机械属性进 manifest。

### 3.3 门禁：合并，不另开腿

那档 §3.8 提议「新增可替换槽位必须同时有切换命令＋数据命令」；本档提议 `check-command-contract`。
⇒ **同一条腿，两个判据**：① 每条命令四件套齐全；② 每个可替换槽位有三命令＋数据命令。⛔ 两条腿各查一半。

### 3.4 边界（互不越界）

| 本档不做 | 那档不做 |
|:--|:--|
| 槽位仲裁、factoryRole、`renderers` | 命令注册表结构、`activation`/`risk` |
| 内容物更新（LPM） | 回执/错误码/自检 |
| 启动期协议 | 串口数据面 |

## 四、与 [插件权限系统](../../待抉择池/插件权限系统/00-提案.md)

| | 权限系统 | 本档 |
|:--|:--|:--|
| 管 | 插件**能力**（`serial.open` 等 17 项） | 命令**风险**（R0–R3） |
| 谁批 | 用户（装时＋权限页） | AI 档位（每次调用） |
| 拒绝码 | `EPERMDENIED` | `EPOLICYDENIED` |
| 迁移 | 三段式（存量 17 仓） | **免兼容直改**（决策 #10） |

- **正交**：插件获了权，AI 仍可能因 `risk` 被问；AI 有档位，插件没获权也调不了。
- ⛔ 不许用 `risk:3` 代替权限（那只是「每次都问」，不是「没授权」）；⛔ 不许用权限代替 risk（装时授权不等于每次调用都安全）。
- **迁移先例只在权限系统那边成立**：本档不需要三段式（无第三方用户），⛔ 照抄过来。

## 七、本档明确**不做**（防范围膨胀）

- ⛔ 不改 `policy/decide.ts` 的档位矩阵（硬约束 29）。
- ⛔ 不改 `capabilities` 的语义与授权流程（权限系统）。
- ⛔ 不改槽位仲裁 / factoryRole / renderers（表现层可替换化）。
- ⛔ 不做通用 `stream`（底盘轴二）。
- ⛔ 不做设备身份握手 / COM 号追踪（底盘轴三）。
- ⛔ 不做烧录 / 探针 / 设备文件系统本身（各插件仓）。
- ⛔ 不做「AI 直接调壳底层 API」——一切经命令面，否则破掉万物皆可插件（[00 前言](00-提案.md)）。
