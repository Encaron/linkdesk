# E5.8 全量回归矩阵

> 对应清单任务 **E5.8#24 场景回归**（[../E5.8-执行清单.md](../E5.8-执行清单.md) Phase 5）——Phase 5 执行本矩阵，每个场景实测后勾选。
> E5.8 是基建工程——回归的唯一目的是证明 **UI/行为零变化**，同时新机制（disposer 卸载 / requires 编排 / 契约生成）本身可诊断、可验证。
> 回归风险列标注各场景与 E5.8 改动的关联点——Phase 5 实测时优先盯这些。

## 场景 1：启动与装载

| 验证点 | 操作 | 期望 |
|:--|:--|:--|
| 冷启动 | 全新启动软件 | 正常进入，欢迎页/文件树就位，无启动报错 |
| 插件全载 | 启动后查看插件列表 | 内置三件套 + 用户插件全部 ACTIVE |
| 坏插件诊断面 | 制造坏插件（坏 schema / 缺 entry / 加载抛错）→ 启动 | 不崩溃；状态机可查"为什么没激活"（#11 诊断面） |
| 依赖编排加载序 | 有 requires 的插件 + 依赖插件乱序放置 | 依赖图决定激活序，扫描序不影响（#14） |
| 无依赖兼容 | 现有插件（无 requires） | 行为不变（#16 零改动兼容） |

**回归风险：** Phase 2/3 重写 loader——装载时序、扫描序语义不得变；`import.meta.glob` 加载路径不得回归（E5.7 冻结语义）。

**✅ 实测（2026-08-20，synthetic 夹具 6 件）：**
- 冷启动正常；内置 + 用户插件全 ACTIVE ✅
- 依赖编排加载序：dep-a requires dep-b → 两者都 ACTIVE，b 先激活，扫描序不影响 ✅
- 无依赖兼容：现有插件零改动正常 ✅
- **⚠️ 坏插件诊断面预期纠正**：坏 entry（指向不存在文件）**不触发** #11 诊断面——`loadPluginComponent` 失败被 `runtime.ts:283` catch 静默吞掉，插件照样 ACTIVE（仅无视图组件）。详情页只显示 plugin.json description，无「为什么没激活」。诊断面仅 plugin.json 解析失败/读盘抛错/依赖环/版本不满足时触发。→ 坏 entry 静默降级 = 静默吞错，呼应 #24.6「失败必出声」治理方向，已立案。

## 场景 2：插件装卸 + 重装（E5.8 核心验收）

| 验证点 | 操作 | 期望 |
|:--|:--|:--|
| 卸载拆净 | 卸载一个活跃插件 | 无残留监听/注册/定时器（#12 实测拆净——disposer 全量回滚） |
| 重装可用 | 卸载后立即重装同插件 | 装载→使用→卸载→重装→再使用全链通（重装契约） |
| 连带卸载 | 卸载被依赖插件 | 消费插件自动 PENDING，不报错（#15）+ toast 提示可见（#15.5） |
| 自动重载 | 重装被依赖插件 | 消费插件自动 ACTIVE（#15） |
| 循环依赖 | 制造 requires 环 | fail-loud 报错，不静默（#14） |
| PENDING 可见 | 制造缺依赖插件（requires 不存在的 ID）→ 启动 | marketplace 显示 PENDING + "等待依赖: xxx" 原因可读（#15.5） |

**回归风险：** Phase 2 是最大推翻项——所有 Registry 从"手动对称"改 disposer 逆序回滚，漏一处 = 卸载残留。卸载/重装本场景必测三轮。

**✅ 实测（2026-08-20，synthetic 夹具 6 件）：**
- 连带卸载：卸载 dep-b → dep-a 自动变黄字「等待依赖: "synthetic-dep-b"」（#15.5 提示可见）✅
- 自动重载：装回 dep-b → dep-a 自动回 ACTIVE，提示消失 ✅
- **三轮重复（#12 拆净验证）**：卸载→装回 ×3，行为一致，无残留堆积 ✅
- 循环依赖：cycle-a/b 互 requires → **fail-loud 报错恰好 1 次/插件，不刷屏**（#24 回归修复 commit 282ec790 生效）✅
- PENDING 可见：missing-dep → marketplace 显示 PENDING + "等待依赖: no-such-plugin-id" ✅
- 卸载拆净 + 重装可用：串口监视器卸载→装回，命令/快捷键/收发全通 ✅
- 循环插件卸载：先卸 cycle-a → b 不报连带警告（b 已 failed 不在活跃集——符合设计），卸 b 正常 ✅

## 场景 3：命令 + 快捷键

| 验证点 | 操作 | 期望 |
|:--|:--|:--|
| 命令面板 | Ctrl+Shift+P | 居中显示，输入过滤，防抖 150ms 不回归 |
| 命令执行 | 面板执行任意命令 | 正常执行 |
| 快捷键 | Ctrl+B / Ctrl+J / F2 等常用快捷键 | 正常触发 |
| 卸载后无残留 | 卸载注册了命令/快捷键的插件 → 触发旧命令/旧快捷键 | 无效——死 handler 清零（#12 后无残留） |
| 齿轮菜单 | 左下齿轮 → 菜单各条目 | 执行正确，无静默 no-op（E5.7#56 教训防回归） |

**回归风险：** Registry register() 改返 disposer——消费方适配漏一处 = 注册泄漏或重复注册。命令/菜单/快捷键三 Registry 是重灾区。

**✅ 实测（2026-08-20）：** 命令面板正常；齿轮菜单各条目执行正确，无静默 no-op；卸载串口监视器后快捷键无残留（死 handler 清零）。

## 场景 5：崩溃恢复五件套（对标 E5.7 场景 8）

| 验证点 | 操作 | 期望 |
|:--|:--|:--|
| renderer 崩溃 | 任务管理器 kill Pool renderer 进程（**注：池是 preload 沙箱，DevTools 无 `process` 全局——`process.crash()` 不可用，用任务管理器 kill） | 2-4s 自动重建 |
| layout 恢复 | 崩溃后 | 标签页/分屏/侧栏/面板全恢复；插件正常 ACTIVE，无 PENDING 假死 |
| Hot Exit | 编辑未保存内容 → 崩溃 | 重建后内容恢复 + dirty 标记 |
| 壳崩 | kill 壳 renderer | 全窗口重建 + tabState 持久化恢复 + lastLayout 兜底 |
| 连续崩溃 | 10s 内 3 次 | 停止重建，显示错误页 |

**回归风险：** E5.8 不碰崩溃恢复链——本场景防连带回归即可（重建后插件正常 ACTIVE，无 PENDING 假死）。

**✅ 实测（2026-08-20）：** 任务管理器 kill 最大 renderer 进程 → 自动重建，插件全 ACTIVE；编辑内容在重建后保留，Ctrl+S 可保存（Hot Exit 通过）。连续崩溃 10s×3 停止重建（此前已测）。
