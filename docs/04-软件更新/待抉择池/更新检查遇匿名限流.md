## 一、现象与实证（2026-09-15 排查）

### 1.1 那条 toast 是真的收到了 403

| 事实 | 证据 |
|:--|:--|
| 文案**唯一**来源 | `electron/services/update-http.ts:30` 的 `RATE_LIMITED_MESSAGE` |
| 触发条件**只有** 403/429 | 同文件 `classifyHttpFailure`（`:42-46`）：`if (status === 403 \|\| status === 429)`；其余非 2xx 归 `network`、404 归 `not-found` |
| 请求端点 | 检查腿打 `product.json.updateUrl` = `https://api.github.com/repos/encaron/linkdesk/releases/latest`（`electron/product.json:8`） |
| 安装版打的是**同一**端点 | 从安装目录 `resources/app.asar` 抠出的 `updateUrl` 与仓内逐字符相同 ⇒ **与「安装版 / dev」无关**，dev 版会用同一条腿 |

⇒ 结论：软件**确实**从更新源拿到了一个 403，这不是 UI 或错误映射的 bug。

### 1.2 403 的来源 = 请求出口 IP 的匿名额度

GitHub 匿名（未认证）调用 REST API 的额度是 **60 次/小时，按来源 IP 计**；`core` 一册。本机实测（直连 `GET /rate_limit`，该端点自身不计账）：

```
limit=60  used=5  remaining=55  reset=本地 08:15
resources: core 60/55 · search 10/10 · graphql 0(未开通) · code_search 60/55 · integration_manifest 5000
```

要点：**按 IP 分册**（同一公网 IP 后所有设备/程序共用一个 60）、**按资源分册**（`core`/`search`/`graphql` 各一本）、**认证换册**（带 token = 5000/时/用户，计数键从 IP 变成用户）。**下载不吃这本账**——安装包走 `objects.githubusercontent.com`，不记额度。

🔴 **而本机的请求不是从用户自己的 IP 出去的**：

- 系统代理**开着**：`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` → `ProxyEnable=1`、`ProxyServer=127.0.0.1:7890`（FlClash）。
- 更新腿**故意**走 Chromium 网络栈（`electron/services/main-fetch.ts`，E6#76 的既有权衡：`net.fetch` 会读系统代理，全局 `fetch`/undici 不读）⇒ 请求从代理节点出口出去，舀的是**节点的**那本册。
- 实测两本册**互相独立**：直连那次 `used=3`、走代理那次 `used=2` ⇒ 两个不同 IP 的计数器。

### 1.3 本机现场读数（2026-09-15 早间）

| 路径 | 结果 |
|:--|:--|
| 直连 `/releases/latest` | `200`（另一时刻 `remaining=57/60`）⇒ 用户自己的 IP **没有**被限流 |
| 走 `127.0.0.1:7890` | 第一次 `curl exit 7`（连不上）；第二次隧道 `200 Connection established` 后 `curl exit 35`（TLS 握手失败）⇒ 节点本身不稳 |
| 同机历史 | `memory/JOURNAL.jsonl` 记着 2026-09-15 02:20 跑 `sync:bundled --latest` 时撞「**匿名 API 限流（60/时）**」 |

⇒ 判定：**那次 403 是真限流**，且限的是**代理出口 IP 的共享额度**（节点被同机人的脚本或同节点陌生人吃光）。软件自身的用量（启动后一次 + 每 4 小时一次，见 `src/hooks/useUpdateScheduler.ts:41-44`）**不可能**吃光 60/时。

> ⚠️ 一个可自证的判据（后来自测用）：**此时再点一次，多半换成另一条文案**——「网络不可用或更新服务无响应…」（走代理的 TLS 就是断的，`fetchWithTimeout` 抛异常归 `network`）。两条不同的 toast 恰好区分「节点断了」与「节点通了但被限流」。

## 二、本档主张要改的两点

### 2.1 文案承诺了**没有实现**的行为

| 文案 | 现状 | 证据 |
|:--|:--|:--|
| 「**稍后会自动重试**」 | 检查腿失败的**自动重试未开工**——本格只兑现手动 `[重试]` | [08-调度归属与失败重试 §2.2](../../02-Electron架构/E6_插件生态与发布/06-主软件更新/08-调度归属与失败重试.md)：自动重试**立案 = #57.9g，实现未开工** |
| 实际兜底 | `auto` 档（默认，`src/App/config/update.ts:32`）下 4 小时后的**周期检查** | `src/hooks/useUpdateScheduler.ts:41-44`。桶按小时重置 ⇒ 4 小时那次基本已恢复，**纯属侥幸对上** |
| `manual` 档 | **一句都不重试** ⇒ 这句话彻底不成立 | 同上 `:92`（`mode !== "auto"` 早退） |
| 「**无需处理**」 | 在共享出口 IP 的情形下不准确——用户可以处理（换节点 / 给 `api.github.com` 加 DIRECT 规则 / 用 token 提升额度） | §1.2 |

### 2.2 归因**不读**能拿到的事实

`01-更新机制设计.md` §2.3 把 `x-ratelimit-remaining: 0` 写成 403 的「**佐证**」，但代码**没有读它**（`update-http.ts:42-46` 只看状态码）。两个后果：

1. **一切 403 都说成「限流」**——GitHub 对受限/被滥用检测的 IP 同样回 403，那种情形不是「稍后重试就会好」，文案指向错。
2. **拿不到恢复时刻**——`x-ratelimit-reset` 是服务端给的确定时刻（实测本机 `reset=本地 08:15`），现文案只能含糊说「稍后」。

## 三、候选方向（列出供决策，未拍板）

### A｜小改，建议先做：把话说实话 + 让失败自愈

- 限流时读 `x-ratelimit-remaining` / `x-ratelimit-reset`，文案改成**可核对的事实**（「更新源额度已用尽，将于 <本地时刻> 恢复」），而不是「无需处理」；读不到头字段时退回现文案。
- 落地 **#57.9g**：仅对 `network` / `rate-limited` 有限重试 + 退避 ⇒ 这句话从「侥幸对上」变成「确实会做」。

### B｜结构解：更新源换自建中继（VS Code 模式）

一个 Cloudflare Worker 之类的小服务持 token，把 GitHub 的 JSON **原样**转发。好处：改动面**极小**（`updateUrl` 换个字符串，下游 sha256 校验 / asset 名比对 / 六类归因全不动）；额度从 60/时·IP 变成 5000/时·用户；中继上挂几分钟缓存的话，**无论多少用户**打到 GitHub 的总量都压得住 ⇒ 共享额度问题彻底消失。代价：多一个要维护的在线上服务，且它成为更新链路的单点（VS Code 也认这个代价）。

### C｜不建议：改打网页 / Atom 路径绕开 API

零额度依赖，但**拿不到 `asset.digest`（sha256）**——只能走既有的「未附校验值 ⇒ 降级放行」（`update-source.ts` 头注 ①），等于把完整性校验拿掉。对本项目水准而言这个退让太大，除非同时补签名校验。

## 六、验收（用户视角）

1. 拔网线（或让代理断开）点「检查更新」→ 得到「网络不可用…」，**不是**限流文案。
2. 用一个额度已尽的出口（或桩一个 403 + `x-ratelimit-remaining: 0`）点「检查更新」→ 文案给出**恢复时刻**，且该时刻与 `/rate_limit` 的 `reset` 一致。
3. 桩一个 403 但**没有** `x-ratelimit-remaining: 0`（受限 IP / 滥用检测形态）→ **不**说「限流」。
4. 若落地 #57.9g：桩 `rate-limited` 后按定案序列重试（次数/间隔/出声次数逐字断言）；桩 `checksum-mismatch` / 404 ⇒ **一次都不重试**（负控）。
5. `manual` 档下限流文案**不再承诺**任何自动行为。
