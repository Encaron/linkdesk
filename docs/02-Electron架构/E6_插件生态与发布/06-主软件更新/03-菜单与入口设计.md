### 2.2 命令清单（`coreCommands.ts` / `settingsCommands.ts` 新增）

| 命令 id | 标题（i18n key） | 行为 | 可见条件 |
|:--|:--|:--|:--|
| `update.checkForUpdates` | 检查更新… | `updateService.checkForUpdate(true)` 手动检查；有更新→发现更新条目；无→「当前已是最新版本」；**失败→归因文案 + `[重试]`** | **恒显**（对比手机 App：检查更新选项永在） |

## 四、TitleBar 更新按钮（声明制 + 有更新才现 + 全文字 + 主题按钮色）

### 4.1 决策记录（完整反转史——2026-08-30 三次表态）

> ① 中途曾拍板「有颜色的更新按钮」（toast 静默 → 按钮补可见存在，`appearance:"accent"` 强调色图标）。
> ② 当日用户说「我不要那个颜色提示」→ 被**误读**为去掉按钮颜色 → 全文件传播「无颜色灰图标」版本。
> ③ **当日晚澄清**（用户原话）：「我之前以为你说的是下拉菜单的『检查更新』那几个字有颜色，当时感觉不美观，刚才看清楚了，你说的是单独的那个『更新按钮』」→ **最终拍板：TitleBar 更新按钮 = 全文字 + 主题按钮色（跟随主题普通按钮）**。菜单里的「检查更新…」保持普通菜单项（无颜色）。

**教训**：用户说「不要颜色」时，先确认「哪个对象有颜色」——这里是指菜单文字，不是按钮本身。

**最终形态**：按钮 = 壳声明插槽 + **全文字**（无图标）+ **主题按钮色**（复用壳共享 Button 组件 `.button` = accent 实心 + `var(--text-on-accent)`，跟随主题切换）。toast 承载信息（04），按钮承载「有更新可处理」的可见存在——互补不重复。三态文字 = 「下载更新 → 更新中 → 重新启动」。

### 4.2 声明制落点（一次通用壳扩展）

```typescript
// 壳侧声明（APP_PLUGIN_ID，对标现有 registerTitleBarContribution 用法——MenuRegistry.ts:188）
registerTitleBarContribution(APP_PLUGIN_ID, "right", {
  command: "update.openUpdateFlow",     // 按状态分支：available→下载 / downloaded·ready→重启 / updating→no-op
  label: "$updateButtonLabel",          // 新增字段——`$` 前缀 = context key 引用，动态文字随状态切换
  when: "updateActionable",             // 状态门控：有可处理更新才显示（对标 sidebarPosition 动态键先例）
});
```

- **渲染方**：`titleBar.slots.right` → `renderSlotButton`。**本次新增 `label` 字段**——一次通用壳扩展：`label` 可为静态文字或 context key 引用（`$` 前缀），任何 TitleBar 按钮可用文字，不需图标。对标 `icon` 字段是通用能力而非更新专用。
  🔴 **分工订正（2026-09-12，E6#57.11 落地时）**：本文原写「`TitleBarZone` 解析 label 引用后渲染」——**与实际分工不符，已改**。实际是**壳侧 `buildTitleBarSlots` 解析完再推最终字符串**给池，池拿到什么画什么（`src/pool/` 对 `ContextKeyService` 零引用，池侧没有这套键的读面）。这与 `sidebarPosition` 同款：壳在推送 effect 里 `setValue` → 组装 slots → 推流。
- **样式**：壳共享 Button 组件（`Button.css .button` = `background: var(--accent)` + `color: var(--text-on-accent)` + `border-radius: var(--radius-sm)`）——**主题普通按钮实机形态，跟随主题切换**。走**新增的紧凑档 `.button--sm`**：`height: 22px` + `padding: 0 12px` + `font-size: var(--font-size-xs)`（12px，= 本档原设计值）。
  🔴 **横向留白 10px → 12px**（2026-09-12 用户裁决）：10px 过不了仓库 `check-spacing-grid` 门禁（要求 padding/margin/gap 要么 ≤6 要么是 4 的倍数）；12px 同时与 `.button` 基类既有留白同值 ⇒「复用壳共享按钮」这句话仍然成立，只覆盖高度。设计规范自己的「4/8dp 节奏」也印证同一件事，**不是为过门禁而将就**。
- **位置**：TitleBar 右侧槽位（窗口控制按钮左侧，对标 VS Code 标题栏布局）。
  ⚠️ **位置曾实现错（2026-09-12 修）**：右槽此前被渲染在 `.titlebar-drag-area`（`flex:1`）**之前** ⇒ 按钮实际贴在菜单右侧。因当时零条右槽贡献而一直没露馅；E6#57.11 同批把渲染序订正到拖拽区之后、窗口控制之前。**另**：共享 Button 没有 `style`/`className` 透传，宿主侧必须补一条 `-webkit-app-region: no-drag`（`.titlebar .button`）——否则按钮落在拖拽区里，**按下去只会拖窗口**。
- **门控键**：`updateActionable` context key = `available/downloading/downloaded/ready/updating` 任一为真（`updating` 见 §4.3 的第四行）。壳把 UpdateService 状态推成动态 context key——**由 `usePoolSync` 主推送 effect 内部 `setValue`**（与 `sidebarPosition` 同一处、同一条「先 set 后组装」顺序契约），状态迁移直接进该 effect 的 deps 触发重推。进度**不**触发重推（`reportProgress` 走 `onProgress` 通道，不碰 `onStateChanged`）。
- **文字键**：`updateButtonLabel` context key——壳随状态推**中文 i18n key 原文**（不是译文），翻译只在壳侧 `buildTitleBarSlots` 发生一次。
- **点击命令**：`update.openUpdateFlow` 按当前状态分支——下载中不重复触发（进度已走通知面）。

### 4.3 状态 × 形态映射（三态文字——用户 2026-08-30 拍板）

| 状态机 type | 按钮 | 形态 | 点击行为 |
|:--|:--|:--|:--|
| `idle` / `checking` / `uninitialized` / `disabled` / 无更新 | **隐藏**（when 门控） | — | — |
| `available` | 文字「**下载更新**」 | 主题按钮色（accent 实心 + `--text-on-accent`，全文字宽度自适应） | 开始下载（进度走 toast 04 §三） |
| `downloading` | 文字「**更新中**」 | 同上（宽度自适应） | 不重复触发 |
| `downloaded` / `ready` | 文字「**重新启动**」 | 同上 | `quitAndInstall()`（toast 04 §四） |
| `updating` | 文字「**更新中**」 | 同上 | **无动作**（安装已在进行，任何动作都会打架） |

> 🔴 **第四行 `updating` 是 2026-09-12 补的一格**（用户拍板，原文表格只有三行）。理由：用户点完「重新启动」到软件真正退出之间有**一段安装期**，此时把按钮抽掉会让人以为「点了没反应」；留着「更新中」才是「你的点击生效了」。该格**点击是 no-op**——按钮只是「有更新在处理的可见存在」，不是可重复触发的动作入口。

> **没有更新时不占位**——when 门控隐藏，避免「常驻无动作按钮」。手动「检查更新…」（恒显）仍随时可查。**主题按钮色**——复用壳共享 Button 组件（主题普通按钮），切换主题即变；菜单里的「检查更新…」保持普通菜单项（无颜色），互不混淆。三态文字由壳推 context key `updateButtonLabel` 动态显示。

### 4.4 为什么是「一次克制的通用壳扩展」（对比中途拍板的「accent 图标」）

最终版本含**一次壳改动**：`registerTitleBarContribution` 插槽新增 `label` 字段 + `TitleBarZone` 渲染文字按钮（解析静态字符串或 context key 引用）。这是**通用扩展**——任何 TitleBar 按钮可用文字（第三方插件同样受益），对标 `icon` 是通用能力而非更新专用；走 audit-contributes 三件套（plugin.schema.json 字段 + 加载器消费 + 文档说明）。

对比中途拍板的「accent 强调色图标按钮」：accent 版本需 `appearance` 字段 + 自绘强调样式；最终版本**样式零新增**——直接复用壳共享 Button 组件（`.button` = 主题普通按钮），唯一新增就是 `label` 通用字段。按钮的「有颜色」来自主题 accent 本身，不是新的强调色概念。

### 4.5 八维度设计前置（`label` = 新贡献点字段 ⇒ 新能力）

> 按项目《新能力设计流程》§8.4 ③ 补。以下逐维度答，**不适用的写「不适用 + 理由」**，不留空。

| # | 维度 | 答 |
|:--:|:--|:--|
| 1 | **能力边界** | 只给 TitleBar 插槽加「按钮可以显示文字」这一个能力。**不做**：不做富文本/Markdown、不做图标+文字并存、不做颜色/尺寸自定义、不做点击外的交互（长按/双击/右键菜单）。同样**不**把更新逻辑搬进池——池仍然只认「命令 id + 图标或文字」。 |
| 2 | **API** | 无新增 `window.linkdesk.*` 面。改的是**声明面**（`plugin.json` 的 `contributes.titleBar.*[].label`）⇒ schema + 类型 + 文档。插件零代码即可用。 |
| 3 | **通信** | 不新增 IPC 通道、不新增事件。`$` 引用的 context key 复用既有 `linkdesk.contextKey`（本来就有 set 面）+ 壳侧 `ContextKeyService`。池仍是哑渲染：文字由壳算好随布局推流过来（layout DTO 加一个可选字段），**不新增往返**。 |
| 4 | **壳侧代码** | `MenuRegistry.TitleBarContribution.label`（类型）+ `usePoolSync/titlebar.ts` 的 `resolveTitleBarLabel`（解析）+ `usePoolSync.ts` 推两个 context key + `TitleBarZone` 多一支渲染分支 + `Button` 加 `size="sm"` 档。 |
| 5 | **插件侧代码** | 声明式，**零代码**。插件只需在 `plugin.json` 写 `"label": "文字"` 或 `"label": "$我的键"`（后者配一句 `linkdesk.contextKey.set()`）。 |
| 6 | **显示** | 文字按钮 = 壳主题普通按钮形态（accent 实心），随主题切换；宽度随文字自适应；`icon` 与 `label` 互斥（有 label 优先）。显示文本铁律：**壳翻译、池渲染**（i18n key = 中文原文）。 |
| 7 | **配置** | **不新增任何配置项**——不设开关、不给默认值选项。插槽本身是声明制的，不填 label 就还是图标按钮（**存量插件行为逐字节不变**）。 |
| 8 | **验收** | 可证伪判据见 §4.3 表（四态）＋ 三条机械判据：① 第三方插件声明 `label` 能渲染出文字（通用性，非更新专用）；② `label` 缺失时既有图标按钮不受影响；③ `$键名` 键不存在时显示字面 `$键名`（失败可见，不是静默空白）。**实机验收挂实机批次**（需真更新包）。 |

**破坏性评估**：纯新增**可选**字段 ⇒ 存量插件零影响（不填 = 老行为）⇒ 0.x 向后兼容，软件轴走 patch 位、作者轴走 patch 位。
