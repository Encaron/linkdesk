# 07 — 体积与内存分析

> 2026-07-23。坦诚分析 Tauri → Electron 迁移后的安装包体积和运行时内存变化。
> **不美化数字——大了就是大了，小了就是小了。然后看"大"在什么场景、"大"多少、能不能接受。**

---

## 一、安装包体积

### 1.1 数字

| | Tauri（当前） | Electron（新方案） | 变化 |
|---|---|---|---|
| 框架 | 系统 WebView2（Windows 自带） | 自带 Chromium + Node.js | — |
| 安装包（压缩） | **~5MB** | **~120-150MB** | **×30** |
| 安装后磁盘 | ~15MB | **~250-350MB** | **×20** |

5MB → 120MB。涨了 30 倍。

### 1.2 多出来的 115MB 是什么

```
Electron 安装包 ~120MB：
  ├── Chromium 渲染引擎    ~90MB（压缩）
  ├── Node.js 运行时        ~20MB（压缩）
  ├── Electron API 胶水层    ~5MB（压缩）
  └── LinkDesk 应用代码      ~5MB（压缩）

Tauri 安装包 ~5MB：
  ├── Rust 二进制            ~3MB（压缩）
  └── 前端静态资源            ~2MB（压缩）
  ├── Chromium → 系统 WebView2，不打包
  └── Node.js → 不存在
```

**多出来的 115MB 就是"把浏览器引擎塞进安装包"的代价。** Tauri 省掉了这 115MB 是因为 Windows 10+ 自带 WebView2——它不在你的安装包里，在系统里。Electron 不能假设"用户一定装了 Chromium"——所以自己带。

### 1.3 对比

| 软件 | 安装包大小 | 安装后磁盘 |
|---|---|---|
| **LinkDesk (Tauri)** | 5MB | 15MB |
| **LinkDesk (Electron)** | 120MB | 300MB |
| VS Code | 90MB | 350MB |
| Discord | 80MB | 200MB |
| Slack | 100MB | 300MB |
| Notion | 120MB | 350MB |
| Figma | 100MB | 280MB |
| QQ (Electron 版) | 150MB | 400MB |

**120MB 的安装包在桌面软件里是正常水平。** VS Code 能做到 90MB 是因为微软有专人裁剪 Chromium（移除 PDF 阅读器、打印子系统、WebRTC 等不用的模块）——这是几个人的全职工作。LinkDesk 不需要对标这个优化。

### 1.4 这张门票只付一次

后续装 100 个插件——Leaflet ~2MB、Monaco ~5MB、THREE.js ~3MB——这些是插件自己的 `node_modules`，不影响框架安装包。

**插件增多 → 插件目录变大，框架安装包不变。**

## 二、运行时内存

### 2.1 基线

| | Tauri（当前） | Electron（新方案） | 差异 |
|---|---|---|---|
| 空壳（无插件、单窗口） | **~50MB** | **~150MB** | +100MB |

多出来的 100MB：
- 壳 BrowserWindow 的 Chromium 渲染进程 ~60MB（Tauri 的这部分是系统 WebView2——跟 Edge 共享，所以基线更低）
- Node.js 主进程 ~30MB（Tauri 的这部分是 Rust ~10MB）
- Electron API 初始化 ~10MB

### 2.2 每个插件的增量

**不管用 Tauri `add_child` 还是 Electron `WebContentsView`——每个独立 WebView 的内存差不多。** 因为底层都是 Chromium 渲染引擎，DOM/CSS/JS 引擎的内存开销是同一个代码基。

但是 Electron 的 WebContentsView 可以共享一些 Chromium 基础设施（网络栈、GPU 进程、V8 代码缓存），而 Tauri `add_child` 创建的是独立系统 WebView——各自跟系统 WebView2 进程管理逻辑走。

**实际差异在 10-20% 以内，不足以成为决策因素。**

| 插件 WebView | 典型内存 | 说明 |
|---|---|---|
| 终端（CM6 + xterm） | ~70MB | xterm 虚拟终端滚动缓冲区 + CM6 编辑器状态 |
| 编辑器（Monaco） | ~130MB | Monaco 是重型编辑器——语法树 + IntelliSense |
| 文件树 | ~60MB | 树组件 + 文件图标 SVG |
| 地图（Leaflet + 瓦片缓存） | ~100MB | 瓦片图片缓存最吃内存 |
| 工作台（卡片网格） | ~80MB | react-grid-layout + 卡片组件 |
| 简单视图插件（无重型库） | ~40-50MB | 纯 React 组件 + 轻量数据 |

### 2.3 实际场景算账

| 场景 | 壳 + 插件 | 内存 | 对标 |
|---|---|---|---|
| 空壳启动 | 0 插件 | **~150MB** | — |
| 只开终端 | 1 插件 | 150 + 70 = **~220MB** | — |
| 终端 + 文件树 | 2 插件 | 150 + 70 + 60 = **~280MB** | — |
| 终端 + 文件树 + 编辑器 | 3 插件 | 150 + 70 + 60 + 130 = **~410MB** | VS Code 类似 ~500MB |
| 工作场景（6 插件） | 6 插件 | 150 + 70 + 130 + 60 + 100 + 80 = **~590MB** | VS Code 同等 ~1GB |
| 重度（10 插件） | 10 插件 | 150 + 10×80 = **~950MB** | VS Code 重度用户 ~1.5GB |

### 2.4 为什么 VS Code 能吃到 1.4GB

有人测过 VS Code 内存 1443MB。大头不是多 WebView：

| 部分 | VS Code | LinkDesk |
|---|---|---|
| 主 UI 渲染 | ~200MB | ~150MB（壳 WebView） |
| C++ 语言服务器 | ~300MB（独立进程） | 无此概念 |
| PowerShell 语言服务器 | ~200MB（独立进程） | 无此概念 |
| Claude Code | ~200MB（独立 Node.js） | —（装了就是插件自己的进程） |
| Extension Host | ~150MB（共享 Node.js，含所有已加载扩展的代码和状态） | 无此概念——每个插件自带逻辑（含在自己的 WebContentsView 里）。**如果对标 ExtHost 方案的内存，见 `02-插件隔离模型与开销分析.md` 第二部分。** |
| 百度 Comate + 豆包 | ~150MB | — |

**VS Code 内存高是因为原生二进制进程——C++ 语言服务器、AI 助手自带完整运行时。** LinkDesk 没有语言服务器这种概念——插件的"逻辑"在自己的 React 组件里，不需要第二个进程。

## 三、不是装了 30 个就有 30 个进程——按需激活

### 3.1 标签页关闭 = WebContentsView 销毁 = 内存回收

```typescript
// 用户关标签页时
function closeTab(tabId: string) {
  const pluginId = getPluginId(tabId);
  pluginWebViewManager.destroy(pluginId);
  // Chromium 渲染进程被 OS kill → ~70MB 回到系统
}
```

**用户只打开了 2 个标签页 → 只有 2 个插件 WebView 在运行。** 装了 50 个插件但只开了 2 个 → 内存 = 150 + 2×70 = **~290MB**。

### 3.2 不是所有插件都需要 WebView

| 插件类型 | 需要独立 WebView？ | 内存开销 |
|---|---|---|
| **view plugin**（终端/地图/编辑器/文件树） | ✅ 需要 | ~50-130MB 每个 |
| **protocol plugin**（协议解析——纯逻辑） | ❌ | **0MB** |
| **theme plugin**（主题——JSON） | ❌ | **0MB** |
| **language plugin**（语言包——JSON） | ❌ | **0MB** |
| **resource plugin**（数据提供者） | ❌ | **0MB** |

插件市场 200 个插件，可能有 50 个 view plugin 需要 WebView。其余 150 个零内存开销——它们的逻辑在壳里跑，不额外创建进程。

## 四、随着时间推移

### 4.1 硬件在变

| 年份 | 主流笔记本内存 | LinkDesk 6 插件内存 | 占比 |
|---|---|---|---|
| 2015 | 4-8GB | 跑不动（VS Code 也跑不动） | — |
| 2020 | 8-16GB | ~590MB | ~5% |
| 2026 | 16-32GB | ~590MB | **~2-3%** |
| 2030 | 32-64GB | ~590MB | ~1% |

**独立进程的内存代价随硬件升级递减。** 2015 年 VS Code 选共享 ExtHost 是因为 8GB 内存跑不了 30 个独立进程——不是因为它更安全。

### 4.2 安装包也在变

2026 年 120MB 的安装包——5G 网络下 ~2 秒。用户从点击下载到安装完成 30 秒内。这个数字 5 年后会更无关紧要。

## 五、内存优化手段（E2 实现）

| 手段 | 效果 | 复杂度 |
|---|---|---|
| **标签页关闭即销毁** WebContentsView | 插件不跑时 0 内存 | 低——核心逻辑 |
| **后台标签页降级**——`backgroundThrottling` | 后台 WebView 降低 JS 定时器频率 | Electron 自带 |
| **共享 GPU 进程**——所有 WebContentsView 共用一个 GPU 进程 | 省 ~50MB/插件 | Chromium 默认行为 |
| **插件预加载池**——空闲 WebView 池复用以加速打开 | 用内存换速度——慎用 | 中 |
| **WebContentsView 的 `paintWhenInitiallyHidden`** | 隐藏时不渲染 | Electron 自带 |

## 六、坦率结论

| 指标 | Tauri | Electron | 差距 | 诚实评价 |
|---|---|---|---|---|
| 安装包 | 5MB | 120MB | ×30 | **退步。** 但 120MB 是桌面软件正常水平，一次下载 |
| 安装后磁盘 | 15MB | 300MB | ×20 | **退步。** 300MB 在今天不算大——手机 App 随便 500MB+ |
| 空壳内存 | 50MB | 150MB | +100MB | **退步。** 多 100MB 基线是 Chromium 的固定门票 |
| 5 插件运行 | ~350MB | ~490MB | +140MB | 差距在缩小——基线差被 WebView 本身的开销摊薄 |
| 10 插件运行 | ~550MB | ~950MB | **接近** | 两者都有多个独立 WebView——框架差被稀释 |

**最痛的是安装包体积——30 倍。** 但从"秒下"到"等 10 秒"——在 2026 年不是什么问题。

**内存方面——多 100MB 基线是真金白银的代价。** 但"多个插件同时跑"的场景下，框架基线差被 WebView 本身 ~60-80MB 的开销逐渐摊薄。开 3-4 个插件后，用户感知不到框架差异——吃内存的是插件，不是框架。

**永远不要忘记 Tauri 的真正问题——不是内存、不是体积——是 `add_child` unstable。** 这个 API 随时可能坏、出 bug 时没有 Stack Overflow 答案、AI 训练数据接近零。LinkDesk 选 Electron 是因为 Chromium 的多进程管理器十年验证过——不是因为 Electron 内存更小。
