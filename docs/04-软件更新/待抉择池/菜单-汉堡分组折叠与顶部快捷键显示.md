## 二、事 1：汉堡把同组成员折进「组标签容器」

### 现象（用户原话）

> 「汉堡菜单现在把"新建文件，新建文件夹，关闭文件夹，编辑"等这些文件树的东西平铺在和文件同级的目录了，明明顶部显示的是在文件这个菜单的内部的」

### 实测判据

`bundled-plugins/file-tree.linkdesk-plugin` 的 `plugin.json` → `contributes.menus.menuBar` 共 6 条，**`group` 全是 `"file"`**：

- 5 条命令项：新建文件 / 新建文件夹 / 打开文件夹… / 关闭所有编辑器 / 关闭文件夹
- 1 条**父项容器**：`{ command: "", label: "编辑", group: "file", children: [剪切、复制、粘贴、搜索] }`

⇒ 于是 `"file"` 组里有两个「无命令父项」：壳自带的**「文件」**（= 组标签容器）与插件带来的**「编辑」**。

### 两面为什么不一样

- **顶栏**：**一个 group ＝ 一个下拉**，按钮**就是**「文件」。`flattenGroupItems`（`titlebar.ts:130-152`）把组标签容器的 children 平铺出来，再把同组其余成员（文件树 5 条 ＋「编辑」父项）当条目排进去 ⇒ 组里有什么，全在「文件」下拉里 ✅
- **汉堡**：没有「文件」这个按钮位。它把**组内成员逐条**渲染在一级（`titlebar.ts:208-222`，`buildHamburgerGroupItems` 之前的写法＝`groupItems.map(resolveItemNode)`），而只有**组标签容器的 children** 会进子面板 ⇒ 插件那 6 条**留在一级** ❌

当前汉堡一级实际长相：`文件▸ · 新建文件 · 新建文件夹 · 打开文件夹… · 关闭所有编辑器 · 关闭文件夹 · 编辑▸ · 查看▸ · 帮助▸`

### 根因

「一个 group ＝ 一个菜单」这个模型，在顶栏**天然成立**（按钮即菜单，整组落进它的下拉）；在汉堡**只覆盖了「组标签容器的 children」**，不覆盖同组的其他贡献者。文件树是第一个同时往 `file` 组里塞「命令项 ＋ 父项」的插件（**插件没做错**——`group: "file"` 是合法声明），这个缺口第一次露头。

### 方案（已落：新增 `buildHamburgerGroupItems`）

`buildHamburgerMenuGroups`：用**与顶栏同一个判据**（`!command && label === 组标签`）认出组标签容器后，把该组**其余成员按其原序折进容器的 children**（`titlebar.ts:180-203` 新函数，容器**原序位置**不动、原位换成带 children 的父项，其余成员一级不再占位）。

- 修完 ☰ 的「文件」面板内容 = 顶栏「文件」下拉内容（**同序同物**，两面不再漂移）
- 每条 item 自带的 `group`（二级分组 = 分隔线依据）与 `when` 过滤**天然保留**（都照旧走 `resolveItemNode`）
- **没有容器的组保持原样**（如只由插件项构成的 `group: "panel"`）——它们本来就没有「文件」那种壳可折
- **容器自己被 when 过滤掉 ⇒ 整组原样返回**（否则整组会跟着容器一起凭空消失）
- 副作用：汉堡**深一层**（☰ → 文件 → 编辑 → 项）。渲染器本就支持 N 层递归（E5.8#148 的兄弟 portal 链），无需改

### 验收（事 1）

- ☰ 一级 = `文件▸ · 查看▸ · 帮助▸`（＋无容器组原样列出）
- 「文件」子面板 = 壳 3 条（导出工作区／导入工作区／打开设置）＋ 文件树 5 条 ＋「编辑▸」（内含剪切／复制／粘贴／搜索）
- 顶栏「文件」下拉**逐字节不变**（本次不碰顶栏那条路）
- 单测：`src/hooks/usePoolSync/titlebar.test.ts` 「2026-10-04 汉堡同组成员折进「组标签容器」」四例——正控（一级只剩容器 ＋ children 序）/ 两面同序同物 / 负控（无容器的组仍平铺）/ 边界（容器被 when 过滤 ⇒ 整组原样）

## 三、事 2：顶部菜单栏把快捷键显示回来

### 现状与判据

- 机制**整套都在**，只是顶栏**故意不传**键位：`resolveItemNode` 仅在 ctx 带 `keybindings` 时才写 `shortcut`（`titlebar.ts:68-85`）；汉堡传了 `getKeybindings()`（`:212`），**顶栏没传**（`:125`，原注释写着「顶部菜单栏无快捷键显示（壳原语义）」）
- 渲染端**零改动**：`ContextMenu.tsx:439`（一级）与 `:474`（子面板）都已吃 `item.shortcut` → `KeybindingHint` 键帽
- 数据契约允许：`src/core/types/pool/poolLayout.ts:430` 的注释即「仅汉堡；titlebar 下拉无快捷键（同壳行为）」
- **当初为什么没有**（这不是"丢了"）：`docs/02-Electron架构/E3_多WebView与壳收尾_暂定/09-E3h-美化专题.md` §二 #65——`:213`「当前只有 HamburgerMenu 显示快捷键…统一为 MenuRenderer 的 `showKeybindings` prop 控制」、`:230`「标题栏 → 文件▼ → **不显示**快捷键（showKeybindings=false）」。⇒ 是当年统一渲染器时给顶栏定的 `false`

### 方案

`buildTitleBarMenuGroups` 的 ctx 加一行 `keybindings: getKeybindings()`（`titlebar.ts:125`，与汉堡同源同函数）；顶栏那条路剩下的全自动。顺带订正三处注释：`titlebar.ts:59`（ctx 字段说明）/ `:120-124`（顶栏 ctx 上方）、`poolLayout.ts:429-430`，并在本档记下「推翻 E3h #65 的那半」。

### 会多出哪几条（只显示**真有绑定**的项）

| 位置 | 项 | 键 |
|:--|:--|:--|
| 文件 | 打开设置 | `Ctrl+,` |
| 查看 | 显示命令面板 | `Ctrl+Shift+P` |
| 查看 | 主题 | `Ctrl+K Ctrl+T` |
| 查看 | 选择语言 | `Ctrl+K Ctrl+L` |
| 查看→界面 | 主侧栏 / 面板 | `Ctrl+B` / `Ctrl+J` |

（据 `src/core/commands/input-bindings/shellKeybindings.ts:10-22`；无绑定的项照旧不显示键帽——这是既有语义，不是本次新增判断）

### 风险与验收（事 2）

- **唯一风险**＝菜单变宽：`.ldk-ctx-menu` 为 `min-width:140px / max-width:280px`（`src/components/shared/context-menu/ContextMenu.css:18-19`）。汉堡今天就在**同一渲染器**里带键帽 ⇒ 长相已知；dev 目视确认长标签（如「关闭所有编辑器」）不挤／不换行。**若挤 ⇒ 才需要动 CSS ⇒ 先过设计 skill**
- 验收：顶栏下拉各项右侧出现与汉堡**同款**键帽；无绑定的项不出现；两处键帽格式一致；`Ctrl+K Ctrl+T` 这类两段和弦显示正常
- 单测：`src/hooks/usePoolSync/titlebar.test.ts` 「2026-10-04 顶部菜单栏快捷键显示（与汉堡同源）」三例——有绑定带 `shortcut` / 无绑定**不带该字段** / 两面逐字相同 / 两段和弦
