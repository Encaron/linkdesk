# 命名规范——七种名字，一条身份

> **任务号：** E6#97f（规范落笔）＋ **E6#98g**（身份显式化，见 §六） · **前置：** 无 · **产物：** 本篇 + 作者面文档 + `pluginId` 进 schema
> **为什么单独立一份：** 用户 2026-09-14 明确要求「**反正我们需要一个比较系统化的东西**」——上一轮只写了「身份 vs 显示名 vs 仓库名三分」两行，不成体系。**本轮的调查又掘出一个比命名更重要的问题**（§二），它直接决定「作者能不能自由改名」。

---

## 〇、一句话结论

> **「作者可以自由改名字」的技术前提是「插件身份不靠任何名字」。**
> 今天不是这样——**身份靠目录名兜底**（§二）。所以搬仓之前必须先做 §六 的身份显式化，否则「仓库取名自由」这条会静默地把插件 id 改掉。

---

## 一、现状实测（2026-09-14，全部回源）

七种「名字」各自有不同读者与可变性——**混为一谈是这一切问题的根源**：

| # | 名字 | 今天的真源 | 谁在读它 | 可变？ |
|:--:|:--|:--|:--|:--|
| 1 | **插件身份 id** | `plugin.json.pluginId` **??** 项目**目录名** **??** zip 基名（**三处兜底**） | 安装目录 `<userData>/plugins/<id>/`、catalog 合并去重键、卸载墓碑键、更新对账 | 🔴 **必须不可变** |
| 2 | **显示名** | `plugin.json.name`（`"文件树"` / `"首次配置"`） | 界面、市场卡片 | ✅ **随便改** |
| 3 | **版本** | `plugin.json.version`，schema pattern `^\d+\.\d+\.\d+$` | 更新比对、Release tag、catalog | 每次发布必变（**无预发布后缀**） |
| 4 | **分发件名** | `<id>.linkdesk-plugin`（`assetNameForId`） | zip 安装裁决（`deriveIdFromZip`）、Release asset | 跟随 id |
| 5 | **Release tag** | `v{version}`（`releaseTagForVersion`） | 更新检查、`/releases/latest` | 跟随版本 |
| 6 | **GitHub 仓库名** | 无规则（自由） | `readmeUrl` / `downloadUrl` / `repository` | ✅ 自由（**改名会断已发布链接**） |
| 7 | **本地目录名** | 无规则（自由） | 构建工具 —— ⚠️ **但 `derivePluginId` 会读它当 id 兜底** | ⚠️ **见 §二** |

**四条既有字符集/格式约束（写规范时要引用，不要重造）：**

| 约束 | 值 | 出处 |
|:--|:--|:--|
| id 字符集 | `^[A-Za-z0-9][A-Za-z0-9._-]*$`（字母/数字/`.`/`_`/`-`，首字符须字母或数字） | `packages/plugin-sdk/src/validate.ts:51` `SAFE_PLUGIN_ID` |
| 版本 | `^\d+\.\d+\.\d+$`（**不许 `-beta` 之类后缀**——schema 会拒） | `public/schemas/plugin.schema.json` |
| 视图容器 ID | `^[a-z][a-z0-9-]*$` | schema / `03-插件contributes规范` |
| `.linkdesk-plugin` 基名 | = 插件 id | `assetNameForId` |

## 二、🔴 核心问题：身份靠「名字」推断，而那个字段不在 schema 里

### 2.1 三处兜底，全是「用名字推断身份」

```ts
// packages/plugin-sdk/src/validate.ts:124
export function derivePluginId(manifest, sourceDirName) {
  const rawId = m?.pluginId;
  if (rawId === undefined) pluginId = sourceDirName;        // ← 兜底①：目录名
  ...
}

// electron/ipc/handlers/plugin-install-handlers.ts:79
/** 解压后包内 pluginId 裁决——manifest.pluginId ?? zip 基名 */   // ← 兜底②：zip 文件名
```

**兜底③ 是「安装目录名」本身**——落盘到 `<userData>/plugins/<id>/`，之后所有对账都按它。

### 2.2 这与硬约束 11 直接冲突

> **硬约束 11**：「插件身份唯一来源是 plugin.json 声明字段。**禁止用文件位置、目录名、是否在 Vite glob 中、是否在源码树里来推断插件属性。**」

⇒ **`derivePluginId` 的目录名兜底，正是硬约束 11 点名禁止的那种推断。** 今天它没爆，唯一原因是**目录名一直很稳定**（`plugins/<id>/` 从没改过）。

### 2.3 而 L7 恰好会引爆它

L7 要把源码搬进**各自独立、名字自由**的仓库与本地目录。一旦：

- 仓库叫 `linkdesk-plugin-file-tree` 而插件 id 该是 `file-tree`，或
- 作者把本地目录改成别的名字再构建，

⇒ **构建出的 zip 里 `pluginId` 兜底成新名字** ⇒ 插件 id 变了 ⇒ **换了一个插件**：

| 后果 | 具体表现 |
|:--|:--|
| 安装目录换了 | 老用户 `<userData>/plugins/file-tree/` 与新装的 `<userData>/plugins/linkdesk-plugin-file-tree/` **并存两份** |
| 墓碑对不上 | 卸载记录认旧 id ⇒ 新 id 的插件"从没被卸载过"，**removed 墓碑失效** |
| 目录合并去重失效 | catalog 里同一只插件出现**两条不同 id 的条目** |
| 更新链断 | `plugins:update-check` 按 id 找条目 ⇒ **找不到，无更新**（静默） |
| 用户数据不跟 | 插件数据目录 `{userData}/linkdesk/plugins/<id>/data` 按 id 分 ⇒ **数据看似丢了** |

**五条后果里没有一条会报错**——这正是它危险的地方。

### 2.4 而且 `pluginId` 根本不在 schema 里

```
node -e "console.log(!!require('./public/schemas/plugin.schema.json').properties.pluginId)"
⇒ false
```

**有读取方（`derivePluginId`）、有写入方（`first-run-setup` 就写了）、schema 里没有**——这违反硬约束 11 的后半句「所有属性都在 `PluginManifest` 类型和 JSON Schema 中有对应字段」。

> 📌 **仓外样板反而是对的**：`first-run-setup` 的 `plugin.json` 显式写了 `"pluginId": "first-run-setup"`——**它就是这么做到"搬出去也不换身份"的**。而**仓内 18 只一只都没写**（`grep -l '"pluginId"' plugins/*/plugin.json` ⇒ 零命中），全在吃目录名兜底。

## 三、决策（N1-N6）

| # | 决策 | 理由 |
|:--|:--|:--|
| **N1** | 🔴 **插件身份 = `plugin.json.pluginId`，显式声明，进 schema。目录名/zip 名兜底降级为「遗留兼容」，并在文档与报错里标明不推荐** | 硬约束 11；也是「作者自由改名」的前提 |
| **N2** | **仓库名完全自由，不强制任何前缀** | 用户原话「**你不能限制人家插件作者给自己的插件换名字**」；对标 VS Code（仓库名与身份无关） |
| **N3** | **官方插件**（我们自己的 18 只）**采用一条统一惯例**——建议 `linkdesk-plugin-<id>`；**第三方零约束** | 「官方零约束」会让几十个仓在 GitHub 上不可扫读；而**官方仓是我们自己的命名自由**，不是对别人的限制。⚠️ 最终选哪条由用户拍板，**选定后写进 §五 并只在此处维护** |
| **N4** | **显示名（`name`）随便改**，改完重发一版即可 | 对标 VS Code `displayName`（实测：`Claude Code for VS Code` 这种长名/自由名完全合法） |
| **N5** | **本地目录名与仓库名同级自由**——但**目录名不得再被当作身份来源**（N1 落地后不再兜底当 id） | 用户 D6 的容器约定因此零风险：目录随便改、插件身份不变 |
| **N6** | 🔴 **版本号「四处同源」**——在既有的「三处锚」上加第四处 `package.json.version`（**保留该字段并强制与 `plugin.json.version` 相等**，不删） | 用户 2026-09-14：「关于这个 version 版本号，我建议**加上**，反正就是**能规范就规范一点**」。既有三处锚见 `09-插件目录规范.md:94`；第四处是 [02-出口打通.md §六](02-出口打通.md) 实测出来的（六只插件 `package.json.version` **全是 `1.0.0`**，与真版本脱节） |

## 四、VS Code 依据（2026-09-14 实测，用户要求「查一查人家的命名规则」）

### 4.1 用户安装目录名 = `<publisher>.<name>-<version>[-<平台>]`

```
ms-vscode.powershell-2025.4.0
ms-vscode.cpptools-1.35.0-win32-x64
github.vscode-pull-request-github-0.166.0
anthropic.claude-code-2.1.270-win32-x64
ms-ceintl.vscode-language-pack-zh-hans-1.131.2026090407
```

**关键理解：这个名字不是「仓库名」，是「装到磁盘上的产物目录名」。** 带版本号的原因只有一个——**磁盘上要能多版本并存**。**它与作者的工程仓叫什么完全无关。**

### 4.2 身份三件套（实测 `ms-vscode.cpptools` 的 `package.json`）

| 字段 | 实测值 | 可变？ |
|:--|:--|:--|
| `publisher` | `ms-vscode` | 🔴 **发布后永不可变**（身份的一半） |
| `name` | `cpptools` | 🔴 永不可变（身份的另一半） |
| `displayName` | `C/C++` | ✅ 随便改 |
| `version` | `1.35.0` | 每次发布必变 |
| `engines.vscode` | `^1.77.0` | 兼容区间 |

⇒ **`publisher.name`（如 `ms-vscode.cpptools`）= 身份**；`displayName` = 显示名。

**旁证（显示名可以多自由）**：`Anthropic.claude-code` 的 `displayName` 是 `Claude Code for VS Code`；`rust-lang.rust-analyzer` 的 `displayName` 就是 `rust-analyzer`。publisher 允许连字符与大小写混合。

### 4.3 内置扩展：97 个，目录名是**裸 id**

`<VS Code 安装目录>/resources/app/extensions/` 下 97 个内置扩展，目录名就是 `git/` `cpp/` `docker/` `emmet/`……**不带 publisher 也不带版本**（因为不需要与第三方区分、也不需要多版本并存）。身份写在各自 `package.json`（`"publisher":"vscode"`），**版本独立于壳**（内置 `git` 扩展 = `10.0.0`，VS Code = `1.105`）。
⇒ **这正是你要的模型（出厂插件独立版本），有人做了十年。**

### 4.4 对照结论

| 维度 | VS Code | LinkDesk（现状） | LinkDesk（N1-N6 落地后） |
|:--|:--|:--|:--|
| 身份 | `publisher.name`（不可变，在 manifest 里） | **目录名兜底**（不在 schema 里） | `pluginId`（显式声明，进 schema） |
| 显示名 | `displayName`（自由） | `name`（自由） | 不变（已对） |
| 版本独立于壳 | ✅ | ✅（`plugin.json.version`） | 不变 |
| 仓库名 | 与身份无关 | 无规则 | **自由**（N2） |
| 装机目录名 | `<publisher>.<name>-<version>[-平台]` | `<id>`（扁平） | 不变（`<id>` 够用——我们不需要多版本并存） |

> ✅ **已落笔（2026-09-14 E6#97f）：作者面条文现住 [`docs/03-插件制造/16-命名规范.md`](../../../03-插件制造/16-命名规范.md)。** 此后**改规则先改那边**（作者面是落点与读者所在），本节降级为**决策出处与论证**（N 系决策、VS Code 实测、七种名字的调查过程），不再逐字维护条文。
> ✅ **N3 已由用户拍板（2026-09-14，随 7.2 轮开工）：官方插件仓名惯例 = `linkdesk-plugin-<id>`** —— 全批 18 只统一，已按此建仓（`Encaron/linkdesk-plugin-<id>`）。**第三方零约束**（N2 不变）。
> ⚠️ **与既有两只官方仓不一致，是有意接受的不一致**：`hello-linkdesk` / `first-run-setup` 是裸名先例（E6 早期建、已上架，改名会断已发布链接）⇒ **不动它们**；新惯例从本批 18 只起生效，下一个官方插件按新惯例走。**这条只在本节维护**（作者面只放指针）。

| 名字 | 规则 | 强制 |
|:--|:--|:--:|
| `pluginId` | `^[A-Za-z0-9][A-Za-z0-9._-]*$`；**发布后永不可变**；建议小写连字符（虽然规则允许大写与点） | 🔴 强制 |
| `name`（显示名） | 任意字符串；可随时改；**改完须 bump 版本重发** | 强制（必填） |
| `version`（`plugin.json`） | `^\d+\.\d+\.\d+$`；**无预发布后缀**；**发布后不可改**（改了就是新版本）；内容变必 bump | 🔴 强制 |
| `version`（`package.json`） | **必须与 `plugin.json.version` 相等**（N6 第四处锚）；`private: true` 下它不是发布载体，但仍要一致 | 🔴 强制 |

### 5.1 版本号——四处同源（N6）

**版本号有四个落点，必须同源。改一处即四处同改：**

```
① CHANGELOG.md 段标题的版本号   ## v<version>
② plugin.json.version          ← 唯一真源（schema 级必填）
③ 目录条目 versions[].version   ← publish 自动写
④ package.json.version         ← N6 新增纳入（今天六只全是 1.0.0，与真版本脱节）
```

- ①②③ **既有规则**（`09-插件目录规范.md:90-94`「与版本号联动」+「三处的锚」）——**本规范引用不复制**。
- ④ 是 N6 新纳入的一处；机械兜底 = `#98e` 的门禁（`package.json.version === plugin.json.version`，**带负控**）。
- **两处不一致的后果**：`package.json` 是独立仓里新人（和 AI）**打开仓库第一眼看到的东西**——两个版本号并存且不一致，**必然有人 bump 错那一个**；而 `publish` 与内容指纹门禁读的都是 ② ⇒ **改错的那个 = 静默无效**（版本没升，更新链不认）。

### 5.2 版本号 —— 三段语义与 bump 判据（**引用既有权威，不在此重述**）

| 要查什么 | 去哪 |
|:--|:--|
| 什么时候 bump（MAJOR/MINOR/PATCH 判据、0.x 特例） | `.claude/skills/version-bump/SKILL.md` §一 核心判据表 |
| **四条版本轴的分工**（软件本体 / contracts / plugin-sdk / **插件自身 version**） | 同上 §〇 多轴模型——**插件版本轴早已是独立一条，服务对象 = 作者自己、发布点 = marketplace、维护者 = 作者** |
| 改了内容没 bump ⇒ 红 | `scripts/check-bundled-version-bump.mjs`（内容指纹比对 git HEAD blob） |
| `CHANGELOG.md` 段标题解析规则（`v` 可省 / 严格等于 `plugin.json.version` / **解析不出 ＝ 诚实留空不猜**） | `09-插件目录规范.md:69-81` |
| 版本与更新的关系（已装副本**按版本固化**，软件只补缺失、永不刷新已装） | `04-插件分发格式.md` §四 |

🔴 **不许在本规范里另写一套 bump 判据**——那会立刻变成第二份真相源。**本规范只加 N6 这第四处锚。**

> ⚠️ **一条 schema 级硬约束**：`version` 的 pattern 是 `^\d+\.\d+\.\d+$` ⇒ **`1.0.0-beta.1` 这类预发布后缀会被 schema 直接拒**。作者想表达"预发布"目前**没有语法可用**——这是现状，不是遗漏；若将来要支持，须先改 schema（属新能力，走 `contributes`/字段新增流程）。
| 分发件名 | `<pluginId>.linkdesk-plugin`（**不要手改**——它参与安装裁决） | 🔴 强制 |
| Release tag | `v<version>`（**由 `publish` 生成，不要手打**） | 🔴 强制 |
| GitHub 仓库名 | **自由**。官方插件建议统一惯例（N3，**待用户拍板**） | ⭕ 建议 |
| 本地目录名 | **自由**（容器约定见 D6）；**N1 落地后不再影响身份** | ⭕ 建议 |
| 视图容器 ID | `^[a-z][a-z0-9-]*$` | 🔴 强制 |

## 六、迁移红线（L7 执行者必读，与 [03-逐个迁移.md](03-逐个迁移.md) 同源）

🔴 **在 `pluginId` 显式化落地之前，一律不许改任何插件的目录名。**

| 步 | 动作 |
|:--:|:--|
| 1 | **`pluginId` 进 schema**（`public/schemas/plugin.schema.json` + 三份拷贝——`check-plugin-schema-sync` 管 3 组 7 份，**必须同笔同步**）；补进 `PluginManifest` 类型 |
| 2 | **官方 18 只全部显式声明 `pluginId`**（值 = 当前目录名，**逐只核对**，不许批量替换错位）；12 只 JSON 型同样要声明 |
| 3 | **兜底路径收窄**：`derivePluginId` 的目录名兜底保留（向后兼容第三方老插件），但**加警告**（`validate` 打黄灯提示「建议显式声明 pluginId」）；`validate` 的报错文案同步 |
| 4 | **迁移时目录名 = id**：`git filter-repo` 抽出的仓，本地目录名允许自由（N5），但**构建基线就绪前先保持 = id**；仓库名随便取（N2） |
| 5 | **迁移后必验身份未变**：新旧 zip 的 `pluginId` 相等 + 装到安装版后**安装目录名仍是原 id** |

**判据：** ① 18 只插件 `plugin.json` 都有 `pluginId`；② 三份 schema 同步绿灯；③ **负控**——把某插件目录改名后构建，其 `pluginId` **仍为声明值**（不是新目录名）；④ 老插件的目录名兜底仍工作（向后兼容未破）。
