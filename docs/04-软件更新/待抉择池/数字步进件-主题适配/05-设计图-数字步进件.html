本页是局部图：只画这一件控件，不画整个设置页。左半「现状」是照产品 CSS 一比一复刻的（含那条"死代码"的真实胜者），右半是两案改后。第 ③ 节有可拖的圆角滑杆，拖一下就能现场比出"跟不跟得上主题"。

你的原话（2026-10-03）：「① 首先 app.surfaceRadius 为 0，也就是直角时候，NumberInput 的加减号就和中间的不匹配，像不连着一样；② surfaceRadius 为圆角的时候更是惨不忍睹，加和减就是两个半圆在两边，中间是个胶囊，十分不协调；③ 它不适配很多情况，比如 app.uiFontScale，它所使用的 NumberInput 就很怪，％ 甚至在外面。」

① 今天长什么样：三个盒子硬拼，谁也不管谁

为什么②会发生：那一句 border-radius: 0 是死代码

产品的 NumberInput.css 里写着"字段圆角归零、好跟按钮拼成一条"，但同特异性下后加载的规则赢，而产物里两条规则的加载顺序是反的：

dist/pool.html

第 21 行　@linkdesk/ui.css　→　.ldk-number-input-field{ border-radius: 0 }
第 25 行　pool-*.css　　　→　.ldk-input{ border-radius: var(--radius-sm) }　← 后加载，赢

两条都是单类名、特异性相同 ⇒ 排在后面的 .ldk-input 胜。所以字段实际带着 var(--radius-sm) 的四角圆角——这正是"中间是个胶囊"的来源。症状②的根不是"圆角写错了"，是"有两套圆角规则在抢，而且抢输了"。

② 改后：一个盒子装三段

边框、圆角、高度各只有一处来源——都写在外框上。内部三段零圆角、零边框，被外框的圆角裁出来；单位搬进"值单元格"，跟值同一个盒子。

判据：从 0 拉到 32 的整条线上，控件的外轮廓应当是一个连续、单调变圆的形状；内部只应看到"被外轮廓裁出来的窄段 ＋ 内缩竖线"，不应出现任何独立成形的第二、第三个圆角块。32px 那一格是三案差异最大处——

④ 尺寸与字号档（症状③ 的正面回答）

产品的度量体系里，一切尺寸乘 --ui-scale、字号走 --font-size-*。今天的病根是按钮乘了、字段的 padding 没乘——所以放大字号后两段错位。改后容器高度是唯一来源，三段用 align-items: stretch 永远等高。

#问建议为什么
D1走 A 还是 BA 分段式三症状全治；"这两处能点"的可供性最强。B 更轻但低对比主题下会显得点不着。
