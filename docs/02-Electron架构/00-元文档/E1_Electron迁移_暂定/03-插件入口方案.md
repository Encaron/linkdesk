# 03 — 插件入口方案

> 2026-07-23。决定"插件怎么写"——React 组件还是 `activate()` 函数。
> **这个决策不是因为"现有代码是 React"——是按照 Encaron 的原则"若仅因为当前写了才这样做那最好不要"，从零重新论证。**

---

## 一、两种入口形式

### 方案 R：React 组件（当前形式）

```tsx
// plugins/map-plugin/index.tsx —— 一个文件 = 一个插件
import L from 'leaflet';

export default function MapView({ isActive }: { isActive: boolean }) {
  // Web 平台自由：import 任何 JS 库
  // 系统能力：window.linkdesk.serial.onData(...)
  // 壳服务：window.linkdesk.commands.register(...)
  return <div id="map" ref={mapRef} />;
}
```

**插件作者需要知道的：** React + `window.linkdesk` 的 TypeScript 类型定义。

### 方案 A：activate() 函数（VS Code 对标）

```typescript
// plugins/map-plugin/src/extension.ts —— 逻辑层
export function activate(context: linkdesk.ExtensionContext) {
  // 注册命令——纯逻辑，无 DOM
  context.subscriptions.push(
    linkdesk.commands.registerCommand('map.zoomTo', async (lat, lng) => {
      // 不能直接操作 DOM、不能 import React
      // 只能调 linkdesk.* API
    })
  );

  // 需要 UI？注册 WebviewView Provider
  context.subscriptions.push(
    linkdesk.window.createWebviewView({
      id: 'map.main',
      htmlPath: context.asWebviewUri('dist/map-ui.html'),
      // ↑ UI 部分在沙箱 HTML 里——独立的 WebView
    })
  );
}
```

**插件作者需要知道的：** `linkdesk.*` API 完整参考文档 + WebviewView 沙箱 HTML 的 postMessage 通信模型。

## 二、逐个维度对比

### 2.1 AI 友好度

| 维度 | 方案 R: React 组件 | 方案 A: activate() |
|------|------|------|
| AI 训练数据密度 | **极高**——GitHub 上几千万个 React 组件 | 中——只有 VS Code 扩展 |
| AI 生成一个插件 | 一个文件——`export default function` | 3+ 个文件——extension.ts + ui.html + bridge |
| AI 需要理解的概念 | 1 个：React | 3 个：ExtHost / WebviewView / postMessage |
| AI 犯错的概率 | 低——写 React 是 AI 最熟练的事 | 中——ExtHost vs WebView 上下文切换容易出错 |

**结论：方案 R 对 AI 更友好。** 这个项目 95% 代码是 AI 写的——AI 的训练数据密度直接决定代码质量。

### 2.2 插件自由度——Encaron 的"天马行空"

模拟 Encaron 想做一个"地图 + GPS 串口数据实时标注"插件：

**方案 R：**

对 AI 说："做一个地图插件，Leaflet，左边 GPS 数据标注，右边卫星数/海拔/速度面板"

AI 产出：**一个 React 组件文件**。`import L from 'leaflet'`，`window.linkdesk.serial.onData(...)`，把经纬度画到地图。丢进文件夹，装上去用。AI 只需要一个技能：React。

**方案 A：**

对 AI 说同样的话。

AI 产出：
1. `extension.ts`——ExtHost 里注册串口监听、坐标转换逻辑
2. `ui/map.html`——沙箱 HTML 页面，加载 Leaflet
3. `ui/map.js`——WebView 里的地图渲染、postMessage 收 ExtHost 的坐标数据
4. 一个 postMessage 桥类型定义

AI 需要理解三个概念：ExtHost（无 DOM 的 Node.js 进程）、WebviewView（沙箱 HTML）、postMessage（跨进程通信）。每次想做一个新插件，AI 要先判断"哪些放 ExtHost、哪些放 WebView、它们怎么通信"。

**Encaron 说："插件实现是 AI 的事情，我只负责说出想法。"** 方案 R 下 AI 只需要一个技能。方案 A 下 AI 每次都要处理"ExtHost vs WebView"的概念切换。不管是 AI 多花 token 还是多花时间——方案 R 的"天马行空到可运行插件"的路径更短、更可靠。

### 2.3 插件代码量

| | 方案 R | 方案 A |
|------|:--:|:--:|
| 简单插件（协议解析，无 UI） | 1 个文件 | 1 个文件（activate 里注册） |
| 中等插件（地图 + 串口数据） | 1 个文件 | 3+ 个文件 |
| 复杂插件（Monaco 编辑器替代） | 1 个文件 + node_modules | 4+ 个文件 + node_modules |

### 2.4 安全边界

| | 方案 R | 方案 A |
|------|------|------|
| 系统级能力谁控制 | `window.linkdesk`（preload 暴露） | `linkdesk.*`（ExtHost 注入） |
| 插件能绕过吗 | 不能——preload 的 contextBridge 是 Chromium 原生防线 | 不能——ExtHost 进程不暴露 require |
| 安全边界的定义方式 | `contextBridge.exposeInMainWorld('linkdesk', { ... })`——声明式 | `linkdesk.*` API 代理——IPC 到主进程 |
| 本质 | **都是白名单**——只暴露精选的系统能力 | **都是白名单**——只暴露精选的系统能力 |

**两种方案的安全边界本质相同。** 方案 R 是"preload 精选 API"——方案 A 是"ExtHost 精选 API"。白名单都在，只是暴露的位置不同。

方案 R 多一层天然优势——Web 平台能力完全不经过白名单。`import Leaflet`、`import THREE.js`——在插件的 WebContentsView 里直接用。方案 A 里这些能力必须通过 WebviewView 的沙箱 HTML 加载——不是不能，但多一层。

### 2.5 调试体验

| | 方案 R | 方案 A |
|------|------|------|
| 调试插件 UI | 开 WebContentsView 的 DevTools | 开 WebviewView 的 DevTools |
| 调试插件逻辑 | 同一个 DevTools（逻辑在 React 组件里） | **还要开** ExtHost 的 Node.js 调试器 |
| 报错追踪 | 一个调用栈 | 两个调用栈——ExtHost 抛了，WebView 收到 postMessage，中间断了 |
| 一个人调试 | 一个窗口 | 两个窗口，需要关联 |

### 2.6 对标 VS Code

方案 A 完全对标 VS Code——`activate()` + `vscode.*` API + WebviewView。

方案 R 对标的是"VS Code 的多进程底座 + React 作为 WebviewView 的实现技术"——**底座一样，插件写法不同**。

### 2.7 Encaron 的原则校验

**"若仅仅因为当前这样写了，为了省事这样干，那最好不要"**

方案 R 被选中不是因为现有 4 个插件是 React 组件——这是次要因素。被选中的原因是：
- 第 2.1 节（AI 友好度）——对 95% AI 产出的项目是关键
- 第 2.2 节（插件自由度）——"天马行空"到可运行插件的路径更短
- 第 2.5 节（调试体验）——单调用栈优于双调用栈

## 三、现有插件怎么处理

选定方案 R 后，4 个现有插件（terminal / settings / marketplace / workspace）**代码一行不改。** React 组件原样保留。

**不改的理由不是"省事"——是方案 R 在对比中胜出，不改恰好是正确决策的结果。**

如果方案 A 在对比中胜出——4 个插件的重写代价（AI ~半天）是值得付的。但方案 A 没胜出。

## 四、给未来 AI 的指引——写一个新插件需要什么

```
📦 my-plugin/
  ├── plugin.json          # 声明 name/version/entry/viewRole/tabBehavior/contributes
  ├── index.tsx            # React 组件——export default function
  └── (可选) sidebar.tsx   # 侧栏组件
```

**plugin.json 规范不在此文档定义**——见 `public/schemas/plugin.schema.json`。

**`window.linkdesk` API 参考**——见 `05-API与协议设计.md`。

**AI 写一个插件只需要两个知识点：**
1. React（AI 最熟练的事）
2. `window.linkdesk.*` 的 TypeScript 类型定义（AI 读一遍就会）

## 五、结论

| 维度 | 方案 R: React 组件 | 方案 A: activate() | 胜出 |
|------|:--:|:--:|:--:|
| AI 友好度 | 极高——AI 最熟 | 中——需专用知识 | **R** |
| 插件自由度（天马行空） | Web 平台全能力直接可用 | Web 能力在沙箱 WebView 中用 | **R** |
| 插件代码量 | 低（1 个文件） | 高（3+ 个文件） | **R** |
| 安全边界 | 清晰——preload contextBridge | 清晰——ExtHost IPC 代理 | **平** |
| 调试体验 | 单调用栈 | 双调用栈 | **R** |
| 对标 VS Code | 底座一样，写法不同 | 完全对标 | A |
| 现有代码兼容 | 100% | 0%（全部重写） | **R** |

**选 React 组件。** 不是因为现在写了 React——是对比后 React 确实更好。
