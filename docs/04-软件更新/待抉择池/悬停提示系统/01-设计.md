## 一、现状实测（读码，全部 `file:line`）

### 1.1 今天那个"菜单"小方框是什么

**它是 Chromium 原生 tooltip，不是 Electron 的、不是我们画的。**

- 落点：图标栏汉堡按钮挂的是 HTML `title` 属性 —— `src/pool/zones/icon-bar/IconBarZone.tsx:284`（`title={iconBar.hamburger.title}`）。
- 文案来源：`src/hooks/usePoolSync/iconbar.ts:82`（`title: t("菜单")`）。
- 机制来源：Electron 内嵌 Chromium ⇒ "给元素写 `title` 就自动出小方框"这套浏览器行为被免费继承。**外观（底色/边框/圆角/字体/字号/延迟/位置）全由系统决定，CSS 碰不到**，因此它**不跟壳的主题、三档玻璃模糊、全局字号缩放、`--ui-scale`**——一条都不跟。

> 结论：这是**系统 UI 长在软件里**。用户看到的是"我们的软件里有一个不属于我们的控件"。

### 1.3 已有第二套：`HintCard`（壳自己的玻璃卡）

- 位置：`src/components/shared/hint-card/HintCard.tsx` ＋ `HintCard.css`；经 `@linkdesk/ui` 导出（`packages/linkdesk-ui/src/index.ts:30`）。
- 出身：E6#120（2026-09-19），由市场插件"兼容状态"那张卡抽成壳共享件。
- 骨相（读 CSS 实测）：`width: 300px` 固定宽 · `padding: 12px` · 玻璃（`OverlayPortal` 的 `[data-overlay-wrapper]` 直接子 ⇒ 吃 `src/index.css` 深度 3 的 `backdrop-filter`）· 可带 `title` 行与 `note` 注脚 · 默认 `openDelayMs: 400`。
- 结构：**必然多包一层** `<span class="ldk-hint-card-host">`（`display: inline-flex`，`HintCard.css` 首条规则）。
- 全软件**只有 1 个消费方**：市场插件的 `CompatStatus`（外部仓 `marketplace/src/views/detail/DetailView/CompatStatus.tsx:61`），且那处文件头写死「⛔ 不挂 `title`——全部由 `HintCard` 承接」——**两套同屏会打架**，这是它自己记下的边界。

### 1.4 好消息：快捷键显示机制**已经存在**（用户第 3 问）

不用从零造。壳里已经有一条完整的"命令 → 快捷键文本"链，正是右键菜单在用的：

| 环节 | 位置 | 做什么 |
|:--|:--|:--|
| 查绑定 | `src/hooks/usePoolSync/titlebar.ts:85` | `ctx.keybindings?.find((k) => k.command === item.command)` |
| 格式化 | `src/hooks/usePoolSync/titlebar.ts:35` | `formatKeyLabel()`——`"ctrl+k ctrl+t"` → `"Ctrl+K Ctrl+T"`（含 chord） |
| 推给池 | `src/hooks/usePoolSync/titlebar.ts:89` | `...(kb?.key ? { shortcut: formatKeyLabel(kb.key) } : {})` |
| 池侧渲染 | `src/components/shared/context-menu/ContextMenu.tsx:405/439` | `<span className="ldk-ctx-item-shortcut">{item.shortcut}</span>` |

也就是说：**"自动带出快捷键"不是新能力，是把已有的一份数据多接一个消费方。** 这大幅压低本期成本。

### 1.5 顺带发现的归一化缺口：快捷键今天已有**两种画法**

| 画法 | 位置 | 长相 |
|:--|:--|:--|
| ① 等宽纯文本 | `src/components/shared/context-menu/ContextMenu.css:92` | `font-family: var(--font-mono)` ＋ `opacity: .6` ＋ `font-size: var(--font-size-xs)`——**不是键帽** |
| ② 键帽（keycap） | `src/pool/floating/quick-pick/QuickPickHost.css:238-245` | `<kbd>` ＋ `--kbd-bg`/`--kbd-border` ＋ `--font-size-2xs` ＋ `--radius-sm`——**是键帽** |

提示条会是**第三种**。所以本期必须顺带拍板：统一到哪一种（见 §九 待拍板 3）。**⛔ 不能让第三种悄悄出现。**

### 1.6 顺带发现：`--shadow-tooltip` 已预留但壳内零消费

- 定义在 `src/index.css:84`（`--shadow-tooltip: 0 2px 8px rgba(0, 0, 0, 0.3)`），契约见于 [外观主题化/02-变量契约.md](../../../02-Electron架构/E5.8_归一化基建/外观主题化/02-变量契约.md)。

- ⇒ 这个 token 当时就是给"提示"预留的。新件正好用上，**不需要新增阴影 token**。

## 二、设计前置（`design-flow` 8 维度）

### ① 能力边界

**壳能力**（核心准入三条件全满足）：多提供方 = 壳自身 43 处 ＋ 所有插件；多消费方 = 窗口内一切可见元素；桌子不知道内容 = 提示文案永远由调用方给，壳不下发任何用户可见句子。

**保底设计（壳能力必须先答）**：
- **保底一（主路径）**：渲染器由**壳无条件挂载**（挂进池根，随 `PoolZoneShell` 一起），无插件时壳自身的提示照样工作。
- **保底二（无障碍）**：`data-hint` 不是可访问名 ⇒ 每个提示点**必须同时具备 `aria-label`**（多数处已有）。渲染器不负责可访问名。
- **保底三（降级）**：提示是**纯增强**——渲染器加载失败/未挂载 ⇒ 只是"没有提示"，**绝不阻断任何交互**（不接管点击、不挡 hover、不占位）。⛔ 绝不在失败时退回 `title`（否则双显）。
- **⛔ 降级不做**：本件不做"退回原生 `title`"的兜底——那正是要消灭的东西。

### ② API 设计

- **不加任何新的 `window.linkdesk.*` 方法**。这是本设计最省钱的一条决定：走**属性式声明**（`data-hint` / `data-hint-command`）＋ **组件式门面**（`@linkdesk/ui` 导出 `HintTip`），两者共用同一个池内渲染器。
- ⇒ `audit-api-contracts` 的"契约四齐全"（d.ts ＋ preload ＋ IpcBridgeHandler ＋ 文档）**整套不需要**，因为不新增 API、不新增 IPC。
- 组件面：`@linkdesk/ui` 导出 `HintTip` ⇒ 过 `check-ui-surface-additive.mjs`（只加不删，天然是加）。
- 文档面：新件必须进 `docs/03-插件制造/05-插件UI写法规约.md` §12 与 `docs/03-plugin-authoring/05-ui-conventions.md`（`check-author-docs-bilingual` 守双语对齐）。

### ③ 通信方式设计

- **壳 → 池**：布局快照里补一份「命令 → `{ title, keybinding }`」映射。⚠️ **必须与菜单用的是同一份**（今天菜单走 `ctx.keybindings`，见 `titlebar.ts:85`）——**两把尺子必然漂移**（memory `two-rulers-one-caliber`）。
- **池 → 壳**：**无新通道**。提示纯展示，不回传。
- **插件 → 提示**：无通道——插件只是在**自己的 DOM 上写属性**，渲染器在同一文档里委托监听，天然生效。这是"插件独立铁律"的体现：插件不需要 import 壳任何东西。

### ④ 壳侧代码设计

| 项 | 落点 | 依据 |
|:--|:--|:--|
| 新件本体 | `src/components/shared/hint-tip/`（组件 ＋ css 同夹） | 照 `hint-card/` 先例（`src/components/shared/` 细分子夹） |
| 渲染器单例 | 池内，**必须复用浮层权威 `OverlayPortal` → `#overlay-root`** | `OverlayPortal.tsx:7/147`（E5.8#107 单一门）；⛔ 不新建浮层通道、不新建 overlay 目录 |
| 快捷键格式化 | **从 `src/hooks/usePoolSync/titlebar.ts:35` 抽成单一权威**（如 `src/core/utils/formatKeyLabel.ts`），菜单与提示共用 | 防两份漂移；菜单侧改为 import |
| 位置计算纯函数 | 与 `HintCard.computeCardPosition` 同族但**独立**（参数不同：无固定宽、四向） | 纯函数便于单测（照 `HintCard.test.tsx` 先例） |

**硬约束自查**：颜色走 `var(--xxx)`（✓ 全走 token）· 文字走 `t()`（✓ 文案由调用方给，壳自带句子才走 `t()`）· 插件 ID 不硬编码（✓）· 路径走 `getAssetPath()`（✓ 无资产）。

**命名纪律**（`docs/开发管理/壳目录规范.md` 命名铁律）：共享件名**描述"它是什么"，⛔ 不描述"谁在用"**。`HintTip` 是通用语义（✓）；机械判据 `src/components/shared/` 下 grep `marketplace|compat|file-tree|serial|settings|editor` ⇒ 必须零命中。

### ⑤ 插件侧代码设计

- **零强制引用**：绝大多数场景只需把 `title="导入"` 改成 `data-hint="导入"`——**一个属性替换，不 import 任何东西**。
- 需要"自动带快捷键"的场景：`data-hint-command="my-plugin.export"` ⇒ 渲染器取命令 title ＋ 快捷键。
- 需要复合内容（图标 ＋ 两行 ＋ 注脚）才用组件：`import { HintTip } from "@linkdesk/ui"`。
- **贡献点零新增**：不新增 `contributes.*` ⇒ `audit-contributes` 的"schema ＋ 加载器 ＋ 文档"三件套**不需要**。
- 测试 fixture 照硬约束 21 用虚构名。

### ⑥ 显示设计

- **在哪显示**：锚元素旁边（贴边浮层，随锚滚动/移动重算）。
- **显示什么**：主文案 ＋ 可选快捷键（等宽/keycap，见待拍板 3）＋ 可选第二行注脚 ＋ 可选图标。
- **怎么显示**：**不是玻璃卡**——宽度 `max-content` ＋ 上限（建议 `max-width: 260px`）· 小内边距 · `--shadow-tooltip`（已预留，§一·1.6）· 圆角 `--radius-sm` · 字号走 token。
- **位置**：四向（`top`/`bottom`/`left`/`right`）首选 ＋ 视口不足自动翻面 ＋ 两面都不够夹紧到边缘、**⛔ 不裁字**（照 `HintCard` 保底②）。
- **延时**：默认比 HintCard 短（HintCard 400ms 是"看一眼就走"的说明卡节奏；轻提示要更跟手）。具体值待拍板。
- **⛔ 密集场景**：鼠标扫过一排紧贴按钮（窗口按钮那排）**只许出一张**——上一个移开即收，不许排队/堆叠。

### ⑦ 配置设计

| 项 | 暂定 key | 默认 | 说明 |
|:--|:--|:--|:--|
| 总开关 | `app.hint.enabled` | `true` | 关掉 = 全软件无提示（原生也早已没有，因为全换掉了） |
| 延时 | `app.hint.delayMs` | 待拍板 | 意图延时 |
| 显示快捷键 | `app.hint.showKeybindings` | `true` | 与菜单的 `showKeybindings` 同语义（命名待拍板） |

- 设置页落 **「通用 › 界面」节**（v0.2.17 刚建好的 `prop.group` 二级分节，见 [已落地/设置页通用分组归类](../../已落地/设置页通用分组归类-并入更新组.md)）。
- **保底**：三条都有壳侧默认值，无插件也成立（`check-config-baseline.mjs` 守）。
- **⚠️ 待拍板 4：要不要给用户这个开关**——给 = 多一个设置面 ＋ i18n ＋ 门禁面；不给 = 零配置、更省。**AI 倾向：先给 `enabled` 一条**（用户能自救"我不想要提示"），延时/快捷键两条先不做（少即是多）。

### ⑧ 代码规范 + 验收

- 归一化：快捷键画法统一（§一·1.5）；`formatKeyLabel` 单权威；提示位置纯函数单测。

## 三、形态决策：为什么是新件，不是复用 `HintCard`（用户第 1 问）

**结论：必须新件，且新件的骨相是"轻提示条"，不是"小号 HintCard"。**

三条理由（前两条是硬伤，第三条是实现选择）：

1. **尺寸骨相冲突**——`HintCard.css` 写死 `width: 300px` ＋ `padding: 12px` ＋ 玻璃 ＋ 阴影。今天"菜单"是个约 40px 宽的系统小方框；换成 HintCard 是**一张 300px 宽的玻璃卡**。43 处全换不是"统一"，是**全都变重变吵**。尤其窗口按钮那排，鼠标扫过会连弹三张大卡。
2. **结构冲突**——`HintCard` 必然多包一层 `<span class="ldk-hint-card-host">`（`display: inline-flex`）。换上去之后原元素不再是 flex item、`>` 直接子选择器与 `:nth-child` 全变、"按钮的兄弟节点"假设错位。高危处：图标栏（按钮旁就有 `ldk-icon-drop-indicator` 兄弟）、标签栏（标签 `draggable`）、侧栏 section（拖拽协议）、`ldk-wc-btn` 紧贴排。**这是 43 处 DOM 结构手术 ＋ 逐个回归**。
3. **（可实现但要改件本身）** 第 2 条不是架构必然——`cloneElement` 可以把事件挂到原元素上、不包层。但那是**改 `HintCard`**，不是"拿来就用"；且它与"300px 玻璃卡"的第一条硬伤无关。

**⇒ 分工定案**：`HintCard` 继续管"说明卡"（有标题/注脚/玻璃/可长文案）；新件 `HintTip` 管"轻提示条"（一行/紧凑/跟手/零结构侵入）。两件同族不同物，`ldk-hint-*` 命名空间下并列。

> ⚠️ `HintCard.tsx` 文件头自己就写明了这个边界：「⛔ 不做点击弹层 / toast / 暗屏大面板 / 模态框——那是别的件」。**"轻提示条"就是它划出去的那个"别的件"。**

## 四、落地方案

### 4.1 两条用法（同一渲染器，两个门面）

**用法 A · 属性式（覆盖 ~95% 场景，也是存量收编的主力）**

```tsx
// 今天
<button title={t("菜单")} aria-label={t("菜单")}>…</button>
// 换后（DOM 结构零变化）
<button data-hint={t("菜单")} aria-label={t("菜单")}>…</button>

// 自动带快捷键与命令名（用户第 3 问）
<button data-hint-command="fileTree.refresh" aria-label={t("刷新")}>…</button>
```

**用法 B · 组件式（复合内容才用）**

```tsx
import { HintTip } from "@linkdesk/ui";

<HintTip label={t("刷新")} command="fileTree.refresh" note={t("同时刷新已展开目录")}>
  <button aria-label={t("刷新")}>…</button>
</HintTip>
```

**为什么属性式是主力**：① 零 DOM 结构变化 ⇒ 43 处 ＋ 95 处是**纯属性替换**，回归面极小；② 插件不需要 import 任何壳的东西 ⇒ 插件独立铁律天然满足；③ 单例渲染器 ⇒ 一处状态机、一处样式、一处翻面/夹紧逻辑，不会出现 43 份 `useState`；④ 与拖拽天然兼容（不包元素）。

**代价（诚实记账）**：属性式需要渲染器挂一个**全局 `pointerover`/`focusin` 委托监听**。三条注意事项：
- 它是 **DOM 事件**不是 IPC ⇒ 不触发硬约束 19 / ESLint `linkdesk/no-module-level-ipc-listener`；但仍必须**在组件 `useEffect` 内注册并返回清理**（不许模块级 guard）。
- 归属：宿主侧（池内渲染器自带），⛔ 不是插件每个自己挂。
- SDK 既有腿 `linkdesk/no-global-key-listener`（`packages/plugin-sdk/src/eslint/checks/no-global-key-listener.ts`）**只判 keydown/keyup**，不含 pointer ⇒ 不冲突；**⛔ 也不许顺手放宽它**。

### 5.1 三条腿（缺一条就有洞）

| 1 | **插件侧 ESLint 腿** | `packages/plugin-sdk/src/eslint/checks/no-native-title.ts` ＋ 进 `lint.ts:387` legs 名单 | **第三方作者**在自己仓里写的每一个 `title`（`ci-verify.mjs` 判红） |

> 🔴 **每条腿必须自带 `--self-test`（正控 ＋ 负控）并同批接进 `check` 链**——否则自测自己就是假门禁（memory `gate-selftest-must-be-wired`）。**⛔ 不许为了让红灯消失而放宽判据**（memory `gate-idle-vs-zero-violation`）。

### 5.2 判据与假红（本设计最关键的一段）

🔴 **最大风险：`title` 在 JSX 里极常见地是"组件 prop 名"，不是 DOM 属性。**

反例（今天仓库里真实存在）：`<SidebarSection title="" …>`、`<Button title={…}>`、`<Badge title={…}>`、视图元数据对象的 `.title` 字段。**一刀切判 `title=` ⇒ 满屏假红 ⇒ 门禁当场失效**（"假红让真红失效"）。

**判据设计（三档）**：

| 档 | 形态 | 判定 |
|:--:|:--|:--|
| **判红** | `title` 落在**小写 HTML 标签**上（`<button title=` / `<span title=` / `<div title=` / `<input title=`…） | 一定落到 DOM ⇒ 红 |
| **按登记表判** | `title` 落在**大写组件**上 | 查「转发登记表」：已知会把 `title` 转发到 DOM 的共享件（`Button.tsx:47`、`Badge.tsx:19`、`Combobox.tsx:134`、`SelectBox.tsx:143`、`DynamicSelect.tsx:139`）⇒ 红；不在表内 ⇒ 放行（它只是自己的 prop） |
| **豁免口** | 正当形态 | `// linkdesk-allow-native-title: <理由>`——照 SDK 既有 `disable.ts` 模式（腿 id 同名可 disable），**理由必填** |

> ⚠️ 转发登记表本身要**防漂移**：登记表若与共享件实现脱节就变成假门禁。**建议**：登记表由共享件源码的**显式标记**生成/校验（比如共享件转发 `title` 的那一行带锚注释），由门禁 `--self-test` 的负控钉住。**⚠️ 待拍板 6**：也可以退一步——**组件一律放行，只判小写标签**（更少假红、但漏掉 `Button title=` 这条真漏点）。AI 倾向：**先做"小写标签 ＋ 五只已知转发件硬编码表"**，生成式登记留作后续归一化件。

### 5.3 存量怎么办：白名单账，不清零就红会瘫痪提交

- 壳侧今天 43 处、插件侧 95 处——**一开红就是 138 处，没人能提交**。
- ⇒ 照仓库既有做法（先例：`scripts/css-selector-baseline.json` 选择器形态基线）：**门禁只判新增**，存量进 `scripts/native-title-baseline.json` 白名单，**收编一处销一行**。
- **收编进度 = 白名单长度递减**，可读可公示；插件侧同理（各仓自己的基线，由 SDK 腿带 `--baseline` 或仓内账）。
- **⚠️ 待拍板 6**：是否给存量定"限期清零"，还是"只判新增、存量随缘"。

## 十、不做清单（边界）

- ⛔ **不替代 `HintCard`**——说明卡（有标题/注脚/长文案/玻璃）继续归它，两件分工。
- ⛔ **不做可交互提示**——条内不放按钮/链接（那是 `HintCard` 已划的禁区，也是本件避免"提示变成菜单"）。
- ⛔ **不加新 `window.linkdesk.*` API、不加新 IPC 通道、不加新 `contributes.*`**——属性式是刻意的设计选择（省掉整套契约面）。
- ⛔ **不新建浮层通道**——必须复用 `OverlayPortal` → `#overlay-root`（E5.8#107 单一门）。
- ⛔ **不动 `--z-*` 语义层级**——复用既有档（提示是轻浮层，具体档位实现时按 `overlayLayer` 表定）。
- ⛔ **不做富文本/Markdown 提示**、⛔ **不做触摸长按菜单**（触屏只做"点按出条"保底）。
- ⛔ **不在插件里加壳 import**——属性式保证第三方永远不需要 import 壳。
- ⛔ **不为凑绿放宽任何既有门禁**（尤其 `no-global-key-listener`）。

## 十一、残余风险与诚实边界

1. **全局委托监听是新增的宿主侧常驻监听**——归属与清理必须写死在渲染器里（`useEffect` ＋ 返回清理，⛔ 模块级 guard）；池层是共享渲染进程，漏清理 = 全软件泄漏。**这是本件最大的实现风险。**
2. **转发登记表可能腐烂**（§五·5.2）——若不做生成式校验，它有变成假门禁的天然趋势。**已登记为后续归一化件候选**。
3. **"揭示类"用短延时是否真的更好用，属**体感判断**——参考图只能给静态对照，最终要 dev 实机让用户试。
4. **95 处插件侧是粗测**——精确数字会变；本档所有插件侧结论以"粗测"标注，不收编前不写死。
5. **`--shadow-tooltip` 的语义**：今天定义在 `src/index.css:84`、由主题六域 token 管辖（`radius`/`shadow` 域），新件消费它 ⇒ 主题若覆盖该 token，提示条跟走。**这是设计想要的**，但需在实现时确认主题配方里没有把它当成别的东西。
6. **本件与本轮"菜单补全"（[`../菜单补全.md`](../菜单补全.md)）有交界**——菜单项若要带提示，两边要约定同一份数据源（命令映射）。**建议**：菜单补全先做，提示条后做，提示条直接复用菜单已推的那份数据。
