### E5.6#23.7 🔴 数据流基础设施——菜单项预解析 + Promise 返回路径 + OverlayWindow 渲染器

> **由来：** #23.5/#23.6 假设 ContextMenu 组件可以直接搬到 OverlayWindow 渲染。
>   审计发现 ContextMenu 的三行核心代码（`getItems` / `executeCommand` / `resolveChildren`）全依赖 OverlayWindow 不存在的 API。
>   [preload-overlay.ts](linkdesk/electron/preload-overlay.ts) 只暴露 `overlay.ready/onCommand/sendResult` + `events.on`——零 `menu`/`commands` API。
>   类似 #22 的 `setIgnoreMouseEvents` 不转发 mousedown——计划假设了一个不存在的路径。
>
>   **🔥 根因——聪慧组件不能搬进哑容器：**
>   - 单 WebView 时代：ContextMenu 是函数调用——`getItems()` 同堆直接读 MenuRegistry
>   - Pool 模型时代：ContextMenu 变成跨进程通信——`getItems()` → IPC → 壳 → MenuRegistry → IPC 回来
>   - **OverlayWindow 时代：三件事（获取数据/执行命令/解析子菜单）从同一个函数调用栈拆到三个不同进程**
>   - 不是设计错误——是写 #23 计划时潜意识假设还留在单进程思维："搬过去就行了"
>   - 拆解方案：壳预解析数据 + OverlayWindow 纯渲染 + 壳路由结果。聪慧→哑的代价是 9 个任务。
>   - 📖 详见 memory [[overlaywindow-smart-to-dumb]]
>
> **目标：** 壳预解析菜单项 → 数据发给 OverlayWindow → MenuRenderer 接收 props 渲染 → 用户点击 → `sendResult` 回传 `commandId` → 壳路由执行。
> **原则：** OverlayWindow = 哑渲染器——不获取数据、不执行命令、不知道菜单项来自哪个插件。

### E5.6#24.5 🔴 聪慧→哑 拆分——QuickPick/Toast/Dialog/SelectBox/ColorPicker 数据流

> **由来：** #24 跟 #23 同一根因——假设组件可以"搬到 OverlayWindow"。
>   但 QuickPick 是**持续双向流**（用户每敲一键 → IPC → 过滤 → IPC 回来 → 重渲染），
>   比 ContextMenu 的"发一次、点一下"复杂一个数量级。Toast/Dialog/ColorPicker 相对简单，
>   但也需区分：哪个用 `show()`（Promise 返回）、哪个用 `push()`（fire-and-forget）、
>   哪个用持续流（QuickPick 实时过滤）。
>
>   **🔥 根因——聪慧组件不能搬进哑容器（同 #23.7）：**
>   - QuickPick 当前：mount → `getCommands()` 全量拉取 → 用户输入 → 本地 filter → 键盘导航 → `executeCommand()` → 关闭
>   - 拆到 OverlayWindow 后：每击键 IPC 到壳过滤 → 结果回传 → OverlayWindow 渲染 → 选中回传 → 壳执行
>   - 五件事（拉取/过滤/导航/执行/UI）拆到三个进程。ContextMenu 是三次 IPC，QuickPick 是 N 次（N = 用户击键数）
>   - 📖 详见 memory [[overlaywindow-smart-to-dumb]]
>
> **复用 #23.7 基础设施：**
> - `overlay.show()` Promise 路径（#23.7a/b）→ Dialog/ColorPicker/SelectBox
> - `overlay.push()` fire-and-forget（已有）→ Toast
> - `MenuRenderer`（#23.7e）→ HamburgerMenu
> - `originPool` 追踪（#23.7h）→ QuickPick 命令执行路由
> - 主题同步（#23.7i）→ 全部

# Phase 8.5：🔴 Registry 主进程化——消灭跨进程数据隔离 bug 类

> 🔥 **Phase 8 后做。Phase 9 之前。** Phase 8 删光了 per-tab 旧代码，架构处于最简态——此时迁移 Registry 零旧代码干扰。
> **根因：** TypeScript 模块在 Electron 多进程中各自独立实例化。壳渲染进程 `loader.ts` 调 `registerLangDef()` 写入壳的 `_extMap`，主进程 `ipcMain.handle` 读主进程的空 `_extMap` → 查询永远为空。
> **E5.6#14 的 `langDef`/`protocol` 两处 bug 是同一根因的两个实例。** `plugins:call` 代理是战术补丁——每加一个 Registry 就多加一个 case，AI 每次都要猜"数据在哪个进程"。
> **目标：** 主进程启动时预加载所有 plugin.json，自行填充各 Registry。所有进程平等查询主进程——不再代理、不再猜。
> 📖 **设计依据：** 本对话——Approach B（主进程唯一真相源）vs A（每通道代理）的 10 条要求对照。B 在全部 10 条上胜出。
>
> **方案：主进程 plugin.json 预加载。**
> ```
> 主进程启动 → 扫描 plugins/builtin/ + plugins/user/
>            → 读每个 plugin.json
>            → 调 registerLangDef() / registerProtocol() / ...
>            → 主进程 Registry._extMap 有数据 ✅
>
> 壳渲染进程 loader.ts → 动态 import React 组件（不变）
>                      → 调 registerLangDef() → 写壳侧 Registry（壳内直接 import 用）
>
> Pool 进程 preload → langDef.get() → IPC langDef:get → 主进程读自己的 _extMap → 返回 ✅
> ```
> **壳侧 Registry 保留**——壳内插件（marketplace 等 shell glob 插件）仍直接 import `@src/core`。
> 两个 Registry 实例并存但数据一致——壳 loader.ts 注册时同时 IPC 同步到主进程。
> **主进程 Registry 是"服务端缓存"——不替换壳侧 Registry，而是镜像一份供跨进程查询。**
