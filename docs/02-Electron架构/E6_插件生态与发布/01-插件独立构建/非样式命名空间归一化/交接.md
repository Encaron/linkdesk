### ⑴ **本轴是干什么的**

E6 第 1 层（插件独立构建）的**第二个专项**，紧接 [样式命名空间归一化](../样式命名空间归一化/00-整理档案.md)（CSS 系列）。

起因：用户 2026-09-16 问「**除了 UI 这部分外，其余部分有没有类似的问题？如数据通信部分？……又或者声明的东西，又或者命令类。**」＋「**不仅仅是我提到的，你还可以自己再找一找。**」

**真问题一句话**：**软件里有一批「公共花名册」——谁都能往上写一个名字，写的时候不核对归属，撞了只小声嘟囔（或连嘟囔都没有）。**

**同形判据（四条全中才算）**：名字空间**扁平** ＋ **多方都能写** ＋ **写时无归属校验** ＋ **冲突静默**（最多 `console.warn`）。
🔴 **第四条是关键**：`console.warn` **对用户不可见，对「被覆盖的那一方作者」也不可见**——因为他**在自己机器上没装对方插件**，一切正常。**「被覆盖」这件事，受害方永远收不到通知。**

**真根因（每一棒收尾都要能复述这句）**：

> **不是名字起坏了，是「谁的名字」被寄托在「取名自觉」上——账本要么没有，要么只用来打印一行字，而宿主自己的名字和第三方名字长着同一张脸。**

**本轴的统一机制（**两条，都在仓里有现成先例，不必发明**）**：
- **A. 宿主保留名账 —— 进 SDK**（照 `packages/plugin-sdk/schemas/reserved-class-names.json` 的形状：单一真相源 ＋ 随 npm 包下发 ⇒ **插件仓自己就能判** ＋ 两条腿读同一份 ＋ **双向对账门禁**）；
- **B. 运行时归属仲裁 —— 首撞者保留 ＋ 后来者降级不覆盖 ＋ `console.error`**（🔴 **不许抛错**：`parseContributions` 无 try/catch ⇒ 抛错 = **整只插件装不上，比现在更坏**）。

**本格（第 0 格）已交付**：① [00 总方案](00-整理档案.md)（根因 / 全量读数 / 收口定义 / 残余边界 / 原则对照 / 轮次总表）；② **12 份任务书**（[01](01-任务-命令id归属评估.md)–[12](12-任务-本轴收口复核.md)）；③ E6 清单任务格；④ 本交接文件。

### ⑶ **你这一棒 = 1.31（`#111a` 命令 id 与协议 id 归属 · 评估）**

**直接读 [01-任务-命令id归属评估.md](01-任务-命令id归属评估.md)**——它已按「专门的 AI 拿来就能干」写好：读数、复跑命令、候选路线、判据草案、禁区、进场第一步全备。

**为什么它排第一**（本格定的序）：命令 id 是**最危险的一条**（功能级静默：**界面正常、点下去执行的是别人的 handler**），而且本格实测发现它**比 CSS 系列 30 号档记的还坏一层**：

> 🔴 **运行时注册的命令，它的「归属」是从名字的第一段推出来的**（`src/core/registry/commands/CommandRegistry.ts:150,186` 的 `commandId.split(".")[0]` ＋ `electron/preload-pool/commands.ts:36-39` 的 `commandOwnerId()`）。
> ⇒ **两个插件都运行时注册 `acme.doThing`，推导归属都是 `"acme"`** ⇒ 覆盖检测的 `pid !== pluginId` **恒 false** ⇒ 🔴 **静默覆盖，连 `console.warn` 都不会响。**

**你要产出的三件事**：
1. **归属来源的方案裁决**（甲「让运行时注册带真身份」/ 乙「名字前缀结构化」/ 丙「运行时仲裁」/ 丁「复合键」——**四条逐条裁，选出一个，不许只列不选**）；
2. **存量 21 个 `explorer.*` 命令 id 的裁决**（**全在 `file-tree`**，照抄 VS Code 的功能命名空间：「漏网」还是「有意的功能命名空间」？**代价量化**）；

🔴 **两条最容易做错的地方（先记住）**：

- **不许改坏「同插件重注册」的合法语义**（`CommandRegistry.ts:59-61`：loader 先注册元数据 → 组件 mount 时重注册 handler，**只更新 handler/title、不动元数据**——**这是既有设计，逐字保留**）。
