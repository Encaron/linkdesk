## 一、这个升级要解决什么（先讲清价值，再谈代价）

**今天的门禁**（`packages/plugin-sdk` 的 `check-css-namespace` 腿）只拦一件事：插件**裸定义**了**宿主保留名**。它的三个局限：

1. **黑名单**：作者必须先知道那 14 个名字才不会撞——**违反「AI 不需要查表」**（memory `ai-friendliness-three-layers` 层 4）。
2. **管不到插件 ↔ 插件**：两只第三方插件都用 `.toolbar`，门禁**看不见**——而池文档里所有已加载插件**同表**（实读 8 张样式表）。这是本系列唯一**完全没有保护**的轴，且它随生态长大而变大。
3. **只管定义侧**：插件把保留名**渲染**到自有元素上（如 `className="toggle"`）无人拦（SDK 源码注释明写「scoped 调优是合法消费，不在本腿管辖」）。

**升级目标**：一条**可一句话复述、不需要任何清单**的规则——「**插件 CSS 里给自有元素起的类名，必须带自己的前缀**」。

## 二、必须先在评估里量清的读数（**不许拍脑袋**）

1. **21 只插件仓（官方 18 + 两只夹具 + my-cool-plugin）各自的前缀实况**：逐仓 `grep` 出 CSS 类名的前缀分布。已有零散读数可作起点——**它们的前缀≠ pluginId**：
   - serial-monitor → `control-*`；
   - marketplace → `mpd-*` / `ms-*`；
   - settings → `settings-*`；
   - file-tree → `file-tree-*`（含 `file-tree-badge`）。
   ⇒ **这是本评估的核心事实**：前缀是**约定俗成的缩写**，不是 id 派生。
2. **每仓「裸定义」的真实数量**（＝升级后要修的行数）：L7 读数说官方 9 只带 CSS 的插件**零裸定义**——但那是按「保留名」判的；**按「无前缀」重扫**要重新量（预期：绝大多数已带前缀，个别可能有 `.row` `.item` 这种）。
3. **`plugin.json` schema 现状**：三份字节相等的拷贝在哪（`packages/plugin-sdk/schemas/plugin.schema.json` / `public/schemas/` / SDK 包内），加一个字段要动几处、`check-plugin-schema-sync` 怎么守。

## 三、候选路线（评估至少覆盖这三条，可再提）

| 路线 | 规则形态 | 代价 | 风险 |
|:--|:--|:--|:--|
| **(a) 清单声明** | `plugin.json` 新增 `cssPrefix` 字段；门禁 = 「裸定义必须以此前缀开头」 | 改 schema（三份字节相等）+ 21 仓回填 + SDK 发版 + 脚手架模板 + 作者面文档 | 低（照硬约束 11「插件身份唯一来源是声明」）；**新增一个作者要填的字段** |
| **(b) id 派生** | 裸定义必须以 `<pluginId>-` 开头 | **不用新字段**，但 `control-*` / `mpd-*` / `ms-*` 这类仓要**改类名**（又一次破坏面 + 重发） | 中（改的是已发布插件的自有类名——**只影响它们自己**，不影响别的插件；但仍要逐仓重发） |
| **(c) 最弱可用规则** | 裸定义**必须含连字符**（拒绝 `.toolbar` / `.badge` 这种单词），不要求前缀归属 | **零改造**（官方 9 只应该都过） | 只能拦「手滑用了通用单词」，**拦不住** `.my-panel` vs `.your-panel` 这类跨插件撞名——收益打折但**成本几乎为零** |

> 评估时请把 (c) 也认真算进去——它是「今天就能上、以后可升级」的中间档；不要把「完美规则」当唯一选项（本仓纪律：宁要能落地的尺子，不要永远立不起来的完美尺）。
