## 1. V2 走到了天花板

### 1.1 V2 做对了什么

串口核心只有四件事——打开、读、写、关。方括号协议让收发数据有了语义，PC 端不再是被动显示器，变成了主动控制台。

V2 证明了这条路走得通。课设三张卡一行，没写一行上位机代码。波形图、传感面板、OLED 画板、双语切换——每一个功能都是用户真正用了、满意了的。

### 1.2 三重天花板

**协议分裂。** `sensor`/`ctrl`/`plot`/`slider`/`key`/`joystick`/`draw`/`fft`/`display`——7 个顶层 type，`sensor` 下 9 个 subType。路由是一个 10+ 分支 switch。MCU 固件要记每种 type 的字段顺序。

**面板筒仓。** Sliders.cs / Keys.cs / Sensors.cs / Plot.cs / Joystick.cs / Display.cs——每个面板是一个封闭王国。滑杆逻辑写了两遍，波形逻辑写了两遍。加按键卡片需要写第三遍按键逻辑。Sensors.cs 膨胀到 3570 行。

**UI 线程瓶颈。** 串口回调 + OxyPlot 渲染 + Slider ValueChanged 三者抢一个线程。v2.2 到 v2.6.7 修了四轮卡顿，修的都是"让每次回调做更少的事"，从没动过"所有东西在同一个线程排队"的根因。卡片多了照样卡。

### 1.3 V2.6 的教训

v2.6 做了主题迁移 B+C（93 处 SetResourceReference）+ 双语系统（~515 EnMap，10 个踩坑）。改动量巨大，用户打开 exe 只能看到"切主题不闪了"和"多了一个中/EN 按钮"。这些是必要的基础设施，但不应该在所有面板写完后再统一手术。

V3 从第一天起就内置：主题引擎、双语引擎、数据管道分离、组件注册表。

### 1.4 V3 的优势

V2 是在完全不知道最终形态的情况下摸索出来的——协议字段是一点一点加的，面板是一个一个摞的，架构没有机会提前设计。

V3 不一样。V3 有：

- V2 的全部协议逻辑作为参照
- 21 色设计系统直接搬
- ~515 条 EnMap 直接搬
- DataConverter 四个方法直接搬
- UI 样式全部有现成参照物——卡片长什么样、开关长什么样、竖条色怎么排
- 几十个踩坑经验

和 V2 相比，V3 发生变化的部分：协议路由简化（ID 替代 type+subType）、卡片壳/组件分离、数据管道双线程、框架切换（WPF → Tauri+React）、CSS 变量主题系统（替代 DynamicResource）、CodeMirror 6 接收区（替代 AvalonEdit）。不变的部分见 §9 继承资产清单。

### 1.5 设计哲学的延伸：AI 友好

V2 的经验已经证明了一个模式——用户不会 C#/WPF，每一行代码都是 AI 写的。V3 延续这个模式，但把它推进一步：**不仅 AI 写代码，以后 AI 可以直接改运行中的软件配置。**

这不需要 AI 学会"操作 GUI"。需要的是：

**所有 GUI 可改的东西，背后有一个纯文本入口。**

| 你改什么 | 纯文本入口 | AI 能改吗 |
|------|------|:--:|
| 卡片类型/颜色/标题/单位 | `workspace.json`，一层平铺 | ✅ |
| 翻译文字 | `EnMap.json`，key-value | ✅ |
| 串口默认参数 | `prefs.json` | ✅ |
| 旧协议映射规则 | 静态 JSON 翻译表 | ✅ |
| MCU 端协议宏 | `#define ID_CHIP_TEMP "chip_temp"` | ✅ |

这和 VS Code 的 `settings.json`、CubeMX 的 `.ioc` 文件是同一个哲学——**文本文件本身就是 API。** 人点鼠标走 GUI、人手写 JSON、AI 改 JSON——三条路径的目标文件是同一个。不需要额外设计"AI 接口"。

具体到你说的场景——"扫我的 MCU 工程，把发送改成 V3 协议，上位机卡片自动配上"：

```
① AI grep MCU 工程 → 找到所有 printf("[...]", ...) 
② 正则提取卡片 ID（方括号第一个字段）→ [chip_temp, pid_p, heart_wave]
③ 推断组件类型（temp → gauge, led → switch, 拿不准 → generic）
④ 生成 mcu_protocol.h（宏定义 + ! 定义函数）+ workspace.json
⑤ 你确认 → AI 改 2 个文本文件 → V3 热加载 → 卡片出现
```

V2 做不到"完全不动手"是因为 AI 要理解 MVVM 的嵌套 Dictionary、WPF 的 Binding、协议 type/subType 路由——这些概念是 WPF 特有的，和"一张卡"的直觉不对齐。V3 的 workspace.json 是平铺的卡片列表，卡片 ID 就是 key——AI 不需要理解任何框架概念就能改。

**这不是"以后再加的特性"。** 从第一天写 CardRegistry 和 PreferenceService 的时候，把接口设计成模块级导出——React 组件能 import，未来的 WebSocket handler 也能 import。不改架构、不加后门——只是写代码的时候不把接口锁死在 UI 组件里。

#### ⚠️ 硬约束：workspace.json 禁止嵌套

```
✅ { "cards": [ { "id": "chip_temp", "type": "gauge", "color": "#FFC107" } ] }
❌ { "panels": { "sensors": { "cards": { "chip_temp": { "type": "gauge" } } } } }
```

每多一层嵌套，AI 找到目标字段的 grep 难度翻一倍。这不是代码质量问题——是 **可被 AI 编辑的门槛**。卡片列表必须是一层平铺数组。

#### ⚠️ 架构规则：唯一配置入口

```ts
// PreferenceService —— 这是唯一能改配置的地方
class PreferenceService {
  saveCard(card: CardConfig): void    // GUI 用、未来的 WebSocket 用、文件监听也用
  deleteCard(id: string): void
  getCard(id: string): CardConfig
}

// React 组件调它：
button.onClick → PreferenceService.saveCard(card)

// 以后的 WebSocket 也调它：
ws.on('setCard', data) → PreferenceService.saveCard(data)

// 文件监听也走它：
fs.watch('workspace.json') → 读到新内容 → PreferenceService 对比 → UI 自动刷新
```

人和 AI 在同一个接口上交汇。没有"人用的 API"和"AI 用的 API"两套东西。

#### AI 友好的衡量标准

做完之后，这个测试必须通过：

> "帮我新加一张卡——温度传感器，ID 是 room_temp，深红色竖条，范围 -10 到 60，单位 °C"

AI 只需要改两个纯文本文件：
- `mcu_protocol.h` → 加一行 `#define ID_ROOM_TEMP "room_temp"` + 一行 `printf`
- `workspace.json` → 加一个 `{ "id": "room_temp", "type": "gauge", ... }` 对象

改完 V3 不重启就生效（文件监听 → 自动热重载 → 卡片出现）。如果 AI 需要改 React 源码、重新 `npm build`——那就不是 AI 友好。

#### AI 场景一：多设备，多套卡片布局

不同 STM32 板子发不同的卡片 ID，卡片排布也不同。V3 的解法：**多 workspace 文件。**

```
workspaces/
  workspace_f407_temp.json      ← F407 温度测试台
  workspace_pid_tuning.json     ← PID 调参
  workspace_heart_rate.json     ← 课设心率
  workspace_default.json        ← 默认
```

顶栏下拉框切换：

```
COM3 ▼  115200 ▼  [● 打开]  工作台: [PID调参 ▼]  中/EN  ☀  ⚙
```

选 "PID调参" → 加载 `workspace_pid_tuning.json` → 卡片全部替换。每个 workspace 文件是一个独立、平铺的卡片列表。AI 可以一次生成多份，也可以在不同 workspace 之间复制卡片。

V2 做不到——卡片状态分散在 `prefs.json` + `SensorPanelViewModel` 运行时 + `Sensors.cs` 的 15 个 Dictionary。换设备 = 删光重建。V3 的卡片配置和运行时状态从架构上分离了——workspace 只管"什么卡、放哪里"，运行时数据由 MCU 发。

#### AI 场景二：让 AI 排卡片

"波形图放左边，三个 PID 滑杆摞在它右边"——AI 的视角：

```json
// AI 知道 pid_plot 是 plot（宽 400×380），pid_p/i/d 是 slider（306×160）
// 算一把坐标：

{ "id": "pid_plot", "x": 0,   "y": 0,   "w": 400, "h": 380 },
{ "id": "pid_p",    "x": 410, "y": 0,   "w": 306, "h": 160 },
{ "id": "pid_i",    "x": 410, "y": 170, "w": 306, "h": 160 },
{ "id": "pid_d",    "x": 410, "y": 340, "w": 306, "h": 160 }
```

不需要碰 React 组件代码，不需要理解 WPF 的 MeasureOverride。就是改 JSON 数组里的 x/y/w/h。同一件事，你自己拖更快——但意义不在快，在**路径是通的**。今天 AI 排四张卡，明天就能把一整页布局存成模板发给别人。

#### AI 场景三：跨项目工作台保留——"上次的心率界面还在不在？"

**用户的实际使用模式：**

```
第一周："我在做心率检测课设"
  → AI 生成 mcu_protocol.h + workspace_heart_rate.json
  → 界面：心率波形 + 实时 BPM 值 + 搏间间隔 + 报警上下限滑杆 + 报警开关灯
  → 保存为 workspace_heart_rate.json

第二周："换课题了，车距报警"
  → AI 生成新的 #define + workspace_distance_alarm.json
  → 界面：超声波波形 + 距离 Gauge + 蜂鸣器开关 + 阈值滑杆
  → 保存为 workspace_distance_alarm.json

第三周："切回心率那块板子看看"
  → 顶栏下拉框选"心率检测" → 六张卡原样回来
  → 串口不关、数据管道不断
```

**AI 只需要改两个纯文本文件（和场景三同路径），外加生成一份独立的 workspace JSON：**

```
① 心率：
   mcu_protocol.h  ← 加 6 个 #define（heart_wave / heart_bpm / heart_ibi / alarm_high / alarm_low / alarm_led）
   workspace_heart_rate.json ← 6 张卡（plot + gauge×2 + slider×2 + switch）
   烧录 → V3 打开 → 选 workspace → 心率界面就绪

② 车距：
   mcu_protocol.h  ← 加 4 个 #define（dist_wave / distance / buzzer / threshold）
   workspace_distance_alarm.json ← 4 张卡（plot + gauge + switch + slider）
   烧录 → V3 切 workspace → 车距界面就绪

③ 切回心率：
   顶栏选 "心率检测" → 心率界面原样回来。
   MCU 固件可能还是车距的 → 收到车距数据找不到对应 ID → 自动建 generic 卡
   → 用户一眼知道"忘换固件了"
```

**和场景一的区别：** 场景一讲的是多 workspace 文件的技术方案，场景四是用户的实际使用节奏——**同一套硬件、不同课设项目、卡片配置跨项目保留。** 每个课设 = 一个 workspace 文件 = 一个独立的"项目存档"。AI 不需要"记着上次的配置"——workspace JSON 文件本身就是存档。

**V2 做不到的原因：** V2 的卡片状态散落在 `prefs.json` + `SensorPanelViewModel` 运行时 + `Sensors.cs` 的 15 个 Dictionary。换课设 = 全部删光重建。V3 的 workspace 是独立 JSON，切换就是加载另一个文件。

#### AI 场景四：扫 MCU 工程，全自动配好

```
你："扫我的 MCU 工程，把发送改成 V3 协议，上位机卡片自动配上"
AI：
  ① grep printf("[...]", ...) → 提取所有卡片 ID
  ② 推断类型（temp → gauge, 拿不准 → generic）
  ③ 生成 mcu_protocol.h（宏 + ! 定义） + workspace.json
  ④ MCU 工程里加 #include "mcu_protocol.h"
你：点两下确认 → 烧录 MCU → 打开 V3 → 卡片全在
```

V2 里 AI 做不了这件事，因为 AI 要理解 `sensor`/`temp`/`humidity` 这个 type/subType 体系才能改对。V3 里 AI 只需要知道卡片 ID 和组件类型——都是字符串平铺。**协议简化不是为了省 1 个字段，是为了让 AI 能扫 MCU 代码自动配对上位机。**

## 2. 协议 V3

### 2.0 先说清楚 V2 的协议到底痛在哪

V2 协议格式：

```
[sensor, 子类型, 卡片名, 值, 辅助参数]
  ↑        ↑       ↑     ↑      ↑
 type   subType   name  value   aux
```

每一条消息的前两个字段（type + subType）是**给 PC 端路由器看的**——路由器需要读懂 "这是 sensor 类型下的 temp 子类型"，然后分发给"温度卡处理器"。

这带来了三个问题：

**问题一：MCU 固件要记两套东西。** `printf("[sensor,temp,%s,%.1f]\r\n", name, value)` —— MCU 固件需要知道 "温度数据对应的 type 是 sensor，subType 是 temp"。这不是嵌入式开发者的自然思维。嵌入式开发者的自然思维是："我有一张叫 chip_temp 的卡片，我要往它里面发 42.5"。

**问题二：路由代码永远在膨胀。** 每加一种新卡片类型，就要在路由器的 switch 里加一个分支。V2 的 `sensor` 下面有 9 个子类型，加上 `ctrl`、`slider`、`plot`、`key` 等等，路由器是一个 10+ 分支的 switch 树。这条 switch 语句会随着功能增加永远增长。

**问题三：同一个逻辑实体有两套协议。** 滑杆数据——MCU 上报走 `[slider,pid,0.5]`，PC 端拖拽发送走 `[ctrl,slider,pid,0.78]`。同是滑杆，方向不同就要用不同格式。MCU 固件要解析两种格式。PC 端路由器要把两条路径导向同一个滑杆组件。

### 2.1 V3 的核心思想：卡片 ID 就是唯一路由凭证

V2 的 type 和 subType 被**一个字段**替代：卡片 ID。

```
V2:  [sensor,  temp,  chip,   42.5]    ← 前两个字段是路由信息，不是数据
      路由用   路由用  数据    数据

V3:  [chip_temp,  42.5]                ← 第一个字段是路由信息，其余全是数据
      路由用      数据
```

路由器只需要知道一件事：**"chip_temp" 对应那张卡片。** 路由动作永远是：`查字典(cardId) → 找到卡片 → 把剩余字段丢给它`。路由器不知道、也不需要知道这张卡是温度卡、开关卡还是波形卡。

### 2.2 两种消息类型

**卡片定义（可选）—— `[!卡片ID, 类型, 显示名, 单位, 参数...]`**

以 `!` 开头，告诉 PC 端"这张卡长什么样"。**这是 MCU 替用户在编辑页面里预先配置好——一条可选捷径，不是必须走的流程。**

**没有 `!` 也完全没问题。** MCU 直接发 `[chip_temp, 42.5]` → PC 端自动建一张通用卡 → 用户在编辑页面里点 ⚙ 把类型改成 gauge、设单位、设颜色。配置完就永久记住了，下次启动自动恢复。

**V2 能做到的事 V3 的纯数据做不到：** V2 的 `[sensor,temp,chip,42.5]` 里有 `temp` 子类型，PC 端可以直接建"温度卡"（黄色竖条 + °C + 迷你波形）。V3 的 `[chip_temp, 42.5]` 里没有类型信息，PC 端只能建"通用卡"（灰色竖条）。想跳过手动配置 → 发 `!`；不在乎 → 不发 `!` 手动配。**上位机的编辑页面就是干这个的。**

```
// 只需要告诉 PC 端一次，启动时发：
[!chip_temp,  gauge,   芯片温度,  °C,    0,     100  ]
    ↑          ↑        ↑         ↑      ↑      ↑
  卡片ID    组件类型   显示名    单位   最小值  最大值

[!blue_led,   switch,  蓝色LED                          ]
[!pid_p,      slider,  PID_P参数, 空,   0,     1,   0.01]
[!heart_wave, plot,    心率波形                          ]
[!btn_panel,  keypad,  按键面板,   空,   2x2            ]
```

| 字段位置 | 含义 | 是否必须 |
|:--:|------|:--:|
| `!id` | 卡片唯一 ID | 是 |
| 类型 | 组件类型名（gauge/switch/slider/plot/keypad/...） | 是 |
| 显示名 | 卡片标题栏显示的文字 | 否（不写就用 ID） |
| 单位 | 值后面的单位字符串 | 否 |
| 后续参数 | 组件特定参数（min/max/step/layout/...） | 否 |

**数据（双向）—— `[卡片ID, 字段1, 字段2, ...]`**

不带 `!`，就是普通数据。MCU 发给 PC 和 PC 发给 MCU 的格式**完全相同**。

```
// MCU → PC：芯片温度现在是 42.5 度
[chip_temp, 42.5]

// MCU → PC：LED 当前是开着的
[blue_led, on]

// PC → MCU：用户拖了滑杆
[pid_p, 0.78]

// PC → MCU：用户点了开关
[blue_led, off]
```

**两个方向的格式完全一样，没有区别。** MCU 只需要知道自己的卡片 ID 是什么。收到消息 → 解析 ID → 如果是认识的 ID 就更新该 ID 对应的变量；发送消息 → `printf("[%s,%s]\r\n", ID_xxx, value)`。

### 2.3 路由全过程，逐步走一遍

假设串口收到一行：`[chip_temp, 42.5]`

```
第 1 步：协议解析器
  输入："[chip_temp, 42.5]"
  输出：["chip_temp", "42.5"]        ← 按逗号切分，去掉方括号

第 2 步：路由器
  取第一个元素 → "chip_temp"
  查字典 registry.get("chip_temp") → 找到 Card 对象

第 3 步：投递
  card.component.onData( ["42.5"] )  ← 把第一个字段之后的所有字段传给组件

第 4 步：组件自己处理
  GaugeComponent.onData( ["42.5"] ):
    this.value = "42.5"              ← 更新内部状态
    React 自动 diff → UI 更新          ← 框架渲染
```

全程没有 switch，没有分支判断。路由核心是 O(1) 字典查找，加多少新类型都不变。（"3 行"是指字典查找这一步——其上的协议解析层和其下的组件内字段分发仍有各自的工作量，复杂度没有消失，只是搬家了。）

### 2.4 如果卡片 ID 不存在

```
收到 [unknown_id, some_value]
      ↓
查字典 → 没找到
      ↓
自动创建一张 generic 卡：
  { id: "unknown_id", type: "generic", title: "unknown_id" }
      ↓
插入工作台（默认位置）
      ↓
generic 卡的 onData(["some_value"]) → 显示值
```

一张灰色竖条的通用卡出现在工作台上，显示值 "some_value"。**编辑页面就是做这个的：**

1. 点卡片的 ⚙ → 弹出配置面板
2. 类型从 generic 改成 gauge（或 switch / slider / plot / ...）
3. 改显示名、单位、颜色、范围参数
4. 配置保存到 workspace.json → 下次启动自动恢复，不需要 MCU 再发 `!`

**所以实际使用流程是：** MCU 管发数据，编辑页面管配置卡片外观。`!` 只是在 MCU 侧就能确定外观时省掉手动配置的快捷键。两个路径都可以，互不依赖。

#### ⚠️ 设计要点：改类型 = 替换组件，历史数据丢失

用户把一张卡从 generic 改成 plot 时，卡片壳不变（标题、ID、布局位置），但内部组件被替换——GaugeComponent 销毁，PlotComponent 创建。新组件从空状态开始，旧组件累积的历史数据（如波形点队列）不会迁移。

**这不需要修复。** 因为 MCU 持续在发数据（几十 ms 一帧），新组件几秒内就会被填满。波形图、数值显示都是如此。设计意图：组件替换的简洁性 > 跨类型数据迁移的复杂性。

**给未来 AI 的约束：** 不要为"改类型丢历史数据"写缓存逻辑。不要试图把 GaugeComponent 的 history 数组复制给 PlotComponent。保持组件替换是干净的销毁+创建。

#### ⚠️ 设计要点：`!` 定义和用户手动修改的优先级

MCU 发了 `[!chip_temp, gauge, 芯片温度, °C, 0, 100]`，用户在编辑页面把标题改成"温度"，单位改成 °F。下次 MCU 又发了一遍 `!` 定义——该用谁的？

**规则：手动修改优先。** 每个可配置字段（标题、单位、颜色、min/max、...）跟踪是否被用户手动改过。`!` 到达时：
- 未被手动改过的字段 → 用 `!` 的最新值
- 已被手动改过的字段（dirty）→ 保留用户的修改

**给未来 AI 的约束：** 这个 dirty 标记存 workspace.json，不存 MCU 固件。不要试图在 `!` 定义里加"锁定字段"之类的语法——规则就是用户 > MCU，简单且不可推翻。

### 2.5 MCU 固件侧完整示例

```c
// ===== 宏定义（集中管理所有卡片 ID）=====
#define ID_CHIP_TEMP    "chip_temp"     // 芯片温度
#define ID_AIR_HUMI     "air_humi"      // 环境湿度
#define ID_BLUE_LED     "blue_led"      // 蓝色LED开关
#define ID_PID_P        "pid_p"         // PID_P参数滑杆
#define ID_HEART_WAVE   "heart_wave"    // 心率波形
#define ID_BTN_PANEL    "btn_panel"     // 按键面板

// ===== 启动时（可选，定义卡片外观）=====
void send_card_definitions(void) {
    printf("[!%s,gauge,%s,°C,0,100]\r\n",   ID_CHIP_TEMP, "芯片温度");
    printf("[!%s,gauge,%s,%%,0,100]\r\n",   ID_AIR_HUMI,  "环境湿度");
    printf("[!%s,switch,%s]\r\n",            ID_BLUE_LED,  "蓝色LED");
    printf("[!%s,slider,%s,,0,1,0.01]\r\n", ID_PID_P,     "PID_P参数");
    printf("[!%s,plot,%s]\r\n",              ID_HEART_WAVE, "心率波形");
}

// ===== 运行时（数据更新）=====
void main_loop(void) {
    float temp = read_chip_temp();
    printf("[%s,%.1f]\r\n", ID_CHIP_TEMP, temp);
    //      ↑          ↑
    //    卡片ID      值（无需 type、无需 subType）
    
    float humi = read_humidity();
    printf("[%s,%.1f]\r\n", ID_AIR_HUMI, humi);
    
    // 波形：多一个"曲线名"字段
    printf("[%s,ch1,%.1f]\r\n", ID_HEART_WAVE, adc_val);
    delay_ms(100);
}

// ===== 串口接收（PC → MCU 控制指令）=====
void on_serial_received(char* frame) {
    char id[32], value[32];
    parse_bracket_frame(frame, id, value);
    //   解析 "[pid_p, 0.78]" → id="pid_p", value="0.78"
    
    if (strcmp(id, ID_PID_P) == 0) {
        pid_p = atof(value);           // 更新 PID 参数
        set_pwm_output(pid_p);          // 生效
    }
    else if (strcmp(id, ID_BLUE_LED) == 0) {
        if (strcmp(value, "on") == 0)  HAL_GPIO_WritePin(...);
        else                           HAL_GPIO_ResetPin(...);
    }
}
```

**整个 MCU 固件只需要：**
1. 一堆 `#define` 宏定义卡片 ID
2. 一个 `parse_bracket_frame()` 函数解析逗号分隔
3. 发送：`printf("[%s,%.1f]\r\n", id, value)`
4. 接收：`if (strcmp(id, ...))` 分支处理

没有 type、没有 subType、没有方向区分。V2 里 MCU 固件要判断 "这是 sensor 还是 ctrl 还是 slider"，V3 里只需要判断 "这是哪张卡"。

### 2.6 场景示例一：PID 调参——三滑杆 + 一波形图（三条曲线）

```c
#define ID_PID_P      "pid_p"      // P参数滑杆
#define ID_PID_I      "pid_i"      // I参数滑杆
#define ID_PID_D      "pid_d"      // D参数滑杆
#define ID_PID_PLOT   "pid_plot"   // 波形图（一张卡装三条曲线）

void setup() {
    printf("[!%s,slider,P参数,,0,100,0.1]\r\n", ID_PID_P);
    printf("[!%s,slider,I参数,,0,10,0.01]\r\n", ID_PID_I);
    printf("[!%s,slider,D参数,,0,5,0.01]\r\n",  ID_PID_D);
    printf("[!%s,plot,PID响应曲线]\r\n",          ID_PID_PLOT);
}

void loop() {
    // 三张滑杆卡：各发各的当前值
    printf("[%s,%.1f]\r\n", ID_PID_P, g_pid.kp);
    printf("[%s,%.2f]\r\n", ID_PID_I, g_pid.ki);
    printf("[%s,%.2f]\r\n", ID_PID_D, g_pid.kd);

    // 一张波形图卡：三条曲线，靠"曲线名"字段区分
    float p_term = g_pid.p_output;
    float i_term = g_pid.i_output;
    float d_term = g_pid.d_output;
    printf("[%s,%s,%.2f]\r\n", ID_PID_PLOT, "P分量", p_term);
    printf("[%s,%s,%.2f]\r\n", ID_PID_PLOT, "I分量", i_term);
    printf("[%s,%s,%.2f]\r\n", ID_PID_PLOT, "D分量", d_term);
    //        ↑         ↑        ↑
    //    卡片ID    曲线名     值
    //  同卡同曲线名→追加点 / 同卡新曲线名→自动建新曲线（新颜色）

    delay(50);
}
```

**PC 端行为：** 收到 `[pid_plot, P分量, 50.0]` → PlotComponent 查内部字典 "P分量" → 没找到 → 新建红色曲线。下一帧 `[pid_plot, P分量, 51.2]` → 找到 "P分量" → 追加点。同理 I分量 蓝色、D分量 绿色。图例自动生成，颜色自动分配。

### 2.7 场景示例二：按钮控制灯——按键卡 + 开关卡联动

```c
#define ID_BTN_A      "btn_a"       // 按键卡
#define ID_BLUE_LED   "blue_led"    // 开关卡

void setup() {
    printf("[!%s,keypad,按键面板,,1x1]\r\n", ID_BTN_A);
    printf("[!%s,switch,蓝色LED]\r\n",       ID_BLUE_LED);
    printf("[%s,%s]\r\n", ID_BLUE_LED, led_is_on ? "on" : "off");
}

void on_serial_recv(char* frame) {
    char id[32], val[32];
    parse_bracket(frame, id, val);

    if (strcmp(id, ID_BTN_A) == 0) {
        if (strcmp(val, "down") == 0) {
            led_is_on = !led_is_on;           // 翻转 LED
            HAL_GPIO_WritePin(LED_PORT, led_is_on);  // 物理灯同步
            printf("[%s,%s]\r\n", ID_BLUE_LED, led_is_on ? "on" : "off");
            //  ↑ MCU 把新状态发回 → PC 端开关卡自动更新
        }
    }
}
```

**数据流：** 用户按按键卡 [A] → PC 发 `[btn_a, down]` → MCU 翻转物理 LED → MCU 发 `[blue_led, on]` → PC 端开关卡从灰变橙。**物理灯和 PC 端开关卡始终同步——因为 MCU 是唯一的状态持有者，PC 端只是显示 MCU 告诉它的状态。**

### 2.8 各 ID 的字段结构一览

每个卡片 ID 自己定义自己的字段规则。路由器不管。OLED 走独立视图路由（§2.10），不走卡片注册表：

> **OLED 行仅描述协议格式——它不经过卡片路由，而是由 🎨 视图直接接管。**

| 组件 | 字段 1 | 字段 2 | 字段 3+ | 说明 |
|------|:--:|:--:|:--:|------|
| Gauge | 值 | 辅助值（可选） | — | `[chip_temp, 42.5]` / `[chip_temp, 42.5, 85]` |
| Switch | on/off | — | — | `[blue_led, on]` |
| Slider | 数值 | — | — | `[pid_p, 0.50]` |
| Plot | 曲线名 | 数值 | — | `[heart_wave, ch1, 1023]` |
| KeyPad | 键名 | 动作 | — | `[btn_panel, LED_ON, down]` |
| FFT | 点数 | bins... | — | `[mic_fft, 256, 0.12, 0.08, ...]` |
| OLED | 子命令 | 参数... | — | `[oled, rect, 10, 10, 50, 30, #F00, 2]` |

**不同卡片、不同字段数量、不同含义——各管各的，谁也不干扰谁。**

### 2.9 PC 端发送（用户操作 → 自动生成协议帧）

用户在工作台上的操作会自动生成协议帧，不需要手动输入：

| 用户操作 | PC 端自动发送 |
|------|------|
| 点击开关卡 | `[blue_led, off]` ← 反转当前状态 |
| 拖拽滑杆 | `[pid_p, 0.78]` ← 节流 50ms |
| 按下按键 | `[btn_panel, LED_ON, down]` |
| 松开按键 | `[btn_panel, LED_ON, up]` |
| 拖拽摇杆 | `[joy_1, 0.35, -0.42]` ← 跟随鼠标 |
| 终端输入栏手动输入 | 原样发送（可以手动敲 `[pid_p, 0.55]` 回车） |

所有发送都走同一个 SendQueue → 后台 Worker 写串口。

### 2.10 OLED 协议（独立视图，不走卡片路由）

OLED 不是卡片组件（见 §7），而是通过 🎨 图标进入的独立视图。它的协议处理不经过卡片注册表，而是视图内部直接接管 `oled` ID 的消息：

```
收到 [oled, rect, 10, 10, 50, 30, #FF0000, 2]
  → cardRegistry.get("oled") → OLED 视图接管
  → 视图内部第二级子命令路由：rect → circle → text → set → del → clear
```

### 2.11 和 V2 旧协议的兼容

V3 可以加一层旧格式翻译器，确保旧的 MCU 固件在新软件上照常工作：

```
收到旧格式：[sensor, temp, chip, 42.5]
    ↓
翻译器：将旧 type("sensor") + subType("temp") + name("chip") → 映射为新 ID "chip_temp"
    ↓
等同于收到了 [chip_temp, 42.5]
    ↓
走正常路由
```

翻译表是一个静态 JSON 配置文件，用户或 AI 可以在初始化时自动生成。**MCU 固件不需要改任何一行代码。**

**V2/V3 天然互斥：** V3 的 `!` 前缀保证了 V2 解析器不会把 `[!chip_temp,...]` 误判为某种 V2 协议——V2 的 type 字段不可能是 `!chip_temp`。同理 V3 解析器看到 `[sensor,...]` 没有 `!` 也不可能是卡片定义。过渡期 MCU 同时发两种格式时，PC 端先尝试 V3 解析，失败后再走 V2 翻译器，路径互不干扰。

## 4. 卡片架构：壳与组件分离

### 4.1 层级

```
工作台
```

## 5. 数据管道：怎么做到不卡

### 5.1 V2 卡顿的根因

```
═══════════════════════════════════════════
        所有东西在同一个 UI 线程排队
═══════════════════════════════════════════

UI 线程：
  ├── 串口 DataReceived → Parse → Route → UpdateCardUI × N → InvalidatePlot
  ├── Slider.ValueChanged（每像素触发）→ UpdateUI → 发串口
  ├── 30Hz 定时器 → RefreshMiniPlots
  └── WPF 布局 + 渲染

三条线串行。拖滑杆被数据回调挤到后面 → 用户看到蠕动。
```

### 5.2 V3 方案

```
═══════════════════════════════════════════
         生产/消费分离，两条线程互不阻塞
═══════════════════════════════════════════

┌─ Web Worker（串口线程）─────────────────┐
│                                         │
│  port.read()  →  ParseProtocol(line)    │
│       │                                 │
│       ▼                                 │
│  RingBuffer.write({id, fields})  ← 无锁  │
│                                         │
│  SendQueue  →  port.write(data)         │
└──────────────┬──────────────────────────┘
               │
       RingBuffer (512 条)
               │
┌──────────────▼──────────────────────────┐
│  UI 线程（渲染，60fps）                    │
│                                         │
│  requestAnimationFrame:                 │
│    results = RingBuffer.drainAll()      │
│    // 同卡取最新，波形保留全历史点          │
│    results.forEach(r →                  │
│      card.Component.OnData(r.fields))   │
│                                         │
│  用户操作（独立的轻量路径）：               │
│    拖滑杆 → 只改一个 double              │
│          → CSS transform（GPU 合成线程）  │
│          → Throttle 50ms → SendQueue    │
└─────────────────────────────────────────┘
```

### 5.3 关键设计

**RingBuffer（无锁环形缓冲）。** 单生产者（Worker 写）、单消费者（UI 读）。容量 512 条。UI 来不及读 → 最老数据被覆盖，安全——UI 只关心最新值。

**固定帧率。** UI 以 60fps 从 RingBuffer 取数据，不是"收到一条就刷一次"。同卡片 ID 有 N 条 → 只取最新（波形除外——自己在组件内维护点队列）。

**滑杆走合成线程。** CSS `transform` 在 GPU 合成线程处理滑块移动，不占 UI 线程。ValueChanged 回调只做两件事：更新一个 double + 通知节流器。

**发送队列独立。** 所有组件的发送请求进 SendQueue，Worker 线程取出写串口。等待 I/O 不阻塞 UI。

**虚拟化渲染。** 只渲染视口内可见的卡片。CSS Grid + IntersectionObserver 判断进出视口。

**虚拟化边界条件（⚠️ 需要正确处理）：**
- **波形卡 unmount 后再 mount → 历史点丢失。** 点队列需存在卡片级 store（不随组件销毁），组件挂载时从 store 恢复
- **离开视口后立即卸载 → 快速滚动抖动。** 加 200ms 防抖——离开视口后 200ms 内不卸载。大多数快速滚动会在 200ms 内停下，不会触发大量 mount/unmount
- **ECharts 实例延迟。** 同上防抖解决。`react-virtual` 或 `@tanstack/virtual` 等成熟库已内置这些策略，不需自己造轮子

### 5.4 效果预估

| 场景 | V2 | V3 |
|------|------|------|
| MCU 1kHz 发数据 | UI 线程被回调淹没，帧率 ~5fps | RingBuffer 缓冲，UI 稳定 60fps |
| 拖滑杆 + 波形滚动 | 抢 UI 线程，滑杆蠕动 | 各自独立路径，互不影响 |
| 100 张卡（50 不可见） | 全部渲染，线性增长 | 只渲染 50 张，资源恒定 |

## 6. 拖拽重排与编辑模式

### 6.1 拖拽：常态化，零门槛

拖拽不是编辑模式专属功能。每张卡的标题栏右侧常驻 ⠿ 句柄，**随时可拖**：

```
┌──────────────────┐
│ 芯片温度   ⚙ ⠿  │  ← ⠿ 句柄常驻，按住直接拖
│                  │
│     42.5 °C      │  ← 内容区，正常交互
│                  │
└──────────────────┘
```

- 按住 ⠿ → 卡片微微放大 + 半透明
- 移动鼠标 → 其他卡片按网格规则滑动让位（200ms 缓动）
- 松手 → 吸附到位，布局存入 workspace.json
- 拖拽句柄不在 Pointer Events 区域内 → 内容区照常交互
- **Windows 开始屏幕磁贴就是这个逻辑**

### 6.2 编辑模式：仅管增删

点 [✏编辑] 按钮进入编辑模式，只做两件事：

1. 卡片间隙出现 [+] 插入热区 → 点击弹出添加卡片面板
2. 每张卡右上角出现 × 删除按钮

退出编辑模式 → 热区和删除按钮消失。拖拽功能不受影响——退出编辑模式后 ⠿ 仍然可用。

### 6.3 备选方案：长按拖拽（保留可能性）

未来可以考虑：鼠标按住卡片内容区的空白区域 ≥ 400ms → 视觉回弹 → 进入拖拽。好处是去掉 ⠿ 句柄更加干净，但 400ms 在桌面端可能体感偏慢。先做方案 A（句柄常驻），如果觉得 ⠿ 碍眼，再切到长按方案或做成可配置选项。

### 6.4 对比

| | 安卓桌面 | Windows 开始屏幕 | V3 |
|------|:--:|:--:|:--:|
| 触发 | 长按 | 直接拖 | 标题栏 ⠿ 句柄常驻拖拽 |
| 让位 | 实时滑动 | 实时滑动 | 200ms 缓动 |
| 吸附 | 最近空位 | 网格 | 网格 |
| 分组 | 文件夹 | 磁贴组 | CardGroup（有标题） |
| 卡片大小 | 1×1/2×1/2×2 | 小/中/大/宽 | 小/中/宽（待定） |
| 防误触 | 长按延迟 | 无编辑模式概念 | 句柄和内容区分区，互不干扰 |

### 6.5 实现

`react-grid-layout`（GitHub 20k+ stars）处理网格布局和拖拽动画核心。胶水代码（Card 组件对接、编辑模式下显示/隐藏 [+] 和 ×、workspace.json 序列化、响应式断点适配）仍需约 250-400 行，但比 WPF 手写完整 Panel + 状态机 + 缓动动画（800-1300 行）少一个数量级。

## 8. 框架选择 ✨

**Tauri + React。**

### 为什么不是 WPF

| V3 核心需求 | WPF | Tauri + React |
|------|------|------|
| 卡片网格 + 拖拽 | 手写 Panel + 状态机，~800-1300 行 | react-grid-layout 处理网格布局和拖拽动画，胶水代码（Card 对接、编辑模式切换、workspace.json 序列化）仍需 ~250-400 行 |
| 不卡（数据管道） | BackgroundWorker + Dispatcher | Web Worker，标准 API |
| 主题切换 | DynamicResource + 41 条约束中 ~20 条为了防它 | CSS 变量，一行 `var(--bg)` 穿透全页面 |
| 双语 | 自建 Locale 系统 | react-i18next，现成库 |
| 组件化 | UserControl | React Component |

WPF 三条核心需求都要手写。React 三条都有成熟库。不是 WPF 不好——是 V3 的需求恰好落在 Web 技术的舒适区。

### 风险

- **Rust 串口层**（~150 行）：AI 对 Rust 串口的训练数据少于 C#，预估需要 5-10 轮对话稳定（Windows COM 枚举、USB 热插拔、异常断开恢复）。代码量小，一旦跑通基本不动
- **项目骨架搭建**：前 5-10 轮对话可能在 Rust 环境安装、IPC 通道调试、WebView2 行为差异上磕绊。骨架通了之后，后续每一轮都是加 React 组件——和加 WPF UserControl 感觉类似
- **降级方案**：如果 Rust 串口层踩烦了，切 Electron 主进程（~150 行 Node.js serialport），渲染层全部保留不动。等串口稳定了再回来也只要改回 150 行 Rust

### 产物

- 单文件 exe，~5MB（Tauri + 自带 WebView2）
- 不需要装 .NET 运行时
- React 代码可部分复用到 React Native（如果将来做手机端）

## 10. 待确认的决策

### 决策 1：卡片 ID 命名

**建议：只用英文/数字/下划线**（和 C 变量名规则一致）。如 `chip_temp`。V2 的 MCU 固件用宏定义管理，`#define ID_CHIP_TEMP "chip_temp"`。

### 决策 2：卡片定义 [!...] 协议

**建议可选。** MCU 不发 → PC 自动建 generic 卡（灰色竖条，可自定义一切）。MCU 发了 → 预设类型和外观，减少手动配置。

### 决策 3：V2 旧协议兼容

**建议兼容。** 新软件加一层翻译器——旧格式 `[sensor,temp,chip,42.5]` 自动映射到新路由。旧 MCU 固件不用改。

### 决策 4：卡片大小

| 选项 | 说明 |
|------|------|
| A：固定 3 档 | 小 160×160 / 中 306×160 / 宽 400×380。和 V2 一致 |
| B：自由 resize | 右下角拖拽句柄，占几个格子 |
| C：全同大小 | 最简，只拖拽重排 |

### 决策 5：OLED 保留还是砍掉

待你决定。V2 花了 34 个踩坑才稳定。HTML5 Canvas 做 2D 绘图是原生能力，比 WPF Canvas 干净很多，但工具交互（选择/控点/旋转/文字）需要重新实现。

## 11. 应用基础设施层（Phase 5）✨

> 2026-07-20。Phase 4 完成了"插件能被加载"。
> Phase 5 做"插件能做什么"——命令、设置、菜单、协议四根柱子。
> 详细设计：[P5-设计.md](../P5-应用基础设施/P5-设计.md)

### 11.1 为什么不是卡片架构

原计划 Phase 5 做卡片工作台。但 Phase 4 暴露一个问题：插件加载后除了"变成标签页"什么都做不了。没有命令系统、没有设置贡献、没有右键菜单。如果直接做卡片，卡片也只是另一个"变标签页"的视图。

**基础设施必须在前。** VS Code 在 1.0 之前就建好了 `contributes` 框架，之后所有功能（Debug、Terminal、SCM）都是扩展自己贡献的。

### 11.2 四个子系统

| 子系统 | 对标 VS Code | 解决什么问题 |
|--------|-------------|-------------|
| Command Registry | `contributes.commands` | 插件注册命令 → 命令面板/右键菜单/快捷键 |
| Configuration Registry | `contributes.configuration` | 插件贡献设置 → Settings Editor 自动渲染 |
| Menu Registry | `contributes.menus` | 右键菜单/齿轮菜单 动态内容 |
| Protocol Registry | 无对标 | 协议解析器注册/切换 |

### 11.3 设计原则

**核心不感知插件。** 和 Phase 4 一样——Settings Editor 不知道有哪些设置项，只知道"ConfigurationRegistry 里有什么"。右键菜单不知道有哪些菜单项，只知道"MenuService.getMenuItems() 返回什么"。

**一条声明多处生效。** `"contributes": { "configuration": {...} }` → Settings Editor 自动出现此插件的设置分组，插件代码直接用 `useConfiguration()` 读写，`settings.json` 自动包含此插件的所有配置项。

**插件不说话，基础设施自动接。** 这是 VS Code 的精髓，也是 Phase 5 要达成的。
