> 2026-07-24。从旧 P7c 语言部分迁移，适配 Electron。
> **性质：** 让语言包成为一等公民插件类型 + 跨 WebView i18n 同步。和 E3b 主题引擎完全对称。

## 一、语言两层退路

| 层 | VS Code | LinkDesk |
|------|------|------|
| 第 1 层 | 语言包扩展的 NLS 翻译表 | `plugins/lang-en/` + `plugins/lang-zh/` 语言插件 |
| 第 2 层 | `localize(key, message)` 的 `message` 参数 = 英文原文 | `t(key)` → key 不在翻译表 → 返回 key 本身（key = 中文原文） |

```
#2 对应 VS Code 的 localize() fallback：
  i18next.init({
    fallbackLng: false,
    parseMissingKeyHandler: (key) => key  // t("终端") → "终端"（key 本身就是中文原文）
  })

  外加 ~30 个壳级关键 key 的显式英文兜底：
  resources: { en: { translation: { "终端": "Terminal", "设置": "Settings", ... } } }
```

## 二、语言贡献格式

### 模式 A：单语言插件（一个插件 = 一个语言）

```json
{
  "name": "日本語",
  "contributes": {
    "languages": [
      {
        "id": "ja",
        "label": "日本語",
        "path": "ja.json"
      }
    ]
  }
}
```

### 模式 B：合集语言包（一个插件 = 多个语言）

```json
{
  "name": "官方语言",
  "contributes": {
    "languages": [
      { "id": "zh", "label": "中文", "path": "zh.json" },
      { "id": "en", "label": "English", "path": "en.json" }
    ]
  }
}
```

和主题 `contributes.themes` 完全对称——数组天然支持单/多。

**🔥 设计约束：两种模式必须走同一条代码路径。** `contributes.themes` 的 `for (const tc of themeList)` 循环已证明单/多都能处理——`contributes.languages` 用同款循环，不引入分支。

**兼容逻辑：**
```
loader 检测语言：
  有 contributes.languages → 新格式注册（走 parseContributions 循环）
  有旧 languages 字段 → loadLanguagePlugin 循环
  都没有 → 不注册
```

出厂预装合集插件 `plugins/lang-defaults/`（中英合一，对标 `theme-defaults`），可卸载。卸载后 `t("终端")` → key 本身 "终端" 作为显示。

## 三、i18n 跨进程同步

多 WebView 后，每个插件 WebView 独立 i18next 实例：

```
切语言 → ja：
  1. 壳 i18next.changeLanguage("ja")
  2. 壳通过 IPC 广播：{ channel: "lang:changed", payload: { lang: "ja", resources: {...} } }
  3. 插件 WebView 收到 → i18next.addResourceBundle + changeLanguage
```

```typescript
// 壳侧
class LanguageEngine {
  async switchLanguage(lang: string): Promise<void> {
    await i18next.changeLanguage(lang);
    const resources = i18next.getResourceBundle(lang, null);
    ipc.broadcast("lang:changed", { lang, resources });
  }
}

// 插件侧
ipc.onEvent("lang:changed", ({ lang, resources }) => {
  Object.entries(resources).forEach(([ns, translations]) => {
    i18next.addResourceBundle(lang, ns, translations, true, true);
  });
  i18next.changeLanguage(lang);
});
```

## 七、🔥 E3b 教训——E3c 避坑指南

> 2026-07-26 写入。主题插件化踩了 5 个坑，每个都会在语言插件化重演。做完 E3b 回头写这份文档——不是为了指责，是为了不再犯。

### 坑 1：`IpcBridgeHandler` `list` case 漏 `contributes` 字段

**现象：** 插件市场齿轮菜单"选择颜色主题"永远不出现。

**根因：** `src/core/IpcBridgeHandler.ts` 的 `plugins:call "list"` handler 返回的 manifest 只挑了 6 个字段（name/description/version/core/author/statusBar），**漏了 `contributes`**。`applyExtensionContextKeys` 设 `extensionHasThemes` → `manifest.contributes` 永远 `undefined` → context key 永远 `false`。

**E3c 对应：** `extensionHasLanguages` context key **已经**在 `applyExtensionContextKeys` 中设置了（`sidebar.tsx:83`），**已经**在齿轮菜单中注册了菜单项（`#36g3` 将注册）。`IpcBridgeHandler` 的 `list` case **已经**包含 `contributes: p.manifest.contributes`（2026-07-26 修复）。E3c 不需要再修这个。

> 🔥 **教训：** IPC 序列化层手挑字段时，任何遗漏都会导致消费端 context key 永远为 false。以后加新的 `extensionHas*` context key 时，必须同时检查两处：① `applyExtensionContextKeys` 有没有设 ② `IpcBridgeHandler` `list` case 有没有传对应字段。

### 坑 2：`parseContributions` 缺 `contributes.*` 处理

**现象：** 插件声明了 `contributes.themes`，列表里能看到，但齿轮菜单的 `when: "extensionHasThemes"` 不生效 → 排查半天发现是坑 1。

**根因（如果只修坑 1 不修这个）：** `parseContributions` 没有 `contributes.languages` 分支。当前代码：
```typescript
// parseContributions 中已有的：
// ✅ contributes.configuration (line 312)
// ✅ contributes.commands (line 323)
// ✅ contributes.menus (line 339)
// ✅ contributes.keybindings (line 347)
// ✅ contributes.configurationDefaults (line 355)
// ✅ contributes.themes (line 360)
// ✅ contributes.fileAssociations (line 382)
// ❌ contributes.languages —— 还没写！
```

语言插件走 `contributes.languages`（新格式）时，plugin.json 能读到、`IpcBridgeHandler` 能传 `contributes`，但 `loader.ts` 的 `parseContributions` 不处理 `c.languages` → 语言资源不注册 → `i18next.addResourceBundle` 没被调用 → 切语言后插件 WebView 没有翻译。

`loadLanguagePlugin`（旧格式 `manifest.languages`）工作正常，但合集插件走 `contributes.languages` 会挂。

**E3c #38 必须做：** 在 `parseContributions` 中加：
```typescript
// contributes.languages → LanguageRegistry + i18next
if (c.languages) {
  const langList = c.languages as Array<{ id: string; label: string; path: string }>;
  for (const lc of langList) {
    LanguageRegistry.register(lc, pluginId);
    const data = getPluginDataFile(pluginId, lc.path);
    if (data) {
      i18n.addResourceBundle(lc.id, "translation", data, true, true);
    }
  }
}
```

### 坑 3：JSON 嵌套对象被 `typeof v === "string"` 跳过

**现象：** 所有插件的主题 `colors count: 0`——`loadTheme` 返回的 Theme 对象 `colors = {}`。

**根因：** 主题 JSON 是 `{ "name": "...", "type": "dark", "colors": { "bg-window": "#XXX", ... } }`。颜色提取代码遍历顶层 `Object.entries(data)`，检查 `typeof v === "string"`。`"colors"` 键的值是**对象** → `typeof` 不是 `"string"` → 跳过 → 所有主题 colors 为空。

Dark/Light 能"正常"工作是因为 `index.css` 的 `:root` / `[data-theme="light"]` CSS 规则写了硬编码兜底——不是 `applyTheme()` 的内联变量在起作用。

**E3c 对应：** ❌ 语言不会出这个问题——语言 JSON 是平铺的 `{ "key": "value" }` 没有嵌套对象。`loadLanguagePlugin` 直接 `i18n.addResourceBundle(lang.code, ns, data, true, true)` 把整个 JSON 对象传进去，不需要提取。

> 🔥 **教训：** 凡是 JSON 数据文件有嵌套结构（如 `{ "colors": {...} }`），提取函数必须显式处理嵌套层。不要让 `typeof v === "string"` 这种条件隐式过滤——应该明确访问 `data.colors`，不做猜测。

### 坑 4：CSS 硬编码兜底蒙蔽 bug

**现象：** Dark/Light 一直"正常"，没人发现 `colors` 为空——直到暮光主题出现。

**根因：** `index.css` 写了 `:root { --bg-window: #1E1E1E; ... }` 和 `[data-theme="light"] { --bg-window: #FFFFFF; ... }`。`applyTheme({ name: "Dark", colors: {} })` 设 `data-theme="dark"` → CSS `:root` 接管 → 看起来正常。实际上主题 JSON 的颜色根本没被用上。

**E3c 对应：** 语言没有这种兜底——`t("key")` 找不到翻译就直接返回 key 本身。如果语言资源没注册成功，用户会直接看到 key 原文而非翻译——bug 会**立即暴露**。这是好事。

> 🔥 **教训：** CSS 硬编码兜底是双刃剑——保障了最低可用性，但也让数据层 bug 隐形。以后加新功能时问：有没有硬编码兜底在掩盖数据层问题？有 → 先验证数据层正确，再把兜底当真正的兜底。

### 坑 5：两处重复代码——同一个 bug 修两次

**现象：** `loadThemePlugin`（旧格式）和 `parseContributions`（新格式）各有一份 11 行颜色提取循环。bug 在两处同时存在。

**修复：** `#36j2` 提取 `extractThemeColors(data)` 归一化函数——两处各一行调用。

**E3c 对应：** 当前 `loadLanguagePlugin` 的代码：
```typescript
i18n.addResourceBundle(lang.code, ns, data, true, true);
```
这行是**唯一的**语言资源注册路径。E3c #38 在 `parseContributions` 加 `contributes.languages` 时，**必须提取共享函数 `registerLanguageBundle(langCode, data)`**，两处共用。不要复制 `i18n.addResourceBundle` 调用到两个地方。

> 🔥 **教训：** 任何时候看到同一逻辑在两处出现——先提取再继续。`#36j2` 做在了 bug 修复之后、E3c 开始之前。E3c 一开始就应该提取，不留债。

### 坑 6：夹逼法 git bisect——硬约束 15

**背景：** 主题插件化（E3b #34、#36e、#36f）总计修复了 ~9 个 bug，其中 H1-H3 用了 git 二分定位。见 memory `non-view-plugin-normalization-lesson`。

**E3c 对应：** 语言插件化如果出问题，不要静态分析死磕。`git checkout -f <commit>` 跳版本，找到最后一个正常版本和第一个异常版本之间的 diff，bug 就在那个 commit 里。**硬约束 15 不是理论，是实践出来的。**
