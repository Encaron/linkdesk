## 一、真根因——三层，不是「早期命名不当」

> 这一节是**给后面每一棒的方法论底座**：先认清病，再谈药。结论：**名字没起坏，是「守门模型」坏了**。

### 层 1（机制）——CSS 没有作用域，而本仓没有加隔离

CSS 类名 / 关键帧名 / 自定义属性名 / 顶层元素选择器，**在一个文档里各是一张扁平全局表**；后定义者或更高优先级者赢。而本仓的隔离手段使用量：

| 手段 | 全仓用量 | 出处 |
|:--|:--:|:--|
| `@layer` | **0** | `grep -rn "@layer" src/ --include=*.css` |
| Shadow DOM（`attachShadow`） | **0** | `grep -rn "attachShadow" src/ electron/` |
| CSS Modules（`*.module.css`） | **0** | `find src -name "*.module.css"` |
| 插件视图 iframe | **0** | 池内直挂 React 组件 |

⇒ 这是**平台既有事实**（CSS 本来没有 encapsulation），不是本项目犯错；但它决定了：**只要存在「没有命名空间的定义方」，碰撞就是迟早的**。

### 层 2（接口）——组件库按「有封装」设计，投进「无封装」的运行时

`@linkdesk/ui` 要做成独立分发给第三方的组件库，按常规组件库惯例设计：公开 API 用**简短语义类名**（`.badge` / `.button` / `.toggle`），并**明确允许**消费方用后代选择器做 scoped 调优（`.control-bar .combobox` 至今是合法消费）。这套设计在「每个应用自己 bundle 一份 CSS」的世界里是对的——**但它要求封装存在**。

投进「宿主 ＋ 组件库 ＋ N 插件共用一张表」的池文档之后，同一套设计就变成「**把公共 API 的名字直接注册成了全局名**」。⇒ **不是起名起坏了，是「按有封装设计、投进无封装的运行时」。**

### 层 3（守门）——纪律只对一方成立，另两方靠手抄表豁免，而那张表的生死由一个错的启发式自动判定 🔴

| 方 | 当年的守门方式 | 结果 |
|:--|:--|:--|
| **插件** | **真规矩**：裸定义必须带自有前缀（SDK 门禁，结构化、可复跑、fail-closed） | 官方 9 只带 CSS 的插件**零裸定义**；至今零事故 |
| **宿主 ＋ 共享组件** | **没有规矩**，只有一张**手抄的登记豁免表**（14 个名字）＋ 门禁里一句 `if (name.includes("-")) continue;` | 🔴 见下 |

那句启发式等于宣布：**任何带连字符的自有名自动安全**。于是：

- 宿主 **244 个**、共享组件 **52 个**带连字符的自有名，**从出生起没有任何门禁看过一眼**；
- 而 [11-样式命名空间审计.md](../11-样式命名空间审计.md) §三 的表（「共享组件 111 类名 / **裸定义 8**」）**用的是同一把错尺子** ⇒ **机器和文档同时瞎、两份数字互相印证** ⇒ 从内部看不出任何异常。

**⇒ 这就是「每换个量法就翻出一大片」的物理原因：不是问题在长大，是尺子一直在漏。**
（旁证：1.14① 实测 4 处 → 9 处；1.21 重算 255 → **244 ＋ 52**，旧数宣布作废；全部是同一件事的重复上演。）

### 一句话根因（后面每一棒收尾都要能复述这句）

> **不是名字起坏了，是「正确」这件事被寄托在「人记得住 ＋ 手抄表维护得对」，而那张表的生死由一个错的启发式自动判定。** 名字只是症状最先露头的地方。

**⇒ 由此推出的两条纪律（件 5–9 全部遵守）**：
1. **规则必须结构性**（判据能独立判定，不查表、不靠白名单）——这是用户 2026-09-16「选 A 真治」的原话口径；
2. **判据必须证明自己活着**（有自测、自测接线、负控真红）——否则下一把尺子还会漏（件 8 专治这条）。

## 六、残余边界（诚实清单——**1.20 报告必带，一条不许省**）

> 这一节是**本方案与「宣布大获全胜」的分界线**。用户 2026-09-16 的原始追问就是「**是不是真收口了，还是还有根因藏着**」——答案写在下面。

1. **机制层未隔离（明文折中，件 9 落决策）**：四条轴收口靠的是**约定 ＋ 门禁 ＋ 运行时断言**，不是**构造上不可能**。⇒ 表述纪律：说「**事实上不会发生**」，不说「**不可能发生**」。
2. **宿主基线选择器是「有意的跨方命中」**：`*, *::before, *::after`、`html`/`body`、`#root`/`#pool-root`、`*:focus-visible`、`input[type="number"]`、`select` 等**故意**命中插件元素（插件依赖它）。⇒ 「零碰撞」的断言必须把基线记为**已登记的例外**（**文件级、条目可数、每条带理由**），而不是假装它不存在。
3. **门禁是静态的**：运行时动态拼出的类名/属性名理论上可绕过（如 `theme-${variant}` 这类由数据拼出来的名字）。⇒ 本轮**不加运行时拦截**；探针须把这一条列为「**探针覆盖不到**」并记录已知形态。
4. **第三方依赖注入的 CSS 不被命名空间化**：`@vscode/codicons` 的 `codicon*`（60+ 图标靠它）是**外部契约**，改了全软件图标变方块。机械依据：本仓**只消费、从不独立定义**它 ⇒ 「独立定义必须带前缀」这条规则天然把它排除（实测交集 = 0）。**别把判据写成「出现过的类名必须带前缀」**——那会逼出白名单。
5. **`<pluginId>-` 唯一性依赖硬约束 11（发布后 id 不可变）**：若将来出现 id 冲突，前缀唯一性失效（今天由 loader 的存在性检查兜）。
6. **scoped 调优是特性不是缺陷**：插件**按设计**可以命中宿主/共享组件的元素（文档明写合法）。件 7 给它加**形态**门禁（必须有自有根类作祖先），但**门禁管形态、不管意图**——一次有意的、写在门禁允许形态里的覆盖，仍然是允许的。

> 用户原话：「**总的来说，你的规划是要符合归一化、AI 友好化（多层含义，记忆中有）、无硬编码、无死代码、符合软件未来发展、高内聚、低耦合、可拓展、第三方易制造插件，符合我们软件的核心理念：万物皆可插件。**」

### 10.1 AI 友好化四层（记忆 `ai-friendliness-three-layers`）——本方案主攻**层 3**、兼顾**层 4**

| 层 | 内容 | 本方案怎么落 |
|:--:|:--|:--|
| 1 | 运行时操作（CDP ／ MCP 桥） | **不属本系列**（另有主线）；本系列只保证「AI 改样式不必追踪影响面」 |
| 2 | 结构化文件（`settings.json` 等声明层） | **不属本系列** |
| **3** | **工程可读**（判据：**高内聚低耦合 · 无硬编码 · 无死代码 · 规范化 · 规整化 · 代码结构化 · 区域化**） | 🔴 **本系列的主战场** —— 逐条见 10.2 |
| **4** | **插件易造**（第三方永不需壳改代码；10 分钟写出首个插件） | 四条轴**一律进 SDK 腿**（§3.6）；规则收敛成一句**不需要查表**的话 ⇒ 作者（与其 AI）**不必记住任何名字** |

**核心公式（记忆原文）**：「你要的不是 AI 更聪明。你要的是**代码不给 AI 犯错的机会**。」⇒ 本系列在 CSS 上的全部工作就是这句话的落地：**名字不会撞 · 规则不用查表 · 判据自己会红**。

**归一化（记忆定义）**：**每个概念只有一种写法** —— 颜色只有 `var(--xxx)` · 文字只有 `t()` · 插件身份只有 `plugin.json` · 跨插件通信只有 `Registry` · 资产路径只有 `getAssetPath()`；**改一个地方 → 确定性生效**。
> 🔴 **据此重判 token 轴（本节修订）**：token 今天**有两种写法**（宿主契约名**裸写** · 其余带命名空间）⇒ **按记忆里那条定义，它还不算归一化**。⇒ [25 号档](25-任务-token轴实测与定案.md) 的裁决标准据此收紧（甲路线**升格**）。

### 10.3 🔴 宽容度模型（**2026-09-16 用户澄清 ＋ 记忆 `plugin-repo-gate-model` 核实**——本方案的一切「判红」都必须先过这一节）

> **用户原话口径**：「第三方可以**自己画组件**，这是他自己的自由；他可以**跟随主题变**，也可以**自己固定颜色**，只不过**黄灯警告，但绝不红灯拦截**——这是**已经有的宽容**。比如我们自己的 monaco 编辑器，它的界面就不随着主题变而变，仅仅是 dark/light 两个颜色变。若第三方作者想统一 UI，则**可以使用官方组件**。」

**记忆侧核实（`plugin-repo-gate-model`）**：
1. **`@linkdesk/plugin-sdk` 的 eslint 规则全部是 `warn` 级** —— `linkdesk-plugin-sdk lint` 的设计是「**警告不是封锁，WARN 永不 fail build/上传**」（刻意的）；⇒ **判红必须自带严格腿**，不可能来自 preset 本身。
2. 🔴 **判红范围判据（本系列最值钱的一条工作法）**：「**能在一个仓里回答的判红；只有跨仓才能回答的给黄灯**」。理由：**假红会让真红失效**。
3. 记忆里**已明确「只报告不拦」的档**：`check-font-scale` / `check-spacing-grid`（属**审美校准档**，存量偏离 36 处）。

**⇒ 对本方案的三条硬约束（新增禁区）**：
1. **第三方侧的一切新判据，默认黄灯**（只报不拦）；**判红必须逐条论证「① 本仓可答 ② 有真害（不是审美）」** —— 两条缺一即降为黄灯。
2. **「自定颜色 / 自画组件」永远是允许的**：第三方不必跟随主题，也不必用官方组件；**跟随主题是可选路径**（用了官方组件就自动跟随）。⇒ 任何规则**不得**要求第三方必须消费 `var(--*)` 或必须使用 `@linkdesk/ui`。
3. **红灯只留两类**：① **占用宿主命名空间**（类名 / 关键帧 / 自定义属性定义了 `ldk-*`）② **本仓可答的真害**（自己元素上的硬编码等既有判红项）。**其余一律黄灯 ＋ 迁移说明**。

🔑 **这一节还解开了一个我原先报错的「冲突」**：我以为 甲（宿主 token 改名）会大面积破坏第三方 —— **错的**。第三方本来就允许不跟随主题；甲 只改变「跟随主题」这条**可选路径**的名字，对他们是一条**黄灯 ＋ 迁移说明**。⇒ **当归一化是软件自己的长期成本时，它与第三方宽容不矛盾**。

### 10.4 🔴 用户 2026-09-16 追加两条硬约束（**本节优先级最高，压过 §10.1–10.3 的一切取舍**）

> 用户原话一：「我希望的是**做完整个系列任务后，我除了版本号外，不要有任何 UI 变化**，无论是**主题统一调控、字体翻译等**。」
> 用户原话二：「**关于共享组件库，我基本只会做加法，添加新组件。不会对已有组件改名等更改。**」

**约束 ①：零 UI 变化 —— 且点名了三条「横切机制」必须零回归**
| 横切机制 | 今天的行为（必须与终态一致） |
|:--|:--|
| **主题统一调控** | 切主题 / 多配色（colorway）· 玻璃（模糊/饱和/不透明度）· 背景（panorama / mask）· 亮暗切换 —— 全表面跟随 |
| **字体** | 字号 `app.uiFontScale` 85–150 步进（`--ui-scale` ＋ `--font-size-*` 档位）· 字体族（`--font-ui` / `--font-mono`）· `window.zoomLevel`（与字号**正交双轴**，分叉点 = monaco 内容孤岛） |
| **翻译** | 中英切换（`t()` ＋ 语言包）· 插件自带 `contributes.i18n`（`lang-defaults` 插件） |
⇒ **这三条被提为 1.20 的显式验收节**（[19 号档](19-任务-收口批-遗留账与系列收口.md) §第 1.20 轮「横切机制零回归」），且**每一轮的实机判据都要带这三条**（不是只在收口时查）。

**约束 ②（🔴 有条件：以「本系列做得好」为前提）—— 只做加法 ⇒ 本系列「**定型后**」的名字是「终名」**
> ⚠️ **别误读（2026-09-16 用户再澄清）**：「不改已有组件名」**指的是本系列定型之后** —— **本系列内部当然要改名**（那正是 1.21 / 1.21b 此刻在做的事）。用户原话：「**不是说不改现在的组件名，毕竟 1.21 正在改名，我指的是做完这个系列后，定型后的名字，我基本不会再改，而是加新组件，做加法，用这种方式更新。**」
> ⇒ 由此明确**未来的更新模型 = 加法**：新组件**自成一个族段**、不与既有族/名字冲突；**判据⑦（族段规则）＋ 判据⑥（跨域唯一性）就是为这种更新方式设计的两条守卫** —— 它们保证「加新组件」永远是一次安全的加法。
> 用户 2026-09-16 补充原话：「**我指的是你这个系列做的好，再完成后，我不会对已有组件改名，以后只做加法，加入新组件。**」
> ⇒ 🔴 **这个「有条件」把本系列的成败变成一次性的**：**做得好 ⇒ 名字就此定终身、以后只加新组件；做得不好 ⇒ 要么带着坏名字过一辈子，要么再来一次改名（而用户已明确不想改名）。**
> ⇒ **「一次定对」不是效率要求，是本系列的硬质量门槛** —— 也是下面三条「升格」的全部理由。

**（升格三条）**
⇒ **推论（本方案的重大升级）**：1.21（宿主 244 名 ＋ 7 关键帧）与 1.21b（共享组件 49–52 名 ＋ 1 关键帧）**不是在「清理存量」，是在给这套命名定终身**——用户以后不会改已有组件名。
⇒ 由此**升格三件事**：
1. **起名质量成为 1.21 / 1.21b 的最高优先级之一**（不只是「加上 `ldk-` 就完事」）：临时短前缀一族（`.tbadge` / `.pv-dot` / `theme-card` / `theme-preview`）**必须并进各自族**，否则它们会被永久冻结成坏名字 —— 这正是 [23 号档 §3c 族段规则](23-任务-共享组件类名归一与作者轴发版.md) 的用武之地。
2. **判据⑦（族段规则）从「卫生要求」升为「终名质量保障」** —— 它是唯一能让「一次定对」可判的机械工具。
3. **判据⑥（`ldk-` 跨域唯一性）是「终名不撞」的最后一道闸** —— 今天交集 0，但改完之后**再撞就没有第二次改名机会**。

**🔴 推论 ③（否决甲）：甲的裁决据此落地** —— [25 号档](25-任务-token轴实测与定案.md) 的「甲（宿主 token 改名 `--ldk-*`）」**建议否决**，两条依据都可判定：
1. **与约束 ① 冲突**：读宿主 token 的第三方插件会在新壳上**掉样式**（可见变化）；要消除它只能靠**永久别名**（与「无死代码」冲突，且别名本身是第二真相源）或**一次性破坏**（与用户「不要有任何 UI 变化」直冲突）。
2. **甲的唯一独有收益（作者侧红灯零清单）已被实测抵消**：丙 的红灯规则是「插件在文档级定义**宿主契约名** ⇒ 红」，而契约名单**由契约块生成**（非手抄）——它抓 `marketplace` 那个真案**是够的**：实测 `--status-connected` **就在** `src/index.css:29` 的 `:root` 里 ⇒ **生成名单必含它** ⇒ **丙 能抓住真案，不需要改名**。
⇒ **翻案条件（写明，别留模糊）**：若将来出现**新证据**表明「丙 漏掉了某类真害」且该害只能靠命名空间化解决，则由当轮把它重新提出；**今天没有任何这样的证据**。
