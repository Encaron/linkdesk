## 2. 关键设计决策——`renderPath`：plugin.json 声明 → 池直接加载

### 问题

池的 `PluginComponent` 当前用 `import.meta.glob` 只匹配 `index.tsx`——即插件的**默认导出**。但插件可能有多个侧栏 view，每个 view 的组件由 `plugin.json` 的 `"render": "src/views/Xxx.tsx"` 声明，由 `loader.ts` 动态 import 后注册进 `ViewContainerService`。

**默认导出 ≠ 侧栏 view 组件。** 如 marketplace 默认导出是主区欢迎页，5 个侧栏 view 各自是独立模块。

### 方案评估

| 方案 | 描述 | 判定 |
|:--|:--|:--|
| ~~池加载 index.tsx + viewId prop → 插件内部 switch~~ | 插件作者为每个 viewId 写 case | ❌ 插件作者改代码适配壳架构——违背插件独立铁律 |
| ✅ **renderPath——池直接加载 plugin.json 声明的 render 模块** | `loader.ts` 构建的 glob key 存入 `ViewDescriptor._renderPath`，池用同一 key 做 O(1) 查找 | ✅ 插件零改动。声明即渲染。 |

### renderPath 机制

```
plugin.json:  "render": "src/views/SearchView.tsx"
     ↓
loader.ts:    renderPath = "../../plugins/builtin/marketplace/src/views/SearchView.tsx"
     ↓         viewRenderModules[renderPath] → import → registerView({ _renderPath: renderPath, render: Component })
     ↓
usePoolSync:  SidebarViewMeta.renderPath = v._renderPath  // 字符串——可序列化！
     ↓
池 PluginComponent:
  viewModules[renderPath] → O(1) 直接命中 → React.lazy 渲染
```

**关键：** `loader.ts` 和 `PluginComponent` 都在 `src/` 下，glob key 格式相同（`../../plugins/...`），可以直接作为 key 互查。

### 为什么这是唯一正确的方案

| 要求 | 满足方式 |
|:--|:--|
| **AI 友好 Layer 2** | plugin.json 的结构化 `render` 字段是唯一真相源——AI 加 view = 加一行 JSON |
| **AI 友好 Layer 3** | 一种写法：`"render": "src/views/Xxx.tsx"`。AI 不需要追踪"池能不能渲染" |
| **无硬编码** | 壳不认识 view ID、不认识组件名——只读 `_renderPath` 字符串 |
| **插件独立铁律** | 第三方作者写 plugin.json → 壳自动 `_renderPath` → 池自动渲染。壳作者零操作 |
| **归一化** | 声明路径的机制只有 plugin.json → loader.ts → SidebarViewMeta.renderPath 一条线 |
| **低耦合** | 池只知道文件路径字符串，不知道组件名、插件名 |
| **无死代码** | `view.render` 仍用于壳 fallback，`_renderPath` 是新增字段——各有其用 |

### 已有插件适配（搬迁期间允许）

| 插件 | 改动 | 原因 |
|:--|:--|:--|
| marketplace | **无** | plugin.json 已完整声明 5 个 view |
| serial-monitor | **无** | plugin.json 已完整声明 2 个 view |
| file-tree | `plugin.json` `views.explorer` 加 `search` view | `search` view 当前纯代码注册（FoldersView.tsx useEffect）——plugin.json 无声明，loader.ts 不设 `_renderPath`。补声明即可 |

## 3. 跨进程硬限制

```
壳 JS 堆                                    池 JS 堆 (独立 WebContentsView)
┌─────────────────────────────────┐         ┌──────────────────────────────┐
│ ViewContainerService (单例)      │         │ ViewContainerService (空实例) │
│  ├ file-explorer: title/icon/…  │ ╳ IPC ╳ │ PluginComponent               │
│  │   folders (render: fn)       │         │  import.meta.glob 可加载插件   │
│  │   …                          │         │  但不知道哪个 view 用哪个组件   │
│  ├ marketplace:                 │         │                              │
│  │   search (render: fn)        │         │ SidebarSection                │
│  │   installed (render: fn)     │         │  纯 UI 组件──壳依赖零──可直接复用 │
│  │   builtin (render: fn)       │         │                              │
│  └ …                            │         └──────────────────────────────┘
└─────────────────────────────────┘
```

**核心约束：**
- `ViewContainerService = new ViewContainerServiceClass()` 模块级单例──池 import 同一模块拿到空 registries
- `view.render` 是 React ComponentType──不可 JSON 序列化走 IPC
- 壳必须把所有 view 元数据序列化进 PoolLayout，池用 PluginComponent 加载插件模块
- **SidebarSection 是纯 UI 组件**──不 import 任何 core 模块──**池可直接复用**

### 3.2 明确不能复现的（硬限制）

| 功能 | 原因 | 替代方案 |
|:--|:-----|:-----|
| `view.actions` (ReactNode) | IPC 不可传 React 节点 | 插件在自己的 view 组件内渲染 actions |
| `view.pinnedContent` (() => ReactNode) | 函数不可 IPC 序列化 | 插件在自己的 view 组件内渲染 |
| ContextMenu (header 右键) | 菜单在壳进程渲染 | 壳 SidePanel 仍挂载（display:none），菜单走壳 |
| ContextKeyService.matches() | 池是独立 JS 堆，ContextKey 全空 | 壳侧预计算 ContextKey → 序列化进 layout |

### 3.3 IPC 通道——池→壳 写操作

池需两个新 IPC 通道，对标 ViewContainerService 的写方法：

| IPC Channel | 方向 | Payload | 壳 Handler |
|:--|:--|:--|:--|
| `pool:sidebar-action` | 池→主进程→壳 | `{ action: "reorder", containerId, viewId, newIndex }` | → `ViewContainerService.reorderView()` |
| `pool:sidebar-action` | 池→主进程→壳 | `{ action: "setCollapsed", viewId, collapsed }` | → `ViewContainerService.setCollapsed()` |
| `pool:sidebar-action` | 池→主进程→壳 | `{ action: "setVisible", containerId, viewId, visible }` | → `ViewContainerService.setVisible()` |

壳处理后 ViewContainerService 触发事件 → usePoolSync 重推 layout → 池刷新。

### 3.4 空状态占位——壳预计算方案

原 SectionStack `getEmptyContent()` 返回 ReactNode → 不可序列化。
改为壳预计算"是否需要空状态"标志，池按此标志决定显示 PluginComponent 还是空状态提示：

- **方案 A（简化）**：view 无数据时，PluginComponent 内部自行判断并渲染空状态
  - 影响：需要每个有侧栏 view 的插件都处理空状态——可行但分散
- **方案 B（layout 标志）**：Shell usePoolSync 对每个 view 调用 `ViewContainerService.getViewEmptyContent(viewId)` → 不为空 → 标记 `hasEmptyContent: true`（不传 ReactNode）→ 池 SidebarRenderer 显示通用空状态提示
  - 影响：通用提示"此视图无可用内容"——不如插件自定义内容

**采用方案 B（layout 标志）+ 插件方案 A（自行判断）并存。** pluginState 标志从 layout 来，PluginComponent 收到不渲染任何 view（空状态走 fallback）。

## 4. PoolLayout 类型扩展

```ts
// src/core/types/poolLayout.ts

/** 侧栏 view 元数据——从 ViewContainerService 序列化，经 PoolLayout 推送 */
export interface SidebarViewMeta {
  id: string;                             // view ID "folders"
  title: string;                          // 显示标题
  pluginId: string;                       // _pluginId——PluginComponent 用它找 import.meta.glob
  renderPath: string;                     // 🔑 E5.6#11：loader.ts 构建的 glob key——池 O(1) 查找 view 组件
  role?: "toolbar" | "section";           // 默认 "section"
  order?: number;
  collapsed?: boolean;                    // 插件声明的初始折叠态
  badge?: string | number;
  titleDescription?: string;
  titleTooltip?: string;
  singleViewPaneContainerTitle?: string;  // mergeHeaderWhenSingle 时替代 containerTitle
  minHeight?: number;                     // 声明最小高度——PaneSash effectiveMinHeight 用
}

export interface SidebarLayout {
  visible: boolean;
  width: number;
  // ── E5.6#11 新增 ──
  containerId: string | null;             // "file-explorer"
  containerTitle: string;                 // "资源管理器"
  mergeHeaderWhenSingle?: boolean;
  views: SidebarViewMeta[];
  collapsedViews?: string[];              // 持久化折叠的 view ID 集合——Shell 从 ViewContainerService.loadCollapsedState() 读取
  // ── 向后兼容 ──
  /** @deprecated 被 views[] 取代 */
  viewId?: string | null;
}
```

## 7. PoolSectionStack 详细设计

```
PoolSectionStack
├── 复用 SidebarSection（直接 import——纯 UI 组件，零壳依赖）
├── 复用 PaneSash（纯 DOM 事件——mousedown/move/up 逻辑完全一致）
├── 复用 ViewPane（flex + ResizeObserver + drop-before——逻辑完全一致）
├── SidebarViewMeta 替代 ViewDescriptor 类型
│   └── 🔑 renderPath 替代 view.render()——PluginComponent 按路径直接加载组件
├── effectiveMinHeight：读 SidebarViewMeta.minHeight（非 ViewContainerService.getView()）
├── 拖拽排序 UI：handleDragStart/onDragOverCapture/handleDrop（同逻辑）
│   └── handleDrop → pool.sidebarAction({ action: "reorder", containerId, viewId, newIndex })
│       → 壳 ViewContainerService.reorderView() → onDidChangeViews → usePoolSync 重推 layout
├── 折叠持久化：
│   ├── 初始：layout.collapsedViews.includes(view.id) ? 折叠 : SidebarViewMeta.collapsed
│   └── toggle：pool.sidebarAction({ action: "setCollapsed", viewId, collapsed })
│       → 壳 ViewContainerService.setCollapsed()
├── ErrorBoundary 包裹每个 PluginComponent
└── 空状态：PluginComponent 始终挂载（防 E4V#44 死锁），空状态由插件内部自行渲染
```

## 8. 壳→池 数据流（usePoolSync 变化）

```
usePoolSync useEffect([sidebarView, …])
  if (!sidebarView) → sidebar = { visible: false, … }
  else:
    1. container = ViewContainerService.getViewContainer(sidebarView)
    2. activeViews = ViewContainerService.getActiveViews(sidebarView)
    3. collapsedSet = ViewContainerService.loadCollapsedState()
    4. 每条 activeView → SidebarViewMeta:
       { id, title, pluginId: _pluginId,
         renderPath: _renderPath,  // 🔑 loader.ts 设置的 glob key——池 O(1) 查找组件
         role, collapsed, badge,
         titleDescription, titleTooltip, singleViewPaneContainerTitle,
         minHeight }
    5. sidebar = {
         visible: true, width, containerId: sidebarView,
         containerTitle: container.title, mergeHeaderWhenSingle: container.mergeHeaderWhenSingle,
         views: [...], collapsedViews: [...collapsedSet],
         viewId: views[0]?.pluginId  // 向后兼容
       }
    6. poolApi.pushLayout("sidebar", { sidebar, groups: [] })
```
