## AI#1 ⬜ 通知读取面：list + subscribe

**做什么**：给 `notifications` 命名空间补**只读列举**与**变更订阅**。

**现状（实测）**：契约面只有 `show`——`src/core/api/linkdesk-api/ui.ts:17` 起是 `notifications: { show(...) }`，**再无第二方法**；全仓 grep `notifications.list` / `notifications.subscribe` / `onDidChangeNotification` **零命中**。壳侧其实**已有全量数据**（`src/hooks/usePoolSync/notif.ts:238-313` 的 `buildNotifPanel` 每帧组装面板 DTO，`src/core/types/pool/poolLayout.ts:665` 的 `notif: NotifLayout` 挂在布局快照上）——**数据在推，只是没开门**。

**两条路线（[../01-设计.md §四 M1](../01-设计.md) ① 原文给了两选）**：

| 路线 | 做法 | 评估 |
|:--|:--|:--|
| **A（建议）** | 新增 `notifications.list()` + `notifications.subscribe(cb)` | 语义直白、按需拉、**与「契约级读取路径」判据最贴**；代价 = 新增一条池→壳请求/响应链 |
| B | 把 `pool.onLayout` 的 `statusBar.notif` **正式定格**为读取通道并写进契约 | 零新通道；但布局快照是**每帧全量推**，用「读一条通知」的名目去读全量布局，语义错位、且 AI 得先知道去哪个字段挖 |

**建议 A ＋ 同时文档化 B**（B 已是既成事实，藏起来反而让 AI 去猜）——但**门面必须 A**。

**判据**：AI 能答「铃铛里有几条、各是什么、几条未读」——**零 DOM 读取**（不许出现 `document.querySelector` 一类的兜底）。

**验收方式**：CDP 连池 target → 只调契约（`window.linkdesk.notifications.list()`）→ 与铃铛面板**目视读数逐条对齐**；再 `subscribe` 后 `show` 一条 → 断言回调被触发。⚠️ 验收必须**与物理指针无关**（[../01-设计.md §三 验收面第 1 条](../01-设计.md)）。

**风险**：`AI#2` 同文件 ⇒ **两格可同批做**（都动通知 DTO，避免两次改同一构造器）。

## AI#2 ⬜ 通知按钮带 command/args（不再剥）

**做什么**：面板 DTO 的 `actions` **带上 `command` + `args`**，让 AI 能回答「**按钮里有什么 / 该执行哪个 / 按下去会发生什么**」。

**现状与根因（实测，本会话新证）**：

1. 插件侧 `show(message, { actions })` 的 `actions` 是**已序列化的 `{command, args, label}`**（契约 `PluginToastAction`，见 `ui.ts:22-24` 注释「点击走壳 `executeCommand(action.command, action.args)`」）。
2. 壳侧 **`src/core/services/plugins/IpcBridgeHandler/ui.ts:259-292`** 把这份序列化数据**转成了闭包**——注释原文「`options.actions`（插件序列化 `{command,args}`，无闭包）**→ 壳 toast action closure**」（`:259`），映射在 `:270`。**`command`/`args` 就是在这里被收进闭包、从此只在壳进程内存活。**
3. 池侧 **`src/hooks/usePoolSync/notif.ts:280`** 构造面板 DTO 时只剩 `{ label, isPrimary }`：
   ```ts
   actions: (n.actions ?? []).map((a) => ({ label: a.label, ...(a.isPrimary ? { isPrimary: true } : {}) })),
   ```
   ⇒ **AI 看得到按钮文字，看不到按下去会发生什么**（[../01-设计.md §2.3 D 类](../01-设计.md) 首行）。

**修法**：让第 2 步产出的 action **同时携带 `command`/`args`**（而不是只留闭包），第 3 步再把它们透传进 DTO。**闭包仍保留**（点击路径零改动、零回归），只是**多带一份可序列化事实**——这是**纯加法**。

**判据**：toast 六问的「按钮里有什么 / 该执行哪个 / 执行后做什么」——AI 能读到 `command`+`args`，并**据此调 `commands.executeCommand(command, ...args)` 真的执行成功**。

**验收方式**：造一条带按钮的通知（如安装失败的 `[重试]`）→ 只经契约读 DTO → 取 `actions[0].command/args` → 调 `executeCommand` → 断言行为与**手点按钮**一致（含收掉通知）。**零 DOM 读取、零坐标点击。**

**风险 / 边界**：⛔ **不要**为了「让 AI 好读」把 `label` 改成 `command`（`label` 是给人看的文案，文案侧已由 i18n 真源统一）；两个字段**并存**。

## AI#3 ⬜ tabs.list()（含活跃位）

**做什么**：`tabs` 命名空间补**只读列举**（每组有哪些标签 + 哪个是活跃）。

**现状（实测）**：`src/core/api/linkdesk-api/tabs.ts:7` 的 `TabsAPI.tabs` 只有 8 个方法（`create` / `openOrFocus` / `focus` / `close` / `focusBySourceId` / `updateLabelBySourceId` / `closeBySourceId` / `onDidChangeActiveTab`）——**有订阅、无列举**。**布局真相源在壳 `useTabManager`，壳侧无 getter**（[../01-设计.md §2.3 D 类](../01-设计.md)）。

**修法**：壳侧加 getter（**壳是标签权威**，不能从池推），经既有请求/响应路径给池——`src/core/services/plugins/IpcBridgeHandler/tabs.ts`（**实测该文件已存在**，是同族 handler 的既有落点）。

**判据**：AI 能答「开了哪几个标签、各属于哪个插件、哪个是活跃的」——**零 DOM 读取**；且与 `AI#4` 的布局树**同源不打架**（标签清单与布局树的 `groups[].tabs[]` 必须对得上）。

**验收方式**：开 3 个标签 → 契约读 list → 与 `AI#4` 的布局树**交叉比对**（两次读数必须一致）；关掉活跃标签 → list 里的活跃位跟着变。

**依赖**：与 `AI#4` **同批**（两格都读布局真相源，分开做要改两遍同一处）。

## AI#4 ⬜ 布局读取面（树 + 分组）

**做什么**：提供 `layout.get`，**或**把 `pool.onLayout` 的 `root` / `groups` 正式定格并文档化。

**现状**：池侧唯 `pool.onLayout`（`electron/preload-pool/layout.ts:46`），快照里**已有全量树 + 每组标签清单**（每 tab 含 `pluginId` / `title` / `id`）——**但未文档化**（[../01-设计.md §2.3 D 类](../01-设计.md)）。也就是说：**能力已在、门未挂**。

**建议**：**两件都做**——`layout.get()` 给「按需拉」（AI 想要当前快照时不用等下一帧），同时把 `pool.onLayout` 的字段**写进契约文档**（它已在推，藏着只会逼 AI 去猜或读 DOM）。

**判据**：§十 第 12 例「**空间定位问答**」三问全可答——①「串口监视器**开着吗**」= 扫 `groups[].tabs` 找 `pluginId`；②「**在哪**」= 走树得出路径（如 `右 → 下 → 右`）；③「**把它区域拉宽**」= `updateSplitSizes(anchorGroupId, sizes)` 精确到百分比数字。

**验收方式**：跑 §十 第 11/12 例（**嵌套分屏** + **空间定位问答**）——全程命令/API，**零坐标输入**。

**边界**：`MAX_TREE_DEPTH=4`（[CLAUDE.md](../../../../../CLAUDE.md) 关键设计与反模式）——读取面要**如实反映深度上限**，别让 AI 以为能无限嵌套。

## AI#5 ⬜ 对话框进行中状态可读

**做什么**：让 AI 能读到「**有个 confirm / alert 正弹着、在等什么**」。

**现状（实测）**：`src/core/services/ui/DialogService.ts:138` 的 `showConfirm` 等一整套（`confirm` / `confirmContent` / `alert` / `showQuickPick` / `showInputBox`）**全是 Promise 式**（观察 `ConfirmRenderer` 类型 `:45`）⇒ **进行中状态完全不可见**：AI 只能看到「Promise 还没 settle」，**说不出弹的是什么**。

**修法**：加只读面（进行中的对话框队列 + 当前项内容），**不改 Promise 语义**（改成事件式会破坏所有既有调用方）。

**判据**：弹着 confirm 时 AI 能报出「在等什么、有几个按钮、按钮文案」。

**验收方式**：触发一个 confirm 不点 → 只经契约读状态 → 断言报出内容与屏幕一致（**用 `el.click()` 收尾，不用坐标点击**）。

**边界（重要）**：这是**读取面**，⛔ **不是**「让 AI 替用户拍板」——按钮归属仍按设计边界②：**AI 是操作员，不是值守员**。读取 ≠ 授权。

## AI#6 ⬜ wake / ttl / persistent 透传

**做什么**：通知 DTO 补齐 `wake` / `ttl` / `persistent`（现在**只有 `autoOpen` 边沿**）。

**现状（实测）**：壳侧**已经在读** `wake`——`src/hooks/usePoolSync/notif.ts:103-121` 的 `shouldWake(n) { return n.wake === true; }`，且注释极详细（「唤醒白名单（E6#73b）……**本文件里唯一决定『这条通知能不能把面板弹出来』的判据**」）。**缺陷不是没算，是没往外说** ⇒ AI 答不了 toast 六问之「**因为什么**弹出」（[../01-设计.md §三 验收锚点①](../01-设计.md)：该问现状为 **◐**）。

**修法**：纯加法——DTO 多带三个字段。

**判据**：toast 六问之「因为什么」从 **◐ 补成 ✅**（AI 能说出这条通知是「用户点击发起的安装终态」还是「插件自发的非进度通知」）。

**验收方式**：分别造「点击发起安装的 job 终态」与「插件自发的 info 通知」→ 读 DTO → 断言 `wake` / `persistent` 与预期一致。⚠️ 注意 `shouldWake` 注释里的**纪律**：⛔ 不得回退成 `isImportantNotif` 一把梭；「最小化」**不带静音权力**（改了会违反 R5-4 / R5-5）。

## AI#7 ⬜ 命令可读描述①：契约与注册面加 description + params

**做什么**：让命令**自带说明与参数结构**——AI 才能「知道怎么调」，而不是凭名字猜。

🔴 **现状实测（本会话新证）**——比设计原文更严重：

| 落点 | 实测形状 | 缺什么 |
|:--|:--|:--|
| `src/core/api/linkdesk-api/types.ts:14` | `LinkDeskCommand { id: string; title: string; category?: string }` | **零 `description`、零参数结构** |
| `src/core/api/linkdesk-api/commands.ts:47` | `registerCommand(id, handler, meta?: { title?; category?; when?; pluginId? })` | 同样零说明、零参数 |
| `src/core/registry/commands/CommandRegistry.ts:23` | `interface Command`（壳内注册表形状） | 同上 |
| `plugin.schema.json` 的 `contributes.commands` | 声明面 | 同上 |
| `linkdesk.d.ts` | 从契约派生 | 派生后同上 |

⇒ **AI 只能凭命令名猜参数**（[../01-设计.md §四 M1 ⑦](../01-设计.md) 原话：「现状命令元数据无参数说明 ⇒ AI 只能凭名字猜参数」）。**这是本格要堵的洞。**

**修法（全加法）**：三处**同名可选字段**——`description?: string` ＋ 参数结构（建议 `params?: Array<{ name; type; required?; description? }>`，或与 `contributes.configuration` 的 schema 语言对齐）。**存量插件零破坏**（可选字段，不填即缺省）。

**判据**：`getCommands()` 的返回值里，**每条命令都有可读说明 + 参数结构**（宿主命令由 `AI#8` 补齐、插件命令由规范/脚手架保证）。

**验收方式**：契约调 `getCommands()` → 断言抽样若干条的 `description` 非空且 `params` 与**实际调用所需参数**一致（挑一条带参数的命令，**照 `params` 说明调一次**，能调通 = 说明是真的）。

**风险**：⚠️ 这是**新能力面**（契约加字段 + schema 加字段）⇒ 按 [CLAUDE.md](../../../../../CLAUDE.md) 硬约束与仓库纪律，**先走 `design-flow` 8 维清单**；作者面文档（`docs/03-plugin-authoring/` + `docs/03-插件制造/`）**双语同步**（α 双语对齐门禁守）。
