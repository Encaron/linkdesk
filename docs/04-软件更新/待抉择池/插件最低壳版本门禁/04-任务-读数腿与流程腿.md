# 04 · 任务：读数腿与第一方流程腿

> 本件两格都**不是**"让声明为真"（那是 G2），而是：
> **G4 让「已经装坏的那一份」也不再显示『正常』**；**G5 让「插件跑到壳前面」这件事在源头出现一次就报**。

---

## 一、G4 · 兼容读数腿（让读数不撒谎）

### 1.1 为什么门禁挡不住"当下这一份"

G2 只管**构建期**。就算门禁上线、settings 也发了抬完声明的新版，**用户机器上那份已经装好的 `1.0.35` 纹丝不动**：

- 它的 `plugin.json` 里写的是 `0.2.32` ⇒ 兼容读数照样算出 `minAppSatisfied = true` ⇒ **照样显示「正常」**；
- 而把声明抬到 `0.2.44` 的新版，在 `0.2.41` 上**反而装不进去**（市场拒装腿会拦）⇒ **用户连"修好"的机会都没有**。

⇒ **只靠"声明为真"永远救不了已经装坏的那一份。读数必须自己会算。**

### 1.2 改法：读数用**同一份账本**算「实际地板」

**判据（改动后的形状）**：

```
地板_声明 = declared.minAppVersion（旧壳没有则 null，语义照旧）
地板_实际 = max{ since(x) | x ∈ 已装产物里对 @linkdesk/ui 的静态具名导入 }   ← 吃 G1 账本
地板      = max(地板_声明, 地板_实际)
minAppSatisfied = versionGte(shellVersion, 地板)
```

- 位置：[compatibility.ts](../../../../src/core/compat/compatibility.ts) 的输入构造（`PluginCompatibilityRequest` 加一个字段，或由 handler 直接算出合并后的地板传入）——**⛔ 不改它已有的五态映射与日期口径**。
- 供数：[plugin-handlers.ts](../../../../electron/ipc/handlers/plugin-handlers.ts) 的 `plugins.getCompatibility` handler（今天已经在从磁盘 manifest 覆盖 `minAppVersion`，加一步算实际地板即可）。
- **扫产物的基建已有先例可复用**：悬空扫描（[dangling-scan-async.ts](../../../../src/core/compat/dangling-scan-async.ts)）就是"worker 后台 + 指纹缓存（`compat-dangling-cache.json`）+ 同版本只扫一次"。**bundle 里的 `import` 清单可以挂在同一次扫描里**，⛔ 不必新起一个通道/worker。

### 1.3 效果（对本事故）

用户那台 `0.2.41` 上已装的 settings `1.0.35`：

- 地板_声明 = `0.2.32`；地板_实际 = `0.2.44`（它有 `PluginCard`）⇒ 地板 = `0.2.44`；
- `versionGte("0.2.41", "0.2.44") = false` ⇒ **`incompatible` ⇒ 界面显示「不适配」**。

⇒ **读数当场停止撒谎**，且**不需要等新版装上**。这是本格的全部价值。

### 1.4 边界与取舍

- **成本**：多一次产物扫描——但**复用悬空扫描的 worker + 指纹缓存**（同版本只扫一次、结果落盘），增量很小。⛔ 不许引入"每次开详情页都全量扫"。
- **离线/读不到产物** ⇒ 退化成"只有声明地板"（**不判坏消息**，照兼容读数既有的诚实纪律）。
- **不给第三方作者增加任何东西**：这条腿对**用户**生效，对**第三方用户的旧壳**同样生效（他的用户也可能装了比他测的更旧的壳）。

## 二、G5 · 第一方流程腿（**壳仓的家务事，⛔ 不进 SDK**）

### 2.1 为什么是第一方特有

[00 §三](00-README.md) 已定：**第三方结构上不会"依赖未发布的壳"**（他们只下已发布壳）。**只有我们**手上同时有"未发布的 dev 壳"和"1–2 分钟就能发的插件" ⇒ 本次事故的成因。

⇒ 这条检查**属于我们发布链**，落壳仓；⛔ **不许塞进 SDK／作者面**（污染第三方契约、违反低耦合）。

### 2.2 判据

```
地板_实际（同一份账本，同 G2 的算法）
vs
最新已发布壳版本（git tag 里最新的 v*）
⇒ 地板_实际 > 最新已发布壳  ⇒  🔴 红 / 🟡 黄灯
   「这只插件要求一个还没发布的壳 —— 用户装不上，或者装上就崩」
```

**为什么这条正好命中本次事故**：settings `1.0.35` 的地板 = `0.2.44` > 最新已发布壳 `0.2.41` ⇒ **当场报**。

**落点**：壳仓 [scripts/check-publish-gate.mjs](../../../../scripts/check-publish-gate.mjs) 一族 ＋ 官方目录收录链。**软/硬已定：黄灯**（§十 D3）——照其同族先例（[发行说明累计跳版](../../已落地/发行说明累计跳版.md)）的裁量：**"跳版是常态，硬门禁会天天误伤"**；此处同理，"插件先于壳"在 dev 节奏里可能是**故意的**，硬红会打架 ⇒ **黄灯提示 + 人工确认**，但**必须让人看见**。

### 2.3 并行的护栏（同族，一并核）

**npm 轴（`@linkdesk/ui` / `@linkdesk/plugin-sdk`）不许把内容发在壳之前**——即"新导出的组件，其 `since` 壳版本还没发布，就不该先上 npm"。这条与 `release:mark` / [`check-npm-release.mjs`](../../../../scripts/check-npm-release.mjs) 同族（现存纪律："**内容不许跑在版本号前面**"），本件只需**核一遍它是否已覆盖 ui 包新增导出的场景**，缺则补齐。

## 三、可选整合（顺手，不必须）

**`dev --real` 顺手跑一次 G2 门禁**：它手里有真壳，正好一边报「这个壳上跑不通」，一边报「你需要 ≥ `X`」。作者在**同一个终端**里拿到 **现象 + 结论 + 动作**，不用等 CI。

- 归属：SDK 的 dev 流程（**作者面**），因此**只做 G2 的判据**（地板 vs 声明），⛔ **不带 G5 的"最新已发布壳"比较**（那是我们的信息，作者侧不该有）。
- 优先级：低——G2 已在 `lint`/`build`/`publish` 上默认跑，这条只是**换一个更早的报点**。

## 四、交付判据

- [ ] 兼容读数对 `0.2.41` 上已装的 settings `1.0.35` **判为 `incompatible`／「不适配」**（不再是「正常」）——这是本格的**正控**。
- [ ] 产物扫描**复用**悬空扫描的 worker + 指纹缓存，**无新增常驻成本**；读不到产物时**退化不判坏**。
- [ ] `compatibility.ts` 的**五态映射与两个日期口径一字未动**（只加了输入）。
- [ ] G5 检查落壳仓发布链，**SDK 内零痕迹**（grep 取证）。
- [ ] ⛔ 没有任何一处把 G5 的"最新已发布壳"信息带进 SDK／作者文档。
