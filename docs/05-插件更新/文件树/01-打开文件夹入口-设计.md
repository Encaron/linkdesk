**用户痛点（原话概括）：** 打开文件夹的唯一 UI 入口在欢迎标签页里；欢迎页一关，就没地方再打开文件夹了——尤其把文件树目录清空之后。

**结论：缺口只在 UI 入口层——但它有两层，第二层是 2026-09-29 才查出来的。**

## 二·六 2026-09-29 勘查发现——文件菜单里的 file-tree 项为何「没有」了（真因）

> 用户原话（2026-09-29）：「我也记得我之前文件菜单项是有打开文件树的东西的，后来不见了，我一直以为是我自己在哪个任务中删的。」
> **结论：他的记忆是真的，而且不是他删的——是一笔重构把菜单槽位的键名写成了枚举的「成员名」，贡献从此落在死键上。**

### 机制（为什么错误键名 = 完全不可见的死键）

| 环节 | 事实 | 出处 |
|------|------|------|
| 槽位表 | `MENU_SLOTS.MenuBar = "menuBar"`、`MENU_SLOTS.FileContext = "fileContext"`（**值是小驼峰**） | `src/core/registry/commands/MenuRegistry.ts:38,42` |
| 存储 | `_menus` 是 `Map<MenuId, …>`，**精确字符串键，零归一化**；`normalizeMenuItem` 只归一化条目**字段**，不动菜单 id | 同上 `:96-106`（归一化）、`:111-138`（`registerMenuItems` → `_menus.set(menuId, …)`） |
| 读取 | 壳只按 `MENU_SLOTS.*` 常量值取：`getMenuItems(MENU_SLOTS.Panel) + getMenuItems(MENU_SLOTS.MenuBar)` | `src/hooks/usePoolSync/titlebar.ts:97` |
| 结果 | 插件写 `"MenuBar"` ⇒ 落进 `_menus` 的另一个键 ⇒ **无任何消费者**；无报错、无日志、界面只是「没有这一项」 | 全仓 grep `"MenuBar"` / `"FileContext"` 在 `src/` `electron/` **零命中**（2026-09-29 实测）= 无别名、真死键 |

### 来源（可指认到具体提交与具体那一行）

| 时间 | 事件 | 证据 |
|------|------|------|
| 2026-08-11 之前 | 插件 `import { MenuId } from "@src/core/registry/MenuRegistry"`，注册写 **`MenuId.MenuBar` / `MenuId.FileContext`** ⇒ 取到的是**枚举值**（`"menuBar"` / `"fileContext"`）⇒ **贡献是活的** | `git show af2ef5712^:plugins/builtin/file-tree/src/components/FileTreeContextMenu.tsx`（`:413` `MenuId.FileContext` / `:447` `MenuId.MenuBar` / `:515` `menuId={MenuId.FileContext}`） |
| commit `af2ef5712`（**E5.6#11.5 Path B 池核心隔离**） | 为切断插件对 `@src/core` 的 import，把 `MenuId` **内联成字符串字面量**——迁移表 F9 行写的目标形状是 `const MenuId = { FileContext: "FileContext", MenuBar: "MenuBar" }`。**把枚举的「成员名」当成了「值」**，而壳侧 `MenuId.MenuBar` 的值当时已经是 `"menuBar"` ⇒ 一刀切成死键 | `git show af2ef5712`（迁移表 F9 行）；改后同文件 `:397` / `:434` 已是 `"FileContext"` / `"MenuBar"` |
| 2026-09-17 `0a52098`、`cc588cf` 等后续重构 | 只是把这两处死键**原样搬**进新文件（`FileTreeContextMenu/commands/menuItems.ts:10,47`），历次门禁与实测都没碰它——因为**没有一条判据看菜单槽位 id 的大小写** | 本仓 file-tree `git log -S'"MenuBar"'`：该字面量自 `61264cf` 起一直在，`fileContext`/`menuBar` 小驼峰写法**在插件仓史上从未出现过**（`git log -S'registerItems("menuBar"'` 零命中） |

### 第二重缺陷（独立于键名，用户 2026-09-29 点名的语义）

即使把键名改对，菜单项**出现时机**仍不对：`registerFileTreeMenuItems()` 由 `activateFileTreeContextMenu()` 调用，而后者只由 **`FoldersView.tsx:54` 的 `useEffect`**（视图 mount）触发 ⇒ 「**必须先打开过文件树视图**，文件菜单里才会有这些项」。

用户要的语义（2026-09-29 原话）：「**安装上文件树这个插件就显示，而不是只有打开文件树才行**。就类似串口监视器在状态栏的小灯一样，只要安装上就显示。」
——用户引用的类比插件 `serial-monitor` 正是用**声明式** `contributes.menus`（`editorContext` / `quickSendContext` / `commandPalette`，小驼峰）声明它的菜单面的。

### 修法（两条缺陷一次消灭；零壳改动）

| 项 | 做法 | 为什么 |
|----|------|--------|
| 菜单槽位键名 | 插件不再**手写槽位字符串**，改为在 `plugin.json` 用**声明式 `contributes.menus`**（键 = `menuBar` / `fileContext`，即壳常量的值） | 键由 schema 键名即契约承载（`plugin.schema.json` 的 `contributes.menus` = `MenuId → 条目数组`，`$defs.menuItem` 允许 `command` 空串父项 + 递归 `children`）；加载器 `src/pluginLoader/contributions/contributions.ts:146-150` 直接 `registerMenuItems(menuId, pluginId, …)` |
| 出现时机 | 声明式 = **加载器在插件装载时注册**（卸载由加载器 disposer 回收），与视图是否 mount 无关 | 一次满足「装了就显示」；且比原先「mount 时注册、无遗弃路径」的生命周期更正确 |
| 附带 | `Menu.tsx` 消费端 `menuId={"FileContext"}` 同笔改 `"fileContext"`（两处必须同改——原先是「读写同一个错键」的自洽，只改一边会把右键菜单弄坏） | 读写同源才叫修好 |

**已否决的替代（记录理由，防回改）：** 把「编辑」子菜单的 `group` 由 `edit` 保留为**独立顶级组**——那样菜单栏会多出一个顶级「编辑」菜单，且因组序由「组内首项的 `order ?? 99`」决定（`titlebar.ts:104-106`）而排在**帮助之后**（最右）。本补丁改为把该父项并入 `group: "file"`，渲染成 `文件 ▸ […, 编辑 ▸]` 嵌套子菜单（`titlebar.ts:131-142`：`label !== 组标签` 的无 command 父项保留层级）⇒ **顶级菜单集合一个不增**，五项 + 一个子菜单都落在「文件」里，与用户心智一致。

### 门禁（用户 2026-09-29 授权添加 · 当日落地）

新增判据，**只判这一类、且零误报可能**：一个菜单槽位 id 若与宿主 `MENU_SLOTS` 的某个值**仅大小写不同** ⇒ 红。
理由：`MenuId` 是开放字符串（第三方可自造注册点，见 `MENU_SLOTS` 头注），所以「未知 id」**不能**判红；但「与宿主槽位仅差大小写」的 id **没有任何合法用途**，只可能是这类拼写事故——判据因此可以做到既严格又零假红。
落点按既有铁律「**新判据先落 SDK，插件 CI 判红**」：SDK 新增一条 check 腿（宿主槽位名单随包下发，照 `schemas/host-css-names.json` 的「生成器 → 随包 JSON → 作者侧腿」三件套先例），壳仓只提供生成器与 `--check` 漂移门禁。

**落地三件套（照抄 `host-css-names.json` 先例，2026-09-29 实现）：**

| 层 | 落点 | 说明 |
|:--|:--|:--|
| 壳生成器 | `scripts/gen-host-menu-slots.mjs` | 解析 `src/core/registry/commands/MenuRegistry.ts` 的 `MENU_SLOTS` → 随包 JSON。带 `--check`（漂移对账）＋ `--self-test`（9 例），两者**都已挂进壳 `npm run check`**；另有 `npm run menu-slots:regen` / `menu-slots:check` |
| 随包名单 | `packages/plugin-sdk/schemas/host-menu-slots.json` | 14 条槽位（`entries: [{key, value}]`）——`key` 是成员名、`value` 是插件该写的值；**生成物勿手改** |
| 作者侧腿 | `packages/plugin-sdk/src/eslint/checks/menu-slots.ts`（＋ `menu-slots.test.ts` 11 例） | 腿 id `linkdesk/no-menu-slot-case`，进 `lint.ts` 的 `legs`（第 12 条）。名单读不到 ⇒ **fail-closed 报「未核验」并红**（⛔ 不许当 0 处通过） |

**判据物 = 三个字面量通道**（匹配前一律先剥注释——本腿的文档注释里就写着 `"FileContext"` / `"MenuBar"` 两个反面例子，不剥注释这条腿会被自己的文档判红）：

1. `plugin.json` 的 `contributes.menus` **键**（声明式注册点，`via: "declarative"`）；
2. `.registerItems("<字面量>"` / `.getItems("<字面量>"`（命令式菜单 API，含 `?.` 可选链与解构后的裸调用，`via: "menu-api"`）；
3. `menuId={"<字面量>"`（`@linkdesk/ui` 的 `ContextMenu` 等件的菜单 id prop，含 `menuId: "…"` 写法，`via: "menu-id-prop"`）。

⚠️ 生成器 `--self-test` 里钉了一条**本门禁自己的题眼**：`MENU_SLOTS` 的**值不得等于任何成员名**（当年那句 `FileContext: "FileContext"` 一旦进真源，「成员名 vs 值」这对概念就在名单里自撞、判据词根失效）——今天真源 14 条零命中。

## 三、8 维度设计（三版共同部分）

### ① 能力边界
