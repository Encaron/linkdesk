# 04 — 运行期契约校验设计（E5.8#22.5）

> 2026-08-20。**编译期契约挡不住版本错配**：用户升级壳而 plugins 目录保留（旧插件 vs 新壳）/ dev 热更新双端瞬时不一致 → 插件侧读到静默异形数据（字段缺失/错型，`undefined` 蔓延）= 生存力漏洞。
> 本设计 = 在**接收边界**对推流载荷做运行期形状断言——「哪条通道拿到异形数据」可查可诊断。
>
> 前置：Phase 4 契约生成已通车（#19 生成器 / #21 contracts-ready 门禁）。设计 §8 约束：**复用 #19 生成管线的类型图，不另起炉灶，输入 = 同一契约源**。

---

## 1. 问题与目标

| 场景 | 编译期契约 | 运行期校验 |
|------|:--:|:--:|
| 旧插件 vs 新壳（payload 形状变更） | 挡不住（插件与壳不同期编译） | ✅ 接收边界报「哪条通道 + 哪条字段」 |
| dev 热更新双端瞬时不一致 | 挡不住（瞬时态无编译） | ✅ 逮到即报 |
| 手写 push 绕过类型检查（`as any`） | 挡不住 | ✅ 逮到即报 |
| 生产环境误判 | —— | ✅ **never-throw + log-only，不崩** |

**目标**：契约从「编译期死」再进一步——**边界运行期断言**，形状失配在 dev 可诊断、生产不崩。

**验收**：故意制造版本错配（注册通道推一个形状与契约不符的载荷）→ dev 下 console.error 报「channel + 字段路径 + 期望/实收」；生产下同载荷不抛异常不崩。

## 2. 范围——注册的 DTO 通道清单

| `tab:activated` | `TabActivatedPayload` | 壳→池 | 同上 |
| `workspace:activeChanged` | `WorkspaceActiveChangedPayload` | 壳→池 | 同上 |
| `settings:requestGroup` | `SettingsRequestGroupPayload` | 壳→池 | 同上 |
| `settings:scrollTo` | `SettingsScrollToPayload` | 壳→池 | 同上 |

| `pool:quickpick` | `PoolQuickPickData` | 壳→池 | [types/pool/poolQuickPick.ts](../../../../src/core/types/pool/poolQuickPick.ts) |

> 通道名**源唯一**：注册表 import `electron/ipc/channels.ts` 的 `IPC` 常量（不手写字面量）。serial:data/system（string）与 p2p（插件自定义载荷）不注册——值类型无结构可查 / 无契约可对。

**注册表文件**：`electron/ipc/runtime-dto-registry.ts`（生成器输入，非产物）——`export const RUNTIME_DTO_REGISTRY: { channel: string; type: string }[]`，channel 取 `IPC.*` 常量、type 取契约类型名。加通道 = 加一行；漏注册 = 该通道无断言（安全降级，不红）。

## 3. 产物形态——`contracts/runtime-shapes.ts`（第二生成产物）

与 linkdesk.d.ts 同构的**自包含单文件**，零 import（内嵌全部 guard），编译到 CommonJS 供 preload require：

```typescript
// contracts/runtime-shapes.ts（自动生成，勿手改；生成器第二产物）
/** 每注册 DTO → assert<Name>(v): string[]——空数组 = 形状正确 */
export function assertConfigurationChanged(v: unknown): string[] { ... }
// ... 每注册类型一个 assert

/** 通道 → 断言查表——未注册通道返回 null（无断言） */
export function validateWire(channel: string, payload: unknown): string[] | null {
  switch (channel) {
    case "config:changed": return assertConfigurationChanged(payload);
    // ... 注册表逐行
    default: return null;
  }
}
```

**guard 语义**：
- 返回**字段路径数组**（`payload.key: 期望 string，实收 number`）——直给「哪条字段错了」；
- `undefined` 允许（可选字段 `?`）、`unknown`/`any` 不查、数组逐元素、`Record<string, T>` 逐值、literal 联合 `===` 任一；
- 嵌套命名类型 → 生成**命名子 guard** 函数引用（不内联展开，防递归类型爆栈/膨胀）；
- **never-throw**——输入任意垃圾值也只返回错误串，绝不抛异常（生产安全的核心）。

## 4. 生成管线——复用 #19，双产物双门禁

```
generate-contract.mjs
  ├─ 契约类型图（现有）            → contracts/linkdesk.d.ts
  └─ 新增：运行期断言发射器         → contracts/runtime-shapes.ts
```

**发射器**（生成器内新模块 `emitRuntimeShapes`）：
1. 读 `runtime-dto-registry.ts`（AST 解析导出 const，取 channel + type 名）+ 解析 `channels.ts` 的 `IPC.*` 常量值（AST 求值）→ 通道名字面量；
2. 对每个注册 type，用**现有 checker** `getTypeOfSymbol` 取解析后类型 → 递归发射 guard（表驱动：primitive/literal/union/array/object/optional/Record/命名引用）；
3. 拼接 `validateWire` 查表 + 头注释（注明生成源/勿手改/--check 门禁）。

**门禁**：`npm run contracts:check`（`--check` 字节比对）**扩展到双产物**——runtime-shapes.ts 与 linkdesk.d.ts 一样：改动契约源/注册表 → 未重新生成即红。`package.json` 脚本不变（contracts:gen/check 同入口，内部双产物）。

**确定性**：guard 发射只依赖类型图 + 注册表，无随机/无时间 → 字节稳定可比对（与 #19 同保证）。

## 5. 挂载点——接收边界 + 诊断面

**接收边界 = 断言点**（「哪条通道拿到异形数据」）：

| 挂载点 | 文件 | 说明 |
|:--|:--|:--|
| **push 分发统一入口** | [electron/ipc/event-system.ts](../../../../electron/ipc/event-system.ts) `createEventSystem.on` 的 handler | 池/壳共用——push 载荷过边界第一站，`cb(data.payload as T)` cast 前 |
| **extraHandlers** | 同文件 | theme:changed CSS 注入等额外处理器载荷 |
| **pool host 直收** | preload-pool/quickpick.ts / toast-dialog.ts 的 `ipcRenderer.on` | PoolQuickPickData/PoolToastData/PoolDialogData 直收点 |

**挂载方式**（新模块 `electron/ipc/wire-guard.ts`）：
```typescript
import { validateWire } from "../../contracts/runtime-shapes";
/** 接收边界断言——never-throw，失配 console.error 进诊断面，透传载荷（不阻断） */
export function guardPush(channel: string, payload: unknown): void {
  const errs = validateWire(channel, payload);
  if (errs && errs.length > 0) {
    console.error(`[wire-guard] 🔴 channel=${channel} 载荷形状失配:\n  ` + errs.join("\n  "));
  }
}
```
- **诊断面** = console.error（与 event-system.ts listenDirect 告警同款——preload 不 import @src，无 ErrorService 可走；dev 控制台即诊断面，够可查）。
- **透传不阻断**——guard 只记录，载荷照常 `cb(payload)` 分发：断言自身绝不影响业务路径。

**dev-only？** v1 设计 = **常驻运行 + log-only + never-throw**：生产零门禁风险（永不抛），且生产真实错配也留痕（比静默强）。perf 可忽略（每 push 几字节形状检查）。「dev 可诊断」由 console.error 满足；不加 dev 旗标（免 preload 旗标管道，见备选 §6）。

## 6. 备选——dev-only 开关（不选，记录理由）

| 方案 | 优点 | 代价 | 结论 |
|:--|:--|:--|:--|
| **A 常驻 + log-only**（采用） | 无旗标管道；生产也保护 | 每 push 微秒级检查 | ✅ 简单 + 生产留痕 |
| B dev-only（`process.env.LINKDESK_DEV`） | 生产零开销零日志 | preload 需旗标管道（主进程传参/global）；生产裸奔 | 不选——生产场景正是本任务防护目标 |

---

## 7. 验收方案

1. **故意错配**：在 dev 对一个注册通道（如 `theme:changed`）push 一个形状不符的载荷（缺 `variables` / `themeType` 错型）→ 控制台出 `[wire-guard] 🔴 channel=theme:changed 载荷形状失配: payload.themeType: ...`，且载荷**照常分发**（业务不阻断）。
2. **生产不崩**：单测喂垃圾输入（`null` / 错型 / 嵌套损坏）到 `validateWire` → 断言返回错误串**而非抛异常**（`expect(() => validateWire(...)).not.toThrow()`）。
3. **门禁**：删/改 runtime-shapes.ts → `contracts:check` 红；恢复/重生成 → 绿（双产物字节比对）。
4. **注册表联动**：向 `runtime-dto-registry.ts` 加一行新通道 → 重生成后 `validateWire` 出现对应 case（grep 实证）。
