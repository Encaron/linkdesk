# 07 — 插件间通信

> 2026-07-28 · E5.8 全量更新 2026-08-21 · **E6 核 2026-09-06**（E6#58：三通信机制 E5.8 后未变，逐段核零残留，原样保留）。**插件之间怎么传数据？** 不是"终端开个门给协议"——所有通信走核心提供的管道。插件只负责用，不需要建。

---

## 一、核心原则

```
❌ 插件 ⇄ 插件    （直接握手——LinkDesk 不允许）

✅ 插件 → 核心 → 插件  （核心提供管道，插件只是用）
```

**只有核心建 API。插件不建 API。** 插件做的事：调核心给的函数，往管道里读写数据。

---

## 二、三通信机制——核心提供，插件选用

| | 广播 `events` | 命令 `commands` | 数据管道 |
|------|------|------|------|
| API | `events.emit/on` | `registerCommand` / `executeCommand` | `serial.onData/onStats/onSystem` + `lsp.onData` + `filesystem.watch` |
| 语义 | 谁订阅谁收到（同池内按 channel 过滤） | 具名可调用动作 | 高频推流——**流**，不是事件 |
| 生产者知道消费者吗 | 不知道 | 不知道（命令谁都能调） | 不知道 |
| 目标不在线 | 无所谓——没人听就没人听 | 命令未注册 → no-op | 订阅方自己负责 |
| 适合 | 事件广播、状态变更、数据共享 | 暴露能力给别人调 | 串口数据、LSP 输出、目录变更 |
| 比喻 | 广场上的喇叭 | 服务台叫号 | 水龙头 |

**三套可同时使用。** 终端收到一串串口数据，可以同时：
- 走 `events.emit` 广播给日志插件（谁都该知道）
- 走数据管道 `serial.onData` 推给协议解析（高频、流式、带端口路由键）
- 暴露 `registerCommand('xxx.send', handler)` 让别的插件发数据回设备

> 历史上有「后门 p2p」作为第二管道——见 §四：已建，但 target 路由已删，语义归一为池内广播。

---

## 三、广播 `events`——广场上的喇叭

```
终端                          协议                        日志插件
  │                            │                            │
  │ events.emit(               │                            │
  │   'serial:rawData',        │                            │
  │   { portName, text }       │                            │
  │ )                          │                            │
  │         ↓                  │                            │
  │     核心广播                │                            │
  │   （池 + 壳，按 channel）   │                            │
  │         ↓                  ↓                            ↓
  │                     events.on(                   events.on(
  │                       'serial:rawData',            'serial:rawData',
  │                       callback                     callback
  │                     )                            )
  │                       解析字节                    记录日志
```

**发送方不知道谁在听。** 0 个人、1 个人、10 个人——都一样，`emit` 完就走。

**频道名是字符串。** 核心不知道 `'serial:rawData'` 是什么意思。频道名约定：`<插件id>:<数据名>`。

**代码（`on<T>` 泛型——载荷类型按订阅方 cb 推断，跨进程类型安全见 §十一）：**
```typescript
// ── 发出数据（插件 A）──
window.linkdesk.events.emit('serial:rawData', {
  portName: 'COM3',
  text: '\xAA\x01\x02'
})

// ── 接收数据（插件 B）──
const unsub = window.linkdesk.events.on<{ portName: string; text: string }>(
  'serial:rawData',
  (data) => {
    console.log(data.portName, data.text)  // COM3, \xAA\x01\x02
  }
)
// 组件卸载时清理
// unsub()
```

**通道是广播到「池 + 壳」。** 池 emit → 主进程 `plugin:emit` → 广播 `plugin:push` → 池 + 壳都收到。想从池侧直接发到壳且不回流 = `p2p`（§四）。

## 四、后门 `p2p`——包间里的电话（已建，target 路由已删）

```
终端                          协议
  │                            │
  │ p2p.send(                  │
  │   'sbq-protocol',     ← 指定收件人（历史语义）
  │   'serial:raw',            │
  │   data                     │
  │ )                          │
  │         ↓                  │
  │     主进程直接发池          │
  │      （不经 broadcast）     │
  │         ↓                  │
  │                     p2p.on('serial:raw', callback)
  │                       按 channel 过滤——不广播
```

**状态：已建（E5#65），不再是「计划」。** 签名：

```typescript
interface P2pApi {
  send(target: string, channel: string, data: unknown): void;   // fire-and-forget
  on(channel: string, cb: (data: unknown) => void): () => void; // 返回 unsubscribe
}
```

**⚠️ E5.7#43 target 路由已删。** Per-Tab WebView（每个插件一个实例）不存在后，唯一接收方就是池——`target` 参数保留（向后兼容、不删签名）但**不参与路由**：发出去就是发到池，谁 `p2p.on` 同一个 channel 谁收到。**零验证、零报错**——target 写错也不会报"目标未运行"。

**p2p vs events 现在的差别：**
- `events.emit` → 广播 `plugin:push` → **池 + 壳**都收到（壳可加桥联动，见 §十一）
- `p2p.send` → 主进程直发 **池**（独立 `p2p:data` 通道），不经 broadcast

所以：需要壳联动 → 用 events；只打算在插件之间传且不想触发壳桥 → p2p。高频场景二者性能差异已无所谓（单池内同进程分发）。新代码默认 events，p2p 用于不想扰动壳广播路径的定向测试通道（serial-monitor 的 `test-p2p` 就是这种用法）。

## 五、命令 `commands`——服务台叫号

**一个插件的"能力" = 一组具名命令。** 别人（壳或另一个插件）调用它 = `executeCommand`。

```typescript
// ── 插件 A 注册能力（组件 mount 时）──
window.linkdesk.commands.registerCommand('serial-monitor.send', (args?: { text: string }) => {
  // 往串口发数据
})

// ── 插件 B 调用能力 ──
await window.linkdesk.commands.executeCommand('serial-monitor.send', { text: 'AT\r\n' })
```

**注册语义：**
- `registerCommand` 幂等（Map.set 覆盖）——StrictMode 双挂载安全
- `when: "false"` = 纯程序化命令，不进命令面板（`titleActions` 声明制专属命令就是这种，见 `08`）
- **命令是 `titleActions` 的落地机制**——声明式 `titleActions` 里每个 widget 的 `command` 字段，点击时池侧 `executeCommand` 执行（池侧注册表优先、壳 IPC fallback）

## 六、数据管道——流，不是事件

广播 `events` 处理"一次性通知"；**数据管道处理"持续灌入的流"**。串口数据、LSP 输出、目录变更都是流——不是"告诉你一次"，是"不停灌给你"。

| 管道 | API | 载荷 | 路由键 |
|------|------|------|------|
| 串口数据 | `serial.onData(cb)` | `SerialDataPayload` | `portName`（E5.8#28 多口） |
| 串口统计 | `serial.onStats(cb)` | `SerialStatsPayload` | `portName` |
| 串口系统事件 | `serial.onSystem(cb)` | `SerialSystemPayload` | `portName` |
| LSP 输出 | `lsp.onData(cb)` | `(channelId: string, data: string)` | `channelId` |
| 目录变更 | `filesystem.watch(dir, cb)` | `FileChangeEvent` | —（内部 `filesystem:changed:<watcherId>`） |

```typescript
// 订阅串口数据——载荷对象化带 portName 路由键：多口并存各口各收
const unsub = window.linkdesk.serial.onData((p) => {
  if (p.portName !== 'COM3') return;   // 谁消费谁过滤——壳不代收
  handleBytes(p.data);
});
// 卸载清理
// unsub()

// 监听目录变更——返回 unsubscribe
const off = await window.linkdesk.filesystem.watch('/workspace', (e) => {
  // e: FileChangeEvent
});
// off()
```

**流语义（RingBuffer 教训）：**
- **数据是流不是事件。** 不是"通知一次"——是"持续灌入"。订阅方自备缓冲/过滤。
- **消费方按路由键过滤**（`portName` / `channelId`）——这是通用路由键模式：谁消费谁过滤，壳不代收。
- **需要完整历史的消费方**可 `import { RingBuffer } from "@src/core/pipeline/RingBuffer"`（纯工具白名单——`@src/core/pipeline/*` 是插件允许 import 的例外，见 `01 §五`）。RingBuffer 是流式消费的标准件，不是事件总线。
- **内部归一化：** E5.8#6.5 起 `serial.onData/onStats/onSystem` 底层就是 `events.on("serial:data"/"stats"/"system")`——三通道走广播管道，无独立 direct 通道。插件不需要知道这些细节，`serial.onXxx` 就是唯一入口。

## 七、终端——第一个交出数据的插件（E3j #77-#79，历史参考）

> 2026-08-21 注：本节是 E3 时代的历史记录，**终端插件的当前实现已与下述任务有出入**（数据源已归一化到数据管道）。保留作为"第一个数据源插件怎么做"的模式参考。

E3j 让终端把三样东西交到大厅：

| # | 做什么 | 用哪个 API | 谁受益 |
|---|--------|-----------|--------|
| #77 | 推原始串口数据 | `events.emit('serial:rawData', data)` | 协议插件订阅后解析 |
| #78 | 广播连接状态 | `events.emit('serial:connected', {...})` | 状态栏/其他插件 |
| #79 | 接收发送命令 | `registerCommand('serial-monitor.send', handler)` | 工作台卡片发数据回 MCU |

**终端没有建任何 API。** 它只调了核心已有的函数：`events.emit`、`registerCommand`。今天的终端走 `serial.onData/onStats/onSystem` 数据管道（§六）+ 命令（§五）——同一原则的进化版。

## 八、以后每个插件怎么做

新插件进场，回答两个问题：

**1. 我有什么数据别人可能需要？**
→ 数据是流 → 走数据管道（§六，串口/LSP/文件场景）或 `events.emit('频道名', 数据)`。频道名按约定起。

**2. 我有什么能力别人可能需要调用？**
→ 调 `registerCommand('命令名', handler)`。命令名自己起。`handler` 是自己写的处理函数。

两个问题答完，该插件没有额外工作要做。**桌子是核心的，管道是核心的，函数是核心的。插件只是用。**

## 九、为什么这么说

> "终端建 API，协议连接终端的 API"

**这不是 LinkDesk 的模式。** 这是"开门"模式——每加一个插件，N 个插件之间开 N×(N-1) 扇门。

LinkDesk 的模式：

- **管道 = 核心建一次。** `events.emit`、`events.on`、`p2p.send`、`p2p.on`、`registerCommand`、`serial.onData`——这些函数是核心的，不是任何插件的。
- **频道名/命令名 = 插件自己起。** `'serial:rawData'`、`'sbq-protocol:parsed'`——字符串而已，核心不知道意思。
- **新数据源 = 不需要改核心。** 新插件调同一行 `events.emit('新频道名', 数据)`，核心代码零改动。

**核心的工作量是 O(1)，不是 O(N)。** 这就是插件自由化。

## 🔥 十一、AI 开发者必读——新插件需要新通信时怎么改

> 2026-08-04（E5.8 更新）。**E5#10 React Fallback 退役后发现的模式。**
> 这也是 LinkDesk 插件自由化的核心循环——不是 bug，是正常开发流程。

**先问一句：这条通信需要壳参与吗？** 答案决定改哪里。

### 11.1 场景

你正在开发一个新插件。它需要接收某种外部指令（壳或其他插件发来的数据），但现有 `window.linkdesk.events` 里没有对应的事件类型。

**示例：** editor 插件需要知道打开了哪个文件。但当前没有 `editor:openFile` 事件——editor 的 `sourceId` 是靠 React props `<EditorView sourceId="xxx" />` 传的。

### 11.2 三种情况，三种改法

| 情况 | 改哪里 | 壳要动吗 |
|:--|:--|:--|
| **插件 ↔ 插件**——只是两个插件间传数据 | **零改动。** `events.emit('myPlugin:xxx', payload)` + 对方 `events.on`。channel 是自由字符串契约，订阅方收窄载荷 | ❌ 不用 |
| **插件 → 壳联动**——壳要响应（关标签/切视图/显隐） | **`src/App/bridges.ts`（`useUiBridges`）加一个桥**：一段 `events.on("channel", ...)` → `shellEvents.emit(...)` | ✅ 只加桥，不改架构 |
| **跨进程载荷要类型安全** | 载荷类型定义进 `src/core/api/` 生成源 → `contracts:gen` 重新生成契约 → 双端 `import type` | ✅ 契约机械门禁 |

**插件 ↔ 插件（最常见，零壳改动）：**
```typescript
// 插件 A——发
window.linkdesk.events.emit('editor:openFile', { filePath: 'xxx' })

// 插件 B——收（零壳改动）
window.linkdesk.events.on('editor:openFile', ({ filePath }) => { ... })
```

**插件 → 壳联动（加桥——`bridges.ts` 现有桥清单）：**

| 桥（`bridges.ts` 已内置） | 壳联动做什么 |
|:--|:--|
| `icon:selected` / `icon:reordered` | 图标栏点选开标签 / 拖拽换位持久化 |
| `file:deleted` / `file:renamed` | 文件树资源事件 → TabManager 关标签/迁移 label |
| `panel:viewSelected` / `panel:resize` / `panel:toggleViewVisibility` | 面板切视图 / 拖拽改高 / 勾选显隐 |
| `panel:createView` | 面板 [+] → QuickPick 视图选择器 |

```typescript
// 壳侧 bridges.ts 加桥的模板（对照现有 file:deleted 桥）：
useEffect(() => {
  const off = window.linkdesk?.events?.on("myPlugin:someEvent", (payload) => {
    shellEvents.emit("myPlugin:someEvent", payload);
  });
  return () => { off?.(); };
}, []);
```

**壳侧事件类型**（`shellEvents.emit` 的载荷）定义在 `src/core/react/events/ShellEvents.ts`——需要时在类型表加一行。

### 11.3 什么情况需要加通信

| 场景 | 需要通信？ | 用哪个 |
|:--|:--|:--|
| 新插件需要接收壳指令 | ✅ 是 | 壳 `bridges.ts` 加桥 → `events.on` 订阅 |
| 新插件推送数据给其他插件 | ✅ 是 | `events.emit`（事件）或数据管道（流） |
| 新插件只在内部管理状态 | ❌ 不用 | 组件内 state / 插件自有 EventTarget model（`05 §8`） |
| 新插件需要读取配置 | ❌ 不用 | `linkdesk.configuration.get()` |
| 新插件需要操作文件 | ❌ 不用 | `linkdesk.filesystem` |

### 11.4 关键原则

- **`contracts/linkdesk.d.ts` 是 API 签名唯一真相源；`bridges.ts` 是壳↔池桥接器集合。** 新 AI 只需要读这两个就知道全部通信面。
- **加通信是正常的，不是 hack。** LinkDesk 的设计就是"壳是空的，API 在管道里长"。VS Code 从 10 个 API 长到 1000+，LinkDesk 同理——频道表会持续增长。
- **不要在壳里为插件写分支代码。** 壳只负责 `emit`/`on` 转发——插件自己处理业务逻辑。
