# 静默吞错审计——`.catch(() => {})` 残留

> 2026-08-06。盲审建议：10+ 处静默吞错让运维排查难。15 分钟修改，价值巨大。
> E5#38 ErrorService 已覆盖 5 种错误处理模式，但盲审发现仍有残留。
> 位于 E5 收尾 → `05-收尾/架构债/`

---

## 一、前因

E5#38-#39 新建了 `ErrorService.reportError()` 统一入口，覆盖了：
- FileService 9 方法——try/catch + reportError
- ConfigurationService 监听器——`catch {}` → `console.error`
- CommandRegistry——动态 import toast → reportError
- App.tsx 串口——setLastError + reportError（双轨）
- loader——pushToast → reportError（2 处）

但审计只覆盖了**已知的 5 种模式**。盲审指出还有 10+ 处 `catch(() => {})` 静默吞错散布在工程各处。

---

## 二、审计方法

```bash
# 找所有静默吞错（空 catch 块）
grep -r "catch\s*(" src/ plugins/ electron/ \
  --include="*.ts" --include="*.tsx" \
  | grep -v "node_modules" \
  | grep -v "reportError" \
  | grep -v "console\." \
  | grep -v "throw"
```

关注模式：
- `catch {}` — 最恶劣，连参数都没
- `catch (e) {}` — 有参数但空块
- `catch { /* 什么都不做 */ }` — 注释表明故意
- `.catch(() => {})` — Promise 链静默
- `.catch(() => undefined)` — 降级但不留痕

---

## 三、修复原则

每个静默吞错至少做**一件事**：

1. **开发者可见：** `console.error("[模块] 描述:", e)` — 最低成本
2. **用户可见：** `reportError({ message, source, error })` — E5#38 的 ErrorService
3. **如果是故意的（可恢复降级）：** 加注释说明**为什么**不需要处理——而不是空块

```typescript
// ❌
try { await persist(data); } catch {}

// ✅ 最低
try { await persist(data); } catch (e) { console.error("[pluginState] 持久化失败:", e); }

// ✅ 最佳——有 ErrorService 的地方
try { await persist(data); } catch (e) {
  reportError({ message: "插件状态保存失败", source: "pluginState", error: e });
}

// ✅ 故意吞——有注释
try { await nonEssentialOp(); } catch {
  // 非关键操作，失败不阻塞主流程
}
```

## 四、和 E5#38 ErrorService 的关系

E5#38 建好了管道——`reportError()` 双轨输出（console.error + toast）。本轮的任务是**扫一遍全项目**，把残留的静默吞错补上 `console.error` 或 `reportError`。

不是重写 E5#38，是补漏。

---

## 五、可能遇到的问题

### 1. 静默吞错是故意的

**风险：** 某些 `catch {}` 是有意为之——比如清理代码、非关键操作、降级逻辑。强行加日志反而制造噪音。

**缓解：** 区分两类：
- **数据操作**（持久化、配置读写、文件操作）→ 必须日志
- **清理代码**（unregister、cleanup、dispose）→ 可保留静默，但加注释

### 2. 循环依赖

**风险：** 某些模块 import `reportError` 会形成循环依赖——E5#38 的零依赖设计就是为了避免这个。

**缓解：** 如果 `import { reportError }` 导致循环 → `import("./ErrorService").then(m => m.reportError(...))` 动态绕路。或者用 `console.error`（无依赖）。

### 3. 插件层不可用 ErrorService

**风险：** ESLint `no-restricted-imports` 拦截插件 import `@src/core/*`——插件不能用 reportError。

**缓解：** 插件用 `console.error` 或 `linkdesk.dialog.alert()`（如果操作需要用户感知）。本轮重点在 `src/` 和 `electron/` 下。
