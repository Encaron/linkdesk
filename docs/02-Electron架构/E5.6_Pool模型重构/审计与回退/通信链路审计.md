## 2. 链路审计——侧栏 → 主区

### 2.1 当前完整路径

侧栏中的插件视图有两种方式打开主区标签页：

**路径 A — ShellEvents / TabActionsContext（壳内）：**
```
SidePanel 渲染的插件组件调用 useTabActions()
    → TabActionsContext.ts:28  shellEvents.emit("tab:create", { type, opts })
    → TabActionsContext.ts:32  shellEvents.emit("tab:openOrFocus", { type, opts })
      → MainContent.tsx:221  shellEvents.on("tab:create", ...)
      → MainContent.tsx:222  shellEvents.on("tab:openOrFocus", ...)
        → createTab() / openOrFocusTab() → tabState 更新
```

**路径 B — `window.linkdesk.tabs.*`（IPC——已跨 WebView）：**
```
插件组件调用 window.linkdesk.tabs.openOrFocus(type, opts)
    → ipcRenderer.invoke('tabs:openOrFocus', { ... })
      → 主进程 handler
        → shellWindow.webContents.send('tabs:openOrFocus', { ... })
          → 壳 preload IPC 监听器 → React handler → tabState 更新
```

### 2.2 涉及的事件

| 事件 | emit 位置 | on 位置 | 跨 WebView？ |
|:--|:--|:--|:--|
| `tab:create` | TabActionsContext:28 | MainContent:221 | 否（壳内） |
| `tab:openOrFocus` | TabActionsContext:32 | MainContent:222 | 否（壳内） |
| `tab:focus` | TabActionsContext:35 | MainContent:223 | 否（壳内） |
| `tab:close` | TabActionsContext:37 | MainContent:224 | 否（壳内） |
| `tab:focusBySourceId` | TabActionsContext:40 | MainContent:225 | 否（壳内） |
| `tab:updateLabelBySourceId` | TabActionsContext:41 | MainContent:226 | 否（壳内） |
| `tab:closeBySourceId` | TabActionsContext:43 | MainContent:227 | 否（壳内） |

### 2.3 Pool 模型分析

| 组件 | 当前位置 | Pool 模型位置 | 通信方式变化 |
|:--|:--|:--|:--|
| useTabActions() 调用方 | 壳 WebView | **SidebarPool** | `shellEvents` 不可用！ |
| TabActionsContext | 壳 WebView | 壳 WebView | **不变** |
| MainContent tab: handlers | 壳 WebView | 壳 WebView | **不变** |

**判决：路径 A（ShellEvents/TabActions）在 Pool 模型下断裂。** SidebarPool 中的插件代码不能调用 `shellEvents.emit()`——`shellEvents` 是壳 WebView 的内存对象。

**但路径 B（`window.linkdesk.tabs.*`）已跨 WebView 可用。** 这是 `preload-plugin.ts` 暴露的 API，走 `ipcRenderer.invoke` → 主进程 → 壳 WebView。

**结论：** SidebarPool 中的插件代码必须走路径 B（`window.linkdesk.tabs.*`）。现有代码中，侧栏插件（file-tree 等）是否已经在用 `window.linkdesk.tabs.*`？

**需要验证的点：**
- 文件树双击打开文件：走 `window.linkdesk.tabs.openOrFocus("editor", { sourceId: path })` — 已在 IPC 上 ✅
- 搜索→打开文件：同上 ✅
- 侧栏中的其他自定义操作（如 marketplace "打开"按钮）：需要确认是否用了 `window.linkdesk.tabs.*` 还是 `useTabActions()`

**风险：** 如果侧栏中有插件组件使用 `useTabActions()`，在 SidebarPool 中将失效。审计 [viewRegistry.ts](../../../src/pluginLoader/viewRegistry.ts) 和侧栏渲染的插件列表。

## 5. 链路审计——拖拽线 resize

### 5.1 当前完整路径

```
App.tsx:342  onResizeMouseDown
    → dragging.current = true

App.tsx:348  window mousemove (useEffect)
    → if (!dragging.current) return
    → layoutEngine.resizeZone("sidebar", w)
    → layoutEngine._recalculate()
    → onDidChangeLayout.fire()

App.tsx:356  window mouseup
    → dragging.current = false

App.tsx:323  layoutEngine.onDidChangeLayout
    → 遍历 getAllZones() → getBounds() → setZoneBounds(b)
    → React 重渲染 IconBar / SidePanel / MainContent / StatusBar（全部用新 bounds）
```

### 5.2 涉及的通信

| 步骤 | 机制 | Pool 模型变化 |
|:--|:--|:--|
| mousemove 事件捕获 | App.tsx window listener | → **移到 OverlayWindow** |
| layoutEngine.resizeZone() | 直接调用 | → **OverlayWindow 通过 IPC 调壳的 layoutEngine** |
| onDidChangeLayout → zoneBounds | App.tsx state + React render | **不变**（壳内） |
| zoneBounds → SidebarPool bounds | 无（单 WebView） | 🆕 **push layout IPC** |
| zoneBounds → MainPool bounds | 无（单 WebView） | 🆕 **push layout IPC** |

### 5.3 Pool 模型分析

**判决：拖拽线需要搬到 OverlayWindow。** 原因：拖拽线是一个独立的、覆盖在 Shell + SidebarPool + MainPool 之上的透明窗口——它的 z-index 必须高于所有 WebContentsView。

**变更：**
```
当前：App.tsx resize handle div → window mousemove → layoutEngine.resizeZone
Pool：OverlayWindow mousemove → IPC('layout:resizeZone', { zone: 'sidebar', width }) → 壳 → layoutEngine.resizeZone
```

## 6. IPC 通信基础设施审计（追加——第二轮自查）

> 2026-08-09 第二轮自查。第一轮只审计了 ShellEvents（壳内事件总线），遗漏了 IPC 层——`events.emit/on`、`bridge.broadcast`、`tabs.*`、`plugin:push` 通道。

### 6.1 `events.emit/on`——跨 WebView 事件系统

**实现：** [event-system.ts](../../../electron/event-system.ts) — `createEventSystem()` 工厂函数，preload-plugin.ts + preload-shell.ts 共用。

**emit 链路（插件→全局广播）：**
```
插件代码: window.linkdesk.events.emit("myEvent", data)
    → ipcRenderer.send('plugin:emit', { channel: "myEvent", payload: data })    [event-system.ts:72]
      → 主进程 ipcMain.on('plugin:emit', ...)                                   [ipc-bridge.ts:261]
        → this.broadcast(channel, payload, sourceId)                            [ipc-bridge.ts:270]
          → 遍历所有 plugin WebView → view.webContents.send('plugin:push', ...) [ipc-bridge.ts:244]
        → this.mainWindow.webContents.send('plugin:push', ...)                   [ipc-bridge.ts:272]
          → 壳 preload-shell events.on 接收
```

**on 链路（任意 WebView→接收广播）：**
```
插件代码: window.linkdesk.events.on("myEvent", cb)
    → ipcRenderer.on('plugin:push', handler)                                     [event-system.ts:66]
    → handler 匹配 data.channel === "myEvent" → cb(data.payload)
```

**Pool 模型判决：✅ 零改动。** 无论 emit 方在 SidebarPool、MainPool 还是壳——事件都会广播到所有 WebView。这是 Pool 模型的通信骨干。

### 6.2 `bridge.broadcast`——壳→所有插件 WebView 广播

**当前使用（4 处）：**

| 文件 | 行号 | 事件 | 用途 |
|:--|:--|:--|:--|
| [App.tsx](../../../src/App.tsx#L175) | L175 | `lang:changed` | 壳切语言→所有插件同步 |
| [loader.ts](../../../src/pluginLoader/loader.ts#L1019) | L1019 | `lang:changed` | 插件加载时推送初始语言资源 |
| [ThemeEngine.ts](../../../src/core/services/ThemeEngine.ts#L111) | L111 | `theme:changed` | 壳切主题→所有插件同步 |
| [ThemeEngine.ts](../../../src/core/services/ThemeEngine.ts#L149) | L149 | `accent:changed` | 强调色变更→所有插件同步 |

**实现：**
```
壳代码: bridge.broadcast("theme:changed", payload)
    → ipcRenderer.send('bridge:broadcast', { channel, payload })    [preload-shell.ts:324]
      → 主进程 IpcBridge.broadcast()                                 [ipc-bridge.ts:281]
        → 遍历所有 plugin WebView → view.webContents.send('plugin:push', ...)
```

**Pool 模型判决：✅ 零改动。** `broadcast()` 遍历的是 `pluginViews` Map（per-tab），Pool 模型下改为遍历 `poolViews` Map（sidebar + main）。广播语义不变。

### 6.3 `tabs.*` IPC——插件→壳标签页操作

**实现：** [preload-plugin.ts:443-457](../../../electron/preload-plugin.ts#L443-L457)

**Pool 模型判决：✅ 零改动。** `tabs:*` IPC 通过主进程中转，源 WebView（SidebarPool/MainPool）和目标（壳）完全解耦。

**验证：** 0 个插件使用 `useTabActions()`（壳内 ShellEvents）→ 所有标签页操作已走 `linkdesk.tabs.*` IPC ✅

### 10.2 断裂分析

所有 11 处调用都是**模块级 Emitter 单例**——存在于壳 WebView 的内存中。当 file-tree/marketplace 迁移到 SidebarPool、editor 迁移到 MainPool 后，这些 Emitter 在各自的 WebView 中是**独立实例**——不与壳的 Emitter 互通。

**为什么现在能工作：** 这些插件组件目前渲染在壳 WebView 中（侧栏渲染 / React fallback），`import` 语句导入的是壳 WebView 中的模块单例。

**为什么 Pool 模型下断裂：** 每个 WebView 有独立的 JavaScript 上下文——`import` 导入的是**当前 WebView 中的模块实例**。SidebarPool 中的 `CoreEvents` 和壳中的 `CoreEvents` 是两个不同的对象。

### 10.3 修复方案

**原则：** 不改插件行为，只改通信通道。所有 Emitter 订阅 → `window.linkdesk.events.on()` IPC。

| 当前 | 修复后 | IPC 事件名 |

| `shellEvents.emit("file:renamed", ...)` | `window.linkdesk.events.emit("file:renamed", ...)` | `file:renamed` |
| `shellEvents.emit("file:deleted", ...)` | `window.linkdesk.events.emit("file:deleted", ...)` | `file:deleted` |
| `shellEvents.emit/on("editor:revealRequested", ...)` | `window.linkdesk.events.emit/on("editor:revealRequested", ...)` | `editor:revealRequested` |
| `CoreEvents.onDidChangeActiveTab.event(...)` | `window.linkdesk.events.on("activeTab:changed", ...)` | `activeTab:changed` 🆕 |
| `CoreEvents.onDidChangeFileSystem.event(...)` | `window.linkdesk.events.on("filesystem:changed", ...)` | `filesystem:changed` 🆕 |
| `onDidChangeFolders(...)` | `window.linkdesk.events.on("workspace:foldersChanged", ...)` | `workspace:foldersChanged` 🆕 |
| `onPluginLifecycleChange.event(...)` | `window.linkdesk.events.on("plugin:lifecycle", ...)` | `plugin:lifecycle` 🆕 |
| `ViewContainerService.onDidChangeViews.event(...)` | `window.linkdesk.events.on("views:changed", ...)` | `views:changed` 🆕 |

**额外发现：** `onPluginLifecycleChange` 位于 `@src/pluginLoader/lifecycle`（非 `@src/core`），之前的 `from '@src/core` grep 遗漏了这条路径。

**为什么断裂：** `ViewContainerService` 是壳内单例——`registerView()` 向壳的视图注册表写入。Pool 模型下插件在 SidebarPool 中调用 → 写入的是 SidebarPool 中的独立实例 → 壳看不到注册 → 视图不渲染。

**修复方案：** `ViewContainerService.registerView` / `.getView` 在 Pool 模型中不再直接可用——插件不应自行注册视图。替代方案：
- **方案 A（推荐）：** 插件改走 `window.linkdesk.events.emit("view:register", { pluginId, containerId, options })` → IPC → 壳的 ViewContainerService 代理执行
- **方案 B：** `plugin.json` 声明 `contributes.views` → 壳启动时统一注册，插件不再运行时调用 registerView

### 10.6 🔴 B 类——单例方法调用（可变状态隔离断裂）——第六轮穷举

> **核心发现：** 插件不仅有 Emitter 订阅（A 类），还大量调用 `@src/core` 单例的**可变方法**——`registerCommand()`、`openFolder()`、`registerView()` 等。Pool 模型下，SidebarPool/MainPool 各有独立的单例副本——池中的 `registerCommand()` 写入池的 `_commands` Map，壳的 `executeCommand()` 读取壳的 Map → 命令静默丢失。
>
> **审计方法：** 逐行读取 14 个单例源码 + `IpcBridgeHandler.ts`（IPC 桥枢纽）+ `preload-plugin.ts`（linkdesk API 面），交叉验证每个方法是否有 IPC 桥。

| ShellEvents 事件总数 | 22 | 定义在 [ShellEvents.ts](../../../src/core/react/ShellEvents.ts) |
| 壳内不改的事件 | 16 | emit + on 都在壳 WebView |
| tab:* 事件（emit 方可能在池中） | 7 | 已验证：0 个插件使用 `useTabActions()` ✅ |
| 可退役的事件 | 1 | `dialog:visibility` → 替换为 `pool.setVisible()` |
| CUSTOM_EVENTS（window.dispatchEvent） | 10 | 全部在壳 WebView 内——零改动 ✅ |
| bridge.broadcast 调用点 | 4 | lang/theme/accent——全部在壳内 emit，零改动 ✅ |
| events.emit/on IPC 通道 | 1 套 | 跨 WebView 事件系统——Pool 模型通信骨干，零改动 ✅ |
| tabs.* IPC 通道 | 1 套 | 跨 WebView 标签页操作——零改动 ✅ |

| p2p:send 定向推流 | 1 | 需 pool-aware 路由（§8.7） |

### 关键结论

1. **ShellEventBus 不需要改。** 它是壳 WebView 内的基础设施，Pool 模型不改变壳内组件之间的通信模式。

2. **IPC 事件系统（events.emit/on + bridge.broadcast + tabs.*）零改动。** 这是 Pool 模型的通信骨干——`plugin:push` 广播通道覆盖所有 WebView。

3. **IpcBridge 代理通道（17 个）全部零改动。** 代理模式天然 WebView-agnostic——无论请求来自 SidebarPool 还是 MainPool，`ipcMain.handle()` 自动按 `event.sender` 路由。

4. **`pool:layout` 是唯一新增通道。** 这是一个单向 JSON push——壳发送，池被动渲染。

5. **主进程数据推流需要改遍历方式。** `serial:data/stats/system` + `filesystem:changed:*` + `broadcast()` 当前遍历 `getAllInstanceIds()`，Pool 模型改为推送到固定的 `sidebarPoolView` + `mainPoolView`。**改的是迭代对象，不是通道名或语义。**

6. **IpcBridge 队列 key 从 instanceId 改为 poolId。** `pushQueues` + `pluginRequestQueues` + `flushing` 的 key 从动态 `instanceId`（N 个）变为固定 `poolId`（2 个："sidebar"、"main"）。

7. **🔴 7 个插件文件 24 处调用直接依赖 Core Emitter 单例（A 类）——必须在 Phase 3-4 修复。** shellEvents emit/on（3 文件 4 处）+ CoreEvents.event/fire（1 文件 3 处）+ onDidChangeFolders（2 文件 3 处）+ onDidChangeActiveWorkspace（1 文件 1 处）🆕 + onPluginLifecycleChange/onDidChangeViews（1 文件 2 处）+ ViewContainerService.registerView/getView（3 文件 4 处）。修复：Emitter 订阅→`window.linkdesk.events.on()` + 壳侧 `bridge.broadcast()`；ViewContainerService→`window.linkdesk.events.emit("view:register")` IPC 代理。

8. **LayoutEngine 留在壳内。** 它是布局的唯一权威——OverlayWindow 通过 IPC 向壳发送 resize 命令，壳更新 layoutEngine → push 新 bounds 到各 Pool。

9. **CUSTOM_EVENTS 全部在壳内——零改动。** 10 个 `window.dispatchEvent` 事件全部 emit + on 在壳 WebView。

10. **TabActions 通信在 Pool 模型下安全。** 已验证：0 个插件使用 `useTabActions()`——所有插件标签页操作已走 `window.linkdesk.tabs.*` IPC。

11. **🔴🔴 B 类单例方法调用——14 个单例 ~43 处调用，8 个 HIGH/MEDIUM 风险（第六轮穷举发现）。** 这不是通信链路问题——是**状态隔离问题**。池中的 `registerCommand()` 写入池的 `_commands` Map，壳的 `executeCommand()` 在壳的 Map 中查找→命令不可见。同样模式适用于 clipboardProviders、FileDecorationRegistry、FileAssociationService、WorkspaceService、ContextKeyService、LangDefRegistry、KeybindingRegistry。**修复分三路：**(a) 已有 IPC 桥的→改用 `window.linkdesk.*` 调用（LangDef、Keybinding、ContextKey GET）；(b) 无 IPC 桥→新增 IPC handler + preload 暴露（clipboardProviders、FileDecoration、FileAssociation）；(c) 协议层不可序列化（CommandRegistry.registerCommand）→在池中注册，壳通过 `plugins:call` IPC 代理执行。
