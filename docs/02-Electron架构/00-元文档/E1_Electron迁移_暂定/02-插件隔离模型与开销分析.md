# 第一部分：为什么——原则论证

## 一、两种模型——用朴素的比喻

### 模型 A：独立别墅（独立 WebContentsView per 插件）

```
插件 A (终端)  → 自己的 Chromium 渲染进程  → 🔥 崩了 → 只崩自己
插件 B (地图)  → 自己的 Chromium 渲染进程  → 🔥 不受影响
插件 C (文档)  → 自己的 Chromium 渲染进程  → 🔥 不受影响
```

**隔离强度：进程级。** 每个插件是操作系统级别的独立进程。A 和 B 之间没有共享内存、没有共享 JS 上下文、没有共享事件循环。

### 模型 B：同一间宿舍（共享 Extension Host）

```
Extension Host (一个 Node.js 进程)
  ├── 插件 A 的 activate()  → 🔥 崩了 ↓
  ├── 插件 B 的 activate()  → 🔥 也被迫重启
  └── 插件 C 的 activate()  → 🔥 也被迫重启
```

**隔离强度：try/catch 级。** 所有插件在同一个 Node.js 进程里。进程崩了 → 全崩。进程卡了 → 全卡。同进程内插件 A 能读到插件 B 的堆内存。

---

## 二、VS Code 为什么选模型 B——历史原因，不是安全原因

### 2.1 官方文档怎么说的

VS Code 官方文档给出了 Extension Host 的三个设计动机：

1. **防止扩展影响主编辑器启动速度和稳定性**——不是防止扩展之间互相影响
2. **防止扩展直接碰 DOM**——强制走 API，避免 VS Code UI 升级时扩展挂掉
3. **用户始终可控**——不管扩展在干什么，用户都能正常打字、保存

**注意：官方说的是"保护 VS Code 不被扩展搞崩"——不是说"保护扩展之间互相隔离"。**

### 2.2 为什么不每个扩展一个进程——2015 年的硬件

- VS Code 1.0 发布于 2015 年
- 2015 年主流笔记本电脑内存 = 4-8GB
- 每个 Node.js 进程 ~50MB → 几百个扩展各开一个进程 = 10-20GB 内存
- **在 2015 年的硬件上根本跑不动**

这不是安全决策——是资源决策。

### 2.3 共享进程的安全代价——有研究记录

第三方安全研究原文：

> "This shared-process model **protects VS Code from extensions, but provides little protection between extensions or for the user** — a malicious extension in the shared host can potentially access data from other extensions."

翻译：**共享 ExtHost 保护了 VS Code 不受扩展影响，但扩展之间几乎没有保护——恶意扩展能读到其他扩展的数据。**

### 2.4 VS Code 自己在做什么——进程集群

VS Code 1.31 引入了 `extensions.experimental.affinity`——允许扩展分布到多个 ExtHost 进程。开发模式每个扩展独立进程。

**他们在往"更多进程隔离"的方向走——但几十万扩展的兼容性让他们不能直接切。** 这是一个历史包袱，不是一个最佳实践。

### 2.5 结论

| 事实 | 含义 |
|------|------|
| VS Code 选共享 ExtHost | 2015 年内存不够——不是因为它更安全 |
| 共享进程 = 扩展间无隔离 | 安全研究确认的缺陷 |
| VS Code 在往多进程方向改 | 但历史包袱太重，只能渐进 |
| **LinkDesk 2026 年起步** | **没有历史包袱——不需要继承 2015 年的妥协** |

## 三、第三种模型——网页 AI 和我的方案各在主张什么

### 网页 AI 的方案

- **逻辑层：** 共享 ExtHost——所有插件的 `activate()` 在一个 Node.js 进程里
- **UI 层：** WebviewView——每个插件的 UI 是独立沙箱 HTML
- **代价：** 插件逻辑崩了 → ExtHost 重启 → 所有插件重载

### 我的方案

- **逻辑 + UI 在一起：** 每个插件在自己的 WebContentsView 里跑 React 组件——逻辑和渲染不分离
- **隔离：** Chromium 进程级隔离——A 崩了不影响 B
- **代价：** 内存消耗更高（每个插件独立 Chromium 进程）
- **对标：** VS Code 的 WebviewView 本身就是独立进程——我们只是把"逻辑"和"UI"放在同一个进程里，而不是拆成 ExtHost + WebviewView 两块

### 为什么我的方案隔离更强

| 攻击场景 | 共享 ExtHost | 独立 WebContentsView |
|------|:--:|:--:|
| 插件 A 死循环 | ExtHost 卡死 → 所有插件全停 | 只卡自己的 WebContentsView |
| 插件 A 内存泄漏 | ExtHost heap 泄漏 → 所有插件受影响 | 泄漏在自己进程 → 关标签页 OS 回收 |
| 插件 A 未捕获异常 | ExtHost 重启 → 所有插件重载 | ErrorBoundary 兜底 → 只影响自己 |
| 插件 A 读插件 B 数据 | **能读到**（同进程 heap） | **读不到**（独立进程，独立 heap） |
| 插件 A 调 `require('child_process')` | 能——如果没有 API 限制 | 不能——preload 不暴露 |

## 四、对 LinkDesk 的未来意味着什么

### 场景推演

**2028 年。** LinkDesk 插件市场有 200 个插件。

**如果是共享 ExtHost（模型 B）：** 用户装了 50 个插件。插件 #37——一个社区写的 Modbus RTU 协议插件——有个内存泄漏 bug。它慢慢吃掉 ExtHost 的 heap。30 分钟后 ExtHost OOM 崩溃。**50 个插件全部重载。** 用户不知道是哪个插件导致的。他只知道 "LinkDesk 崩了"。

**如果是独立 WebContentsView（模型 A）：** 同样的插件 #37 泄漏。它只在自己进程里泄漏。30 分钟后它的 WebContentsView 被 OS OOM killer 杀掉。**其他 49 个插件正常工作。**

**这就是进程级隔离 vs try/catch 级隔离的差别。不是理论——是用户感知。**

### 内存代价可以接受——而且 ExtHost 方案在进程级隔离下反而更贵

每个 WebContentsView ~60MB。装 10 个插件 ~600MB 额外内存。

**注意：** 初版分析简单对比了"共享 ExtHost（低内存）vs 独立 WebContentsView（中内存）"。经过逐进程拓扑对比（见本文第二部分）：
- **进程级 WebviewView 的 ExtHost 方案 = ExtHost 进程（50MB）+ N×WebviewView 进程（70MB 每个）= 比独立 WebContentsView 更贵**
- **iframe 级 WebviewView 的 ExtHost 方案 = ExtHost 进程（50MB）+ N×iframe（10MB 每个）= 确实更省，但牺牲插件 UI 隔离**

2026 年主流笔记本 = 16GB 起步。2030 年可能 32GB 起步。

**独立进程的内存代价随着时间递减——硬件越来越便宜。共享进程的安全风险随着插件数量递增——生态越大隐患越大。**

---

## 五、结论

| 维度 | 共享 ExtHost | 独立 WebContentsView | 胜出 |
|------|:--:|:--:|:--:|
| 隔离强度 | try/catch 级 | OS 进程级 | **独立** |
| 插件崩影响面 | 全部插件 | 只崩自己 | **独立** |
| 恶意插件防护 | 弱——同进程可读 heap | 强——独立进程 | **独立** |
| 内存占用 | 进程级 WebviewView = 更贵。iframe 级省内存但牺牲隔离（详见第二部分） | 每个 view 插件独立进程，未打开不创建 | **独立**\* |
| 历史包袱 | VS Code 2015 年的妥协 | 2026 年起跑——无包袱 | **独立** |
| 未来趋势 | VS Code 在往这边改 | 天然支持 | **独立** |

\* **关于内存的澄清：** 初版分析简单标了"ExtHost 低，独立中"——经过逐进程拓扑对比（见本文第二部分），发现**进程级 WebviewView 的 ExtHost 方案在所有场景下内存都更差**（多一个 ExtHost 进程）。iframe 级 WebviewView 确实更省，但牺牲了插件 UI 隔离——对 LinkDesk 的第三方插件生态不可接受。

**独立 WebContentsView 是 2026 年从零起步的正确选择。** VS Code 选共享 ExtHost 不是因为"最安全"——是因为 2015 年做不到。LinkDesk 在 2026 年起跑，没有义务继承 2015 年的妥协。

# 第二部分：多少——冷冰冰的数字

> 不讨论哲学、不讨论原则——只算账。

## 六、两种模型的进程拓扑

### 模型 A：独立 WebContentsView（本方案）

```
┌─ Main Process (Node.js, ~30MB) ──────────────────────────┐
│  SerialService  FileService  ConfigService                │
│  WindowManager  IpcRouter                                 │
└───────────────────────────────────────────────────────────┘
        │                │                │
        ▼                ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ 壳 BrowserWindow │ │ 终端 WebContentsView │ │ 设置 WebContentsView │
│ ~150MB          │ │ ~70MB               │ │ ~70MB               │
│                 │ │                      │ │                      │
│ 图标栏+侧栏+    │ │ React 组件           │ │ React 组件           │
│ 标签栏+分屏     │ │ 逻辑+UI 在一起        │ │ 逻辑+UI 在一起        │
│                 │ │ 一个调用栈            │ │ 一个调用栈            │
│                 │ │                      │ │                      │
│ 非 view 插件加载  │ │ 崩了 → 只崩自己      │ │ 崩了 → 只崩自己      │
│ (protocol/theme/ │ └──────────────┘ └──────────────┘
│  language/resource)
└──────────────┘

标签页关闭 → WebContentsView.destroy() → Chromium 进程 kill → 内存回收
未打开的 view 插件 → 不创建进程 → 0 内存开销
```

### 模型 B：共享 ExtHost + WebviewViews（VS Code 方案）

```
ExtHost 始终在运行——所有已安装插件的 activate() 都加载在里面
WebviewView 在标签页关闭时可以销毁——但 ExtHost 不能
```

**每个 view 插件 = 两个部分。** 逻辑在共享 ExtHost（一个 Node.js 进程），UI 在 WebviewView（独立进程或壳内 iframe）。

---

## 七、核心差异——一个参数决定一切

WebviewView 有两种隔离模式，这个选择直接决定方案 B 的内存表现：

| 模式 | 隔离强度 | 每个 WebviewView 内存 | 插件间 UI 安全 | Web 能力限制 |
|---|---|---|---|---|
| **进程级**（独立 Chromium 渲染进程） | 强——独立进程 | **~70MB** | ✅ 互相隔离 | 无限制 |
| **iframe 级**（壳进程内 `<iframe>`） | 弱——同进程 DOM | **~5-10MB** | ❌ 同进程，跨 iframe 访问可能 | 跨域限制、部分 API 受限 |

**重要：如果你选 iframe 级来省内存，等于放弃了"插件 UI 之间互相隔离"——因为它们在同一个 Chromium 进程中，共享同一个 JS 堆。**

---

## 八、内存算账——逐场景

### 8.1 你的 4 个插件（全有 UI）

| 场景 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 空壳启动 | **150MB** | 200MB | 200MB |
| 只开终端 | **220MB** | 270MB | 210MB |
| 终端 + 设置 | **290MB** | 340MB | 220MB |
| 4 个全开 | **430MB** | 480MB | 240MB |

**进程级 WebviewView 的方案 B 比方案 A 更费内存。** 每个 WebviewView 的 Chromium 进程和 WebContentsView 是一样的东西。方案 B 额外多一个 ExtHost 进程（50MB）。

### 8.2 真实场景：50 个已安装，3 个打开

| 场景 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 已安装 50 个，打开 3 个 view 插件 | 150 + 3×70 = **~360MB** | 230 + 3×70 = **~440MB** | 230 + 3×10 = **~260MB** |
| 其余 47 个插件（非 view） | 加载在壳进程里，不额外创建进程 | 逻辑在 ExtHost 里（含在 80MB 中） | 同左 |

**ExtHost 的 80MB 包含所有 50 个已安装插件的 `activate()` 及其依赖——无论用户是否打开。** 方案 A 里，未打开的插件不创建进程。

### 8.3 两者都有的开销（与模型无关）

| 开销项 | 大小 | 说明 |
|---|---|---|
| Electron 框架自身 | 120MB 安装包 | 一次性 |
| Main Process (Node.js) | ~30MB | 串口/文件/配置服务 |
| 壳 BrowserWindow | ~150MB | 图标栏/侧栏/标签栏/分屏 |
| 每个打开的 view 插件的 Chromium 渲染 | ~70MB | 不管叫 WebContentsView 还是进程级 WebviewView——同一个东西 |

## 九、启动时间

| | 模型 A | 模型 B |
|---|---|---|
| **冷启动过程** | 壳渲染 → 用户看到界面 | 壳渲染 + ExtHost 启动 + **加载所有已安装插件的 activate()** → 用户看到界面 |
| **10 个插件** | ~2-3s（壳渲染时间，与插件数无关） | ~3-5s（需初始化 10 个 activate） |
| **50 个插件** | ~2-3s（**不变**——未打开的插件不加载） | ~5-10s |
| **100 个插件** | ~2-3s（**仍不变**） | ~8-15s |
| **打开终端标签页** | ~1-2s（创建 WebContentsView + 加载 React） | ~0.5-1s（逻辑已在 ExtHost 中运行） |

方案 A 的壳启动时间与安装的插件数量无关。**方案 B 的启动时间随安装插件数量线性增长。** 这是 VS Code 用户熟悉的体验——装了很多扩展后启动变慢。

---

## 十、插件崩溃影响面

| 场景 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| **终端插件 JS 死循环** | 终端 WebContentsView 卡死，其他不受影响。关闭标签页 → 进程 kill → 恢复 | WebviewView 卡死，ExtHost 不受影响 | iframe 卡死，**壳进程也被卡死，整个软件无响应** |
| **终端插件内存泄漏** | 泄漏在终端进程，关闭标签页 → OS 回收 | 泄漏在 WebviewView 进程，关闭 → OS 回收 | 泄漏在壳进程，**无法单独回收** |
| **恶意插件读其他插件数据** | **读不到**——独立进程，独立 heap | **读不到**——独立渲染进程 | **能读到**——同进程 heap |
| **ExtHost 崩溃** | 无 ExtHost | **所有插件的逻辑层重启** | 同左 |

**iframe 级方案 B 的致命问题：** 一个坏插件拖垮整个软件。用户不知道是哪个插件导致的——只知道 "LinkDesk 崩了"。

---

## 十一、为什么进程级 WebviewView 的方案 B 没有意义

进程级 WebviewView = 独立 Chromium 渲染进程 = 跟 WebContentsView 是同一个东西。

```
模型 A:   WebContentsView   = Chromium 渲染进程 (逻辑+UI 在一起)   = ~70MB
模型 B:   ExtHost 进程       = Node.js (纯逻辑)                    = ~50MB
         + WebviewView       = Chromium 渲染进程 (纯 UI)            = ~70MB
                              ─────────────────────
                              总共 ~120MB + 两个调用栈
```

**方案 B 进程级 = 用两个进程做方案 A 一个进程做的事——贵一倍，多一个调用栈，多一层 postMessage。** 唯一的"优势"是逻辑和 UI 分离——但对 UI 插件来说这不是优势，是负担。

## 十二、场景推演——50 个插件 vs 200 个插件

### 12.1 50 个插件——中等规模

假设：30 个 view 插件 + 10 个 protocol + 5 个 theme + 5 个 language。用户日常打开 3 个标签页。

| | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 冷启动 | ~2-3s，150MB | ~5-8s，230MB | ~5-8s，230MB |
| 日常使用 | 150 + 3×70 = **360MB** | 230 + 3×70 = **440MB** | 230 + 3×10 = **260MB** |
| 崩溃隔离 | ✅ 每个插件独立 | ✅ UI 独立，逻辑共享 ExtHost | ❌ 所有 UI 共享壳进程 |

### 12.2 200 个插件——生态繁荣

假设：100 个 view 插件 + 60 个 protocol + 20 个 theme + 20 个 language。用户日常打开 5 个标签页。

| | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| 冷启动 | ~2-3s，150MB | **~15-30s**，280MB | **~15-30s**，280MB |
| 日常使用 | 150 + 5×70 = **500MB** | 280 + 5×70 = **630MB** | 280 + 5×10 = **330MB** |
| ExtHost 稳定性 | 不存在此问题 | **200 个 activate() 共享一个进程——任一个崩 → 全部逻辑重启** | 同左 |

**200 个插件时 ExtHost 冷启动需加载 200 个 `activate()`——这是 VS Code 级别的启动时间。** 方案 A 的启动时间与安装插件数量无关。

## 十三、综合对比

| 维度 | 模型 A | 模型 B (进程级) | 模型 B (iframe 级) |
|---|---|---|---|
| **4 个 UI 插件内存** | 430MB | 480MB ← **更差** | 240MB ← 更好但... |
| **50 安装/3 打开内存** | 360MB | 440MB ← **更差** | 260MB ← 更好但... |
| **200 安装/5 打开内存** | 500MB | 630MB ← **更差** | 330MB ← 更好但... |
| **冷启动（50 插件）** | ~2-3s ✅ | ~5-8s ❌ | ~5-8s ❌ |
| **冷启动（200 插件）** | ~2-3s ✅ | ~15-30s ❌ | ~15-30s ❌ |
| **插件 UI 进程级隔离** | ✅ | ✅ | **❌** |
| **插件逻辑进程级隔离** | ✅ | **❌** try/catch 级 | **❌** try/catch 级 |
| **一个插件崩 → 影响面** | 只崩自己 | UI 崩自己，逻辑崩全部 | **全崩** |
| **调试调用栈** | 1 个 | 2 个 | 1 个（都在壳里） |
| **写插件文件数** | 1 个 | 3+ 个 | 3+ 个 |
| **AI 训练数据密度** | React——极高 | ExtHost API——低 | ExtHost API——低 |

## 十四、最终结论

**进程级 WebviewView 的方案 B 在所有内存场景下都不如方案 A。** 每个 WebviewView 和 WebContentsView 是同一个底层东西（Chromium 渲染进程）——方案 B 在此基础上多一个 ExtHost 进程。

**iframe 级方案 B 在内存上确实更省——但牺牲了三件事：**
1. **插件 UI 隔离**——同进程，iframe 之间的隔离远弱于进程隔离
2. **崩溃容错**——一个坏插件的 iframe 死循环 → 整个壳进程卡死
3. **Web 能力**——iframe sandbox 限制部分 API

**这三点中的任何一点对 LinkDesk 都是致命的。** 尤其是第二点——LinkDesk 的插件来自第三方，你无法假设它们都写得好。

**独立 WebContentsView（方案 A）在几乎所有维度上都是最优解——包括内存（与进程级 WebviewView 对比时反而更省）。**
