## 二、「打开帮助」为什么是大章节而不是一条链接

写作时不许把它当「加个 URL」——它至少要回答下面这些，每一条都可能反过来改 `03-插件制造`：

1. **帮助内容住在哪**——本地打包（随壳发）还是远端站点？远端 = 又要一套发布链路 + 离线降级。
2. **三个读者，三种写法**——插件作者（写插件）/ 使用者（用软件）/ 开发者（改壳）。混成一份会三边都不好用。
3. **和 `03-插件制造` 的关系**——那一套是**面向插件作者的文档**，本身就是「帮助」的一部分。
   到底是「帮助站点引用它」还是「它生成帮助站点」？**这是必须先定的架构问题**。
4. **API/IPC 面**——帮助内容要能跟随版本走（版本 A 的帮助不该出现在版本 B 上），
   就得有取数通道；通道归谁（壳？插件？）又是一次「壳改动边界」判定
   （见 [`通道范式·设备插件独立`](../../02-Electron架构/通道范式·设备插件独立.md)）。
5. **离线与代理**——`external-links.ts` 只管把 http/https 交给系统浏览器；
   「在软件内看帮助」是另一条路（内嵌标签页？），过不过代理、失败了怎么降级都要写。

**开工条件**：先出上述五问的答案（一份独立设计档），**再**动菜单项。

## 三、「隐私政策」为什么不是写一页字

它是**对外承诺**，写下去就要能兑现。开工前必须先答：

1. **收集什么**——现状盘点（更新检查会打 GitHub API、插件市场会拉目录、可能有的遥测/崩溃上报）。
   **没有的必须敢写「没有」**，写了「不收集」又偷偷收集 = 比不写更糟。
2. **本地存了什么、存在哪**——`userData` 下的清单（配置、workspace.json、更新缓存…），
   哪些可被用户一键清除。
3. **第三方边界**——插件能拿到什么（`window.linkdesk.*` 契约面）、拿不到什么，
   以及**插件自己的收集行为由谁负责**（作者的义务要写进 [`03-插件制造/`](../../03-插件制造/)，不只是政策页）。
4. **发布节奏**——政策**改了怎么告知**（版本更新说明里出声？首启弹一次？）。
   ⇒ 这一条又要求「更新说明」这条链路先通（`#57.13`）。

**开工条件**：①②先盘点出事实清单（可证伪，不是措辞），**再**写文本、**再**做页面。
