## 〇、脚手架 git init——现状是个人肉步骤在填

### 实测（2026-09-14 回源）

| 查了什么 | 结果 |
|:--|:--|
| `packages/create-linkdesk-plugin/template/` 里有 `.git` 吗 | **没有**（模板内容 = `.vscode/` `CHANGELOG.md` `README.md` `gitignore` `i18n/` `package.json` `plugin.json` `resources/` `src/` `tsconfig.json`） |
| `index.js` 里有 `git init` 吗 | **没有**——只调了 `git config user.name` 拿作者默认值（[:43](../../../../packages/create-linkdesk-plugin/index.js)） |
| 那作者是怎么建仓的 | **被报错挡住、手敲三条命令**：[publish.ts:226](../../../../packages/plugin-sdk/src/publish.ts) 原文让作者 `git init` → `git remote add origin …` → `git push -u origin main` |

⇒ **这是个真实的、被人肉步骤填着的缺口**——而且它正好卡在「作者第一次尝到甜头」之前（先学一套流程，还没见到任何产出）。

### 你举的 Cargo 例子是对的，而且你机器上就有实物

`E:\my-cool-plugin\` 同时有 `Cargo.toml`、`src/`、`**Cargo.lock`、`.git/`**——那就是 `cargo new` 的产物，**自带 git 仓**。

**`cargo new` 的精确语义（要照抄的是这三条，不是「一律 `git init`」）：**

| # | cargo 行为 | LinkDesk 照抄 |
|:--:|:--|:--|
| 1 | 目标目录**已在某个 git 仓内** ⇒ **不 init**（不造嵌套仓） | ✅ 同 |
| 2 | 不在任何仓内 ⇒ 自动建仓（默认 `--vcs git`） | ✅ 同 |
| 3 | `--vcs none` 关掉 | ✅ 加 `--no-git` 旗标 |

### 落地要点

- **`git init -b main`**（显式指定默认分支名）——避免作者第一次 `push` 撞上 `master` 提示，也和 GitHub 默认一致。
- **建议连带一次初始 commit**：模板已经会生成 `.gitignore`，一次 commit 省掉作者第一次 `git status` 看到满屏 untracked。**（可选：若认为「替作者提交」越界，就只 init 不 commit——但那要写清，别让作者以为漏了。）**
- 🔴 **`--no-git` 逃生口必须有**——别把不想建仓的人卡住（对标 `cargo new --vcs none`）。
- 🔴 **这是 npm 包改动**（`create-linkdesk-plugin` 0.1.2 → 0.1.3）：要走它自己的发版线——bump + [`scripts/check-npm-release.mjs`](../../../../scripts/check-npm-release.mjs) 基线（`npm run release:mark`）。
- 🔴 **`scripts/check-scaffold.mjs` 要同步加断言**：它在**仓外一次性目录**里真跑一遍模板（这意味着那里 `git init` 是安全的），但**必须断言「该建的建了 / 该跳的跳了」**，否则这条规则没有机械兜底。

### 判据（三种情形都要实测，缺一不可）

- [ ] 在**仓外空目录**跑 `npm create linkdesk-plugin foo` ⇒ `foo/.git` 存在，`git -C foo log` 有一次初始 commit，`git -C foo branch --show-current` = `main`
- [ ] 在**某个 git 仓内**跑 ⇒ **不建** `.git`（`git rev-parse --show-toplevel` 仍指外层仓）
- [ ] 带 `--no-git` ⇒ 不建 `.git`（其余产物照常）
- [ ] `check-scaffold.mjs` 断言上述两条相反路径，并挂 `npm run check`

## 一、本地容器目录（D6）

### 你机器上的现状（2026-09-14 实查）

```
E:\linkdesk-build+scratch\
├── first-run-setup/        hello-linkdesk/       ← 两只仓外插件（平铺）
├── linkdesk-marketplace/   marketplace-repo/     ← 目录仓的两个本地副本
├── cdp/  cdp-*.mjs  一堆调试脚本
├── 3.5.3-封面样张/   b2/   memory-backup-20260911/
```

**插件工程、CDP 调试脚本、备份、封面样张混在一起平铺。** 你说的「造一个文件夹」是对的。

### 建议落位

```
E:\linkdesk-plugins\          ← 容器（或沿用 linkdesk-build+scratch 下的子目录，见下）
├── official\                 ← 你的官方插件（settings/ file-tree/ marketplace/ editor/ …）
│   ├── settings\
│   └── …
├── third-party\              ← 别人的（若在本机改）
└── _legacy\                  ← hello-linkdesk / first-run-setup 可选挪入（不挪也行，见 §三）
```

### 两点主张（各带理由）

**① 分类维度用「归属」（官方/第三方），不要用「功能类别」（硬件/主题/工具）。**
归属是稳定的；功能类别会随插件增加不断重划——而且 catalog 里的 `category` **已经在做功能分类**，本地目录再分一遍是重复劳动。

**② 容器名里不该有 "scratch"。**
`E:\linkdesk-build+scratch` 从名字到现状都是「可丢弃的工作区」。而按 D2，**插件仓是插件源码的唯一真相源**——把唯一真相源放进一个名字叫 scratch 的目录，等于给未来的自己（和未来的 AI）留坑：「哪天清理一下 scratch」这个动作看起来完全无害，而它会是唯一一份插件源码的葬身处。
⇒ **建议 `E:\linkdesk-plugins\`**（与 `E:\linkdesk\`、`E:\linkdesk-build\` 同前缀，名字自带「不是临时物」的语义）。**建在 `linkdesk-build+scratch` 里也可以，但目录名里别带 scratch。**

### 🔴 红线：容器自己绝不能建仓

`E:\linkdesk-plugins\` 是**容器，不是一个仓库**。一旦它被 `git init`（**很容易误触发**：IDE 的「初始化仓库」提示、在错层级敲 `git init`、从父目录 `git add .`），后果是双重的：

1. 每只插件的 `.git` 变成**嵌套仓**，父仓把它们记成 gitlink——**静默坏掉且极难看出来**。
2. 更要命：它会**把 §〇 那条「已在某 git 仓内 ⇒ 不 init」的规则反转成灾难**——每只新建的插件都不建自己的仓，全变成容器 repo 的子目录，**正好就是你最不想看到的 monorepo**。

**要做的事：容器里放一张说明**（`README.md` 或 `不要在这里建仓.md`），写清「容器不建仓 + 为什么」。防的不只是你本人，还有以后进场读目录的 AI——**AI 看到一堆工程目录平铺，第一反应很可能是「给它建个仓管理起来」。**

### 为什么这件事零风险

**本地目录位置与插件身份完全无关**：插件仓是自足的（`git clone` 到哪都能构建），壳只认 Release URL 与 catalog，**不认任何本地路径**。⇒ 目录结构随时可重排、可改名、可换盘，**不涉及任何代码依赖**。不需要「设计」，想改就改。

## 二、可选小工具：批量同步

几十个仓之后，「挨个 `git pull`」是真实的体力活。一个几行的 `pull-all.mjs`（遍历容器下各目录 `git pull --ff-only`，打印哪些有更新/哪些有本地改动）就够。**它正好也能喂给 7.2 轮的批次执行。**

> ⚠️ **不许把它做成「一键 commit/push 全部」**——那会绕过 `push-wait-for-user` 红线。

---

## 三、那两只平铺的怎么办

`hello-linkdesk` / `first-run-setup` **建议原地不动**。理由不是懒：它们平铺在不同位置，**恰好是「本地目录与插件身份无关」这条性质的活证据**——将来第三方作者把插件放在自己硬盘任何地方，对你的市场零影响，你的系统里已经有一对现成的样本。

（用户自己也说了「这两个就先平铺着，也没什么关系」——与建议一致。）
