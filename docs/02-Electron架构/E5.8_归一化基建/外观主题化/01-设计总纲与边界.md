# 01-设计总纲与边界

> **状态：** 骨架已拍板（2026-08-23）
> **范围：** Phase 10 #50.6-#50.12 的扩围重述。从「玻璃态八任务」扩为「外观全量变量化 + 主题定制 + 域混搭 + 设置调节」。

## 1. 背景与动机

> 用户原话精髓（2026-08-23）：「主题不仅只是定颜色。整个液态玻璃是否可实现、极简风格是否可实现，都由相应的主题来定，再比如说里面的字体。这些字体、圆角弧度之类写的都是死代码，能不能让他活起来。对标手机 app 里厂家给的主题选项——自定义图标、自定义系统字体、自定义背景颜色、自定义背景图片，都通过主题这个东西来配置。液态玻璃正好可以以最终主题的形式实现。」

**一句话定义：** 主题从「换颜色」升级为「换整套外观配方」——颜色、字体、圆角、玻璃开不开、极简不极简、背景图，全由主题决定。液态玻璃 = 其中一个配方；design skill 里的美学（极简/高端/玻璃）未来各做一个配方主题。

**对标对象：** 手机厂家主题（换图标 / 换系统字体 / 换背景色 / 换背景图）。LinkDesk 的「主题」就是这个角色。

**启发来源（2026-08-23 讨论）：** 用户参照手机主题 app 的「混搭」功能，提出多主题按部件组合、字体独立成插件的设想 → 见 [03-域贡献者与混搭](03-域贡献者与混搭.md)。

## 2. 主题管什么 / 不管什么——边界上限

> 用户拍板：「整个页面都可以由主题插件定制，当然也是有上限的，比如不可能把侧栏变成横向的。」

| 主题管（改值） | 主题不管（改结构） |
|:--|:--|
| 颜色、字体、圆角、玻璃、阴影、背景图/遮罩、透明度 | 侧栏横竖、图标栏位置、zone 存在与否、分隔线布局、z-index 堆叠 |
| 每个表面长什么样（per-surface 覆盖） | 表面怎么排列、谁在左边谁在右边 |

- **一句话：主题 = 换皮肤（token 覆盖），布局 = 换骨架（布局引擎 + grid + 视图注册表）。两者正交。**
- 侧栏横变竖要改 layoutEngine + grid 结构，是布局树的事（见 [[e5.8-layout-tree-grid]]），主题碰不到。
- **边界由 schema 锁死**：theme schema 只开放「外观 token 段」，根本不提供布局字段——主题作者想改布局也无从下手。边界由类型系统兜底，不是约定。

**边界是卖点，不是缺陷**：主题作者能放心大胆定制任何视觉，因为碰不到结构、不会做坏布局。对第三方作者友好（呼应 E6 验收 = 10 分钟第一个插件）。

## 3. 继承链——壳只认「一组生效 token」

```
:root 全局默认（壳，最保守现状）
  ↓ 主题/插件（域贡献者）——缺的域自动落回默认
  ↓ 设置层 scale（用户全局粗调，含拉到 0 = 关）
生效 token 集 → 渲染
```

**壳不知道混搭了几个来源、每个来源贡献哪个域。** 这是核心无知原则在外观层的延伸。

**极简 vs 玻璃不需要新机制**——同一套变量集的不同取值（`--glass-blur: 0` + 实心表面 + 小圆角 + serif 标题 = 极简；`--glass-blur: 20px` + 透明面 + 大圆角 + 背景图 = 玻璃）。这就是「变量集 = 外观契约」通用性的证据。

## 5. 已拍板决策（2026-08-23 全量确认）

1. **字体来源：壳零内置字体。** 系统字体栈兜底（现在的样子）+ 主题插件自带字体文件（走 getAssetPath，硬约束 12 已支持）——连字体都是「主题 = 插件」。
2. **图标主题先不做，单独立案。** 图标来源是插件 `contributes.iconPath`，换图标 = 图标 remap 机制，是另一块大工程，不混进本次。
3. **摸底先行。** 见 [02-变量契约](02-变量契约.md) §2。
4. **主题 = 外观 token 覆盖层。** 边界原则（本档 §2）。
5. **覆盖粒度 = 全局系数 scale。** 主题层 per-surface 绝对值 + 设置层全局缩放系数（`--radius-scale`/`--glass-scale`）。主题作者管精致，用户管粗调。（精化：[08 §3](08-持久化与配置.md)——圆角走 scale，玻璃因无档位可缩放改走绝对覆盖。）
6. **圆角 = 语义档位 + 偏门值归并。** `--radius-xs`…`--radius-2xl` 八档，偏门值归并到就近档，接受 ±1-2px 视觉差。
7. **字体纯主题层，不进设置层。** 字体是「质」的更换（跟配方走），设置层 slider 只管「量」（圆角/玻璃强度/背景透明度）。留口子：`app.fontFamily` 配置字段可后补注册。
8. **外观全局共享 + 按窗继承。** 主题 + 设置覆盖全局（ThemeEngine 广播机制已支持）；拖出窗继承主窗外观（#50.5 ⑤ 的「继承 = 保持一致」）；要补的是 #46.11 那类 reload 后重新 seed 的竞态，不是 per-window 独立主题。
9. **主题 = 域贡献者。** 主题文件贡献你有的域，缺的继承全局默认。这一个模型统一目录格式/部分覆盖/混搭/字体独立插件。
10. **风格 vs 配色分离。** 契约分「风格 token」（radius/glass/shadow）和「颜色 token」，「换色不动风格」独立操作。
11. **玻璃连续 scale 不是二元开关。** 主题定默认强度，设置层覆盖到 0 = 关。
12. **配色变体严格只颜色**（决策 B）：`colorways[].colors` 只管颜色 token；想换风格 = 混搭按域换来源，不给 colorway 开风格口子（[05 §6](05-主题数据模型.md)）。
13. **主题组 = 独立配置贡献**（决策 D）：壳注册 pluginId `appearance`（标题「主题」），主题 key 从「通用」组迁走（[08 §5](08-持久化与配置.md)）。
14. **新格式 only，零向后兼容读**（决策 F）：引擎只读 `colorways[]` 格式；现有主题插件（theme-defaults/mint-soda/twilight-forest）迁移改造，不保留旧格式兼容（[05 §5](05-主题数据模型.md)）。
15. **ai化 = AI 友好度**（2026-08-23 澄清）：主题创作的 AI 友好三层（GUI / 结构化文件 / 归一化）——schema 自文档化、文档读者含 AI、示例可仿造、新主题一种写法（[07 §0](07-代码规划.md)）。
