## 二、设计决策（每条都带理由，别当成风格）

1. **`findController` 原语 vs 自绘 —— 当场评估的结论：文本层借原语，搜索与高亮自绘。**
   pdf.js 的 `PDFFindController` / `TextLayerBuilder` 住在 **320 KB 的 `web/pdf_viewer.mjs`**，且与 stock `PDFViewer`/`PDFPageView` 的页模型强耦合（`linkService.page` 驱动滚动、EventBus 广播 `updatetextlayermatches`、builder 自持 container/viewport/scale 生命周期）。本仓阅读区是**自绘的虚拟化列表**，套 stock 页模型要么重写阅读区、要么写一层适配——回归风险大于收益，而 T3 判据明写「缩放锚点与虚拟化不许被破坏」。而 `TextLayer` 本身是 `pdfjs-dist` 主入口已导出的**同一个渲染原语**（stock viewer 建文本层也是拿它），定位/字体度量/`--scale-x` 这些难活它全包。⇒ 文本层借原语，命中定位与高亮照 pdf.js 原语同一套算法自绘（`TextHighlighter._convertMatches` 的同一件事，换成显式偏移表）。
2. **搜索条是绝对浮层，⛔ 不进布局行。** 若把浮条排进布局（如工具栏下方一行），开条就挤矮阅读区 → `ResizeObserver` → 适宽/适页重算 → **倍率当场跳**。所以新增 `.pdf-reader-body` 相对定位壳，浮条 `position: absolute` 浮在阅读区之上。实机读数：开条前后 `--scale-factor` 完全相同。
3. **高亮是「拆 span 内文」而不是「上面盖方块」。** 文本层是叠在 canvas 上的透明文字，命中底必须画在文字身后；另起绝对定位方块去盖，滚动/缩放都要自己重算坐标（每方块一次 `getBoundingClientRect` × 滚动帧），还会挡住文字本身的划选。拆 span 这套是 pdf.js `TextHighlighter._renderMatches` 的做法：命中子串包一个 `<span>`，父 span 的 `textContent` 一字不变 ⇒ 划选/复制、pdf.js 自己的 `--scale-x` 度量（它读 `div.textContent`）都不受影响。
4. **整页文本的取数口径：逐项 `str` 拼接，`hasEOL` 时补一个 `"\n"`。** 不学 pdf.js 只拼 `""`——行尾不留边界，上一行末词与下一行首词会粘成一个词（「…end」＋「Start…」=「…endStart…」），搜索里就是假命中。代价是**偏移不再等于项长累加**，所以 `starts[]` 必须显式记账，命中下标 → (项, 项内偏移) 只认它。搜索扫全文档与文本层渲染**共用同一份取数**（`TEXT_CONTENT_OPTIONS` ＋ `buildPageText`）——两处各算一份 = 命中框迟早偏。
5. **命中匹配用正则 `i` 旗标，⛔ 不用「小写化后 indexOf」。** 小写化会改长度（`İ` 小写是两个码元），下标当场失真；正则在原串坐标系里给下标，映射进文本层零换算。查询串先转义正则元字符（用户随手敲的 `(`/`[`/`*` 不许当语法）。
6. **pdf.js 文本层 CSS 契约是接口不是装饰。** 逐条对齐（`.textLayer` 的 `position/inset/overflow/line-height/transform-origin/z-index`、`span` 的 `color: transparent`/`white-space: pre`/`user-select: text`、`--total-scale-factor`/`--font-height`/`--scale-x`/`--min-font-size` 那几支自定义属性）。🔴 一条容易踩的：**自定义属性里的 `var()` 在「声明它的那个元素」上求值**——pdf.js 把 `--total-scale-factor` 声明在 `.page` 上，本仓没有 pdf.js 的 `.page`，所以这组变量必须落在**文本层宿主自己**身上，否则 `--font-height` 的字号链静默坍缩（字全变 1px 大）。
7. **`user-select: text` 是硬需求。** 壳全局 `html, body, #root, #pool-root { user-select: none }`——不显式打开，文本层整层选不中（用户观感 = 「复制功能没做」）。
8. **换档只改一个自定义属性和一次度量，⛔ 不重建 span。** `setScale(viewport)` 只更新 `--scale-factor`（＋ `--user-unit`）再交给 pdf.js `update()`；重建会丢掉已画上的高亮，也会在 Ctrl+滚轮连档时把上千个 span 反复拆装。
9. **高亮先复原再画**（`clearHighlights` → `applyHighlights`）：改查询时新命中不一定覆盖旧命中碰过的每一项，不先复原会留下上一轮残影。复原靠 `itemsStr`（pdf.js 给的原样字符串）而不是 DOM 快照——同一份既可重建原文，也让「清了再标」幂等。
10. **搜索态命名避坑**：`SearchState.currentMatch` **故意不叫 `current`**——JSX 里写 `s.search.current` 会被本仓 eslint 规则 `linkdesk/no-ref-current-in-jsx` 判成「ref.current 参与渲染」（那条规则只认属性名，分不出 store 状态与 ref）。⛔ 别改回去。
11. **落点当前页起算、且环形回绕**：扫完从 `currentPage` 往后找第一条命中（读到这里的人多半在找眼前这段），当前页往后没有就回文档头一条；`searchStep` 同款环形（末尾的下一条是第一处，pdf.js 查找同款）。
12. **长文档扫描不 abort、只作废**：`searchSeq` 递增，旧扫描在循环里自行收手；⛔ 不 abort pdf.js 取数（页文本在 pdf.js 侧有缓存，重扫几乎零成本，abort 会把正在读的页一起连坐）。单页文本取不出来（畸形页）跳过不判死整场。
13. **命中上限 5000/页**：病态文档（一页几千个同一串）不该把高亮 span 铺满 DOM；超出即截断，读数如实报。

## 四、实机逮到的东西（三条，第一条未复现但必须留档）

1. 🔴 **一次「canvas 不跟随换档、文本层与页卡却跟随」的未复现观察**。在某个 `preview.pdf` 视图上：`zoomTo 1.0` 时 canvas/文本层/页卡三者一致（538×360），随后 `zoomTo 2.5` 与 `fitWidth` **两次换档 canvas 都停在 538**，而文本层与页卡正确跟到 1346 / 937，`phase` 仍是 `ready`、无错误态、`--scale-factor` 也在变。**判断依据（为什么不算本格的回归）**：① canvas 渲染链是 T3 的路径，本格一行没改；② 换档时文本层/页卡/状态条**全都跟上了**，只有 canvas 那一条停住；③ 池页 reload 后新开视图，**连续 15 次以上换档（含 1 / 1.5 / 2 / 2.5 / fitWidth / fitPage）canvas 全部逐档对齐**，并按「开条 → 打字 → 划选 + Ctrl+C → Esc → 再换档」原样复刻该视图的前序操作，也没能复现。**怀疑点（留给 T6/T7 或引擎格）**：`readerSurface` 的渲染是「单条 drain 循环 + 请求位」设计，若**某一次 `doc.renderPage()` 的 await 永不 settle**（pdf.js 分帧渲染依赖 rAF，T3 档案已记「后台窗口 rAF 冻结 ⇒ 分帧渲染永远完不成」），则 `drainingRef` 一直为真、之后**所有渲染请求都被吞**，症状正是「canvas 冻在最后一次成功的档位上、别的一切照常」。建议后续格加一条**看门狗**（渲染超过 N ms 未 settle 即 abort 重发），或把 drain 的 await 包一层超时。本格⛔ 不动 T3 的渲染路径（改它要重跑 T3 的整轮实机）。
2. **一条 eslint 误报，用改名消掉（⛔ 不是 disable 注释）**。`linkdesk/no-ref-current-in-jsx` 的实现是 `JSXExpressionContainer > MemberExpression[property.name='current']`——只认属性名，分不出 store 状态与 ref。`SearchState.current` 因此被误判，改名 `currentMatch`（并留了「⛔ 别改回去」的注释）。改名后 eslint 规则腿 **23 文件零偏离**。
3. **`ci-verify` 的「退役名提示」3 处是第三方 API 名字误命中**（ℹ 只提示、不拦）：`src/services/textLayer/render.ts:66` 与 `src/views/readerSurface/index.tsx:369/437` 命中的是 pdf.js 的 `layer.update()` 与注释里的 `update()`——那是 pdf.js 的 API 名，不是宿主退役名，⛔ 不改（改了就是为让扫描器闭嘴而污染注释）。

**诚实边界两条**（都不是本插件的缺陷，但读数里要分清）：
- **`preview.pdf` 部分字形复制出来是乱码**（如 `\u000f\u0006\u0007\u0010`）：该文档的 CJK 子集字体没有 `ToUnicode` 表，任何阅读器都还原不出这些码位。同一份文档里 `西安交通大学第一附属医院` 这类**有** `ToUnicode` 的串逐字正确 ⇒ 文本层本身没坏。
- **浮条底色偏淡是本机主题的现象**：实测 `--bg-card` 在本机被主题覆写成 15% 透明洗色（`color(srgb 0.0862745 … / 0.15098)`），浮条因此偏透明、文字对比度偏低。本插件用的是**壳自家浮动面同款 token**（`src/pool/floating/dialog/DialogHost.css:27`、`QuickPickHost.css:41` 都是 `background: var(--bg-card)`）⇒ 同一主题下壳的弹窗同样偏淡。判定：**⛔ 不改**（插件只消费 00.5 §二 表里的既有 token，⛔ 不自造不透明色值——那才是违反「无新色值」）；要改归主题侧。
