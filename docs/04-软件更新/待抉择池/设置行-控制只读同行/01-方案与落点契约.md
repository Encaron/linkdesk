# 01 · 方案与落点契约

> 先立「归属三层」判断框架（本案与以后一切「该谁做」的判据），再给方案 A 契约。

## 〇、归属三层——判断「这个能力归谁」的框架

| 层 | 归属 | 管什么 | 现状 |
|:--|:--|:--|:--|
| **声明层** | **宿主配置 schema** | 键名/类型/控件意图：`uiHint`、`unit`、`effectiveToken`、`statusCommand`、`actionCommand`… | 已有（E5.8#50/#65/#77/#87/#155 一路建起来的就是它） |
| **渲染层** | **设置插件**（可替换，万物皆插件） | `SettingRow` 行骨架 ＋ `renderControl` 分发；**键名零知识** | 已有，铁律写在代码注释里 |
| **存储层** | 配置存储 | **一键一值** | 本案不动 |

**病史规律**：出事从来不是「配置太多」，是**元素住错了层**——
- 图标栏看不见 = 极性判断住在**静态 CSS 皮肤**层（越权，本该住声明/引擎层）→ 前景可读性案；
- 假想中的「设置仓写死 `surfaceRadius` 分支」= 渲染层越权学声明层的事（实际没发生，铁律挡着）；
- 本案的 `renderHint` 互斥**不是住错层，是声明层表达力不足**——一行放不下「控制＋伴生」，于是各组分家。⇒ 补表达力，**不动归属**。

## 一、方案 A（推荐）：伴生声明正交化

### 1.1 契约（一句话）

`statusCommand` / `actionCommand` 从「`renderHint:"readonly"/"action"` 的附属品」升为**可与任何主控件共存的伴生声明**；`renderHint` 的这两个值退化为「主控件就是只读/按钮」的**简写**。

### 1.2 渲染规则（定稿 · 2026-10-04）

**主部件判定**（优先级自上而下，第一命中即主控件）：

1. `renderHint === "readonly"` ⇒ 主控件 ＝ 只读状态行（**现状最前分支，⛔ 不动**——保证零回归）；
2. 否则 `uiHint` 命中分发表 ⇒ 主控件 ＝ 该控件；
3. 否则 `renderHint === "action"` ⇒ 主控件 ＝ 操作按钮；
4. 否则按 `type` 兜底（现状）。

**伴生件**（与主控件正交，可 0–2 件，顺序固定）：

- `actionCommand` ⇒ **伴生按钮**——文案沿用既有规则 `t(description)`（action 行只有这一个字符串可承载文案，先例 `ai.mcp.openDetails`）；置灰语义照抄 `actionDisabledAll`。
- `statusCommand` ⇒ **伴生只读**——复用只读底座（共享 `ReadOnlyText` 的 `statusCommand` 轮询；共享件缺席回落设置仓本地 `ReadOnlyStatus`。3s / alive 守卫 / 空值不占位 / 抛错保现值逐格照旧，⛔ 不造第二套轮询）。**不带标题**（它是读数不是键）；过长 → 省略号＋title 全文（ReadOnlyText 既有行为）。
- ⛔ 伴生件**不承载编辑能力**——编辑仍一键一值（存储层不动）。

`SettingRow` 控制区 ＝ **`[主控件][伴生按钮][伴生只读][生效徽标]`**（生效徽标仍由 `SettingRow` 在 `renderControl` 之后追加，位置与今天一致）：

| 声明形态 | 主控件判定 | 渲染 | 对应现实需求 |
|:--|:--|:--|:--|
| 只声明 `uiHint` | ② | `[控件]`（现状，零回归） | 绝大多数键 |
| `uiHint` ＋ `statusCommand` | ② | `[开关][状态小字]` | `ai.mcp.enabled` 想要的形态 |
| `renderHint:"action"` ＋ `actionCommand` ＋ `statusCommand` | ③ | `[按钮][只读路径]` | 缓存目录合并形态 |
| `renderHint:"readonly"` ＋ `actionCommand` | ① | `[只读][按钮]`（只读为主、按钮为伴） | 反向同排 |
| `renderHint:"readonly"`（单） | ① | `[只读]`（现状，零回归） | 今天那 5 个状态行 |

- 🔴 **值标签 × 生效徽标互斥显示（E1 拍板 · 定稿机制）**：主控件**自带值标签**（滑杆，即声明了 `unit`）且键声明 `effectiveToken` 时——**跟随主题态**（`useSettingRowBadges` 的 `effectiveBadge !== null`，**现成信号**，不为本案新造判定）向 Slider **不传 `unit`**（Slider 既有语义：`unit === undefined` ⇒ 不渲染值标签）让位给行尾生效徽标；**自定义态**显值标签、不显徽标（徽标本就只在跟随态出现）⇒ **永不同屏**。⛔ 不加区分标识、不做按键声明开关。
  - 实现口径：`renderControl` 增一个**入参** `suppressValueLabel: boolean`（由 `SettingRow` 传 `!!effectiveBadge`）；滑杆分支 `unit={suppressValueLabel ? undefined : (prop.unit ?? "")}`。⛔ 判据是「该键声明了 `effectiveToken`」，对未声明者零影响。
  - 📌 今日**零键命中**（`effectiveToken` 只在 `app.glassTint` / `app.fontFamily` / `app.fontFamilyMono`，均非滑杆）⇒ 规则为将来「滑杆 ＋ 生效 token」的键而备，本轮**零视觉变化**。

### 1.3 校验与优先级（定稿 · 2026-10-04）

- `statusCommand` / `actionCommand` 与**任意**主控件声明**共存合法**；`renderControl` 的「互斥分支」改「主/伴排序」，**不再报错**。反向简写仍成立：只声明 `renderHint:"readonly"`/`"action"` ＝ 主控件就是只读/按钮，**语义零回归**。
- **壳侧无**「statusCommand 只配 readonly」的机械校验代码（1.1 读数②）⇒ 2.1 的壳改动 ＝ **类型注释语义改写 ＋ 作者面 schema description 同步**（`ConfigurationRegistry` 的 `ConfigProperty` 注释 ＋ 四份 `plugin.schema.json`），**不新增运行期校验**。
- 主控件优先级**保持「readonly 最前」**＝现状零回归（今日无键同时声明 `uiHint` 与 `renderHint:"readonly"`）。

## 二、方案 B / C 与不推荐理由

- **B · composite uiHint**（一键声明子控件数组）：表达力强，但**破坏一键一值**——来源徽标/生效徽标/齿轮菜单全以「单键」为粒度，组合键要把整套徽标语义重新定义。⛔ 不推荐。
- **C · 维持两行**：零成本，但「控制＋状态」类需求（已出现 ai.mcp 组、缓存组两处）永远两行，第三方只能靠排版凑。留作 D1 不通过时的兜底。

## 四、验收判据（三例，全是实键实况）

1. 缓存目录一行：`[打开缓存目录] [%APPDATA%\linkdesk\cache]`；
2. ai.mcp 一行：`[开关] [已开启 · 端口 xxxx]`；
3. 第三方假键：任意插件键声明 `statusCommand` 即得伴生（**无特权**——共享 `ReadOnlyText` / 本地 `ReadOnlyStatus` 注释里「任何插件声明即得同款」的承诺兑现）。

另加：现有设置页**每组抽 1 键**回归（零变化）＋ token 快照（[主题案 06 §四](../../已落地/主题系统-前景可读性适配/06-总纲-刀序路线.md) 同款）。

## 五、⛔ 不许

- 设置仓出现**任何键名字面量**（其既有铁律）；
- 动「一键一值」存储模型；
- 壳渲染代码写死任何键名；
- 为伴生件新造第二套轮询/第二套徽标。
