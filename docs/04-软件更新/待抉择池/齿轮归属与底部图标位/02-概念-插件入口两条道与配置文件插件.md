# 02 · 概念 —— 插件入口的两条道 · 以及「配置文件插件」为什么和「设置插件」同族

> **本件是概念件，不是施工图**（施工图是 [01-设计.md](01-设计.md)）。
> 它服务两个目的：
> 1. **把 2026-09-30 与用户谈透的判据落盘**——「这个 UI / 这个入口归壳还是归插件」到底该怎么定；避免下个 AI 又从「它长在哪个位置」去推；
> 2. **当「配置文件（Profiles）」这件未来任务的接口档**——用户希望：将来他要跟做配置文件的 AI 讲需求时，只要说一句「**看看 04 里之前做的那个设置部分的那个文档**」，对方就该全懂，不用他再解释一遍。
>
> ⇒ 🔴 **读本件的姿势**：如果你是被派来做「配置文件插件 / Profiles」的 AI，**先读完本件再写第一行代码**。本件替你回答了「它该长什么样」的大部分前置问题，也标出了哪些是**它自己那件任务要拍板**的，别人替不了。

## §一 两条道：插件想往菜单里放东西，只有两种写法

### 1.1 道 A —— 插件自己声明（`contributes.menus`）

落点：`src/pluginLoader/contributions/contributions.ts:146-152`

```ts
if (c.menus) {
  for (const [menuId, items] of contribEntries(pluginId, "menus", c.menus)) {
    registerMenuItems(menuId, pluginId, contribArray<ManifestMenuItem>(pluginId, `menus.${menuId}`, items));
  }
}
```

插件在 `plugin.json` 里写：
```json
"contributes": {
  "menus": {
    "menuBar":    [ { "command": "myext.doThing", "group": "tools" } ],
    "fileContext": [ { "command": "myext.doThing" } ]
  }
}
```

**今天活着的先例**：`file-tree` 插件（出厂自带）声明了 `menuBar` / `fileContext` 两个槽位——**它往壳的菜单栏里塞了自己的条目，而壳对它的存在一无所知**。

### 1.2 道 B —— 壳替它声明（`APP_PLUGIN_ID`）

落点：`src/core/commands/shell/settingsCommands.ts:503-515`、`developerCommands.ts:71-74`、`coreCommands.ts:60-68`

```ts
registerMenuItems(MENU_SLOTS.ExtensionGear, APP_PLUGIN_ID, [ … 8 条 … ]);
```

`APP_PLUGIN_ID = "app"` 是**壳自己的伪插件 id**——壳用「我也是个插件」的方式注册自己的命令与菜单。齿轮那 8 条就是这么来的。

### 1.3 判据：一句话

> **把那只插件卸了，这个入口还该不该在？**

- **该在** ⇒ **道 B（壳注册）**。说明这个入口背后的能力**不在这只插件里**。
- **不该在** ⇒ **道 A（插件自声明）**。说明这个入口**就是这只插件自己的门**。

齿轮菜单是**教科书式的道 B**：把设置插件卸了，「主题 / 语言 / 快捷键 / 检查更新 / 关于」照样该在——它们的能力全在壳上（主题引擎、LanguageRegistry、KeybindingRegistry、更新服务）。**只有「设置」那一条**在设置插件不在时无处可去（见 §三 3.4）。

### 1.4 两条道的实务差别（是行为差别，不是审美差别）

| | 道 A · 插件自声明 | 道 B · 壳代声明 |
|:--|:--|:--|
| 入口生死 | **随插件**——卸载即消失，装回即回来 | **恒在**——与任何插件无关 |
| 「空点」问题 | **没有**（插件不在 ⇒ 入口不存在） | **有**（入口恒在，指向的插件可能不在 ⇒ 点下去静默无反应）⇒ **必须配 `when` 门控** |
| 壳要不要改代码 | **不要**（`MenuId` 自 E5.7#64 起是**开放 string**——新槽位零壳改动） | **要**（加一条就得动壳） |
| 谁的名字成了契约 | 槽位名 | 槽位名 **+ 命令 id** |
| 幂等键 | `command + pluginId + when`（`MenuRegistry.ts:121-132`） | 同左（壳的 pluginId 是 `"app"`） |

### 1.5 两条道都通，不是「一条正经一条歪门」

`MenuId` 在 `MenuRegistry.ts:21` 被定义成 `export type MenuId = string`——注释写得很明白：**「E5.7#64：闭合 enum → 开放 string——第三方作者可声明新注册点（任意字符串），壳零改动即可消费（插件独立铁律：壳不因新菜单点改代码）」**。

⇒ **槽位是一个「名字契约」**：谁提供菜单项、这个槽位长在界面哪个角落，**都不影响契约本身**。这正是用户最初问的那句「**在什么位置都无所谓，名字对就行**」的准确答案——**对槽位成立**。

⚠️ **但「图标位置」不是契约**——见 §二。

## §二 一条从本件提炼出来的原则：「槽位 = 名字契约；位置 = 几何，不承载身份」

2026-09-30 这一件的全部戏剧性，就出在这条原则被破了：

- `MENU_SLOTS.ExtensionGear`（值 `"extensionGear"`）是个**名字契约**——谁注册、槽位渲染在哪、叫什么，都不影响「往这个槽位注册的条目会出现在齿轮里」。
- 而 `location === "bottom"`（`IconBarZone.tsx:220`）被当成了**身份判据**——「底部 ⇒ 齿轮」。这是**位置耦合**：一个纯几何字段，被赋予了「这是什么」的语义。

**后果**：任何插件只要声明 `location: "bottom"`，就自动变成齿轮（并且自己的标签页打不开）。**位置一改，身份就跟着变——身份不该由位置决定。**

⇒ **落成规矩**（写给后来人）：

> **一个字段只承载一个语义。** 「放在哪」（几何）与「这是什么」（身份）必须是两个字段。
> 当你想用 `location === X` 去判「这是不是某样东西」时——**停**，那说明缺一个身份字段。

本件的修法就是这条规矩的落地：齿轮的身份改由 `IconBarLayout.owned[].id === "gear"` 承载，`location` 退回纯几何。

## §三 「配置文件（Profiles）」为什么和「设置插件」是同族

用户 2026-09-30 讲的那段（原话大意：「我为什么说它和设置这个插件非常像呢？原因很简单，因为它的这些东西肯定都是来自于壳的，不可能来自于这个配置文件插件自己」）——下面把它展开成可复用判据。

### 3.1 先看「设置插件」今天到底在做什么

设置插件**没有自己的数据**。它显示的东西，逐条都是壳的：

| 设置页里的东西 | 真相源在哪（壳） |
|:--|:--|
| 主题 | 主题引擎（壳） |
| 语言 | LanguageRegistry（壳） |
| 快捷键 | KeybindingRegistry（壳） |
| 更新检查 | 更新服务（壳） |
| AI 接入开关 | `src/App/config/aiBridge.ts`（壳声明的配置项） |
| 外观 | `src/App/config/appearance.ts`（壳） |
| 插件管理 | PluginStateService（壳） |

设置插件干的事只有两件：**① 把这些东西摆出来；② 决定摆在哪、长什么样。**

⇒ 用户那个思想实验因此成立：**造第二只设置插件**（另一套 UI，扁平开关 vs 雾化开关，另一套布局），
- 在 A 里关掉某个开关 ⇒ B 里那个开关**也是关的**；
- 在 A 里是扁平开关、B 里是雾化开关 ⇒ **同一套根源**。

**因为它们读写的不是「自己的数据」，是壳的 configuration / registry。**

### 3.2 「配置文件插件」同理——它操作的东西，全是壳本来就持有的

一个 profile（配置文件）说的是「**这套工作方式叫什么名字，它由哪些插件 + 哪些设置覆盖 + 哪个布局组成**」。而这三样东西今天**全部已经在壳手里**：

| profile 要管的东西 | 今天在壳哪 |
|:--|:--|
| **激活了哪些插件** | PluginStateService（`getPluginStateValue` / 启用停用记录） |
| **哪个套是激活套**（一对多插件） | `factorySlots`（`getActive(role)` / `getDefaultPluginId`，见 `FactorySlots.ts`） |
| **设置的值** | ConfigurationService（`getConfigurationValue`） |
| **工作台布局** | layout snapshot（`layoutSnapshot.register`，`usePoolSync` 推送的那份） |
| **键盘映射** | KeybindingRegistry |

⇒ **配置文件插件自己一行数据都不该持有。** 它和设置插件一样：**壳持有根源，插件只提供视图。**

### 3.3 于是判据可以写死成一句话

> **看它操作的东西，是不是壳本来就持有的？**
> - **是** ⇒ 它必然是「壳能力 + 可替换 UI」这一族——**同族于设置插件**。它的能力自然归壳。
> - **不是**（它自己造了数据、自己维护状态）⇒ 它是**普通功能插件**，与设置/配置文件不是一回事。

用户那句留了后门的假设也一并记下：**「除非你哪天说我把这个管理插件的能力也做成一个插件，那我无话可说。」**——即：如果你把「插件管理」本身也做成插件（把 PluginStateService 搬出去），那判据的输入就变了。**但今天没搬，所以判据成立。**

### 3.4 由此得出的两个直接结论（对齿轮）

1. **配置文件插件的入口，该由壳注册（道 B）**，和「设置」那条一样——因为它背后的能力是壳的；把设置插件卸了，「配置文件」入口照样该在。
   ⇒ 用户 2026-09-29 问的「难道也是壳写死吗？」——**是**。但注意：壳写死的是**命令 id**，命令内部的**路由**指向**槽位**（`factorySlots.getActive("profiles")`），**谁提供 UI 都行**。这就是道 B 在「一切插件可替换」的世界里能站住的原因。
2. **「设置」那一条在设置插件缺席时会空点**（`settingsCommands.ts:208-209` 静默 return）——将来「配置文件」那条会有**一模一样**的处境。所以 [01-设计.md](01-设计.md) 件 3 的空槽门控（`when: "settingsSlotFilled"`）**不是给设置做的补丁，是给整族做的模式**——配置文件入口到时照抄这个 `when` 写法。

### 3.5 可替换性：「无所谓」是用户拍板过的答案（照抄，别自己发明）

用户 2026-09-30 的口径：
- 配置文件插件**是否做成可替换的**——**无所谓**；
- **不可替换**：那往齿轮里想注册几条就注册几条，**名字相同而已**（「入口可多处，命令源唯一」——同一个命令 id 出现在齿轮、菜单栏、命令面板多处是常态，`app.on about` / `update.checkForUpdates` 就是这个先例）；
- **可替换**：那到时候再说也行——**因为本项目的存量前提是「所有插件都允许同时存在、并且可以被替换」**（先例：串口监视器那类，连 HTML 参考图都做过）。

⇒ **机制上怎么选**（记给未来 AI）：
- **不声明 `factoryRole`** = **形态一**：与其他插件**并排共存**，自己一个图标/入口，谁都不删谁。
- **声明 `factoryRole: "profiles"`** = **形态二（进槽可替换）**：壳会**把非激活套剔除**——`iconbar.ts:45-48` 的 `slotActive` 过滤就是这条；
  ```ts
  const slotActive = ordered.filter((p) => {
    const role = p.manifest.factoryRole;
    return !role || factorySlots.getActive(role) === p.pluginId;
  });
  ```
  **注意**：形态二插件**本身是槽位感知的、不会掉进 [01](01-设计.md) §一 1.7 那个坑**（同角色只渲染激活那一套，不会出现两只齿轮）。

⇒ **做配置文件插件时，选哪个都可以先做形态一**（只往齿轮注册一条入口，不动图标栏），**形态留到真要「替换别人」时再声明**——这正是用户说的「到时候再说也可以」。

## §四 VS Code 类比（用户点名要的对照）

### 4.1 左下角那一竖排：VS Code 里它整排都是壳的

VS Code 左下角是**一个竖排栈**（不是一颗齿轮）：

```
  👤  Accounts          ← 人头（账户/设置同步）
  ⚙  Manage            ← 齿轮
```

齿轮点开的菜单：**Settings / Command Palette / 检查更新 / About / Extensions 相关**——**全部是 workbench（壳）自己的命令**，**没有任何扩展「是」这颗齿轮**。

⇒ **用户的架构与 VS Code 一致**：齿轮归壳。本件就是把实现补齐到设计档早就写明的样子（`docs/02-Electron架构/E3_多WebView与壳收尾_暂定/06-E3f-壳UI收尾.md:588-603`）。

⇒ **未来那颗「GitHub 人头」也是 VS Code 同款**（Accounts 在 Manage 之上，齿轮恒在整列最末）——[01](01-设计.md) 件 1.3 改 C 的渲染顺序（`owned` 数组序：人头在 gear 之前）已经把位置留好了。

### 4.2 Profiles：VS Code 里它是**壳的能力**，不是扩展

VS Code 的 Profiles 在哪：`File > Preferences > Profiles`（或左下齿轮 → Profiles）。它能：

| 能力 | VS Code 里的样子 | 本项目今天的状态（2026-09-30 实测） |
|:--|:--|:--|
| 新建 / 重命名 / 删除 profile | 列表 + 命名输入 | ✅ **壳侧已实现**：`getProfiles` / `loadProfile` / `saveProfile` / `deleteProfile`（`src/core/services/plugins/ProfileService.ts:88-127`） |
| **从其他 profile 复制** | 「Create from」下拉，可选 `Default` 或任一已有 profile | ⚠️ **半实现**：`snapshotCurrentAsProfile(name)`（`:146`）只能「把**当前**运行态存成一个新 profile」；**从「另一个已有 profile」当模板**这条路**没有**——**这正是用户点名要的那条**（「选择从其他配置文件中选初始插件（这样就不用每次重新点下载插件了）」） |
| profile 里含什么 | 扩展启用集 / 设置 / 键盘映射 / 代码片段 / UI 状态 | ✅ **已定**：`Profile = { name, icon?, plugins[], settings, workspace? }`（`:46-57`）——本项目版 = **插件集 + 设置 + workspace**。⚠️ 键盘映射 / 工作台布局**不在**里面 |
| 导出 | **`.code-profile` 文件**（可含扩展列表、可导出成 JSON） | ✅ **等价物已在**：profile 本身就是磁盘上的 `<appDataDir>/profiles/<name>.json`——**那个文件就是导出物**（设计档原写 `.linkdesk/profiles/`，实现改成了 appData 目录，**以实现为准**） |
| 导入 | 选文件 → 冲突提示（哪些扩展本机没有） | ❌ **没有**：无「缺插件」提示；`switchProfile` 有**五维验证 + 失败回退 + toast**（`:312`、E3d §一），但那是**切换**时，不是**导入**时 |
| 入口 / UI | `File > Preferences > Profiles`（壳视图 + QuickPick） | ❌ **零入口**（见 §4.3） |

**关键对照（也是本项目比 VS Code 更进一步的地方）**：
- VS Code 把 Profiles 的 **UI 也做在壳里**——它是一个 workbench 视图（settings sync / profiles 都在壳）。**没有「Profiles 扩展」这种存在**。
- 用户想做的是**把 Profiles 的 UI 外置成一只插件**——**VS Code 不允许，本项目的架构允许**（`factoryRole` 槽位 + 视图插件机制）。这就是 `factoryRole` 存在的意义：**壳能力可以被多套 UI 覆盖，且可换。**
- 所以「配置文件插件」不是「VS Code 有我们也做一个」，而是**本项目架构下「壳能力的可替换 UI」这一族**的第二个成员（第一个是设置）。

### 4.3 🔴 本件最值钱的实测发现：**壳侧早就写好了，只是没人把它接出来**

2026-09-30 读码实测，配置文件（Profiles）在本项目的**真实存量**是：

| 项 | 状态 |
|:--|:--|
| **壳侧服务** | ✅ **已实现**——`src/core/services/plugins/ProfileService.ts`（**399 行**）：`getProfiles` / `loadProfile` / `saveProfile` / `deleteProfile` / `getCurrentProfileName` / `snapshotCurrentAsProfile` / `switchProfile` ＋ `onDidChangeProfile` 事件 ＋ **五维验证 + 失败回退 + toast**（`:312`） |
| **持久化** | ✅ **已定**——profile 文件在 `<appDataDir>/profiles/<name>.json`；当前名存 `PluginStateService` 的 `currentProfile` 键 |
| **API 面** | ✅ **已导出**——`src/core/index.ts:39` `export * from "./services/plugins/ProfileService"` |
| **设计档** | ✅ **已有**——[`04-E3d-Profile与激活.md`](../../../02-Electron架构/E3_多WebView与壳收尾_暂定/04-E3d-Profile与激活.md)（2026-07-24，任务 43；**五维验证表**就是现成的验收蓝本） |
| **入口 / UI** | ❌ **零**——全仓 grep `switchProfile` / `snapshotCurrentAsProfile` / `getProfiles`，**除服务本体、它的测试、和上面那条 re-export 之外零消费方**（`src/` `electron/` `packages/` 全域实测） |
| **设计档设想的交互** | `04-E3d-Profile与激活.md:31`——「**Ctrl+Shift+P → "切换 Profile…" → QuickPick**」＝**壳自己的 QuickPick，不是插件视图** |

⇒ **两条重要结论，写给未来的 Profiles AI**：

1. **这不是从零开始的任务。** 壳侧能力（含验收蓝本的「五维验证」）已就位，缺的是**入口 + 视图**。你上手第一件事应该是**读 `ProfileService.ts` 和 E3d**，而不是自己设计一遍 profile 的数据结构——**数据结构已经定了，`Profile` 就是那个 interface**。
2. **用户要做的是比 E3d 更进一步的一步。** E3d 把 UI 放在壳（QuickPick）；用户要把它**外置成可替换的视图插件**。⇒ 按 §3.3 判据这完全成立（能力是壳的，UI 换成插件），**也正是 `factoryRole` 机制存在的理由**（见上 §4.2 末条）。

⛔ **由这一条直接推出的禁令**（比原来那句「别自己发明存储位置」更重要）：
- ⛔ **别在插件里再实现一遍 profile 的读写 / 切换**——壳已有 `switchProfile`（带五维验证与失败回退）。插件该做的是**调它**，不是**重写它**。
- ⛔ **别把 profile 的存储位置、五维验证逻辑抄进插件**——那是壳的能力（§5.4 单一真相源）。
- ⚠️ **要补的缺口清单**（这些才是你那件任务的真工作量）：**入口命令族**（`workbench.action.*Profile`）· **列表 / 新建 / 重命名 / 删除视图** · **「从其他 profile 复制」**（`snapshotCurrentAsProfile` 只覆盖「从当前复制」）· **导入 / 导出**（文件已是 JSON，缺的是选文件与缺插件提示）· **齿轮菜单入口**（照抄 [01](01-设计.md) 件 3 的 `when` 门控模式）。

### 4.4 「账户/人头」这条留个记号

用户 2026-09-29 说人头是「后话」，且「决定这个登录 github 的图标及其内容到底属于壳还是插件（理论上那里的图标谁都可以注册，不管壳还是插件，显示的内容也不过是绑定到壳上，还是独立成第三方插件）」——
⇒ 按 **§1.3 判据**当场就能定：
- 「GitHub 登录」这个能力**在壳上**（凭据、API、同步都归壳）⇒ **入口道 B（壳注册），图标进 `owned`**；
- 若「内容」是某个第三方插件的能力（比如它自己去读某个仓库）⇒ **那部分道 A（插件声明自己的菜单）**。
⇒ 一半壳、一半插件是**允许的**，按能力切开就行。**本件不做，只留判据。**

## §五 门禁与坑（安全带，未来的 AI 照着躲）

### 5.1 🔴 `menu-slots` 那条真实事故（大小写）

`packages/plugin-sdk/src/eslint/checks/menu-slots.ts` 文件头记着 **2026-08-11 的事故**：某插件在 `contributes.menus` 里写了 **`"MenuBar"` / `"FileContext"`（成员名）**而不是 **`"menuBar"` / `"fileContext"`（值）**——它的菜单项**静默消失两个多月**，**零门禁拦住**。

规则至今在守：**「槽位 id 与宿主某个值仅大小写不同 ⇒ 红」**。

⇒ **写槽位名，抄值不抄名字。** 值在哪：`src/core/registry/commands/MenuRegistry.ts:24-53` 的 `MENU_SLOTS`，以及生成件 `packages/plugin-sdk/schemas/host-menu-slots.json`（当前 `slotCount: 14`）。

### 5.2 `host-menu-slots.json` 是**生成的**

由 `scripts/gen-host-menu-slots.mjs` 产出。**手改它 = 下次生成被覆盖**。要加壳内置槽位，改 `MENU_SLOTS` + 重跑生成脚本。

### 5.3 幂等键是 `command + pluginId + when` 三条

`MenuRegistry.ts:121-132` 的注释先例：E5.8#37.6 那两条「移动到右侧/左侧」**共享同一个命令 id**（`toggleSidebarPosition`），**只有 `when` 不同**——它们是两条不同的菜单项（对换当开关）。**曾因只按 `command + pluginId` 判重把第二条当重复丢掉。**

⇒ **同一个命令 id 在同一个槽位出现多次是合法的**，靠 `when` 区分。别自己判「重复」。

### 5.4 别把壳的状态搬进插件（单一真相源铁律）

配置文件插件**最容易犯的错**：自己去存一份「当前 profile 里有哪些插件」。**一旦插件持有副本，就有两份真相**，切换/导入/外部变更后迟早不一致。

⇒ **剖面**：插件视图层可以有一份**渲染用的临时态**（如向导里未保存的勾选），但**「生效的 profile」必须只有壳一份**。

### 5.5 插件往齿轮注册（道 A）是允许的，但要清楚你在承诺什么

插件完全可以 `contributes.menus.extensionGear`（槽位是开放 string，零壳改动）。**但**：
- 你的条目会**随你生死**——卸载即消失（这通常是你要的）；
- 你的条目**排在壳那 8 条之后**（`getMenuItems` 按 `order` 排序，默认 100，壳那几条也是 100 ⇒ **同级按注册序**，壳先注册）；
- ⚠️ **别把自己的「设置」入口塞进齿轮再指望它跟壳的「设置」一样**——那两个是**两条道**的两条入口，语义不同（壳那条路由到可替换的设置槽，你那条只到你自己）。**要清楚自己在哪条道上。**
