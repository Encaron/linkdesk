# 06 · 派工与交接（**AI-1 ～ AI-3**）

> **一句话**：**AI-1 独占 SDK 轴（串行做完全部）→ AI-2 与 AI-3 并行 → 两者收口后由 AI-3 兼职验收 = 3 个 AI**。
> 🔴 **顺序是"先串后并"**（2026-10-06 用户拍的妥当版）：**AI-1 全部收口后**才起 AI-2/AI-3。宁可慢一点墙上时间，也不让消费者对着一个**还会动的契约**写代码（§一 有收益说明）。
> 本件只讲**谁先谁后、谁许动哪个文件**；每格具体做什么，看 [00 §四](00-README.md) 任务全景与各格正文。

---

## 一、为什么是 3 个、为什么"先串后并"

### 1.1 决定条数的是「出口单点」，不是格子数

| 出口 | 谁从它发 | 结论 |
|:--|:--|:--|
| **`@linkdesk/plugin-sdk` npm 包**（G1 账本 ＋ G2 lint ＋ G3 脚手架与 README 全从这里出去） | G1 / G2 / G3 | 🔴 **三条腿共用一个出口 ⇒ 必须同一个 AI 串着做**（并行改同一个包 = 版本号与 `release:mark` 互撞） |
| **壳仓运行期**（`src/core/` ＋ `electron/ipc/`） | G4 | 与上面**零文件重叠** ⇒ 可并行 |
| **壳仓发布链**（`scripts/`，dev 工具、**不占版本号**） | G5 | 与上面**零文件重叠** ⇒ 可并行 |

⇒ **三条线**：SDK 轴（AI-1）／壳运行期轴（AI-2）／壳发布链轴（AI-3）。**验收不再单独占人**，并进 AI-3（§三·阶段四）。

### 1.2 为什么等 AI-1 **全部**做完，而不是只等 G1

G1 只冻结**账本形状**。但 **G2 与 G3 落地时还会反推账本**：

- G2 的报错文案要给「地板值 ＋ 越界的导入名 ＋ 出处」⇒ 可能要求账本**多记一列**（比如子路径归属）；
- G3 的脚手架要**从模板自源码算出地板** ⇒ 可能要求账本暴露一个查询形状。

**若让 AI-2 在 G1 之后就开工，它就是在对着一个会变的契约写解析。** 而"等 AI-1 全收口"让 **S2（契约冻结）自动完成**——这个隐患直接消失。**这就是"先串后并"换来的真实收益，不是保守。**

**代价**：AI-3 的 G5 本可零依赖最早开工，等 AI-1 是白等墙上时间（**不是白花钱**——AI 按次计费，不是按日历）。想省时间见 §五 的「可选提速」。

## 二、派工表

| AI | 棒名 | 负责 | 落点 | 依赖 | 开工 |
|:--:|:--|:--|:--|:--|:--|
| **AI-1** | **SDK 轴**（串行，一人扛三格） | **G1 → G2 → G3** | 壳 `scripts/`（账本生成器）→ SDK `schemas/`＋`src/eslint/checks/` → 脚手架模板＋SDK README＋`docs/03-插件制造/` 中英双语 | 自身串行 | **立刻**（§五 第一步） |
| **AI-2** | **壳运行期轴** | **G4** 读数腿 | `src/core/compat/compatibility.ts`（＋ `electron/ipc/handlers/plugin-handlers.ts` 供数；复用 `dangling-scan-async`） | **AI-1 收口**（契约冻结） | 阶段二 |
| **AI-3** | **壳发布链轴 ＋ 验收** | **G5** 流程腿 → 收口后**兼做验收**（原 AI-4 的活） | `scripts/check-publish-gate.mjs` 一族 → 官方插件仓存量回归＋[05](05-验收判据.md) 全表验收 | G5 **无依赖**；验收须等 **AI-2 交话** | 阶段二起 G5；阶段四转验收 |

**AI-1 为什么一个人扛三格**：G1 定账本、G2 吃账本、G3 把账本讲给作者听——**同一个契约的三面**。拆给三个人就等于让他们各自猜格式，必然漂移（[02 §七](02-设计-账本与门禁.md)「归一化」红线的反面：**两份必然漂移**）。

## 三、串行与并行（时刻表）

| 阶段 | 谁在跑 | 谁在等 | 为什么 |
|:--:|:--|:--|:--|
| **一 · 串行** | **只有 AI-1**（G1 → G2 → G3） | AI-2 / AI-3 | **S1 硬闸门**：`since` 能否从壳仓 tag 历史回溯，决定全案成不成立（[02 §九](02-设计-账本与门禁.md)）。回溯不出来 ⇒ 换设计，**早派出去的 AI 全白干**。顺带把 **S3（SDK 出口独占）** 与 **S2（契约冻结）** 一并解决 |
| **二 · 并行（P1）** | **AI-2（G4） ∥ AI-3（G5）** | — | 两条线文件**零重叠**（§四）。这是**本案唯一允许的并行** |
| **三 · 交话** | AI-2 收口后**先给 AI-3 传话** | AI-3 收到后才动验收 | 🔴 **被验方先交，验方后动**——见 §六。方向 = **AI-2 → AI-3** |
| **四 · 验收** | **AI-3**（兼职） | — | 跑 G2 门禁扫官方全部插件仓＋修声明＋[05 §一](05-验收判据.md) 真机正控 1（`0.2.41` 上 settings 必须显示「**不适配**」）＋[05 §四](05-验收判据.md) 七条原则自检 |

> 🔴 **G0（救火）已按 D1 暂缓**（[00 §十](00-README.md)），**不派工、不阻塞**。将来重启它是**独立一件**，不并进这三条线。

### 为什么不设第 4 个 AI（验收者为什么是 AI-3）

- **AI-2 不能当验收者**：验收的正控 1 验的就是**读数腿（G4）**——那是 AI-2 亲手写的，**自己验自己**正是 [05 §一](05-验收判据.md) 最不能接受的那种。
- **AI-3 是天然的外部视角**：它做的是发布链（G5），与门禁（G2）、读数腿（G4）**文件零重叠**，没写过被测对象。
- **负载也合适**：G5 是三格里最小的一格，AI-3 有余量接验收。

⚠️ **诚实的残余**：G5 自己那条黄灯判据属于"自写自验"（AI-3 写的 G5、AI-3 验）。风险低（**纯提醒、不拦、不进 CI**，[04 §二](04-任务-读数腿与流程腿.md)），**登记备查**，不必另立第 4 人。

## 五、派工节奏（**三步 · ⛔ 别一次派齐**）

### 第一步（现在）：**只派 AI-1**

> 交付 = **G1 → G2 → G3 全部收口 ＋ 账本 schema 冻结 ＋ 交接板**。
> ⛔ 这一步**不许**顺手去动 `src/core/compat`（那是 AI-2 的地）。

### 第二步：**AI-1 收口后**，并行派 **AI-2 ＋ AI-3**

- **AI-2** 做 **G4**（契约已冻，可以放心写）；
- **AI-3** 做 **G5**（无依赖）。
- 两者各写各的 §六 交接板。

### 第三步：**两者都收口后** —— **先交话，再验收**

1. **AI-2 → AI-3 传话**（被验方先交，§六 三件套）；
2. **AI-3 转验收**：存量回归（扫官方全部插件仓、修声明）＋ [05](05-验收判据.md) 全表。

### 可选提速（不影响正确性）

AI-3 的 **G5 与 AI-1 零依赖**。若想把墙上时间压短，可**让 AI-3 从第一天就开工 G5**，做完先挂着，等 AI-2 交话再转验收。代价只是 AI-3 要等（**空等不花钱**）。⛔ **AI-2 没有这个选项**——它的契约必须等 AI-1。

## 六、交接板（每棒必须留什么）

每棒收口时在**本夹内**追加一节 `交接 · AI-x`（或更新自己那格正文），**只写三件**：

1. **现状**：做到哪、哪些是**真跑过**的（门禁 EXIT / 实测读数），哪些只是"写完没验"；
2. **冻结项**：我这棒定死的契约（AI-1 必写**账本 schema**；AI-2 必写**读数返回字段**）——下一棒照此实现，⛔ **不许改形状**；
3. **下一棒的第一件事**：一句话，可执行。

🔴 **方向纪律**：**被验方先交，验方后动**。阶段三里是 **AI-2 → AI-3**（AI-3 收到 AI-2 的"现状＋冻结项＋未验项"之后才开始验收）；AI-3 的**验收结论**回写本夹，供下一位维护者。

⚠️ **⛔ 不要复述本夹已有内容**（读 00–06 即可），交接板只写"变化量"。

## 七、与排队中任务「插件仓自足与壳耦合清账」的关系（能否并行）

**对面**：[插件仓自足与壳耦合清账](../../待抉择池/插件仓自足与壳耦合清账/00-README.md)（D1–D5 已于 2026-10-06 拍板，自述**全排队**、前置＝「文件打开方式与贡献点」全案收口）。

### 7.1 判定：**语义不冲突，资源上撞车 4 处 ⇒ SDK 轴那一段不能并行；只有 G4 一格可并行**

**语义层不冲突**：一个治「插件**自己声明的地板**真不真」，一个治「插件仓**要不要回头依赖壳**」。互不否定，谁也不是谁的前置。

**资源层撞车 4 处**（全是"同一出口／同一行链"，不是同一步骤）：

| 热点 | 清账 | 本案 | 度 |
|:--|:--|:--|:--:|
| **`@linkdesk/plugin-sdk` packument** | D1-B 往 SDK 加 `import-icon-theme` 命令（一次发版） | G1 账本进 `schemas/` ＋ G2 改 `eslint/checks/` ＋ G3 改 README（一次发版） | 🔴 **同一 packument 两次 bump 必打架** |
| **`packages/create-linkdesk-plugin/template/`** | D2-A 加 iconThemes 骨架 | G3 改 `minAppVersion` 默认值 | 🔴 **同一批文件** |
| **`npm run check` 一行链 ＋ `check-gate-health`** | D3 加「插件仓自足」腿（并入 R6） | G2 改 lint 腿；[05](05-验收判据.md) 要求新腿进 `check-gate-health` 认账 | 🔴 **一行链，两笔各自插入必冲突**（清账 §五 原话） |
| **作者文档** | D2-B `plugin-docs/docs/03-contributes-spec.md` §3.7 | G3 改 `plugin-docs/docs/**` ＋ `docs/03-插件制造/**` | 🟠 同包不同文件，但**同属"文档连锁"**（AI-4.5 那条） |

**运行期零冲突**：清账 ⛔ **零运行期改动**（只动开发工具／作者文档／门禁），本案 **G4** 动 `src/core/compat/**` ＋ `electron/ipc/handlers/plugin-handlers.ts` ⇒ **这一格可与清账并行**（前提：账本契约已冻）。

### 7.2 建议排队顺序（三件一条队）

1. **「文件打开方式与贡献点」**（在途：AI-4.5／5／5.5／6）；
2. **本案（门禁案）**——🔴 **排在清账之前**，两条理由：
   - 它有**真机事故**背景（用户机器上真崩）；清账是"防未来 ＋ 治一处耦合"，紧急度低；
   - **本案会改官方插件的 `minAppVersion` 声明**（AI-3 存量回归），而**清账 D4/D5 也动插件仓**（marketplace/editor 注释、出厂账）⇒ **门禁案先落，清账收尾时一次到位，不必改两遍**。
3. **清账**——⚠️ 它现有文档只写了「前置＝文件打开方式与贡献点收口」，**未登记本案** ⇒ 开工前需补一行互指。

### 7.3 两案共有的前置（同一约束）

**都排在「文件打开方式与贡献点」之后**——它的 **AI-4.5「契约文档连锁」**（contracts · sdk · ui · plugin-docs）与 **AI-5.5 的 R1–R6 门禁腿**，正是本案 **G2／G3** 要改的**同一批落点**。
⇒ 🔴 **本案开工前置 ＝ 对方全案收口**（与清账同口径）。

> ℹ️ 清账 §五 记的"对方在改 `contracts/linkdesk.d.ts` 导致壳仓 `typecheck` 为红、任何跑 check 链的动作都被卡"那条**现状约束已解除**（2026-10-06 实测 pre-push 的 typecheck ✔ 通过）——但**排队结论不变**（撞的是同一行 check 链与 packument，不是那个红）。
