# E5.8-背景图存储位置入口档案（#153）

> 2026-08-27。**用户实机痛点：爱换壁纸的用户「换到最后 C 盘爆了都不知道发生了什么」**——需要一眼看见外观图片堆在哪、堆多大、可当场清理。
> **用户拍板：入口 = 背景图两行（app.backgroundImage / app.zoneBackgroundImage）齿轮菜单加「打开存储位置」；动作 = 直接打开资源管理器（`shell.openPath` 开目录内容），非复制路径。**
> 清单指针：E5.8-执行清单 Phase 11.22 #153。

## 一、背景与需求

- 用户问「复制存储路径 vs 打开资源管理器哪个好」→ 拍板 **打开资源管理器**：它直接打中「C盘爆了不知道发生了什么」的痛点（打开即见堆积 + 可当场删）；复制路径对非技术用户是死路（还得自己会粘进资源管理器）。
- **只给两行**：用户明确「单独给它两个加」——背景图 + zone 背景图，其他行齿轮不出现。

## 三、关键差异——为什么不能直接复用文件树命令

| | 文件树「在文件管理器中显示」 | 本需求「打开存储位置」 |
|---|---|---|
| 目标 | **单个文件**（父目录高亮它） | **整目录**（看堆积、可清理） |
| 路径来源 | 渲染层**已有**（ctx.uri，列目录时已知） | 渲染层**没有**（userData 主进程权威） |
| 底层方法 | `shell.showItemInFolder(file)` | `shell.openPath(dir)`——开目录**内容**；showItemInFolder 只高亮目录不显示内容 |

复用的是**同一套 shell IPC 基础设施**（main.ts:205 链路），不同 Electron shell 方法。

## 四、8 维度设计前置

> 任务性质：**壳能力升级**（新 `window.linkdesk` API `appearance.revealStorage` + 新壳命令 + 齿轮菜单项）。方向已由用户拍板（openPath 打开资源管理器，只两行）。

### ① 能力边界
- **壳能力**。保底：无插件时命令不显示（when 不匹配任何行 = 菜单零项），两行设置本身不依赖插件存在。
- 打开存储位置 = 外观资产目录揭示，壳级通用能力（非 settings 插件专属）。

### ② API 设计
- **新增 `appearance.revealStorage(): Promise<void>`**——4 件套契约：`contracts/linkdesk.d.ts` 类型声明 + pool preload（`preload-pool/namespaces-plugin.ts` 转发 IPC）+ 主进程 handler（`electron/ipc/handlers/appearance-handlers.ts`）+ `docs/03-插件制造` 文档说明。
- 复用：无新事件通道、无新配置、无新贡献点。命令 `workbench.action.openAppearanceStorage` 走既有命令系统（coreCommands 同款注册）。

### ③ 通信方式
- 池（齿轮点击）→ 壳命令 handler → `window.linkdesk.appearance.revealStorage()` → IPC `appearance:reveal-storage` → 主进程解析 `path.join(app.getPath('userData'), 'appearance')` → `shell.openPath(dir)`。数据流单向（池 → 主 → OS），无回传。

### ④ 壳侧代码设计
- 改动文件：
  - `electron/ipc/handlers/appearance-handlers.ts` — 加 `appearance:reveal-storage` handler（`shell.openPath`，目录不存在时 fail-loud 不崩）。
  - `src/core/commands/shell/coreCommands.ts` — 注册 `workbench.action.openAppearanceStorage`：`title: "打开存储位置"`（走 t()）+ `menuId: MENU_SLOTS.SettingItemGear` + `when` 门控两行 + handler 调 `window.linkdesk.appearance.revealStorage()`。
  - `contracts/linkdesk.d.ts` + `preload-pool/namespaces-plugin.ts` — `appearance.revealStorage` 契约与转发。
  - `docs/03-插件制造` — API 文档补一条。
- **单一权威**：目录路径 = 主进程 `app.getPath('userData')` 派生，池内零路径知识（不暴露 userData 面）。
- 硬约束：label 走 t()；零插件 ID 硬编码（config key 是壳自有键，when 门控引用合法）；零颜色/路径改动。

### ⑤ 插件侧代码设计
- **零改动，零贡献点**。齿轮菜单本身由 SettingRow 现成渲染，菜单项由壳注册。

### 六.5 实机 bug 修复——齿轮 when 门控从未生效（2026-08-28）

**用户实机**：每个齿轮都见「打开存储位置」「跟随主题」——要求只有背景图两行见打开存储位置、主题分组见跟随主题。

**根因（两层）**：
1. **`ensureCoreCommands` 漏传 when**（coreCommands.ts 注册循环）——`registerCommand` 与 `registerMenuItems` 的载荷都是 `{command, group}`，声明的 `when` 从未落注册 → 壳侧 getItems 过滤 `whenExpr = item.when ?? cmd?.when` = undefined → `matches(undefined)` 恒真 → **全部核心 when 门控命令裸奔**。`git log -S "when: cmd.when"` 空 = **长期 bug**（#153 只是新增一个泄漏项；「跟随主题」#153 前就已在裸奔）。
2. **`ContextKeyService.evaluate` eq/neq/regex/in 忽略 `overrides`**——只有裸 key 分支认 context prop，与「overrides 优先于全局 _state」文档意图不符；gear 的 per-row `settingKey` 只能走全局 contextKey:set 竞态广播。

**改法**：① 注册循环补 `when: cmd.when`（命令 + 菜单项双落；菜单项是过滤主源，命令侧让命令面板也按 when 过滤）；② `evaluate` 统一经 `_readKey(key, overrides)`（overrides 优先）——修复后 `settingKey` 由 ContextMenu context prop 权威直判，零竞态。

**连带行为**：命令面板不再显示无 settingKey 上下文的门控命令（resetSetting/followTheme/openAppearanceStorage 在面板本就 no-op，隐藏 = 修正）。非门控项（复制设置 ID / 复制为 JSON）不受影响。
