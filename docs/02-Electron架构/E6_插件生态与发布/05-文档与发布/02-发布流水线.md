## 〇、🔴 安装包文件名唯一真理源（2026-09-11 补——本档原稿埋了 `asset-missing` 的雷）

**问题实锤**：同一个安装器，本仓当前有**三个不同的名字**在流通——

| 出处 | 写的名字 | 后果 |
|:--|:--|:--|
| `electron-builder.yml` | **没写 `artifactName`** ⇒ 走 electron-builder 默认 = `LinkDesk Setup 0.1.47.exe`（**带空格**） | 实际产物 |
| 本档 §2.2 官网下载链接 | `LinkDesk-Setup.exe`（无版本号） | 死链 |
| [01 §2.3 Release asset 约定](../06-主软件更新/01-更新机制设计.md) | `linkdesk-setup-{version}.exe` | **更新器精确匹配它** |

⇒ **更新器按 `linkdesk-setup-{version}.exe` 找，Release 上躺的却是 `LinkDesk Setup 0.1.47.exe`** ⇒ 检查更新能成功、下载永远失败，报 `asset-missing`。这就是 [01 §2.3](../06-主软件更新/01-更新机制设计.md) 自己预警的那个 bug，**在本流水线文档里已经成型了**。

**定案 —— 唯一真理源 = `electron-builder.yml` 的 `artifactName`**（清单 **E6#42e**）：

```yaml
# electron-builder.yml（本轮新增）
artifactName: "${name}-setup-${version}.${ext}"   # → linkdesk-setup-0.1.47.exe（name 小写，见下）
```

- `${name}` 取 `package.json` 的 `name`（`linkdesk`，全小写）——**不是 `productName`（`LinkDesk`，大写 L/D）**。大小写差异同样是 `asset-missing` 的成因（Linux/URL 场景大小写敏感）。
- **所有消费方一律从这一处取真值，禁止再手抄字符串**：官网下载链接（§2.2）、CI 上传 glob（§1.1）、更新器匹配（[01 §2.3](../06-主软件更新/01-更新机制设计.md) `linkdesk-setup-{version}.exe`）、Release 页眉文案。
- 🔴 **验收硬判据（#42e）**：`npm run electron:build` 之后 `release/` 里**有且只有一个** `.exe`，其文件名**逐字符等于** `linkdesk-setup-{package.json version}.exe`；否则红灯。这条断言要写成脚本（`scripts/assert-installer-name.mjs`，对照 [E6#57.15d](../E6-执行清单.md) 同款门禁风格），**不许靠肉眼看**。
- 🔴 **门禁必须证明自己会红**：故意把 `artifactName` 删掉 → 断言必须红。**恒绿的门禁不是门禁**（memory `snapshot-shadows-truth-bug-class`：判定挂在「期望从现场读」上 = 断言恒真 = 假门禁）。
- ⚠️ **别把两个名字看成一个（这是两个概念，不是一个拼错）**：

  | 名字 | 在哪 | 是什么 |
  |:--|:--|:--|
  | `linkdesk-setup-{version}.exe` | **GitHub Release 上的 asset** | 发布侧产出的文件（本文档管的就是它） |
  | `linkdesk-update-{version}.exe` | **用户机 `{userData}/update/` 里** | 更新器校验通过后**本地改名**保存的待装包（[01 §2.4](../06-主软件更新/01-更新机制设计.md) 管） |

  ⇒ 两者**故意不同名**（远端 asset 名 vs 本地暂存名），**不是笔误，不要「统一」它们**。真正要求一致的是：更新器要按 `linkdesk-setup-{version}.exe` 精确匹配去 Release 上找 asset——**这一条只跟 §〇 的 `artifactName` 对齐**。

## 一、GitHub Actions CI（E6#42）

### 1.1 工作流

文件：`.github/workflows/build.yml`

```yaml
name: Build and Release

on:
  push:
    branches: [electron]
    tags: ["v*"]

jobs:
  build:
    runs-on: windows-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Install dependencies
        run: npm ci

      - name: Check
        run: npm run check

      # 🔴 E6#57.15d —— CHANGELOG 段头门禁（发布前必过，缺段 = 发布后发行说明页空白）

        shell: bash
        run: node scripts/assert-changelog-section.mjs

      - name: Build

      # 🔴 E6#42e —— 安装包文件名断言（防 asset-missing；见 §〇）
      - name: Assert installer filename

        run: node scripts/assert-installer-name.mjs

      # TODO: v1.0 发布前启用代码签名

      #     organization-id: ${{ vars.SIGNPATH_ORG_ID }}

      # 方案 C——正规证书（DigiCert/Sectigo，$200-500/年）
```

### 1.2 触发条件

| 事件 | 干什么 |
|:--|:--|
| push 到 `electron` 分支 | build + check + 上传 artifact |
| push tag `v*` | build + check + 发布到 GitHub Releases |

### 1.3 Release 步骤

```
push tag v0.2.0
  → CI 跑 check + CHANGELOG 段门禁（#57.15d）+ 安装包名门禁（#42e）
  → 产出 linkdesk-setup-0.2.0.exe（名字由 artifactName 唯一决定，§〇）
  → 创建 GitHub Release v0.2.0
  → 上传 .exe（**同名**）
  → Release body 必须写入本次 CHANGELOG 正文（不是 GitHub 自动罗列的 commit 列表）
```

> 🔴 **Release body 的正文来源（2026-09-11 定，与 #57.15d / #57.8e 配对）**：
> 更新器与发行说明页读的是 **Release body**（[05 §2.4](../06-主软件更新/05-发行说明.md)），**不是 GitHub 的 `generateReleaseNotes` 自动列表**——自动列表是 commit 流水，用户看不懂，也不是人写的那份说明。
> ⇒ CI 的 Release 步骤要把 `CHANGELOG.md` 里 **`## v{version}` 那一段正文**灌进 body。**`generateReleaseNotes: true` 保留但不作为正文**（可退化为「首次贡献者名单」之类的附加区）。
> ⇒ **这就是 #57.15d 那条门禁存在的理由**：缺段 ⇒ body 空 ⇒ 用户点「查看更新内容」看到一片空白。

### 1.4 覆盖安装方向（🔴 E6#42d——发布前必测，别省）

**测试 = 双向往返**，不是只测「装新版」：

| 方向 | 期望 | 不过怎么办 |
|:--|:--|:--|
| 旧版 → 新版（更新器正路） | 覆盖成功、版本号变新、插件与设置全在 | 红灯，修 |
| 🔴 **新版 → 旧版**（手工跑老安装器） | **NSIS 应当拒绝或至少不静默降级** | **如果 NSIS 不拦，则必须在应用层加方向守卫**——判据复用插件侧 **E6#33c 锚①**：`electron/ipc/handlers/plugin-install-handlers.ts` 的**同版恒拒 / 旧版默认拒 / 只有显式 `allowOlder:true` 才放**，比对函数就是 [`src/core/utils/plugin/semverUtils.ts:88`](../../../../src/core/utils/plugin/semverUtils.ts#L88) 的 `updateTargetDirection()`（返回 `upgrade`/`downgrade`/`same`）。**直接复用它，不许各写一份判断**（[01 §2.4 残留清理](../06-主软件更新/01-更新机制设计.md) 那条陈旧 `.exe` 清理用的是同一套语义） |

> ⚠️ **为什么单列一条**：插件侧在第 3 层为「装旧版覆盖新版」这事反复修过好几轮（第 3.5/3.6/3.7 层都有回响）。**主软件侧是同一个病、不同的载体**，不要在第五层重新踩一遍。判据必须是**实测出来的**，不许以「NSIS 应该会拦」结案。

## 四、版本号策略

```
v1.0.0  — 首个正式版（E6 完成后）
v1.0.1  — bug 修复
v1.1.0  — 新功能（终端系统 / 可拖出标签页 / 自动更新）
v1.2.0  — 卡片工作台
...
```

> 🔴 **2026-09-11 用户拍板：不进 1.0，继续在 `v0.x.x` 游荡。** 上表是**方向**不是触发器——**E6 结束也不自动跳 1.0**，要不要进 1.0 须用户另行点名（目录里 `1.0.0` 只是「首个正式版」的语义占位，**不是承诺**）。**E6 全程软件版本恒 `0.x`**：`0.1.x` 补丁向后走 patch，破坏性变更走 minor。判据与提交前缀规则见 [.claude/skills/version-bump/SKILL.md](../../../../.claude/skills/version-bump/SKILL.md) 与硬约束 22。
> 🔴 **数到 2.0 先问能不能增量**——0.x 里破坏性变更走 minor，补丁向后走 patch（memory `version-axes-separated` / `version-major-additive-first`）。**软件 / 契约 / SDK 三条版本轴各自独立，别互相带着走。**
