### E1 步 7：Electron 打包

```
操作：配置 electron-builder.yml + npm run electron:build
```

**🔴 文档空白。** 整个 29 份文档中，没有 `electron-builder.yml` 的设计。这个文件决定：
- 哪些文件打进安装包（`dist/` + `dist-electron/` + `plugins/` + `node_modules/` 的子集）
- ASAR 打包策略：`linkdesk://` 协议需要读 `plugins/` 目录——ASAR 内的文件读取路径和开发模式不同
- NSIS 安装器配置（Windows）
- 代码签名

**这不是打包时才想的事——必须在步 1 就确认 `linkdesk://` 协议在 ASAR 打包后仍然能读到文件。**

Electron `protocol.handle` 在 ASAR 内读取文件需要特殊处理：
```typescript
// 开发模式：
const fullPath = join(PLUGINS_DIR, normalizedPath);  // PLUGINS_DIR = __dirname/../../plugins

// 打包后 ASAR 内：
// __dirname = resources/app.asar/electron
// PLUGINS_DIR = resources/app.asar/plugins — 但 linkdesk:// 需要读这里
// 如果 plugins/ 打进 ASAR，file:// 协议能读
// 如果 plugins/ 不打进 ASAR（保持为独立目录），需要 asar.unpacked 路径
```

**建议补：** 在步 1 或步 5 确定 ASAR 策略：`plugins/` 保持为独立目录（不打包进 ASAR），用 `electron-builder` 的 `"asar": { "unpackDir": "plugins" }` 或更简单的 `"asar": false`（开发阶段先不压缩）。

## 六、与工程实际代码的对齐检查

### 6.1 插件加载的双路径

**实际代码有两条加载路径，文档部分覆盖：**

| 加载路径 | 代码位置 | 用途 | Electron 后变化 | 文档覆盖？ |
|---|---|---|---|---|
| `import.meta.glob` → `loadViewPlugin()` | `loader.ts:42-60, 466-510` | 源码树中的插件（Vite 构建时扫描） | **不变**——Vite build 仍然生成 chunk。Electron dev 模式 Vite 即时编译 | ✅ E1 没说，但逻辑确实不变 |
| `loadPluginRuntime()` → `/@fs/` | `loader.ts:382-462` | 外部安装的插件（不在源码树） | **dev 模式：`/@fs/` 仍可用。prod 模式：需要 `linkdesk://` 协议替代** | ⚠️ `10-缺口补丁.md` §5 覆盖了，但没区分 dev/prod |

### 6.2 插件文件监听

当前 `startPluginWatcher()`（`loader.ts:925-966`）用 2s 轮询 `invoke("list_plugin_dirs")`。

E1 后改为 `window.linkdesk.plugins.listDirs()`。Electron 的实际实现走 `fs.readdir`——比 Rust 版更简单。✅ 文档步 3 覆盖。

### 6.3 `initV3Api` 的运行时插件 SDK

`v3Api.ts` 导出 `useTauriEvent` 给运行时插件用。E1 后改为 `useIpcEvent`。但运行时插件在 E3 后才迁移到独立 WebView——在 E1-E2 期间运行时插件仍在壳 WebView 内。

**⚠️ 时序问题：** `v3Api` 给运行时插件暴露的 hook 需要和当前插件所在进程一致。
- E1-E2（单 WebView）：`useIpcEvent` 内部调 `window.linkdesk.events.on()` → IPC 到 main process → 回壳 renderer。比直接 `ipcRenderer.on()` 多一跳。
- E3（多 WebView）：插件在自己的 WebView 里，`window.linkdesk.events.on()` → IPC → main process → IPC → 回插件 renderer。和 E1-E2 行为一样。

**所以 `useIpcEvent` 在两种拓扑下都正确。** ✅

### 6.4 StorageService 的 `localStorage` 双写

当前 `StorageService.ts` 用 localStorage + Tauri fs 双写（F5 安全）。Electron 的 renderer 同样支持 `localStorage`。

**⚠️ 但 Electron 下 `localStorage` 的行为需要注意：**
- 壳 BrowserWindow：`localStorage` 正常工作 ✅
- E3 插件 WebContentsView：`localStorage` 独立——插件 A 的 localStorage 和壳的 localStorage 是**两个不同的存储空间**（不同 Chromium 进程）。

**这实际上是正确行为**（插件不应该访问壳的 localStorage）。但之前 Tauri 单 WebView 时代，插件可以和壳共享 localStorage——迁移后它们的持久化数据需要显式通过 `ConfigurationService` 的 `onDidChangeConfiguration` 同步。文档没提这个变化。
