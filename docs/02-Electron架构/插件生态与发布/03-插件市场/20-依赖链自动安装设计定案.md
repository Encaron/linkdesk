> 上游档案：[18-通知系统全账与设计定案.md](18-通知系统全账与设计定案.md)（job 表 / 槽模型 / 73d 面板语义）。

## 〇 一句话

装 A 时，A 清单 `requires` 里**缺失**的依赖由壳在**同一个安装 job 内**自动先装（内联递归、不占第二个槽），用户在父 job 行上看到依赖进度；解析不到/装失败/依赖环 ⇒ 父 job 失败并指名依赖。

## 一 设计前置（8 维度）

**① 能力边界**：壳能力（安装编排住 loader `install-ops`）。保底：请求不带 `catalogUrl` ⇒ 行为与现状逐字节一致（缺依赖照旧 parked）；解析失败 ⇒ 父 job 失败、文案指名依赖——不比现状差。

**② API**：**零新方法**——`PluginInstallRequestOpts` 增可选 `catalogUrl?: string`（依赖解析目录）。契约两份同笔（`contracts/linkdesk.d.ts` ＋ `src/core/api/linkdesk-api/types.ts`）；preload 与主进程路由零改动（opts 结构化克隆透传，实测穿线：`namespaces-plugin.ts installWithProgress → IPC.plugins.call → pluginManager 路由 → 池 installPlugin`）。文档：04 分发格式 §requires 两棵树同笔。

**③ 通信**：全走现有安装链——`plugin:installJobs` 快照 ＋ `plugin:installProgress` 事件。依赖进度 = 父 job 行的 `message`（「阶段自带文案优先于 stage 派生」是既有机制，18 档 §五 I.6⑤）。

**④ 壳侧**：纯函数（环守卫/缺失计算）住新模块 `lifecycle-ops/dependency-install.ts` ＋ 单测；挂钩点 = `installPackageFromSource` 解压之后、`loadPlugin` 之前。**单一权威**：依赖声明归一复用 `resolution/dependencies.ts getDependencyIds`（requires ∪ extensionDependencies，不写第二份）；「依赖已已知」判定 = runtime `getKnownManifest`（本格导出复用）。

**⑤ 插件侧**：marketplace 穿 `entry.sourceUrl`（CatalogEntry 自 71k 起携带）→ `startMarketInstall` → opts.catalogUrl；**面板零改**。插件独立铁律：第三方作者只需声明 `requires`，无需改壳。

**⑥ 显示**：父 job 行 message「正在安装依赖：{{name}}」；失败红行文案指名依赖；成功 toast 不变（lifecycle 消费端唯一发声，73h D2）。

**⑦ 配置**：无新配置项——拍板即常驻行为，无开关。

**⑧ 验收**：单测（环/缺失/计划纯函数）＋ `npm run check` 全绿 ＋ CDP 实机（scratch 夹具：虚构 demo id `requires` 一个真实官方插件，经官方目录自动装入目标依赖＋父插件激活——真实接线验证，硬约束 21 豁免口径）。

## 二 关键决策（五条）

- **D1 内联不进队（73q「子包占槽护栏」的结构解）**：依赖安装在父 job **已持有的槽内**进行——不建第二条 job、不进 FIFO。三个父 job 各占槽等依赖排队的经典死锁**从构造上不可能**。护栏 = 本结构＋`dependency-install.ts` 头注成文，不是运行时补丁。
- **D2 递归在线解析**：依赖自己的 `requires` 解压后才可知 ⇒ 逐层在线：装 B（同一父槽）→ 读 B 清单 → B 缺的 C 继续内联。环守卫 = 祖先链栈（A→B→C→A 判红，文案给全链）——与 runtime `detectDependencyCycle` 的 fail-loud 口径一致，但早在安装期就拦。
- **D3 依赖 URL 解析复用 updateCheck**：`packageUpdateCheck(depId, catalogUrl)` 本就返回目录里该插件最新版的 `downloadUrl`（主进程 fetch ＋ 选最大非 prerelease 版）——**零新主进程 API**。解析不到 ⇒ 父 job 失败、文案指名。**解析半径 = 请求来源目录**：壳不内置任何目录 URL（无硬编码），marketplace 传条目来源 ⇒ 第三方源天然同权。
- **D4 已知依赖跳过**：判定源 = loader 已知清单（manifestIndex ∪ pending）。已装但**禁用**的依赖**不自动启用**——父插件照旧 PENDING 等待（诚实可见，用户显式启用才激活）。
- **D5 取消语义**：父 job 取消 ⇒ 同一 `jobId` 的中止钩子打断进行中的依赖下载（复用 `packageCancel(jobId)`）；依赖间隙查取消标提前收手；被取消的父 job 整行吸收（既有语义）。

## 三 边界（v1 不做）

1. **更新腿不接**：更新 A 时新版新增的依赖不自动装（parked 可见，后续格再议）。
2. **目录源安装不接**：`installPluginFromDirectory` 是 dev 流，无 catalogUrl。
3. **`origin: "dependency"` 保留不启用**：内联设计下不存在第二条 job；类型面留待将来（不删——它是 73q 设计时的登记语义）。
4. **73d「依赖子行」的 v1 形态 = 父行 message 行**（进行中可见「正在安装依赖：X」）；逐依赖独立子行（装完留 ✓ 行）不在本格，将来有面板语义需求再立案。
5. 版本约束：`requires` 仍是纯 id 声明、无版本约束（现状），自动装取目录最新正式版。
