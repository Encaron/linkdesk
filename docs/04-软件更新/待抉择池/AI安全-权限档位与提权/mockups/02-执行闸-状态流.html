AI 安全 · 执行闸与提权回路 一张图回答：AI 的一个请求，从哪里进来、被哪三道锁拦、什么情况下放行/询问/拒绝、AI 想升权只能怎么走。
实线 = 正常路径；红色 = 拒绝；黄色 = 等用户；紫色 = 用户批准后写档位（不经命令面）。

Frame 1 · 一个 AI 请求的完整路径执行点只在主进程；池只负责画
AI 客户端（Claude Code / Codex / 脚本） exec / notifyAction / install / requestElevation 经 aiBridge 白名单进入；9 个 op 之外一概不可见
L2 · 命令锁（新增）
目标命令是否 userOnly？ 是 → EPROTECTED，不进下一步。
例：aiPolicy.setMode / aiPolicy.resetToDefault
风险解析
riskOfCommand(id) 壳内建表 > 插件清单 contributes.commands[].risk > 兜底 R1（写类 op 兜底 R2）
唯一判定
decide(aiPolicy.mode, risk) —— 纯函数，16 格矩阵 读不到策略 ⇒ 按 ask（fail-closed）
allow
直接执行 ledger 记 op / command / risk / mode
⛔ 不弹窗
ask
DialogHost 等用户 Enter 允许 / Esc 拒绝 / 超时 10 分钟
不点 = 不执行
deny
EPOLICYDENIED 动作未发生；账本记 deny
AI 可改走提权请求
提权回路（AI 唯一的升权通道）
requestElevation(mode, reason) → 弹框 → 用户点「批准」 批准动作在弹窗 handler 里写 ai.policy.mode（source:"user"）→ 发 onDidChangePolicy → 设置页/状态栏同步
为什么 AI 自提权不可能：① setMode 标 userOnly，runShellCommand 直接拒； ② ai.policy.mode 属 ai.*，配置写命令已拒（settingsCommands.ts:41）； ③ 批准写点在用户点击的 handler 里，AI 没有可调用的「批准」op。
Frame 2 · 三道锁各挡什么缺一不可；任何一层单独失效仍有另外两层
L1配置锁（已存在）

WRITE_BLOCKED_PREFIXES = ["ai."]
挡：AI 用 setConfiguration / clearConfiguration 改档位。
文案：「被管的那个不许改自己的门」。

L2命令锁（新增）

命令元数据 userOnly:true。
挡：即使命令在命令面里，AI 的 exec 也调不到。
改名不失效（不是 id 名单）。

L3批准锁（新增）

写档位只在用户点击的弹窗 handler 里发生。
挡：AI 自己批准 / 伪造批准结果。
AI 只能 requestElevation。

Frame 3 · AI 看到的 vs 用户看到的同一事实，两个视角

AI 侧（可读、可请求）

  • aiPolicy.getState() → 档位 + 风险表 + 受保护命令
  • describe.askFirst → 哪些动作会停下来等人（动手前就知道）
  • requestElevation(mode, reason) → 请求升权
  • 拒绝码：EPOLICYDENIED / EPROTECTED / EUSERDENIED / ESHELLTIMEOUT
  • ⛔ 看不到「批准」入口；⛔ 不改档位

用户侧（可见、可批）

  • 设置页四段控件：只读 / 逐次确认 / 自主 / 完全访问
  • 确认框：允许一次 / 拒绝（Esc/Enter）
  • 提权框：批准（只能你点）/ 拒绝
  • 状态栏徽标：AI 只读 AI 询问 AI 自主 AI 全权
  • 账本：谁在何时改了什么、被拒的也记
Frame 4 · 错误码与 AI 的正确反应防止「失败就重试」把弹窗刷屏
code含义AI 应该AI 不要
EPOLICYDENIED当前档位不允许带理由调 requestElevation原样重试
EPROTECTED命令标了 userOnly提示用户去设置页重试 / 换命令绕
EUSERDENIED用户点了拒绝/关框尊重拒绝，换方案连环弹
ESHELLTIMEOUT无人应答（10 分钟）视为未发生，稍后再问立刻重试（用户可能刚走开）
相位：等人点头期间上报 ask-user 相位，客户端超时后回读相位才不会把「人在犹豫」误报成「对面卡住」——避免用户随后一点头、动作做了两遍（沿用 AI#60）。
