### 为什么现在做——四条实打实的理由

**① 你的真实痛点根因不是 `core:true`，是「没上架」。**

> 用户原话：「**我现在在这个安装版里面，根本就不敢卸载任何的插件**……包括现在安装版里面，它理论上所有插件来源只有网络，卸载就是真真正正从电脑里面卸载掉。所以除了那两个已经上传到插件市场的插件，其余的插件我一个都不敢卸载。」

这个判断是准的。`core: true` 只挡 UI 上的卸载按钮（防新手误点），它不解释「为什么一个都不敢卸」——**原因是卸载之后没有地方能拿回来**。所以解法是上架，而上架的前置是**这只插件得有一个归它自己的仓库**（发布链路的目标仓库 = 工程自己的 `git remote origin`，[publish.ts:2](../../../../packages/plugin-sdk/src/publish.ts)）。

**② 壳仓的 Git 历史被插件迭代污染——这是你第一轮的原始动机。**

> 用户原话：「**这样子一来，不用动我源码的这些 GitHistory 之类的；二来，它们的修改也会更加安全。**」

只要插件源码住在壳仓，改一个设置插件的按钮就是一笔壳仓 commit。E6 期间这还不是问题（都在同一个阶段推进），出厂之后它会天天发生。

**③ 壳仓正在替插件背依赖——而且有一半是「白吃」。**

实测（§1.1）：六只插件里 **4 只 import 了 `@linkdesk/ui`、2 只 import 了 `@linkdesk/contracts`，但声明了依赖的数量是 0 只**——全靠根 `package.json` 的 `workspaces: ["plugins/*"]` + `"@linkdesk/ui": "file:./packages/linkdesk-ui"` 提升上来。**这种「能跑」是假象**：它是壳仓的安装结果，不是插件自足。搬出去第一分钟就会断。

**④ 这件事的架构早已拍过板，缺的只是执行。**

「一个插件一个仓库」不是本层新提的方案——2026-08-17 用户拍板的**多市场源模型**（[01-GitHub-Releases方案.md §六](../03-插件市场/01-GitHub-Releases方案.md)）+ `publish` 实现，**前提假设就是「一插件一仓」**。`first-run-setup` 与 `hello-linkdesk` 两只已经这么跑通了，本层是把剩下的搬过去。

**三个必须记住的实测结论：**

1. **零只插件声明 `@linkdesk/ui` / `@linkdesk/contracts` / `@linkdesk/plugin-sdk`。** `grep "@linkdesk/ui" plugins/*/package.json` 的命中全在 `description` 字符串里，不是 `dependencies`。

| **D1** | 🔴 **一个插件一个仓库**。——不是口味，是 `publish` 的实现前提 | [publish.ts:2](../../../../packages/plugin-sdk/src/publish.ts)：目标仓库 = 工程 origin |

### D2 的辨析——「壳内源码留着」到底留什么

用户原话：「**搬出去指的是它们的单独仓库搬出去，对不对？**……壳内的源码还是留着」。这里必须点破一个混淆——**是三样东西，不是一样**：

| | 是什么 | 搬后住哪 |
|:--|:--|:--|
| **(a) 源码** | `plugins/<id>/src/**` | **只能有一个真相源** → 插件仓 |
| **(b) 构建产物** | `bundled-plugins/<id>.linkdesk-plugin` | **留在壳仓**（出厂发货用，D3 保鲜） |
| **(c) 文档档案** | `docs/05-插件更新/`、各层档案、CLAUDE.md 指针 | **留在壳仓** |

⇒ 用户想「壳里留着」的是 **(b)(c)**——这两样本来就留着、一样不动。**(a) 不能两边都留**：一旦双份，改了这头那头不变，**且没有任何门禁能发现**（内容指纹门禁只管 zip 不管源码）。

### D1 为什么不能是 monorepo（用户其实问过这条）

「在 `linkdesk-marketplace` 里不停添加新插件」= 合集仓 = monorepo 变体，**在现有工具链下跑不起来**，三条硬证据：

1. **Release tag 撞车**：tag = `v{version}` 不带插件 id（[publish.ts:337](../../../../packages/plugin-sdk/src/publish.ts)），且发布前有「tag 已存在 → 拦」（[:431](../../../../packages/plugin-sdk/src/publish.ts)）。同仓两只插件都发 1.0.0，第二只必被拦，报错还骗人「先 bump version 再发」。
2. **目录文件读改写冲突**：`marketplace.json` 走 Contents API 的 read-sha-merge-PUT，代码自己写着「写冲突（409）」（[:529](../../../../packages/plugin-sdk/src/publish.ts)）。
3. **商业语义串味**：详情页 `repository` 字段是「**插件自己的**主页」（[01-GitHub-Releases方案.md §3.2](../03-插件市场/01-GitHub-Releases方案.md)）——全挤一个仓，用户点每只插件的「仓库/问题」都跳到同一处。

**另：`linkdesk-marketplace` 的定位已经定了，是「目录」不是「货架」。** 实查该仓根目录只有 `README.md` + `marketplace.json` 两个文件；§6.7 把它的角色写成「官方目录收录」（作者发 PR 往 catalog 加条目），§6.8 明确「目录是公开文件，任何插件可读」。往里塞源码 = 把索引与内容混成一锅。

⚠️ **但要如实标注：monorepo 并非架构上不可能——VS Code 的内置扩展就是主仓子目录 + 独立发版。** 它走的是「monorepo 子目录发版」的专用流水线；我们改 `publish` 支持子目录发版**也能做到**。**选独立仓的理由是「工具链单一 + 你的原始动机是壳仓历史干净 + 官方插件要能当第三方作者的样板」**，不是「做不到」。详见 §三 风险表。

## 五、验收标准（全层过不过，只看这一张）

| # | 判据 | 怎么验 |
|:--|:--|:--|
| ① | **壳仓 `plugins/` 下只剩夹具**（`panel-demo` / `floating-panel-demo`），发货插件源码归零 | `git ls-files plugins/` 逐条归类 |
| ② | **每只发货插件在壳仓外可自足构建**：`git clone <插件仓> && npm ci && npm run build` 出 zip | 逐仓在一个全新临时目录跑一遍（**不许在壳仓里跑**） |
| ③ | **每只官方插件已上架且默认可见**：在官方目录 `marketplace.json` 里能找到条目（18 条） | fetch 官方目录逐 id 对账 |
| ④ | **出厂种子新鲜**：每只 **`seed:true`（随包）** 插件的箱子版本 = 官方目录最新版 | `check-bundled-freshness` 门禁（7.4 轮产出，已挂 `npm run check`）绿灯 |
| ⑤ | **壳侧绑定归零**：`tsconfig` / `vitest` / `eslint` / `knip` / 门禁脚本里指向发货插件的路径全部摘除 | `grep -rn "plugins/\(editor\|file-tree\|marketplace\|settings\|python\|serial-monitor\)"` 归零 |
| ⑥ | **装载无回归**：安装版启动后**随包 6 只基础插件**全部正常（设置/市场/语言/基础主题/文件树/编辑器），**其余 12 只从市场装得回来且能用**（编辑器跳转 / Python LSP / 串口收发） | 实机 + `lsp:smoke`；**收箱口径见 7.4 轮（[05 §七.6](05-出厂种子保鲜.md)）** |
| ⑦ | **`npm run check` 全绿**且**比 L7 前更短**（插件从壳的编译/测试图里摘出） | 前后各跑一次，记录文件数/用例数变化 |

## 六、不做什么（边界）

- ❌ **不动 `hello-linkdesk` / `first-run-setup` 的本地位置**——它们平铺就是「本地目录无关」的活证据（D6 只管新收编的）。
- ❌ **不重编层号/轮号**（memory `e6-checklist-structure-keep-layers`）——L7 编号即插队序，执行序写在「执行顺序与依赖」段。
- ❌ **不改 `publish` 的「origin 即目标仓」假设**——那是 D1 的支点；要改它等于改走 VS Code 的 monorepo 路线（§二 已记为何不选）。
- ❌ **不引入「插件 ID 硬编码」**——搬出去之后壳更不该知道插件叫什么（硬约束 10 不仅不放松，反而更严：连「哪个插件随包」都只由 D4 那份清单声明，见 [05-出厂种子保鲜.md](05-出厂种子保鲜.md) §五）。
