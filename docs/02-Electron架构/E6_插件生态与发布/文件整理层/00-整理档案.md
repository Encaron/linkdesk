### 为什么现在做——三条实打实的理由

**① 门禁设计好了，但一直没开，没人看守的地方必然膨胀。**

E6#0.6（2026-09-04 用户拍板）造了 `scripts/check-file-size.mjs`：
- `src/` + `electron/` → 800 行红线，**已生效**
- marketplace 插件 → 12 档阈值（views 150 / services 200 / components 150 / styles 300 / index 120），**`SCAN_MARKETPLACE = false` 休眠中**

休眠的代价是实打实的。对照 12 档 §一·一 记的 2026-08-29 实测值：

| 文件 | 2026-08-29 审计值 | 2026-09-11 实测 | 变化 |
|:--|--:|--:|:--|
| `styles/MarketplaceSidebar.css` | 377（🔴 已超限，注「最先拆」） | **680** | ↑ 303 |
| `views/DetailView.tsx` | 未建（30.11a 才迁入） | **1258** | 8.4× 超限 |
| `services/marketplaceShared.ts` | 180（⚠️ 「接近上限…可留」） | **779** | ↑ 599，3.9× 超限 |

**该拆的第一个文件没拆，反而翻倍。** 这正是 V2 教训（MainWindow.xaml 2738 行 / code-behind 3866 / Display 3775）的复现路径——一次性审计治标，机械门禁治本；**门禁不打开 = 只治了一次标**。

**② 门禁的开关挂在一个「已完成、但没产出该产物」的任务上。**

`check-file-size.mjs` 第 22 行注释原文：

> 门开关——marketplace per-scope 档仅在 **#30.11 拆完 MarketplaceSidebar.css（377 > 300）** 后翻转 true。

而 E6#30.11（a-f）**已全部 ✅ 收官**（2026-09-05 前），收官行里没有一条动过 `MarketplaceSidebar.css`。**任务完成了，但它承诺的产物不存在** → 门禁永远等不到翻转条件，静默休眠到今天。

这是 **E6#81④ 同一类 bug 形的第二次现身**（见 memory `snapshot-shadows-truth-bug-class`）：

> **判定挂在别人的一次性产物上**——问「这个判断依赖的那份数据，是谁写的？那个写入者一定会先跑吗？」答不上或答「不一定」⇒ **判定自己现算**。

当时是详情页的版本显示，这次是门禁开关。**同一个形，换了个地方又长出来一次**——所以本层把门禁开关改成**自己看文件行数**（拆完自然绿），不再挂任何任务的完成状态。

**③ 官方插件是第三方作者的教具，超限 = 教错。**

[09-插件目录规范](../../../03-插件制造/09-插件目录规范.md) 开篇原话：「**官方插件模板——第三方开发者看任一官方插件，目录结构一致。**」
E6 的核心验收之一是「**10 分钟写出第一个插件**」（memory `e6-10min-first-plugin`）。

marketplace 是**最大、最像样、最会被抄**的那只官方插件（**产线 7009 行 / 27 个文件**），它现在的 `views/` 是 9 个文件平铺、`services/` 是 12 个文件平铺、单个视图 1258 行。**作者照着抄，就抄到一套超限结构。**

**① feature-folder，不许拆成更平铺**（E6#0.4d / #0.6c / 12 档 §一·〇 原话）：

> 拆完必须 feature-folder（聚合器 + 子模块），参照 preload-pool / linkdesk-api 先例——**不许拆成更平铺**。
> 超限走 feature-folder（domain 内聚合器 + 子模块），**禁止拆同 domain 平铺多文件**。

**② UI 功能域 = 文件夹**（壳目录规范 §8 反模式表）：

> 「这个界面/控件/页面只有几行，平铺放着吧」 → **UI 功能域 = 文件夹**——界面/控件/页面一律建夹（tsx + css + 测试 + 子节同夹）。

**③ 外部消费方 import 路径零变更**（0d.10-x 十一个先例的共同验收项）：
聚合器门面 + 同名夹的标准做法 = **聚合器文件保留原名**，子模块进同名夹；`import "./X"` 命中文件、`import "./X/Y"` 命中子模块。

### 决策 ①：聚合器阈值（views 档 150 放不放行）

**问题：** feature-folder 的**聚合器文件**（如拆分后的 `views/detail/DetailView.tsx`）天然装 state + 编排 + JSX 组合，很难压到 150 行。但门禁按「首段 dir」取档，`views/**/*.tsx` 一律 150。

**推荐：** 放行**同名夹聚合器**到 **role 档 × 2**（views → 300），并附硬条件：
- **只对「有同名夹的聚合器文件」生效**（`views/detail/DetailView.tsx` 存在时才有 `views/detail/DetailView/`）
- 聚合器**不许含纯逻辑**——纯函数 / 数据变换 / 类型定义必须下沉子模块（0d.10-8 同款）
- 门禁实现 = 探针「同名夹是否存在」，存在则上聚合器档

**若不同意：** 则聚合器必须压到 150——DetailView 的 JSX 会被切成更多子组件，可读性反而下降。**需要用户明确选。**

### 决策 ②：`views/` 建子夹的分组轴

> 🔴 **订正（2026-09-11，E6#87 前置）：本节结论有效，但「按容器分」这个命名有误导，已改口径为「按落位块分」。**
> 本节是被读的历史记录，**原文保留不动**。要读的是 [12 档 §一·〇①](../03-插件市场/12-插件目录与UI细节.md) 的现行说法：
> - 分组轴 = **视图落在界面哪一块**（侧栏 / 主区 / 确认弹窗）——**不是** `contributes.views` 的 key。
> - 两条轴在 marketplace 上**恰好重合**（5 个侧栏视图 = 5 个侧栏容器），所以当年叫「按容器」看不出问题；**换一个插件就不重合了**（如 settings 只有 1 个容器却有多块）。
> - 🔴 **例外：只有一个落位块的插件不建这一层**（建了只是多一层没有信息量的夹，还要同步改 `render`）⇒ **E6#87 的四个插件 `views/` 全部保持平铺**。

**原文（按容器分，与 `plugin.json` 的 `contributes.views.{容器}` 一一对应）：**

```
views/
├─ sidebar/     ← contributes.views.marketplace（5 个）
├─ detail/      ← contributes.views.main 的详情（DetailView + 同名夹）
└─ ConfirmInstall.tsx   ← contributes.views.main 的确认（单独一个，或与 detail 同夹）
```

**理由：** 现有 4 个 CSS 已经按这个轴分好了（`MarketplaceSidebar.css` 被 5 个侧栏视图 import、`MarketplaceDetail.css` 只被 DetailView import、`MarketplaceConfirm.css` 只被 ConfirmInstall import）——**作者心里的分组本来就是这三块，只是没落到目录上**。且容器 = plugin.json 的声明单位，改名时两边对齐。

**备选轴：** 按功能域（search / installed / explore / detail / confirm）——更细，但 5 个侧栏视图各自成夹 = 「一个文件一个夹」，与「UI 功能域 = 文件夹」的精神相反。

### 决策 ③：门禁扩域到全部官方插件

**问题：** `check-file-size.mjs` 第 43 行明写「plugins/ …不在此门禁」，第 24 行明写「编辑器/file-tree/settings 等插件同界**不扩域（清单未授权）**」。

**推荐：** **扩。** 本层 = 授权源。给**全部官方插件**（`plugins/*/src/**`）上 per-scope 档，阈值取 12 档同一套，并补两条既有目录但门禁没登记的：**`.css` 恒 300**（不看目录，这样 settings 的 co-located `views/SettingsView.css` 也管得住）；**`views`/`components`/`hooks`/`utils` = 150 · `services` = 200**（`hooks`/`utils` 是 09 规范已有房间，只是门禁漏登记）。完整规则表见 [05 §二](05-门禁扩域与验收.md)。

**若不同意：** `serial-monitor/src/index.tsx`（1642 行）拆完之后**没有任何机制阻止它再长回去**——这正是 MarketplaceSidebar.css 从 377 涨到 680 的复现路径。

### 决策 ④：settings 插件的测试位置

**问题：** [09-插件目录规范](../../../03-插件制造/09-插件目录规范.md) 明写「**`__tests__/` 是插件层约定**」，但 settings 插件把 6 个测试**同夹**放了（`SettingsView/*.test.ts`、`keybinding-settings/keybindingRowSort.test.ts`），走的是**壳**的做法。marketplace / file-tree / editor / serial 四只都规规矩矩用 `__tests__/`。

**推荐：** **迁到 `__tests__/`**，与另外四只一致。理由 = 09 号规范开篇那句「第三方开发者看任一官方插件，目录结构一致」——**五只插件里四只一个样、一只另一个样，就是不一致**。

### 决策 ⑤：12 档的 views 上限 150 是否维持

**问题：** 拆完后 `ExploreView.tsx`（现 325）能否压到 150？`SearchView.tsx`（现 203）呢？如果压不到，是拆得更碎，还是抬阈值？

**推荐：** **维持 150 不动**，靠拆子组件达成。如果某个视图确实拆不到 150，**走 `@E6#0.6b` allowlist 拍板制**（已有机制，须用户逐例放行 + 文件头注 token）——**不要为了省事整体抬阈值**。

## 六、风险清单——拆的时候可能炸什么

> 每条都给「症状 → 根因 → 规避」。**3.6 层每一轮开工前先过一遍本表。**

### 风险 1：`plugin.json` 的 `render` 路径不同步 → 视图白屏

- **症状：** 点开市场侧栏某视图，空白 / 控制台报动态 import 失败。
- **根因：** 池按 `_renderPath` 动态 import（[contributions.ts](../../../../src/pluginLoader/contributions/contributions.ts) `${resolvedRoot}/${viewDef.render}`）。**文件搬了、`plugin.json` 没改 = 路径指向不存在的文件。**
- **规避：** 搬运任务里**必须同一步改 `plugin.json`**；改完 grep 核对：每个 `render` 值都能在盘上找到文件。

### 风险 2：SDK bundle key 撞名

- **症状：** 打包产物里出现 `DetailView_.bundle.js`（多了下划线后缀）。
- **根因：** [vite-config.ts:115](../../../../packages/plugin-sdk/src/vite-config.ts#L115) `key = basename(rel, extname(rel))`——**key 只取文件名，不含目录**。同夹两个同名文件 → `while (usedKeys.has(key)) key += "_"` 兜底改键。
- **规避：** 方案里**不安排同名文件进同一夹**。这条同时是好消息：**bundle 名只由文件名决定，搬子夹对构建零影响**（已验证）。

### 风险 3：模块级单例被拆散 → 跨视图不同步 / 订阅丢失

- **症状：** 侧栏装了插件、主区详情页不刷新；或搜索词在侧栏变了、另一个视图没跟上。
- **根因：** `marketplaceShared.ts` 里有三个模块级 `Set` 监听器（`_searchListeners` / `_dataListeners` / `_catalogListeners`）+ 多个 store。**拆文件时若同一份状态被复制到两个模块，两个模块各持一份 = 各说各话。**
- **规避：** 照 0d.10-8 先例——**每个模块级 mutable 状态各归单域属主**，跨域读走公开 accessor；拆完 grep 确认每个 `_xxxListeners` 只在一处声明。

### 风险 4：循环 import

- **症状：** 运行时某导出是 `undefined`；或构建报环。
- **根因：** 代码里已明确记录 `updateDiscovery` 是 `marketplaceShared` 的**下游**（「不 import marketplaceShared——那是本模块的下游，import 会成环」）。
- **规避：** 拆分组时**保持依赖单向**：底层（纯函数/类型）→ 中间（store/service）→ 上层（编排/命令）→ 视图。拆完跑 `npm run check`（vitest 会暴露 `undefined`）。

### 风险 5：serial-monitor 的 CM6 双栏失同步（硬约束 17）

- **症状：** 拆完主接收栏有内容、HEX 栏空；或标签页切换后第二帧跳空白。
- **根因：** `index.tsx` 里主栏 + HEX 栏是两个常驻 `EditorView`（keep-alive，CSS 显隐），靠 `useRef` + `Compartment` 管；`renderLine` 一处同时喂两栏。**拆 hook 时若 ref 归属错、或渲染决策误用 ref（硬约束 17），两栏就散。**
- **规避：** 这轮**最后做**（3.6.4）+ 拆前先用 CDP 录一遍双栏正常态；拆完逐项对照。**CM6 相关代码只搬家、不改生命周期逻辑**。

### 风险 6：测试 fixture 用了真实插件名（硬约束 21）

- **症状：** 测试通过，但读者/AI 误以为存在运行时引用。
- **根因：** 拆测试文件时新增/搬移 fixture。
- **规避：** 一律用虚构值（`demo-plugin` / `demo-view` / `Alpha`/`Beta`）。**只在验证真实接线（loader/FactorySlots 等）时才用真 id。**

### 风险 7：拆完聚合器自己超门禁

- **症状：** `npm run check` 红，报聚合器文件超限。
- **根因：** E6#0.4 验证项原话——「**拆出聚合器超 800 = 0.4 拆坏，门禁立即抓**」。
- **规避：** 聚合器按决策 ① 的档位（role 档 ×2）控制；拆完先跑门禁再提交。

### 风险 8：版本轴算错 / 随包 zip 没重建（硬约束 22）

- **症状：** 插件源码变了、版本没动 → `check-bundled-version-bump` 红；或装了旧 zip。
- **根因：** 改 `plugins/*` = **插件轴**（各自 bump）；改 `src/` `electron/` = **软件轴**。见 memory `version-axes-separated`。
- **规避：** 每轮收尾跑 version-bump skill 判定 + 重建随包 zip（memory `stale-sdk-built-plugin-zip`）。

### 风险 9：allowlist 过期豁免报错

- **症状：** `npm run check` 报「过期豁免」。
- **根因：** 门禁会检查被豁免文件的头注 token `@E6#0.6b`；**已瘦身回阈值内的文件若还挂着豁免 = 报错**。
- **规避：** 拆完瘦身的文件**若曾在 allowlist 里，必须移除条目 + 删头注 token**。

### 风险 10：dev 模式插件源码树 glob 失效（**已排除，记录备查**）

- **核查结论：** 已实地核对——[state.ts:68](../../../../src/pluginLoader/resolution/state.ts#L68) 的 `pluginManifestRaw` glob 只扫 `plugins/*/plugin.json`（与子夹无关）；`pluginModules` / `viewModules` 入口 glob 已随 E6#62a/#62b **退役**，视图加载唯一执行者 = 池按 `_renderPath` 动态 import。⇒ **views/services 建子夹对 dev 零影响。**

## 七、本层不做什么（边界）

- **不改任何功能行为。** 本层 = 纯组织手术（搬家 + 拆分 + 门禁），**零新增 `window.linkdesk.*` / `contributes.*` 面**。
- **不推翻 E6#0.4 的拍板。** 已判「达标不拆」的文件（`contributions.ts` / `appearance.ts` / `tabCallbacks.ts` / `ViewContainerService.ts` / `coreCommands.ts` / `window-manager.ts`）**本层不动**，除非出现新理由并经用户拍板。
- **不做「顺手改文案 / 顺手改样式」。** 与拆分无关的改动一律不做——**混在搬运 commit 里 = 审查时分不清哪行是搬家、哪行是新功能**。
- **不碰第三方插件。** 只动 `plugins/` 下的官方插件。
