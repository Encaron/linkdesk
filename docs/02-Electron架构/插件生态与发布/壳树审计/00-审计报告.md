## 三、#0.4 全树大文件复核（核心：两真候选草案的证据修正）

### 3.1 真候选草案为何修正——共性发现

清单预写草案（2026-08-30）按**行数 + 职责分段名**判定两候选为「多职责真候选」。本次审计逐文件读结构，两候选存在清单草案**未料及**的共同事实：**两者都是「共享可变状态核心的内聚模块」，而非多独立能力的函数聚合**。草案的 feature-folder 切片会横切共享状态核心 → 需共享 state 叶模块 + 协调聚合器（聚合器模式退化为协调器）→ 与 0d.10-11「高内聚类不硬拆」先例（ViewContainerService，清单 0.4c 列 492 单类达标）及 codex「大但单职责 → 拆=返工」字面冲突。细节分别如下。

### 3.2 window-manager.ts（585）——类形态 · 中央共享注册表

**现状结构（实证）：**
- 组织形态 = **单类** `export class WindowManager`（64-585），非函数平铺。
- 类字段 = 中央共享状态：`poolWindows = Map<string, PoolWindowEntry>`（注册表）+ `ipcBridge` + `memoryTimer` + `shellClosingWindows` + `_focusedWindowId`。
- 40+ 方法成 5 方法族：**生命周期**（createMainPool/createPoolWindow/createPoolView/destroy*/rebuildPool/closePoolWindow）/ **bounds 同步**（syncPoolBounds/pushWindowBounds/pushAll/notifyShellWindowBoundsChanged）/ **IPC push**（pushLayout/pushQuickPick/pushToast/pushDialog/pushFloatingPanel/pushAdsorbHint/sendShellPoolReady…）/ **内存监控**（checkMemoryPressure/startMemoryMonitoring + MEMORY_PRESSURE_THRESHOLD）/ **查询 getter 族**。所有族经 `getPoolEntry()` 读写同一 `poolWindows`——共享注册表把各方法族绑成一个内聚状态机。
- 结构性耦合证据：crash-recovery.ts 头注声明「WindowManager 反向 import 本模块 cacheLayoutSnapshot——单向依赖，无环」——E5.7/E5.8 刚稳定的崩溃恢复 DI 接线。

**草案可行性评估：**
- 草案 4 子模块（pool-lifecycle/ipc-push/bounds-sync/memory-monitor）把**一个中央注册表对象的方法族拆成 4 个兄弟文件** → 每文件都要访问 `poolWindows`/`ipcBridge`/`this` → 状态碎片化，子模块互相依赖对方 state，耦合不降反升。
- **外部消费方零变更验收行破坏：** 消费方全在 electron/ 主进程 NodeNext 显式 `.js` 域——实证 6 处 specifier（main.ts / ipc-bridge.ts / dialog-handlers.ts / file-handlers.ts / plugin-view-handlers.ts / crash-recovery.ts 全写 `./windows/window-manager.js`）。NodeNext 下目录→index **不解析** → folder 化每处须改 `window-manager/index.js`，违反清单验证行「外部消费方 import 零变更」。
- 内存监控确是可摘叶模块（只经回调触 rebuild/destroy，不碰 poolWindows），但约 40-60 行，摘除后 585→~530，导航/行数净收益边缘。

**判定：改判「达标不拆」。** 类形态 + 中央共享注册表 = 高内聚单域（pool 窗口注册表管理）；585 < 800 机械门禁线（#0.6 不拦）；对照 0d.10-11 ViewContainerService 先例与 codex「大但单职责→拆=返工」。E5.8-fresh delicate（崩溃恢复 + 单 Pool 生命周期）拆 = 真 bug 风险换零功能收益，违背本轮「保证无错」。

### 3.3 ConfigurationService.ts（572）——函数平铺 · 单一状态机

**现状结构（实证）：**
- 组织形态 = **函数平铺模块**（15+ export function over 模块级私有 state）——形态上比 window-manager 更接近「可拆」。
- 但私有 state 高度互锁（读头 1-58 实证）：`_userSettings`/`_workspaceSettings`/`_workspaceRoot`/`_initialized`（三层缓存）+ `_userPersistChain`/`_workspacePersistChain`/`_pendingUserPersists`（E5.8#61 持久化串行队列）+ `_persistDebounceTimer`/`_persistWaiters`/PERSIST_DEBOUNCE_MS（#89 E3 去抖）+ `_changeListeners` + `_configApplier` + watcher 计时器——**读缓存→取值→改→去抖持久化→reload→diff→监听发射全走同一核心**，是单一「配置服务」状态机（对标 VS Code IConfigurationService），非多独立能力。
- 对照真 folder 先例：preload-pool / linkdesk-api / IpcBridgeHandler 每个文件是**独立能力、各持自有 state、零跨文件共享可变核心**——ConfigurationService 的 5 草案切片全共享同一 mutable 核心，不具备该先例的独立性。

**草案可行性评估：**
- 草案 5 子模块（applier-registry/value-access/change-listener/settings-io/cache）映射函数分组**在字面上成立**（每组确有专属职责标签），src/ 侧 bundler 无扩展名目录→index 解析，10+ 消费方 specifier 全指向 `.../configuration/ConfigurationService` → **folder 化消费方零变更成立**（与 window-manager 的 NodeNext 侧不对称）。
- **但**：5 切片共享缓存叶（cache）+ 写管道，跨文件必须反复 import 共享 state 模块；reload→diff→emit 是跨切片编排 → 聚合器 index 从「纯 re-export」退化为「持编排逻辑的协调器」，背离 feature-folder 先例（聚合器=纯透传）。
- 文件内已用 `/* ── 三层缓存 ── */` 等 section banner 组织——导航已可用，拆分净收益为边缘导航改善。

**判定：改判「达标不拆」。** 大但单职责（配置服务全域）= codex 判据字面的「拆=返工」情形；对照 0d.10-11。E5.8#61 持久化串行队列（文件损坏级 bug 刚修）+ #89 去抖均为 delicate——拆 = 跨文件 state 线程风险。

> 🔄 **2026-09-04 此判定被推翻（用户挑战后改判拆）**：0d.10-11 判据只适用于**单类**（this.* state），ConfigurationService 是**平铺函数模块**（模块级 state）——正确先例 = 0d.10-8 KeybindingRegistry（folder 化「状态单域属主 + accessor + 单向无环」）。E5.8#61/#89 的 delicate 不构成不拆理由——folder 化可保持**逐行等价**（live-ref accessor 保留去抖 fire 时读终态语义）。最终 = §六 ③ feature-folder 拆。§3.3 保留作快照。

## 六、用户挑战 → 拍板 A′（决策记录 + 三项手术执行）

### 6.1 挑战与两处纠错

**2026-09-04 拍板建议 A 后，用户挑战：**
> 「你是怕麻烦还是真的不用整理子文件夹？这涉及到未来软件的发展问题。」……「未来添加新功能、新添加方法之类，很多地方都需要加文件，这时候如果一直平铺，一来难以找到相应文件，二来不利于新功能拓展，所以说出你的推荐。」

自查发现两处**真错误**（非「怕麻烦」——是判据套错 + 概念混淆）：
- **① 误套先例**：用 0d.10-11（**高内聚单类**不硬拆，ViewContainerService 先例）论证 `ConfigurationService.ts` 不拆——但它是**平铺函数模块**（KeybindingRegistry 形态）≠ 单类。0d.10-11 管「单 CLASS over 共享 this.* state」；ConfigurationService 是 0d.10-8 管「FLAT FUNCTION MODULE over 模块级 mutable state」——**后者 folder 化正是先例教法**。§3.3「共享可变状态核心」观察没错，错在把 KeybindingRegistry 形状套进 ViewContainerService 判据。

## 七、目录守则（向前原则——本报告沉淀，E6 后续加文件照此）

> 用户挑战的本质 = 平铺让「未来加功能加文件」难以定位与扩展。本守则把「何时建夹」从拍板制变成判据制——
> 判据命中即建夹，不用等膨胀再审计。

**建夹（文件夹收纳）的判据——命中任一条即建夹：**
1. **共享词汇簇（coupling topology）**：多个文件共用同一批术语/类型/策略表/注册表（互引或共享声明）→ 同夹收纳。实证：window 族（windows.ts 策略表 ↔ windowHost 注册表 ↔ windowRelocation 搬迁）/ ConfigurationService 域（config 声明 ↔ applier）。
2. **增量堆积位（accretive growth）**：该域「加一个东西 = 加一个新文件」是常态（未来扩展明确在此发生）→ 建夹给增长位。实证：窗口模式加成员/面板形态加款式。判据②允许在**尚无文件数压力**时前瞻建夹——正是本报告 window 域建夹的正当性（8 文件平铺检查时无硬触发，但增长位明确）。
3. **功能域=文件夹（0d.10-3 §2.5 既有）**：域内成员共享聚合器被消费，或域内职责天然多文件。

**留平铺（不建夹）的判据：**
4. **独立叶子**：单 hook/单纯函数/单 schema 文件，消费方就一个（常是被聚合器直引），且该文件不是共享词汇簇成员、未来也无同簇兄弟要加入——与七功能 hook 同型。实证：panelReveal/panelHost/panelDrift 等单 hook 文件本次留平铺。

**判据冲突时：** 「大文件拆不拆」照 0d.10-11（单类高内聚不硬拆）/0d.10-8（平铺函数模块 folder 化）两先例——**组织形态（类 vs 函数平铺）决定适用先例**，行数不决定。`#0.6` 机械门禁（800 行）只管超限红旗，不管建夹——建夹是导航/增长决策，非行数决策。
