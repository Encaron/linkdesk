# 第一部分：events 归一化（#77a #77b）

## 背景

#77 给 `preload-plugin.ts` 加了 `events.on/emit`，让插件能收发大厅事件。串口监视器收到数据后 `emit('serial:rawData', ...)` → 主进程广播 → 所有插件 WebView 可订阅。

测试时发现壳崩溃，根因：串口监视器有**双份渲染**：

| 实例 | 运行环境 | preload | events.emit |
|------|---------|---------|:--:|
| WebView 实例 | 独立 WebContentsView | preload-plugin.js | ✅ 存在 |
| React fallback | 壳主窗口 DOM | preload-shell.js | ❌ 不存在（#77 前） |

壳里的 fallback 实例调 `events.emit` → 壳 preload 没这个方法 → 崩溃。

### 临时修复（已完成）

给 `preload-shell.ts` 补了 `events.on/emit` + `plugin:push` 监听器。不崩了。但留下两个问题：

1. **未归一化**：`events.on/emit` 代码在 `preload-plugin.ts` 和 `preload-shell.ts` 各写一遍——复制粘贴。改一处忘一处 = 又一个缝 bug。
2. **重复发射**（假设）：两个实例都收到串口数据 → 两个实例都 `emit` → 协议插件收到**重复数据**（后来实测推翻——见下文）。

## #77a：events 归一化——提取共享模块

### 目标

一份代码，两处 import。消复制粘贴。

### 设计

新建 `electron/event-system.ts`：

```typescript
export function createEventSystem(ipcRenderer, options): { on, emit }
```

- `subscriptions: Map<channel, Set<callback>>` ——内部管理

## #77b：双份渲染无害共存——fallback 只渲染不发射

### 设计意图

shell fallback 只做安全网该做的事——渲染 UI 骨架。数据和事件留给 WebView 实例处理。

判别方法：`isPluginWebView` = `typeof window.linkdesk?.pluginViews?.notifyReady === 'function'`。`onData` 回调中，仅 WebView 实例发射到大厅——fallback 不发射。

**为什么安全网仍然有效：** WebView 崩了 → `notifyReady` 不会被调用 → React fallback 照样渲染 UI → 用户至少能看到界面框架。数据虽然不推大厅，但自己的显示仍然正常。

### 🔥 实测推翻假设

**实测推翻了设计假设。** 串口数据不是"两处都到"——只到**打开串口的那个 webContents**。当前场景下数据到壳 → emit 在壳 → 不重复。#77b 的守卫反而把唯一管道堵了。

**已回退守卫**（commit `3eea884`）。正确的结论：
- 串口数据只到一个地方（谁 openPort 谁收数据）→ 不存在重复 emit
- 崩的根因是壳缺 `events.emit`（#77a 修复），不是重复
- #77b 的设计文档保留作为记录——假设如何被推翻、为什么守卫是错的

# 第二部分：双份渲染根因分析（#81）

## 一、什么是双份渲染

LinkDesk 的插件同时存在于两个地方：

| 实例 | 位置 | 目的 |
|------|------|------|
| WebView 实例 | 独立 WebContentsView | 多 WebView 架构——进程隔离 |
| React fallback | 壳主窗口 DOM | 安全网——WebView 崩了/没加载完时有 UI 兜底 |

历史原因：E3a 建了多 WebView 基础设施，但不敢立即关掉壳里的旧渲染——怕 WebView 没就绪用户看到空白。于是留了"渐进增强"：WebView 覆盖在 React fallback 上面，用户看到 WebView；WebView 失败时 fallback 可见。

**设计意图是好的——渐进增强不是断崖切换。但实现有缝。**

## 三、三条根因

| 根因 | 症状 | 修复策略 |
|------|------|---------|
| ① 双份渲染同时存在 | 壳 fallback + WebView 各跑一份 SerialContext，互不知情 | **方向 B**：组件级生命周期 + 引用计数——不判断环境，mount 注册/unmount 清理 |
| ② `_initIPC()` 模块级永不清理 | 壳切空 div 后 IPC 监听器仍存活 | **方向 B 已修**：`_registerIPCListeners`/`_unregisterIPCListeners` 走 React useEffect |
| ③ 串口数据路由不确定 | 数据到壳还是 WebView 取决于谁先 openPort | **不修复**——#77b 实测推翻假设：数据只到一个地方 |

## 四、之前所有尝试为什么失败

| 尝试 | 思路 | 失败原因 |
|------|------|---------|
| #58d | 删 React 渲染 | WebView 还没激活 |
| #58e 第一版 | ref/state 异步关 | 时序窗口：关 React 时 WebView 未就绪 |
| #58e 第二版 | ready 信号驱动 | ready 前模块级代码已初始化，清不掉 |

**共性问题：试图从外部"关掉"一份渲染，而不是从内部让模块知道自己该做什么。**

## 五、修复策略——方向 B：组件级生命周期 + 引用计数

拆 `_initIPC` 为三函数：

- `_initOnce()` —— 一次性数据拉取（listPorts/getStatus），模块级 guard
- `_registerIPCListeners()` —— 注册 onData/onStats/onSystem，引用计数（第一个 consumer → 注册）
- `_unregisterIPCListeners()` —— 减引用，最后一个 consumer unmount → 全清

壳 fallback 和 WebView 用同一套逻辑——不判断运行环境。壳切空 div → ControlPanel unmount → 自动清理监听器 → 零僵尸。

**方向 A（环境感知）已废弃**——isPluginWebView 判别治标不治本，新插件作者不知道规则照样写出同款 bug。
