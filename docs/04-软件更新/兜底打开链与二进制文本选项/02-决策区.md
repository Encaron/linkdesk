## D1 · 点「仍旧以该编辑器插件打开」之后，能不能编辑 / 保存？🔴 会动数据安全边界

| | 甲 · **只读预览** | 乙 · 可编辑可保存（对齐 VS Code） |
|---|---|---|
| 行为 | 内容画出来（乱码照实显示）＋ 能搜能选，**保存禁用** | 完全当普通文本文件，可改可存 |
| 风险 | 零（原文件不可能被写坏） | **写回即把原文件抹平**（把乱码写进 `.pdf`） |
| 代价 | 看不到「编辑」的可能（但二进制本来也没有可编辑的意义） | 至少要一次保存前确认；否则是隐形数据杀手 |
| 落点 | Monaco `readOnly:true` ＋ 命令面同挡（T7 甲） | 同上但放开写 ＋ 写前确认 |

**我的推荐：甲。** 理由：「强制文本打开」的实际用途是**看一眼 / 搜个串**（找 header、确认版本），不是改二进制；而 T1 当年立这条守卫的原文就是「写回去就是把原文件抹平」。⛔ 二选一都不许做成「静默可写」。
**不拍会怎样**：B 半实现卡住（半个 T5 + T7 无法落）。

**【拍板】**：＿＿＿＿＿＿（甲 / 乙）

## D2 · 装了阅读器之后，用户还有没有路「强制用编辑器看」？🔴 用户诉求的边界

**事实**：`resolveOpenTarget` 的覆盖档只认**声明者**（指向者必须在该扩展名的声明表里）；而「打开方式」面板的数据源 `listHandlersFor(ext)` 只列声明者，`OpenWithService.assembleHandlers` 在 `entries.length === 0` 时直接返回空 ⇒ **`.pdf` 一旦有阅读器声明，编辑器就不在候选里**，面板里选不到它。

| | 甲 · 面板补一行「以文本方式打开」 | 乙 · 不做（现状：先卸载阅读器） |
|---|---|---|
| 行为 | 「打开方式…」对任意扩展名都多列兜底挂牌者一行（选了即 `forcedText` 打开） | 提示页第三颗钮只在**已经落到编辑器**时可用 |
| 缺口 | 覆盖表写入需一并放宽（现在只能写「声明者」）；面板/覆盖/仲裁三处同改 | **用户装完阅读器就再也没有强制文本的路**（与「不该被抹除」的诉求相抵） |
| 体量 | 中（壳侧 3 处 ＋ 用例） | 零 |
| 参照 | VS Code：`Reopen with… → Text Editor` 恒在 | — |

**我的推荐：甲，但可后置**——本件先把 A 半 ＋ 第三颗钮落地（用户当场点名的正是这两件），甲另立一小格（T11）。
**不拍会怎样**：不影响本件主体落地；但「装了某 PDF 插件后完全无法文本打开」会在用户下次试用时再冒出来。

**【拍板】**：＿＿＿＿＿＿（甲 / 甲后置 / 乙）

## D4 · 所有 text-fallback 挂牌者都没了时，兜底落 `welcome`——要不要把 E22 的「提示页语义」做真？

**事实**：`FALLBACK_PLUGIN_ID = "welcome"` 是**兜底兜底**（编辑器被卸载/禁用时）。而 welcome 视图**不认** `opts.filePath`、不画任何「这个文件打不开」的提示 ⇒ 用户看到的是一个普通欢迎页（**又一个静默死胡同**，与本件前半同型）。

| | 甲 · 做真（welcome 在带 filePath 的兜底语境画提示） | 乙 · 不做，登记进池 |
|---|---|---|
| 触发面 | 极小（要把编辑器在内的所有挂牌者都卸掉） | — |
| 体量 | 小-中（welcome 插件 ＋ 载荷约定：怎么把「我是被当兜底叫来的」告诉它） | 零 |

**我的推荐：乙（本件不做，登记进 [待抉择池](../待抉择池/)）** —— 它不是用户今天遇到的路，且涉及「兜底语义要不要跨插件传递」的新约定，值得单独一案。
**【拍板】**：＿＿＿＿＿＿（甲 / 乙）

## D6 · 壳渲染进程的兜底恒等于 `welcome`（进程内表为空）——本次根治吗？

**事实**：`FileAssociationService` 是**双进程共用模块**，但 `registerFileAssociation` 只在**主进程**（插件 manifest loader）被调 ⇒ 壳渲染进程的 `_associations` / `_roleHolders` **永远空** ⇒ 渲染进程里 `resolveFallbackTabType()` **恒返回 `welcome`**（`tabs.ts` / `useOpenPathIntake.ts` 两处兜底都吃它）。

| | 甲 · 根治 | 乙 · 不根治（本次） |
|---|---|---|
| 做法 | ①把角色挂牌镜像同步进渲染进程；或②把这两处兜底改成「异步问主进程」 | 保持现状：IPC 恒有答案后这条路基本不可达（仅 IPC 失败 / 旧壳时可见） |
| 代价 | 新增一份跨进程同步面（主↔壳），比本件大 | 留一个"结构性死兜底" |
| 风险 | 中（新同步面 = 新漂移点） | 低（是最后防御，不是主路） |

**我的推荐：乙（本次）+ 把该结构性隐患落在档案里**。理由：A 半修好后，兜底档只在异常路径被吃到；为它引入新同步面不划算。
**【拍板】**：＿＿＿＿＿＿（甲 / 乙）
