## 一、FileService（~80 行）

### 1.1 为什么是基础设施

**底层：** `window.linkdesk.filesystem.*`（Electron preload 暴露的 Node.js fs 封装）。

### 1.3 旧代码归一化（必做）

**🔥 这是阻塞项，不是"机会式"。** 不归一化 = 模式 1（持久化错乱）16 个 bug 全部保留。

FileService 建成后，以下路径必须归一化：

| 旧代码 | 当前 I/O 方式 | 归一化为 |
|------|------|------|
| `ConfigurationService`——读写 `settings.json` | `_fsApi.readTextFile` / `writeTextFile`（Tauri fs 动态 import） | `FileService.readFile` / `FileService.writeFile` |
| `LayoutService`——读写 `v3_layout` | `StorageService.read` / `write`（localStorage + Tauri fs 双写） | `StorageService` 内部改走 `FileService`（localStorage 保留作为同步兜底） |
| `StorageService`——底层 I/O | Tauri fs 动态 import | `FileService`——StorageService 管路径，FileService 管 I/O |

**归一的理由：**
- B66 教训：`PluginStateService` 和 `ConfigurationService` 往同一个 `settings.json` 写——互相覆盖
- B67 教训：`quickSends` 绕过 ConfigurationService 走 PreferenceService——多套路径
- B68 教训：`beforeunload` 和 `LayoutService` 各写各的 `v3_layout`——两套序列化路径不同步

**归一后：所有 fs 操作走 FileService 同一实例——不存在"A 写 B 不知道"的问题。**

**⚠️ 如果改动超过 20 行就拆任务——不能记 TODO 留到 E3d。** E3d 是 Profile + activationEvents——不是"清理残骸"阶段。

## 五-B、KeybindingResolver——冲突检测与优先级仲裁（~30 行）

> 来源：再审计 D3。VS Code 的 `KeybindingResolver` 是快捷键系统的一半——没有它，两个插件声明同一个快捷键 → 谁后注册谁赢 → 用户不知道为什么另一个不工作。

### 5B.1 问题

`KeybindingRegistry.registerKeybinding()` 当前行为：同 key 字符串 → 按 source 优先级静默覆盖（user > plugin > builtin）。无冲突日志、无冲突数据结构、无对外暴露的检测接口。E3f §九 规划了快捷键 UI 的"冲突自动高亮"——但后端零基础。

### 5B.2 方案

```typescript
// KeybindingRegistry.ts —— KeybindingResolver（~30 行）

interface KeybindingConflict {
  key: string;
  bindings: Keybinding[];  // 至少 2 个
}

class KeybindingResolver {
  // 检测所有冲突
  detectConflicts(): KeybindingConflict[] {
    const byKey = new Map<string, Keybinding[]>();
    for (const b of _bindings) {
      const list = byKey.get(b.key) ?? [];
      list.push(b);
      byKey.set(b.key, list);
    }
    return [...byKey.values()]
      .filter(list => list.length > 1)
      .map(bindings => ({ key: bindings[0].key, bindings }));
  }

  // 单个 key 的仲裁——when 条件匹配度 + source 优先级 + 注册顺序
  resolve(key: string, context: ContextKeySnapshot): Keybinding | undefined {
    const candidates = _bindings.filter(b => b.key === key);
    if (candidates.length === 0) return undefined;

    // 1. 有 when 条件且不满足 → 排到最后
    // 2. source 优先级：user > plugin > builtin
    // 3. 同优先级 → 后注册者生效（用户最近的操作）
    const sorted = candidates.sort((a, b) => {
      const aMatch = a.when ? ContextKeyService.matches(a.when) : true;
      const bMatch = b.when ? ContextKeyService.matches(b.when) : true;
      if (aMatch !== bMatch) return aMatch ? -1 : 1;
      const priority = { user: 2, plugin: 1, builtin: 0 };
      return (priority[b.source] ?? 0) - (priority[a.source] ?? 0);
    });
    return sorted[0];
  }

  // E3f 快捷键 UI 消费
  getConflictingBindings(): KeybindingConflict[] {
    return this.detectConflicts();
  }
}
```

### 5B.3 改动

| 文件 | 改动 | 行数 |
|------|------|:--:|
| `src/core/KeybindingRegistry.ts` | 新增 `KeybindingResolver` 类 + `detectConflicts()` + `resolve()` + `getConflictingBindings()` | +30 |

### 5B.4 验证

### 6.3 实现（自研 ~30 行，不引入 fuse.js）

```typescript
function fuzzyScore(query: string, target: string): number {
  query = query.toLowerCase();
  target = target.toLowerCase();
  let score = 0, qi = 0, consecutive = 0;
  for (let ti = 0; ti < target.length && qi < query.length; ti++) {
    if (target[ti] === query[qi]) {
      qi++; consecutive++;
      if (ti === 0 || target[ti - 1] === " " || target[ti - 1] === ".") score += 10;
      if (consecutive > 1) score += 5; else score += 1;
    } else { consecutive = 0; }
  }
  return qi === query.length ? score : 0;
}
```

## 八、旧代码归一化 + `||` vs `??` 审计

> 来源：`../00-元文档/00-旧Bug预警与新生风险.md`——模式 8（falsy 陷阱）+ 模式 9（迁移不完整）。

### 任务 19b：`||` vs `??` 审计（~15 行修改）

**为什么 Electron 后更危险：** `ipcRenderer.invoke()` 可能返回 `""`/`0`/`false`/`null`/`undefined`——比 Tauri `invoke()` 更多 falsy 可能性。

**执行：**
```bash
grep -rn "||" src/ --include="*.ts" --include="*.tsx" | grep -v "|| {" | grep -v "||\s*$"
```
逐条判断：
- ID/名称 fallback → `||` ✅（空串是非法 ID）
- 数值默认（含 0） → `isNaN(n) ? default : n`（G22 教训）
- 对象/可选字段 → `??`（语义更精确）
- IPC 返回值 → **默认用 `??`**（`""`/`0`/`false` 可能是合法值）

**常见模式（grep 实际代码确认过的）：**
```
e?.message || e          → e?.message ?? String(e)  （空错误消息罕见但可能）
parseInt(...) || 220     → 检查 isNaN              （0 是合法值——G22 教训）
name || pluginId         → name || pluginId         ✅（空名字非法）
```

## 十一、状态栏自动配置——`configurable` 字段

### 11.1 现状

插件声明 `"statusBar": [...]` → 壳渲染。但用户无法控制显示/隐藏——每个插件如果想让自己的状态栏项可配置，需要手动注册 `contributes.configuration`。

### 11.2 问题

随着插件增多，状态栏会越来越拥挤。编译器插件加小扳手+下载图标，GPS 插件加卫星信号强度，每个插件都希望自己的状态栏项能开关。如果每个插件都要手动写 `contributes.configuration` + 写配置读取逻辑 → 重复代码 → 违反归一化。

### 11.3 方案——`configurable: true`

```json
{
  "statusBar": [
    { "id": "stats", "label": "TX:0  RX:0", "align": "left", "configurable": true },
    { "id": "connection", "icon": "circle-filled", "label": "", "configurable": true }
  ]
}
```

**`configurable: true` → 壳自动做两件事：**

1. **自动注册配置项**——`loader.ts` 解析 `statusBar` 时，`configurable` 项自动注册 `<pluginId>.statusBar.<itemId>` 到 `ConfigurationRegistry`（`boolean`，默认 `true`）。出现在 Settings Editor 该插件分组下，用户可开关——**插件作者零代码。**

2. **自动注入 `visible` prop**——`StatusBar.tsx` 渲染 `statusBar.tsx` 组件时，读取该项配置值，作为 `visible` prop 传入。插件组件收到 `visible: false` → 返回 `null`。

```typescript
// 壳——StatusBar.tsx 渲染逻辑
const configKey = `${pluginId}.statusBar.${item.id}`;
const visible = getConfigurationValue(configKey) ?? true;
if (item.configurable && visible === false) return null;
```

**不声明 `configurable` → 始终显示，不出现在 Settings Editor 里。** 向后兼容——现有 `"label": "TX:0  RX:0"` 不加字段，行为不变。

### 11.4 改动

| 文件 | 改动 | 行数 |
|------|------|:--:|
| `src/core/types.ts` | `StatusBarItem` 加 `configurable?: boolean` | 1 |
| `plugin.schema.json` | 加字段 | 3 |
| `src/pluginLoader/loader.ts` | 解析 `configurable` 项 → 自动注册 `contributes.configuration` | ~10 |
| `src/components/StatusBar.tsx` | 渲染时读取配置 | ~5 |

### 11.5 验证

```
1. 终端 statusBar 声明 configurable: true → Settings Editor "串口监视器"分组出现两个开关
2. 关掉 TX/RX → 状态栏 TX/RX 消失 → F5 → 仍是关的
```

## 十五-B、deriveType 排他分类（~10 行）

> 来源：再审计 N7。`PluginDetailView.tsx:19-28` 的 `deriveType()` 逻辑不完整——`hasView` 总是 `true`，所有插件都被标记为 "view"。第一个非视图插件（纯主题插件、纯语言插件）出现时标签就是错的。

### 15B.1 问题

```typescript
// PluginDetailView.tsx —— 改前（问题代码）
function deriveType(m: PluginManifest): string[] {
  const types: string[] = [];
  const hasView = !!m.entry || !!m.sidebar;  // ← 总是 true（PluginDetailView 只渲染 viewRegistry 中的插件）
  if (hasView) types.push("view");
  if (m.mode) types.push("protocol");
  if (m.resources) types.push("resource");
  return types.length ? types : ["unknown"];
}
```

当 `m.mode` 和 `m.resources` 都存在时 → 输出 `["view", "protocol", "resource"]`——不是排他分类，是标签追加。

### 15B.2 修复

**排他分类——一个插件只有一个主类型：**

```typescript
// PluginDetailView.tsx —— 改后（~10 行）
function deriveType(m: PluginManifest): string {
  // 优先级：theme > language > protocol > view
  if (m.themes?.length) return "theme";
  if (m.languages?.length) return "language";
  if (m.mode) return "protocol";
  return "view";  // 有 entry || sidebar → 视图插件
}
```

单一返回值（不是 `string[]`），消费端从数组遍历改为单值显示。

### 15B.3 验证

```
终端插件（entry+sidebar+mode） → "protocol"（串口协议） ✓
纯主题插件（themes）           → "theme" ✓
纯视图插件（仅 entry）        → "view" ✓
100 个插件后新插件类型        → 明确的单一分类 ✓
```
