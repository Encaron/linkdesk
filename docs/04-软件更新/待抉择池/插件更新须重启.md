# 插件更新须重启（池按 URL import 不 cache-bust）（待抉择池）

> **来源**：2026-09-30 追查「插件更新 vs 软件更新的重启体感不一致」时查明。用户实机观察「卸载重装当场可用、更新要按一下重启」，根因定位到**池的模块缓存**。此前只在 E6 层档案记账（[12-多表面共享状态塌缩-立案.md §六](../../02-Electron架构/插件生态与发布/01-插件独立构建/12-多表面共享状态塌缩-立案.md)），**04 里没有这条**，故补立本档防遗忘。
> **要防的**：这是**已知、在案、未修**的缺口，不是待发现的 bug——不落档，下一个会话只能从 E6 档案里刨，刨不到就当成"设计如此"。

## 一、现象与根因

**现象（用户实机）**：同一只插件——

- **卸载后重装** ⇒ 图标出现、视图当场可用，**零重启**；
- **不卸载直接更新** ⇒ 必须点 toast 的 [立即重启]，否则不生效。

**根因 = 两层缓存的键里都没有版本号**：

| 层 | 键 | 出处 |
|:--|:--|:--|
| 池侧模块表（Chromium module map） | 表面 URL：prod `linkdesk://<pluginId>/...`、dev `/@fs/<abs>/...` | [contributions.ts:321-326](../../../src/pluginLoader/contributions/contributions.ts) `resolveRuntimePluginRoot`——两个分支都不带版本 / hash / 时间戳 |
| 池侧 `_lazyCache` | `renderPath \|\| pluginId` | [PluginComponent.tsx:32](../../../src/pool/shared/plugin-component/PluginComponent.tsx) 定义 · `:153` 取键 · `:189` set；**`:171` / `:185` 是全部 `delete` 点——卸载路径没有清理点** |

⇒ **同一个 URL 永远命中同一份模块**：

- **同版本重装**：缓存里那份与盘上新落的**内容相同** ⇒ 看不出问题。注意措辞——**不是重装刷新了缓存，是缓存恰好还对**；
- **换版本更新**：缓存里是**旧版**、盘上是新版 ⇒ 会话内无手段驱逐 ⇒ 只有整机重启。

这就是 `update.ts:225` 那句「bundle 模块缓存无法 in-session 破除」的真身。⚠️ 同处 `update.ts:101` 的旧注释写的是「壳+池双 realm module map」——**壳侧这条已不成立**：壳 bundle 已零插件 JS 源码（[state.ts:57-72](../../../src/pluginLoader/resolution/state.ts)），组件加载唯一执行者是池。真正的阻塞只剩池里那一份。

## 二、为什么算「缺口」而不是「设计」

E6 台账的措辞已经把它定性了——**它是在否认一个归类，不是在陈述一条规则**（[12 号档 §六](../../02-Electron架构/插件生态与发布/01-插件独立构建/12-多表面共享状态塌缩-立案.md)）：

> ⛔ **不是**「壳加载器的 cache-bust」题：池按 URL `import()` 表面 bundle、**同 URL 不随磁盘替换重载** ⇒ 插件升级须重启才生效。这是**另一个**已知面…**归加载器优化域，不并案**。

配套两条边界：E6#159（多表面共享状态塌缩）明确**不并**本案；`E6-执行清单.md` 记「chunk 用**内容哈希名**、**升级须重启这条既有前提不变**」——即构建侧**有意保留**。

**设计之内的是「形态」，不是「必须重启」**：

- **是设计的**：更新走用户点击而非自动 reload（[P4-设计.md:1351](../../01-Tauri_P1至P5.5/P4-插件系统/P4-设计.md)：安装→通知 + [立即重启]…不自动 reload，不自动跳转）＋ 常驻可攒批（`ttl:0`，E6#73j G3/G7）。这一层还翻过一次面——Tauri Phase 4.7 选的是自动（1.5s 后 `window.location.reload()`），后收敛到 VS Code 的按钮式；
- **不是设计的**：「更新这一步非重启不可」是机制后果，**从未被设计过** ⇒ 它没有设计档，只有一条挂账行。

## 三、一条可达的缝（顺带记下）

「即时生效」的真实判据是「**缓存内容 == 盘上内容**」，不是「安装就一定即时」。因此：

**卸载 → 装更高版本**：池里仍留着旧版 URL 的缓存，重装后视图渲染旧 bundle；而 `needRestart` 只在 `loadPlugin` **抛错**时才置位（install-ops.ts 的 catch 支 `:170-179`），这条路不抛错 ⇒ **既不提示重启、也不真生效**。

（E6#80 补记里用户实机走的就是「降级 → 卸载 → 重装」，当时修的是 **manifest** 那一层；bundle 这层仍挂着。另：`install-ops.ts:345` 旧注释仍写「view 插件提示重启」，而实际文案是 `lifecycle.ts:89` 的「已安装：X v（**即时生效**）」——两处说法至今不一致，属历史层积没抹平。）

⚠️ 该缝为**据代码推出的可达路径，未做实机验证**。

## 四、候选修法（未拍板）

| 案 | 做什么 | 成本／风险 |
|:--|:--|:--|
| **A**｜给缓存键加版本维度 | 表面 URL 与 `_lazyCache` 键纳入版本（或内容指纹） | 改动面小；但「版本键够不够」（同版本重装要不要也换）以及 dev `/@fs` 轨的等价性都要先定 |
| **B**｜给池加重建通道 | `pool:` 通道块补一条「重载池」入口，更新收尾改走它而非 `app.relaunch()` | 可复用崩溃恢复既有的 `rebuildPool()`（`electron/windows/window-manager.ts:522`）；⚠️ 注意 `getPoolView()` 只覆盖**主池**（`:603`），脱出窗走 `getAllPoolViews()`（`:608`）——打通后 `needRestart` 才有机会从「整机重启」降级为「池重建」 |

两案都不是 `needRestart` 归零的完整解（还有脱出窗、热退出的配合面），但都比现状小。**选 A 还是 B、要不要做，都是拍板题。**
