# 03-域贡献者与混搭（核心模型）

> **状态：** 定论（2026-08-23 讨论）——混搭排期靠后，域分契约先行
> **一句话：** 主题文件不再要求是「完整配方」，而是「**域贡献者**」——贡献你有的域，缺的继承全局默认。

## 1. 域表（token 命名空间）

| 域 | token 族 | 谁贡献 |
|:--|:--|:--|
| 颜色 | `--bg-*`/`--text-*`/`--accent`… | 主题（现有） |
| 字体 | `--font-ui`/`--font-mono` | 主题 / **字体插件** |
| 圆角 | `--radius-*` | 风格主题 |
| 玻璃 | `--glass-*` | 玻璃主题 |
| 背景 | `--bg-image`/`--bg-mask`/`--bg-opacity` | 主题 |
| 菜单/表面 | `--menu-*`/`--surface-*` | 主题 |

## 2. 继承链（详见 [01](01-设计总纲与边界.md) §3）

```
:root 全局默认（壳，最保守现状）
  ↓ 主题/插件（域贡献者）——缺的域自动落回默认
  ↓ 设置层 scale（用户全局粗调，含拉到 0 = 关）
生效 token 集 → 渲染
```

**壳只认「一组生效 token」，不知道混搭了几个来源、每个来源贡献哪个域。** 核心无知原则在外观层的延伸。

## 3. 部分覆盖——天然支持

只设右键菜单 = 只贡献 `--menu-*` 域，其余自动继承全局默认。**CSS 变量天生稀疏——未定义 token 落回 :root 默认，零变化。不用特殊处理。**

## 4. 风格 vs 配色分离（mint-soda 实证）

- **mint-soda 现状**（见 [02](02-变量契约.md) §1.3）：4 变体共享 Claymorphism 风格，只换配色
- **契约分「风格 token」（radius/glass/shadow）+「颜色 token」（`--bg-*`/`--text-*`）**
- 收益：① 插件可写成「1 个风格基座 + N 个配色」②「换色不动风格」成为独立操作（对标 Windows accent 色板）③ 用户「不想放弃颜色但保持单一风格」直接成立

## 5. 混搭——架构可行，排期靠后

> 用户参照手机主题 app「混搭」：既想要主题 A 的右键菜单样式，又想要主题 B 的玻璃。

- **引擎不难**：CSS 变量天生适合按域组合——:root → 混搭组合（各来源取各自域）→ scale。就是一个「多来源 token 合并」函数
- **真正难在**：① token 契约分域（本文档 §1 是设计工作）② 设置页「混搭板块」UI（选各域来源）③ 用户心智负担（混搭破坏配方整体性 → 需**一键复位**）
- **结论：不是「算了」级别，是「可以但排期靠后」级别。** 手机主题是整包皮肤，我们是 token 域，天然可分——混搭是域模型的自然产物
- **落地顺序：先做域分契约（#50.6）→ 混搭自然长出来（Phase 10 后独立立案）**

## 6. 字体独立插件

字体 = 一个 token 族（`--font-ui`/`--font-mono`），天然可独立成插件（只贡献字体域）混搭进来。与「壳零内置字体」（[01](01-设计总纲与边界.md) §5 决策 1）一致——连字体都是插件。

## 7. 对主题插件的目录格式影响（#50.12 落地时定型）

现状（mint-soda）：1 插件 = N 个 json，每个平铺 colors 全部字段。
目标：主题 json 按域组织，**缺的域不写**（零变化继承）。示例形态：

```jsonc
// glass-aurora.json —— 玻璃域 + 风格域 + 颜色域
{
  "name": "Glass Aurora",
  "type": "dark",
  "appearance": {
    "radius": { "xl": 18, "2xl": 24 },        // 只覆盖大圆角，其余继承
    "glass": { "blur": 20, "saturate": 1.4 }, // 玻璃域
    "background": { "image": "assets/bg.png" } // 背景图（getAssetPath）
  },
  "colors": { "accent": "#8B5CF6" }            // 颜色域，sparse
}
```

> ⚠️ 目录格式的精确 schema（域字段命名/结构）是 #50.6 的执行产物，本文档定方向不定细节。
