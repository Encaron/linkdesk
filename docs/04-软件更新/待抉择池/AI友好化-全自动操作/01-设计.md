## 一、需求（用户原话概括）

1. 「**总之我要的是一个能够完全自动化的软件。**」——AI 友好四层之层 1（运行时操作）的终局形态。
2. 「**AI 可以知道这个界面正在发生什么，可以掌握这个界面的每一处数据，可以操作它。**比如弹了一个 toast 铃铛，AI 应该清楚：它在什么位置、因为什么弹出、内容是什么、有几个按钮、按钮里有什么、该执行哪个按钮、执行之后应该做什么。」——**「读」与「操作」是一对**，缺一不可。
3. 「**MCP 和 CLI 最好两个都有，AI 习惯哪个用哪个。**」——外部 AI 接入通道双轨（用户听说 MCP 较贵、CLI 直接命令行；两条都要，详见 M4）。
4. 「至少 AI 得知道**怎么用 MCP / CLI 操作我这个软件**。」——操作知识必须成文可查（M3）。
5. 范围**不止 dev 版**——安装版上同样要让 AI 容易操作（M5 + M4 的既有实证）。

## 二、缘起现象与调查账（2026-09-14）

### 2.1 现象（起点）

A1 实机批场景 6：测试 AI 用自动化驱动「**把设置标签页拖到主区右半边形成分屏**」失败——按下/移动/抬起事件全到、标签页也进入 dragging 半透明态，但**松手不出分屏、也没有玻璃预览层**；测试 AI 上报口径「纯自动化问题，不是软件问题」，最后请用户手动拖了一下。用户质疑：**这是不是不符合 AI 友好化？是不是像 LabVIEW 那样只能手拖？**

### 2.2 调查结论（一句话账）

**标签页拖拽不是 LabVIEW 式死路**——分屏有完整直通车（命令 + 池 API），测试 AI 失败的真原因是两条**任何文档都没写的隐藏规则**；往全软件看，账是：**操作层整体健康 / 读取层半成品 / 知识沉淀空白**。

拖拽失败的两个真原因（读码核实，非 isTrusted 问题——代码零防自动化检查，单测就是用合成事件跑通分屏的）：

| # | 原因 | 证据 |
|:--|:--|:--|
| 1 | **手势门控**：reorder→split 相位切换要求**垂直位移 >15px 且光标越过 35px 标签栏进入"纯编辑区"**；横向拖（如沿标签栏拖到右侧）永远停在 reorder 相位 → 不分屏。**玻璃预览只在 split 相位渲染，"没有玻璃预览"恰是"从未进入 split 相位"的铁证** | `src/pool/hooks/useDragReorder.ts:196`（`dy > splitThreshold && inEditor`）、`src/pool/hooks/tabDragTypes.ts:22-38`（SPLIT_THRESHOLD=0.25）、`src/pool/zones/main/MainZone/DragOverlays.tsx:71-101` |
| 2 | **CDP 坐标缺陷**：Chromium 给合成鼠标事件的 `screenX` 不加窗口偏移 → 窗口屏幕原点推算错误 → 跨窗判定（脱出/吸附）全失效（工具层坑，不解释窗内不分屏） | `useDragReorder.ts:140-141, 240-254`；`src/App/windows/windowRelocation.ts:186-196` |

**它不知道的正解（这就是不友好的部分）**：分屏根本不用拖——

- **池 API 直达**：`window.linkdesk.pool.tabAction({action:"splitTab", direction:"horizontal", zone:"right"})`（支持精确 zone/targetGroup，比拖拽更精确）——`src/core/types/ipc/tabActions.ts:37`、处理端 `src/App/tabCallbacks.ts:401-412`；

## 三、判据定稿（什么是「AI 可全自动操作」）

**三条判据，缺一不算达标：**

1. **可读**：界面每一处状态（布局/标签页/通知/对话框/面板）都有**契约级读取路径**，不靠 CDP 读 DOM 猜。
2. **可操作**：每一个用户可做的动作，至少有一条**非鼠标路径**（命令 / API / CLI）——鼠标手势可以是"给人用的手感"，但**不得是唯一路径**；OS 层够不着的如实列册。
3. **可查**：操作知识有**单一真相源文档**（命令索引 / 隐藏规则 / 够不着清单 / 安装版路径），任意 AI 不读源码即可上手。

**验收锚点①（用户 toast 例——"读"的验收，逐条对账口径）**：位置 ✅（铃铛宽面板唯一面）｜因为什么 ◐（缺 wake 透传）｜内容 ✅｜按钮数/文字 ◐（缺 command/args）｜该执行哪个 ❌（M1 补齐）｜执行后做什么 ◐（行为在源码，契约未写 → M1/M3 补齐）。

**验收锚点②（用户操作例——自然语言操作插件，2026-09-14 用户原话·语音整理）：**

> 「我用自然语言跟 AI 说：用那个**日程插件**，建一个今天早上 **9 点到 12 点**的日程，题目/内容是什么什么；然后这个小卡片用**接近灰色**的颜色；再把日程**提前一点**；并且告诉 AI**如果时间到了就自动给这个日程打上一个勾**。」

（示例插件 = 假想日程插件，用于检验「一个插件怎样才算 AI 可操作」。）

| # | 动作 | 结论 | 前提 |
|:--|:--|:--|:--|
| 1 | 「用那个日程插件」（打开它） | ✅ 框架级——声明驱动，AI 自动可开 | 无需插件额外做什么 |
| 2 | 「建 9:00–12:00、题目/内容 X 的日程」 | ⚠️ 依赖插件 | 插件把「新建日程」注册为命令、参数含时间 + 内容（M2⑤） |
| 3 | 「颜色接近灰色」（自然语言描述颜色） | ⚠️ 依赖插件 | 该命令支持颜色参数（或插件有对应设置项） |
| 4 | 「把日程提前一点」 | ⚠️ 依赖插件 | 有「改时间 / 移动」命令 |
| 5 | 「到时间自动打勾」 | ❌ 不是 AI 的操作面 | 这是插件的**定时功能**；AI 只能**配置**它，"值守"归插件/软件（见下方边界②） |

**这条例子的意义**：一句话同时检验四件事——① 自然语言→操作序列的翻译质量（靠 M1⑦ 命令说明 + M3 手册，AI 才知道怎么调）；② 插件业务动作必须"挂牌子"（M2⑤）；③ 框架级动作免挂（声明驱动）；④ 边界不写清就会预期落空（边界②）。

**边界（本系列不承诺什么——防预期落空，2026-09-14 用户问答时补）：**

1. **OS 层动作够不着**（拖文件进出窗口等，A 类）——如实列册，不算达标范围。
2. **AI 是操作员，不是值守员**：AI 只在被调用时做事。「到时间自动执行」这类**持续逻辑归软件/插件**（如日程插件的到点提醒/自动打勾）——AI 可以把这类功能**配置**好，但"守着时间执行"的不是 AI。未来若要「AI 定时任务」，需另立自动化系统，**不在本系列**。
3. **插件业务动作的覆盖度取决于插件作者**：框架不知道插件是干什么的（核心无知原则）——插件把动作**注册为命令** ⇒ 自动进入 AI 操作清单；没注册 ⇒ AI 做不到（不用模拟点击兜底）。让"注册命令"成为插件规范与脚手架的默认动作 = **M2⑤**。

**操作质量判据（用户核心口径，2026-09-16）**：达标 = **结构化操作**（读结构化状态 → 调命令/API 带参数 → 读结构化结果），**不是**「截图 → 视觉理解 → 猜坐标点击 → 再看截图」的视觉循环——那套是"软件没给 AI 门"时的**兜底流派**（慢、脆、不精确、不可验证、不可审计）。本系列全部设计（M1 读取面 / M1⑦ 命令说明 / M4 通道）都朝"**给出正门**"方向：AI 不需要看屏幕，它需要的是**数据与命令**——甚至能做到人做不到的（批量、精确值、可重复、可脚本）。
**且「达标」是持续纪律，不是一次性交付**：此后每个新功能 / 新插件都必须遵守「每个用户动作至少一条非鼠标路径」＋「业务动作注册为命令」——否则破洞会随迭代重新出现（本系列缘起正是如此：一个老功能里的隐藏门控卡住了 AI）。

## 九、风险自查——对 E5.6 / OverlayWindow 教训的逐条对照（2026-09-16 用户点名）

> 用户原话（意）：「别像 E5.6 双 Pool 那样——前期讨论得好好的，甚至 OverlayWindow 都想好把右键悬浮搬进去，真做到的时候发现不能持久化、点击矛盾，最后迫不得已转 E5.7。」**要求：设想必须周全可实现。**

### 9.1 E5.6 翻车的根因（OverlayWindow 档案原话）

- **聪慧组件搬进哑容器**：组件依赖的三件事（取数据 / 执行 / 展开子级）本来在同一个函数调用栈里，拆分后分到三个不同进程 ⇒ 碎。
- **通则**：「设计任何跨边界组件前先问『**这个组件在哪个进程跑？它依赖的 API 在那个进程里存在吗？**』——**别问『这个组件怎么搬过去』**。」
- 症状类型（纸面看不见、真机才炸）：不能持久化 / 点击矛盾 = **多系统的隐含假设在真机上对撞**。

### 9.2 逐模块自查（同一把刀）

| 模块 | 有没有新边界 / 新进程 / 搬组件？ | 判定 |
|:--|:--|:--|
| M1 读取面 | 无——数据**已在推**（壳→池全量快照每帧在传），本项 = 开放 + 文档化 | 低风险 |
| M1⑦ 命令说明 | 无——加元数据（description / 参数） | 低风险（工程量：逐条审命令，清单会长） |
| M2 操作面 | 无——逐条补入口（在已有通道上加门） | 低风险（审计会变长，见 9.4） |
| M3 手册 | 无——写文档（命令部分建议从实现生成，防漂移） | 低风险 |
| **M4 通道** | **唯一新机制**——但网关住**主进程**（依赖的 IPC / 命令 / 插件管理全在主进程存在）；**不新建进程 / 窗口、不碰渲染层、不搬任何组件** | **中风险——唯一要 spike 的模块，见 9.3** |
| M5 参数保留 | 无 | 低风险 |

**关键对照**：OverlayWindow 倒下的地方是「**要承载渲染层聪慧组件**」；M4 建在「**命令 + 数据**」之上——这东西**本来就跨边界工作**（命令系统天天在池→壳→主进程三层间走；开发期 AI 每天经 CDP 在调）⇒ **不重复错误类型**。

### 9.3 M4 的已知设计难点（如实列，不假装不存在）

1. **CLI ↔ 运行中实例的本地通道**：有标准先例（VS Code CLI 同型），但 Windows 细节（命名管道 / 回环 + token）要设计＋验证。
2. **MCP 冷启动悖论**：AI 客户端拉起 MCP server 时软件可能没开 ⇒ 要么等软件、要么只暴露离线能力——要设计（含「等多久 / 怎么唤醒」）。
3. **多窗口 / 单实例锁交互**（与 M5 合并处理）。
4. **对策 = spike 先行**：开工第一步做**最小垂直切片**——「CLI 一条命令控制运行中的软件」跑通（含冷启动与失败路径），通了再铺全。

### 9.4 防翻车机制（与 E5.6 的结构性区别）

1. **零新边界承诺**：M1-M3/M5 全在已有边界内；M4 网关在主进程、不搬组件、不加渲染层。
2. **实证状态逐条标注**：本文各模块「依据」栏已区分「实机验证过 / 现有件 / 待建」——不把设想与现实混写（E5.6 的混写正是误判之源）。
3. **最小切片先行**：每模块先跑最小实验（M4 先一条命令；M1 先一个 list）——**判据不成立立刻暴露，不等到全做完**。
4. **全加法结构**：每块 = 加 API / 加字段 / 加命令 / 加文档——单条路不通就换那一条，**不存在「一个架构推翻重来」的量级**。
5. **诚实预告**：审计会产出比今天更长的清单（「隐藏门控」式问题发现一个补一个）——**但量级是「补一条命令」，不是「推翻架构」**。

### M4 · 接入双通道：MCP + CLI（↔P5，方向 B 重开）

- **做什么**：一个**内核**（白名单 `linkdesk.*` 语义操作面网关，`toolbox-sop §5.2` 原方向 B 设计：本地 HTTP + token），**两个皮**：
  - **MCP Server**（按 MCP 标准、JSON-RPC，AI 客户端开箱即用）；
  - **CLI**（`linkdeskctl <命令>`——**人和 AI 共用的命令行**：用户自己敲、AI 经 shell 调、按需 `--help` 自省；子命令覆盖状态查询 / 开标签 / 执行命令 / **装插件（含从 URL）** 等，2026-09-16 用户追问补）。
- **「MCP 贵 vs CLI」的口径处理**（用户口径入档）：MCP 协议本身免费开源；"贵"的三个可能来源须在立项前逐项厘清——① 实现工程量、② 工具清单占 AI 上下文 token、③ 常驻依赖。CLI 的天然优势 = 零常驻、按需读帮助。**结论：两条都做，共用内核；AI 习惯哪个用哪个**（用户拍板口径）。
- **安全半径**：**给白名单能力，不给任意 JS 权限**（与 `e5.7-extreme-simple-pool` 哲学同源）；token 鉴权 + 本机回环默认。
- **判据**：任一通道可完整走通「开标签 → 执行命令 → 读通知 → 执行通知按钮」全链路；`--help` / `tools/list` 能自查操作清单。
- **落点**：主进程新服务（`electron/services/` 新目录）+ 安装版随包 + 设置页「AI 接入」分区（见增量图；开关/状态/token + **接入引导**：一键复制 MCP 配置片段 / 指明 CLI 用法与手册位置）。
- ⚠️ **立项前必办**：重开当年「花费巨大、不如 CLI」那笔账（原讨论未落盘，原话已不可考——记忆 `toolbox-sop §5.2` 已补注记）。

### M5 · 安装版一致性（↔P1）
