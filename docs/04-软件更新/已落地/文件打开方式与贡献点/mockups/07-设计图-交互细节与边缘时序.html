单击 / 右键文件➜ ContextMenu（共享件）➜ 「打开方式…」（无 handler 时隐藏，E13）➜ 选择器：列 listHandlersFor(ext)➜ 打开（仅此一次） 设为默认 → 覆盖表 恢复自动 → 删覆盖键（仅当存在覆盖时显示该行） ↻ 下次解析：覆盖表优先（D1）

二、边缘时序卡每张卡 = 一个「如果…会怎样」的完整剧本

E1/E19第二只 pdf 阅读器装上——默认不许静默漂移D7 · T2.5
1只装了一家默认=它（激活序优先）
➜
2第二家激活壳发现「同扩展名新声明者＋用户从未选过」
➜
3toast 一次「当前默认仍是 X——右键→打开方式可换」（会话内一次，E1/E2 同规则）
➜
4默认没变覆盖表没动、声明序没动——只是多了一个候选
➜
5用户挑了才换选择器「设为默认」＝唯一换默认的通道
为什么重要：插件永远不能靠「装上」这个动作抢走默认——抢默认的通道只有用户的手。
E3两只编辑器同时挂牌（极客上传 → 小白没卸官方就装）T7 · D7 同规
1官方 editor 挂牌且先激活兜底=官方（现状零变化）
➜
2极客编辑器入market、被安装它也声明 role="text-fallback" —— 第二个挂牌者出现
➜
3不静默漂移同 E1 第 3 步：提示一次，兜底仍官方
➜
4选择器两家并列右键 .txt → 打开方式：官方 ● 自动默认 / MyEEEEEditor pro plus max ultra
➜
5极客自己机器上的情形他卸了官方再装自己的 ⇒ 只剩一家挂牌 ⇒ 自然接管，无需任何特殊逻辑
设计结论：⛔ 不写「冲突处理」新规则——一套仲裁天然覆盖两个场景；写新规则反而制造第二套真相。
E6/E7覆盖表指向的插件没了（悬空覆盖）T2 · D1
1覆盖表 {".pdf": "X"}用户曾设 X 为默认
➜
2X 被卸载/禁用解析时发现指向者不在场（禁用=不参选，E5）
➜
3跳过该键视同未覆盖 → 回声明序；toast 一次「默认已失效，已恢复自动」
➜
4键惰性清除不专程清盘——下次「设为默认」自然覆盖；避免多余的写盘
与 E25 的界线：pluginId 精确匹配，拼写不符=同格处理；没有模糊匹配。
E24Windows 层：壳只加候选，⛔ 永不碰 UserChoiceT6 · OS 主权在用户
1壳登记候选HKCU OpenWithProgids += .pdf → LinkDesk（per-user，无需提权）
➜
2「打开方式」菜单多一项LinkDesk 出现在候选列表
➜
3用户在 Windows 里手选了别的程序UserChoice 归用户——壳看见了也装没看见
➜
4⛔ 壳不做的事不自作主张改回、不弹「要不要改回 LinkDesk」、不写 UserChoice 键
一句话：应用内的默认归覆盖表；OS 层的默认归用户在 Windows 里的手。两层主权互不越界。
E16/E26OS 登记生命周期（装 → 卸 → 开关）T6 · D6
装阅读器插件激活总开关开 ⇒ HKCU 增候选 ⇒ 设置页「系统集成」现算出 .pdf 行（行随插件生灭）
卸插件卸载撤该扩展名候选（别家也声明则保留）⇒ 设置页该行消失；覆盖表按 E6 处理
开关关 → 开关=撤回运行期登记（安装器静态不动）；再开=按当前插件集幂等重放（重复写无害）
恒等式：exe 永不出现在任何环节（无插件能开＋登记 exe 打开器本身危险）。
