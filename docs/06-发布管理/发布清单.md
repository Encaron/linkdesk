> | 当前版本号是多少 | `package.json` 的 `version`（**唯一真值**，全仓不写第二份） |

## 一、发布前（这些没过完，不许打 tag）

> ### 🔴 先看跨仓顺序——四步，**别把它当成「一条命令」**
>
> 插件的更新走市场，**不必与壳同批**；但只要这一版软件要**带上某个插件的新版出厂**，就必须按这个顺序——
> **① 在别的仓里，壳仓看不见它**，所以这是**顺序依赖**，不是可选项。
>
> | 步 | 在哪 | 做什么 |
> |:--:|:--|:--|
> | **①** | **各插件仓**（`Encaron/linkdesk-plugin-<id>`） | 按需发版：`npm run validate` → `npm run verify` → `npm run build` → `npm test` 全绿，再 `npm run publish`（产 zip + Release + 仓根 `marketplace.json`） |
> | **②** | 壳仓 | 刷新出厂种子——就是下面那条「两步，缺一不可」 |
> | **③** | 壳仓 | `npm run check`（含 `check-bundled-freshness`——**默认联网那一跑不能省**） |
> | **④** | 壳仓 | 发布：bump + tag + CI 出安装包（见「二、发布」） |
>
> ⚠️ **① 的插件仓门禁是插件仓自己的那份**（E6#102 / L7 7.5 装的，`.github/workflows/ci.yml` + `npm run verify`）：
> 它与壳仓的 `npm run check` **互相覆盖不到对方**——插件源码搬出去之后，壳仓那次 check 够不着它。
> `npm run verify` 是唯一会把 WARN 判成红的闸（SDK 自带的 `npm run lint` 只报告、永不 fail，那是给作者本地留的）。
> 细则见 [06-门禁与CI.md](../02-Electron架构/插件生态与发布/插件源码外移层/06-门禁与CI.md)。
>
> 🔴 **插件发版的最后一步是「官方目录收录」，不是 `npm run publish`**（2026-09-27 插件市场 1.1.0 立此判据）。
> 插件仓根那份 `marketplace.json` 只是**它自己的**市场源；**软件默认拉的官方源是另一个仓** `Encaron/linkdesk-marketplace`
> （`OFFICIAL_SOURCE_URL`，raw CDN 路径）——**不往那儿收录，用户在软件里永远点不到这个新版**。
> 判据一句话：**「发版」= 用户能在软件里点更新**，不是「GitHub 上有个 Release」。
> 顺序：插件仓 `build`（⚠️ `publish` **不重建**，只上传仓里既有的 `<id>.linkdesk-plugin`）→ `publish`（Release ＋ 资产 ＋ 远端仓根 `marketplace.json`）
> → **目录收录**（版本 ＋ tag-pinned `downloadUrl`/`icon`/`readmeUrl`；壳仓 `scripts/sync-official-catalog.mjs` **只生成不推**，禁整文件覆盖）→ 目标机 `sync:bundled --latest`。
> ⚠️ 收录后仍有一段**不可见窗口**：官方源走 raw CDN（`max-age=300`）＋ 客户端 5 分钟目录 TTL。

```
[ ] npm run check 零错误（双工程 tsc + ESLint 0 警告 + 全量测试 + 各道门禁）

      纯攒批发版提交连 tag 一起推（§二 两档），同一套 check＋build 在 tag 上重跑＝同提交、同「无插件容器」宇宙。
```

## 二、发布（打 tag → CI → 检查）

> ### 🟢 两档发版路径（2026-10-06 用户拍板——发版耗时压缩第一档，v0.2.50 实测 58 → 目标 ≤15 分钟；**地板＝单次 tag 运行 10m11s，2026-10-06 逐步实测：npm ci 43s＋Check 3m56s＋Build 4m09s＋收发尾 ~1m20s**）
>
> | 档 | 判据 | 路径 |
> |:--:|:--|:--|
> | **纯攒批**（**打包面零改动**：`electron-builder.yml` / 安装器脚本 / bootstrapper / 随包资源都没碰） | tag 运行绿（同一次运行既出产物又出证明） | CHANGELOG 定稿（攒批时随手维护）→ 发版提交（版本号＋CHANGELOG）**连 tag 一起推**——tag 运行重跑同套 check＋build，**本身就是 CI 口径全链，只付一次运行（实测 10m11s）**；⛔ 本地不重复打包（正式产物由 CI 出，product.json 身份由 CI 写）→ `npm run check:release-notes-sync`（联网只读、秒级；E6#167 对账在攒批档没有 publish.mjs 代跑，必须单跑）→ Release 验收（资产 exe＋latest.yml、正文＝段同源）→ 当场复盘耗时（memory version-and-release §X）。**红（低概率：发版提交只含版本号＋CHANGELOG）⇒ 修后移动未发布 tag 重推（先例 v0.2.50 当日两用）** |
> | **打包面有改动** | — | 本地 `npm run publish` 打包＋**自绘安装器实测**照旧全走（§一 其余各行不豁免），再 tag。 |
>
> 产物必须对应**一个提交**且该提交 check 全绿——纯攒批档下这份证明就是 **tag 运行本身**（同套 check＋build 重跑）；失败未发布的 tag 移动重打有先例口径（v0.2.50 当日即用）。⚠️ **已发布** tag 的移动/撤版仍归用户（AGENTS.md 红线）。

```
[ ] 版本号已 bump 且同笔写了 CHANGELOG 段（死规矩，3.7.3 立）
[ ] git tag v{版本号}   ← tag 名 = package.json 的 version + `v` 前缀
[ ] git push origin v{版本号}
[ ] 等 GitHub Actions build 完成（两道门禁要过：CHANGELOG 段 / 安装包名）
[ ] 检查 Release 资产有**两件**：`.exe` ＋ `latest.yml`
      · 🔴 件 3b（2026-10-02）：`*.blockmap` **已退**——它是 NSIS 差分更新的伴随件，目标改 `7z`
        后 electron-builder 不再产出（留着那条上传 glob 会匹配空 ⇒ Release 步骤失败）
      · 功能上**必需的只有 `.exe`**——本仓自研更新器读 Releases API、按 asset 名匹配，
        **不读 `latest.yml`**（别把「没传 latest.yml 就没有新版」当成理由，那是错的）
      · `latest.yml` 留着是为了给安装包名门禁的**判据③**留现场 ＋ 发布惯例；🔴 NSIS 退役后
        electron-builder 不再生成它，**改由 `scripts/build-installer.mjs` 写**（字段口径不变：
        `path` = 磁盘上 exe 的真名）
[ ] Release 正文非空，且**是 CHANGELOG 正文**（不是 GitHub 自动罗列的 commit 流水），
    且带下载信息块（文件名 / 版本号 / 发布日期 / 系统需求）——由 CI 自动拼，禁手写
[ ] 🔴 **Release 正文的写法（2026-09-14 用户拍板）**：**面向所有用户的正式发布说明，不是工程日志**——
    按分类组织（✨ 新功能 / 🐛 问题修复 / 📄 说明），**一眼看懂这版改了什么**。
    **禁止出现**：① 内部任务号与轮次（`feat:E6#57.x`、「第 N 轮」）② 版本策略注记（「0.x 向后兼容走 patch 位」）
    ③ 对话腔与第二人称（「不让您再干等」「念给您听」）④ 门禁/负控/如实记账等工程过程叙述。
    这些留给提交记录与执行清单；CHANGELOG 段本身就是 Release 正文（同源），写的时候就按这个口径写。
[ ] 🔴 **CHANGELOG 段（文件里那段）＝ 上面同一条口径**（2026-10-01 拍板，E6#164 T1）——
    只写「**用户视角发生了什么**」（一条一句，按 ✨ 新功能 / 🐛 问题修复 / 📄 说明 分类）；
    「为什么这么修 / 踩了哪个坑 / 判据与门禁细节 / 任务号轮次」⛔ **不写进段里**，留给提交记录、`docs/` 存档与执行清单。
    判据：**段 = Release 正文（同源）** ⇒ 段里能写的，用户就一定会在 Release 页看见；Release 页不该有的，段里也不该有。
    💰 为什么是纪律而不是洁癖：这条段同时喂三个分发面（市场目录 / 插件 zip / 仓库文件），**多写 1 KB 散文 = 每个用户每次「检查更新」多下 1 KB**。
[ ] 🔴 **归档（体积纪律，2026-10-01 拍板，E6#164 T3）**：`CHANGELOG.md` 越 **> 50 版 或 > 300 KB（任一先到）** ⇒
    把**已封版的版本线**整条搬进 [../04-软件更新/CHANGELOG-归档-<版本线>.md](../04-软件更新/00-README.md)（同目录另起文件 ＋ 顶部索引）——
    ⛔ **不许机械倒切「最近 50 版」**：那会把一条版本线劈成两半，读者无法判断「这条线还剩多少在根文件里」；
    ⚠️ 归档**只动历史**：**当前版本段必须留在主文件**（CI 的 `--changelog-body` / `--changelog-date` 从主文件切段）。
[ ] Release 页上的 `.exe` 文件名与 tag 版本号对得上
[ ] 下载入口：README 的 `releases/latest` 链接**通常不用动**（别名自动跟随）；
    ⚠️ **一旦发现要手改 README 里的版本号，就是写错了**——那说明你把 `latest` 别名写成了死版本号
```

## 三、发布后（从 Release 页当一次真用户）

```
[ ] 从 Release 页下载安装包 → 装到干净环境
[ ] 启动 → 全功能正常（无白屏 / 各部件齐 / 无启动报错）
[ ] 市场装一个插件 → 正常
[ ] 🔴 旧版实机点「检查更新」→ 发现新版 → 下载 → 重启安装 → 版本号**真的变新**
    （E6#57.16 全链路；依赖 E6#37 的构建产物）
[ ] 建维护分支（分支名随实际版本，别写死 v1.0.x）
```

> 🔴 **判据不是「脚本全绿」，是「货架真新」**——脚本绿只证明基线被标记过。
> 同理：`npm run check` 绿 ≠ 发布成功；**能下载、能装、能起来、版本号真变了**才算。
> （这条在 npm 作者包那侧已经用血换过一次，见 L3.7：脚本绿灯装上才发现货是旧的。）

## 四、这份清单什么时候改

- **新增一道门禁** → 在「一、发布前」加一行，并写明**判据**（不是「注意一下」）
- **改了打包/发布机制** → 同步改指向的真理源，本档只改指针
- ⚠️ **本档不许写死版本号、不许写死文件名**——两者都有唯一真理源，写进来就是第二份
