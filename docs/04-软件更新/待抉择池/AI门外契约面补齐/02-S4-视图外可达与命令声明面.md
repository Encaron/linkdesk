# S4 · 视图外可达与命令声明面

> 归属：[00-提案](00-提案.md) 主线 S4。证据：B1-7（`when=…` 命令不开视图够不着）、I-2（placeholder 让 AI 看得见调不动）、I-3（整片摘＋补注册）。
> 目标不是「让所有命令都能无视图调」——那既不可能也没必要；目标是 **「AI 永远能预判，且失败时拿到可判读的码」**。

---

## 一、问题：三层现状，AI 只看得见第一层

| 层 | 现状 | AI 能否预判 |
|:--|:--|:--|
| 声明面（manifest） | `contributes.commands` 在加载时以 `placeholder` 进壳注册表（`contributions.ts:147-168`） | ❌ 全是「存在」，看不出哪条要视图 |
| 执行面（池） | 真实 handler 住 `_poolCommands`；entry 顶层注册的随 `import` 懒激活，视图组件里注册的随 mount | ❌ 两种混在同一张表里 |
| 注销面 | 最后一个视图卸载 ⇒ `unregisterCommands(pluginId)` **整片摘** + 手写 `registerSerialCommands()` 补回（`useViewCommands.ts:96-106`） | ❌ 摘了又不报，AI 只收到「未在池内注册」裸字符串 |

三个直接后果：

1. **不可预判**：`describe` 分不出「可直接调」和「先 open-tab」。
2. **不可判读**：失败信息是内部实现用语，没有码、没有下一步。
3. **不可靠**：`_cmdMap.size <= 1` 这个「最后一个视图」判断依赖跨 hook 的 cleanup 顺序；`quickSendEdit`/`quickSendDelete` 在插件级与视图级**注册同一个 id**，谁最后注册谁生效。

## 二、设计

### 2.1 `activation` 的判定权：宿主自动判定为主，声明为辅

> 🔴 核心决定（待拍 #5）：**不把「要不要视图」交给作者手写**——那会变成又一份需要维护的元数据，且必然漂移。

宿主在**注册那一刻**就知道上下文：

| 路径 | 上下文 | 判定 |
|:--|:--|:--|
| `entryActivation` import 属主 entry，顶层同步调 `registerCommand` | `entry` | **无需视图，可由命令 miss 懒激活** |
| `PluginComponent` mount 后，组件内 hook 调 `registerCommand` | `view` | **需要该视图在场** |

落点：

- 池侧维护一个**激活上下文栈** `_activationContext`（默认 `"entry"`；`PluginComponent` mount 压 `"view"`、unmount 弹栈）。
- `preload-pool/commands.ts` 的 `registerCommand` 读栈顶，随 handler 一起记 `activation`。
- 壳 `CommandRegistry` 的条目增 `activation?: "entry" | "view"`（运行期真值）。
- `describe` 输出该真值；**未注册**的命令输出 manifest 声明（必填，见下）。

manifest 侧字段**必填**（内测免兼容，决策 #10），用途是「未激活时提前告知」：

```jsonc
{ "id": "serial-monitor.clear", "activation": "view" }  // 必填：entry | view
```

**两个来源的分工（⛔ 不许互相覆盖成第二套真相）**：

| 来源 | 角色 | 何时用 |
|:--|:--|:--|
| 注册上下文 | **运行期真值** | 命令已注册 ⇒ 一律以它为准 |
| manifest 声明 | **提前告知** | 命令尚未激活 ⇒ 用它让 `describe` 能说清 |

冲突（声明 `entry` 但实际在视图里注册，或反之）⇒ **以运行期为准** ＋ loader 记诊断 ＋ `audit:plugin-commands` 黄灯（只报不拦）。

⛔ **禁止延迟注册**：`setTimeout` / `await` 之后再 `registerCommand` 会读错上下文。写进作者规范，并用审计腿抓「注册点不在同步路径」。

### 2.2 注册作用域：视图关只摘视图，不碰插件级

> 🔴 这一条同时干掉 I-3 的「整片摘＋补注册」和双注册隐患。

池命令表从「一个平铺 Map」改为**按作用域分区**：

```
_poolCommands: Map<commandId, { handler, pluginId, activation, scope }>
```

- `scope = "plugin"`：entry 顶层注册，**插件存活期常驻**，不随任何视图卸载。
- `scope = "view:<viewInstanceId>"`：视图态注册，只在**该实例**卸载时摘除。
- 同一 `commandId` **只允许一个作用域**；重复注册（不论同层还是跨层）⇒ 开发期诊断 + 后者不覆盖，⛔ 不再靠「谁最后注册谁赢」。

于是：

- 最后一个视图关闭 ⇒ 只摘 `view:*` 的条目，**插件级一条不动**，无需手写补注册；
- 多标签 ⇒ 每个实例独立作用域，关一个不误伤另一个；
- `_cmdMap.size <= 1` 这类脆弱判断**整段删除**（无死代码）。

### 2.3 失败必须可判读

| 码 | 何时 | 字段 | hint |
|:--|:--|:--|:--|
| `EVIEWREQUIRED` | 命令存在、但该命令是 `view` 作用域且视图不在场 | `{pluginId, commandId, activation}` | 「先 open-tab `<pluginId>`，再重试」 |
| `ENOTACTIVE` | 插件未启用 / entry 加载失败 / 声明了但无人认领 | `{pluginId, commandId}` | 「插件未启用或加载失败；查看插件管理器」 |
| `EUNKNOWNCOMMAND` | 连声明都没有 | `{commandId}` | 「命令不存在；跑 describe 看可用面」 |

⛔ **禁止**再把内部用语（「未在池内注册」）直接抛给门外。三个码都由**一处**映射（壳的桥接层），⛔ 不许 CLI / MCP / 插件各拼一份。

### 2.4 `when` 的纪律（保留原文）

- `when` **只影响菜单/面板/快捷键的可见性**，⛔ 不得用于「把用户动作锁进视图」；
- 视图不在场时：要么可用，要么回 `EVIEWREQUIRED`，⛔ **不得静默不注册**；
- 门③达标：**每个用户动作必须有命令**，插件侧可审计（`audit:plugin-commands` 加「动作类能力是否有命令」）。

## 三、落地清单（一处定义，多处消费）

| 落点 | 改什么 | 判据 |
|:--|:--|:--|
| `contributes.commands` schema | 增**必填** `activation: "entry"\|"view"` | 声明式；缺失 ⇒ loader 拒绝（免兼容） |
| 池 preload `commands.ts` | 上下文栈 + `registerCommand` 记 `activation/scope` + 分区表 | 唯一真相源 |
| `PluginComponent` | mount/unmount 压弹上下文栈 | 不做业务判断 |
| 壳 `CommandRegistry` | 条目增 `activation`；`getCommands()` 仍返回全量但带标记 | 显示真相源 |
| `aiBridge/whitelist.ts` | `describe` 输出 `activation`；exec 失败映射三码 | 映射只此一处 |
| SDK | `registerCommand` 类型增 `activation`/`scope` 由宿主填，作者无需传 | 作者零负担 |
| 插件仓 | 删除「整片摘＋手写补注册」与同 id 双注册 | 02 的验收对象 |

## 四、判据（对着 07 过一遍）

- **归一化**：`activation` 只有一个真相源（注册上下文）；注销只有一个机制（作用域分区）。⛔ 保留第二套「补注册」。
- **无硬编码**：⛔ 壳里出现任何插件 id / 视图 id 字面量；作用域由运行期对象标识，⛔ 不按名字判。
- **无死代码**：`placeholder` 从「只打 warn 的桩」变为「懒激活入口 ＋ 声明提示」；`_cmdMap.size <= 1` 整段删除。
- **高内聚低耦合**：壳只认 `activation/scope` 两个通用标记，⛔ 不知道任何插件的业务；插件不感知壳的注册表结构。
- **AI 友好化**：`describe` 事先说清 → AI 不试错；失败给码 + hint → AI 能自纠。

## 五、不做

- ⛔ **不做「所有命令都无视图可调」**：视图态命令（`copy`/`clear`/`exportLog`/`togglePause`/`quickSend*`）本来就依赖视图像素与编辑态，强行无视图化是把 UI 状态搬到后台，属于过度抽象。
- ⛔ **不做「自动 UI 遮罩」**：不要为了满足 AI 而偷偷创建一个不可见 tab（那会把用户布局写脏）；要无视图就真的无视图。
- ⛔ **不做按插件白名单**：任何 `if (pluginId === ...)` 一律禁止（硬约束 10）。
- ⛔ 不把 `when` 升级成权限闸——可见性与可达性是两件事。

## 六、验收

1. **无视图可用**：不开任何标签页，`openPort`/`send`/`readSince` 均成功。
2. **可预判**：`describe` 里每条命令带 `activation`；`view` 类的 `needs` 一目了然。
3. **可判读**：无视图调 `copy` ⇒ `EVIEWREQUIRED` + hint「先 open-tab serial-monitor」；插件被禁用 ⇒ `ENOTACTIVE`。
4. **注销不误伤**：开两个 serial-monitor 标签，关掉其中一个 ⇒ 另一个的视图态命令仍可用、插件级命令全程可用。
5. **无双注册**：`quickSendEdit` 只剩一个作用域，重开视图不改变生效者。
6. **跨领域**：file-tree 的 `selectForCompare` 同样给出 `EVIEWREQUIRED`（⛔ 不是串口特例）。
7. `npm run check` 全绿（含新增审计腿）。
