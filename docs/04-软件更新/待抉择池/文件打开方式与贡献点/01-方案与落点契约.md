# 01 · 方案与落点契约（T1–T7 逐格）

> 本文是 [00-README](00-README.md) §四任务表的逐格展开：每格 = 现状（file:line）→ 改法（改哪、怎么改、改成什么）→ 判据 → 门禁连锁。**本文只规划，不动码**；开工时逐格照抄落点。
> 归属总纲（用户 2026-10-04 拍板口径：无死代码、无硬编码、AI 友好、高内聚低耦合、万物皆可插件）⇒ 本案三条铁律：
> ① **判定归壳、呈现归插件、配方进 `@linkdesk/ui`**——壳只回答「这是什么、谁能开」，绝不画任何文件的内容或兜底页；
> ② **壳不认识任何插件 id**——兜底用**角色声明**解析（T7），不写死 `"editor"`；
> ③ **插件只声明、不耦合**——阅读器抢默认就声明 `fileAssociations`，做次要方式就声明 `menus.fileContext`＋命令；换掉任何一只，壳与别的插件零改动。
> ④ **默认打开方式的主权在壳（=用户覆盖表，背后是用户），插件只有提名权（声明=候选），文件树只有执行权（查表就开）**——插件永不自封默认。多只 PDF 阅读器共存（微软/Adobe/第三方）全靠这条：谁都在「打开方式」选择器里并列，谁也不是特权层。

```
声明面（插件 plugin.json）          判定面（壳，多提供方多消费方）         呈现面（各插件自己画）
contributes.fileAssociations  ──▶  FileAssociationService（映射表        ▶ file-tree：选择器 UI
  [{ext, command?, displayName?,      ＋用户覆盖表＋角色解析）                 ▶ editor：文本/兜底页
    role?}]                       ──▶  getPluginFor / listHandlersFor      ▶ pdf·图片·md 阅读器：各自视图
contributes.menus.fileContext   ──▶  MenuRegistry（合并＋when 过滤）     ▶ 任何插件：菜单项
context keys（公共 resourceExtname）▶ ContextKeyService.matches
OS argv／安装器关联             ──▶  useOpenPathIntake（同一次解析）
```

## T1 二进制守卫＋未关联兜底（判定归壳 · 呈现归插件 · 配方进 ui 包）

**现状**：`EncodingService.detect`（`src/core/services/files/EncodingService.ts:132-148`）只测 BOM/UTF-8 有效性/GBK 特征，**无二进制检测**；editor `EditorModel.load`（`E:\linkdesk-plugins\official\editor\src\services\EditorModel.ts:100-106`）读二进制强解文本 ⇒ pdf/exe 开成不报错的乱码。

**改法（三层各一段）**：
1. **壳判定**：`EncodingService` 新增 `isBinary(bytes)`（启发式：首 8KB 内 NUL 字节占比／控制字符密度，阈值拍板时定；**纯函数、可单测**）并经既有 files IPC 面暴露给插件（`filesystem.isBinary` 或 detect 结果加字段——落点按现 API 面定，⛔ `configuration.get` 那次「表面不可动」的同款纪律：先探再动，additive only）。
2. **`@linkdesk/ui` 共享组件**：`FileOpenFallback`（能力注入式，同 `BackgroundImagePicker` 先例：**零 `window.linkdesk` 直呼**）——props `{ fileName, extension, onOpenWith?, onMarketSearch? }`；渲染「无法作为文本显示」＋两颗钮。按钮是可选注入：用方不注入就不渲染该钮。
3. **editor 参考实现**：`EditorModel.load` 拿到 `isBinary` ⇒ 渲染 `FileOpenFallback`，两颗钮分别接宿主命令（T2 的 `file-tree.openWith` 选择器；市场搜索=扩展名关键词）。editor 是**参考实现**不是特权层——它只是今天声明了最多扩展名、恰好被兜底的「方式之一」。

**判据**：① `isBinary` 纯函数单测（pdf/exe/png 头 → true；md/ts/json → false；负控：摘掉 NUL 检查 → pdf 判假）；② editor 对 pdf 呈现兜底页不再乱码（截图读数）；③ 第二个作者视角验证：任一最小插件 consuming `FileOpenFallback` 十行内出同款页。

**门禁连锁**：新用户可见串走**外仓 `lang-defaults` 发版链**（`audit-i18n --strict` 会拦）；`@linkdesk/ui` 发版走 **npm 列车错峰**（`check-api-surface-additive` 全绿才发）；作者面文档同步（`generate-plugin-docs`）。

## T2 打开方式选择器＋用户覆盖表

**现状**：`file-tree.openWith` 是占位（`E:\linkdesk-plugins\official\file-tree\src\components\FileTreeContextMenu\commands\navigation.ts:63`）；`FileAssociationService` 只有 `getPluginFor` 单答，无「列全部」、无用户覆盖；**行为不一致**：FoldersView 查不到落 editor 兜底（`FoldersView.tsx:122-131`），SearchView 查到不到**静默不打开**（`SearchView/openMatch.ts:11-21`）。

**改法**：
1. **宿主新只读面**：`fileAssociation.listHandlersFor(ext)` → `[{pluginId, displayName, isCurrent}]`（IPC＋preload＋主进程 handler，additive）。单答 `getPluginFor` 保留但内部改走统一解析函数。
2. **解析序归一**：提取纯函数 `resolveOpenTarget(ext, override?)`＝**用户覆盖表 → 声明表（稳定序）→ 角色兜底（T7）**；FoldersView／SearchView／`useOpenPathIntake.ts:66-71` 三处消费同一次解析（**消灭「SearchView 静默」与「FoldersView 落兜底」的分叉**——两处行为统一为：有 handler 开之，无 handler 走 T1 兜底页）。
3. **用户覆盖表**：`settings.json` 键 `workbench.fileAssociations`（D1，`{".pdf":"my-pdf-reader"}`）；壳 `FileAssociationService` 读它为最高优先级；设置基线 `check-config-baseline` TARGETS 同笔登记。
4. **选择器 UI 住 file-tree**（呈现归插件）：实现 `openWith` 占位——列 handler＋默认标记＋「仅此一次／始终」；「始终」写覆盖表。UI 是 file-tree 的命令与组件，数据来自宿主面 ⇒ 换一套文件树插件，选择器跟着文件树走，壳零感知。
5. **第二只同类型插件装上不静默漂移**（D7）：激活事件后若发现另一插件声明了同一扩展名且用户从未选过 → toast「检测到另一款 PDF 阅读器，当前默认仍是 X——右键→打开方式可换」；消费 `listHandlersFor` 的 `isCurrent` 标记，不新增面。

**判据**：① 覆盖表写入后重启仍生效；②「仅此一次」不落盘；③ 覆盖表清空 → 回声明序；④ 三入口（文件树/搜索/OS intake）解析结果一致（同一纯函数的三个消费方，负控=改一处解析另两处行为跟随）。

**门禁连锁**：`host-reserved` 三处账本（壳 json／SDK schema／运行时 ts——新 IPC 面）；`generate-contract`／`gen-api-surface`／`manual:build` 生成物重生；i18n 新串走 lang-defaults。

## T3 公共 context key（`resourceExtname`）

**现状**：file-tree 注入的是**私有旗子**（`itemIsFile/itemIsDir/itemIsRoot/resourceReadonly`，`FileTreeContextMenu/Menu.tsx:25-50`）——第三方 `when` 无文件属性可判；壳有现成 when 求值与宿主保留键账（`ContextKeyService`；`settingsSlotFilled` 由 `usePoolSync.ts:155` 推送、进 `host-reserved.generated.ts:81`）。

**改法**：file-tree 在同一注入点增注**公共键** `resourceExtname`（带点小写，VS Code 同名口径，如 `".md"`）与 `resourcePath`（或按需最小集）；键名进宿主保留 context key 账（**写权限=file-tree**，读=任何插件——与 `settingsSlotFilled` 同构，D2）。菜单声明方即可写 `when: "resourceExtname == .md"`。

**判据**：第三方样例插件 `when: "resourceExtname == .md"` 对 .md 出现、对 .txt 不出现；file-tree 自有菜单在无文件上下文（根节点）时公共键未定义、不误判。

**门禁连锁**：host-reserved 账本＋SDK context-ownership 自测；作者面文档（T5 一并写）。

## T4 受控 openExternal 通道

**现状**：`shell.openExternal` 仅主进程内部用（`electron/windows/external-links.ts:29`，window-open 拦截路由）；preload 池未暴露（`namespaces-plugin.ts` 无此方法）。

**改法**：`namespaces-plugin.ts` 新增 `shell.openExternal(url: string)` → 主进程 handler：**scheme 白名单**校验（D5：`http/https/mailto` ＋ 常量登记的已注册协议如 `vscode`；`file:`/`javascript:`/`data:` 明确拒绝）→ Electron `shell.openExternal`。白名单即宿主保留账（host-reserved），第三方不进账不用改——白名单是**协议级**不是插件级。

**判据**：正例 `vscode://file/E:%5Cx.md` 拉起 VS Code；负控 `file:///C:/x`、`javascript:` 被拒（红测）；`openExternal` 出现在 host-reserved 面，`check-api-surface-additive` 绿。

**门禁连锁**：host-reserved 三账本＋contracts 重生＋manual:build；主进程 IPC 审计面（`check-ipc-audit`）。

## T5 菜单贡献点收口（自[菜单补全](../菜单补全.md)剥入）

**现状**：槽位机制已通（`MenuRegistry.ts:18-53` 14 槽；`contributes.menus` 解析在 `contributions.ts:147-152`）；缺的是**规范与文档**——`菜单补全.md`（2026-09-13 写）设想的斜杠命名 `explorer/context` 与现行小驼峰 `fileContext` 不一致，且那份文档不知道 fileContext 已存在；第三方无「往文件树右键加项」的正式指引。

**改法**：① **命名拍板（D2 附带）**：建议**保持小驼峰现状**（`fileContext` 等 14 槽已有消费者与生成器账本 `host-menu-slots.json`；改名＝breaking 全部现有声明，收益仅是审美）——`菜单补全.md` 的历史设想在文档里注明已被现实超越；② 作者面新文档「菜单贡献点」：槽位清单、`group` 排序约定（VS Code 口径 `navigation`/`1_x`/`2_x`）、`when` 与公共 context key 表（接 T3）、命令 id 归属纪律（`check-command-ownership` 已拦前缀顶替）；③ SDK 腿：`host-menu-slots.json` 已防「成员名当值」，补一条作者文档同步检查（`generate-plugin-docs` 链）。

**判据**：第三方照文档从零声明到出现在文件树右键**不问人**（AI 友好化口径：手册可达、门禁可查）；`npm run check` 作者文档链全绿。

## T6 OS 关联与插件状态同步（解「薛定谔的猫」）

**现状**：`build/installer/bootstrapper/syswrite.cpp:60-64` 写死 13 扩展（txt/py/js/json/md/html/css/ts/tsx/yaml/xml/csv/log）＋ ProgId `LinkDesk.Document` ＋ `*\shell` 全文件右键项。两个病：① **第二真相源**——清单与插件声明脱节（editor 声明 45 扩展、安装器只登记 13，**已经漂移**；违反归一化，用户 2026-10-04 点破）；② **薛定谔态**——登记 `.pdf` 时本机未必装着 pdf 阅读器，登记了等于把用户引到乱码页；不登记，装了阅读器的用户又少掉 OS 入口。

**改法（静态走向动态，三步）**：
1. **静态清单瘦身＋构建期生成**：随包 6 基础件的 `contributes.fileAssociations` 在安装包构建期**机械收割**（构建链本来就拉随包插件、`bundled-plugins.lock` 在账）→ 生成 `syswrite.cpp` 的扩展数组——单一真相源 = 插件声明，漂移从机制上消灭。随包件全是文本类 ⇒ 这份静态默认**不薛定谔**（editor 真开得了）。**exe 永不登记**（无插件能开，登记 exe 打开器本身危险）。
2. **运行期同步**：主进程新增小模块——订阅插件**安装/激活/卸载**事件，对「该插件声明了、随包件未声明」的扩展名按设置页开关**增/撤** OS 登记（HKCU `OpenWithProgids`，per-user 无需提权；Windows 走注册表直写或 `reg` 子进程，macOS/Linux 后议）。设置页「系统集成」组出**「系统『打开方式』」**块：列随包＋已装插件声明的扩展名、每项开关（D6）。
3. **与「安装器-更多配置」的接缝**：安装时的勾选清单 = 同一份账的**静态半**（预选=随包件），运行期同步管**动态半**——两案一份账，⛔ 别立第二处真相源。

**判据**：① 构建期生成的清单与随包件声明逐字节一致（负控：手工往 `syswrite.cpp` 加一个不在任何声明里的扩展 → 门禁红）；② 装阅读器插件 → OS「打开方式」出现 LinkDesk；卸载 → 撤（或按开关保留）；③ exe 永不出现在候选；④ 覆盖安装不残留已卸插件的登记。

## T7 DEFAULT_TAB_TYPE 去硬编码（角色声明）

**现状**：`tabs.ts:14` 写死 `DEFAULT_TAB_TYPE="editor"`——壳认识具体插件 id（证据⑧）；file-tree 反而没写死（传空串）。卸载/替换 editor 后兜底指向不存在的插件，再落 `FALLBACK_PLUGIN_ID="welcome"`（`fallbackPluginId.ts:8`，另一处硬编码，**本件不动**——那是视图加载失败的另一件事）。

**改法**：① schema：`fileAssociations` 条目加可选 `"role"`（首版仅 `"text-fallback"` 一枚，进作者面）；② 壳：`FileAssociationService` 建角色索引（激活插件中声明了 role 的）；`tabs.ts` 的兜底从常量改为 `resolveFallbackTabType()`＝查角色索引；③ editor 的 plugin.json 45 条扩展名**原样保留**、同笔补 `role:"text-fallback"`；④ 无人声明角色 ⇒ 不再塞给不存在的插件：走 T1 兜底页语义（开 welcome＋toast 提示装编辑器——此形态官方 editor 随包在场（seed）几乎不可达，判据仍要写）。

**判据**：① 单击 txt 仍开 editor（默认行为零变化）；② 临时样例插件声明同角色并激活 → 单击 txt 开**它**（第三方整体接管兜底位，零壳改动）；③ 卸载所有声明角色的插件 → 兜底页＋提示，不再乱码/白屏。

**门禁连锁**：schema 四份字节拷贝（`check-plugin-schema-sync`）；`FileAssociationService` 单测；作者面文档（T5 同笔）。

**顺序**：T1（判定＋共享组件）→ T7（角色）→ T2（选择器，吃 T1/T7 的解析函数）三格串行（同改 `FileAssociationService`／`tabs.ts`）；T3、T4、T5 三格相互独立、随时可插；T6 跟「安装器-更多配置」走。
