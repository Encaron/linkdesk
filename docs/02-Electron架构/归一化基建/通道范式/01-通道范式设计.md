## §1 背景——用户的核心担忧

**问题链（2026-08-20 四轮问答）：**

1. 串口多串口是插件功能扩展——为什么还要改壳？
2. 第三方作者以后要实现多串口/多模态，总不能每个都要找壳作者帮忙吧？
3. 第三方作者做 CAN、逻辑分析仪这类设备插件，软件作者是不是也要买设备、做测试、发版本？
4. 数十万个插件，难道软件版本要升级数十万次？

**核心担忧（用户亲口确认）**：如果连插件功能扩展（多串口）都要改壳，则「万物皆插件」是假的；第三方复杂/进阶功能到头来都要依赖壳作者改壳 → 壳一点一点长回重量级软件（VS Code 甩不掉 Monaco 同款）→ 平台作者被绑死在核心维护上，当不成「圆形大厅的建筑师」，只能当每个房间的装修工。

**真相**：这个担忧的根源是一个历史遗留——串口是第一个数据源插件（壳插件未分离时代），把「单口互斥」这种串口监视器专属的 UX 决策长进了壳的 `serial-service.ts`（openPort 先关旧口）。这是「专属假设」的标本：能力存在但带着插件专属行为。E5.8 的全部工作 = 把这类历史单例假设清零。

## §2 核心原则——通道范式宣言

```
设备无限归插件          —— CAN/逻辑分析仪/GPS/烧录器/示波器……设备永远在插件，壳一个都不认识
通道收敛归壳            —— 串口/USB/网络/蓝牙……传输介质可枚举，壳只提供「打开 → 流式读写 → 关闭」
平台测通道 · 作者测设备  —— 平台用最少硬件验证通道正确；设备协议正确性由作者自持
插件发布永不触发壳发版  —— 设备插件进市场，壳版本纹丝不动；壳发版仅因壳 bug 或加新通道
```

**类比（行业标准分工）**：
- Windows 不测你的打印机驱动——打印机厂商测。Windows 只保证打印子系统正确。
- VS Code 不测调试器扩展——各语言工具链作者测。
- Linux USB 子系统作者不需要买世界上所有 USB 设备——他保证通用 USB 栈正确，设备驱动由厂商/社区写。

**责任分工表：**

| | 平台作者 | 插件作者 |
|:--|:--|:--|
| 职责 | 通道正确 + API 稳定承诺（版本化演进） | 设备测试 / 协议解析 / 发布 |
| 需要的硬件 | 最少（手头已有的够测通用字节流） | 自己的目标设备 |
| 领域知识 | 通道语义（打开/流式读写/关闭/错误/多实例/资源回收） | 设备协议（CAN 帧/NMEA/采样） |

## §3 判定标准——改壳的边界

**改壳 = 加通用通道，不是加设备业务。**

- **加通道**（允许，且是「改壳」的全部含义）：出现全新的传输介质（串口 → 已建；USB/网络 → 未来版本化演进候选）。通道 = 打开/流式读写/关闭/错误语义/多实例/资源归属，**不含任何插件专属行为**（插件 ID 零硬编码——硬约束 10）。
- **加设备**（永远不允许）：任何具体设备协议、解析、交互长进壳。设备解析归插件，壳不认识任何设备。

**次数是收敛的**：要改壳 = 每通道一种（传输介质几十种封顶），不是每设备一次（设备无限）。

**版本化演进**：E6 上架后加新通道 = 加 API + 版本声明（VS Code `engines.vscode` 同款），加了不违约、不加不影响现有插件。破坏性变更窗口收敛在 E5.8（上架前无第三方存量插件，现在改零代价）；E5.8 后改壳 = 破坏存量第三方 = 违约。

**不能承诺「永远不改壳」**（不诚实）——真正的保证是：改壳只在出现全新资源通道类型时发生，且收敛、可枚举、走版本化演进。

## §4 通道 vs 设备——分层可行性全景

第三方作者做设备插件，按传输介质分三层：

| 层 | 设备示例 | 通道 | 状态 |
|:--|:--|:--|:--|
| **串口系**（最大头） | USB-CAN 适配器（CH340/CP210x 虚拟串口）、GPS 模块（NMEA）、USB-TTL、便宜的逻辑分析仪 | `linkdesk.serial.*`（Phase 6 通用化后） | ✅ **Phase 6 后立即可写，零壳依赖**；多口/多插件并存成立 |
| **自定义 USB** | 专业逻辑分析仪（Saleae 类，自定义 USB 端点） | usb 通道 | ⏳ E6 后版本化演进加一条通用 usb 通道（一次性，同 serial 同构）；加完所有 USB 设备可写 |
| **厂商私有 DLL** | 高端设备（只有厂商 SDK/DLL） | 原生通道 | ⚠️ 独立架构课题（渲染沙箱无 Node 权限，vs VS Code 扩展宿主 = Node 可 require DLL）；非 E5.8 范围 |

**每补一条通道，第三方生态扩大一大块，且是一次性。** 不补通道不违约（不建空框架——§12）。

## §5 VS Code 实证（源码证据，2026-08-20 实查）

**VS Code 核心零串口：**
- `src/vs/workbench/contrib/serial` → 404
- `src/vs/platform/serial` → 404
- 核心 `package.json` grep `serialport` → 0 命中

**串口是独立扩展**：微软官方维护 `ms-vscode.serialmonitor`，独立发布 marketplace + 独立 API 包 `@microsoft/vscode-serial-monitor-api`。串口不是 VS Code 的能力，是扩展的能力。

**为什么设备代码能住在扩展里——扩展宿主 = Node 进程**：`src/vs/workbench/api/node/extensionHostProcess.ts` 实证：
```typescript
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
// process.execArgv / require('module') patch → 扩展可 require 任意原生模块
```
VS Code 扩展跑在完整 Node 环境，可以 `require('serialport')` 甚至厂商 DLL——**所以 serialport 原生绑定直接进扩展，核心零负担**。

**模型对比：**

| | VS Code | LinkDesk |
|:--|:--|:--|
| 核心 | 零串口 | 零串口（目标，Phase 6 去专一化中） |
| 设备驱动位置 | 扩展里（扩展宿主 = Node，serialport 自带） | 主进程通用通道（插件沙箱无 Node 权限） |
| 插件权限 | 扩展宿主 = 完整 Node 权限 | 渲染沙箱 + `linkdesk.*` 白名单 IPC |
| 安全代价 | 恶意扩展 = 全磁盘读写 | 插件无权限，壳按需补通道 |

**殊途同归**：核心都不管具体设备。差别在 Node 能力授予方式：VS Code 把整个 Node 给扩展宿主（能力全，安全靠信任扩展）；LinkDesk 收口成白名单 IPC（更严安全，代价 = 壳按需补通道）。LinkDesk 的等价物 = 「壳收口成通用通道」，设备逻辑永远在插件。

## §7 边界与不做

- **USB/原生通道现在立案实现** → 不做。无消费者 + 不建空框架（§12）；触发条件 = 真实设备作者需求出现时版本化演进。
- **平台作者买设备/写示例设备插件** → 不做。违背「作者测设备」分工，是抢第三方作者的活。
- **通用连接框架 `linkdesk.connections`** → 不做（同 §12 边界）。
- **键控路由升格壳 hook** → 不做（E6 出现第二键控信息源时评估）。
