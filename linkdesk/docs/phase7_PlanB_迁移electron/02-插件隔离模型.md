# 02 — 插件隔离模型

> 2026-07-23。这是整个 Plan B 方案最关键的架构决策。
> **为什么选独立 WebContentsView per 插件，不选 VS Code 的共享 Extension Host。**

---

## 一、两种模型——用朴素的比喻

### 模型 A：独立别墅（独立 WebContentsView per 插件）

```
插件 A (终端)  → 自己的 Chromium 渲染进程  → 🔥 崩了 → 只崩自己
插件 B (地图)  → 自己的 Chromium 渲染进程  → 🔥 不受影响
插件 C (文档)  → 自己的 Chromium 渲染进程  → 🔥 不受影响
```

**隔离强度：进程级。** 每个插件是操作系统级别的独立进程。A 和 B 之间没有共享内存、没有共享 JS 上下文、没有共享事件循环。

### 模型 B：同一间宿舍（共享 Extension Host）

```
Extension Host (一个 Node.js 进程)
  ├── 插件 A 的 activate()  → 🔥 崩了 ↓
  ├── 插件 B 的 activate()  → 🔥 也被迫重启
  └── 插件 C 的 activate()  → 🔥 也被迫重启
```

**隔离强度：try/catch 级。** 所有插件在同一个 Node.js 进程里。进程崩了 → 全崩。进程卡了 → 全卡。同进程内插件 A 能读到插件 B 的堆内存。

---

## 二、VS Code 为什么选模型 B——历史原因，不是安全原因

### 2.1 官方文档怎么说的

VS Code 官方文档 [Our Approach to Extensibility](https://vscode-docs.readthedocs.io/en/latest/extensions/our-approach/) 给出了 Extension Host 的三个设计动机：

1. **防止扩展影响主编辑器启动速度和稳定性**——不是防止扩展之间互相影响
2. **防止扩展直接碰 DOM**——强制走 API，避免 VS Code UI 升级时扩展挂掉
3. **用户始终可控**——不管扩展在干什么，用户都能正常打字、保存

**注意：官方说的是"保护 VS Code 不被扩展搞崩"——不是说"保护扩展之间互相隔离"。**

### 2.2 为什么不每个扩展一个进程——2015 年的硬件

官方没有明确说"因为内存"，但事实是：

- VS Code 1.0 发布于 2015 年
- 2015 年主流笔记本电脑内存 = 4-8GB
- VS Code 默认装几十个扩展，重度用户装几百个
- 每个 Node.js 进程 ~50MB → 几百个扩展各开一个进程 = 10-20GB 内存
- **在 2015 年的硬件上根本跑不动**

这不是安全决策——是资源决策。

### 2.3 共享进程的安全代价——有研究记录

第三方安全研究 [Access Control and Sandboxing for VS Code Extensions](https://github.com/Aymaan-Ashhab-Ahmed/Access-Control-and-Sandboxing-for-VS-Code-Extensions) 的原文：

> "This shared-process model **protects VS Code from extensions, but provides little protection between extensions or for the user** — a malicious extension in the shared host can potentially access data from other extensions."

翻译：**共享 ExtHost 保护了 VS Code 不受扩展影响，但扩展之间几乎没有保护——恶意扩展能读到其他扩展的数据。**

### 2.4 VS Code 自己在做什么——进程集群

VS Code 1.31 引入了 `extensions.experimental.affinity`——允许扩展分布到多个 ExtHost 进程。开发模式（`--extension-development`）每个扩展独立进程。

**他们在往"更多进程隔离"的方向走——但几十万扩展的兼容性让他们不能直接切。** 这是一个历史包袱，不是一个最佳实践。

### 2.5 结论

| 事实 | 含义 |
|------|------|
| VS Code 选共享 ExtHost | 2015 年内存不够——不是因为它更安全 |
| 共享进程 = 扩展间无隔离 | 安全研究确认的缺陷 |
| VS Code 在往多进程方向改 | 但历史包袱太重，只能渐进 |
| **LinkDesk 2026 年起步** | **没有历史包袱——不需要继承 2015 年的妥协** |

## 三、第三种模型——网页 AI 和我的方案各在主张什么

### 网页 AI 的方案

```
Electron Main Process
  ├── Shell Window (壳 UI)
  └── Extension Host (共享 Node.js 进程)
      ├── 插件 A activate()
      ├── 插件 B activate()
      └── 插件 N activate()
          │
          └── postMessage 通信 ↓
  ┌─────────────────────────────────┐
  │ WebviewView 1 (插件 A 的 UI)     │
  │ WebviewView 2 (插件 B 的 UI)     │
  │ WebviewView N (插件 N 的 UI)     │
  │  每个是独立沙箱 HTML              │
  └─────────────────────────────────┘
```

- **逻辑层：** 共享 ExtHost——所有插件的 `activate()` 在一个 Node.js 进程里
- **UI 层：** WebviewView——每个插件的 UI 是独立沙箱 HTML
- **代价：** 插件逻辑崩了 → ExtHost 重启 → 所有插件重载

### 我的方案

```
Electron Main Process
  ├── Shell Window (壳 UI)
  ├── WebContentsView 1 (插件 A——终端 React 组件)
  ├── WebContentsView 2 (插件 B——地图 React 组件)
  └── WebContentsView N (插件 N——...)
      每个是独立 Chromium 渲染进程
      崩了只崩自己
```

- **逻辑 + UI 在一起：** 每个插件在自己的 WebContentsView 里跑 React 组件——逻辑和渲染不分离
- **隔离：** Chromium 进程级隔离——A 崩了不影响 B
- **代价：** 内存消耗更高（每个插件独立 Chromium 进程）
- **对标：** VS Code 的 WebviewView 本身就是独立进程——我们只是把"逻辑"和"UI"放在同一个进程里，而不是拆成 ExtHost + WebviewView 两块

### 为什么我的方案隔离更强

| 攻击场景 | 共享 ExtHost | 独立 WebContentsView |
|------|:--:|:--:|
| 插件 A 死循环 | ExtHost 卡死 → 所有插件全停 | 只卡自己的 WebContentsView |
| 插件 A 内存泄漏 | ExtHost heap 泄漏 → 所有插件受影响 | 泄漏在自己进程 → 关标签页 OS 回收 |
| 插件 A 未捕获异常 | ExtHost 重启 → 所有插件重载 | ErrorBoundary 兜底 → 只影响自己 |
| 插件 A 读插件 B 数据 | **能读到**（同进程 heap） | **读不到**（独立进程，独立 heap） |
| 插件 A 调 `require('child_process')` | 能——如果没有 API 限制 | 不能——preload 不暴露 |

## 四、对 LinkDesk 的未来意味着什么

### 场景推演

**2028 年。** LinkDesk 插件市场有 200 个插件。

**如果是共享 ExtHost（模型 B）：**

用户装了 50 个插件。插件 #37——一个社区写的 Modbus RTU 协议插件——有个内存泄漏 bug。它慢慢吃掉 ExtHost 的 heap。30 分钟后 ExtHost OOM 崩溃。**50 个插件全部重载。** 包括正在收 GPS 数据的终端、正在实时渲染波形的逻辑分析仪、正在编辑文件的 Monaco 编辑器。

用户不知道是哪个插件导致的。他只知道 "LinkDesk 崩了"。

**如果是独立 WebContentsView（模型 A）：**

同样的插件 #37 泄漏。它只在自己进程里泄漏。30 分钟后它的 WebContentsView 被 OS OOM killer 杀掉。**其他 49 个插件正常工作。** 用户看到终端标签页闪了一下——关掉重新打开，正常。他甚至没注意到地图插件和文档插件完全没受影响。

**这就是进程级隔离 vs try/catch 级隔离的差别。不是理论——是用户感知。**

### 内存代价可以接受——而且 ExtHost 方案在进程级隔离下反而更贵

每个 WebContentsView ~60MB。装 10 个插件 ~600MB 额外内存。

**注意：** 初版分析简单对比了"共享 ExtHost（低内存）vs 独立 WebContentsView（中内存）"。经过逐进程拓扑对比（`08-多WebView-vs-ExtHost-开销对比.md`）：
- **进程级 WebviewView 的 ExtHost 方案 = ExtHost 进程（50MB）+ N×WebviewView 进程（70MB 每个）= 比独立 WebContentsView 更贵**
- **iframe 级 WebviewView 的 ExtHost 方案 = ExtHost 进程（50MB）+ N×iframe（10MB 每个）= 确实更省，但牺牲插件 UI 隔离**

2026 年主流笔记本 = 16GB 起步。2030 年可能 32GB 起步。

**独立进程的内存代价随着时间递减——硬件越来越便宜。共享进程的安全风险随着插件数量递增——生态越大隐患越大。**

## 五、结论

| 维度 | 共享 ExtHost | 独立 WebContentsView | 胜出 |
|------|:--:|:--:|:--:|
| 隔离强度 | try/catch 级 | OS 进程级 | **独立** |
| 插件崩影响面 | 全部插件 | 只崩自己 | **独立** |
| 恶意插件防护 | 弱——同进程可读 heap | 强——独立进程 | **独立** |
| 内存占用 | 进程级 WebviewView = WebContentsView——但多一个 ExtHost 进程（+50MB），反而更贵。iframe 级省内存但牺牲隔离。**详见 08。** | 每个 view 插件独立进程，未打开不创建 | **独立**\* |

\* **关于内存的澄清：** 初版分析简单标了"ExtHost 低，独立中"——经过逐进程拓扑对比（见 `08-多WebView-vs-ExtHost-开销对比.md`），发现**进程级 WebviewView 的 ExtHost 方案在所有场景下内存都更差**（多一个 ExtHost 进程）。iframe 级 WebviewView 确实更省，但牺牲了插件 UI 隔离——对 LinkDesk 的第三方插件生态不可接受。
| 历史包袱 | VS Code 2015 年的妥协 | 2026 年起跑——无包袱 | **独立** |
| 未来趋势 | VS Code 在往这边改 | 天然支持 | **独立** |

**独立 WebContentsView 是 2026 年从零起步的正确选择。** VS Code 选共享 ExtHost 不是因为"最安全"——是因为 2015 年做不到。LinkDesk 在 2026 年起跑，没有义务继承 2015 年的妥协。
