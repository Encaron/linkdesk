§二 头部按钮：旧的撤掉，换这两个

按钮现在改后
「清除全部」 删掉 store 里所有通知（含进行中的）。此后进度更新静默失效、永不再现 改名「清除已完成」：只清已完成/已读的旧消息，进行中的一条不碰，面板本身不关
「×」 关闭面板 —— 和"最小化"看着一样，但它是"关掉"，最容易误点（你点的就是它） 撤掉。关闭面板这个动作由「最小化」承担，语义只有一个：收起，什么都不丢
🆕「最小化」 不存在 把面板收起来 —— 任务照跑、进度不丢；想看时点铃铛
为什么不是"三个按钮都在"：如果「×」和「最小化」并存，它们在观感上是同一个动作（窗没了），结果却相反（一个销毁、一个保留）——这种同形不同义就是误点的温床。所以只留一个。

§四 并行 30 条 —— 现在的代码根本跑不起来 界面之下有三堵墙，必须先拆

墙一：软件是「一次只能装一个」的。 marketplaceShared.ts:591-593 写死：另一个插件正在装时，新的安装请求 直接 return false，而且不告诉用户任何话。所以你说的"连点 30 个插件"—— 从第 2 个开始全部静默失败。这就是为什么你从没见过并行进度：不是界面没画，是根本没发生过。
墙二：进度条不知道自己是「谁的」进度。 plugin-install-handlers.ts:50-52 的进度走一条全局广播通道 plugin:installProgress， 而下载那一段（:74-78）推的进度不带插件 id。 意思是：就算拆了墙一放开并发，界面收到的也是一串没有署名的「45%」——分不清是哪个插件的。
墙三：软件里根本没有「装一个自动带上依赖」这条腿。 现在的安装只管它自己那一个包——依赖缺失时只弹一句「因依赖 X 消失转入等待」 （src/pluginLoader/resolution/loadState.ts:216-221）， 没有任何代码去把缺的依赖下下来。所以「点 STM32 会带出 30 个插件」这件事， 今天在软件里压根不会发生——不是慢、不是排队，是这条腿还没长出来。
所以「30 条并行」是四层活，不是一件：
层 0 · 触发——先得有「装 A 就自动取来它依赖的 B、C、D…」这条链（墙三）。没有它，后面三层都无从谈起
① 放开单会话（墙一）——并先定：是真并发，还是排队一条条装？（真并发要考虑带宽与磁盘竞争，排队更稳但就不是"同时"了）
② 给进度加身份（墙二）——每条进度带上 pluginId / 安装 id，界面才能归位
③ 界面——头部加最小化 + 30 条列表 + 展开/收起状态机

③ 才是你现在催的那件事，但它单独做出来，你点了 STM32 一样只会看到一条。所以我把这四层一起摆出来，由你决定这次做到哪一步。

§五 进度条四态 回答"为什么老是来回滚的条"

形态什么时候出现你看到的样子说明
① 真百分比
0→100 实心涨		 下载中，且服务器给了包大小 蓝色实心条慢慢爬 已经做了（实测填充 = 42%）。但只在下载段存在，而小包一瞬就下完
② 有信息量的不定态（改） 下载中，但服务器没给包大小 改显「已下载 3.2 MB」 你看到「老是来回滚」的真因就在这一格——不是包太小。收到的字节数本来就知道，数字至少在涨。真数值永远优先于动画
③ 阶段文字（本图采用） 解压 / 校验 / 落盘 / 启用 百分比位置改显「解压中」「校验中」 这几步物理上算不出百分比。编个假数字会卡在 87% 不动，比扫动更难受。改显阶段名 = 真信息；30 条并行时文字也比点阵省地方
④ 完成 装完 条填满 + 「已完成」 留在原位，不移到别处、也不整条消失——30 条并行时任何位移/消失都会让列表跳动，把用户正盯着的那一行挤走
