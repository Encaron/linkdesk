## 缺口 1：Vite 构建配置——具体改什么

### 1.1 现状（读 `vite.config.ts`）

当前 Vite 配置服务于 Tauri 单 WebView 模式：

```typescript
// vite.config.ts 关键点
const host = process.env.TAURI_DEV_HOST;                    // ① Tauri dev host
server: { port: 1420, strictPort: true, host: host || false,
  watch: { ignored: ["**/src-tauri/**", "**/plugins/**"] }  // ② 忽略 src-tauri + plugins
},
build: {
  rollupOptions: {
    input: {
      main: resolve(__dirname, "index.html"),                // ③ 壳 + 插件同入口
      ...pluginEntries,  // "plugins/terminal": "plugins/terminal/index.tsx"
    },
    output: {
      entryFileNames: (chunkInfo) => {
        if (chunkInfo.name.startsWith("plugins/")) {         // ④ 插件独立 chunk
          return `${chunkInfo.name}.js`;
        }
        return "assets/[name]-[hash].js";
      },
    },
  },
},
resolve: { alias: { "@src": resolve(__dirname, "src") } },  // ⑤ @src/ 别名
```

### 1.2 Electron 后需要的变更

#### 删除项

| 行 | 内容 | 原因 |
|---|---|---|
| `const host = process.env.TAURI_DEV_HOST` | Tauri dev host 变量 | 不再需要 |
| `host: host \|\| false` | server.host 配置 | 不再需要 |
| `hmr: host ? { protocol: "ws", host, port: 1421 } : undefined` | Tauri HMR 配置 | Electron 用标准 Vite HMR |
| `ignored: ["**/src-tauri/**", "**/plugins/**"]` | watch 忽略 | `src-tauri/` 整个删除。`plugins/` 需要保留 watch——Electron 下插件变更应触发 HMR |

#### 修改项

| 当前 | 改为 | 原因 |
|---|---|---|
| `server.port: 1420` | 保留 `1420` | Electron BrowserWindow 在 dev 模式加载 `http://localhost:1420` |
| `scanPluginEntries()` | **保留，不改** | 函数逻辑正确——读 `plugins/*/plugin.json` 的 `entry` 字段。Electron 下插件构建方式不变 |
| `build.rollupOptions.input` | **保留，不改** | 壳 + 插件仍用同一个 Vite build。`linkdesk://` 协议在 prod 模式下从 `dist/` 目录读文件 |
| `entryFileNames` 逻辑 | **保留，不改** | 插件输出到 `dist/plugins/<pluginId>.js`——和 `linkdesk://` 协议的路径对齐 |

#### 新增项

### 2.3 preload 时序防御（🔥 新风险 3）

**问题：** preload.ts 在 React mount 之前运行。出错 → `window.linkdesk` undefined → 全部调用报错。这个错误不进 ErrorBoundary。

**防御：**

```typescript
// electron/preload-shell.ts —— 头部 try/catch
try {
  contextBridge.exposeInMainWorld('linkdesk', { /* ... */ });
  // 通知 renderer：API 就绪
  ipcRenderer.send('preload-ready');
} catch (e) {
  console.error('[preload-shell] 致命错误——window.linkdesk 未暴露', e);
  // 在 window 上挂错误标记——renderer 可检测
  contextBridge.exposeInMainWorld('__linkdesk_preload_error__', { message: e.message });
}
```

```typescript
// electron/main.ts —— 新增 preload-ready 确认
let preloadReady = false;

ipcMain.on('preload-ready', () => {
  preloadReady = true;
});

// BrowserWindow 创建后——设置 5s 超时
setTimeout(() => {
  if (!preloadReady) {
    console.error('[main] preload 加载超时——window.linkdesk 可能未就绪');
    // 非致命——如果 preload 部分成功（少数 API 挂了），resilience 模式继续
  }
}, 5000);
```

```typescript
// src/main.tsx 或 App.tsx 最早执行处

```

## 缺口 5：`plugin.json` 的 `entry` 字段——语义确认

### 5.1 结论：不变，但需明确

当前 `plugin.json` 中 `entry: "index.tsx"` 指向**插件目录下的源码文件**。Electron 迁移后语义不变。

| 环境 | 加载链 | `entry` 的作用 |
|---|---|---|
| **Tauri dev** | `import.meta.glob` → Vite 即时编译 | 告诉 Vite 哪个文件是入口 |
| **Tauri prod** | `import.meta.glob` → `dist/plugins/<id>.js` | 同上 |
| **Electron dev** | `import.meta.glob` → Vite dev server HMR | **同上——不变** |
| **Electron prod** | `linkdesk://<id>/dist/bundle.js` → 协议处理器 → 文件系统 | `entry` 指向源码，build 后映射到 `dist/plugins/<id>.js` |
| **E3 外部插件** | `linkdesk://<id>/index.html` → 独立 WebContentsView | `entry` 指向插件自己的构建产物 |

### 5.2 不需要改 `entry` 字段，但需补一个约定

`entry` 字段保持语义 —— "插件入口文件，相对于插件目录"。新增约定：

> **插件构建产物约定：** 构建系统（Vite/独立构建）将 `entry` 指向的文件编译为 `dist/plugins/<pluginId>.js`。`linkdesk://` 协议按 `<pluginId>/dist/<filename>` 映射。此约定由 Vite build 配置自动满足（见缺口 1），插件作者无需关心。

### 5.3 `plugin.json` Schema 补字段（远期——E3g）

```json
{
  "entry": "index.tsx",         // 不变——源码入口
  "main": "dist/bundle.js",     // 新增——构建产物入口（外部插件用）
  "html": "index.html"          // 新增——独立 HTML（E3 多 WebView 用）
}
```

**E1 不需要加。** `main` 和 `html` 在 E3（外部插件独立 WebView）时才需要。E1 期间所有插件仍和壳同 WebView。

## 缺口 6：RingBuffer 数据管道——IPC 边界行为

### 6.1 当前架构（单 WebView）

```
串口硬件
  │ UART
  ▼
Rust serialport-rs (src-tauri/src/serial.rs)
  │ listen("serial-data", callback)
  ▼
App.tsx → 数据推给 useTauriEvent → RingBuffer → ProtocolParser → DataDispatch → 卡片/终端
  │
  └── 全部在同一个 JS context——零 IPC 开销
```

### 6.2 E1-E2 架构（单 WebView + Electron）

```
串口硬件
  │ UART
  ▼
Node.js serialport (electron/services/serial-service.ts)
  │ ipcMain → ipcRenderer (serial:data channel)
  ▼
BrowserWindow Renderer → useIpcEvent(替代 useTauriEvent) → RingBuffer → ...（不变）
  │
  └── 一次 IPC 跳转（main → renderer）。开销 < 1ms/包。
```

### 6.3 E3 架构（多 WebView）

```
串口硬件
  │ UART
  ▼
Node.js serialport
  │
  ├── IPC → Shell BrowserWindow → RingBuffer → ...（壳侧消费，不变）
  │
  └── IPC → Plugin WebContentsView（terminal 插件）
              │
              └── useIpcSerialContext → 和原来的 useSerialContext 接口一样
```

### 6.4 高频数据流分析

以 115200 bps 为例：

| 项目 | 数值 |
|---|---|
| 原始速率 | 115200 bps = ~11.5 KB/s |
| 文本模式（UTF-8） | ~11,500 字符/秒 |
| 按行拆分（平均 80 字/行） | ~144 行/秒 = **~7ms/行** |
| IPC 序列化/反序列化（JSON） | <1ms（小 payload） |
| 壳侧 RingBuffer → 插件 WebView IPC | <1ms（同机 Electron IPC 走 Chromium 内部管道） |

**结论：** 在 115200 bps 速率下，IPC 不是瓶颈。每行数据 ~7ms 间隔，IPC 开销 <1ms。

**需要关注的是极端情况：**
- 如果串口以最高速率连续输出（不分行，如二进制数据流）→ 需要**批量传输**而非逐包 IPC。
- 建议在 `serial-service.ts` 中实现**行缓冲 + 批量推送**：收集 ~16ms 的数据作为一个 IPC 包发送。

### 6.5 E3a 补 IPC 批量模式

```typescript
// electron/services/serial-service.ts —— 数据推送策略
class SerialService {
  private buffer: string[] = [];
  private flushTimer: ReturnType<typeof setTimeout> | null = null;

  private onData(chunk: string) {
    this.buffer.push(chunk);

    // 如果有换行符 → 立即推送整行
    if (chunk.includes('\n')) {
      this.flush();
      return;
    }

    // 纯二进制数据 → 批量收集，16ms 推送一次
    if (!this.flushTimer) {
      this.flushTimer = setTimeout(() => this.flush(), 16);
    }
  }

  private flush() {
    if (this.buffer.length === 0) return;
    const data = this.buffer.join('');
    this.buffer = [];
    if (this.flushTimer) { clearTimeout(this.flushTimer); this.flushTimer = null; }

    // 推送给壳窗口
    shellWindow.webContents.send('serial:data', data);
    // 推送给所有订阅的插件 WebView
    for (const [pluginId, view] of this.subscribedViews) {
      view.webContents.send('serial:data', data);
    }
  }
}
```

这个模式和 Tauri 时代的行缓冲一致——只是推送目标从单一 WebView 变成了壳 + N 个插件 WebView。

## 缺口 7：G14——PluginDetailView 幽灵页

### 7.1 G14 是什么

从 `P6-Bug修复完整记录.md:1006`：

> **G14. PluginDetailView 在插件被卸载后不刷新——用户看到幽灵详情页。**
>
> 场景：打开插件 A 的详情页 → 切换到插件市场 → 卸载插件 A → 切回详情页 → 仍显示"已安装"状态（幽灵页）。
>
> 推迟到 Electron 迁移的原因：涉及跨 WebView 状态同步——Tauri 单 WebView 内没有干净的跨组件广播机制（CoreEvents 的 Emitter 零订阅——G18 死代码）。

### 7.2 为什么 Electron 迁移改变了局面

E3 多 WebView 后，插件详情页（壳 WebView）和插件市场（壳 WebView）仍在同一进程——和现在一样。但 E3a 的 `onDidUnregister` Emitter 是壳级事件总线——卸载插件时 fire，详情页订阅就能自动刷新。

**实际上 E1-E2 就能修——不需要等 E3。** CoreEvents 的 Emitter 已经有 `onDidUnregister`（`viewRegistry.ts:24`），只是详情页没订阅。

### 7.3 补入 E2c 任务

在 E2c 的 7 个任务中加一个：

| # | 任务 | 行数 | 独立验证 |
|:--:|------|:--:|------|
| 19a | PluginDetailView 订阅 `onDidUnregister`——卸载/禁用后自动刷新状态 | ~10 | 打开详情页→卸载插件→详情页即时显示"已卸载" |

```typescript
// src/components/views/PluginDetailView.tsx —— ~10 行改动
import { onDidUnregister } from "../../pluginLoader/viewRegistry";

// 在组件内：
useEffect(() => {
  const sub = onDidUnregister.event((uninstalledId) => {
    if (uninstalledId === pluginId) {
      // 重新读取缓存状态——显示"已卸载"而非"已安装"
      refreshStatus();
    }
  });
  return () => sub.dispose();
}, [pluginId]);
```

**G14 不再"推迟到 Electron 迁移"——E2c 直接修掉。** 原推迟理由（"涉及 WebView 间通信"）不成立——详情页和卸载逻辑都在壳 WebView 内。

## 缺口 8：动态懒加载 → 同步调用——模式差异

### 8.1 问题

`ConfigurationService.ts`、`LayoutService.ts`、`StorageService.ts` 使用**动态异步懒加载**模式访问 Tauri FS：

```typescript
// 当前——首次调用时才 await import，之后缓存在模块变量
const { readTextFile, writeTextFile } = await import("@tauri-apps/plugin-fs");
const { appDataDir, join } = await import("@tauri-apps/api/path");
```

迁移到 Electron 后，`window.linkdesk.filesystem` 在 preload 阶段已注入——**同步可用**。不需要懒加载。

### 8.2 迁移时的两件事

1. **改 API 目标：** `import("@tauri-apps/plugin-fs")` → `window.linkdesk.filesystem`
2. **改调用模式：** `await import(...)` 懒加载 → 直接调用（`window.linkdesk.filesystem.readTextFile(...)`）

第二件事虽然简单（删 `await import` + 缓存逻辑），但容易遗漏——执行 AI 可能只改了 API 名字而保留了懒加载结构。

### 8.3 正确迁移示例

```typescript
// ❌ 只改 API 名不改模式——保留了不必要的懒加载
let _fsApi: typeof window.linkdesk.filesystem | null = null;
async function getFs() {
  if (!_fsApi) _fsApi = await import(???);  // Electron 下无意义
  return _fsApi;
}

// ✅ 正确——window.linkdesk 始终可用，直接调
async function read(key: string): Promise<Record<string, unknown> | null> {
  const path = await window.linkdesk.path.join(
    await window.linkdesk.path.appDataDir(), key + ".json"
  );
  if (!(await window.linkdesk.filesystem.exists(path))) return null;
  const text = await window.linkdesk.filesystem.readTextFile(path);
  return JSON.parse(text);
}
```

**执行检查：** E1 步 4 完成后，grep `await import.*filesystem\|await import.*tauri` → 零结果。

> 注：`04-迁移方案.md` §2.1 的"完全保留"表中 `ConfigurationService.ts` 和 `LayoutService.ts` 已标注 ⚠️——它们有 Tauri 动态导入。E1 步 4 先替换为 `window.linkdesk.*`，E2c #19c 再归一化走 FileService。两步，不是一步。
