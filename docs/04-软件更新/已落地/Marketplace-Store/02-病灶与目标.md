# 病灶与目标——为什么要做主区 Plugin Store

> **为什么存在**：本档是任务的「因」——不写清病灶与推演，后面的设计决定（入口、分类、卡片）就成了无源之水，接手 AI 会以为是在凭空堆功能。
> **上游**：[00-README](00-README.md)（任务定位）；**地基**：[01-插件侧现状](01-插件侧现状.md)（本文所有「现状」陈述的出处）；**下游**：[03-入口与数据归一](03-入口与数据归一.md)、[04-分类体系](04-分类体系.md)（本文的病灶分别被这两档的方案对症）。

## 一、病灶：侧栏容器架构的三病（2026-11-19 用户陈述）

侧栏是一个 **section 容器**——toolbar 段（搜索框）＋多个可折叠列表段，顺序固定在 `plugin.json` 的 view 声明里（order -1/0/1/2/3，见 01 §一），用户不可重排。从上到下：搜索框 → 已安装 → 探索插件 → 已禁用 → 内置。

| # | 病灶 | 为什么是结构性的（不是调参数能修的） |
|---|---|---|
| 1 | **够不着底**——内置、已禁用压在最底下 | 容器段顺序是声明式固定的；段再多/再长，「最后一段」永远被压底。列表变长只会加剧 |
| 2 | **探索与已安装双重陈列**——探索段是唯一安装通道（没有它，已安装/禁用/内置全空，这是当初刻意的设计，本身合理），但装完条目仍留在探索里 ⇒ 同一插件出现两次 | 这是「按陈列位置分信息」的必然结果：探索段=「可装的」，已安装段=「已装的」，而「可装」不因「已装」而减少。要根治必须换信息组织方式（分类页/商店页按插件组织一次），不是给探索段加过滤 |
| 3 | **排序死板**——按目录收录顺序排，无热度/相关性语义 | 目录数据里没有参与排序的用户信号（下载数有抓但没用于排序），且侧栏列表形态天然不承载排序/筛选 UI |

## 二、未来场景推演：为什么现在不做，以后会烂

假设目录涨到 **500 个插件**（用户原话场景）：

- 探索段 500 行；已禁用、内置还压在这 500 行**下面**——看一眼内置要翻 500+ 行，翻三五百下，不可用。
- 侧栏搜索框虽能检索，但它是「先知道名字才能搜」的工具——发现新插件靠的是浏览，侧栏列表形态给不了分类、合集、榜单这些浏览骨架。
- 同一个插件在已安装/探索两段各一份，500 插件时双重陈列的维护混乱翻倍。

结论：**问题不随时间自愈，只随插件数放大**。而主区现在几乎闲置（只有详情页＋空 hero 落地页，见 01 §一）——把发现浏览搬进主区，是唯一有余地的空间。

## 三、目标形态（拍板）

1. **互补，不替代**：侧栏 = 日常快速操作（我主区在改代码，只想侧栏搜一下装个插件）；主区 Store = 发现和浏览（分类、合集、榜单、大屏卡片网格）。两态共存，各干各的活。
2. **入口不抢主区**：点 🧩 图标只切侧栏、主区保持当前标签页——这是现状默认行为，**保住**（详见 03 §一）。
3. **侧栏是否退位，不预设**：将来插件多到侧栏彻底不适用再说（剧本见 §五）。

## 四、扩展位清单（现在没有数据/服务器，但形态必须先留好）

> 为什么这条清单重要：Store 的价值一半在「现在好用」，另一半在「将来接得上」。每一项都是「今天没数据，明天要位置」——形态先留好，将来填数据不重画。机制落法分别在 04（合集/榜单/推荐位）和 05（动作槽）。

| 扩展位 | 现状 | 落法（指向） |
|---|---|---|
| 推荐位/横幅（对标小米/华为/OPPO/MS Store/App Store 顶部推荐区） | 无服务器无统计，做不好推荐 | 推荐位 = 第一大**合集**槽，先手写编辑推荐，将来换数据源不换 UI → 04 §五 |
| 评论区/评分（将来接服务器） | 现基于 GitHub，评论没什么用；借 GitHub issue 抓评论可行性未知 | 详情区扩展项，暂不设计 UI，只保证卡片/详情组件可插信息块 → 05 |
| 卡片信息密度（大图？更多元数据？hover 弹窗·移开即消失） | — | 归一化信息组件，不写死 JSX → 05 |
| **动作槽抽象**（将来收费插件/购买/二维码支付） | 卡片动作现为安装/卸载/禁用 | ⛔ 不能写死三件套——加一种动作 = 往槽里加一项声明，不是大改代码；**七条质量要求的试金石** → 05 |
| 分类体系 | `marketCategories.ts` 已存在 | 数据驱动＋注册表＋其他桶 → 04 §三 |
| 排序/检索（热度=下载量/GitHub star/收藏） | `downloadCounts.ts` **已在抓** GitHub release 下载数 | 数据地基现成，缺排序 UI；榜单=换排序键 → 04 §五 |

## 五、可删除性：侧栏退位剧本（设计目标，不是当前工作项）

> 为什么写这个：用户拍板「归一化做得好，将来侧栏市场那几个 TS 文件一删就完事」。**删除的容易程度是架构质量的验收标准**——耦合在视图里的业务逻辑，删视图就会撕烂功能。

剧本（将来某个时点，不是现在）：

1. 主区 Store 成熟（分类页/合集/榜单全在主区，是**全功能实现**，不依赖侧栏）。
2. 若主区空间不够或交互形态变化，分类浏览可迁去侧栏或反方向迁——**表面只是容器声明，视图本体不耦合容器**（views 声明在 plugin.json `contributes.views`，换容器=改声明不改编码）。
3. 彻底退位时：侧栏市场段（5 个 surface 视图＋sidebar 样式 3 件）**整体删除**，`marketplaceShared` 数据面一根毫毛不动——因为所有业务逻辑住数据层，侧栏从来只是薄壳。

**成立前提**（= 本任务实施期的硬要求）：
- 视图组件零业务逻辑（只订阅 store ＋ 渲染 ＋ 发动作）；
- store 单属主（03 §二）；
- 新 Store 页与旧侧栏段共享同一数据面，禁造第二份状态（01 §一的多表面教训）。

## 六、贯穿一切的前提

七条代码质量要求（测试必写/归一化/AI 友好/高内聚低耦合/无硬编码/无死代码/拓展性优先）正典住**插件仓 `AGENTS.md` §3.5**（2026-11-19 拍板，对一切改动生效，不因刀小豁免）——本档案集不复制正文，实施与评审一律对照那边。任务级补充：改造中被替代的旧代码（如 entry 落地页 hero 旧段）**同笔清走**。
