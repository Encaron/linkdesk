## 一、你令的原话（2026-10-03）

> 「咱们的软件在早期主题系统是非常简陋的，基本上是追随大多数软件的主题系统，只有浅色和深色以及跟随系统三种模式……前期的主题工作基本就是从图标开始的，就是浅色的适配以及深色的适配……现在随着咱们的主题系统已经变得十分强大，它可以调控玻璃，调控背景，圆角变大变小，放大放小，字体变化，字体颜色变化，字体字形变化之类的。那么在前期的它只有浅色和深色的这个适配，就已经显得力不从心了。」
> 「在咱们现在这样子的情况下，这个所谓的浅色和所谓的深色，似乎没有多大的区别了……如果现在我添加了图片，那么很多时候这个浅色和深色完全取决于这个玻璃的模糊度、玻璃的明暗度以及背景图片的明暗度、各个分区图片的明暗度，并不是完全取决于我所设定的暗色和浅色。」
> 「鉴于这个现状你可以直接去看看图标栏，它目前的图标基本上除了我聚焦的那一个以外，其他的几个图标基本就是看不清的样子……因为图标栏图标现在**是白色的线条款式，那就应该是暗色模式**对不对？整个软件理论上是暗色模式，然后线条就是白色的，但是现实就是我这个图片它本身亮度也比较亮，导致这个线条根本看不清。」
> 「那么相应的，如果我在这个亮色模式……这些线条页面就是显示黑色，而这个时候我如果挑一个颜色比较暗的图片的话，这个时候再把这些玻璃亮度、玻璃透明度之类的调暗，或者把图片透明度调暗，再加上图片本身就是比较暗的，这样子这些线条又看不清。」
> 「基于这个，你去看看，然后想一想比较好的策略。」
> 「先建立文件夹，然后建立文档，接着再画这个 html 图，让我看看你的不同，这个修法是什么样子的，包括你说什么这个结合之类的。」

**补充（同日稍晚，你切到 light 型主题实机看）**：

> 「看看这个，是 light 型主题下（如你所见，聚焦的那个变成黑色的），然后那几个图标的样子。」
> 「现在再看一次，这次我调了一下玻璃不透明度，未聚焦的几乎看不清。」

⇒ 这两句把病灶从暗分支推到了**亮分支**，并顺带证伪了一个我以为能用的旋钮（玻璃不透明度）——重测与实算见 §二·补。

⇒ 归纳成一句：**「前景色（图标／文字）的极性，今天由静态的深浅两套皮肤决定；但真正的底色是「图 × 图不透明度 × 玻璃 × 遮罩」在运行时合成出来的、逐区甚至逐像素变化的照片。判据和事实脱钩，所以两头都不成立。」**

### 二·补 · 实机复测（2026-10-03 晚间 · 你点单的 light 型主题）

> 上面那张表是 **04:2x 的快照**（当时跑 `theme-panorama` ＋ 暗色 ＋ `--bg-mask: 0.15`）。你随后把主题换成 **`theme-pill.pill-bubble`**（`"type": "light"`）、遮罩提到 **0.42**，又把玻璃不透明度从 **0.50 压到 0.38**。经 CDP 9333 重测——**结论改了两处，都是要紧的**。

| 项 | 实测值（此刻） |
|:--|:--|
| 主题 | `app.theme = theme-pill.pill-bubble`（`"type": "light"`）· `app.appearanceMode: custom` · `--bg-mask: 0.42` |
| 根属性 | `data-theme="light"` ⇒ 走 [index.css](../../../../src/index.css) **浅块** |
| 非激活滤镜 | `invert(0.60)` ⇒ **`#999999`**（⚠️ **不是**主题声明的 `#B4A6AD`） |
| 激活滤镜 | `invert(0.18)` ⇒ **`#2E2E2E`**（近黑）——**这就是你说的「聚焦的那个变成黑色的」** |
| 图标栏自身底色 | `color(srgb 1 1 1 / 0.38)` ＝ **白 38%**（`--bg-icon-bar-solid: #FFFFFF` × `--glass-surface-alpha: 0.38`） |
| `--glass-blur` | `0px`（没模糊） |
| 主题声明的图标色 | `icon-active: #D6336C`（accent 粉）· `icon-inactive: #B4A6AD` |

**🔴 发现一 · 主题声明了图标色，图标栏一个字都不读。**
`--icon-active` 在**全仓 grep 零消费者**；`--icon-inactive` 的唯一真实消费者是欢迎页（[WelcomePoolView.css:266](../../../../src/pool/views/welcome/WelcomePoolView.css)）。图标栏的 `img` 走**写死的 `--icon-filter-*` 反相链**（拿不了色），`codicon`/`lucide` 走 `--text-primary`。⇒ 主题作者写了「激活图标 ＝ 强调粉」，**图标却是近黑 `#2E2E2E`**——那点粉色**只出现在图标左边那根 2px 指示条上**。

**🔴 发现二 · 但「让主题色生效」不是修法——它会连激活态一起弄坏。**
面 ＝ 玻璃白 ×α ＋ (1−α)×(照片 × 0.58)。按 sRGB 合成实算（α = 0.38）：

| 墨色 | 面 ＝ 照片全黑 → 全白 |
|:--|:--|
| 现状 非激活 `#999999` @55% | **1.57 → 1.25**（仍全线看不见） |
| 现状 激活 `#2E2E2E` @100% | **2.19 → 7.20** |
| 主题想要的 非激活 `#B4A6AD` @55% | 1.79 → 1.42（**更差**） |
| 主题想要的 激活 `#D6336C` @100% | **1.34** → 2.45（**也比现状差**，暗底上直接消失） |

**🔴 发现三 · 玻璃不透明度这个旋钮，数学上救不了非激活图标——而且正在伤害激活图标。**
把 `α` 与照片亮度**全平面扫一遍**（α 0→1 步长 0.01，照片 0→255 步长 3）：

| α | 非激活 CR 区间 | 激活 CR 区间 |
|:--|:--|:--|
| 0.50（上一版） | 1.21 – 1.33 | 3.41 – 8.24 |
| **0.38（此刻）** | 1.57 – 1.25 | 🔴 **2.19** – 7.20 |
| 0.30 | 1.89 – 1.19 | 🔴 1.59 – 6.55 |
| 0.15 | 2.60 – 1.08 | 🔴 1.11 – 5.45 |
| 0.00 | 2.78 – 1.04 | 1.55 – 4.47 |

⇒ **非激活 `#999999` @55% 的全局天花板 ＝ CR 2.82**（要 α≈0.03 ＋ 照片近黑才拿到，而那个点上激活态只剩 **1.43**）。**无论怎么拧玻璃，它都到不了 3:1。** 你刚才把 α 从 0.50 压到 0.38，是拿**激活态从 3.41 掉到 2.19** 换来非激活**从 1.33 涨到 1.57**——两头都不划算。**「未聚焦的几乎看不清」不是你调错了，是这个旋钮到不了那里。**

**🔴 发现四 · 推翻本夹 §四 的 B 案口径：遮罩护栏在这条分支上不但无效，还有害。**
B 案原来的算法是「面跟着照片走，把照片压暗就能把面压到及格」——**错在面不跟照片走**。图标栏自己那层白玻璃给面设了**下限**（α = 0.38 时面最暗也只能到 `#616161`），**遮罩拉到 1 也压不下去**；抬遮罩只会让面更暗、把激活的近黑墨色推得更近（2.19 已经是那条路的尽头）。⇒ **B 只在暗分支（白墨 vs 亮底）里有可能成立**，⛔ 别当成两条分支的公共兜底。

## 三、根因（三条叠在一起，不是一条）

| # | 根因 | 说明 |
|:--:|:--|:--|
| **①** | **图标取色完全脱离主题引擎** | 走的是 [index.css](../../../../src/index.css) 里静态的 `--icon-filter-*`（一个 light 块一个 dark 块）。这个 token **不看 `--text-primary`**（主题算出来的极性）、**不看 `app.fontTone`**（你已经有的三态极性槽）、更**不看图／玻璃／遮罩**。它连浅色深色都只差 19 级灰。 |
| **②** | **可读的那一极只发给了激活态** | `.active` 才拿 `invert(1)`＝纯白，其余挂在 `#858585` × 0.55 上。所以「可读」是**一个按钮的待遇**，不是一栏的基线。 |
| **③** | **底色是运行时合成的，静态 token 结构上算不出来** | 面 = 照片像素 × 图不透明度，再经玻璃 tint／`glass-surface-alpha`／`--bg-*-solid`／`--bg-mask` 合成 ⇒ **逐区、甚至逐像素**不同（这张图左 3% 条带 0.317、右侧 3% 条带 0.379）。一个全局静态值**不可能**对整栏都成立。 |

**一条旁证**：`codicon` / `lucide` 两条路走的是 `color: var(--text-primary)`——**它们本来就跟着极性链路**（含 `app.fontTone`）。**只有 `img` 那条被漏在外面**。所以你栏里 6 个全中招，恰因为它们是 `img`。

## 四、四个候选方向（含一个明确否掉的）

| 案 | 一句话 | 能治什么 | 治不了什么 |
|:--:|:--|:--|:--|
| **A 主修** | 把 `img` 图标的取色**并回主题链路**——墨色跟 `--text-primary` 极性（含 `app.fontTone`），删掉静态两套死滤镜 | ①（不跟主题）、②（可读那极只给激活）、以及「两套灰等价」的假分支 | 🔴 **亮底上连自己那一极都过不了**：白墨对 L≈0.55 的面，**理论极限只有 1.75**（给多少不透明度都超不过）；也治不了「底图与极性相反」。⇒ **A 必要，但不充分** |
| **C 兜底** | 图标加**反向光晕**（`drop-shadow` 一道，浅墨配深晕、深墨配浅晕；墨色居中时退双色调） | **逐像素本地生效**：照片半明半暗、逐区不同，它能兜住（这是唯一不用算亮度就本地生效的手段） | 数值上它能过线（实测多为 3.9–5.4，实测面 2.97 差一点），但**救不了「墨色≈底」的墨色本身**——它只勾出形状，单用会退化成**描边空壳** |
| **B 护栏** | 给现成的 `--bg-mask` 加**可读性下限**（它就是既有的「图+玻璃可读性生命线」）——估出的对比不达标就把遮罩自动抬上去，并在设置页显示抬到了多少 | **只在暗分支成立**：白墨 vs 亮底，把面压暗确实抬对比 | 🔴 **亮分支上无效且有害**（见 §二·补 发现四）：图标栏自身那层白玻璃给面设了下限，遮罩拉到 1 也压不暗；抬遮罩反而把「近黑激活墨」推得更近。且它是**全局一个数**，对「照片一半亮一半暗」只能取折中；抬遮罩**改整窗观感** |
| **D** | ~~`mix-blend-mode: difference` / `exclusion`（自动反色）~~ | 🔴 **否掉**。盲区实测：白图标下 `difference` 在 **sRGB 0.35–0.65（L≈0.10–0.38）整段 CR<3**，最差点 `#808080` **CR 1.07**；而你这张图**合成后的面 sRGB≈0.52、L≈0.23，正落在带中央**。另有三条独立否决理由：**①** 图标被迫变成底色补色，主题墨色／`fontTone`／强调色**一律失效**；**②** `mix-blend-mode` 在同一层叠上下文内混合 ⇒ 会跟按钮自己的 `hover` 底／`active` 强调色径向盘**一起算**，悬停激活时外观不可预期；**③** 彩色照片上补色落在 1px 细笔画上＝一团视觉噪点。 | — |

> 📐 **表内 CR 全部按 sRGB 空间合成实算**（口径见 [01 §一·1.3 注](01-方案与落点契约.md)／[05 图](05-设计图-前景可读性.html) 可逐格复算）。⚠️ 我第一稿把「白墨@78%」按**亮度线性混合**估成 ≈3.15，**真值是 2.95**（差 0.05 过不了线）——差之毫厘而结论相反，已在全线改正。

> **推荐组合 ＝ A（主修）＋ C（兜底）；B 降为「暗分支可选」**。理由一句话：**A 修的是「判据错」（该跟主题的没跟），C 补的是「判据不可能对」（照片逐像素变化，任何全局值都不成立）。** B 兜的「全窗最低线」经实测（§二·补 发现四）在亮分支上**既不生效又有害**，故从「三者并列」降为**暗分支的可选护栏**。
> 🔴 **实测把「A 与 C 是二选一」这个念头直接掐死了**：A 单独在**亮底上过不了线**（纯白极限 1.75），C 单独**数值能过但图标退化成描边空壳**；**只有 A+C 在五种底色 × 两种极性下全部 ≥3:1**（最低 3.47）。⇒ A+C 不是「叠加选项」，是**一个组合里的两条腿**。
> 🔴 **另一条实测把「靠背景旋钮就能救」这条路也堵死了**：玻璃不透明度 × 照片亮度**全平面扫描**，非激活墨色的**全局天花板只有 2.82**（到不了 3:1）。⇒ **修法必须动墨色（A＋C），⛔ 不能动背景。**
> 另有一案**只建议留给 active/hover**：把激活态那块强调色径向盘变成常驻「底片」——最稳但最毁设计（整套主题的卖点就是照片直接垫在图标下，常驻胶囊等于把图标栏变回不透明工具条）。
> **5 张对照图（现状 / A / C / A+C 四列 × 五种底色，含「上下对半亮暗」的杀手现场）＋ CR 实算矩阵 ＋ D 案失效现场 ＋ B 护栏前后，全在 [05-设计图-前景可读性.html](05-设计图-前景可读性.html)。**
