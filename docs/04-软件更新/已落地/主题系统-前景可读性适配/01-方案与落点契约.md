# 01 · 方案与落点契约

> 本文件回答五件事：**墨色从哪来**（极性链）· **img 图标怎么着色**（唯一的正路）· **光晕怎么长**（兜底形态）· **护栏怎么算**（B）· **哪些不改**。
> 一句话方案：**把「前景墨色的判据」从「静态深浅两套皮肤」换成「主题极性 ＋ 极性反转光晕」——墨色跟主题走（A），形状靠自己勾边（C）。**（原方案里的第三腿「全窗最低线交给既有的遮罩（B）」经实机复测**只在暗分支成立、在亮分支有害**，已降为可选，见 §四 尾。）
> ⚠️ 本夹**零代码改动**，下面所有 CSS 都是**提案**，数值即实现口径（可直接抄）。

## 一、A 主修 · 墨色的极性链（根因 ①② 的正面回答）

### 1.1 今天错在哪（一行看穿）

```css
/* 今天：index.css 静态两套 —— 一个 light 块一个 dark 块 */
:root { --icon-filter-inactive: brightness(0) saturate(100%) invert(52%); }  /* #858585 */
[data-theme="light"] { --icon-filter-inactive: brightness(0) saturate(100%) invert(60%); }  /* #999999 */

/* today: IconBarZone.css —— 55% 不透明度 */
.ldk-icon-btn .plugin-icon--img { opacity: .55; filter: var(--icon-filter-inactive); }
```

两个分支相差 19 级灰，**都对**「跟随主题极性」这件事无话可说。改法是**换判据来源**，不是调这两个数（调数是治标：亮照片下无论多极端都可能撞色，见 [02 E12](02-边缘情况清单.md)）。

### 1.2 目标契约（正版）

```css
/* ① 墨色的唯一来源 = 主题极性（含 app.fontTone）——三级阶梯用 alpha，不用固定灰 */
:root {
  --icon-ink:        color-mix(in srgb, var(--text-primary) 78%, transparent); /* 非激活 */
  --icon-ink-hover:  color-mix(in srgb, var(--text-primary) 92%, transparent); /* 悬停 */
  --icon-ink-active: var(--text-primary);                                      /* 激活（= 今天也是白） */
}

/* ② img 型图标：以自身 alpha 为遮罩、色由 currentColor 供 —— 这是 img 着任意色的唯一正路 */
.plugin-icon--img {                       /* 渲染层由 <img> 改为 <span>，见 §三 */
  width: 24px; height: 24px;
  background-color: currentColor;
  -webkit-mask: var(--icon-url) center / contain no-repeat;
          mask: var(--icon-url) center / contain no-repeat;
  color: var(--icon-ink);                 /* ← 唯一的极性入口 */
}

/* ③ 三级态：只改 color（极性），不再用 opacity 表达灰度 */
.ldk-icon-btn:hover  .plugin-icon--img { color: var(--icon-ink-hover); }
.ldk-icon-btn.active .plugin-icon--img { color: var(--icon-ink-active); }
```

**为什么必须 `mask` 而不是继续 `filter`**：`filter` 的 `brightness/saturate/invert` 组合**只能产出黑白灰**，吃不了 `--text-primary` 这样的任意 token 色（要着任意色得堆 `sepia()+hue-rotate()` 那套近似 hack，且无法直接吃 token）。**只有「`mask` 取形状 ＋ `background: currentColor` 上色」能让 `img` 图标着任意色。** 这一条决定了 A 案**必须碰渲染层**（见 §三），不是纯 CSS 能收的。

### 1.3 A-最小版（两处 token，立刻能验）

如果只想**先止血、当天可验**，可以不动渲染层，只改两处：

```css
:root {
  --icon-filter-inactive: brightness(0) saturate(100%) invert(100%);  /* 52% → 100%：改成白 */
}
.ldk-icon-btn .plugin-icon--img { opacity: .78; }                     /* .55 → .78 */
```

效果可推算（**sRGB 空间合成，口径见下注**）：非激活墨色由 `#858585`@55%（实测 **CR 1.01**）变成 **白@78%**——对实测合成面 **CR 2.95**，对亮照片合成面只有 **1.56**。
**但它仍写死「白」**——浅色主题那半照旧错，且完全不吃 `app.fontTone`；而且 **2.95 差 0.05 就是过不了线**（纯白对那张亮照片的理论极限仅 **1.75**，给多少不透明度都超不过）。⇒ 这是**取证用**的止血版（能立刻证伪/证实推算），**不是交付版**。[04 D1](04-任务清单.md) 要你拍「先最小版还是直接正版」。

> 📐 **本夹所有 CR 的算法（可复算）**：sRGB → 线性光（WCAG 相对亮度 `L`）→ `CR = (Lmax+0.05)/(Lmin+0.05)`；图标颜色按「墨色在面上乘不透明度」**在 sRGB 空间**合成；有光晕时取「墨色 vs 面」与「晕 vs 面」**较大者**。
> ⚠️ ⛔ **不要用亮度线性混合去估算**——我第一稿就是这么估的，把白@78% 估成 3.15，**与真值 2.95 差 0.2 且跨过了 3:1 这条线**。这个坑请下一棒别重踩：**算对比度一定在 sRGB 空间合成完再转线性光**。

### 1.4 极性链（谁定 `--text-primary`）

| 上游 | 怎么影响图标 |
|:--|:--|
| `app.theme` 的主题配方 `type` | 主题自带极性 ⇒ 写 `--text-primary` |
| **`app.fontTone`**（三态：`light` / `dark` / `followTheme`） | 显式选档时**覆盖** `text-primary/secondary/muted`（[seeds.ts:329](../../../../src/core/services/ui/ThemeEngine/seeds.ts) 的 E5.8#91）⇒ **图标跟着一起翻**（这正是 A 的价值：今天图标对 `fontTone` 完全无感） |
| `app.appearanceMode = custom` | 走覆盖链，与上两条不互斥 |

> ⚠️ **A 案的边界（必须说清，且比"极性相反"更宽）**：`--text-primary` 是**全窗一个值**，它标定的是**面板底**，不是**照片底**。实测两种失效都躲不掉：
> - **亮底**（L≥0.5）——**两种极性都过不了线**（白墨对 L0.55 的面理论极限仅 **1.75**）；⇒ 与极性无关，**纯靠 A 无解**。
> - **极性反转**（亮主题的黑墨 + 暗照片）——黑墨对 L0.03 的面只有 **1.20**。
> ⇒ 两处都只能靠 C 的光晕（[05 图](05-设计图-前景可读性.html)的 A+C 列：亮底 8.09／暗底 9.12，两半都过）。⛔ 不要试图让 A 去读照片亮度（见 §四 尾）。

## 二、C 兜底 · 极性反转光晕（根因 ③ 的正面回答）

### 2.1 形态契约（✅ 2026-10-03 阶段 1 定稿：晕值改由引擎发射，见下「机制落定」）

```css
/* 单色反向晕：墨色亮 → 晕暗；墨色暗 → 晕亮。1px 贴字形，不需要算任何亮度。
   ⚠️ 晕的「颜色 ＋ 开不开」由引擎按生效墨色极性与生效底图发射成一个 filter 串 token（--icon-glow）——
      底座 CSS 只消费，不做任何分支（理由见下方「机制落定」）。 */
.ldk-icon-btn .plugin-icon--img {
  filter: var(--icon-glow, none);   /* 无底图 = none（纯面板零多余描边，D3）；有底图 = 反向 1px 晕 */
}
```

**机制落定（阶段 1 补的缺口——原稿写的 `:root[data-icon-polarity="dark"]` 在程序里没有出处）**：

| 问题 | 定稿 |
|:--|:--|
| 晕跟着谁翻 | **生效墨色极性 = 生效 `text-primary` 的相对亮度**（🔁 **2026-10-04 · 9.4 修正**，原稿「跟随主题时用配方 `type`」被实机推翻，见下）——`> 0.179` 判亮墨（发暗晕）；解析不出（`color-mix`/`var`/named）**回落到 `app.fontTone` 显式档 ▸ 配方 `type`** 这个旧档位判据（零行为倒退） |
| ⚠️ 为什么必须改读亮度（9.4 实测依据） | 混搭（`appearanceMode=custom`）/自配外观下**生效墨色与主题声明的 `type` 可能不同源**：实测主题 `type=dark` ＋ 自配暗墨（`--text-primary: #1A2A2D`）时旧口径仍发**亮晕** ⇒ 晕与墨**同向**，等于没隔离（照片近黑块上 CR 1.01，正是最需要它的时刻）。⛔ 这不违 D3：D3 禁的是读**照片**亮度，此处读的是**墨色**；⛔ 也不碰作者写的任何颜色（与 9.2「作者保有 final say」不冲突） |
| 分界为什么取 0.179 | 黑白各半的**等对比交叉点**：(L+0.05)² = (1+0.05)(0+0.05) ⇒ L≈0.179，即「与黑晕还是白晕对比更高」的临界。⚠️ **不取 0.5**：`#4EC9B0`（L≈0.46）这类中间色是亮墨，0.5 会误判成暗墨、把 terminal 今天正确的观感改坏 |
| 为什么不能挂 `[data-theme]` | `data-theme` ＝ **配方 type**（[tokens.ts:146](../../../../src/core/services/ui/ThemeEngine/tokens.ts)），**`app.fontTone` 覆盖 text-* 时它不翻** ⇒ 挂它会与 A 案（墨色跟 `--text-primary`）**分道扬镳**，而 `fontTone` 与主题相反**正是这个槽的正常用法**（图亮选暗字） |
| 为什么是 token 不是新属性 | 属性要三处同笔（引擎 `setAttribute` ＋ **池侧镜像层** `preload-pool/events.ts` 广播 ＋ `public/boot-theme-snapshot.js` 首帧），而 **token 随既有 variables 全量广播/快照自动到池**，池侧零管道改动（池是哑渲染器，⛔ 不给它加逻辑） |
| 开不开的判据 | **生效** `--bg-image` ≠ `none`（D3 原判据；引擎本就解析这张图，`effective["bg-image"]` 是最终值 ⇒ 判据不靠猜）。⚠️ `--surface-bg-image`（zone 表面图）**不**算——主题自带 zone 纹理会让纯面板也长描边，违背 D3 本意；该缺口记 [04 §六](04-任务清单.md) |
| 取值 | 亮主题（暗墨）＝ `drop-shadow(0 0 1px rgba(255,255,255,.65))`；暗主题（亮墨）＝ `drop-shadow(0 0 1px rgba(0,0,0,.85))`（D4 实测对：8.09 / 9.12）；半径 **1px** 先落，糊就退 0.5px（[03 §七·5](03-实现交接.md)，目视定） |

**为什么单色反向晕够用**（不用双色调）：极性正确的墨色下，**暗底那侧靠墨色本身读、亮底那侧靠光晕读**——一张图里一半亮一半暗时，两者各管一半，天生覆盖。**双色调**（一深一浅两道）只在**墨色本身处在中间灰**时才需要多一层保险；而 A 案已经把中间灰消灭了（中间灰正是根因①）。⇒ 推荐**单色反向晕**：更少一层、更不糊。[04 D4](04-任务清单.md) 备了双色调作为「若 A 不做」的退路。
⚠️ **双色调为什么不能用来「免掉极性信号」**：它两道晕的**外层那道**才是起隔离作用的那道（内层贴着墨色只是把笔画加粗）⇒ 亮底暗字时会平白多一圈白边、暗底亮字时多一圈黑边，**与 [05 设计图](05-设计图-前景可读性.html) 已过审的形态不符**（改形态＝要重出参考图），且图标整体变粗。故宁可把极性交给引擎算（上表），守住「一道晕」。

### 2.2 什么时候开

| 策略 | 何时生效 | 取舍 |
|:--|:--|:--|
| **① 挂底图时恒开**（建议） | `--bg-image` 非 `none` 时给图标栏加 `.plugin-icon--glow` | 判据最简单、行为最可预期；纯面板下不留多余描边 |
| ② 按需开 | 只在估算出的对比不达标时开 | 要算亮度（= 引入 §四 那摊复杂度），**判据还可能是错的** |
| ③ 不做 | —— | 「亮主题＋暗照片」无人兜底 |

**推荐 ①**：`--bg-image` 是不是 `none` 是**已知的、逐区无关的**信号，用它当开关既准确又不引入估算。

### 2.3 代价（诚实写下来）

- 视觉上图标**略微变粗**（1px 晕 ≈ 24px 图标的 4%）。这是新增的设计语言——仓里目前**零 `text-shadow`／`drop-shadow` 先例**（已 grep 确认），所以它需要你点头，不能当"顺手"。
- 它**救不了「墨色≈底」的墨色本身**：光晕只把**形状**勾出来，如果 A 没做（墨色还是 `#858585`），图标会退化成**描边的空壳**——[05 图](05-设计图-前景可读性.html) 的 C 列画的就是这个效果，用来证明「C 不能单独当主修」。

## 三、A 案的落点：为什么必须碰渲染层

`filter` 吃不了 token 色（§1.2），而 **CSS 拿不到 `<img>` 的 `src`**（`mask-image: image(attr(src))` 不被支持）。⇒ 只有两条路：

| 路 | 做法 | 评价 |
|:--:|:--|:--|
| **1**（建议） | 渲染层把 `img` 型图标渲成 **`<span class="plugin-icon--img" style="--icon-url:url(...)">`**（不带内容），CSS 用它做 mask 上色 | 内容为空 ⇒ mask 上色干净；`alt`／`onerror` 的兜底改由外层按钮的 `aria-label` ＋ 渲染件的失败分支承担 |
| 2 | 保留 `<img>`，用 mask 挂在**容器 `::after`** 上、img 自身隐藏 | 绕、要两层，且 `::after` 拿不到 per-图标 url（同样得靠自定义属性）⇒ 不比 1 简单 |

**✅ 阶段 1 定稿（路 1 ＋ 按类名分叉）**：`PoolPluginIcon` 的 `img` 分支**只对图标栏那一支**改形（图标栏三处调用传的类名就是 `ldk-icon-bar-plugin-icon`，[IconBarZone.tsx:263/289/348](../../../../src/pool/zones/icon-bar/IconBarZone.tsx)），**其余调用（标签栏 `ldk-group-tab-icon`、拖影预览另计）保持今天的 `<img>` 逐字节不变**。

- **为什么分叉**（D6 给了「接受／按类名分叉」两条路，选后者）：标签栏 img 图标**今天没有单色化**（[GroupTabBar.css:106](../../../../src/pool/shared/group-tab-bar/GroupTabBar.css) 只给尺寸，无 filter）⇒ 一锅端会把标签栏**从原图原色改成单色**，那是**行为变化**（D6 要求「如实登记」，登记的最好形态就是**不动它**），也把本刀的回归面从「图标栏 6 个」扩到「所有标签」。
- **代价与去处**：标签栏那半的可读性问题**照旧存在**（同一张照片下它也会撞色）——这正是 [04 D6](04-任务清单.md) 把「全前景层」升格为**第 4 刀**的原因，届时连同壳侧孪生点 [`PluginIcon.tsx:80`](../../../../src/components/shared/plugin-icon/PluginIcon.tsx) 一起收。
- 判据相应改口径（[03 §五](03-实现交接.md)）：⛔ **不再是**「`grep` 命中处不再有 `<img`」，而是「**图标栏那一支**不再有 `<img`／不再消费 `--icon-filter-*`」。

**改动量**：一个共享渲染件（`PoolPluginIcon` 一类，池侧统一图标渲染）＋ 一处 CSS。⚠️ 若它落在**共享件**（`src/components/shared/**` 或池共享件）上，改完必跑 `npm run ui:build`（[03 §二](03-实现交接.md)）；只动 `IconBarZone.css` 则不用。**落点定在哪 = 开工前第一件事**，见 [03 §七](03-实现交接.md) 待查项。

## 四、B 护栏 · 给 `--bg-mask` 一个可读性下限

`--bg-mask` 在 [BackgroundLayer.css:6](../../../../src/pool/zones/BackgroundLayer.css) 里被明确写成「**图+玻璃可读性生命线**」（对标 dsh `mask-photo` 0.88），已经存在、已经被 `app.backgroundMask` 暴露给用户。B 案**不造第二套亮度引擎**，只给这个现成旋钮加一条下限：

```
① 估一个面亮度      surface ≈ composite(照片均值, 图不透明度, glass-surface-alpha, --bg-*-solid, --bg-mask)
② 算墨色对比        cr = CR(iconInk, surface)
③ 若不达标（< 3.0）则反解出需要的 mask 值 m，抬到能达标为止（上限 0.9）
④ 若抬到底仍不达标  ⇒ 说明墨色与遮罩方向相反（暗墨 + 暗遮罩），退一步：翻墨色极性
⑤ 全程可见         设置页显示「为保证图标/文字可读，遮罩已自动抬到 X」＋ 一个可关的开关
```

**为什么用「照片均值」估而不是读像素**：读像素要 canvas（**异步**）、要逐区采样，而且**同一张图不同区域答案不同**——全局一个数本来就不该假装精准。**B 的定位是「全窗最低线」，不是「逐像素正确」**；逐像素正确那件事归 C（光晕本地生效）。

**反解实测（⚠️ 仅暗分支：目标为白墨@78% 对遮罩后的面 ≥3:1）**：

| 对哪张面 | 需要的 `--bg-mask` | 结论 |
|:--|:--|:--|
| 实测合成面（L≈0.23） | **0.02** | 今天 0.15 **本来就够** ⇒ 护栏救得了“这一格”，**救不了“亮照片”** |
| 亮照片合成后（L≈0.55） | **0.34** | 今天 0.15 的 **2.3 倍** ⇒ 照片会**明显变暗** |

⇒ 这条读数还有一个副作用：**它证明 C（光晕）比 B（护栏）便宜**——光晕不碰任何全局观感就把亮照片那格抬到 8.09，而护栏为达标要动整窗。

### 4.1 🔴 更正（2026-10-03 实机复测 · light 型主题 `theme-pill`）

**上面那套反解算法有一个隐含前提：「面跟着照片走」。亮分支上这个前提是错的。**

图标栏**自己会铺一层玻璃**（`--bg-icon-bar` ＝ `--bg-icon-bar-solid` × `--glass-surface-alpha`；`theme-pill` 里是 `#FFFFFF` × 0.38）。这层玻璃给「面」设了一个**下限**：

```
面 = 玻璃白 × α  +  (1−α) × (照片 × (1 − mask))
```

α = 0.38 时，**哪怕照片纯黑、遮罩拉到 1**，面最暗也只能到 **`#616161`** —— 遮罩压不动它。

| 事实 | 数值 |
|:--|:--|
| 遮罩拉到 1、α=0.38 时的最暗面 | `#616161` |
| 该面上非激活墨色（`#999999` @55%） | 🔴 **CR 1.57** |
| **非激活墨色在「α × 照片亮度」全平面上的全局上限** | 🔴 **CR 2.82**（需 α≈0.03 ＋ 照片近黑；该点上激活态只剩 1.43） |
| 抬遮罩对亮分支激活态的影响 | 🔴 **反向有害**：面越暗，近黑墨色越贴回去（α=0.38 时已从 3.41 掉到 2.19） |

⇒ **结论：B 从「三腿之一」降为「暗分支可选护栏」。** 亮分支要修，只能动**墨色**（A ＋ C）——**⛔ 不能靠背景旋钮**（遮罩、玻璃不透明度、图不透明度都不行：它们的**全局天花板 2.82 到不了 3:1**）。

⛔ **不许**在 A/C 里塞「先算亮度再决定墨色」的逻辑——那会把一个**静态可推理**的 CSS 契约变成一个**运行时估算**，判据可能错、还难验。⇒ B 是唯一允许碰亮度的地方，且必须**可见、可关**。

### 4.2 🔴 复算复核（2026-10-03 阶段 3 开工前）：§四 第一张反解表**复算不出**，暗分支的数从来没算过

按 §4.1 更正后的暗分支模型（面 = **暗**玻璃 × α ＋ (1−α) × 照片 × (1−mask)，墨 = 白 @78% 在 sRGB 空间合成，CR 照 §1.3 口径）把 §四 那张表重跑一遍：

| §四 表里那一行 | 契约写的 | **复算值** | 判 |
|:--|:--|:--|:--|
| 实测合成面（L≈0.23） | 需 0.02 | **0.02**（抬 0.02 正是把 CR 2.95 顶到 3.0） | ✅ 对得上 |
| 亮照片合成后（L≈0.55） | 需 **0.34** | **0.01**（α=0.38）/ **0**（α=0.50） | 🔴 **差 34 倍** |

⇒ 那张表是 **§4.1 更正之前**的产物——它按「面跟着照片走」（无玻璃 / 白玻璃）算的。**§4.1 一旦把暗玻璃（`#18181B`）算进去，面在 mask=0 时就已被玻璃压到 L≈0.21（白墨 CR 已 3.03）** ⇒ 暗分支的「需要抬多少」与契约表差一个数量级。**B 的暗分支数从来没算过**，3.1 直接照 §四 反解会落一个 3–4 倍高估的遮罩。

**暗分支重算（本次复算，供 3.1 用）**——玻璃取壳默认暗 `#18181B`，遮罩基色黑，图不透明度按 1（放大照片贡献 = 对白墨取最坏）：

| 契约行「亮照片 L≈0.55」（≈196） | 0.01 | 0 |
| 实测图均值 L=0.352（≈163） | 0 | 0 |

**另一条读数（与用户当前配置有关）**：α=0.38 且用户已手抬 `app.backgroundMask` 到 **0.42** ⇒ 最坏照片下白墨 CR 已 **4.30**（亮照片 5.71）。**⇒ 护栏对这个配置是空操作**，B 只剩「没手动抬过遮罩的用户」这一个受益人。

**3.1 还缺一个输入（⏸ 待拍板，三选一）**：算法要「照片均值」，而契约**没写它从哪来**，全仓也**没有这份机制**（`grep` 图像解码：无 canvas / ImageBitmap / getImageData；`importImage` 只做主进程拷贝入库，不解码）：

- **(c) 用户可见的「背景图亮度」旋钮**——多一个可调旋钮（= 05 设计图里那个草稿控件），护栏可预测且不必假装精准，代价是又多一个键。

## 五、⛔ 不许（踩了就是返工）

- ⛔ **只改 `invert(52%)` → `invert(x%)` 就交差**——治标。亮照片 + 暗照片两头不可能同时满足一个固定灰（[02 E12](02-边缘情况清单.md)）；且实测亮底上**纯白的理论极限只有 1.75**，任何固定墨色都过不了。要止血就照 §1.3 明确标成「取证版」，别混进正版。
- ⛔ **给 emoji 图标套单色 mask 或反向晕**——emoji 是**彩色字形**，单色化会毁掉它（[02 E1](02-边缘情况清单.md)）。emoji 走原样。
- ⛔ **用 `mix-blend-mode: difference` / `exclusion`**——盲区实测在 sRGB 0.35–0.65（最差 CR 1.07），而你那张问题面 sRGB≈0.52 正落在带中央；另有三条独立否决理由（丢墨色／与自身 hover·active 串味／彩色照片上出噪点）。见 [00 §四 D](00-README.md)。
- ⛔ **用亮度线性混合去估对比度**（见 §1.3 注）——会跨过 3:1 这条线而不自知。
- ⛔ **让 A 去读照片亮度**（见 §四 尾）。
- ⛔ **把激活态的强调色径向盘／2px 左条改成常驻**——那是「最稳但最毁设计」的一案，只留给 active/hover。
- ⛔ **写死 hex 或裸 px 当产品值**（硬约束 1）：墨色走 `--text-primary` 派生，光晕半径**故意**是绝对 px（视觉常量，不随 `--ui-scale` 缩放，与 `--radius-*` 同为绝对标尺）。
- ⛔ **在 `IconBarZone.css` 里 `@import` 壳 CSS**（池 CSS 门禁 `pool-css`）。
- ⛔ **改主题引擎的极性算法**（`app.fontTone`／主题 `type` 判定是既定拍板）——本件只做**消费侧**。
