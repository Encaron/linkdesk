## 一、VS Code 对标证据（产品身份三件套）

> 来源：VS Code `product.json`（运行时注入）+ `src/vs/platform/product/common/product.ts`

VS Code 的身份字段长这样（用户实测「关于」对话框全字段）：

```jsonc
// product.json（示例，VS Code 实际值）
{
  "nameLong": "Visual Studio Code",
  "nameShort": "Code",
  "version": "1.135.0",               // ← SemVer 主版本
  "commit": "08d4889…",               // ← git 提交哈希（更新 URL 用：服务端拿它判断落后几个版本）
  "date": "2026-08-25T14:26:52Z",     // ← ISO 发布时间（发行说明/更新时间戳用）
  "electronVersion": "42.8.1",
  "chromiumVersion": "148.0.7778.280",
  "nodeVersion": "24.18.1",
  "v8Version": "14.8.178.38-electron.0",
  "updateUrl": "https://update.code.visualstudio.com",
  "quality": "stable"                  // ← 更新通道（stable / insider）
}
```

**关键设计**：
- **版本 = 三件套：`version`（SemVer）+ `commit` + `date`（ISO）**——三者缺一不可：版本号给人看，commit 给更新服务比对，date 给发行说明排序。
- **runtime 展示的运行时版本（Electron/Chromium/Node/V8/OS）不是 product.json 手写的**——是运行时的 `process.versions` + `navigator.userAgent` 动态读取（一次读取缓存），所以永不漂移。
- `commit` 是更新 URL 的核心参数（`${updateUrl}/api/update/${platform}/${quality}/${commit}`）。

## 二、LinkDesk 设计——product.json（壳启动时注入）

### 2.1 文件位置与加载

新建 `electron/product.json`（**在 electron 工程根，随打包进 asar 根**）。壳启动时 `product.ts` 读取（对标 VS Code `productService`）：

```
electron/
  product.json      ← 身份唯一真相源（版本/commit/date/质量）
  product.ts        ← loadProduct(): Product 类型读取 + process.versions 运行时增强（一次读取缓存）
```

### 2.2 Schema

```jsonc
{
  "nameLong": "LinkDesk",
  "nameShort": "LinkDesk",
  "version": "0.1.0",                    // ← 与 package.json version 同步（发布脚本保证）
  "commit": "91e6aa36…",                 // ← 构建时注入 git HEAD（发布脚本写）
  "date": "2026-08-30T00:00:00Z",        // ← 构建时注入构建时间（发布脚本写）
  "quality": "stable",                   // ← 通道：stable / preview（第二版才用 preview）
  "updateUrl": "https://api.github.com/repos/encaron/linkdesk/releases/latest"  // ← 更新源
}
```

TS 类型：

```typescript
export interface Product {
  nameLong: string;
  nameShort: string;
  version: string;          // SemVer
  commit: string;           // git HEAD 短哈希
  date: string;             // ISO 8601
  quality: 'stable' | 'preview';
  updateUrl: string;
}

export interface ProductRuntime {       // runtime 增强（process.versions，不落盘）
  electron: string;
  chromium: string;
  node: string;
  v8: string;
  os: string;              // `${platform} ${release}`（用户实测 VS Code 的 "OS: 1.0.81-0"）
}
```

### 2.3 version 与 package.json 同步（单一真相源）

**原则：`package.json` 的 `version` 是发布时的唯一真值，product.json 的 version 由发布脚本写入（不是手写两份）。**

- 开发期：product.json 可留 `"version": "0.1.0"` 占位，**壳代码永远从 `app.getVersion()` 读**（Electron 自动读 package.json version，单点）。
- 发布期：`npm run publish`（E6#26d 命令族）→ 读 package.json version → 写 product.json `version/commit/date/quality` → electron-builder 打包（app 内嵌 product.json）。
- **规则：任何地方都不手写第二份版本号。** `app.getVersion()` = 唯一运行时来源；product.json 的 version 字段仅供打包产物自证（与 app.getVersion 一致性由发布脚本断言）。

### 2.4 历史版本怎么表示（用户第一问的直答）

**规范：** 每个发布 = GitHub Release 一个 tag，tag 名 = `v{version}`（`v0.2.0`）。历史版本 = GitHub Releases 列表，天然按时间倒序。

| 维度 | 规范 | 类比 |
|:--|:--|:--|
| 版本号 | **SemVer `MAJOR.MINOR.PATCH`**（`0.1.0`）；E5.7/E5.8 等内部阶段号不进入版本号 | VS Code `1.135.0` |
| 每个版本标识 | `version` + `commit` + `date` 三件套 | VS Code 三件套 |
| 版本存储 | GitHub Release（tag=`v0.2.0`），Release body = 该版发行说明 | 无（VS Code 用 update 服务 + 独立 md） |
| 历史列表 | GitHub Releases 页天然倒序（`https://github.com/encaron/linkdesk/releases`） | 无（VS Code 用 changelog 页面） |
| 版本间关系 | semver 升序单调；破接口大版本升 MAJOR（0.x 时代 minor 即破坏性） | VS Code 同 |
| 当前版本在哪看 | 关于标签页 + 发行说明标签页头部 | VS Code 帮助→关于 |
| 更新比对 | `latest.tag_name > current`（semver 比较） | 服务端 commit 比较 |

**发行说明 = 每版 Release body**（存 GitHub，不造第二套存储）——查看面见 [05-发行说明.md](05-发行说明.md)。

### 2.5 版本比较算法（sematic version，零依赖）

```typescript
// 更新比对：返回 -1 (a<b) / 0 / 1 (a>b)；忽略 v 前缀；非纯数字段（如 0.2.0-beta.1）按 semver 预发布规则
function compareVersions(a: string, b: string): number {
  const va = a.replace(/^v/, '').split('.');
  const vb = b.replace(/^v/, '').split('.');
  for (let i = 0; i < Math.max(va.length, vb.length); i++) {
    const na = parseInt(va[i] ?? '0', 10);
    const nb = parseInt(vb[i] ?? '0', 10);
    if (na !== nb) return na > nb ? 1 : -1;
  }
  return 0;
}
```

> 0.x 语义补充（沉档）：`0.x.y → 0.x.(y+1)` = 补丁级；`0.x.y → 0.(x+1).0` = 破坏性（0.x 时代 minor 承担 MAJOR 职责）；进 1.0 前不承诺向后兼容。这是 LinkDesk 尚在 0.x 的合理过渡，市场 `minAppVersion` 字段按此比对（E6#29）。

### 2.6 版本号机械校验层（2026-08-31 用户拍板立案——防「更新上去了版本号没更」）

> 决策模型：**发布经理定版（用户拍板）+ 机器校验（脚本卡死）**——对标大厂「版本号由规则+机器算、人只打类别标签」，但保留用户拍板权（**不做 semantic-release 全自动**，用户要「询问我升级版本号」的控制权）。

| 机制 | 内容 | 落点 |
|:--|:--|:--|
| **发布门禁脚本** | `npm run publish` 前置断言：① 当前版本号 > 最近 release tag（`compareVersions` §2.5）② `package.json` version === `product.json` version === Git tag `v{version}` **三处一致**；任一不符 → **拒绝发布**（对标 CI 门禁，机械卡死非自觉） | E6#57.15d |
| **commit 分类约定** | commit message 前缀 `feat:`（新功能）/`fix:`（修复）/`breaking:`（破坏）——与 E6#编号组合（如 `feat:E6#xxx`）；历史可审计 + 将来自动生成 changelog | E6#57.15e |
| **CHANGELOG.md** | 每次 bump 写一条：`## v0.1.1（2026-08-31）` + 类别清单（feat/fix/breaking）；对标 VS Code changelog；~~当前无此文件，首次 bump 时创建~~ **⚠️ 2026-09-10 校正：文件早已建立**（仓库根 `CHANGELOG.md`，最新条目 `## v0.1.27（2026-09-10）`；首页明写「历史真相源 = E6 执行清单，此文件只记类别清单」） | E6#57.15e |

**分类映射**（与 version-bump skill 同源）：MAJOR = `breaking:` / MINOR = `feat:` / PATCH = `fix:`。**E6 结束 ≠ 1.0**——生态验证期（插件上市/联网测试/API 补充）仍 0.x，三条件（生态闭环+API 冻结+数据格式冻结）齐才 1.0。

### 2.7 MAJOR/2.0 判定前置自检——先问「能不能增量」（2026-09-04 用户拍板）

> 补强 §2.4「破接口才升 MAJOR」。**2.0 = 兼容失败的症状，不是随手选的档位。** 判定口径与 version-bump skill §2.0 界限同源，两侧改动必须同步。

- **能增量 + 默认值兜底 → MINOR（1.x）**，哪怕改动是「所有插件须声明新字段才能用新能力」——只要老插件不声明仍装得上、跑得动，就是增量，不是 schema 断裂。
- **「拒绝安装 / 强制全员声明」= 自选 2.0**：拒绝 = 逼所有下次要发布的作者同时适配。祖父条款只能减痛、不能把 2.0 降回 1.x；只有「祖父 + 不拒绝 + 增量解锁」才留在 1.x。
- **唯一必须 2.0**：默认值填不了、旧插件留着会出事（真数据/schema 断裂、必然冲突）→ 兼容层兜不住才动用拒绝 + 大版本 + 迁移文档 + 插件作者过渡期。
- **依据**：VS Code 十年几百版停 1.x（2026 普通用户仍 1.105.x，2.0.0 只灰度预览从未全量）——一切新能力增量进、旧格式永续兼容、从不用「拒绝」逼适配；`engines` 让插件自报目标宿主，宿主对旧契约长期兜底（对标 LinkDesk `contributes` 版本化 + marketplace `minAppVersion` 的对称机制）。
