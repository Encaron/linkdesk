# §2.5 裁决：视图容器 id `explorer`（1.42 · `#111n-1`）

> **裁决：不改。**（理由逐条带实测，非推断）
>
> **非新能力声明（`check-design-flow` §8.4 ③）**：本档是**既有名字归属的裁决记录**——引用 `contributes.*`
> 只是在**描述既有 manifest 字段**，**零新增能力、零新 API、零新控件、零视觉变化** ⇒ **无需新能力设计前置**。

## 一、事实（`file:line` ＋ 实测读数）

| 项 | 值 |
|:--|:--|
| manifest 声明 | `contributes.viewsContainers.explorer`（`plugin.json:25`）· `contributes.views.explorer`（`:31`） |
| 运行时注册 | `registerView("file-tree", "explorer", …)` **2 处**（`src/views/FoldersView/useViewRegistration.tsx:27,58`）——**已带 `pluginId` 归属** |
| 视图 id | `folders` · `search`（同样裸名） |
| 壳侧归属表 | `ViewContainerService._containerOwner`（`:73,104,110`）——容器 id 有归属，**但键是裸容器 id** |

## 二、容器 id 进了哪些用户盘面（**逐面实测，不是推断**）

| # | 面 | 是否含容器 id | 实测证据 |
|:--:|:--|:--:|:--|
| 1 | `layout.json`（窗口布局） | ❌ **不含** | `layout.json` 顶层 = `tabs/cards/panel/sidebar/detachedWindows`，全文 `"explorer"` 命中 **0** |
| 2 | `settings.json` | ❌ 不含 | 命中 0 |
| 3 | `keybindings.json` | ❌ 不含 | 命中 0 |
| 4 | `workspace-folders.json` / `windows-state.json` | ❌ 不含 | 命中 0 |
| 5 | `plugin-states.json` → `app.viewOrder.<容器id>` | ⚠️ **理论含，本机实测无** | 键名模板 `viewOrder.${containerId}`（`ViewContainerService.ts:379,388`）；本机 `app.*` 键**零命中** `viewOrder`（用户从未拖排过视图） |
| 6 | `plugin-states.json` → `app.activeSidebarPlugin` | ❌ **存的是 `pluginId` 不是容器 id** | `sidebarHost.ts:76,124`；本机值 = `"marketplace"` |
| 7 | `plugin-states.json` → `hiddenViews` / `collapsedViews` | ❌ **复合视图键 `pluginId:viewId`，不含容器 id** | `hidden.ts:33` / `collapsed.ts:31` 走 `viewKey(pluginId, viewId)` |
| 8 | `plugin-states.json` → `app.pluginMetadataCache` | ✅ **含（47 处）** | 缓存整份旧 manifest；**但每次加载刷新**（`resolution/state.ts:198` · `runtime.ts:247` 的 `cachePluginMetadata(…, "installed")`）⇒ **自愈，不构成迁移面** |

> **全盘实测结论**：本机用户盘上**没有任何键名或值与容器 id 绑定**（唯一含 `explorer` 的是 manifest 缓存，而它每次启动自愈）。

## 三、裁决：**不改**（四条理由）

1. 🔴 **`views.explorer` 与容器 id 是同一个字符串** ⇒ 改容器 id 必然要么**同时改视图 id**，要么让 manifest 自我不一致（`views` 的顶层键就是容器 id）。**"只改容器 id"这个动作在 manifest 结构上不存在。**
2. 🔴 **改了就真会丢用户数据（有迁移需求）**：`app.viewOrder.explorer` 会失配 ⇒ 用户拖排过的视图顺序**静默回默认**（`loadViewOrder` 读不到新键直接 return，无报错）。今天本机恰好没这条键，但**第三方用户可能有** ⇒ 这是**真用户数据面**，不是理论面。
3. 🟠 **不是本轴判据要治的病**：容器 id 已进 `ViewContainerService._containerOwner` 归属表 + `registerView(pluginId, containerId, …)` 已带显式身份 ⇒ **无跨插件顶替风险**（对抗性实测：`file-tree` 与 `marketplace` 各有裸名容器，复合键域天然隔离）。它缺的只是「名字里有归属」，**那是外观一致性，不是行为安全**。
4. ⚠️ **不在 1.35/1.37 射程，也没有任何一档替本格定过它的映射**——本格**不许自行发明映射**（作业包纪律：映射只从 1.31/1.33/1.35/1.37 的裁决来）。若要改，须**先由一轮评估定映射 ＋ 补 `viewOrder.<容器id>` 键迁移**，那是**另一件事**。

⇒ **登记为「本格不做」，理由如上；不静默跳过。** 归口建议：与 [1.49](19-任务-门禁与作者面收口.md) 的「账定稿」一并复核是否要立一项。
