4. ⛔ **不许跳棒**：会话五（尺子 ＋ 收口）**必须等**会话一~四全部收口（尺子的读数对象就是它们补出来的测试）；会话二/三/四**必须等**会话一的 0.1.47 **上架 npm 货架**（否则它们的 lock 装不到新 subpath ⇒ CI 直接红）。

## 编排与依赖（为什么是这个顺序）

- **一必须最先**：它是地基棒——不收 ⇒ 后面每仓补测试都要在自己那份 `vitest.setup.ts` 上再抄一遍 mock，本层产出立刻变成**新的漂移源**（用户点名这条排第一）。
- **二/三/四可并行**：每会话只动自己的仓；`#147`/`#149`/`#151` 是「纯逻辑 ＋ 先裁决」的主干，`#148`/`#150`/`#152` 是同会话的第二格（替身层/小仓），**同一 AI 连做**——这正是用户要的「一个 AI 多个任务，不太少也不太多」。
- **五必须最后**：尺子的判据要照**既成事实**写（先有正例、后定判据）；销账要引各仓最终读数。
- ⚠️ **别在二/三/四期间发版**：本层的五仓**默认不 bump**；唯一发版情形 = 补测**发现真 bug**（`fix:`＋发版＋目录收录；种子仓还要 `sync:bundled`）——那条链路要走就走全，别半套。
- 🟢 **2026-09-25 用户明示授权（这一条解除含糊）**：补测**发现真 bug ⇒ 先汇报、再改**——典型情形 = **某只插件里藏着一个用户从没撞上的隐藏 bug**（帧缓冲越界、状态合并漏字段这类算法 / 时序缺陷，测试一写就现形）；**因修复产生的版本变化（该仓 PATCH ＋ 发版 ＋ 目录收录；种子仓 ＋ `sync:bundled`）是被允许的**——⛔ 别因为「本层默认不 bump」而压着不改，也别只报不改。汇报要含五项：**哪仓 · 症状 · 判据（哪条测试抓到的）· 打算怎么修 · 涉及哪个版本号**；修复**单独一笔**提交，⛔ 不与测试同笔、⛔ 不推送。
