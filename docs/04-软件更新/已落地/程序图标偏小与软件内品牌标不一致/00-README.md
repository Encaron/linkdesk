## 〇、一句话结论

- **外部偏小**：程序图标 `build/icon.ico` 的图形**留白过大**——256px 帧内容只占画布 **63% 宽 / 73% 高**，而对照的桌面软件是 **92%–100%**；桌面默认中图标取 48px 帧，那一帧只有 **71%×81%**，所以**看起来小一圈**。图形放大约 **1.5 倍**、并统一各帧留白即可解决。
- **软件内不一样**：软件里那个是 **「蓝圆角方块 + 白『LD』文字」**（`public/assets/logo.svg`，迁移期临时资产），而程序图标是 **「六边形 + 三个节点」**（本文实测像素得出）。**同色（`#0078D4`）不同形**，所以观感"压根不是同一个图标"。而且软件内部自己就不统一：欢迎页背景水印用的**正是**六边形节点标。

## 〇之一、首次实现做反了颜色 ⇒ C 案返工（2026-09-27，本项最终状态）

### 0.1.1 做错了什么

v0.2.19 交付的正典标画成了「**蓝线条勾勒 + 三个蓝点**」（描边形态）；**原版是「蓝色实心六边形 + 三个白孔**」（实心形态）——**填充与空白正好反了**。用户装上 v0.2.19 一眼看出，原话：「本来是蓝色填充大部分，现在变成蓝色线条勾勒，然后中间三个蓝色点了，就是说你是不是把颜色反了一下，本来填充的，你弄成空白，本来空白的，你填充的蓝色」，并点名「包括关于 lindesk 标签页的」（同一份 `logo.svg` 资产喂标题栏/关于页/BootMark，一处反、处处反）。

### 0.1.2 根因：§五 方法② 的像素读法本身不可靠

原版 `icon.ico` 实为**实心蓝底 + 三个白孔**。当初用「按不透明度 + 亮度映射成 ASCII」读图时，**白孔被读成了「节点」、实心蓝底被读成了「底」**，于是写出「六边形轮廓 + 三个节点」的结论——按这个错结论重绘，颜色就反了。

**教训（写给下一棒）：品牌资产不能靠降采样 ASCII 摘要判形——「描边」与「实心＋反色孔」在亮度摘要里长得一样。** 要判形就量像素：内容框内**主色像素占比**、白/主色簇的**重心与半径**（本轮判 C 案用的就是这个：主色 `(0,120,212)` 铺满六边形内部，三个 `(255,255,255)` 圆簇在 `(128,63)/(72,163)/(182,163)` 附近、半径 ≈8）。

### 0.1.3 返工怎么定的

用户要求「先设计好，不同地方的图标怎么显示，画 HTML，让我看看」。⇒ 归档参考图 [mockups/01-图标显示设计-参考图.html](./mockups/01-图标显示设计-参考图.html)：**三案并排**（A = git 历史 `82833d904^` 的**原版真帧**；B = v0.2.19 已发布版；C = 修正提案＝原版几何按 1.46× 放大）**× 六个显示位真实尺寸**（桌面大/中图标、任务栏、开始菜单、标题栏、关于页、BootMark），带亮/暗系统底切换。**用户 2026-09-27 拍板 C 案。**

## 一、问题一：桌面 / 任务栏 / 开始菜单图标偏小

### 1.1 实测（方法可复现，见 §五）

| 图标来源 | 内容框（256px 帧） | 占画布宽 | 占画布高 | 最大留白 |
|:--|:--|:--:|:--:|:--:|
| Cherry Studio | 256×256 | 100% | 100% | 0px |
| VS Code | 256×256 | 100% | 100% | 0px |
| ZCode | 256×256 | 100% | 100% | 0px |
| 豆包 | 256×256 | 100% | 100% | 0px |
| Telegram | 236×236 | 92% | 92% | 11px |
| **LinkDesk（仓内 `build/icon.ico`）** | **162×186** | **63%** | **73%** | **47px** |

⇒ 达到 Telegram 那种"留了一点安全边"的水平要放大 **≈1.46×**；达到主流 App 的满画布水平要 **≈1.59×**。**"小一圈"的观感就是这么来的——不是 Windows 显示有问题，是图形本身只占了画布的三分之二。**

### 1.2 同一个 .ico 里各帧留白还不一致

| 帧 | 内容框 | 占宽 | 占高 | 左边距 |
|:--:|:--|:--:|:--:|:--:|
| 16px | 16×16 | 100% | 100% | 0% |
| 24px | 20×22 | 83% | 92% | 8.3% |
| 32px | 24×27 | 75% | 84% | 12.5% |
| **48px（桌面中图标）** | **34×39** | **71%** | **81%** | **14.6%** |
| 64px | 44×50 | 69% | 78% | 15.6% |
| 256px | 162×186 | 63% | 73% | 18.4% |

⇒ 留白随尺寸**递增**（16px 满画布 → 256px 只剩 63%）。后果是**同一个图标在不同位置看起来大小不一**——小尺寸位置（任务栏 24/32）勉强，大尺寸位置（桌面中图标 48、大图标/高 DPI）明显偏小。**修的时候要一起统一**，只改 256px 帧没用。

### 1.3 帧集缺两档

现有帧：**16 / 24 / 32 / 48 / 64 / 256**——**缺 96 与 128**。Windows 在 125%/150% 缩放的桌面与资源管理器里常取 96/128，缺档只能由邻近帧缩放 ⇒ **发虚**。

### 1.4 影响面：一处改、处处好（所以值得做）

| 位置 | 图标来源（证据） |
|:--|:--|
| 桌面快捷方式 / 任务栏 / 开始菜单 / Alt-Tab / 文件关联 | exe 内嵌图标 ⇒ electron-builder 打包时取自 `build/icon.ico`（`electron-builder.yml` 的 `win` 段**未显式声明 icon**，靠 electron-builder 的约定目录 `build/` 兜着） |
| 窗口图标（dev 与 prod 两条路） | `electron/main.ts:483-485`——dev 与打包后**都**指 `icon.ico` |
| Shell 文件关联「打开方式」图标 | `build/installer.nsh` 的 `DefaultIcon` 指向 `$INSTDIR\LinkDesk.exe`（即上面的 exe 图标） |

**附带发现（顺手可做）：** `electron-builder.yml` 没写 `win.icon`，今天靠约定成立；显式声明一行更稳（将来加平台/挪目录不会静默丢图标）。

|:--:|:--|:--|:--|
| 1 | **程序图标**（桌面/任务栏/窗口） | **实心六边形 + 三个白孔**（顶部中一个、底部左右各一个），主色 `#0078d4` | `build/icon.ico`——⚠️ 本行原写「六边形轮廓 + 三个节点」，**是错读**（§0.1.2 已更正：原版是实心填充＋白孔） |

**兄弟条目：[`关于LinkDesk标签页重设计/00-README.md`](../关于LinkDesk标签页重设计/00-README.md)**（2026-09-26 立案）。**两项在「关于页那颗 logo」上相遇，但管的不是同一件事**：

⇒ 一句话分工：**标归本项，摆法归那一项。** 谁先落地都不会挡住对方。

> **2026-09-26 追记（启动过场立案在同日之后）**：新兄弟条目 [启动过场与加载态](../启动过场与加载态/00-README.md) 的**池首帧品牌过场（BootMark）**也是本项的下游表面——其 logo 同样取 `logo.svg` 同源资产，本项换源后**零代码跟随**，「同一份资产喂三处」随之变**喂四处**（标题栏 / 关于页 / 启动过场 / + 打包图标本体）。分工口径不变：**标归本项，摆法归各页与过场条目**，谁先落地都不挡对方。

### 2.2 为什么不一样（归因）

- `public/assets/logo.svg` 是**迁移期的临时标**：它自己的注释就写着"替换此文件即可更换 logo"，是留给"以后换真标"的占位；程序图标那份（六边形节点标）才是被打进 exe 的真品牌标。
- 于是软件内**同时存在两种品牌语言**：欢迎页水印是**六边形节点标**（与程序图标同源），标题栏/关于页是 **LD 文字标**。用户看到的"左上角、关于页是个 ld，不是我 LinkDesk 那个图标"——**完全成立，且是两处不一致**（对程序图标不一致 + 软件内部自己也不一致）。

## 三、方向（大体怎么改，不含详细方案）

1. **定「正典标」**：建议取 **六边形 + 三节点**（理由：它既是程序图标、又是欢迎页水印，且"Link＝连接节点"这个意象比文字缩写更贴品牌；`LD` 文字标可退为辅助或直接弃用）。
2. **建单一源**：仓里补一份**矢量真源**（如 `build/icon.svg`），由它导出 ① `.ico` 各帧 ② 软件内用的 `public/assets/logo.svg`——**一次改源、两处同步**，根治今天"程序图标与软件内标各写各的"。
3. **尺寸与留白规范**：内容占画布 **92%–96%**（对齐 Telegram 量级；满画布 100% 也可以，但要与同类 App 一致），**所有帧同一比例**（16px 可单独微调，但不得 0 留白）；`.ico` 帧集补齐为 **16 / 24 / 32 / 48 / 64 / 96 / 128 / 256**。
4. **打包显式化**：`electron-builder.yml` 的 `win.icon: build/icon.ico` 写死。
5. **软件内落地**：`public/assets/logo.svg` 换成同源标 ⇒ 标题栏、关于页、池 logoUrl 三处自动跟随（现有单一入口，**零代码改动**）。

## 五、复现方法（未来 AI 复核用，2026-09-13 实测）

**① 量留白（对照桌面软件）：** 用 `user32.PrivateExtractIconsW` 从 exe 取 256px 图标存 PNG，再用 Pillow 取 alpha 的 bounding box，算「内容框 / 画布」比。桌面快捷方式指向的程序清单可用 `WScript.Shell` 的 `CreateShortcut().TargetPath` 一次读出（本次取的是 `D:\360MoveData\Users\fengy\Desktop\*.lnk`）。

**② 读 .ico 里到底画了什么（不看图也能判断）：** 用 Pillow 打开 `build/icon.ico`、按 `info['sizes']` 逐帧取，把 256 帧降到 64×64 后**按不透明度+亮度映射成 ASCII**——当时读成「六边形轮廓 + 上中一个圆 + 下左右两个圆」（与欢迎页水印的 `polygon` + 三个 `circle` 坐标吻合）。

> 🔴 **本方法已被证伪（2026-09-27，§0.1.2）**：原版实为**实心蓝底 + 三个白孔**——亮度 ASCII 把「白孔」读成了「节点」、把「实心蓝底」读成了「底」。**改用色值法复核**：清点内容框内的主色像素占比 + 白/主色像素簇的重心与半径（原版实测：主色 `(0,120,212)` 铺满内部，三个 `(255,255,255)` 圆簇在 `(128,75)/(85,152)/(170,152)` 附近、半径 ≈5.5，256 帧内容框 162×186＝63%×73%）。**判形看色簇，不看亮度摘要。**

**③ 三处资产/消费点的核对位置：** 见 §1.4、§2.1 表格右列（`file:line` 全部当场核过）。
