> 当年缺的不是「解耦意识」，是**归属判据**。解耦管住了 import 方向，**没管住「这份能力该住哪一层」**；没有第二个实现者，就没有人问「换一台插件谁来画」。
> 设置插件**出生在壳仓**……写它的时候，「第二台设置插件」**不存在**。

## 三、缘起：用户新提的需求（P1/P6 的触发条件可能就是它）

用户 2026-10-05 原话要点：**「很多的插件都需要这种特殊功能」**——例：一个「每日日记」插件把日记存成 markdown，插件**自己内部**有个「打开这篇日记」按钮，右键可选「用编辑器插件／记事本／以 VS Code 形式打开」；「**如果说这个功能存在于文件树的话，那么其他的插件怎么样才能够用到这个功能？**」

**今天第三方插件的能力矩阵**（证据：`contracts/linkdesk.d.ts:1941-1953` `LinkDeskAPI.fileAssociation`；通道 `electron/ipc/channels.ts:84-93`；声明面 `electron/plugins/plugin-manifest-loader.ts:89-110`；打开用法 `file-tree/src/views/FoldersView.tsx:126-134`）：

| 它要做的事 | 今天 | 缺口 |
|:--|:--|:--|
| 声明自己是某类文件的打开者 | ✅ `contributes.fileAssociations`（每个 manifest 都注册） | 只认扩展名（P3） |
| 编程问「该用谁打开／列出全部 handler」 | ✅ `lk.fileAssociation.getPluginFor` / `listHandlersFor` | — |
| 写默认／恢复自动 | ✅ `setDefault` / `setDefaultBulk` | — |
| 编程真打开 | ✅ `lk.tabs.create(pluginId, {filePath,…})` | — |
| **弹出同一个「选择打开方式」面板** | ❌ **只能自己重写** | **缺共享件 `OpenWithPicker`（P1）＋ 缺壳级调用面（P2）** |

⇒ 结论：日记插件今天要做「我自己的按钮 → 选打开方式」，除了判定/声明/打开已开放，**面板与入口都得自造**，且拿不到共享的「当前默认／恢复已动」语义。
