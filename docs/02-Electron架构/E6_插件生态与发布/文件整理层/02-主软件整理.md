### 1.1 `src/pluginLoader/lifecycle/lifecycle-ops.ts`（779 行）

**判据命中**：500-800 区间 + **≥4 个独立职责**。

**现状结构**（实测行号）：

| 区段 | 行 | 内容 |
|:--|--:|:--|
| 状态开关 | 74–250 | `getMutableManifest` / `disablePlugin` / `enablePlugin` / `uninstallPlugin` |
| 进度 + 包操作 | 252–312 | `emitInstallProgress` / `jobProgress` / `isPackageSource` / `packageOps` |
| **安装域** | 313–590 | `installPlugin` / `installWithProgress`（**~280 行，本文件最大一块**） |
| 查询投影 | 591–752 | `getLoadedPluginManifests` / `getListPluginManifests` / `getDisabledPluginInfo` / `getUninstalledPluginInfo` |
| 重装 + 转出口 | 753–779 | `reinstallPlugin` + 三条 re-export |

**拆法——同名夹 feature-folder**（照 0d.10-8 `KeybindingRegistry` 先例）：

```
src/pluginLoader/lifecycle/
├─ lifecycle-ops.ts          ← 聚合器门面：纯 re-export，本文件零逻辑
└─ lifecycle-ops/
   ├─ state-toggles.ts       ← disable / enable / uninstall + getMutableManifest
   ├─ install-ops.ts         ← installPlugin / installWithProgress / packageOps
   ├─ progress.ts            ← emitInstallProgress / jobProgress / isPackageSource
   └─ query-projections.ts   ← 四个 get*Manifests / Info
```

**🔴 关键约束（照 0d.10-8 逐条对齐）：**

1. **聚合器门面零逻辑**——`lifecycle-ops.ts` 只剩 `export { x } from "./lifecycle-ops/x"`。子模块**不重新导出**，聚合器是唯一出口。
2. **re-export 逐字保留**——`export { isUnderHome } from "./plugin-disk-location"` 与 `export { revertThemeIfCurrent, revertLanguageIfCurrent, reapplyThemeAfterUnload }` 必须在聚合器里**原样**保留（**别搬进子夹**，它们在 `plugin-disk-location.ts` 里，搬了就成"二次转手"）。
3. **`packageOps()` 与 `installPlugin` 同域**——`packageOps()` 是 `installPlugin` 的包操作句柄（源解析 + 解压 + 落盘），**不要拆到独立文件**。
4. **依赖单向无环**：`progress.ts`（零依赖）→ `install-ops.ts` → `state-toggles.ts` → `query-projections.ts`。**拆完确认无环**。
5. **外部消费方 import 零变更**——13 处消费方（`PluginInstallService.ts` / `notif.ts` / `useSubscriptions.ts` / `contributions.ts` / `update.ts` / `loader.ts` / `runtime.ts` / `state.ts` / `plugin-disk-location.ts` / `plugin-install-handlers.ts` + 2 test）**全部继续 `from "./lifecycle-ops"` 或 `"../lifecycle/lifecycle-ops"`**，一行不改。

**验证：**
- 聚合器 + 每个子模块**都不 >800**
- `npm run check` 全绿
- 实机：装一个插件 → 装成功；禁用/启用/卸载 → 各走一遍（`plugin:installJobs` 广播仍到）

### 1.2 `src/pluginLoader/lifecycle/install-queue.ts`（611 行）

**判据命中**：500-800 区间 + **≥4 个独立职责**。

**现状结构**（实测行号）：

| 区段 | 行 | 内容 |
|:--|--:|:--|
| 常量 + 类型 + 状态 | 31–135 | 5 个常量 + `InstallJob` / `JobRecord` 接口 + **模块级 `_jobs` / `_waiters`** |
| 身份 / 广播 / 落盘 | 137–258 | `snapshot` / `_listeners` / `onDidChangeInstallJobs` / `broadcast` / `persist` / `consumeUnfinishedInstallJobs` / `pruneSettled` |
| **队列编排** | 259–556 | `beginInstallJob` / `startInstallJobDirect` / `identifyInstallJob` / `acquireInstallSlot` / `settleInstallJob` / `touchInstallJob` / `updateInstallJobProgress` / `setInstallJobCanceller` / `cancelInstallJob` / `isInstallJobCancelled` / `cancelInstallJobByPlugin` / `waitInstallJob` / `openInstallJob`（**~300 行，最大一块**） |
| 槽位与看门狗 | 557–611 | `startJob` / `releaseSlot` / `armWatchdog` / `clearWatchdog` |

**拆法——同名夹 feature-folder**：

```
src/pluginLoader/lifecycle/
├─ install-queue.ts          ← 聚合器门面：纯 re-export，零逻辑
└─ install-queue/
   ├─ types.ts               ← InstallJob / JobRecord / terminal 类型
   ├─ store.ts               ← 🔴 **`_jobs` / `_waiters` 唯一属主** + 查询 + listeners + broadcast
   ├─ persistence.ts         ← snapshot / persist / consumeUnfinished / pruneSettled
   ├─ scheduler.ts           ← 槽位编排 + 看门狗（startJob/releaseSlot/arm/clearWatchdog）
   └─ job-ops.ts             ← 单任务生命周期（begin/start/identify/settle/touch/progress/cancel/wait/open）
```

**🔴 关键约束（这条是本轮最容易炸的地方）：**

1. **`_jobs` / `_waiters` 必须单一属主**——照 **0d.10-8** 先例「模块级 mutable 状态各归单域属主（`_bindings`→registry / `_chordState`→chord），跨域读走公开 accessor」。
   **`store.ts` 是唯一持有者**，`scheduler.ts` / `persistence.ts` / `job-ops.ts` 一律经 store 导出的函数读写。**绝不允许出现第二份 `_jobs`。**
   - ⚠️ **这是风险 3（模块级单例被拆散）在本轮的具体形态**：拆错了 = 队列有两份账、同一个 job 在 A 表排队在 B 表结算 → **表现为「装到一半不动了」或「重复装两次」，且只在并发时才现形**。
2. **`persist` / `broadcast` 的调用点不许变**——它们是有时序语义的副作用（落盘快照 = 崩溃复位用；广播 = 池通知面板用）。**只搬家，不改调用时机。**
3. **`SNAPSHOT_KEY` / `INSTALL_CONCURRENCY` / 三个超时常量集中一处**（`types.ts` 或 `store.ts`），**不要在多个子模块各写一份**。
4. **聚合器 re-export 全部公开符号**——消费方 `notif.ts` / `useSubscriptions.ts` / `plugin-install-handlers.ts` / `PluginInstallService.ts` **import 零变更**。

**验证：**
- **并发验证（本轮的必过项）**：连点 3 个插件安装 → **三个都进队列、并发槽 3 个都占上**、通知面板三段式显示正常（这是 E6#73q/73c 刚建好的能力，**拆坏了这里会第一个红**）
- 落盘快照仍在（`install-jobs` key）
- `consumeUnfinishedInstallJobs()` 仍能被 `startup.ts` 消费（E6#73l）
- `npm run check` 全绿

## 二、复核项（7 个）——**只有 7 个，判完可能一个都不拆**

> **复核 ≠ 必拆。** 下面 7 个都在 400–500 区间（低于 500 属「观察名单」），按 E6#0.4 的判据**默认不拆**。给出的是**复核方法**，不是结论。

**统一复核流程（每个文件走一遍）：**

1. **读导出清单** —— `grep -n "^export" <file>`
2. **数职责** —— 能不能把导出**分成 2 组以上、每组互不调用**？
3. **判归属** —— 是「一个东西的多个方法」（→ 不拆，0d.10-11 高内聚判据）还是「多个东西挤一个文件」（→ 拆）？
4. **查消费方** —— `grep -rn "<文件名>" src/ electron/ | wc -l`，>10 处消费时**拆的收益更低**（门面保留成本高）
5. **下判** —— 拆 / 不拆 / 提请用户拍板（**只有真该拆时才请**）

## 三、🔴 开工前必读的风险（本轮专属）

照 00 号档案 §六，本轮要盯的：

| 风险 | 本轮形态 |
|:--|:--|
| **① plugin.json 不同步** | ❌ 不适用（本轮不动插件） |
| **③ 模块级单例被拆散** | 🔴 **`install-queue` 的 `_jobs`/`_waiters`**——见 §1.2 约束 1 |
| **④ 循环 import** | 🔴 两个 feature-folder 都要**保持依赖单向无环** |
| **⑤ CM6 生命周期** | ❌ 不适用（本轮不碰 serial-monitor） |
| **⑦ 聚合器超门禁** | 🟡 聚合器是纯 re-export，**天然短**——本轮不会撞 |
| **⑧ 版本轴** | 🔴 本轮改 `src/` = **软件轴**，走 version-bump 判定（0.x 向后兼容 → patch） |
| **⑨ allowlist 过期豁免** | 🟡 本轮拆的文件若曾在 allowlist 里 → 移条目 + 删头注（当前 `EXEMPT_FILES = []`，**预期不适用**） |

**外加本轮专属一条：**

> **不要顺手改逻辑。** 拆 `lifecycle-ops` / `install-queue` 时，**只搬家、只改 import 路径、只加 re-export**。
> 看到旁边的代码「有点问题」→ **记下来单独立案**，不要混在这次 commit 里。混淆搬家与新逻辑 = 审查时分不清哪行是搬运、哪行是新行为，**回归时无法二分定位**（硬约束 15 的二分法会失效）。
