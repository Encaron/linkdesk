## 八、结论速览

**五句话**：

1. **外观族 id 今天没有任何归属机制**——五个 id 空间（配方 / 配色变体 / 图标主题 / 共享图标 / 语言包）**全部 last-wins ＋ `console.warn`**；其中「插件顶替宿主兜底」这一路**连告警都没有**（`ThemeEngine/registry.ts:40-42` 注释明写「覆盖 fallback 主题（无 pluginId）不告警——插件主题上位是预期行为」）。

3. 🔴 **账必须拆栏 ＋ 记持有者**——现行 `appearanceIds = ["dark","dark-fallback","light"]` 把**两个 id 空间混成一栏**，会让**官方自己的 `theme-defaults` 当场假红**（它声明的配色 id `dark` 落在这一栏里）⇒ 不拆栏的保护区判据**一上线就失效**（假红会让真红失效，宽容度模型 §十）。
4. 🔴 **一条腿带五个 id 空间参数**（否决五条腿）；**两本主题账不合并**（否决合并），但**必须登记「键不是同一概念」**（一本键 = id，一本键 = 显示名）。

## 十一、四问裁决（05 §2.2 逐条作答）

### 11.1 主题两本账要不要合并？ ⇒ **(乙) 不合并 ＋ 登记 ＋ 两侧共用同一归属判据**

- **合并属重构**，且**直接踩 05 §四 禁区第 2 条**（`commitTokens` / `theme:changed` 广播链 / flat 桥接是 29 号档 P1–P7 的保护对象）。
- 两本账是**两次架构迭代的产物**（`ThemeEngine/registry` 是 E5.8#50.x flat 桥接遗留的路由表，`ThemeRegistry` 是元数据＋配方权威）。
- 🔴 **但必须登记一条判据级事实**：**两本账的键不是同一个字段**——
  `ThemeRegistry` 键 = `themes[].id`；`ThemeEngine/registry` 键 = `themes[].label`（＝ theme JSON 的 `name`）
  ⇒ **一把尺子量两本账 = 量错一本**（§11.4）。

### 11.2 五本账用一条腿还是五条？ ⇒ **(甲) 一条腿 ＋ 五个 id 空间参数**

- 判据逻辑**同形**（归属段 ＋ 宿主兜底保护区），差别只在「账里取哪一栏 ＋ 从哪取 id」。五条腿 = **五份重复逻辑 = 下一把漏尺子的温床**（05 §2.2 原文）。
- **腿名**：`appearance-ownership`（承 1.32 `command-ownership` / 1.34 `config-ownership` 的命名）。
- **五个参数**：`recipe` / `colorway` / `iconTheme` / `sharedIcon` / `language`。🔴 其中 `language` 的判据**恒空转**（语言码永久豁免）——照 1.34 `HostReservedNames` 对未消费栏的姿势「**声明但不读**」，留位给将来的语言包命名（若有）。

### 11.3 配色变体 id 入不入账？ ⇒ 🔴 **入账，且必须单列一栏**（不是「并入配方 id 栏」）

**实测依据（05 要的就是这条）**：

1. **它是持久化载体**：`app.themeColor`（`appearance.ts` / `DynamicSelect.tsx:102` 写 `cw.id`）＋ `MIX_DOMAIN_KEYS.colors = "app.themeColor"`（`constants.ts:145`）⇒ 用户配置里真的存着配色 id；`findColorwayOwner`（`mix.ts:44`）按它反查属主 ⇒ **顶替 = 用户配置指向他物，真害成立**。
2. 🔴 **它与配方 id 不共享命名空间**（两个 id 空间：不同 Map、不同配置键、不同解析路径）⇒ **混成一栏会造假红**。**实证**：账现在这栏 `["dark","dark-fallback","light"]` 里，`dark` 是**配方** id、`dark-fallback` 是**配色** id ⇒ 而 **`theme-defaults` 声明的配色 id `dark`** 会**正好撞上**这一栏 ⇒ **官方仓当场红**（§十五.2 详解）。
3. 05 §2.2 提到的 `:118-130` React key 先例（`ThemePicker.tsx:120 key={cw.id}`）**成立但不构成真害**——React key 只在**同一配方内**去重，跨插件不同配方不会同框 ⇒ **不写进判据理由**，只作旁证。

**判据**：配色 id 唯一性面 = **跨插件**（异插件两配方声明同一配色 id ⇒ 🔴 红）；**同插件跨配方同名**（实测：`theme-zones` 的 `paper-zones` 与 `image-zones` **都**声明 `image` / `kraft`）⇒ 🟡 **黄 ＋ 登记**（§十八 边界 3）。

### 11.4 `.id` vs `.name` ⇒ 🔴 **两个字段、两个概念；显示名是「第二命名空间」且今天毫无保护**

**实测三条链**：

| 链 | 用哪个字段 | 出处 |
|:--|:--|:--|
| 元数据本 / 配方本（注册 + 查） | **`themes[].id`**（配方 id） | `ThemeRegistry.register/registerRecipe/get` |
| flat 本（注册 + 查） | 🔴 **`recipe.name`**（显示名！） | `contributions.ts:393` `registerTheme({ name: recipe.name, … })` |
| `app.theme` 的 enum | **配方 id ∪ flat 显示名** | `contributions.ts:601` `flatNames = getAvailableThemes().filter((n) => !recipeIds.includes(normalizeThemeValue(n) ?? n))` |

- **显示名 = UI 文案**（`RecipeMeta.name` ← theme JSON `name` ← plugin.json `label`；实测 10/10 一致）。
- 🔴 **后果（本格新发现，登记残余边界）**：显示名被**当作键**（flat 本）**且**被灌进 `app.theme` 的 enum ⇒ **两个插件用同名 label 会在 flat 本互相覆盖**，且**显示名能被存进配置**（legacy flat 桥接值）。
- **裁决**：
  1. 改名轮**只动 `.id`，绝不动 `.name`/`.label`**（动它就是可见变化，违 §〇c 上位约束）。
  2. 显示名 **不入账**（它不是 id ⇒ 入账会造假红，与 §11.3 同理）。
  3. 但**登记为残余边界**（§十八 边界 1）：显示名冲突今天**无判据、无保护、且能落盘**——留给 1.37（上下文旗子）之后的「名字面总账」或用户拍板，**本轴不夹带**。

## 十二、归属规则与改名形状

### 12.1 规则三条（交 1.36 的最终措辞）

1. **归属段 = id 的第一段 = pluginId**（1.31/1.33 已定的轴级口径；本件把外观族纳入同一口径）。
2. **新 id 形状 = `<pluginId>.<旧id>`**（见 §12.2）。
3. **宿主兜底 id 不带点、不改名**：`dark` / `light` / `dark-fallback` / `default` / `followTheme` —— 归属 = **宿主**；官方兜底仓（`theme-defaults`）对 `light`（配方 ＋ 配色）有**正当共持**（§十五.2）。

### 12.2 改名形状 = **点号 `<pluginId>.<旧id>`**（不是 `-`；00 §三 与 06 §〇 的 `-` 写法要**同笔订正**）

**理由（三条，逐条可验）**：

1. 🔴 **已发布的 SDK 判据算的就是这个**：`packages/plugin-sdk/src/eslint/checks/command-ownership.ts:137-138`
   ```ts
   const dot = id.indexOf(".");
   const suggested = `${pluginId}.${dot > 0 ? id.slice(dot + 1) : id}`;
   ```
   ⇒ **裸名（无点）的建议名 = `pluginId + "." + 旧名`**。外观族 id **绝大多数是裸名**（无点）⇒ 走的正是这一支。
2. **轴级一致性**：1.31（命令 id）/ 1.33（设置键）已把「第一段 = pluginId」定为轴口径；`00 §三` 与 `06 §〇` 的 `<pluginId>-` 是 **1.30 起草期的写法**，与已落地的 SDK 判据**不一致** ⇒ **必须订正**（否则 1.36 照 06 写成 `-`，SDK 腿会把它判成 `no-plugin-prefix`，**自己咬自己**）。
3. **形状可机械证明**：`explorer.newFile → file-tree.newFile`（只换第一段）；裸名支 = 加一段。**两种支路同一公式**，词干零变化 ⇒ 「功能语义不变」可逐字节证明。
4. ⚠️ **明确否决「顺手美化」**（如 `theme-mint-soda.mint-soda` → `theme-mint-soda.soda`）：那是 **25 次人工判断 = 25 个错机会**，且没有「词干零变化」这条机械证明 ⇒ 与 1.31 §10.2 的形状纪律相悖。

### 12.3 🔴 「零 UI 变化」的证据链（本格放行改名的**唯一依据**，逐条 `file:line`）

| # | 事实 | 出处 |

### 15.1 账拆四栏 ＋ 一条「持有者」表

**现行**：`"appearanceIds": ["dark","dark-fallback","light"]`（**一栏混两空间** ⇒ 造假红，§11.3）。

```jsonc

```

🔴 **`appearanceIdGrants` 不是白名单**（05 §四 禁「白名单/基线/棘轮」）：它**按 id 记证照**（每条 id 的正当持有者），不记「哪些仓被宽恕」——**新插件永远不在表里 ⇒ 永远判红**。这正是 1.34「归属从身份来」的同构。

### 15.2 🔴 头号发现：不拆栏 ＋ 不记持有者 ⇒ **官方 `theme-defaults` 当场假红**

**实况链**（逐条可验）：

1. 宿主保底：`registerFallbackThemes()`（`src/core/services/ui/ThemeEngine/registry.ts:120-125`）注册配方 `dark`（配色 `dark-fallback`）与配方 `light`（配色 `light`），`pluginId = undefined`。
2. 官方实现者：`theme-defaults` 声明 `themes[0].id = "light"`、`label = "Light"`、`path = "themes/defaults.json"`，其配色 = `light` ＋ **`dark`**。
3. ⇒ **`theme-defaults` 是宿主兜底 `light` 的官方实现者**（它顶替宿主 stub 是**设计意图**——`ThemeEngine/registry.ts:40-42` 注释明写「覆盖 fallback 主题（无 pluginId）不告警——插件主题上位是预期行为」）。
4. ⇒ 若账保持一栏 `["dark","dark-fallback","light"]`：`theme-defaults` 的**配色 id `dark`** 落在这栏里 ⇒ **官方仓判红**。
5. ⇒ **假红 ⇒ 真红失效**（宽容度模型 `plugin-repo-gate-model` §十）。这条假红**今天就能复现**（`audit:plugin-scope` 已经在对 `theme-defaults` 报「主题 id 不带归属 1: light」——**它连宿主保底 id 都判成「不带归属」**）。

**⇒ 两条判据修正（1.36 必须落）**：① 拆栏（§15.1）；② 保底 id 的**正当共持**入账（`appearanceIdGrants`）；③ 探针 `audit-plugin-scope` 对 `light` 那一行**必须换口径**（宿主保底 id ⇒ 不是「不带归属」）。

### 15.3 生成器缺陷（`scripts/gen-host-reserved.mjs`）

```js
/* ⑤ 宿主兜底外观 id —— 从 registerFallbackThemes 体内取 id: "..."（配方 id ＋ 配色变体 id） */
const at = src.indexOf("export function registerFallbackThemes");
const body = src.slice(at, at + 1200);                    // 🔴 盲切 1200 字符
for (const m of body.matchAll(/\bid:\s*"([^"]+)"/g)) appearance.add(m[1]);
```

| 缺陷 | 后果 | 1.36 处置 |
|:--|:--|:--|
| 🔴 **盲切 1200 字符** ＋ **一个正则抓所有 `id:`** | ①**配方 id 与配色 id 混成一栏**（§11.3）；②函数体一旦超 1200 字符 ⇒ **静默漏 id**（保护区漏一个就是漏一条）；③顺手抓到别的字段名叫 `id` 的也一样进账 | 改为**按注册调用分别抓**（`registerRecipe({ id: … })` → recipe 栏；`colorways: [{ id: … }]` → colorway 栏），并**加自检**：切出的片段必须含 `registerRecipe` 两次（否则报错，不许静默） |
| 漏 `default` / `followTheme` | 两条宿主外观 id 无保护（§9.3） | 显式补进账（不是靠扫描——它们**不在** `registerFallbackThemes` 体内） |
| `renderRuntimeModule()` **故意只发两族** | 外观保护区**运行时判不了**（§15.4） | 改为**外观四栏 ＋ grants 表进运行时**（体量 3＋2＋1＋1＋1 条） |

### 15.4 🔴 运行时副本的取舍（**外观族要账，但不需要「顺序」**）

- **一个天然优势（本件新发现）**：六个注册本**每条 entry 都带 `pluginId`**（`RegistryBase.track`），且 **宿主兜底条目的 `pluginId === undefined`** ⇒ **「是不是宿主」在运行时是可直接读的事实**，不必押注册顺序。
- **但「是不是保底 id」判不出来**：插件顶替宿主兜底那一支（`pluginId` 有值、前者无值）需要知道「这条 id 是宿主保底 id」⇒ 必须读账（`appearanceRecipeIds` 等四栏 ＋ grants）。
- ⇒ **裁决**：四栏 ＋ grants **进运行时副本**；`commandPrefixes` / `protocolIds` / `contextKeys` **仍不进**（它们的判据在 SDK 静态腿，运行时不需要）。
- **运行时机制 B（首撞保留 ＋ 出声）三条分支**（1.36 落地）：

| 情形 | 今天 | **裁决后** |
|:--|:--|:--|
| 两方**都有** pluginId 且**不同** | 后注册者**静默**覆盖 | 🔴 **先注册者保留 ＋ 拒后者 ＋ `console.error` 点名双方**（本轴第一处真行为改动；跨仓静态不可判 ⇒ 只能运行时） |
| 后者有 pluginId、**前者是宿主兜底**（`pluginId === undefined`） | 🔴 **静默上位**（明写预期） | **保留上位**（`theme-defaults` 靠它接替保底）**但**：登记者**不在** `appearanceIdGrants[id]` 内 ⇒ **拒 ＋ `console.error`**；在表内 ⇒ 静默上位（**唯一一处**） |
| 后者是宿主兜底（`pluginId === undefined`） | 不会发生 | 不变 |

🔴 **两条铁律不破**：① **不许把 `console.warn` 改成 `throw`**（00 §2.7 —— `throw` 会让整个插件装载失败）；② **不许碰 `commitTokens` / `theme:changed` / 池写入**（§十七）。
