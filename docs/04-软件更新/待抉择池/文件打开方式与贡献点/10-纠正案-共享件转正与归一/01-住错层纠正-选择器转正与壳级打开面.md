## 二、为什么必须转正（判据）

### 2.1 判据 A · 声明对等律（本纠正案新增，详文 [05](./05-防复发-机械准入原则.md) §二）

面板要渲染的东西**全部来自宿主声明**：
- 「哪些插件声明了 .pdf」→ `fileAssociation.listHandlersFor(ext)`（宿主面）
- 插件名/图标 → `pluginManager.list()`（宿主面）
- 「设为默认」写的是宿主覆盖表 `workbench.fileAssociations`（宿主面）

⇒ 它消费的是**宿主声明**，却住在**只装了文件树的用户才有**的地方。卸载 file-tree 后：
设置页那条入口整条消失（现在被当成 E39 的正常行为）、编辑器按钮失灵。
**宿主能力由第三方插件把持 = 住错层。**

### 2.2 用户拍板的依据（原话）

- 8.6.1：「禁止当前仅有文件树，未来第二个插件进场再归壳，这就是白做工……第二个相同插件的进场是必然的事情，必须在一开始就彻底规避这种状况」
- 6.3.3：「对于归壳，结论可以写」
- 3.3：编辑器**已经**是第二个入口（用户当时的判断「事实上已经有第二个消费者了」成立，但实现是**交叉调用**而非第二实现——口径见 §三）

### 2.3 D10 的口径校正（重要，⛔ 别搞混）

| 旧读法（被废止） | 新读法（本纠正案） |
|:--|:--|
| 「现在只有 file-tree 一个消费者 ⇒ 先住 file-tree，第二个出现再共享」 | ① **判据 A 先判层**：消费宿主声明 ⇒ 必须住壳/共享层，与消费者数量无关；② D10 仍然管**进池时点**：⛔ 不为**假想**消费者预造共享件（这条没错，继续守） |

⇒ 本次之所以「消费者数量够」只是**第二个理由**；**真正的理由是判据 A**。写进文档的目的就是：下一个 AI 不能再说「等第二个再共享」。

## 三、转正方案（落点一览）

```
新增（共享层，壳仓）
  src/components/shared/open-with-picker/OpenWithPicker.tsx      ← 纯 props in / events out（照 PluginCard 模式：零壳 core import、零数据知识）
  src/components/shared/open-with-picker/open-with-picker.css    ← 由 open-with.css 迁入（改名 + 前缀 ldk-openwith-）
  src/components/shared/open-with-picker/OpenWithPickerHost.tsx  ← 壳内宿主：订阅壳命令 → 装面板（挂 App 根，一次；照 #overlay-root 先例）
  src/components/shared/open-with-picker/types.ts                ← OpenWithRequest / OpenWithHandler / OpenWithChoice
  src/core/commands/infra/…（或既有常量模块）SHELL_COMMANDS.openWith = "workbench.action.openWith"
  壳命令实现：workbench.action.openWith  ← 组装数据（fileAssociation + pluginManager）→ 交给 Host

改动
  packages/linkdesk-ui/src/index.ts        ← 导出 OpenWithPicker（＋类型）
  scripts/build-pool-vendor.mjs            ← 收录新共享件（照 PluginCard 先例）
  contracts（生成源）                       ← 把 OpenWithRequest 形状纳入契约生成（[04](./04-契约API与文档连锁.md) §二）
  packages/plugin-sdk/src/index.ts         ← 导出 SHELL_COMMANDS ＋ openWith() helper（[04](./04-契约API与文档连锁.md) §三）

删除（插件侧，⛔ 无死代码）
  /e/linkdesk-plugins/official/file-tree/src/openWith/OpenWithPanel.tsx
  /e/linkdesk-plugins/official/file-tree/src/openWith/open-with.css
  /e/linkdesk-plugins/official/file-tree/…/openOpenWithPicker 的私有实现（保留薄转发或删除，见 T7）
```

**Props 契约（写什么）**——照 `PluginCard` 的「纯 props in / events out、零数据知识」：

```ts
// types.ts
export interface OpenWithRequest {
  /** 文件身份：有 path 走 path（右键/编辑器入口），只有类型时走 ext（设置页入口）。两者至少给一个。 */
  uri?: string;
  /** 显示用文件名（无 uri 时可省） */
  name?: string;
  /** **归一化后**的扩展名（无点、小写；由壳侧 normalizeExt 产出，⛔ 面板不自己解析 uri） */
  ext?: string;
  /** 可选锚点：右键入口传（就近弹出）；缺省 ⇒ 居中模态（[03](./03-面板口径-居中与遮罩.md) §二） */
  anchor?: { x: number; y: number };
}
export interface OpenWithHandler { pluginId: string; title: string; manifest?: ManifestIconShape; isDefault: boolean; isAuto: boolean; }
export interface OpenWithPickerProps {
  request: OpenWithRequest;
  handlers: OpenWithHandler[];         // 数据由调用方喂（壳命令组装）；面板**不查 registry**
  onOpenOnce(pluginId: string): void;  // 「打开（仅此一次）」
  onSetDefault(pluginId: string | null): void; // 「设为默认」/「恢复自动」（null = 恢复自动）
  onSearchMarket(): void;              // 空态那颗「在市场搜索阅读器」
  onClose(): void;
}
```

**为什么面板不自己取数据**（写给下一棒，别怀疑这条）：
① 与 `PluginCard` 同一条解耦口径（E6#54b：共享件不 import 壳 core、不查 registry）；
② 面板因此可被**设置页内嵌**（将来要嵌入时喂 props 即可，不用再搬一次）；
③ 数据组装放壳命令里，AI/CLI 直接 `exec` 同一条命令也能得到相同结果（归一化）。

## 四、调用面的契约自洽（P2 · 用户 3.x 的根因之一）

**现病**（`OpenWithPanel.tsx:138-144` 的注释「非右键入口居中」是画饼，实现没做；`navigation.ts:50-110` 的首参是「裸路径字符串 **或** `{uri, anchor}`」）——同一个参数两种形状、且**没有类型**。

**新契约（写什么）**：调用面**只有一个形状**，统一走 `OpenWithRequest`：

```ts
// 壳命令：workbench.action.openWith（唯一入口）
executeCommand("workbench.action.openWith", request: OpenWithRequest)
```

- ⛔ 废止「首参可以是裸字符串」的写法（file-tree 兼容期除外，见 T7；兼容期也要**立刻**转成 `OpenWithRequest` 再往下走）。
- ⛔ 面板不解析 uri、不 `extension()`——`ext` 由**壳侧**算好（`normalizeExt` 单一真相源）。
- 无锚点 ⇒ 居中；有锚点 ⇒ 就近（且 `top ≥ 30`，硬约束 18）。

## 六、实施顺序（⛔ 严格照此，防中间态）

```
① 壳：共享件 + 类型 + 壳命令 + Host + 门禁腿（先不动任何插件）
② file-tree：切消费 + 删私有件 + 留兼容转发
③ settings：改常量 + 菜单项载荷（与 02 同笔）
④ editor：补依赖 + 换 Button + 调壳命令
⑤ 发版：ui / contracts / plugin-sdk（npm 自主发）＋ file-tree / settings / editor（插件版自主发）
⑥ 实机 dev 验收：§七 清单逐条点
```

**为什么先壳后插件**：壳先上线 + 兼容转发就位 ⇒ 老插件（未更新）与新插件**都能用**，任何一步中断都不会产生「用户点不动」的窗口。
