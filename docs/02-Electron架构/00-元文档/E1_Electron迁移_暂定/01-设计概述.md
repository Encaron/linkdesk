# 01 — 设计概述

> 2026-07-24。此文档定义 **E1（Electron 迁移）** 的总体设计、决策记录和架构全景。
> **这不是"换框架"——这是在换地基。** LinkDesk 的壳、注册表、插件、原则——全部保留。只换承载它们的底层。
> **迁移完成后 → E2 底层加固与侧栏扩展 → E3 多 WebView 与壳收尾 → 架构完工。**

---

## 一、为什么这件事存在

### 1.1 Tauri 路径的上限

LinkDesk 目前跑在 Tauri v2 的单 WebView 里。Phase 5.5 完工。

原计划的 Phase 7 要在 Tauri 上实现多 WebView 进程隔离——每个插件独立系统 WebView。使用的 API 是 Tauri 的 `add_child`——一个标记为 `#[cfg(feature = "unstable")]` 的实验功能。（注：原 Phase 7 指 Tauri 时代的计划，现已存档。）

**问题不在"Tauri 不好"——在于"多 WebView 的管理是操作系统级的工作"。**

```
Tauri add_child 路径：
  每个插件 → 独立系统 WebView
  创建/销毁/IPC/资源调度/跨窗口拖拽/主题同步
  → 全部由你的 Rust 核心管理
  → 随着插件数量增长，Rust 核心膨胀为一个"窗口操作系统"
  → 这个核心必须知道每个窗口的类型、优先级、通信协议
  → 它变成了整个软件最知道"自己是干什么的"的地方
  → 违背了核心无知原则
```

### 1.2 Electron 路径为什么不同

```
Electron WebContentsView 路径：
  每个插件 → 独立 Chromium 渲染进程
  创建/销毁/IPC/资源调度/崩溃恢复
  → 全部由 Chromium 内核管理
  → 你的主进程只做路由——消息格式 { pluginId, type, payload }
  → 主进程不知道也不关心 payload 的内容
  → 核心无知原则在消息路由层继续生效
```

**关键差异不是"Electron 比 Tauri 好"——是"Chromium 已经替你写了多进程管理器"。**

Tauri 的 `add_child` 要求你从零建造 Chromium 十年打磨出来的东西。Electron 的 `WebContentsView` 直接给你。

### 1.3 决策时间点——已定稿

**迁移时间点：剩余 bug 全部修完 → E1 开始前。** 这是三个候选时间窗中沉没成本最低的。

| 时机 | Tauri 耦合度 | 迁移成本 | 是否可行 |
|------|------|:--:|:--:|
| **剩余 bug 修完、E1 前（✅ 选定）** | 751 行 Rust + 7 个 TS 文件 | **~2 天（AI）** | ✅ 最优——Rust 投资最小，无 add_child 代码 |
| 旧 Phase 6d 后 | +400 行 Rust 插件化代码 | ~3 天 | ❌ 旧 6d 白写 400 行再删 |
| 旧 Phase 7 后 | +500 行 add_child 代码 + 300 行 IPC | ~2 周 | ❌ 不可能——已经写了 add_child 再切框架 |

**延迟一天，Tauri 耦合只增不减。** 每多写一个 `invoke()` 调用、每多加一个 Rust 命令——迁移时就多改一处。延迟不会让迁移更简单——只会让差异面变大。

## 二、三个核心架构决策

### 决策 1：框架 → Electron

| 对比维度 | Tauri | Electron |
|------|------|------|
| 多 WebView API | `add_child`（unstable） | `WebContentsView`（stable，Electron 30+） |
| 进程管理器 | 你自己写（Rust） | Chromium（10 年验证） |
| 后端语言 | Rust | Node.js |
| 安装包 | ~5MB | ~120MB |
| 内存基线 | ~50MB | ~150MB |
| AI 训练数据密度 | 低（Tauri 多 WebView <10 个公开项目） | 极高（Electron 数十万公开仓库） |

**选 Electron 的理由：** 多进程管理是标配，Chromium 替你扛。安装包和内存的代价是平台级软件的入场券——VS Code/Discord/Slack 都付了。

### 决策 2：插件隔离 → 独立 WebContentsView per 插件

| 对比维度 | 共享 ExtHost（VS Code 模型） | 独立 WebContentsView（本方案） |
|------|------|------|
| 插件 A 崩了 | ExtHost 重启 → 所有插件重载 | 只崩自己 |
| 插件 A 死循环 | ExtHost 卡死 → 所有插件全停 | 只卡自己 |
| 恶意插件读其他插件数据 | **能读到**（同进程） | **读不到**（独立进程） |
| 内存占用 | 进程级 WebviewView ≈ WebContentsView——**但方案 B 多一个 ExtHost 进程（+50MB），反而更贵。** iframe 级省内存但牺牲隔离。 | 每个 view 插件独立 Chromium 进程。未打开的插件不创建进程。 |
| VS Code 为什么选它 | 2015 年硬件内存小、几百个扩展各开进程不现实 | — |
| 我们为什么选 | — | 没有历史包袱。**进程级 WebviewView 的方案 B 在所有内存场景下都不如本方案。** 详见 `02-插件隔离模型与开销分析.md` 第二部分。

**详见：** `02-插件隔离模型.md`

### 决策 3：插件入口 → React 组件

**选 React 组件的理由：**

1. **AI 友好度是第一优先级。** 项目 95% 代码是 AI 写的。React 组件是 GitHub 上最密集的训练数据——AI 生成的 React 代码质量远高于任何专有 API 模式
2. **Web 平台能力无限制。** `import THREE.js`、`import Leaflet`、Canvas、WebGL、WebAssembly——插件在自己的 WebContentsView 里直接可用，不经任何中间层
3. **一个文件 = 一个插件。** AI 写一个 React 组件，丢进 `plugins/` 文件夹，装上去就能用

**系统级能力（串口、文件、子进程）通过 preload 的 `window.linkdesk` 暴露——这是安全边界，不是能力限制。**

**选定 React 组件不是"因为现在写的 React"——按照原则"若仅因为当前这样写了才这样做那最好不要"。** React 组件被选中是因为 AI 友好度和 Web 平台自由度在对比中胜出，不是因为已有代码省事。

**详见：** `03-插件入口方案.md`

## 三、架构全景

```
┌────────────────────────────────────────────────────────────────┐
│  Electron Main Process (Node.js)                               │
│                                                                 │
│  Core Services:                                                 │
│    SerialService (serialport)    FileService (fs)              │
│    ConfigService (JSON r/w)     PluginFileService (dir ops)    │
│    WindowManager (WebContentsView lifecycle)                    │
│    IpcRouter (message relay: {pluginId, type, payload})        │
│    ProtocolHandler (linkdesk:// → file path resolution)        │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Shell Window (BrowserWindow, Chromium Renderer)           │  │
│  │   Workbench UI: IconBar / SidePanel / TabBar / SplitPane  │  │
│  │   preload → window.linkdesk (壳侧 API)                    │  │
│  │   Phase 1-5 代码 100% 保留                                │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Plugin WebContentsView 1 (独立 Chromium 渲染进程)         │  │
│  │   preload → window.linkdesk (插件侧 API，比壳窄)          │  │
│  │   linkdesk://terminal/dist/bundle.js                      │  │
│  │   React 组件: TerminalView                                │  │
│  │   崩了 → 只崩自己                                         │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Plugin WebContentsView 2 (地图 + Leaflet)                  │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Plugin WebContentsView N (...)                             │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 通信模型

```
插件 React 组件
  │
  ├── (A) 系统能力  →  window.linkdesk.serial.*  →  IPC  →  Main Process
  │    串口、文件、配置读写
  │
  ├── (B) Web 能力  →  直接使用，不经任何中间层
  │    import THREE.js / Leaflet / Canvas / WebGL / WebAssembly
  │
  └── (C) 壳服务    →  window.linkdesk.commands.register(...)  →  IPC  →  Shell
       命令、菜单、快捷键、配置项注册
```

**核心无知原则在消息层生效：** 主进程只看 `{ pluginId, type }` 做路由，不读 payload。主进程不知道串口数据的含义、不知道配置项的内容、不知道插件在做什么。

## 四、什么变、什么不变

| 层 | 变化 |
|------|------|
| **壳 UI** | **不变。** 图标栏/侧栏/标签栏/分屏/状态栏/命令面板——全部 React 组件原样保留 |
| **核心服务** | **不变。** CommandRegistry / ConfigurationRegistry / MenuRegistry / ProtocolRegistry / ThemeEngine……全部 TypeScript 逻辑原样保留 |
| **插件** | **不变。** 4 个现有插件的 React 组件代码一行不动 |
| **底层 I/O** | **变。** Rust serialport-rs → Node.js serialport npm；Tauri fs → Node.js fs；Tauri invoke → `window.linkdesk.*` |
| **插件加载** | **变。** `plugin://` 协议 → `linkdesk://` 协议；同 WebView mount → 独立 WebContentsView |
| **后端语言** | **变。** Rust（751 行）→ Node.js（~500 行） |

**改动量：** ~80 个文件保留，7 个文件 ~50 处修改，~15 个文件新建，1 个目录删除（释放 3.9GB）。

详见：`04-迁移方案.md`

## 五、原则更新

### 原则 5（CLAUDE.md 硬约束 #5）

**旧版：** "Tauri `listen()` 必须用 generation counter 模式"

**新版：** "`ipcRenderer.on()` 必须用 generation counter 模式——底层变了，模式不变"

### 原则 6（软件介绍 §二.6）

**旧版：** "插件没有 API 白名单。给你自由，也给你安全。"

**新版：**

> **插件 Web 平台能力无限制，系统级能力走 `window.linkdesk.*` API。**
>
> 插件在自己的 WebContentsView 里能 `import` 任何 JS 库、调用任何 Web API——Canvas、WebGL、WebAssembly、WebRTC、Web Audio……Web 平台的一切，不加限制。
>
> 系统级能力（串口、文件系统、子进程）通过 preload 的 `window.linkdesk` 暴露——插件不能直接 `require('child_process')` 或 `require('fs')`。这是安全防线，也是插件市场的前提。
>
> **没有系统级白名单 = 没有插件市场。** VS Code 用 `vscode.*` API 证明了：开发者愿意用精心设计的 API 换取安全分发的信任。
