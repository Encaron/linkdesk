## 三、要做

### 1. 复量 ＋ 补齐 ⑪ 那批未查的
至少补：`contributes.keybindings[].key`（chord 冲突：E5.8 做过"Keybinding conflict 红"的 UI —— 是**只提示**还是也拦？）· `contributes.views[].id` · 菜单/工具栏/状态栏插槽 id · `window.linkdesk.*` 有没有 storage 面及其键空间 · `when` 子句引用的 context key 全集（与 ④ 联动）。

### 2. 逐条给「严重度排序」——按**受害方能不能察觉**排
> **这是本格的核心判据**：CSS 那一类之所以难查，就是**受害者看不见**。本格按同一把尺子排：
> - 🔴 **最高**：受害方**收不到任何信号**（④ 上下文键 · ① 命令 id · ③ 主题 id）⇒ 同类里最坏的
> - 🟠 中：有 `console.warn`，但 warn 只在**覆盖发生的那台机器**上打印 ⇒ 用户看不见、被覆盖的作者看不见
> - 🟡 低：有 UI 提示或用户可感知

### 3. 逐条裁「该怎么修」——**不许一律"改抛错"**

🔴 **已记录的顾虑（必须读）**：`ConfigurationRegistry` 注释自述「**parseContributions 没有 try/catch，抛错会导致整个插件加载失败**」⇒ **"冲突即拒绝加载"可能太狠**（一个第三方插件的重名会让**整只插件废掉**，用户侧表现为"装不上"）。
⇒ 候选修法（本格逐条选，照[宽容度模型](22-收口总方案-跨方样式污染九件套.md)）：
- **(a) 归属前缀**（`<pluginId>.` / `<pluginId>-`）—— 与 CSS 同款，**结构性、零表**；适用于 ①②③；
- **(b) 首撞者保留 ＋ 后来者降级（不覆盖）＋ 明确提示** —— 比抛错温和、比 warn 有效；
- **(c) 只黄灯 ＋ 文档**（适用于 ⑤ i18n 这类**跨仓不可判**的）；
- **(d) 宿主键保护区**（插件不得占用 `app.*` / 宿主 context key 等）—— ② ④ 需要它。

### 4. 判「要不要立落地轮」
若普查出的 🔴 项 ≥1 条可机械判且是真害 ⇒ **建议立 1.31（落地）** 并把任务书写齐（照 22 档 §四 纪律：**评估轮的下一格任务书由评估轮写齐**）。

### 5. 与件 8（门禁健康度）的交界
⚠️ 本格的修法若产出新门禁 ⇒ **必须一开始就带 `--self-test` 并接线**（件 8 的纪律）；且**不要与 1.27/1.28 的体检表重复登记**（那一格管的是"已有门禁活不活"，本格管的是"还缺哪些门禁"）。
