# 多仓开发与本地工作区

> 2026-09-14 · E6#97b（E6 第 7 层判据先立）。**回答三问：我的插件工程该放哪？仓库该叫什么？怎么改显示名？**
> 每条都带「为什么」——这份文档的读者包含未来的 AI，只写「怎么做」它会在下一个会话里按自己的理解改掉。命名规则（id/版本/分发件名的字符集与可变性）的权威条文 → [16-命名规范](16-命名规范.md)，本篇不复制。

---

## 一、本地目录约定——工程收进容器，按归属分

**推荐布局**：所有插件工程收进**一个容器目录**（建议 `E:\linkdesk-plugins\`），内部按**归属**分两夹：

```
E:\linkdesk-plugins\
├─ official\          ← 你自己的插件（官方 18 只 + 后续新插件）
│   ├─ file-tree\
│   └─ settings\
└─ third-party\       ← 别人的插件（clone 下来学习/二开的）
```

**为什么按归属不按功能**：归属稳定（一只插件不会从官方变第三方），功能分类会随插件增加不断重划；且市场 catalog 里的 `category` 已经在做功能分类，本地再分一遍是重复劳动。

**为什么收进容器**：不收就会平铺散落（`E:\linkdesk-build+scratch\` 里现在就躺着两只），找不到、备份漏、AI 进场也不知道去哪找。

---

## 二、🔴 容器目录本身绝不建仓

`E:\linkdesk-plugins\` **永远不要 `git init`**。这不是洁癖——一旦容器被建成仓库，三件坏事自动发生：

1. **每只插件的 `.git` 变成嵌套仓**，父仓把它们记成 gitlink——**静默坏掉且极难看出来**（clone 容器的人拿到的是空目录）。
2. **脚手架的规则被反转成灾难**：`create-linkdesk-plugin` 检测「已在 git 仓内 → 不再 init」，容器一旦是仓，**每只新插件都不建自己的仓**，全部变成容器的子目录——恰好造出你想避开的 monorepo。
3. 触发方式防不胜防：IDE 的「初始化仓库」提示、在错层级敲 `git init`、从父目录 `git add .` 都可能中招。

**护栏**：容器里放一张说明（`README.md` 或 `不要在这里建仓.txt`）——防的不只是作者本人，还有以后进场读目录的 AI。

---

## 三、仓库名完全自由（D5/N2）

**仓库名不强制任何前缀，第三方零约束。** 这是拍过板的：作者给自己的插件（仓库）取名是正当权利，不能定死。

- **建议但非强制的惯例**：官方插件仓统一 `linkdesk-plugin-<id>`（N3 待用户拍板，拍板后条文住 [插件源码外移层/09-命名规范.md §五](../02-Electron架构/E6_插件生态与发布/插件源码外移层/09-命名规范.md)——只此一处维护）；第三方随意。
- **改仓库名的代价**：已发布 catalog 条目里的 `downloadUrl` / `readmeUrl` 内嵌 `owner/repo`，**改名会断已发布插件的下载与 README 链接**（源码本身不受影响）。改名后重发一版新条目即可自愈，但旧版本条目仍指旧链——**能不改就不改，要改趁早**。

---

## 四、身份 vs 显示名 vs 仓库名（D5）

三个「名字」互不相干，混为一谈是一切命名问题的根源：

| | 是什么 | 能不能改 |
|:--|:--|:--|
| **插件身份**（`plugin.json` 的 id） | 安装目录名、卸载墓碑、更新对账的**唯一键** | 🔴 **发布后永不可变** |
| **显示名**（`plugin.json` 的 `name`） | 界面、市场卡片上给人看的 | ✅ **随便改**（改完 bump 重发一版） |
| **仓库名** | GitHub 上的工程仓 | ✅ 自由（代价见上节） |

对标 VS Code 的实测口径（`ms-vscode.cpptools`：身份 = `publisher.name` 永不可变，`displayName` = 随便改，仓库名与身份无关）→ 完整实测与论证 → [插件源码外移层/09-命名规范.md](../02-Electron架构/E6_插件生态与发布/插件源码外移层/09-命名规范.md)；作者面规则条文 → [16-命名规范](16-命名规范.md)。

## 五、本地目录位置与插件身份无关（本篇最重要的一条）

**插件工程 clone 到哪、目录叫什么，都不影响插件身份**——插件仓是自足的，壳只认 Release URL 与 catalog，**不认本地路径**。⇒ 本地目录结构随时可重排，零风险。

活证据：`hello-linkdesk` 与 `first-run-setup` 两只插件的源码仓平铺在容器外，照样构建、发布、上架、被安装版正常装卸。等 L7 第 7.2 轮跑完，官方 18 只也全是这样。

⚠️ **一条现状红线**（2026-09-14 时点）：插件身份今天还靠**目录名兜底**（`pluginId` 显式化的落地在 7.1 轮 #98g）——**在那一格落地之前，不许改任何插件的本地目录名**，否则构建出的 zip 会把新目录名当插件 id，五条后果全不报错。详见 [16-命名规范](16-命名规范.md) 与 [插件源码外移层/09-命名规范.md §六](../02-Electron架构/E6_插件生态与发布/插件源码外移层/09-命名规范.md)。

## 六、发布链路上的四个名字不许手改

它们参与安装裁决与更新对账，**手改即身份漂移或更新链断**：

| 名字 | 为什么不许手改 |
|:--|:--|
| `<id>.linkdesk-plugin`（分发件名） | zip 安装裁决按基名反查插件 id |
| `v<version>`（Release tag） | 更新检查按 tag 找版本 |
| 版本号格式 `^\d+\.\d+\.\d+$` | schema 直接拒预发布后缀等异形 |
| 插件 id | 身份永不可变（§四） |
