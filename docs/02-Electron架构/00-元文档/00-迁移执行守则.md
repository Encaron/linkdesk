## 一、每步通用检查（E1/E2/E3 全步适用）

执行任何步后 commit 前：

```bash
# 1. 类型检查
npx tsc --noEmit
# → 零错误，零警告
# 为什么：B73 教训——重构变量名漏改两处→ReferenceError。tsc 能抓到这类错误，但抓不到逻辑遗漏

# 2. 单元测试
npx vitest run
# → 全过
# 为什么：B22/B33 教训——改了分屏逻辑但测试没过=引入了回归。vitest 是安全网

# 3. 变更范围
git diff --stat
# → 确认只动了该动的文件——没有"顺手"改无关文件
# 为什么：B66/B67 教训——"顺手"改了两个不相关的服务→两个服务往同一个文件写互相覆盖
#         如果 diff 显示改了不相关的文件→停下来检查是否真的需要

# 4. 零新硬编码
git diff --staged | grep -E 'pluginId === "[a-z]|case "[a-z].*":|BOTTOM_ICONS|PLUGIN_ICON_PATH'
# → 返回空（无新增插件 ID 硬编码）
# 为什么：Phase 5g 花了 50+ commits 把 8 个硬编码 TabType 改成动态 string。
#         每次写死一个 pluginId→未来每加一个插件就要改壳代码。对照硬约束 #10

# 5. UI 组件归一化——不重复造轮子
# 新增按钮/颜色选择器/对话框/下拉框/确认弹窗等 UI 控件前 → grep 是否已有相同组件
# 为什么：V2 教训——调色盘在设置页和按键布局里各有一个，颜色不同/规格不同/主题不跟。
#         B66/B67 同根——两份代码 = 两套维护 = 两处可能不同步。
#         按钮归一化同理——不同页面的"确认"/"取消"按钮样式/颜色/大小必须一致。
grep -rn "<input type=\"color\"|<ColorPicker|<button" src/components/ --include="*.tsx" | grep -v "node_modules"
# → 如果同一个概念出现在多个文件 → 提取到 src/components/shared/
#         例如：全局只有一个 <ColorPicker> 组件。设置页用它，主题编辑器用它，插件也用它。

# 6. 一条 commit 只修一个概念
# → 如果 diff 涉及两个不相关的改动 → 拆为两个 commit
# 为什么："慢工出细活"——一条 commit 做多件事=回退时无法单独回退=bug 难以定位
```

## 二、E1 逐步检查

### 步 1：Electron 壳初始化

- [ ] **验证范围正确**：此步只验证壳框架渲染——串口和插件管理不可用。确认 `invoke()` 调用抛异常有 try/catch 兜底
  - 为什么：`loader.ts:170` 的 try/catch 兜底→`invoke("list_plugin_dirs")` 抛异常→回退到 glob 全量加载。壳不崩，但串口/插件管理的 API 不存在
- [ ] **preload 确认**：`electron/main.ts` 有 `ipcMain.on('preload-ready', ...)`——preload 加载成功后通知 main
  - 为什么：新风险 3——preload 抛异常不进 ErrorBoundary。`window.linkdesk` undefined→所有调用白屏。必须有双向确认机制
- [ ] **单实例锁**：启动两个 Electron → 第二个不弹新窗口
- [ ] **main.ts 持有 BrowserWindow 引用**：后续 SerialService 需要 `mainWindow.webContents.send()`
  - 为什么：SerialService 需要推送串口数据到 renderer 进程。如果 mainWindow 引用丢了→串口数据到了 main process 但 renderer 收不到

**👤 Encaron 验什么：** `npm run electron:dev` → 窗口出现 LinkDesk UI → 图标栏/侧栏/标签栏正常渲染。串口按钮点不了是正常的（还没接后端）。关掉窗口 → 进程退出 → 没有残留。

### 步 2：串口服务

- [ ] **读 `src-tauri/src/serial.rs` 后再写**：逐函数映射——行缓冲/`\n` 拆行/读错误休眠/DTR-RTS 控制
  - 为什么：Rust serial.rs 是经过 48 个 bug 验证过的正确逻辑。不读就写=把已修过的 bug 重新发明一遍
- [ ] **H1 回归**：MCU 断电 → 软件不卡死
  - 为什么：H1 根因是 Rust `read_loop` 死循环抢锁+`close_port` flush 在锁内。Node.js serialport 事件驱动没有阻塞锁——理论上不会再现。但必须实测验证
- [ ] **B61 回归**：GBK/Shift-JIS 编码数据不乱码
  - 为什么：B61 根因是 Rust 硬编码 `String::from_utf8_lossy()`。Node.js `iconv-lite` 原生支持 GBK/Shift-JIS——不会再现。但必须实测验证
- [ ] **数据推送策略**：行缓冲 + 16ms 批量推送——`10-迁移方案缺口补丁.md` §6.5
  - 为什么：如果串口以 115200bps 连续输出二进制数据（不分行），逐包 IPC = 每秒数千次 IPC 调用→性能问题。16ms 批量=一帧一次

**👤 Encaron 验什么：** 打开串口助手对照——LinkDesk 枚举的 COM 口列表和串口助手一致。连接你的 STM32 板子 → 收发数据 → 内容和串口助手完全一样。拔掉 MCU 电源 → LinkDesk 不卡死。换 GBK 编码 → 中文不乱码。

### 步 3：文件/配置/插件管理

- [ ] **plugin-handlers 完整覆盖 6 个 invoke**：`listDirs` + `install` + `uninstall` + `reinstall` + **`readManifest` + `resolvePath`**
  - 为什么：后两个容易遗漏——`loader.ts:386,415` 的 `loadPluginRuntime()` 依赖它们加载外部插件。漏了=外部插件静默加载失败→没有任何错误提示→"为什么插件装不上？"
- [ ] **卸载走 `fs.cp` + `fs.rm`**：不用 `fs.rename`
  - 为什么：卸载 9 轮反复的根因——Windows 下 Vite 持有插件文件锁→`fs::rename` 跨目录失败→卸载静默不生效。`cp+rm` 是已验证的正确方案
- [ ] **事件触发在文件操作之后**：消费者需要读到文件移动后的新状态
  - 为什么：卸载 9 轮的另一半根因——事件先触发（消费者查状态时文件还在）→消费者认为"卸载失败"→UI 不一致

**👤 Encaron 验什么：** 安装一个外部插件（从磁盘选 .zip）→ 图标栏出现 → 卸载 → 图标栏消失。重装 → 正常加载。安装时选一个不存在的路径 → toast 提示错误（不崩）。

  ```bash
  grep -rn "localStorage" src/ | grep -v "StorageService" | grep -v "node_modules"
  # → 只允许 StorageService 内使用 localStorage
  ```
- [ ] **`||` vs `??` 审计（#19b）——逐条判断不能机械化**：
  ```bash
  # 为什么：H2 根因——空串 "" 是合法 session ID 但被 `||` 吞掉。
  # G22 根因——parseInt("0")||1000 → 0变成1000。`0` 是合法数值（已发 0 字节）。
  # Electron IPC 比 Tauri invoke 返回的 falsy 可能性更多——`ipcRenderer.invoke()` 可能返回 ""/0/false/null/undefined。
  grep -rn "||" src/ --include="*.ts" --include="*.tsx" | grep -v "|| {" | grep -v "||\s*$"
  # 逐条判断规则：
  #   ID/名称 fallback（空串是非法ID）→ `||` ✅
  #   数值默认（含0）→ `isNaN(n) ? default : n`   （G22 教训——0 是合法值）
  #   对象/可选字段 → `??`                       （语义精确，不吞 falsy）
  #   IPC 返回值 → 默认用 `??`                   （""/0/false 可能是合法值）
  ```
- [ ] **G14 幽灵页（#19a）**：PluginDetailView 订阅 `onDidUnregister`
  - 为什么：G14 场景——打开插件 A 详情页→切换到插件市场→卸载 A→切回详情页→仍显示"已安装"。根因是详情页不监听卸载事件。`onDidUnregister` Emitter 在 `viewRegistry.ts:24` 已有——只是没人订阅
- [ ] **恢复后计数器同步（G3 预防）**：每次从持久化恢复数据后，扫描所有已用 ID，将对应计数器设为 `max + 1`
  - 为什么：G3 根因——F5 刷新后模块级计数器归零（`_terminalCounter=0`）但恢复的数据保留了旧 ID→新创建的 session 和旧 ID 碰撞→侧栏/标签栏混乱。`syncCountersAfterRestore()` 已修好——E2c 不改这个逻辑但要确认没被迁移破坏

**👤 Encaron 验什么：** 
1. FileService：改设置→F5→设置不变。改布局→F5→布局不变。存快捷发送→F5→仍在。
2. `||` 审计后：打开串口→状态栏 TX/RX 显示 0（不是空白）。session ID 包含空串时不丢数据。
3. G14：打开插件详情→卸载该插件→详情页即时显示"已卸载"。
4. G3：F5 刷新→新创建的 session 不和旧 session ID 碰撞。

## 四、E3 逐任务检查

### E3a：多 WebView 进程隔离（#24-#32）🔥 最高风险——仅次于 E1 步 4

**为什么这是最高风险：** 终端是 Tauri 时代最复杂的插件——串口/session/多标签页/侧栏联动。C1-E5 全部教训要重新验证。多 WebView 后同步链路更长（侧栏在壳 WebView→标签栏在壳 WebView→标签内容在插件 WebView）。

- [ ] **WebContentsView `crashed` 处理（新风险 2 + 模式 2 预防）**：
  - 为什么：插件 WebView 崩溃时壳必须检测到并触发清理链。否则注册表残留（命令/菜单/快捷键/配置项仍存在但对应的 WebView 已死）→"点按钮没反应"
  - 检查：`view.webContents.on('crashed', ...)` → 触发 `PluginLifecycle.onWillUninstall` → 壳侧清理所有注册表
- [ ] **新 WebView 主动拉取当前状态（新风险 4）**：
  - 为什么：`theme:changed`/`lang:changed` 是 push 广播。新创建的 WebView 在下次广播前用的是什么主题/语言？默认值。如果用户不切换主题→新 View 永远收不到广播→永远用默认值→"黑白混合"
  - 检查：`did-finish-load` → 壳主动推送当前主题 var、当前语言 resources→插件 View 注入后再显示
- [ ] **IPC 回调 stale closure 审计（模式 4 预防）**：
  ```bash
  # 为什么：B86 根因——闭包捕获了 mount 时的 portName=""。IPC 多一层异步→风险更高。
  # G7 根因——onKeyDown handler 闭包捕获 mount 时的 sendValue=""。每个异步回调都是潜在的 stale value trap。
  grep -rn "ipcRenderer.on\|ipc.onEvent" plugins/ --include="*.ts" --include="*.tsx"
  # 每个回调 → 检查回调内是否引用了 React state（useState/useRef 以外的变量）
  #   → 引用了 React state → 必须用 ref 桥接（portNameRef.current）
  #   → 只引用了 ref → ✅
  ```
- [ ] **IPC 超时（新风险 1）**：每个 `ipcRenderer.invoke()` 加 5s 超时
  - 为什么：主进程忙→invoke 排队。WebContentsView 销毁→Promise 永远不 resolve。不加超时=调用方永远挂起→"点了按钮没反应也不报错"
- [ ] **C1 回归**：两个终端标签页独立 WebContentsView → 侧栏点 A → 主区显示 A 不是 B
  - 为什么：C1 根因在 E2b 已修（消灭模块级状态），但 E3a 后标签内容在不同 WebView——session 数据和 IPC 通道仍需正确隔离
- [ ] **B86 回归**：首次打开串口按钮正常工作
  - 为什么：B86 根因在 Phase 5.5 已修（ref 桥接），但 IPC 多一层异步→同事件循环 race 可能以新面目重现
- [ ] **SidebarTabSync 归一化**（E3a 新增任务 ~30 行）：侧栏↔标签页三向同步走单一函数
  - 为什么：模式 3——18 个 bug 的根因是侧栏/标签栏/主区各自维护状态同步逻辑。`activateSidebarItem(sourceId)` 是单一真相源
- [ ] **插件 preload 包含 `filesystem`**（受限——只能读写 `.linkdesk/plugins/<id>/`）
  - 为什么：文件树插件需要读目录、Monaco 需要读文件。不给 filesystem→这两个插件做不了。给完整 fs→安全漏洞。中间地带：scoped filesystem
- [ ] **插件 WebView 崩溃 → 壳侧清理链执行 → 注册表无残留**
  - 验证方法：插件 console 执行 `process.crash()`→壳检测到 crashed→清理注册表→图标栏该插件图标消失

**👤 Encaron 验什么：** 
1. 打开两个终端标签页→在 Task Manager 看到各自独立的 Chromium 进程
2. 打开终端→侧栏点会话 A→主区切换到 A。点会话 B→主区切换到 B（C1 不回归）
3. 终端插件 console 执行 `throw new Error("崩")`→只有终端标签页崩→设置/插件市场正常→点 [重试]→终端恢复

5. 卸载终端→Task Manager 中终端进程消失→内存回收到卸载前水平
6. 新建插件 WebView→主题颜色和壳一致→切主题→插件 View 颜色跟着变

  - 为什么：`phase6` 分支是退路。删了退路=遇到不可逾越的问题时回不去

### E2 红线（只加固不扩展）

  - 为什么：对标 VS Code——VS Code 发布后框架层几乎不动。所有新能力通过 extension API 暴露。LinkDesk 同理
- ❌ 插件 preload 比壳 preload 宽——`plugins.*`/`window.*`/`dialog.*` 绝不在插件侧暴露
  - 为什么：插件能装其他插件→恶意插件可以卸载你的出厂插件。插件能创建 WebView→恶意插件可以无限弹窗
