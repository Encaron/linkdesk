### 3. 三条纪律

1. 🔴 **缓存状态是必填字段**——「🆕全新首装」与「♻️有旧数据」**必须分开记**。有一类缺陷会长期藏在旧缓存／旧注册表后面，只在**真·首次安装**时才现形；两条混在一起记，就会把「安装器的错」和「本体的潜伏旧 bug」判反。

### ⇒ 判归因的第一条分流（本基线的全部意义）

这台机器上看到的任何异常，只有三种来历：

- **(a) 安装器**——引导器（`build/installer/bootstrapper/`）的安装/卸载/更新链；

🔴 **两侧都要防**：别默认算在安装器头上；也别因为"以前没这毛病"就判本体无罪——**"以前没这毛病"恰恰可能是缓存掩盖的症状**，而不是本体的免罪牌。

### B-1 安装目录自动补一层 `\linkdesk`（2026-10-02 用户拍板 · ✅ **已实施**，随 **0.2.35** 落地；回填见本格末）

**用户拍板原话**（2026-10-02）：

> 「关于这个，我更想要 B 方案」/「**B：改成多数软件的口径 —— 选中夹子后自动追加 `\linkdesk`（选 `D:\` 就得到 `D:\linkdesk`）。再也不会混装**，代价是输入框路径 ≠ 实际落点（完成屏要改成显示真实落点），且「盘根」那条拦截可以放宽。」

**缘起**（为什么会提这件事）：当前口径是「**选中的文件夹就是安装目录本身**」（平铺进去），而卸载走 `WipeTree` 整棵树递归删（`main.cpp:1428`，唯一闸门是"目录里有 `LinkDesk.exe`"）。于是「装进一个非空的共用文件夹」有个真隐患：卸载会把那个共用文件夹**整个清空**。对照用户见过的其它软件，多数是"自己建一层子夹"——B 就是改成那个口径。

#### 口径（要落成的行为）

用户**自己选/自己敲**的目录，其最后一段若不是 `linkdesk`（大小写不敏感），就补一层：

| 用户给 | 实际落点 |
|:--|:--|
| `D:\`（或 `D:`） | `D:\linkdesk` |
| `D:\Apps` | `D:\Apps\linkdesk` |
| `D:\Apps\`（尾斜杠） | `D:\Apps\linkdesk` |
| `D:\Apps\linkdesk` / `…\LinkDesk` | **原样不动**（幂等） |
| `\\server\share` | `\\server\share\linkdesk` |
| 默认值 `%LocalAppData%\Programs\linkdesk` | 原样（本来就合规） |

#### 三条硬规矩（写进代码注释与 README，改动时不许省）

1. 🔴 **只规整「用户亲手给的」**——浏览对话框选完、手输后失焦、点安装时各规整一次。**从别处来的目录一律不碰**：ARP 反推出的旧目录（覆盖装**必须落回同一处**，改了就是"另装一份"）、宿主 `?dir=` 注入的默认值、`--silent` 走的 `DefaultInstallDir()`。**这条是防止把升级链写坏的闸。**
2. 🔴 **输入框显示的永远是最终落点**——规整发生在 `setInstallDir` / `beginInstall` 之前，所以"输入框 = 完成屏 `#finish-path` = 7zr 实际 `-o` 目标"三者仍然同源（这是现架构已有的性质，不许破）。
3. 🔴 **盘根不再报错，但宿主的拦截留着**——页侧 `pathSyntaxError` 撤掉 `root` 那一支（B 之后它不可达）；`main.cpp:951-957` 的 `root` 判**保留**，因为它现在只剩一条可达路径：`--dir=D:\` 这种**精确指定**（自动化开关，不补层）。那种情况下必须拦——注释里已写明「盘根：7zr 会把整盘当目标铺开」。

### #1 装/卸过程把 `HKCU\Environment\Path` 的值类型从 `REG_EXPAND_SZ` 降级成 `REG_SZ`

- **报告人 / 时间**：ZCode（2026-10-02 全机清理时发现）· 清理期发现，**非用户当面复现**
- **现象**：清理前读 `HKCU\Environment\Path`，其值类型是 `REG_SZ`；而它本应是 `REG_EXPAND_SZ`（里面含 `%USERPROFILE%` 之类变量，类型一变，变量在装卸之后就不再展开了——依赖 PATH 变量的程序会找不到路径）。清理时已按备份手工改回 `REG_EXPAND_SZ`。
- **复现步骤**：装一次 → 卸一次 → `reg query HKCU\Environment /v Path` 看类型。
- **环境**：安装版（清理前那版）· 装在哪已不可考 · 缓存状态 ♻️有旧数据
- **归因**：**安装器**（据实机残留推出；`reg add` 不带 `/t` 会写成 `REG_SZ`）。⚠️ **一处已确证、一处未确证**：写入侧**已有**门禁——`syswrite-test.ps1` 路 3b 断言「`REG_EXPAND_SZ` 进必 `REG_EXPAND_SZ` 出」，而它绿；所以嫌疑集中在**卸载侧的 PATH 还原**（`customUnInstall` 那一段）是否没保类型，**此点未经实机复现验证**。
- **处置**：✅ **已修**（2026-10-02，随 0.2.35）。实施回填：`syswrite.cpp` 新增 `PathValueType()`——**值里有 `%` ⇒ 一律 `REG_EXPAND_SZ`**；**没有 `%` ⇒ 保留原类型、`REG_EXPAND_SZ` 不降级**（`:201-219`），写入侧与**卸载侧的 PATH 备份还原**都过这一道（`:565`）⇒ 原先的嫌疑点（卸载还原不保类型）已封住。`syswrite-test.ps1` 路 3b（`:609` 起）＋ `:255` 的类型断言照旧绿。⚠️ **遗留**：卸载**完成之后**再回读一次 PATH 类型的断言本轮没单加（`uninstall-test.ps1` 里搜不到 `REG_EXPAND_SZ`）——将来想更硬就补这一条。原判：~~**待复现**~~。建议修法 = 宿主改写/还原 PATH 时**保留原值类型**（读原类型 → 原样写回），并给卸载侧补一条与路 3b 同款的值类型断言。
- **关联档案**：`build/installer/bootstrapper/main.cpp`（PATH 写入/还原段）· `tools/syswrite-test.ps1` 路 3b · 备份里的 `reg-env-path.reg`
