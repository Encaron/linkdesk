# 已落地 · HintTip 滚动后跟着旧锚走、不收条

> **已落地（2026-09-30 用户实机立案 → 当日分析 ＋ 拍板 A 案 → 当日实现；✅ **已发版 v0.2.30**〔2026-10-04 销账订正〕——与同日「[插件详情标签名退成兜底文案](./插件详情标签名退成兜底文案.md)」同批攒着，随下一批一起 release；软件轴类别 = **PATCH**（0.x 向后兼容修复）。
> **立案原话（用户实机，按大意记述）**：「面对滚动容器这类东西的时候，如果我鼠标悬停在某个 ui 上面，这时候会出现 hint-tip，但是如果此时我鼠标滚动一下，这时候鼠标会失焦（这是正常的，因为滚动后鼠标坐标没变，但是内容滚动了），只是这个 hint-tip，它随着失焦，它不会消失，这个 hint-tip 反而会跟着滚动容器的东西往上滚动，直到我鼠标移动一下。」
> **拍板**：**A 案 —— 在"几何重算"那一点补一条「指针还在锚上吗」判据**（用户「按你推荐的改」）。
> **归属**：软件本体（壳侧 `src/components/shared/hint-tip/placement.ts` ＋ `HintTipRenderer.tsx` ＋ 两个测试文件）——**零插件侧改动、零配置、零契约**。

## 一、根因：同一个决定只写了一半

设计里那条原话是「锚元素旁边（贴边浮层，**随锚滚动/移动重算**）」（[悬停提示系统/01-设计.md §六·⑥](./悬停提示系统/01-设计.md)）——**这半句没错，实现也对**：`follow()` 确实挂在 `scroll`(capture) ＋ `resize` 上重算落点（capture 才听得到内层滚动容器）。漏掉的是另一半：

> **几何一变，指针**还在不在锚上**？**

条的生命周期原本只有四个收条动作——**移开 / 失焦 / Esc / 点下 / 拖拽**，全都是"指针自己动了"的事件。而本件报障的场景恰好反过来：**鼠标一动不动，动的是内容**。

```
指针停在 (x, y)，条开着
  ↓ 用户滚轮滚了一下（指针没动）
滚动容器把内容挪走 ⇒ 锚从指针底下走掉了
  ↓
浏览器**不发 pointerout**（指针没动，动的是元素）⇒ 四个收条动作一个都不来
  ↓
`scroll` 事件到了 ⇒ 但 `follow()` 只做"按新矩形重算落点"
  ↓
条忠实跟着一个**已经不在指针底下的锚**，一路滚出视口（用户原话「跟着滚动容器的东西往上滚动」）
  ↓
直到鼠标动一下 ⇒ pointerout/pointerover 终于来了 ⇒ 才收
```

**为什么以前没暴露**：四个收条动作覆盖了"指针动"的**全部**形态，而缺陷只在"指针不动 ＋ 内容动"这一种组合下出现——它没有第二个入口，所以四条腿各自的测试全绿（`HintTipRenderer.test.tsx` 里此前**一个滚动用例都没有**：滚动只被当成"重算落点"的输入，从没被当成"判据的时刻"）。定性 = **未覆盖的组合**，不是早期决策错误（同族前科见 memory `plugin-name-sources-beyond-viewregistry` 记的那条：「判据只写了一半」在本仓不是第一次）。

**顺带被这条判据救回来的同族场景**（都走 `follow()`，都一并覆盖）：`resize` 改写布局后锚从指针下离开 · 分栏拖拽 / 面板折叠 / 侧栏收起把锚挤走 · 主区切视图导致锚位移。

## 二、改法（已落地）

| # | 改了什么 | 位置 |
|:--:|:--|:--|
| 1 | 新增纯函数 `isPointerOnAnchor(anchor, point, hitTest)`——**三态**：`true` 在锚上 / `false` 不在 / `undefined` **无从判断**（无坐标或环境无命中测试）；沿 `parentNode` 上溯且**跨 Shadow 边界**（`Element.contains` 不跨影子树，会误判"不在锚上"）；命中测试**注入**（生产传 `document.elementFromPoint`），本函数不读 `document`/`window` ⇒ 纯函数可钉 | `placement.ts` |
| 2 | `OpenState` 加 `openedBy: "pointer" \| "focus"`——`enter()` 显式带上来源（⛔ 不用 `delayOverride === 0` 反推：揭示类提示的延时本来就是 0） | `HintTipRenderer.tsx` |
| 3 | **开条那刻记一次指针坐标**（用触发 `pointerover` 的 `clientX/clientY`；`Number.isFinite` 不过 ⇒ 记 `null`）——报障场景除了这一刻，没有任何事件会把坐标交出来。键盘路径记 `null` | 同上 `show()` |
| 4 | 条开着时挂 **passive `pointermove`** 续采坐标（只写 ref，不引发渲染；随活跃守卫一起挂/清）——否则"滚动后指针在哪"用的是开条那一刻的旧样本 | 同上 活跃守卫 effect |
| 5 | `follow()` 在"锚已卸载 ⇒ 收"之后插一条：**鼠标开的条 ＋ 指针已不在锚上 ⇒ 收条**（`=== false` 严格判，`undefined` 照旧跟随）；随后才是原有的重算落点 | 同上 `follow()` |

`close()` 同笔把 `lastPoint` 清成 `null`——坐标只属于刚收掉的那条（否则下次"滚动判定"会拿上一条的坐标做答）。

## 三、为什么不做别的

- **`anchor.matches(":hover")`**（否决）：`hover` 的刷新时机由引擎自己的指针重算决定，**恰恰在"滚动后指针没动"这个时刻不保证已更新**——要拦的就是它；且 jsdom 恒 `false` ⇒ 在测试里不可测、在现场不可信。
- **监听 `wheel`**（否决）：`wheel` ≠ 滚动。键盘翻页（PageDown/空格/方向键）、拖滚动条、`scrollTo`、惯性滚动、程序化 `scrollIntoView` **全都不走 wheel** —— 只覆盖鼠标滚轮等于漏一半现场。
- **`requestAnimationFrame` 逐帧比对矩形**（否决）：能覆盖全部形态，但代价是条开着期间**常驻一帧一次的轮询**（本件不是动画件）；而且"判据放哪"仍要落在 `follow()` 那个汇合点上，等于多一层机器换同一个答案。**若真机验收发现"某些滚动不触发 `scroll` 事件"（如某些合成滚动），这条是备选方案 2**。
- **"让条跟着走但别收"**（否决）：那是另一个设计决定（条=锚的附属物），用户要的恰好相反——**锚已经不在指针底下了，条就没有存在理由**；留着它反而挡住用户正在看的内容。
- **不做 rAF 合并 / 节流**：`follow()` 每次滚动事件重算一次落点（既有行为），新增的判据只是一次命中测试 ＋ 一次上溯，比落点计算本身还便宜；引入节流会改变既有跟随手感。

## 四、验收

**单元层（已量，`npm run check` 全绿）**

- `placement.test.ts` **7 例**：命中锚自身 ⇒ `true` · 命中锚的后代（按钮里的小图标）⇒ `true` · 命中树外元素 ⇒ `false`（**这就是该收条的现场**）· 影子树内的节点 ⇒ `true`（前提断言 `anchor.contains(inner) === false`，钉住"必须走 host 那一步"）· 无坐标 ⇒ `undefined` **且一次命中测试都不问** · 命中测试返 `null` ⇒ `undefined` · 坐标原样透传。
- `HintTipRenderer.test.tsx` **7 例**（状态机，真事件）：指针已不在锚上 ⇒ 收条并归还 aria · 指针仍在锚上（命中锚的后代）⇒ **不收**且落点按新矩形重算（设计「随锚滚动重算」的回归钉：`data-tip-placement` 由 `bottom` 翻回 `top`、`top/left` 按新矩形算出）· 键盘开的条 ⇒ 不收**且一次命中测试都不问**（`openedBy` 一票否决）· 鼠标开的条但事件根本没有 `clientX` ⇒ `undefined` ⇒ 不收 · 环境没有 `elementFromPoint` ⇒ 不收（降级方向：宁可不收）· 锚已卸载 ⇒ 滚动照样收（原有那条守卫不许被新判据挤掉）· 条开着时指针又移动过 ⇒ 用**最新**坐标判（`pointermove` 续采的钉）。

**⚠️ 量具限制（必须写下来）**：jsdom **没有** `document.elementFromPoint` ⇒ 判据在测试环境里天然落"无从判断"，上面那几条"收条"用例全靠**显式桩**才有意义。因此——

**⏳ 真机读数（待用户实机验收，四项）**

1. 悬停侧栏/主区的某个提示点 → **滚动** → 条应**立刻消失**（原报障场景；两种子情形：内容把锚带离指针 ⇒ 收；滚动幅度很小、锚仍压在指针底下 ⇒ 条应继续跟着走、**不许误收**）；
2. 悬停时**用键盘** PageDown / 拖滚动条 / `scrollTo` 滚动 ⇒ 同样收（这三种都不走 `wheel`）；
3. **键盘 Tab** 聚焦出条 → 滚动 ⇒ **不许收**（没有指针，判据不该管它）；
4. 拖分栏 / 折叠面板 / 缩窗口把锚挤走 ⇒ 收；锚只是位移但指针仍在其上 ⇒ 跟随不误收。

若出现**误收**（指针确实还在锚上却被收掉），备选修法是给判据加一条 OR：`anchor.matches(":hover")` 或"指针坐标是否落在锚的新矩形内"（`getBoundingClientRect()` 包含判定），两者都比命中测试宽松。

## 五、边界与遗留

- **降级方向是"不收"**：判据三态里 `undefined` 一律照旧跟随——宁可多留一帧旧条，也不许凭猜把用户正看着的条收掉（`elementFromPoint` 在老引擎/无头环境可能缺席）。
- **`pointer-events: none` 的锚**：命中测试会命中它底下的元素 ⇒ 判"不在锚上"。但那种锚**根本收不到 `pointerover`**（进不去鼠标路径），所以不可能出现"鼠标开的条 + 这种锚"的组合，判据不会被它触发。
- **条自身不会污染命中测试**：`.ldk-hint-tip` 带 `pointer-events: none`（设计 §四·4.2），`elementFromPoint` 不会返回它。
- **`ScrollEnd` / 被动监听**：`pointermove` 用 `{ passive: true }`（只写 ref）；`scroll` 仍走 capture（内层容器），两者都不调 `preventDefault`。
- **不做的事**：不给"条跟着滚动"加过渡动画（本件是收条判据，不是动效件）；不动 `GAP_PX`/翻面/尖角那五条几何约定（见 `placement.ts` 头注）。
