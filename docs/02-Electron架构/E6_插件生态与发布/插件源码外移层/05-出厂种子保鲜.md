# 7.4 出厂种子保鲜——新用户拿到的就是最新

> **任务号：** E6#101 · **前置：** 7.3（上架——种子的来源是各插件仓的 Release） · **产物：** `sync:bundled` 命令 + `bundled-plugins.lock.json` + 新鲜度门禁
> **回答的是你这句话：** 「软件更新到了第二版，这个插件没有更新，那就无所谓；但有一天我突然给这个设置插件更新到了第二版，那么一个新的用户下载软件，想体验到全新的效果，**我就应该给他提供第二版的软件和第二版的插件一起下载**。」

---

## 〇、病灶

### 现状机制（已实测，不是推测）

| 环节 | 现状 | 出处 |
|:--|:--|:--|
| 箱子里的 zip | **静态提交进仓库**（`bundled-plugins/*.linkdesk-plugin`，18 个） | 仓库现物 |
| 打包时 | electron-builder 把 `bundled-plugins` 原样拷进 `resources/` | `electron-builder.yml` 的 `extraResources` |
| 首启 | boot 解压落 `{userData}/plugins/` | `electron/plugins/bundled-install.ts` |
| **之后** | **同版本跳过；异版本「不动（升级归安装流）」** | `electron/plugins/bundle-zip.ts:200-214` |

⇒ **两道后果，方向相反但都要认：**

- ✅ **好的一半**：出厂插件装上后**本来就不随壳升级**——「插件独立更新」这条架构早就成立（与你的模型一致）。
- ❌ **坏的一半**：`bundled-plugins/` 里的 zip 是**打包那一刻的快照**。插件之后再发多少版，箱子里还是那份旧的——**直到有人手工把新 zip 拷进来**。

**你怕的就是这个：软件 V2 + 插件还是 V1。**

### 为什么「加一条门禁报警」不够

报警只告诉你「落后了」，不解决「怎么追上」。所以本轮**机制（sync）+ 账（lock）+ 门禁（check）三件套必须一起上**，单独任何一件都不成立。

---

## 一、目标模型（D3）

> **出厂 = 打包时把该插件的最新已发布版塞进箱子。** 与「源码住在哪」彻底解耦。

```
插件仓发版（7.3 轮）
      ↓
sync:bundled 拉取 → 刷新 bundled-plugins/*.linkdesk-plugin + 更新 lock
      ↓
壳打包（electron:build）→ 箱子随包
      ↓
新用户首启 boot 解装 → 拿到「当前壳版 + 出厂插件各自最新已发布版」✅
```

**这套成立的前提只有一条：上架必须是真的（7.3 轮）**——拉取源就是各插件仓的 Release 直链。

---

## 二、三个命令档

| 命令 | 行为 | 用途 |
|:--|:--|:--|
| `npm run sync:bundled` | 按 lock 逐条**校验并拉取**；加 `--latest` 时**先查官方目录最新版再刷新 lock + zip** | 日常：发壳前跑一次 |
| `npm run sync:bundled -- --offline` | 只用 lock 里已有的指纹/缓存校验，**不出网** | CI 无网环境 / 复现构建 |
| `npm run check:bundled-freshness` | **只查不改**——每只出厂 zip 的版本 vs 官方目录该插件最新版，落后 ⇒ exit 1 | 挂 `npm run check`（日常）与发布门禁（发版那一下） |

**默认档为什么是「按 lock」而不是「按最新」**：可复现。**同一份 commit 两次构建必须装进同样的箱子**——「按最新」会让同一个 commit 在两天后构建出不同的产物，而壳的发布是「打 tag → 事后可重建」的模型。⇒ **刷 lock 必须是显式动作**（`--latest`），且刷完的 lock 变更进 commit、可审查。

## 三、`bundled-plugins.lock.json`（新文件，提交进仓库）

```jsonc
{
  "schemaVersion": 1,
  "syncedAt": "2026-09-14T00:00:00Z",          // 上次 sync 时间（信息性）
  "plugins": [
    {
      "id": "settings",                        // plugin.json 的 id（不是仓库名）
      "repo": "Encaron/linkdesk-plugin-settings",
      "version": "1.0.5",                      // §四 的版本单一真源
      "downloadUrl": "https://github.com/.../releases/download/v1.0.5/settings.linkdesk-plugin",
      "fingerprint": "<sha256>",               // 算法与 check-bundled-version-bump 一致
      "seed": true                             // 是否随包（§五）
    }
  ]
}
```

**三个字段的必要性：**

| 字段 | 为什么必须有 |
|:--|:--|
| `version` | **这是「箱子里装了什么」的唯一可审查答案**——不用解开 zip |
| `downloadUrl` | 按 lock 复现时要去哪拉 |
| `fingerprint` | 同一版本号被重打成不同内容（本仓明令禁止且已有门禁）时能发现；也是 offline 档的校验依据 |

> 🔁 **指纹算法复用现成的**：[scripts/check-bundled-version-bump.mjs](../../../../scripts/check-bundled-version-bump.mjs)（对 zip 内非目录条目做 `名字:sha256(LF 归一后内容)` 排序拼接）+ [scripts/lib/text-eol.mjs](../../../../scripts/lib/text-eol.mjs) 的 EOL 归一。**不许新写一套**——两套指纹算法必然漂移，然后门禁之间互相打架。

## 四、与既有门禁的分工（别重复，别打架）

| 门禁 | 管什么 | 与本轮的关系 |
|:--|:--|:--|
| `check-bundled-version-bump.mjs`（已有） | zip 内容变了 ⇒ **`plugin.json.version` 必须 bump** | **不动**。它管「改了内容没 bump」，是内容纪律 |
| `check-bundled-freshness`（本轮新增） | 箱子里的 zip 是不是官方目录里的**最新已发布版** | 新职责：**新鲜度** |
| `check-version-bump` / `check-changelog-section`（已有） | 软件侧版本/CHANGELOG 纪律 | 不动 |

⇒ 两者**正交**：一个管「内容与版本号一致」，一个管「这颗种子是不是最新的」。**同一个 zip 可以既满足前者又落后于后者**——这就是为什么两条都要。

## 五、bootstrap 清单放哪（🔴 硬约束 10 的红线）

**要声明的是：哪 6 只随包出厂。** 用户点名的四只 + 本轮建议补的两只：

| 插件 | 为什么必须随包 |
|:--|:--|
| `settings` | 没它没地方改东西 |
| `marketplace` | 没它没地方装东西 |
| `file-tree` | 没它看不到东西 |
| `editor` | 没它打不开东西 |
| `theme-defaults` | 没它界面无主题 |
| `lang-defaults` | 没它界面无语言 |

判据（可复用的一句话）：**「断网、零插件时，用户能不能自救？」**

### 🔴 清单**不许**写成代码里的插件 ID 列表

硬约束 10 明令：禁止 `["hardcoded", "list"]` 形式的插件名单（`PLUGIN_SUBDIRS = ["builtin", "user"]` 是被点名的反模式）。

**本轮的解法很干净：清单的载体就是 `bundled-plugins.lock.json` 本身（`seed: true` 的那些条目）+ `bundled-plugins/` 目录里的 zip。** ⇒

- **壳代码里一个插件 id 都不用出现**（现状本来也是这样：boot 扫 `bundled-plugins/` 目录，不认名字）。
- 想改「谁随包」= 改数据（lock / 目录），**不是改代码**。
- `sync:bundled` 与 `check-bundled-freshness` 也**只读 lock**，不内嵌 id。

> ✅ 这条同时满足 `sync-official-catalog.mjs`（7.3 §2.2）的「不许写死 18 个 id」——它同样只读 lock。

### 7.1 开工前盘出来的三件事（决定了本轮的实证设计）

1. 🔴 **「箱旧仓新」的落差当时并不存在**——箱内 18 只、各仓 `releases/latest`、官方目录那 18 条，**三方 18/18 版本一致**（7.2/7.3 收官时种子已随包刷过）。⇒ `--latest` 与门禁的落差实证**必须自己造**，否则验的是一条恒真门禁。本轮做法 = 真发一版 settings（见 7.4）。

| 件 | 产物 | 实测读数 |

| **账** | `bundled-plugins.lock.json`（18 条 = 官方全集；`seed:true` 6 只 = 随包集） | 18 条指纹**现下载现算**，与箱内 zip 逐字节一致；`sync-official-catalog` 的清单来源随之切到账（日志：「清单来源：bundled-plugins.lock.json（18 只）」） |

| **门禁** | `scripts/check-bundled-freshness.mjs`（挂 `npm run check`，紧跟 `check-bundled-version-bump`） | `--self-test` **9/9**（含「目录比箱新 ⇒ 红」「箱比目录新 ⇒ **不假红**」「种子不在目录 ⇒ 红」）＋ **真箱负控**：把 settings 换成历史真旧版 1.0.5 ⇒ **2 处红**（箱≠账、箱落后于目录） |

🔴 **判定方向（写进门禁头注，理由在本档留档）**：`目录 > 箱 ⇒ 红`；**箱 ≥ 目录 ⇒ 绿**。
任一条读取路径带缓存滞后时，只会**延迟发现落后**，**永不假红** —— 假红让真红失效，是本仓最贵的坏法。
（易误读处已实测：负控期间「新鲜度比对」这一行报的是**箱内实际版本**，不是账里写的版本 —— 早期实现读账，会出现「箱子明明是旧的、新鲜度却说全过」的错读，已修。）
