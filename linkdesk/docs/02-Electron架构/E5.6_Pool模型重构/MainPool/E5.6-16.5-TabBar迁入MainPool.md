# E5.6#16.5 TabBar 迁入 MainPool——每个 group 自包含

> **状态：** 设计完成，待执行。
> **父任务：** Phase 4 MainPool 迁移（E5.6#14-#17 的根治性重构）。
> **依赖：** E5.6#15 #16 #17（分屏+分隔线+keep-alive 已完成，当前 #16 的分隔线将被部分重写）。
> **目标：** TabBar 从壳 WebView 迁入 MainPool WebView。每个 group 自包含（TabBar + 内容 + 分隔线），同 DOM 天然同步。上下分屏基础设施。

---

## 0. 由来——为什么有 #16.5

### 0.1 用户反馈的三个现象

E5.6#14-#17 落地后，分屏和 TabBar 的架构问题暴露：

| # | 现象 | 根因 |
|:--|:--|:--|
| 1 | 拖 MainPool 分隔线 → TabBar 不跟着动 | TabBar 在壳 WebView，不知道 MainPool 里拖了分隔线 |
| 2 | 拖完松手 → 分隔线弹回原位置 | 壳 tabState 重新 pushLayout → MainPool 收到的是壳算的比例 → 本地拖的被覆盖 |
| 3 | 上下分屏不可能 | 壳只有一个横条位置放 TabBar——MainPool 下半部分被完全盖住，没有地方放第二个 TabBar |

**这三个不是"bug 可以修"，是架构不支持。**

### 0.2 根因——两层 DOM

```
壳 WebView（z-index: 上层）           MainPool WebView（z-index: 下层）
┌──────────────────────────────┐     ┌──────────────────────────────┐
│ [hello.c] [hello.h] ← TabBar │     │ (TabBar 下方留白 35px)       │
├──────────────────────────────┤     ├──────────────┬───────────────┤
│                              │     │ hello.c      │ hello.h       │
│   ← 壳 DOM 透明/display:none │     │ 编辑器       │ 编辑器        │
│                              │     └──────────────┴───────────────┘
└──────────────────────────────┘
```

TabBar 和内容不在同一个进程 → 两个独立 DOM 树 → 永远无法真正同步。左右分屏勉强能混（TabBar 整条不变），上下分屏彻底穿帮。

### 0.3 唯一解——TabBar 进 MainPool

```
壳 WebView（只剩壳级 UI）              MainPool WebView（自包含 group）
┌──┬───────────────────────────┐     ┌──────────────────────────────┐
│🔵│                           │     │ ┌──────────┬───────────────┐ │
│  │                           │     │ │[hello.c] │ [hello.h]      │ │
│🔴│    SidebarPool            │     │ │ hello.c  │ hello.h        │ │
│  │                           │     │ └──────────┴───────────────┘ │
│🟢│                           │     │   ↑ 分隔线在 MainPool 内部    │
│  │                           │     └──────────────────────────────┘
└──┴───────────────────────────┘
```

每个 group 自包含：自己的 TabBar + 自己的内容。分隔线 → TabBar 和内容一起动——同 DOM，天然同步。上下分屏也天然支持——上半 group、下半 group，和左右分屏完全对称。

## 1. 目标架构

### 1.1 壳变薄

| 壳保留 | 壳删除 |
|:--|:--|
| IconBar + SidebarPool placehold | ~~TabBar 组件渲染~~ |
| 状态栏 | ~~SplitPane 组件~~ |
| tabState 管理（useTabManager） | ~~TabPanePositioner 绝对定位~~ |
| 标签页 IPC handler（tabs:create/openOrFocus/close等） | ~~drop zone overlay~~ |
| OverlayWindow（右键菜单/命令面板等）（Phase 6） | ~~drag-drop split/copy-split 逻辑~~（迁到 MainPool 本地） |
| 崩溃 fallback——最小 TabBar 覆盖层 | |

### 1.2 MainPool 自包含

每个 group = 一个 `GroupPane`：

```
<GroupPane group={group} isLast={idx === groups.length - 1}>
  <GroupTabBar tabs={group.tabs} activeTabId={group.activeTabId} groupId={group.id} />
  <div class="group-content">
    {group.tabs.map(tab => <keep-alive-div display={tab.id === activeTabId ? "flex" : "none"} />)}
  </div>
</GroupPane>
```

`GroupPane` 之间插入 `<Divider>`（分隔线——重写 #16 的逻辑）。

### 1.3 数据流

```
用户操作 MainPool
  → pool.tabAction({ action, ...args })
  → ipcRenderer.send('pool:tab-action', ...)
  → 主进程 plugin-view-handlers.ts
  → mainWindow.webContents.send('pool:tab-action', ...)
  → 壳 preload-shell ipcRenderer.on('pool:tab-action')
  → onTabAction 回调
  → useTabManager 方法（focusTab/closeTab/moveTab/reorderTab/splitTab/...）
  → tabState 更新
  → usePoolSync pushLayout
  → MainPool 收到新 layout → 重渲染 → 确认用户操作
```

和 SidebarPool 的 `pool:sidebarAction` 完全同模式。

### 1.4 和 SidebarPool 的对称性

| | SidebarPool | MainPool（改后） |
|:--|:--|:--|
| 壳推什么 | `{ sidebar: { views[], containerId, ... } }` | `{ groups: [{ tabs[], activeTabId, flex }] }` |
| 池渲染什么 | SidebarRenderer → PoolSectionStack + PoolToolbarSlot | MainRenderer → GroupPane[] → GroupTabBar + 内容 |
| 池→壳写操作 | `pool.sidebarAction({ action: "reorder" })` | `pool.tabAction({ action: "focusTab" })` |
| 壳处理 | ViewContainerService 写方法 | useTabManager 写方法 |
| 回环 | onDidChangeActiveViews → layoutVersion bump → pushLayout | tabState 变 → useEffect → pushLayout |

**MainPool 改后 = 和 SidebarPool 完全对称的"哑渲染器 + IPC 写回"模式。**

## 4. 拖拽排序——乐观更新 + 服务端确认

### 4.1 为什么不能每帧 IPC

TabBar 在壳时，拖标签页排序是**零延迟**——同 DOM 内的 `onDragOver` / `onDrop`。搬进 MainPool 后，每次鼠标移动都 IPC 往返太慢（~1ms × 60fps = 不可见延迟但架构上浪费）。

### 4.2 乐观更新模式

```
MainPool 本地                         壳（服务端）
─────────────────────────────────────────────────────
1. 用户开始拖拽 tab "hello.c"
2. onDragStart: 记录 tabId + 原始位置
3. onDragOver: 本地交换 tabs 数组       ← 无 IPC
   → React setState → 即时视觉反馈

4. onDrop: 发送 IPC
   → pool.tabAction({                  →
     action: "reorderTab",
     groupId: "group-1",
     tabId: "hello.c",
     newIndex: 2,
     oldIndex: 0  // 用于冲突检测
   })

                                       5. useTabManager.reorderTab(tabId, oldIndex, newIndex)
                                       6. tabState 更新
                                       7. usePoolSync pushLayout
                                       8. MainPool 收到新 layout →
   ← 收到确认                          ←   tabs 顺序和本地一致 → 不做任何事 ✅
                                       ←   tabs 顺序和本地不一致 → 回退动画 ⚠️
```

### 4.3 回退处理

发生场景极少——仅当壳拒绝了操作（如目标 group 在拖拽期间被其他操作删除了）。

处理：`useEffect` 监听 `groups` prop 变化 → 如果 `tabs` 顺序和 `localTabs` 不一致且非拖拽中 → 7 帧缓动动画回到正确位置。动画用 `requestAnimationFrame` + CSS `transform`——不引入依赖。

### 4.4 跨 group 拖拽

拖 tab 到另一个 GroupPane 上方 → 显示 drop indicator（亮色竖线/横线）→ 松手：

```
pool.tabAction({
  action: "moveTab",
  tabId: "hello.c",
  targetGroupId: "group-2",
  newIndex: 0
})
```

壳 `useTabManager.moveTab(tabId, targetGroupId)` → tabState 更新 → pushLayout。

## 5. 右键菜单——方案 A（MainPool 内渲染）

### 5.1 菜单项

| 命令 | IPC action |
|:--|:--|
| 关闭 | `pool.tabAction({ action: "closeTab", tabId })` |
| 关闭其他 | `pool.tabAction({ action: "closeOtherTabs", groupId, tabId })` |
| 关闭右侧 | `pool.tabAction({ action: "closeTabsToRight", groupId, tabId })` |
| 关闭全部 | `pool.tabAction({ action: "closeAllTabs", groupId })` |
| 向右分屏 | `pool.tabAction({ action: "splitTab", tabId, direction: "right" })` |
| 向下分屏 | `pool.tabAction({ action: "splitTab", tabId, direction: "down" })` |
| 复制标签页 | `pool.tabAction({ action: "duplicateTab", tabId })` |
| 固定/取消固定 | `pool.tabAction({ action: "pinTab", tabId })` |

### 5.2 裁剪问题

MainPool 是一个 `WebContentsView`——右键菜单贴近边缘时可能被裁剪。

**方案 A 对策：** 检测菜单 rect 是否超出 View bounds → 超出时翻转方向（`translateY(-100%)` 或 `translateX(-100%)`）。串口监视器 ControlPanel 的选择框已有此逻辑——提取到 `src/pool/MenuPositioner.ts` 共用。

**未来（Phase 6）：** 切换到 OverlayWindow 渲染右键菜单——`pool.tabAction({ action: "showContextMenu", items, screenX, screenY })` → 壳在 OverlayWindow 里渲染菜单。MainPool 代码只需改一行（调用方从本地渲染改为 IPC），GroupTabBar 其余逻辑不变。

### 5.3 分屏方向

右键 "向下分屏" 需要壳的 `tabState` 支持垂直分屏 SplitNode（`direction: "vertical"`）。当前 `reduceSplitTab` 默认 `direction: "horizontal"`——需要加参数。

`pool.tabAction({ action: "splitTab", tabId, direction: "down" })` → 壳 `splitTab(tabId, "vertical")`。

**上下分屏的视觉呈现：** MainRenderer 当前是水平 flex 容器。上下分屏需要垂直 flex 容器 + 嵌套的水平 flex。MainRenderer 改为渲染 SplitNode 树——递归渲染，branch 的 `direction` 决定 flex 方向。

> **这是真正的分屏架构升级。** 不在 #16.5 范围——留到 #16.7 做。见 §10 "后续预留给 #16.7"。

## 7. IPC——pool:tab-action 通道

### 7.1 通道定义

```
池→主进程→壳: pool:tab-action
壳→主进程→池: pool:layout（已有——不需要改）
```

### 7.2 消息类型

```typescript
type TabAction =
  | { action: "focusTab"; tabId: string }
  | { action: "closeTab"; tabId: string }
  | { action: "closeOtherTabs"; groupId: string; tabId: string }
  | { action: "closeTabsToRight"; groupId: string; tabId: string }
  | { action: "closeAllTabs"; groupId: string }
  | { action: "reorderTab"; groupId: string; tabId: string; newIndex: number; oldIndex: number }
  | { action: "moveTab"; tabId: string; targetGroupId: string; newIndex: number }
  | { action: "splitTab"; tabId: string; direction: "right" | "down" }
  | { action: "duplicateTab"; tabId: string }
  | { action: "pinTab"; tabId: string }
  | { action: "createTab"; groupId?: string };
```

### 7.3 各文件变更

| 文件 | 变更 | 行数 |
|:--|:--|:--|
| `electron/preload-pool.ts` | `pool.tabAction(action: TabAction)` → `ipcRenderer.send('pool:tab-action', action)` | +5 |
| `electron/ipc/plugin-view-handlers.ts` | `ipcMain.on('pool:tab-action', ...)` → `mainWindow.webContents.send('pool:tab-action', action)` | +10 |
| `electron/preload-shell.ts` | `ipcRenderer.on('pool:tab-action', ...)` → `onTabAction` 回调 | +8 |
| `src/hooks/usePoolSync.ts` | `onTabAction` 回调 → `UsePoolSyncInput` 新增字段 | +5 |
| `src/components/MainContent.tsx` | `usePoolSync({ ..., onTabAction })` + handler 实现 | +40 |

### 7.4 壳侧 handler 实现（MainContent.tsx）

```typescript
const handleTabAction = useCallback((action: TabAction) => {
  switch (action.action) {
    case "focusTab":
      focusTab(action.tabId);
      break;
    case "closeTab":
      closeTab(action.tabId);
      break;
    case "closeOtherTabs":
      closeOtherTabs(action.groupId, action.tabId);
      break;
    case "closeTabsToRight":
      closeTabsToRight(action.groupId, action.tabId);
      break;
    case "closeAllTabs":
      closeAllTabs(action.groupId);
      break;
    case "reorderTab":
      reorderTab(action.tabId, action.oldIndex, action.newIndex);
      break;
    case "moveTab":
      moveTab(action.tabId, action.targetGroupId);
      break;
    case "splitTab":
      splitTab(action.tabId, action.direction === "down" ? "vertical" : "horizontal");
      break;
    case "duplicateTab":
      duplicateTab(action.tabId);
      break;
    case "pinTab":
      pinTab(action.tabId);
      break;
    case "createTab":
      createTab(undefined, { groupId: action.groupId });
      break;
  }
  // tabState 自动变化 → usePoolSync 自动 pushLayout → MainPool 自动更新
}, [focusTab, closeTab, ..., splitTab, ...]);
```

## 8. 崩溃 fallback——壳最小 TabBar

### 8.1 场景

MainPool 崩溃（`render-process-gone`）→ 用户无法切标签页 → 软件看起来死了。

### 8.2 方案

壳在 MainPool 崩溃时渲染一个**最小 fallback 覆盖层**——纯文本标签列表，无拖拽、无样式。Phase 7 崩溃恢复机制重建 MainPool → fallback 自动消失。

```tsx
// MainContent.tsx
{mainPoolCrashed && (
  <div className="tab-bar-fallback">
    {tabState.groups.flatMap(g => g.tabs).map(tab => (
      <button
        key={tab.id}
        className={tab.id === activeTabId ? "active" : ""}
        onClick={() => focusTab(tab.id)}
      >
        {tab.label}
      </button>
    ))}
    <button onClick={() => rebuildMainPool()}>🔄 重建主区</button>
  </div>
)}
```

~30 行。不是优先任务——Phase 7（崩溃恢复）已经有 #28a-d 覆盖此场景。**16.5 只加一个占位 div 和 `mainPoolCrashed` state**，完整 fallback UI 留给 Phase 7。

| 垂直方向分隔线 | 同上 | **#16.7** |
| 跨 Pool 拖标签页 | 需要 OverlayWindow 画拖影 | Phase 6 |
| 拖出成独立窗口 | BrowserWindow 管理 | E6 |
| 右键菜单 → OverlayWindow | 依赖 Phase 6 | Phase 6 完成后的 #16.5 增补 |

### 10.2 #16.7 做什么

`MainRenderer` 从平铺 `groups[]` 改为递归渲染 `SplitNode` 树：

```tsx
function RenderSplitNode({ node, groups }: { node: SplitNode; groups: PoolGroup[] }) {
  if (node.type === "leaf") {
    const group = groups.find(g => g.id === node.groupId);
    if (!group) return null;
    return <GroupPane group={group} />;
  }
  // node.type === "branch"
  const flexDirection = node.direction === "horizontal" ? "row" : "column";
  return (
    <div style={{ display: "flex", flexDirection, flex: 1 }}>
      <RenderSplitNode node={node.children[0]} groups={groups} style={{ flex: node.sizes[0] }} />
      <Divider direction={node.direction} ... />
      <RenderSplitNode node={node.children[1]} groups={groups} style={{ flex: node.sizes[1] }} />
    </div>
  );
}
```

`PoolLayout` 加 `root: SplitNode`——壳推整个树。MainRenderer 递归渲染。**这是真正的分屏架构升级，但依赖 #16.5 先把 TabBar 搬进来。**

## 11. 壳特殊视图——欢迎页 / 插件详情 / 输出面板

### 11.1 问题

当前有三类"壳内部视图"不经过插件路由——由 `renderTabContent` + `SHELL_VIEWS` Record 直接渲染：

| tab.type | 组件 | 用途 |
|:--|:--|:--|
| `"welcome"` (`FALLBACK_PLUGIN_ID`) | `WelcomeView` | 兜底标签页——无标签时自动打开 |
| `"plugin-detail"` | `PluginDetailView` | 查看插件元数据、启用/禁用/卸载 |
| `"output"` | `OutputPanel` | 输出日志面板（E3f #54） |

这些组件定义在 `src/components/views/`，通过 `isShellRenderedTab()` 判断（`tabIdentity.ts:100` → `SHELL_RENDERED_TYPES`）。

**#16.5 的矛盾：** TabBar 迁入 MainPool 后，这些标签页的 TabBar 条目在 Pool 里渲染，但内容组件在壳 DOM 里——跨层撕裂。

### 11.2 分析——三个视图的依赖

| 视图 | 壳侧依赖 | 能否迁 Pool |
|:--|:--|:--|
| **WelcomeView** | `viewRegistry.getTabCreatableViews`, `WorkspaceService`, `PluginStateService` | ⚠️ 中等——依赖壳侧 service，但都可用 `window.linkdesk.*` 替代 |
| **PluginDetailView** | `viewRegistry.getViewPlugin`, `loader` (disable/enable/reinstall/uninstall/status), `lifecycle.onPluginLifecycleChange` | 🔴 重度——直接 import `pluginLoader/loader` 的 7 个函数 + `lifecycle` 事件。迁 Pool 需完整重写数据层 |
| **OutputPanel** | `SelectBox` (壳组件) | 🟢 轻量——只依赖 `SelectBox`，无 shell 专有 service |

### 11.3 方案——分阶段处理

**#16.5 阶段的处理（最小可行方案）：**

三层策略，按复杂度分流：

#### 策略 A：WelcomeView → 池内空态替代（零成本）

`MainRenderer` 已有 `groups.length === 0` 空态（"没有打开的标签页"）。`WelcomeView` 本身是当没有任何标签页打开时显示的欢迎界面。

**#16.5 后：** 当 `tabState.groups` 里唯一的 tab 是 welcome 类型时：
- 壳 `usePoolSync` 推送空 `groups: []` 到 MainPool
- MainRenderer 渲染空态 div
- 壳侧不再渲染 `WelcomeView` 组件——`TabPanePositioner` 已删除

增强：把 `WelcomeView` 的快捷操作（打开文件夹/新建文件等）做成 `pool.tabAction` 可触发：
```
pool.tabAction({ action: "createTab", pluginId: "editor" })
pool.tabAction({ action: "openFolder" })
```

这些走 IPC → 壳 `useTabManager` → 标签页打开 → pushLayout → MainPool 渲染编辑器。

**改动量：** ~5 行——空态 div 里加一个"新建文件"按钮。

#### 策略 B：PluginDetailView + OutputPanel → 壳 Overlay 层（~50 行）

这两个视图的 TabBar 标签页在 MainPool 中正常渲染。点击时：
1. Pool `GroupTabBar` 发送 `pool.tabAction({ action: "focusTab", tabId })` → IPC
2. 壳 `handleTabAction` 处理 `focusTab` → tabState 更新
3. `usePoolSync` pushLayout → Pool 把对应 tab 的 `activeTabId` 设为此 tab
4. **Pool 内容区渲染一个"壳渲染"占位 div**（不是实际内容）
5. **壳在 MainContent 中渲染一个 overlay div**，`position: absolute` 覆盖在 MainPool WebContentsView 上方，显示 PluginDetailView/OutputPanel

```
壳 DOM（MainContent.tsx）
┌──────────────────────────────────────────────┐
│  MainPool WebContentsView (z-index: 0)       │
│  ┌─ GroupTabBar ───────────────────────────┐ │
│  │ [hello.c] [插件详情: serial-monitor]     │ │
│  ├─────────────────────────────────────────┤ │
│  │ <壳渲染占位>                             │ │
│  └─────────────────────────────────────────┘ │
│                                              │
│  shell-overlay (z-index: 1, position:absolute)│
│  ┌─────────────────────────────────────────┐ │
│  │ PluginDetailView / OutputPanel          │ │
│  └─────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

**为什么可行：**
- 壳 overlay 在 MainPool WebContentsView 的**上层**（z-index）——OS 层面壳 WebView 在池 WebView 上方
- 壳知道 MainPool 的 bounds（`WindowManager.getBounds("main")`）→ 精确定位 overlay
- 壳知道当前活跃的 tab 是否是 shell-view 类型 → `isShellRenderedTab(tab.type)`

**壳侧新增代码（MainContent.tsx）：**
```tsx
// 当前活跃 tab 是否为壳渲染类型
const activeTab = /* 从 tabState 推导 */;
const showShellOverlay = activeTab && isShellRenderedTab(activeTab.type);

{showShellOverlay && (
  <div className="shell-view-overlay" style={{
    position: "absolute",
    top: TAB_BAR_HEIGHT,  // 35px——给 Pool 的 TabBar 留空间
    left: 0, right: 0, bottom: 0,
    zIndex: 10,
  }}>
    {renderTabContent(activeTab, true, createTab)}
  </div>
)}
```

> **TabBar 避让：** overlay 的 `top: 35px` 确保壳视图内容不会盖住 MainPool 里的 GroupTabBar。35px = `TAB_BAR_HEIGHT`。

**改动量：** ~30 行壳 + ~5 行池占位。

#### 策略 C：长期——迁入 MainPool（#16.5 后续）

`PluginDetailView` 和 `OutputPanel` 最终应改为池原生渲染：

| 视图 | 迁移方案 |
|:--|:--|
| **WelcomeView** | 重写为池内空态组件——使用 `window.linkdesk.workspace.*` 和 `window.linkdesk.plugins.*` API |
| **PluginDetailView** | 重写数据层——用 `window.linkdesk.plugins.*` 替代 `pluginLoader/loader` 直接 import。插件启用/禁用/卸载/重装走 IPC |
| **OutputPanel** | 最轻量——把 `SelectBox` 提取到 `src/pool/shared/`（或改为原生 `<select>`），其余逻辑不变 |

> **不做为 #16.5 的一部分。** 这三个视图目前功能正常，策略 B 的 overlay 足够过渡。策略 C 记入 E5.6 清单 future 任务，在 Phase 8（API 补全）后执行。

### 11.4 `isShellRenderedTab` 的后续

`tabIdentity.ts` 的 `SHELL_RENDERED_TYPES` 在 #16.5 后仍有用——标记哪些 tab 的内容在壳 overlay 渲染而非 Pool 渲染。

**#16.5 不删 `isShellRenderedTab`。** 壳 overlay 依赖它判断是否显示。策略 C 完成后才删。
