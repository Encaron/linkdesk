# 04 — 数据流

> 从串口到卡片 + 从卡片回 MCU。每个卡片可独立绑定协议——不跟标签页。

---

## 一、核心变化——per-card 协议 vs 标签页协议

```
旧模型（标签页级）：一个标签页 = 一个协议，所有卡片共用
新模型（卡片级）：   每个卡片声明自己的协议，并行解析，双键路由

标签页协议 = 默认——卡片不显式绑定时走标签页协议
卡片独立协议 = 覆盖——卡片显式绑定 "sbq" → 只收 SBQ 解析器的输出
```

---

## 二、显示方向——并行解析 + 双键路由

```
MCU 固件
  │  Serial.print("[temp,37.2]\\n");
  │  Serial.print("s128\\n");           ← 同一条串口，混合格式
  │  Serial.print("B72\\n");
  │  Serial.print("[fan,on]\\n");
  │  Serial.print("Q800\\n");
  ▼
串口硬件 → serial-service → 原始字节流 → 行分割器 → 逐行文本
  │
  │  "[temp,37.2]"  → 跑所有活跃协议的解析器 ──┐
  │  "s128"         → 跑所有活跃协议的解析器 ──┤
  │  "B72"          → 跑所有活跃协议的解析器 ──┤  并行——不是选一个
  │  "[fan,on]"     → 跑所有活跃协议的解析器 ──┤
  │  "Q800"         → 跑所有活跃协议的解析器 ──┘
  │
  ▼
每行 → 每个活跃协议 → 各自解析 → 输出打上 protocolId 标签

  方括号解析器（bracket）:
    "[temp,37.2]"  → { protocolId: "bracket", cardId: "temp",  value: 37.2 }
    "s128"         → 无匹配
    "B72"          → 无匹配
    "[fan,on]"     → { protocolId: "bracket", cardId: "fan",   value: "on" }
    "Q800"         → 无匹配

  SBQ 解析器（sbq）:
    "[temp,37.2]"  → 无匹配
    "s128"         → { protocolId: "sbq",     cardId: "adc_value",     value: 128 }
    "B72"          → { protocolId: "sbq",     cardId: "heart_rate",    value: 72 }
    "[fan,on]"     → 无匹配
    "Q800"         → { protocolId: "sbq",     cardId: "beat_interval", value: 800 }

  ↓ 所有结果汇入 RingBuffer
  │
  ▼
DataDispatch——双键路由: (protocolId, cardId)
  │
  ├── (bracket, temp)       → 温度卡片   ← 绑定 protocolId="bracket"
  ├── (bracket, fan)        → 风扇卡片   ← 绑定 protocolId="bracket"
  ├── (sbq, adc_value)      → ADC 卡片   ← 绑定 protocolId="sbq"
  ├── (sbq, heart_rate)     → 心率卡片   ← 绑定 protocolId="sbq"
  └── (sbq, beat_interval)  → 搏间卡片   ← 绑定 protocolId="sbq"
```

**一行数据跑所有活跃协议——不是 per-card 单独跑。** 5 张卡片绑了 2 种协议 = 每行数据最多跑 2 个解析器，不是 5 个。

## 三、活跃协议收集——动态计算

```typescript
// 每行数据到达时动态计算哪些协议需要跑
// 不是启动时固定——卡片增删后自动调整

function getActiveProtocols(): ProtocolEntry[] {
  // 1. 侧栏勾选的协议 ID 集合（用户手动控制）
  const checkedIds = getCheckedProtocolIds();         // 如 {"bracket", "sbq"}

  // 2. 标签页默认协议（自动加入已勾选）
  const tabProtocol = getActiveProtocol();
  checkedIds.add(tabProtocol.id);

  // 3. 卡片显式绑定的协议（自动加入已勾选——不能绑了但不激活）
  for (const card of allCardInstances) {
    if (card.protocolId) {
      checkedIds.add(card.protocolId);
    }
  }

  // 4. 协议 ID → ProtocolEntry，过滤未勾选的
  return [...checkedIds]
    .map(id => getProtocol(id))
    .filter(Boolean);
}
```

**标签页协议永远活跃。** 即使没有卡片显式绑定，它也在跑——兜底那些不设 `protocolId` 的卡片（默认跟随标签页）。

## 四、控制方向——卡片用自己的协议编码

```
用户操作（拖滑块/点按钮/拨开关）
  │
  ▼
卡片组件 → 知道自己的 protocolId
  │  滑块卡片 protocolId="sbq" → 用 SBQ 协议的 encode 函数
  │  开关卡片 protocolId="bracket" → 用方括号协议的 encode 函数
  ▼
protocol.encode(cardId, value)
  │  bracket.encode("fan", "off")   → "[fan,off]"
  │  sbq.encode("speed", 75)        → "s75"
  ▼
serial-service.write(encodedString + "\\n")
  │
  ▼
MCU 收到 → 执行 → 回发确认
  │
  ▼
回到显示方向 → 并行解析 → (protocolId, cardId) 双键路由 → 卡片确认
```

**每张控制类卡片用自己绑定的协议编码。** 滑块绑了 SBQ → 发送走 SBQ 格式。开关绑了方括号 → 发送走方括号格式。互不干扰。

## 五、协议系统——全插件，核心无默认

> 🔥 **核心不知道任何协议。** `ProtocolRegistry` 是桌子——只管注册/查找。协议解析逻辑全在插件里。

### 架构原则

```
❌ 旧（V2 遗留）：
   src/core/ProtocolParser.ts     → 核心硬编码方括号语法
   _activeProtocolId = "bracket"  → 核心默认方括号
   → LinkDesk 预设自己是"串口调试器"

✅ 新（E4 后）：
   src/core/ProtocolRegistry.ts   → 桌子——不管协议怎么解析
   _activeProtocolId = null       → 不默认任何协议
   plugins/protocol-bracket/      → 方括号协议——独立插件
   plugins/protocol-sbq/          → SBQ 协议——独立插件
   → LinkDesk = 空壳——协议是插件之间的约定
```

**核心准入标准机审：**

| | ProtocolParser (旧) | ProtocolRegistry (新) |
|------|:--:|:--:|
| 多提供方？ | ❌ 只有方括号 | ✅ 所有协议插件 |
| 多消费方？ | ✅ 终端/工作台 | ✅ 终端/工作台 |
| 桌子不知道内容？ | ❌ 知道方括号语法 | ✅ 不知道任何协议 |
| 结果 | 🔴 迁出核心 | 🟢 留在核心 |

### 方括号协议——独立插件

```
格式:  [cardId, value1, value2, ...]
示例:
  [temp, 37.2]           → cardId="temp", fields=["37.2"]
  [fan, on]              → cardId="fan", fields=["on"]
  [gps, "116.40","39.90"] → cardId="gps", fields=["116.40","39.90"]

编码（控制方向）:
  encode("speed", 75) → "[speed,75]"
```

### SBQ 协议示例

```
格式:  单字符包头 + 数值
  s128  → cardId="adc_value",     value=128
  B72   → cardId="heart_rate",    value=72
  Q800  → cardId="beat_interval", value=800

编码（控制方向）:
  encode("speed", 75) → "s75"
```

### JSON 行协议示例

```
格式:  {"id": "chip_temp", "val": 32.5}
  → cardId="chip_temp", value=32.5

编码:
  encode("relay", "on") → '{"id":"relay","val":"on"}'
```

## 六、弹窗中的协议选择

```
┌─────────────────────────────────┐
│  卡片设置                    ✕  │
│─────────────────────────────────│
│  名称  [温度__________________] │
│                                 │
│  ── 数据 ──                     │
│  数据源 [temp ▾]  ← cardId      │
│  协议  [跟随标签页 ▾]  ← 🆕     │
│        [方括号 bracket]         │
│        [SBQ]                    │
│        [JSON 行]                │
│                                 │
│  ── 外观 ──                     │
│  ...                            │
└─────────────────────────────────┘
```

| 选项 | 行为 |
|------|------|
| **跟随标签页**（默认） | `protocolId` 不存储——数据走标签页的活跃协议 |
| **方括号** | `protocolId: "bracket"`——只收方括号解析器输出 |
| **SBQ** | `protocolId: "sbq"`——只收 SBQ 解析器输出 |
| **JSON 行** | `protocolId: "jsonl"`——只收 JSON 行解析器输出 |

## 七、cardId + protocolId——卡片的完整数据地址

```
旧:  cardId 唯一标识数据源
新:  (protocolId, cardId) 双键唯一标识数据源

MCU 发 "s128"
  → SBQ 解析器 → { protocolId: "sbq", cardId: "adc_value", value: 128 }
  → ADC 卡片 (protocolId="sbq", cardId="adc_value") → 收到 128

MCU 发 "[adc, 128]"
  → 方括号解析器 → { protocolId: "bracket", cardId: "adc", value: 128 }
  → 温度卡片 (protocolId="bracket", cardId="adc") → 收到 128

两个不同的 cardId、两个不同的协议——互不串扰。
虽然都是 "128" 这个值，但路由到了不同的卡片。
```

**多张卡片可以绑定同一个 (protocolId, cardId)：**

```
温度卡片 A ─┐
            ├── (bracket, temp) ← 方括号解析器的 temp
温度卡片 B ─┘

两个卡片同时收到同样的数据，各自独立渲染。
```

## 八、控制类卡片的真相源原则

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   硬件是真相源。用户操作 = 请求，不 = 确认。          │
│                                                     │
│   用户点开关 OFF                                     │
│     → 本地显示 OFF（乐观更新）                        │
│     → 用卡片自己的协议编码: bracket.encode("fan","off") │
│     → 发送 "[fan, off]"                             │
│     → MCU 收到、执行                                  │
│     → MCU 回发 "[fan, on]"（确认）                    │
│     → 并行解析 → (bracket, fan) = "off"              │
│     → 卡片保持 OFF（和本地一致，无变化）                │
│                                                     │
│   如果 MCU 拒绝：                                     │
│     → MCU 回发仍是 "[fan, on]"                       │
│     → 卡片回弹到 ON（以 MCU 回发为准）                │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**超时处理：** 发送后 3s 内未收到回发 → 卡片恢复到发送前的值 + toast "未收到设备响应"。

## 九、数据管道架构——大厅模式

```
                    大厅的桌子（RingBuffer + DataDispatch）
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
     协议解析器群            CardRegistry        卡片实例们
     (并行运行)             (卡片类型注册)        (工作台创建)
          │                   │                   │
     "每行数据跑             "我知道哪些卡片       "我只关心我的
     所有活跃协议"           绑了哪个              (protocolId, cardId)"
                            (protocolId, cardId)"
```

**三方都不互相 import。** 协议解析器不知道 CardRegistry 的存在，CardRegistry 不知道卡片实例长什么样——它们通过大厅的桌子松耦合通信。
