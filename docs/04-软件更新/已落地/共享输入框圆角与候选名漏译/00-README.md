## 一、案由（2026-10-06，用户实机目视 + 复问）

用户在 dev 实机（英文界面）看「默认打开方式」管理器时提两条（要点，非逐字）：

> ① 那个「过滤文件类型」框**没有圆角**，而文件树侧栏搜索区的「要包含的文件」有圆角——**难道它用的不是共享组件吗？**
> ② 英文界面下，卡头那名字已经变成 `Editor`，**下拉里那一条还是中文「编辑器」**——这是写了死代码的原因吗？插件侧即便有翻译也翻不过来？
> ③ 后续追认：「这个翻译问题**不仅仅是表面问题**」。

三条实测结论（逐条有据，见 §二）：① 文件树那个框是**插件自绘**（不走共享件），它的圆角是它自己补的——**不是本案射程**（2026-10-06 用户拍板「文件树那边的问题，暂时不管」）；② 不是死代码、也不是「插件侧翻译过不来」——**插件侧翻译是通的**（正因通，卡头才变 `Editor`），漏的是**下拉那一处从未调用 `t()`**；③ 「不只是表面」站得住：这是**两道门之间的空档**（§三）。

## 三、为什么这「不仅仅是表面问题」（门禁空档登记）

| 门 | 它管什么 | 为什么漏过本案 |
|:--|:--|:--|
| 字面量门（壳 ESLint ／ 插件 SDK 同名腿） | 引号里的中文字面量必须走 `t()` | 该位点源码里**一个汉字都没有**（`{o.label}`），扫描器无字可见 |
| 覆盖率门（`audit-i18n --strict`） | `t("…")` 用到的键，词典里有没有 | 该位点**从未调用 `t()`**，无键可查；且词条本身是全的 |
| 词典覆盖腿（SDK `own-dict-coverage`） | `plugin.json` 声明过的串有没有词条 | 同上：管「有没有货」，不管「有没有去取」 |

**空档 = 「值是运行时变量（模型字段）、本该翻译、但没人调用 `t()`」**。这一格今天**没有任何一条腿管**，而且纯静态判不了（要判它得做数据流分析）。⇒ 本案把它当**一等条目**办：登记缺口 ＋ 定一条能机械判定的替代判据（[01 §六 D2/D3](01-方案与落点契约.md)：把「谁负责翻」从约定升级为**类型上不可混用**，再用一条英文界面的行为断言钉住）。

## 五、边界（本轮明确不做）

- ⛔ **不动文件树插件的自绘输入框**（2026-10-06 用户拍板「文件树那边的问题，暂时不管」）——它是插件自己的皮，本案只补共享件。
- ⛔ **不动数据面／动作面／键名／分组／默认值／contracts**——`fileAssociation.*`、`workbench.fileAssociations`、`uiHint` 词表（仍 14 枚）、模型形状的**字段语义**全不变。
- ⛔ **不动词典内容**——`编辑器 → Editor` 本来就在（编辑器插件自己的 `i18n/en.json`）；本案只补**调用**，⛔ 不加 i18n 白名单、不改 `audit-i18n` 断言。
- ⛔ **不让共享控件自己翻**（`SelectBox` 内 `t(label)` 属否决案，理由见 [01 §四 反论表](01-方案与落点契约.md)：通用控件不能假设 label 是词典键，第三方传普通文本会被误翻）。
- ⛔ **不改插件仓**（settings／file-tree／serial-monitor 一行不动）——四处消费位自动随共享件受益。
- ⛔ **不为「万一有第三方渲染方」预造抽象**——收口只做在**已有**的四个位点上。
