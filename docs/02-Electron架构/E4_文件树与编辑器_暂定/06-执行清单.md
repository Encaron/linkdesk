> **CSS `position: sticky` 因 `.file-tree-body` 的 `overflow: hidden` 拦截不行。以下 E4V#20+i–viii 保留为历史记录。核心发现：`getAncestors` + `findStickyState` 算法留存到 E4V#20+F。

#### 第 1 步：数据层

#### 第 2 步：滚动检测

  - **Why：** 真正的滚动不在 `.file-tree-scroll`（`height:100%`=内容高、无溢出），而在 `.side-panel-content`（`overflow-y:auto`）。
  - **验证：** 滚动侧栏→`scrollTop` state 更新。

#### 第 3 步：StickyState 类型

- [x] **E4V#20+iii** `StickyState` 类型 + `StickyRow` 接口——`{ item: ExplorerItem; depth: number; position: number; height: number; startIndex: number; endIndex: number }` | `FileTree.tsx` ~15 行
  - **对标：** VS Code `StickyScrollNode<T, TFilterData>`（L1267-1272）。
  - **`position`** = 该 sticky 行在 overlay 中的 top 像素值（不是 CSS `top: i*22`——是动态计算的）。
  - **`startIndex`/`endIndex`** = 该祖先在 `flatItems` 中第一个/最后一个后代的索引（用于计算"推出"位置）。

#### 第 4 步：核心算法 `findStickyState`

- [x] **E4V#20+iv** `findStickyState(firstVisibleIndex)`——对标 VS Code 的迭代循环 | `FileTree.tsx` ~50 行
  - **算法（对标 `StickyScrollController.findStickyState` L1451-1473）：**
    1. 从 `scrollTop` 决定第一个可见节点 `firstVisible`
    2. 循环：
       a) 从 `firstVisible` 沿父链向上走——找"下一个该粘的祖先"（`getAncestorUnderPrevious` 模式——遇到上一个 sticky node 就停）
       b) 计算 sticky node 的 `position`——**对标 `calculateStickyNodePosition`（L1538-1558）**：
          - 取最后一个后代在视口中的 `relativeTop`
          - 如果 sticky 底边 > 最后一个后代底边 → 往上推（"推出"过渡）
          - 否则 sticky 钉在它该在的位置
       c) push 进 stickyNodes
       d) **计算 sticky widget 下方的下一个可见节点**——`getNextVisibleNode(stickyNode)` = `indexAt(stickyNode.position + stickyNode.height + scrollTop)`
       e) 回到 (a)，用 (d) 的结果作为新的 `firstVisible`
    3. 约束：最多 7 个 + 总高 ≤40% 视口（`constrainStickyNodes`）
  - **为什么不用旧方案：** 旧方案永远取视口第一个节点→`getAncestors`→约束→映射 depth→渲染。错误有三：
    - (a) 每个 sticky 行创建后没有重新定位"下方第一个可见节点"——导致 ancestor 链重复/遗漏
    - (b) `top: i*22` 硬编码——没有根据最后一个后代的视口位置做"推出"动画
    - (c) 没考虑 sticky 自身高度对视口的影响——边界振荡
  - **验证：** 展开多层目录→滚动→sticky 条数在 0-7 之间变化，同级目录边界不闪。

## 第 19.6 轮：IPC 文件监听频道隔离——独立频道防 watcher 串扰 🔧

> 🔥 **E4V#55f 发现——文件树 10s 缩回史诗级 bug 的治本修复。**
> **症状：** 启动 10s 后展开的目录自动缩回，twistie 显示 ▼ 但子节点消失。
> **根因：** `FileService.watchFile()` 底层 IPC 频道 `filesystem:changed` 是全局的。KeybindingRegistry 监听 `appDataDir` 的 `fs.watch` 事件和文件树的 `fs.watch` 事件走同一条 IPC 通道——所有 `onFileChange` 监听器收到所有 watcher 的事件。10s 时 Electron 写 Preferences + .tmp 文件 → 快捷键系统的 watcher 检测到 → IPC `filesystem:changed` → 文件树的监听器也收到了 → `model.refresh()` ×28 → 竞态 → 树缩回。
> **教训：** 全局 IPC 频道是缝 bug 的温床——第一个 watcher 时没问题，第二个 watcher 加入后无声崩溃。两个模块互不知道对方存在，各自看代码都看不出毛病。

### E4V#56 🔧 `watchFile` 独立 IPC 通道——每个 watcher 物理隔离

- [x] **E4V#56a** `file-handlers.ts`——频道从 `filesystem:changed` → `filesystem:changed:${watcherId}` | `electron/ipc/file-handlers.ts` ~3 行
- [x] **E4V#56b** `preload-shell.ts`——`watch` API 改为一步式：`(dirPath, callback) => Promise<unsubscribe>`。内部 `ipcRenderer.on(filesystem:changed:${watcherId})`。删 `onFileChange`/`offFileChange`/`unwatch` 三个 API | `electron/preload-shell.ts` +10/−3 行
- [x] **E4V#56c** `FileService.ts`——`watchFile` 简化——直接 `return a.watch(dirPath, onEvent)`，删手动 `onFileChange` 注册 + `unwatch` 清理 | `src/core/FileService.ts` +5/−15 行
- [x] **E4V#56d** 🔥 调用方零改动——`FoldersView.tsx` 和 `KeybindingRegistry.ts` 的 `watchFile(dir, callback)` 签名不变，返回 `unsubscribe` 不变。API 签名 = 实际行为（"我只监听这个目录"真的只收到这个目录的事件）
- [x] **E4V#56e** 防线——`FoldersView.tsx` 加路径过滤（非工作区事件直接丢弃）+ 300ms 防抖（批量文件操作合并为一次 refresh） | `views/FoldersView.tsx` +18 行

## 第 19.7 轮：Sticky 推出动画——对标 VS Code 平级目录平滑过渡 🔧

> 🔥 **E4V#20+P5 发现——sticky 在平级目录边界（bin/Release ↔ obj/Debug）剧烈振荡。**
> **根因：** 1px 的 scrollTop 差让 `getAncestors(firstVisible)` 在两个目录间反复跳变——sticky 整套换→DOM 高度回弹→scrollTop 微调→恶性循环。
> **VS Code 做法：** 不瞬间替换，旧行平滑向上推出、新行从下方顶入——"只要旧目录还有后裔在视口里，sticky 就不消失，而是被推走"。
> **对标：** `StickyScrollController.findStickyState` + `calculateStickyNodePosition`（~200 行）。

#### S2 核心：`buildStickyState`

- [ ] **E4V#57-S2** 替代当前 `stickyRows` useMemo | `FileTree.tsx` ~60 行

**算法：**
```
1. committedRef 存"当前展示的 sticky 祖先列表"
2. 从 scrollTop 读第一个可见行 → getAncestors → 候选 ancestors
3. committed === [] → 直接提交候选
4. committed 的 deepest.parent === null → 直接提交候选（根不参与过渡）
5. 候选是最 committed 的超集（进入子目录）→ 直接提交候选
6. 候选是 committed 的子集（退回父目录）→ 直接提交候选
7. 平级——committed 和候选在某层分叉：
   a. findLastDescendant(committed最深目录) → lastDescIdx
   b. stickyH = committed.length × 22
   c. push = clamp(stickyH - (lastDescIdx × 22 - scrollTop), 0, 22)
   d. push < 22？
      → 返回：旧行(_push=push, _key="old") + 新行(_key="new")
      → 不更新 committedRef
   e. push ≥ 22？
      → 更新 committedRef = 候选，返回候选（无 _push）
```
- [ ] **验证：** Release 最后一行滚到 sticky 区底部 → Release/bin 开始上滑，obj/Debug 在下面出现
