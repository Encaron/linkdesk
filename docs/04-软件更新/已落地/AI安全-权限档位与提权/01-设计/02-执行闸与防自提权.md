# 02 · 执行闸与防自提权

> 回答用户最担心的问题：**「档位如果是命令，外部 AI 是不是就能把自己改成完全访问？」**

---

## 一、结论先行

**是——如果只把档位做成一条命令。** 所以本设计不让 AI 碰「批准」：
- 档位**写**的入口在用户点击的弹窗 handler 里，不在命令面；
- 如果为了 A 判据必须注册「切档位」命令，则标 `userOnly: true`，AI 正门（`runShellCommand`）**统一拒调**；
- 配置层已有第二道锁：`ai.*` 键对所有 AI 写命令拒写（`settingsCommands.ts:41`）。

---

## 二、三层锁（缺一不可）

| 层 | 锁 | 落点 | 挡什么 |
|:--|:--|:--|:--|
| **L1 配置锁**（已存在） | AI 写 `ai.*` 直接被拒（`blocked`） | `src/core/commands/shell/settingsCommands.ts:41,412-419` | AI 用 `setConfiguration` / `clearConfiguration` 改档位 |
| **L2 命令锁**（新增） | `userOnly` 命令在 AI 出口一律 `EPROTECTED` | `electron/services/aiBridge/whitelist.ts` 的 `runShellCommand` | AI 用 `exec` 调 `aiPolicy.setMode` / `aiPolicy.resetToDefault` |
| **L3 批准锁**（新增） | 升档只能由用户点确认框完成；AI 只有 `requestElevation`（只问不答） | `policy/elevation.ts` ＋ 池 `DialogHost` | AI 自己批准、或伪造批准结果 |

> L2 的判据是**命令元数据**，不是 id 名单：`registerCommand({ ..., userOnly: true })`。名单会漏（改名就绕过），元数据跟着命令走。

---

## 三、执行闸（唯一出口）

现状：`exec` 与 `notifyAction` 已经共用 `runShellCommand`（`whitelist.ts:145-149`），这是本档最好的地基。改成：

```ts
async function runShellCommand(ctx, commandId, args) {
  const risk = riskOfCommand(commandId);            // 合并：壳表 > manifest.risk > 兜底 R1
  const policy = await ctx.policyState();            // 读 ai.policy.mode（主进程内存缓存）
  if (isUserOnly(commandId)) throw coded("EPROTECTED", ...);  // L2
  const decision = decide(policy.mode, risk);        // 纯函数
  if (decision === "deny") throw coded("EPOLICYDENIED", ...);
  if (decision === "ask") await askUser(ctx, what, why);      // 复用唯一弹框出口
  return ctx.shellRequest(IPC.commands.execute, [commandId, undefined, ...args]);
}
```

- `install` 同理：风险固定 R2，`decide` 为 `ask` 时走 `askUser`，为 `deny` 时 `EPOLICYDENIED`。
- **R3 在 `auto` 档仍 ask**：`install` 是否算 R3 见 D9（建议仍问）；`update.openUpdateFlow` 固定 R3。
- **`full` 档不问**：但账本照记；R3 执行前仍要求命令自带 `description`（AI 可解释）。

## 四、`requestElevation`（AI 唯一的「升档」通道）

```ts
requestElevation: {
  name: "requestElevation",
  kind: "write",
  params: [
    { name: "mode", type: "string", required: true },   // read|ask|auto|full
    { name: "reason", type: "string", required: true }, // 为什么需要
    { name: "scope", type: "object", required: false }, // 预留：命令/风险级范围
  ],
  run: ...
}
```

流程：
1. AI 调 `requestElevation` → 主进程弹**提权请求框**（复用 `askUser` 的 `dialog:confirm` 通道；富文本走 `confirmContent`）。
2. 框内文案：当前档 → 目标档、原因、将获得什么（风险矩阵摘要）、**「批准后常驻，直到你在设置里关掉」**。
3. 用户点「批准」→ 壳 handler 写 `ai.policy.mode`（`source:"user"`，`via:"elevation"`）→ 返回 `{ granted:true, mode }`。
4. 用户点「拒绝」/ 超时 → `{ granted:false, code:"EUSERDENIED" }`，档位不变。
5. **批准动作不经命令面**：它写在 shell 的 dialog 应答处理里，AI 没有可调用的「批准」op。

> 用户 D2 已拍板「完全访问常驻」：提权框必须把「常驻」写进文案，并给「打开设置」的入口。

---

## 五、fail-closed 与超时

- 用户不在场（10 分钟无应答，沿用 `ASK_TIMEOUT_MS=600_000`）⇒ `ESHELLTIMEOUT`，动作**不执行**。
- 读不到策略（配置损坏/未初始化）⇒ 按 **`ask`** 处理（最保守的可执行档），⛔ 不按 `auto`/`full` 放行。
- 策略读两次不一致（变更竞态）⇒ 以**执行时点**那次为准，并在账本记 `policy_raced:true`。
- 客户端超时与「人在犹豫」的相位区分沿用 `AI#60`（`phase("ask-user")`），⛔ 不让 AI 把「在等人」当「失败」重试。

---

## 六、错误码

| code | 含义 | AI 应怎么反应 |
|:--|:--|:--|
| `EPOLICYDENIED` | 当前档位不允许 | 可调 `requestElevation`（带理由），⛔ 不要原样重试 |
| `EPROTECTED` | 命令被标 `userOnly`，AI 永远不可调 | 提示用户去设置页；⛔ 不要重试 |
| `EUSERDENIED` | 用户点了拒绝/关框 | 尊重拒绝；可换方案，⛔ 不要连环弹 |
| `ESHELLTIMEOUT` | 无人应答 | 视为未发生；⛔ 不要立刻重试（用户可能刚走开） |

---

## 七、为什么不在渲染层加锁

- 池（renderer）可被插件 UI/第三方设置页替换，「锁」必须住主进程（照插件权限系统铁律 1：执行点只在主进程）。
- 池只负责**画**确认框；批准结果的 settle 在壳侧（`DialogHost` 只回传动作类型，壳侧 settle——既有机制，`DialogHost.tsx:6`）。
