## 〇、收口的对象——这一类问题的定义（先钉死，后面全靠它）

> **问题类**：`一个扁平的全局名字表（Map / JSON 字典 / i18next namespace / 前缀约定），多方都能往里写名字，写时不核对"这名字是谁的"，撞了不报错——最多一句 console.warn；而「被覆盖」这件事，受害方永远收不到通知。`

**「公共花名册」的五条识别特征**（照 30 号档的**同形判据**，四条全中才算同形）：

| # | 判据 | 反例（不同形的样子） |
|:--:|:--|:--|
| 1 | 名字空间是**扁平的**（名字里没有天然归属） | `pluginId:viewId` 复合键（自带归属） |
| 2 | **多方都能写入**（宿主 ＋ 官方插件 ＋ 第三方插件） | 只有宿主写、插件只读 |
| 3 | 写的时候**没有归属校验**（不检查"这名字是谁的"） | 注册时核对 pluginId 并拒绝 |
| 4 | 冲突**静默**（不报错；最多 `console.warn`） | 有用户可见的提示 / UI 高亮 |

🔴 **第 4 条是关键**：`console.warn` **对用户不可见，对「被覆盖的那一方作者」也不可见**——因为他在自己机器上**没装对方插件**，一切正常。**「被覆盖」这件事，受害方永远收不到通知。**

### 〇c.2 修订后的判据（**本轴此后一切结论以此为准**）

**🔴 根治的定义（三层同时闭合，且第 ① 层要求「零例外」）**：

| 层 | 修订后的闭合条件 |
|:--|:--|
| **① 归属层（预防）** | **规则零例外**：**宿主保留的名字不许占；凡自己写的名字必须带 `<pluginId>`**。⇒ **官方插件里所有不合规的名字一律改名**（不是"登记例外"）。这样第三方作者照抄 VS Code 时，**在他自己的仓库里就会被自己的门禁当场拦下**，不必等装上软件才发现 |
| **② 仲裁层（兜底）** | 静态判不了的那一类（**两个不同第三方**、**运行时动态拼名**）由**运行时归属仲裁**兜：**首撞者保留 ＋ 后来者降级不覆盖 ＋ `console.error` 点名双方**。⇒ 这不是安慰奖：**运行时是唯一能看见"这一台机器上到底装了谁"的地方** |
| **③ 迁移层（体验不变）** | 任何改名都必须**同笔写迁移**：用户 `settings.json` 的值 / `app.theme` 选的主题 / 用户自定义快捷键 / 官方目录条目，**逐类搬运**。⇒ **判据 = 逐项操作实测：改名前后，点每一个设置项、按每一个快捷键、选每一个主题，行为一致** |

**🔴 唯一保留的黄灯**：**i18n 字典键**（键**可以合法住在应用级字典**——官方 `settings` 的 t() 键一个都不在自己仓，全在 `lang-defaults` ⇒ 插件仓**看不见**别人的键与宿主字典）⇒ 硬判必出假红。**这一条如实写成黄灯，不假装能判。**

**🔴 不许改名（或改名无意义）的三类**——它们是**全局概念名**，不是"没主"：
1. **文件关联的扩展名**（`editor` 声明了 41 个：`.ts` / `.md` / `.py` …）——`.ts` 不可能是"编辑器的 ts"，且 [FileAssociationService](../../../../../src/core/services/files/FileAssociationService.ts) 的**设计就是多插件同扩展名**（"打开方式…"选择器消费全部）；
2. **语言定义的扩展名**（`python` 的 `.py` / `.pyi`）——同上，`.py` 就是 `.py`；
3. **语言包的语言码**（`lang-defaults` 的 `zh` / `en`、`lang-test-ja` 的 `ja`）——语言码是国际标准标识符，不是命名空间。

**🔴 上位约束的修订（逐字替换旧措辞）**：
> 旧：「做完整个系列任务后，我除了版本号外，**不要有任何 UI 变化**」
> **新（以此为准）**：**操作体验零变化** —— 点每个设置项仍能切换/正确响应 · 每个快捷键仍能触发 · 每个主题仍能选、仍能跟随 · 翻译仍能切换；**名字可以变**，**用户已存的值不许丢**。⇒ 两条旧禁区据此**解除**（「不改存量名」），新增一条**更硬**的禁区：**改任何名字必须同笔写迁移，且必须逐项操作实证**。

## 一、真根因——三层，不是「谁起错了名」

> 这一节是**给后面每一棒的方法论底座**。结论：**名字没起坏，是「谁的名字」这件事被寄托在「取名自觉」上——账本要么没有，要么只用来打印一行字。**

### 层 1（机制）——这些名字空间在一个进程里是**扁平的全局表**

| 名字空间 | 载体 | 出处 |
|:--|:--|:--|
| 命令 id | `Map<string, Command>` | `src/core/registry/commands/CommandRegistry.ts:42` |
| 设置键 | `Map<string, ConfigurationContribution>` ＋ `Map<string, string>` 归属表 | `src/core/registry/ConfigurationRegistry.ts:108-109` |
| 主题 id / 配方 id | 两张 Map（**同一个概念两本账**） | `src/core/registry/appearance/ThemeRegistry.ts:22,29` ＋ `src/core/services/ui/ThemeEngine/registry.ts:27` |

### 层 2（接口）——契约面按「每个插件自己一份」设计，投进「所有插件共处一个运行时」

`plugin.json` 的 `contributes.*` 与 `window.linkdesk.*` 都是**照着 VS Code 的扩展契约设计的**——在 VS Code 的世界里，每个扩展的贡献**最终都落进同一个扁平表**（这也是 VS Code 的真实形状）。LinkDesk 沿用这套设计，同时继承了它的**未设防部分**；而 LinkDesk 又多了一样 VS Code 没有的东西：**宿主自己的贡献用的是普通命名**（见层 3）。

### 层 3（守门）——**归属只有两种表达方式，而两种都不设防** 🔴

| 表达方式 | 谁在用 | 为什么等于没设防 |
|:--|:--|:--|
| **① 表里记了归属，但只用它打印一行 warn** | 设置键（`_configKeyOwner`，`ConfigurationRegistry.ts:109,123-130`）· 主题配方（`recipeOwners`，`ThemeRegistry.ts:32,209`）· 命令（`_pluginCommands`，`CommandRegistry.ts:43,62-67`） | warn **只在覆盖发生的那台机器**上打印；覆盖照旧发生（"所有权归后注册者"），**没有任何一处降级或拒绝** |
| **② 表里根本没有归属，靠名字前缀「推」出来** | 命令 id 的运行时路径（`commandId.split(".")[0]`，`CommandRegistry.ts:150,186`）· 池命令属主（`commandOwnerId()`，`electron/preload-pool/commands.ts:36-39`）· 插件语言包（`ns = pluginId`，`i18nResources.ts:28`） | **名字既是标识符又是身份声明，而没有任何一处核对两者是否相符** |
| **③ 🔴 宿主自己的名字用的是普通命名** | 宿主伪 pluginId = `"app"`（`src/core/services/plugins/PluginStateService.ts:17`）· `"appearance"`（`src/App/config/appearance.ts:55`）· `"update"`（`src/App/config/update.ts:22`）· 宿主命令前缀 `workbench.*` / `core.*` / `app.*` / `update.*` / `view.*` / `theme.*`（实测 64 条） | 这些 pluginId **全部通过 schema 的 `pattern`**（只禁 `ldk-`）⇒ 第三方插件**可以合法地把自己的 `pluginId` 取成 `app`**，此时与宿主**同一个 owner**，**连 warn 都不会响**，且它的配置会 `Object.assign` **合并进宿主的外观贡献**（`ConfigurationRegistry.ts:133-137`） |

> **③ 是这一轴最值钱的一条**：它与样式那条 `ldk-` 规则**是同一件事的两个面**——**身份层早就设防了（`pluginId` schema `pattern` 禁 `ldk-`），问题是「名字层」没跟上**。宿主保留的是 `ldk-` 前缀，但宿主**自己用的名字**（`app` / `appearance` / `update` / `workbench.*` / `core.*`）**一个都没进保留面**。

### 一句话根因（后面每一棒收尾都要能复述这句）

> **不是名字起坏了，是「谁的名字」被寄托在「取名自觉」上——账本要么没有，要么只用来打印一行字，而宿主自己的名字和第三方名字长着同一张脸。**

**⇒ 由此推出的两条纪律（本轴全部遵守）**：
1. **归属必须结构性**（判据能独立判定，不查表、不靠白名单）——**「宿主保留名账」是唯一被允许的表，且它必须是「生成式 + 双向对账」的**（先例已存在，见 §二.6）；
2. **判据必须证明自己活着**（有 `--self-test` 正负控、自测接线、负控真红）——否则下一把尺子还会漏。

### 2.1 🔴 ① 命令 id——「归属是**从名字推出来的**」（本格新发现，30 号档未记）

**两条注册路径给出**两种不同的归属**，而它们写进同一本账：

| 路径 | 归属怎么来 | 出处 |
|:--|:--|:--|
| **plugin.json 声明** | **真 `pluginId`** | `src/pluginLoader/contributions/contributions.ts:65` |
| **运行时注册**（`commands.registerCommand`） | 🔴 **`commandId.split(".")[0]`——名字的第一段** | `src/core/registry/commands/CommandRegistry.ts:150`（池元数据）· `:186`（壳侧本地）· `electron/preload-pool/commands.ts:36-39`（属主推导，同一约定） |

**由此产生三个可判定的真害**：

1. **覆盖告警会被整段吞掉**：覆盖检测是 `for (const [pid, ids] of _pluginCommands) if (ids.has(id) && pid !== pluginId)`（`CommandRegistry.ts:62-66`）。两个插件都**运行时注册** `acme.doThing` ⇒ 两者的推导归属都是 `"acme"` ⇒ `pid !== pluginId` **恒 false** ⇒ **静默覆盖，一声不响**。
2. **注销会牵连别人的命令**：`unregisterCommands(pluginId)` 的实现是 `ids.startsWith(pluginId + ".")` 后整片删（`electron/preload-pool/commands.ts:82-87`）⇒ 插件 `beta` 注册的 `acme.foo` 会被**卸载 `alpha`** 时一并摘掉。
3. **`on-command` 激活会去 import 别人**：命令 handler 池内 miss 时，池按 `commandOwnerId(commandId)` **去激活那个插件**（`electron/preload-pool/commands.ts:45-61`）⇒ 名字的第一段被当成**身份**使用。

**存量读数**（官方 18 仓，`plugin.json` 静态声明面）：**35 个独立命令 id**，**跨插件共写 0**；其中**带本插件归属前缀 14 / 不带 21**——不带的 21 个**全部属于 `file-tree`**（`explorer.newFile` / `explorer.copy` / `revealInExplorer` …，是**照抄 VS Code 的功能命名空间**）。

> 🔴 **为什么 B 不能用「抛错」**：`ConfigurationRegistry` 注释自述「**parseContributions 没有 try/catch，抛错会导致整个插件加载失败**」（`:120-121`）⇒ 一个第三方插件的重名会让**整只插件装不上**，**比现在更坏**。⇒ B 的形态只能是 **「首撞者保留 ＋ 后来者降级为不覆盖 ＋ 明确出声」**——**比抛错温和、比 warn 有效**（它真的改变了结果，不只是打印）。

**禁区（用户与本系列共同定，逐格照抄）**：
1. 🔴 **不许一律把 `console.warn` 改成 `throw`**（§2.7 的顾虑：会让整只插件装不上，**比现在更坏**）。
2. 🔴 **不许动已设防的四处**（它们是样板，不是问题）：数据推流唯一路径 `IpcBridge.broadcast` · `pluginId` schema `^(?!ldk-)…` · **视图 id 复合键 ＋ fail-loud** · 快捷键冲突的 UI 高亮。
3. 🔴 **不许把 i18n 键硬判成红**（跨仓不可判；硬判必出假红）。
4. 🔴 **不许引白名单 / 基线 / 棘轮** —— 优先**结构性判定**（「宿主保留名账」是唯一例外，且它**生成式 ＋ 双向对账**，不是手抄豁免表）。
5. 🔴 **不许改机制**：只加归属与判据，**不重构注册表、不换数据结构**（尤其**不许动 `commitTokens` / `theme:changed` 广播链**——[29 号档](../样式命名空间归一化/29-主题系统保护条款.md) P1）。
6. 🔴 **上位约束（§〇c.2 修订后口径，逐字照此）**：**操作体验零变化** —— 点每个设置项仍能切换/正确响应 · 每个快捷键仍能触发 · 每个主题仍能选、仍能跟随 · 翻译仍能切换；**名字可以变**，**用户已存的值不许丢**。⇒ 含**主题统一调控 / 字体 / 翻译**三条横切机制零回归。**只做加法且名字一次定对** · 对外宽容（第三方可自画 / 可自定，只黄灯不拦；跟随官方是**奖赏不是枷锁**）。
7. 🔴 **【§〇c 新增】改任何名字 ⇒ 必须同笔写迁移，且必须逐项操作实证**（用户 `settings.json` 的值 / `app.theme` 选的主题 / 用户自定义快捷键 —— 逐类搬运）。**只改名字不写迁移 = 半成品，直接判不合格。**
8. 🔴 **【§〇c 新增】不许把「全局概念名」当"没主"去加前缀**：文件关联扩展名（`.ts`）· 语言定义扩展名（`.py`）· 语言包语言码（`zh`/`en`/`ja`）—— 加前缀 = 语义错误。

## 五、收口的定义与判据（**1.50 执行**）

### 5.1 什么叫「收口」（**四层**同时闭合，缺一层都不算 —— §〇c 修订后为四层）

| 层 | 闭合条件 | 谁负责 |
|:--|:--|:--|
| **① 归属层**（名字自带归属 / 宿主名字有保留账） | 每条花名册都有**结构性的归属表达**：**宿主保留名账**（生成式 ＋ 双向对账 ＋ 进 SDK）＋ **插件归属前缀**。规则一句话可复述：**宿主保留的名字不许占；凡自己写的名字必须带 `<pluginId>`**。🔴 **零例外**（存量全部改名 —— §〇c.1 撤回"不改名"） | 1.31–1.40 ＋ 1.42–1.48 |

## 六、残余边界（诚实清单——**1.50 报告必带，一条不许省**）

> 这一节是**本方案与「宣布大获全胜」的分界线**。用户 2026-09-16 的原始追问就是「**是不是真收口了，还是还有根因藏着**」——答案写在下面。

1. **机制层未隔离**：本轴收口靠的是**归属约定 ＋ 门禁 ＋ 运行时仲裁**，不是**构造上不可能**（对照：视图 id 用复合键，那是构造性的）。⇒ 表述纪律：说「**事实上不会发生**」，不说「**不可能发生**」。
2. 🔄 **【§〇c 修订】** ~~存量名字不改名~~ ⇒ **存量全部改名 ＋ 迁移**（官方 ≈ 122 处，逐插件清账面见 §〇c.4）。**新的残余边界**：改名本身**会改变用户可见的键名文字**（设置页主标签显示的就是键名，实测 `SettingRow.tsx:65` 的 `{configKey}`）⇒ **这是明文接受的取舍**：**功能与取值不变，名字会变**（用户 2026-09-16 原话：「**名字变是名字变，只要功能不变我还能使用它的功能**」）。
3. **静态门禁只看得见静态声明**：运行时用字符串拼出的 id（`` `${prefix}.${action}` ``）理论上可绕。⇒ 本轴**不加运行时拦截**，由 §八 的探针把这一条列为「**探针覆盖不到**」并记录已知形态。
4. **i18n 天然跨仓不可判**：键可以合法住在应用级字典（官方 `settings` 的 t() 键**一个都不在自己仓**，全在 `lang-defaults`）⇒ **只黄灯 ＋ 文档**，**不许判红**。⚠️ 本轴**不解**这一条（它要改「`t()` 键 = 中文原文」这条**硬约束 2** 级的架构决定，属另一件事，**不许假装在命名清理里顺手做掉**）。
5. **宿主保留名账需要一次「生成」且必须防漂移**：账是生成式的，但**宿主新增名字时若忘了重跑生成器**，账就陈旧。⇒ 对策 = **双向对账门禁**（照抄 `check-reserved-names-doc-sync.mjs` 的形状：账 ↔ 实况两侧都查，任一侧多出就红）。
6. **`pluginId` 唯一性依赖硬约束 11**（发布后 id 不可变）。⚠️ 同族账：宿主伪 pluginId `app` / `appearance` / `update` **今天不设防**（第三方可合法取名 `app` ⇒ 同 owner、连 warn 都不响）。**处置归 1.33/1.34**（候选：schema `pattern` 加禁 ＋ SDK `validate` 报点）。
7. **键盘 chord 串的静默死键不属本轴**（`normalizeKey` 把 `ctrl+k ctrl+h` 打乱成 `ctrl+h+k ctrl`，记忆 `keybinding-system-complete` 末节**已立案**）：它是**单方的解析缺陷**（不是「多方共写一本花名册」），**本轴只登记、不动手**。
8. **「已设防」的四处不被本轴改动**：数据推流唯一路径 · `pluginId` schema `ldk-` 禁令 · 视图 id 复合键 ＋ fail-loud · 快捷键冲突 UI 高亮。它们是**样板**，任何一轮若顺手去"统一风格"就是破坏。
9. **不回答「哪块宿主 UI 该变成插件」** —— 那是架构问题（另有主线）；本轴只把**名字边界**做成机械可判。**不许把「命名干净」当成「已经插件化」**。
10. 🔄 **【§〇c 新增】「改名的收益是面向未来，不是修当前故障」**：官方插件今天**并没有实际打架**（用户原话：「**我知道目前已有插件在这方面似乎并没有什么冲突，这是因为这些插件都是一脉相承的**」）。⇒ 本轴的收益是**给第三方作者一个机器能判的边界**；**报告里不许把它写成"修了 N 个 bug"**。⚠️ 例外：§〇c.3 的**三条活体**（`file-tree` 借 `editor.*` 与共享组件 `inputFocus`、宿主兜底 id 无主）是**真实存在的跨方冲突**，可独立计。
11. 🔄 **【§〇c 新增】三类「全局概念名」永久豁免**：文件关联扩展名 · 语言定义扩展名 · 语言包语言码 —— 它们**不是"没主"，是"本就不该有主"**。⇒ 报告里要写清这条**不是欠账**，避免下一个 AI 又去"清"一遍。

### 10.3 🔴 宽容度模型（记忆 `plugin-repo-gate-model` §十——本轴一切「判红」必须先过这一节）

### 10.5 🔴 上位约束二：[主题系统保护条款](../样式命名空间归一化/29-主题系统保护条款.md)（冲突时以它为准）

### 10.6 一句话结论

> 本方案在**层 3 / 层 4** 上是「**能机械判的全机械判，不能的如实登记**」。**唯一的机制创新是「宿主保留名账」——而它不是发明，是把样式侧已经跑通的 `reserved-class-names.json` 模式推广到非样式面**。
> 🔄 **§〇c 修订后的收口口径**：**根治 = 规则零例外（官方仓需改处全 0）＋ 运行时仲裁兜住静态判不了的那类 ＋ 每一处改名都带迁移并逐项操作实测**。**唯一如实留下的黄灯是 i18n 字典键**（跨仓不可判 —— 它要动「`t()` 键 = 中文原文」这条硬约束 2 级的架构决定，**不在命名清理的射程内**）。
> 🔴 **表态纪律**：本轴的收益**主要是面向未来的**（给第三方作者一个机器能判的边界），**今天官方插件并没有实际打架**（用户原话「这些插件都是一脉相承的」）⇒ **报告里不许把它写成"修了 N 个 bug"**；可独立计的只有 §〇c.3 的**三条活体**。
