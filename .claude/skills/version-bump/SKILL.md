# Version Bump（版本号更新仪式）

> 2026-08-31 用户定案：版本号策略对标 VS Code——**MAJOR 由「生态兼容」驱动，不由「功能」驱动**。
> 判据来源：[06-主软件更新/02-产品身份与版本.md](../../../docs/02-Electron架构/E6_插件生态与发布/06-主软件更新/02-产品身份与版本.md) §2.3-§2.5 + 2026-08-31 拍板扩展。

## 〇、多轴模型——先分清「改的是哪根轴」（2026-09-06 拍板）

**版本号是多个独立轴，不是一条线。** 软件整体升级 ≠ SDK/契约升级——它们服务不同人群、发布点不同（GitHub Release vs npm）。**动手 bump 前先回答：这次变更动了「谁的面」？**

| 轴 | 服务对象 | 发布点 | 版本维护 |
|:--|:--|:--|:--|
| **软件本体**（根 `package.json`） | 用户 | GitHub Release tag | 本 skill 判定 + 发布门禁（#57.15d） |
| **@linkdesk/contracts** | 插件作者（拿类型） | npm | **发布者手工维护**——2026-09-06 拆焊反向 E5.8#22.6，版本轴独立于壳（壳升级≠契约升级）；只随 `window.linkdesk.*` API 面变而升 |
| **@linkdesk/plugin-sdk** | 插件作者（构建） | npm | 同上，手工维护；依赖 `^0.1.x` contracts |
| **create-linkdesk-plugin** | 插件作者（建工程） | npm | 手工维护；**模板改了必须发版**——不发 = 作者拿到的骨架是旧的（`check-npm-release` 黄灯盯） |
| **@linkdesk/ui** | 插件作者（共享 UI 零件） | npm | 手工维护；壳 `src/components/shared/` 是单源，改组件即动了本轴 |
| **@linkdesk/plugin-docs** | 插件作者（读文档） | npm | 🔴 **第五根轴（E6#105l 立）**：内容变即 PATCH；表面 = 生成物 `packages/plugin-docs/docs/**`（真源 `docs/03-插件制造/**`，改了不重生成 ⇒ `docs:check` 先红）。基线待首次真发后 `release:mark` 落 |
| **插件自身 version**（各 plugin.json） | 作者自己 | marketplace | 作者维护，更新机制消费 |

**判例**：优化拖出动画 → 只动软件轴（用户升级，不碰 npm）；优化 `linkdesk.*` API 面 → 作者轴（升 contracts/sdk 真发 npm，软件轴可不动）。**每轴变更仍必须跑该轴检测**——拆焊只拆错轴的「版本相等」断言，检测一条不撤（memory [[version-axes-separated]]）。

**🔴 E6 结束前恒 0.x（2026-09-06 用户拍板）**：内测期所有轴留 0.x 线，**v1.0.0 等真实上线再说**。0.x 补丁向后兼容走 patch 位、破坏性走 minor 位。**npm 发版 ≠ 软件 bump**——@linkdesk/contracts、@linkdesk/plugin-sdk 升版真发时根 `package.json` 保持不动（本次实证：npm 两包发 0.1.1，壳仍 0.1.0）。

## 什么时候用

用户完成测试后说「更新版本号 / 发版 / 上架」→ 调用本 skill。**前置条件：本次变更已测试通过**（commit ≠ 完成）。未测试不 bump。

**🔴 防遗漏强制出口（2026-08-31 用户要求）**：任何软件侧用户可见变更（新功能 / 修复 / 破坏性重构）**完成验证后、提交前，必须走本 skill 判定版本号，并询问用户确认**。即使本次判定「不 bump」（纯文档/内部零行为变化），也要在报告里明说「本次不 bump，理由：…」。**禁止「代码更新上去了，版本号没更」**——代码提交与版本号 bump 同批完成。

## 一、核心判据表（先判定类别，再算数字）

### 1.x 及以后（正式版，标准 SemVer）

| 类别 | 定义 | 触发判据（任一满足即该类） | 数字 |
|:--|:--|:--|:--|
| **MAJOR**（1→2） | 破坏性平台变更——已发布第三方插件无法运行/必须改代码 | ① `window.linkdesk.*` API 破坏性改动（删/改签名且无法兼容层兜底）② 插件 manifest/贡献点 schema 破坏 ③ 用户数据格式不兼容（workspace.json/配置需手动迁移）④ 运行时架构推倒（用户必须重装） | `major+1`，minor/patch 归 0 |
| **MINOR** | 向后兼容的功能新增 | 纯新增 API/贡献点/能力/UI，旧插件零影响 | `minor+1`，patch 归 0 |
| **PATCH** | 修复 | 崩溃/安全/性能回归/关键 bug，零新功能 | `patch+1` |

### 0.x 阶段（当前，开发期）

| 变更 | 结果 | 说明 |
|:--|:--|:--|
| 向后兼容（新功能/修复，**不**破坏已发布插件） | `0.x.(y+1)` | 0.x 不承诺 API 稳定，一切向后兼容变更走 patch 位（对标 semver 官方：0.y 里 minor 位留给破坏性） |
| 破坏性（已发布插件/数据格式不兼容） | `0.(x+1).0` | minor 位承担 MAJOR 职责（02 §2.5 已定） |
| 满足 1.0 三条件 | `1.0.0` | 0.x 直接跳 1.0（对标 VS Code 0.10→1.0），不走 0.10→0.11 硬攒 |

### 1.0 上架判定（三个条件**同时**满足才跳 1.0.0）

1. **插件生态闭环**——E6 全部完成（发布/安装/卸载/市场/更新机制/出厂插件），第三方作者能独立写出插件（10 分钟第一个插件验收标准）
2. **壳 API 冻结**——`linkdesk.*` 面宣布稳定，不再随意增删改（新增可以，破坏不行）
3. **数据格式冻结**——workspace.json / 配置 schema 稳定

> **E6 结束 ≠ 1.0（2026-08-31 用户定案）**：E6 完成只满足条件 1（机制全通）。E6 结束后仍是**生态验证期**——插件上市（官方目录+多源）、软件联网测试（更新机制等实机）、API 补充（真实第三方作者暴露缺口→补 API）——期间 API 还在生长，**条件 2/3 未满足，不跳 1.0**。必须完整经历生态实弹验证、API 面稳定后才 1.0。

> 1.0 ≠ 功能齐全，= **敢承诺**。对标 VS Code：2015 年首秀到 2016 年 0.10→1.0，中间是近一年生态验证（1000+ 扩展、2M 安装、狗食自己的 API）才敢宣布 API 稳定。

### 2.0 界限（LinkDesk v2，非旧串口助手 v2）

**一句话：当「升级会让已发布的第三方插件跑不了/要改代码」成为事实，才升 2.0。** 功能加再多都不升——VS Code 十年停在 1.x（2026 普通用户仍在 1.105.x，2.0.0 只做过灰度预览、从未全量上）。升 2.0 前必须先判断能否兼容层兜底（旧 API 继续可用）→ 能兜底就不升；兜不了才发布 2.0 + 迁移文档 + 插件作者过渡期。

**🔴 数到 2.0 前先问：「这为什么不能做成增量的？」（2026-09-04 用户拍板，VS Code 实证）**
VS Code 十年几百版不升 2 的根因：**一切新能力增量进、旧格式永续兼容、从不用「拒绝安装」逼适配**——旧插件不声明新字段就照跑，只是用不了新能力；`engines` 让插件自报目标宿主，宿主对旧契约长期兜底。对照到 LinkDesk：

- **能增量 + 默认值兜底 → MINOR（1.x），不是 2.0**。哪怕改动是「所有插件须声明新字段才能用新能力」——只要老插件不声明仍装得上、跑得动，就是 1.x 增量，不是 schema 断裂。
- **「拒绝安装 / 强制全员声明」= 自选 2.0**：拒绝 = 逼所有下次要发布的作者同时适配 = 真 MAJOR。祖父条款只能减痛、不能把 2.0 降回 1.x；只有「祖父 + 不拒绝 + 增量解锁」才留在 1.x。
- **2.0 应当 = 兼容失败的症状，不是随手选的档位**。唯一必须 2.0 的情形：默认值填不了、旧插件留着会出事（真数据/schema 断裂、必然冲突）→ 兼容层兜不住才动用拒绝 + 大版本。

## 二、变更 → 类别映射表（逐项对照本次变更清单）

| 本次变更包含 | 映射类别 |
|:--|:--|
| 删/改已发布 API 签名（无兼容层） | MAJOR |
| 插件 manifest / 贡献点 schema 破坏 | MAJOR |
| workspace.json / 配置 schema 不兼容 | MAJOR |
| 运行时架构推倒 | MAJOR |
| 纯新增 API / 贡献点 / 能力 / UI | MINOR |
| 纯 bug 修复 / 安全 / 性能回归 | PATCH |
| 仅文档 / 注释 / 内部重构零行为变化 | 可不 bump |

**混合变更**：取最高类别（修复+新功能 → MINOR；新功能+破坏 → MAJOR）。

## 三、流程（4 步）

**Step 1 读当前版本**：`package.json` 的 `version` 字段（唯一真相源，02 §2.3）。同时确认上一版 Git tag：`git tag --sort=-v:refname | head -3` 或最近 `vX.Y.Z`。

**Step 2 分类**：拿本次变更清单逐项过映射表 → 取最高类别。检查是否满足 1.0 三条件（若在 0.x 且全满足 → 直接 1.0.0）。

**Step 3 算新版本号**：
- 0.x 向后兼容：`0.x.(y+1)`；0.x 破坏性：`0.(x+1).0`
- 1.x PATCH：`patch+1`；MINOR：`minor+1, patch=0`；MAJOR：`major+1, minor=0, patch=0`
- 校验：新版本 > 上一版（用 `compareVersions`，02 §2.5 算法）；不许倒退或重复

**Step 4 输出决议**（固定模板，含精确数字 + 原因）：

```
📦 版本号更新决议
- 当前版本：<0.1.0>（package.json）
- 更新类别：<MINOR / PATCH / MAJOR / 0.x 向后兼容 / 1.0>
- 新版本号：<0.2.0>
- 判据：本次变更 = <逐项列变更 → 类别映射> → 类别判定
- 数字：<计算规则说明，如「0.x 向后兼容 → patch+1」>
```

## 四、更新落点（类别判定后，改这些文件）

1. **`package.json`** `version` —— 唯一真值，改这里
2. **`electron/product.json`** `version` —— 开发期可留占位；发布期由壳发布脚本（E6#57.15a）写入，**不手写第二份**（02 §2.3：任何地方不手写第二份版本号；`app.getVersion()` = 唯一运行时来源）
3. **CHANGELOG.md** —— 每次 bump 写一条：`## v0.1.1（YYYY-MM-DD）` + 类别清单（feat/fix/breaking）（02 §2.6，对标 VS Code）
4. **Git tag** —— `vX.Y.Z`（无 v 前缀的版本号比较，02 §2.4），Release body = 该版发行说明（05 数据源）

> **🔴 发布门禁（02 §2.6，E6#57.15d 机械校验）**：发布时 `npm run publish` 自动断言——① 当前版本号 > 最近 release tag ② `package.json` = `product.json` = Git tag `v{version}` 三处一致；任一不符 → 拒绝发布。**本 skill 负责决策层（判定类别 + 算版本号 + 用户拍板），门禁脚本负责校验层（机械卡死）——两层共同防「更新上去了版本号没更」。**

> 发版 = 生成 GitHub Release 必须 bump（tag 需要）。不对外发版的内部迭代不 bump，但不要为此跳过发版仪式——完成一轮用户可见变更就 bump，保持「发布即 tag」节奏。

## 五、铁律

- **未测试不 bump**——测试通过是前置，commit ≠ 完成
- **版本号不手写第二份**——package.json 是唯一真相源，product.json 由发布脚本写
- **0.x 阶段不承诺向后兼容**——但破坏已发布插件仍算破坏性（升 minor 位），不默默 patch 掩盖
- **1.0 前不 bump MAJOR**——0.x 里 MAJOR 职责由 minor 位承担
- **MAJOR 是最后手段**——每次 MAJOR bump = 生态断裂（所有已发布插件作者要适配），能兼容层兜底就绝不升
- **🔴 数到 2.0 先问「能不能增量」**——能增量 + 默认值兜底 = MINOR；只有默认值填不了 / 旧插件不安全（真兼容失败）才 2.0。别拿「让生态现代化」当 2.0 理由——**2.0 是兼容失败的症状，不是政策选择**（2026-09-04 用户拍板）

## 六、示例

**场景 A（当前 0.x 新功能）**：E6 完成插件市场（纯新增能力）→ 类别 = 0.x 向后兼容 → `0.1.0 → 0.1.1`。理由：新增能力不破坏已发布插件，0.x 向后兼容走 patch 位。
**场景 B（0.x 破坏性）**：重构 `linkdesk.*` 删了某 API 且无法兜底 → 类别 = 破坏性 → `0.1.0 → 0.2.0`。理由：minor 位承担 MAJOR 职责。
**场景 C（1.0 上架）**：E6 全闭环 + API 冻结 + 数据格式冻结 → `0.x → 1.0.0`。理由：对标 VS Code 0.10→1.0，「API 稳定承诺」。
**场景 D（1.x 修复）**：修 3 个崩溃 bug → `1.0.0 → 1.0.1`。理由：纯修复 PATCH 级，零新功能。
