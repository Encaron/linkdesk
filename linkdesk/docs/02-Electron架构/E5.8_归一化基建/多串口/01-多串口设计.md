## §1 有意设计变更声明

**单口互斥是 2026 年当时的明确设计，不是 bug。** 设计意图：一个串口监视器标签页开 COM3（侧栏 COM3 灯亮），另一标签页切 COM13 直接打开 → **第一个口自动关闭、灯灭**——"顶替"语义，保证全局只有一个活跃串口（serial-service.ts L109-111 `openPort` 先关旧口，ControlPanel.tsx L94 注释明文记载）。侧栏换灯机制（SessionListView.tsx E5.7#89-fix："换端口顶替时唯一信号是 :sourceName 变更，补订阅该键换灯"）就是为这个设计打的补丁。

**多串口模式把这个语义改掉：端口共存。** 标签 A 开 COM3 后，标签 B 开 COM13 **不再顶掉 COM3**——两灯同时亮、两路数据各收各的。顶替语义只保留在**同一标签页内部**（一个会话换口 = 关本会话旧口、开新口——每标签页单口模型不变，见 D3）。

## §3 语义变更决策（定死）

| # | 决策 | 内容 | 论证 |
|:--|:--|:--|:--|
| D1 | 端口共存 | openPort 不再关其他口；顶替只发生在同一会话内换口 | §1 |
| D2 | 请求面加可选 portName | closePort/sendData/sendText/setDtr/setRts 加 `portName?`；缺省 = **唯一打开口**：0 口 → 抛"串口未打开"（现网同文案）；≥2 口 → 抛"多串口已打开，请指定 portName" | 静默选错口比报错更糟——失败可见性（uninstall-bug-recurring 教训）；旧插件单口场景零变化 |
| D3 | 每标签页仍单口 | 会话-端口绑定不变（#29）——一个会话一个口；标签页内换口 = 关本口开新口（定向） | 每标签页单口模型是会话系统地基，多口发生在**跨标签页**维度 |
| D4 | Map + 资源归属 | `Map<portName, PortState>`；PortState = 六字段（port/lineBuffer/isClosing/encoding/portName/baudRate/flushTimer）+ **ownerPluginId** | 六字段内聚防跨口串扰（A 口关闭期间 B 口数据被 isClosing 丢弃 = 真实风险）；ownerPluginId 支撑 D8 |
| D5 | getStatus 双形态 | `getStatus()` 无参 → `SerialStatus[]`（全部打开口，空数组 = 全关）；`getStatus(portName)` → 单口快照 | Hot Exit 遍历恢复 + 壳诊断面 |
| D6 | 载荷对象化加 portName（**现有通道演化，不新建 API**） | serial:data/stats/system 三通道载荷加 `portName` 字段（现有通道 + 现有契约文件，不加通用包络层；Phase 1.5 broadcast 若已定义包络则用其形态）；回调签名同步。路由键语义（key=portName）是通用**模式**——写进契约注释，不建通用包络**类型** | 已有 API 优先原则：现有 serial 通道 + 契约文件直接承担，见 §7 审计表 |
| D7 | 键控过滤 = **插件本地 helper + 现有 API** | 三态过滤收敛为插件 utils 一个 ~15 行 helper（S12/S13 收敛到一处）；侧栏灯直接读**现有** per-port pluginState 键（E5.5#9l 已就位——S15 只改消费方式，零新 API）。**推广路径**：E6 出现第二键控信息源时升格壳 hook——记录在案，不现在建 | 已有 API 优先：events + pluginState 现成（§7 审计表：新建壳 API 面 = 0——通用已有 API 全覆盖，非消费者门槛）；E6 出现第二键控信息源时升格壳 hook |
| D8 | 同口二开拒绝 + 卸载连坐 | ① 打开已打开的口 → **拒绝 + 错误提示**（不自动关先开者——自动关 = 别的标签页数据丢失；Windows 驱动层本来也排他，服务层 Map 是显式仲裁，报错文案可控）；② OpenPortConfig 加可选 `ownerPluginId`，卸载插件 → `closePortsByOwner(pluginId)` | 见下方同口决策论证 |

**同口二开决策论证（用户提问：两标签页同口怎么办）：**
- ❌ 两标签页同时亮灯：一个口只有一个硬件数据流——两消费方谁发？谁收到谁的数据？收发归属不可定义，且 OS 层不允许双 open
- ✅ **拒绝 + toast**：先开者独占（灯亮）；后开者收错误提示「串口 COM3 已被打开」灯不亮；先开者关闭后，后开者可重试成功。F5 恢复时按**会话创建序**确定性恢复，后到者收拒绝提示
- 拒绝信息走 SerialContext 现网 lastError 通道（onSystem 系统消息）——零新 UI 基建

## §6 壳改动最小化分析（用户追问：不动壳能否实现？为什么必须动壳？为什么这不是插件自己的功能？）

### §6.1 为什么必须动壳——三层论证

1. **物理层**：preload 沙箱不暴露 require/node:fs/child_process（`system-capability-linkdesk-api-only` 铁律）——插件**物理上没有打开串口的代码路径**。串口监视器一行串口驱动代码都没有，所有 open/read/write 经 `linkdesk.serial.*` 请求主进程执行。「两个口同时开着」这个状态只能存在于主进程。
2. **现状层**：16 条单口假设有一半长在壳里——S1 单口字段组、S2 顶替语义、S3 getStatus 单形态。不动壳 = 顶替语义原样保留 = 多串口做不成。
3. **协议层**：S6 三通道载荷无口名——多口下消费者无从分辨数据来自哪个口（寻址不可表达）。

### §6.2 为什么这不是串口监视器自己的功能

**进程判断标准：功能代码跑在哪个进程。** 全部能在插件进程（WCV 渲染层）跑完 = 插件自己的功能；越过 `linkdesk.*` 边界 = 壳能力。

- **插件自己的那部分**（本 Phase 插件 6 文件）：多标签页各绑一口（D3）、portFilter 过滤（D7）、会话-端口 UI、消费方改造——纯渲染层代码，一行壳都不用动。若多串口只需要这些，就是纯插件功能。
- **插件做不了的那部分**：顶替语义跑在 serial-service.ts L109-111，插件拦不住、改不了、绕不开。唯一 workaround = **伪装**（只开一个真口 + 缓存重放），不是真并发——硬件真实并发只存在于主进程。
- **类比**：摄像头——两个播放器播两路流 = 网页自己的功能；系统同时开两个摄像头 = 宿主能力。串口通道 = 宿主控制的系统资源（content-vs-space-ownership），解析/展示/过滤数据才是插件内容。
- **验收视角**：Phase 6 的验收不是"串口监视器多了个功能"，而是**壳里 16 条单口假设清零**。动壳 3 文件无一行 serial-monitor 专属逻辑（Map/可选 portName/载荷字段全部是通用串口语义——未来 GPS 记录器、固件烧录器用同一份能力）。

### §6.3 插件独立铁律——满足是分能力的（时机论证）

| 时间点 | 第三方作者写单口插件 | 第三方作者写多口插件 |
|:--|:--|:--|
| Phase 6 前（现状） | 零壳改动——铁律成立 | **做不成**——必须找壳作者改壳——**铁律违反状态** |
| Phase 6 后（E6 上架） | 缺省 portName 零壳改动 | 带 portName 零壳改动——铁律成立 |

**反推灾难**：若 E6 之后才做多串口——第三方存量插件已依赖顶替语义 → 改壳 = 破坏存量第三方（违约）；不改 = 能力永久缺失。两边死路。**破坏性变更窗口 = E5.8**（上架前无第三方存量插件，现在改零代价）。E5.8 的 62 个任务本质 = **铺路**：把"唯一消费者时代"留在壳里的专属假设清零，让第三方上架后拿起 API 就能走。

### §6.4 专属假设 vs 版本化演进

铁律 ≠ 壳预知一切未来能力。上架后两类需求分开处理：

- **专属假设**（能力已存在，但里面带了某个插件专属行为——顶替语义就是标本：壳的单口能力里长着串口监视器的专属 UX 决策）→ **必须上架前清零**（§1）；上架后改 = 破坏第三方 = 违约，上架后不改 = 能力永久缺失
- **全新能力**（壳从未提供，如未来串口 break 信号/DTR 引脚）→ **版本化演进**——上架后加 API + 版本声明（VS Code `engines.vscode` 同款），随时可加，不违约

### §6.5 结论——壳改动只加能力、不加功能

**不能零壳改动——服务层是硬阻塞**（§6.1 物理层），`Map` 必须在主进程。但量最小：

| 面 | 文件 | 改动性质 | 必须动壳的理由 |
|:--|:--|:--|:--|
| 壳 | electron/services/serial-service.ts | Map 化 + 语义变更 | 硬件所有权在主进程——物理必然 |
| 壳 | electron/ipc/serial-handlers.ts | 载荷对象化（广播机制 Phase 1.5 已接管，零重复） | 推流源头不带口名 → 下游无法路由 |
| 壳 | src/core/types/ipc/serial.ts + linkdesk-api.ts | 契约 + API 签名 | 契约本身就是壳的 API 面 |
| 插件 | SerialContext.tsx / index.tsx / ControlPanel.tsx / statusBar.tsx / SessionListView.tsx / utils/portFilter.ts | 消费方改造 | 会话/灯/过滤/UI 全是插件侧 |
| 无新建壳 API | — | 键控过滤 = 插件本地 helper + 现有 events/pluginState | 已有 API 优先原则（§7 审计表）——不新建 hook/包络/命名空间 |

**壳改 3 文件 ≈ +80/−60 行，插件改 6 文件 ≈ +165/−140 行。零新壳 API 面（新命名空间/hook/包络 = 0）。** 壳不加任何 serial-monitor 专属逻辑（插件 ID 零硬编码——硬约束 10）。

## §7 API 设计原则——已有 API 优先（用户拍板：有 API 用已有，迫不得已才新建）

**原则（2026-08-17 用户定死）**：如果已有 API 能承担，就用已有 API；只有**没有它做不成**时才新建 API。逐项审计：

| 需求 | 已有 API 能否承担 | 结论 |
|:--|:--|:--|
| 通用信息交流 API（未来 MQTT/TCP 插件也用） | ✅ **`linkdesk.events` 已经是**——自由字符串通道 + 泛型载荷（E5.7#97），E3j #77 串口原始数据已走 events 上车 | **零新建**——serial 推送经 preload 进 events（现有链），未来 MQTT 插件同链 |
| 数据按口路由 | ✅ serial 三通道是**现有通道**——载荷加 `portName` 字段 = 演化现有契约，不新建通道/包络层 | **扩展现有**（唯一新建成本 = 契约字段） |
| 三态键控过滤 | ✅ 插件本地 5 行 helper 可承担（index.tsx 现网 isMyPort 就是这个逻辑的雏形） | **插件本地 helper**（utils/portFilter.ts ~15 行）——不建壳 hook；**推广路径**：E6 第二键控信息源出现时升格壳 hook，记录在案不现在建 |
| 侧栏/状态栏每口灯 | ✅ **per-port pluginState 键 E5.5#9l 已就位**（`COM3:isOpen` 格式）+ `plugin-state:changed` 现有事件 | **只改消费方式**（按口读键，删 #89-fix 换灯补丁）——零新 API |
| 指定操作目标端口 | ❌ 现网 closePort()/sendData() 无目标参数——多口歧义无法表达 | **迫不得已新建**：加可选 `portName?` 参数（向后兼容，缺省唯一口语义）——没有它多口操作无法寻址 |
| getStatus 多口查询 | ❌ 现网无参单口快照——Hot Exit 无法恢复多口 | **迫不得已扩展**：getStatus 双形态（无参数组 + 有参单口）——没有它恢复不了 |
| 卸载连坐（端口随插件卸载回收） | ✅ **Phase 2 可逆注册主进程侧机制（#8 定案面）**——端口打开注册 disposer，卸载逆序回滚 | **走 Phase 2 机制**（不新建生命周期通道）；唯一被迫新建 = OpenPortConfig 可选 `ownerPluginId` 字段（pool WCV 多插件同 JS 上下文，主进程无法从 sender 识别插件——字段是唯一可靠归属声明） |

**审计结论：新建壳 API 面 = 0（新命名空间/hook/包络/通道全为零）；扩展现有 API = 3 处（serial 三通道载荷加 portName + 请求面可选 portName + OpenPortConfig 可选 ownerPluginId）——全部是"没有它做不成"的最小集。**

**通用性交代：** 信息交流通用 API = 现有 `linkdesk.events`（已通用，无需新建）；串口硬件专属 API（listPorts/setDtr/setRts/波特率）留在 `linkdesk.serial` 命名空间（硬件枚举通用化没有消费者——准则 5 是"未来容易拓展"，不是"现在建空框架"）；路由键语义（portName/topic/host:port 同构）以契约注释形式记录为通用模式，未来第二信息源照抄模式即可。

## §10 回归验证

**用户可实机验证清单（#30 逐项过）：**
1. **双口共存**：标签 A 开 COM3（A 灯亮）→ 标签 B 开 COM13 → **B 灯亮且 A 灯不灭**（旧行为 A 灭——语义变更的可见证据）
2. **同口二开**：标签 B 再试开 COM3 → 拒绝提示、A 数据不断
3. **断一不断二**：COM3 拔线 → COM13 数据流不断
4. **F5 恢复**：双口重启 → 两状态各自恢复、两灯亮
5. **标签页内换口**：B 内 COM13→COM5 → 只影响 B，A 不动
6. **卸载连坐**：卸载 serial-monitor（口开时）→ 端口关闭；重装 → 可重开
7. **单口回归**：只用一个口的旧路径全链无变化（下拉框/连接/收发/灯）
8. **第三方形态并存**（2026-08-20 第三方视角审计新增）：临时第二个串口插件（轻量/单口/终端式）与重型并存——两插件各开各的口、各亮各的灯、各收各的数据；两插件同时开**同一物理口** → 后开者收拒绝提示（D8 物理排他，非壳任性）。E6 前无第二插件 → 该项以「契约文档化声明（#28 补充）+ 单口缺省语义实测」兜底

## §11 风险

| 风险 | 对策 |
|:--|:--|
| 每口独立计时器/标志漏迁（isClosing/flushTimer 共用 → 跨口数据丢/串） | PortState 六字段内聚设计时即防；#26 验收含双口并发冲刷实测 |
| 缺省"唯一口语义"旧插件静默作用错口 | D2：≥2 口时抛错不静默（失败可见性） |
| wire 载荷变化漏改消费方（IPC 载荷运行时无编译期兜底） | 消费方清单 = §8 #29 表（7 插件文件）+ #22.5 运行期校验兜底 + #28 验收旧签名 grep 清零 |
| 推送量 ×N（每口独立 100ms 冲刷） | 多口场景 IPC 量线性可控；若 #30 实机见拥塞，冲刷计时器合并（实机判断，不预设） |
| Hot Exit 恢复竞态（双口同时恢复、同口双会话争抢） | #27 确定性顺序（会话创建序）；同口争抢走 D8 拒绝 |
| 卸载连坐误关（插件 B 卸载误关插件 A 的口） | closePortsByOwner 按 ownerPluginId 精确匹配；owner 是插件自声明（openPort 时传），壳不猜 |

## §12 明确不做（边界）

- **多进程/多服务实例**——Map 化够了（E5.7 极简 Pool：安全靠 preload 沙箱不靠进程数）
- **通用连接框架 `linkdesk.connections`**——§7 边界记录：无第二消费者不建空抽象，扩展位已留
- **串口虚拟化/设备模拟层**——09-Serial-Simulator 插件自会做
- **PortInfo 缓存/热插拔事件推送**——listPorts 按需拉取现状不动
- **跨标签页共享同一口的数据广播**——D8 拒绝语义，不存在"一源多消费"场景（真需要时是 E6 通用连接框架的候选需求，届时评估）
