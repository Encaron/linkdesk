# 壳目录规范

> 2026-08-12。E5#30 写了插件目录规范，但没写壳目录。E5#42 建 `data/` 没定义语义→今天的 #36k 返工。**此后所有壳代码遵守此规范。**

---

## 1. `src/core/`——圆形大厅（桌子集合）

**准入标准（三条同时满足）：**
1. 多提供方——多个插件可能登记到这张桌子上
2. 多消费方——多个插件可能翻这张桌子
3. 桌子不知道内容——桌子本身不知道登记的信息是什么意思

| 子目录 | 语义 | 放什么 | 不放什么 |
|--------|------|--------|----------|
| `registry/` | Registry 模式——登记/查询/注销 | CommandRegistry, MenuRegistry, ThemeRegistry, CardRegistry, ProtocolRegistry, KeybindingRegistry, IconRegistry, ConfigurationRegistry, ContextKeyService, LangDefRegistry, LanguageRegistry, FileDecorationRegistry, StatusBarService, QuickPickService, MenuRegistry, ClipboardProviderRegistry | 有副作用的 Service（放 services/） |
| `services/` | 有副作用的 Service——读写/网络/IPC | ConfigurationService, FileService, LayoutEngine, WorkspaceService, NotificationService, PluginStateService, StorageService, DialogService, EncodingService, FileSearcher, LogChannel, FactorySlots, ErrorService, ThemeEngine, AppInitializer, ViewContainerService, IpcBridgeHandler, ProfileService, FileAssociationService, LayoutService | 纯 Registry（放 registry/），纯工具函数（放 utils/） |
| `pipeline/` | 数据管道——原始字节→卡片消费 | ProtocolParser, RingBuffer, DataConverter, DataDispatch | Registry/Service/通用工具 |
| `utils/` | 纯函数工具——无状态/无副作用 | CancellationToken, pathUtils, assetPath | 有模块级状态的（放 services/） |
| `react/` | React hooks + context + 事件总线 | useSendData, useConfiguration, usePluginIpcEvent, TabActionsContext, CoreEvents, ShellEvents, SidebarTabSync, useConfigurationIpc | 非 React 代码（放对应目录） |
| `api/` | 类型定义 + API 契约 | linkdesk-api.ts, v3Api.ts, types.ts | 业务逻辑 |
| `types/` | 纯类型——跨模块共享的 type/interface | poolLayout.ts | 带实现代码的（放对应目录） |
| `builtin/` → `commands/` | 壳自举代码——命令/快捷键/菜单注册 | coreCommands, shellKeybindings, shellMenus, CoreCallbacks, settingsCommands, tabCommands, developerCommands, registerBuiltinProtocols | 插件代码（放 plugins/） |

**判据：** 文件放 `core/` 根目录之前——它属于哪个 subsystem？找不到 → 别放 core/。

## 2. `src/pool/`——Pool 渲染层（WebContentsView 内）

| 子目录 | 语义 | 放什么 |
|--------|------|--------|
| 根目录 | 入口 | `pool-main.tsx`——根据 `?zone=` 路由到对应 Renderer |
| `shared/` | 跨 Pool 共享 | PluginComponent, GroupTabBar（两个以上 Pool 用的组件放这里） |
| `sidebar/` | SidebarPool 专属 | SidebarRenderer, PoolSectionStack, PoolToolbarSlot |
| `main/` | MainPool 专属 | MainRenderer |
| `views/` | 壳级视图（跨 Pool） | ShellViewRenderer, WelcomePoolView, PluginDetailPoolView, OutputPoolView |
| `bottom/` | 未来 BottomPanelPool | BottomRenderer |
| `floating/` | 未来 FloatingWindow | FloatingRenderer |

**原则：加 Pool = 加目录。不碰现有目录。**

---

## 3. `src/components/`——壳 React 组件

| 子目录 | 语义 | 放什么 |
|--------|------|--------|
| `shared/` | 归一化 UI 控件——全局唯一 | SelectBox, ContextMenu, MenuRenderer, InlineInput, ErrorBoundary, SidebarSection, OverlayPortal, ConfirmDialog, ToolbarSlot, SectionStack, PluginIcon |
| `views/` | 壳级页面 | PluginDetailView（壳版） |
| 根目录 | 壳布局组件 | SidePanel, MainContent, StatusBar, TitleBar, IconBar |

**判据：** 两个以上地方用 → `shared/`。只有一个地方用 → 放消费方目录。

## 4. `src/hooks/`——React hooks

纯 hooks——`use*` 前缀，一个文件一个 hook。不夹带组件、不夹带 service。

## 8. 反模式——加文件前自检

| 反模式 | 正解 |
|--------|------|
| "不知道放哪，先放 `core/` 根目录" | 对照此表——找不到归属 = 不应该进 core |
| "就一个文件，建子目录太早了" | 正确目录宁可只有一个文件——命名就是文档 |
| "这个和那个有点像，放一起吧" | "像"≠"同类"。Registry 和 Service 都管理数据，但一个纯查询一个有副作用——不同目录 |
| "以后再说" | 以后不会再说——E5#42 就是"先分堆"的教训 |

## 9. 历史教训

| 问题 | 根因 | 今天 |
|------|------|------|
| `core/data/` 杂货铺（E5#42 → #36k 返工） | 建目录时没定义语义——"放数据的"太模糊 | pipeline/utils/registry/services 四类明确 |
| `core/builtin/` vs `plugins/builtin/` 同名异义 | 壳代码和插件代码共用一个形容词 | `core/commands/` 单独命名 |
| `pool/` 平铺所有 Renderer | 两个 Pool 时没觉得需要分，没想三个以后 | shared/sidebar/main 一 Pool 一目录 |
| 插件目录不规范（E5#33 前） | 每个插件自定结构 | plugins/ 目录规范（E5#30） |

**Why:** E5#42 52 文件迁移只做了"分堆"没做"分类"，因为当时没有这份规范。今天的 #36k #36l 是补上"分类"这一步。
**How to apply:** 新 AI 加文件前先查此表——确认归属子目录再 `touch`。找不到归属 → 问，不要猜。
