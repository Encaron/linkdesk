# 插件目录分离与角色覆盖——`builtin/` + `user/` 物理隔离

> 2026-07-29。**#86 设计文档。** 此文档解决三个问题：目录物理分离（防小白误删）、死路径消除（路径引用归一化）、角色覆盖（第三方可替换内置插件）。
>
> **讨论来源：** Encaron + AI 在 #86 执行前进行的完整讨论——边界模糊/死路径/第三方能力/VS Code 对照。
> **性质：** 设计文档——执行前必读。所有改动以此文档为理论支撑。

## 一、背景——为什么要分目录

### 当前状态

`plugins/` 下 9 个目录平铺，无任何视觉线索告诉用户"哪个是系统自带的、哪个是你自己装的"。

### 目标

小白打开 `plugins/` 文件夹，看到两个子目录，瞬间明白——不需要警告弹窗。

```
plugins/
├── builtin/              ← 跟安装包来，软件更新时覆盖
│   ├── settings/
│   ├── serial-monitor/
│   ├── marketplace/
│   ├── workspace/
│   ├── theme-defaults/
│   └── lang-defaults/
└── user/                 ← 用户从市场装的
    ├── theme-mint-soda/
    └── lang-test-ja/
```

### 为什么叫 `builtin` / `user` 而不是 `factory` / `market`

| 命名 | 含义 | 问题 |
|------|------|------|
| `factory` / `market` | 按分发渠道 | 暗示"工厂品质"vs"市场品质"，第三方基础设施插件不应低人一等 |
| **`builtin` / `user`** | **按来源** | 中性。`builtin` = 内置（安装包带的）、`user` = 用户装的。对标 VS Code `ExtensionType { System, User }` |

## 二、VS Code 怎么做

```
// src/vs/platform/extensions/common/extensions.ts
export const enum ExtensionType {
    System,   // 跟着安装包来的 Git/Markdown/TypeScript
    User      // 用户从 marketplace 装的
}
```

**物理布局（Windows）：**

```
C:\Program Files\Microsoft VS Code\resources\app\extensions\   ← System
C:\Users\<用户>\.vscode\extensions\                            ← User
```

**核心事实：** 第三方不能做 System 扩展。System 扩展在 VS Code 源码仓库里，走 VS Code 构建流水线。

## 三、LinkDesk 的方案

### 3.1 `plugin.json` 声明字段

```jsonc
{
  "id": "settings",
  "name": "官方设置",
  "distribution": "builtin"  // "builtin" | "user"（缺省 = "user"）
}
```

### 3.2 物理保护——`builtin/` 不锁死、不防替换

- `builtin/` 里的东西随着安装包更新被覆盖
- `user/` 里的东西安装包不动
- 小白删了 `builtin/settings/` → 下次软件更新自动恢复
- 文件夹名字就是提示——不会阻止故意删，但保证"你知道这是系统自带的"

### 3.3 逻辑自由——第三方可以替换任何内置插件

**物理上**：官方设置永远在 `builtin/settings/`。不删、不动。

**逻辑上**：`FactorySlots` 机制（E2c #19e 已有）——相同 role 的插件在 UI 里以下拉菜单切换：

```
┌─────────────────────────────┐
│ 设置 UI:  [官方设置 ▼]      │
│           ├── 官方设置       │  ← builtin/settings
│           ├── Material 设置  │  ← user/material-settings
│           └── 极简设置       │  ← user/minimal-settings
├─────────────────────────────┤
│  (当前选中的设置 UI 内容)    │
└─────────────────────────────┘
```

**切换逻辑：**
1. 扫描所有注册了同一 slot 的插件
2. 仅 1 个注册者 → **不显示下拉**，直接用唯一的那个
3. ≥2 个注册者 → **下拉菜单出现**，供用户切换
4. 切换后 → **下拉菜单仍在**，用户随时可以切回来
5. `user/` 下的第三方插件卸载 → 注册者从 2 变 1 → **下拉自动消失**，退回 `builtin/`
6. ≥2 个注册者时默认优先级：`user/` 下最近使用的 > `user/` 下第一个 > `builtin/`

**名字冲突兜底：** 下拉菜单显示 `plugin.json` 的 `name` 字段。万一重名 → 补插件 ID：
```
├── 设置 (settings)
├── 设置 (material-settings)
```

### 3.5 换 UI 不换数据——底层配置共用

**数据层不变。** 无论官方设置还是第三方设置，读写的是同一份配置数据：
- 同一份 `settings.json`
- 同一个 `ConfigurationService`
- 同一套配置 schema（`plugin.json` 的 `contributes.configuration`）

第三方设置插件只是换了**渲染方式**——底层数据源、schema、读写逻辑全不变。

### 3.6 持久化——记住用户选了哪个 UI

对标主题选择：选了 Dark → 下次打开还是 Dark。设置 UI 选择同理。

```
用户选了 Material 设置
  → PluginStateService.set("settings", "activeUi", { pluginId: "material-settings" })

下次打开设置
  → PluginStateService.get("settings", "activeUi")
  → pluginId = "material-settings" → 用 Material 的 UI 渲染
  → 不存在或未设置 → 退回 builtin/settings
```

**下拉菜单逻辑更新：**
1. 持久化的选择优先——上次用哪个，这次还用哪个
2. 持久化的插件已被卸载 → 自动退回 `builtin/`
3. 切换时更新持久化记录
4. `PluginStateService` 已有——不引入新机制

## 四、死路径问题——完整影响面分析

`plugins/<id>/` 路径散落在多文件多处。只改目录结构而不改这些引用 → 全部变成死路径。

### 4.1 前端（`src/pluginLoader/loader.ts`）

| 行号 | 当前代码 | 死因 |
|:--:|------|------|
| 59-66 | `import.meta.glob("../../plugins/*/index.tsx")` 等 6 个 | 路径从 `plugins/<id>/` 变成 `plugins/builtin/<id>/` 或 `plugins/user/<id>/` |
| 91-93 | `import.meta.glob("../../plugins/*/plugin.json")` | 同上 |
| 98-103 | `extractPluginId(path)` — 找 "plugins" 后下一段 = id | 下一段变成 "builtin" 或 "user"，不是 pluginId |
| 929-930 | `http://localhost:1420/plugins/${pluginId}/${filePath}` | dev 模式下 Vite 静态服务找不到文件 |

### 4.2 Electron 侧（`electron/services/plugin-file-service.ts`）

| 方法 | 当前代码 | 死因 |
|------|------|------|
| `listPluginDirs()` | `fs.readdir(pluginsDir)` | 扫不到 `builtin/` / `user/` 下的子目录 |
| `installPlugin()` | `path.join(pluginsDir, name)` | 应装到 `user/` 而非根 |
| `uninstallPlugin()` | `path.join(dir, pluginId)` | 找不到插件（在子目录里） |
| `reinstallPlugin()` | `path.join(dir, pluginId)` | 同上 |
| `readManifest()` | `path.join(pluginsDir, pluginId, ...)` | 同上 |
| `resolvePath()` | `path.join(pluginsDir, pluginId)` | 同上 |

### 4.3 协议（`electron/protocol.ts`）

| 行号 | 当前代码 | 死因 |
|:--:|------|------|
| 41 | `path.join(pluginsDir, urlPath)` | `linkdesk://serial-monitor/...` → `<pluginsDir>/serial-monitor/...` 而不是 `<pluginsDir>/builtin/serial-monitor/...` |

### 4.4 解决方案——归一化查找

在 `PluginFileService` 中加一个 ~15 行的 `_findPluginDir()` 方法，所有路径解析走它：

```typescript
/** 查找插件所在的子目录——"builtin" | "user" | null */
private _findPluginDir(pluginId: string): string | null {
  const dir = this.pluginsDir();
  for (const sub of ['builtin', 'user']) {
    if (existsSync(path.join(dir, sub, pluginId))) return sub;
  }
  return null;
}
```

`resolvePath()`、`readManifest()`、`uninstallPlugin()` 等所有方法各改 ~2 行——把 `path.join(dir, pluginId)` 换成 `path.join(dir, subdir, pluginId)`。

`installPlugin()` 固定装到 `user/`——用户安装的永远是 user 类型。

`protocol.ts` 的 handler 试两次：先 `builtin/<path>`，再 `user/<path>`。

### 4.5 不会断的——注释 / 用户数据路径（无需改动）

| 文件 | 行 | 为什么不断 |
|------|:--:|------|
| `loader.ts` 注释 | 57,1081,1234,1369,1412,1420 | 注释——不执行，仅更新文字 |
| `env-service.ts` | 6-8,28 | `.linkdesk/plugins/<id>/data/` 是 **AppData 用户数据路径**，不是插件源码路径——这个不变 |
| `preload-plugin.ts` | 132 | 同上——插件数据目录，非源码目录 |
| `file-service.ts` `pluginsDir()` | 38 | 返回根目录——正确，子目录解析在调用方 |

## 四-B、不需要重写任何东西——改动量分析

### 这不是架构改动，是文件组织改动

改的就是一件事：**"插件文件在哪里"**。不影响：

| 不变的 | 原因 |
|------|------|
| 插件怎么加载 | `import()` 还是 `import()`——Vite glob 换路径，加载机制不变 |
| 插件怎么注册 | Registry 模式不变 |
| 插件怎么通信 | IPC 管道不变 |
| `plugin.json` 格式 | 只多一个可选字段 |
| 主题/语言/设置系统 | 不碰 |
| 插件生命周期 | 不碰 |
| 标签页/分屏 | 不碰 |

### 工程量的真实数字

**82 行，5 个文件。** 没有任何一个现有模块需要重写——每个文件只改路径拼接的那一两行。

### 用户需求对照——大部分已经存在

| 你的要求 | 需要改什么 | 要新写什么 |
|------|------|:--:|
| 丢 `user/` 下就能用 | glob 扫 `user/` 子目录 | ❌ 已有 |
| 市场下载自动进 `user/` | `installPlugin()` 目标改 `user/` | ❌ 已有 |
| 同名出下拉框 | `FactorySlots`（E2c #19e）已有 | ❌ 已有 |
| `core: true` 不出删除按钮 | 已有 | ❌ 已有 |

### 5.1 开发阶段不做物理分离（打包后自然分离）

- **开发阶段：** 所有插件在 `plugins/` 下混着——你是开发者，不会手滑删自己的代码
- **打包后：** Electron builder 配置中 `builtin` 插件打进 `resources/plugins/builtin/`（跟安装目录走），`user` 插件位置指向 `%APPDATA%/LinkDesk/plugins/user/`
- `distribution: "builtin"` 告诉打包脚本哪些插件跟着安装包走

### 5.2 不引入 `_findPluginDir` 之外的路径解析新机制

所有路径查找走一个方法。不分散改 10+ 处各写 try-builtin-then-user 的重复逻辑。

## 八、与现有设计的兼容

- `plugin.json` 的 `core: true` 字段不变——标记不可卸载
- `distribution` 是独立字段——标记物理归属（`builtin` / `user`）
- `FactorySlots.ts` 的 `factoryRole` 声明不变——标记逻辑角色
- 三个字段互不冲突：`core` = 能不能卸载，`distribution` = 放在哪个文件夹，`factoryRole` = 提供什么角色
