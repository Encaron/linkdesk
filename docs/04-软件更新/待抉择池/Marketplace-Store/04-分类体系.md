# 分类体系——怎么分、怎么长、为什么这么定

> **为什么存在**：分类是 Store 信息架构的骨架，也是上一版任务死掉的地方（串口类/地图类）。本文先提炼失败教训成规则，再立机制，再给种子——顺序不能反，因为**机制比分类名单重要**：名单错了改一行数据，机制错了每加一个插件都要开会。
> **上游**：[02-病灶与目标](02-病灶与目标.md)（扩展位清单的「分类」「排序」两条）；[03-入口与数据归一](03-入口与数据归一.md)（分类页住 Store 标签页）；**下游**：[05-卡片与动作槽](05-卡片与动作槽.md)（分类页网格里的卡片）；**参照系**：微软商店（桌面端）＋ OPPO 软件商店（移动端）实地走查（2026-11-19 用户口述，全程记录见 §二）。

## 一、上一版为什么失败（教训提炼，不是八卦）

上一版分类：硬件类、软件类、**串口类**、**地图类**——被用户否决。失败模式提炼：

- **点名册问题**：分类按「现有插件」逐个命名——有一个串口助手就开「串口类」，用户提过一嘴地图插件就开「地图类」。分类名单成了现有插件的点名册。
- **后果链**：加一个插件 → 想要不要开新类 → 类目越分越碎 → 每类一两个成员 → 分类失去导航价值 → 拓展性归零。
- **判定规则（本文一切机制的出发点）**：**一个分类值不值得存在，看它能不能装下几十个假想插件，不看它现在有几个成员。**

## 二、三种「看起来像分类的东西」（参照系走查结论）

界面上叫「分类/栏目/板块」的东西混着**三种不同性质**的维度，混用就是上一版的死因。必须拆开：

| 维度 | 例子（参照系） | 性质 | 变更频率 | 谁维护 |
|---|---|---|---|---|
| **① 分类 Taxonomy** | OPPO 左栏 17 大类；微软 Apps 页的文档处理/浏览器… | 稳定、宽泛、互斥的**骨架** | 几年一动 | 数据（slug＋i18n 值表） |
| **② 合集 Collection** | 微软「装机必备」「办公神器」；OPPO「精品随心选」 | 编辑出来的**临时清单**，成员可跨分类重叠 | 随时增删 | 数据（collections 声明） |
| **③ 榜单 Ranking** | OPPO 排行榜；微软热门 | 对同一目录**换排序键**的视图，零维护 | 自动 | 代码（排序逻辑，一次性） |

上一版把「串口助手」上升为 ①（它顶多是 ① 里的一员）。**用户要的推荐位 = 第一大 ②**：现在没服务器就手写「编辑推荐」合集，将来接服务器同一套槽换数据源——推荐位「先留好」的正确落法就是合集槽，不需要新机制。

## 三、机制四条（拍板；每条对应杀死哪个失败模式）

| # | 机制 | 为什么 |
|---|---|---|
| 1 | **分类是数据不是代码；声明值与显示名彻底分离**：作者在**自己仓的 plugin.json** 声明英文 slug（`hardware`），市场用 i18n 值表翻译成任意显示名（想叫「硬核玩家必备」就叫） | 用户拍板（2026-11-19）：「声明项写 hello world 都行，写标准通用一点，要宣传到外网」＋「市场里我想怎么写就怎么写」。两层各管各的=高内聚低耦合；改显示名不动声明，改声明不崩显示。**🔥 此机制已有正典先例：E6#32b（2026-09-08 用户拍板 B）——目录条目 `category`/`categories[]` = 英文 slug，i18n `category.*` 键翻译，未注册 slug 显示原文（不硬编码白名单）；实现住 `src/services/marketCategories.ts`（纯函数＋vitest 直测），详情页「分类」行今天就在用。本次沿用并升级（见 §四），不另发明。** |
| 2 | **主分类单值（`category`）决定抽屉归属；`categories[]` 多值作副标签**（喂搜索与小类 chips） | 多主分类 ⇒ 同一插件在网格重复出现 ⇒ 重蹈 02 §一·病灶 2「双重陈列」。恰好与目录格式既有字段语义吻合：legacy `category` 在前=主，`categories[]` 续后=副（`categoryListFromEntry` 已按此归并）——**不新增字段格式，沿用** |
| 3 | **小分类 = 封闭名单（2026-11-20 二次拍板，推翻旧「自由标签＋满 3 出 chip」）**：每桶挂一份小类名单（§5.1），作者从名单**选填**，⛔ 自由创作 slug；chip **有货即显（≥1）**；名单外 slug → validate 警告＋UI 归「未标注小类 · N」兜底 chip；只声明大类/未选小类的件在「全部」视图可见（不丢） | 结构性理由：VS Code 近 50 万插件实证该量级真实可达——自由标签在该规模 = 十万级 chip 灾难（用户原话「开什么玩笑」）；封闭名单 = OPPO 应用商店同构（小类固定、开发者选填），管理可控、聚合可靠 |
| 4 | **不设人工审查**：注册表（i18n 值表＋rail 顺序声明）加行即生效；未注册 slug **降级「其他」桶（rail 不渲染该条目），不崩不藏** | 审查流程 = 拓展性天花板；兜底桶保证任何脏数据可见可修。~~市场尊重第三方自定义分类~~ → **2026-11-20 二次拍板收窄**：显示名自由（值表作者侧不变的是**市场**值表；声明值已收窄为封闭名单）——「尊重自定义」只保留给**显示文案**，不给声明值 |

## 四、声明链路全景（谁声明、谁升级、谁读取、谁显示——2026-11-19 用户提问的逐环回答）

> 用户的原问题：「插件自己怎么知道自己该往哪住？谁来读取？怎么读取？读取后怎么显示？主仓要不要升级？」

```
作者 plugin.json（自己仓，声明 category/categories[]，英文 slug）
   ↓ ①收录管道复制（catalog:official 工具已有，01 §五·③）
目录 marketplace.json 条目（catalog 条目格式已支持，marketCatalog/types.ts:23）
   ↓ ②市场数据层读取（marketSources→marketCatalog→catalogStore，01 §二）
marketCategories.ts 纯函数（slug 归并＋i18n 翻译——已有，零新建）
   ↓ ③显示层消费
详情页「分类」行（今天就在用）／Store 分类 rail＋chips＋网格分组（本次新增消费面）
   ↘ ④未注册 slug →「其他」桶；i18n 未命中 → 显示 slug 原文（已有回退语义）
```

**每环的现状与缺口**：

| 环 | 现状 | 缺口（= 升级项，见 §九） |
|---|---|---|
| 作者声明 | ⛔ plugin.json 顶层**无** category 字段（SDK schema 只有 commands[].category） | SDK schema 加顶层 `category`/`categories[]`；作者文档补说明 |
| 收录管道 | catalog:official 出候选（01 §五·③） | 管道把 manifest 的分类复制进条目（大概率已随字段透传，实施期核实） |
| 读取/翻译 | ✅ marketCategories.ts 已有，DetailPage 在用 | 零缺口 |
| 显示 | ✅ 详情页一行 | Store rail/chips/网格 = 新消费面，复用同一纯函数 |
| 存量数据 | 抽检目录仓首条：条目**未填**分类值；存量 slug（serial/tool 等旧值）与新种子并存 | 各官方插件仓升级 manifest 时补齐；旧 slug 归并进新 slug（一次性数据迁移），旧值不删（历史目录兼容） |

## 五、主分类＋小分类种子（2026-11-20 二次拍板：小分类封闭名单＋有货即显——**大分类维持 HTML 已有的 7 桶不变**）

> 🔴 **机制拍板（用户以 OPPO 应用商店为参照）**：① 副标签与主分类**同为封闭名单**——作者只能**选**，⛔ 自由创作（自由标签在 VS Code 近 50 万插件量级 = 十万级 chip 灾难）；② chip 显示规则 = **有货即显（≥1）**，不是满 3；③ slug 全英文（作者声明 ID 利于传播），中文走市场值表显示；④ 没声明小类的件在大分类「全部」视图可见（不丢）。
> 🟡 **大分类扩充 = 将来时**：现役只保留 HTML 已有的 7 桶（下表）；**预留桶清单见 §5.4**（教育学习为用户点名的将来第一顺位）——启用 = 用户明示走 §5.3 SOP，⛔ AI 自行扩桶。
> ⛔ 名单外 slug：validate 警告不红，UI 归「未标注小类」兜底 chip（诚实落位）。名单扩充 = 市场值表加行（数据，非代码）。

### 5.3 标签扩充 SOP（用户对 AI 说「加标签」时的对话流程——2026-11-20 拍板，AI 必须接住）

**🔴 触发词识别**：用户说「加标签／加分类／大分类不够／小标题／我想加个 XX 类」且语境是插件市场 ⇒ **本 SOP 启动**。⛔ 不识别出本流程 = 漏拍板。

**AI 反问清单（一次问全，⛔ 挤牙膏）**：
1. **启用预留桶、现役桶内加小类，还是全新大分类**？（预留桶见 §5.4——教育学习是点名第一顺位）
2. **中文显示名**？（如「教育学习」）
3. **英文 slug**？——用户没给就按命名规范**提议**：小写连字符、语义化（⛔ 中文 slug、⛔ 拼音）
4. （小分类）挂在哪个大分类下？（可多个）
5. （新增大分类时）**小类名单要不要一并定**？至少 2–3 个起步（AI 可按桶语义先草拟，用户增删）

**执行步骤（顺序固定）**：
1. **§5.1 名单加行/列**（小分类加进现役桶）或**启用预留桶**（§5.4 → 现役表搬入）或加全新大分类行——纯数据；
2. **zh 值表登记**（市场侧标签显示名表加中文——⛔ slug 用中文）；
3. **影响面核对（通常为零发版）**：⛔ 不发 SDK（schema 是 array-of-string，⛔ enum）· ⛔ 不发市场插件版 · ⛔ 不发壳版——**加标签 = 数据＋值表，代码全链零改动**（chip 有货即显自动生效）；
4. 若用户同时想让**官方 18 件**中有件归入新桶/新小类 → 立项（各仓 plugin.json 一行＋插件轴发版——照 #25/I27 形态）；
5. **对账回勾**：12 I27 状态／00 §三 #25 行（若涉及）＋真机验证 chip 出现。

**禁区**：⛔ AI 不得自行决定加桶/启用预留桶（名单是**拍板面**，必须用户明示）；⛔ 反问挤牙膏；⛔ slug 用中文/拼音。

## 六、合集与榜单（拍板）

- **合集**：住目录仓 `marketplace.json` collections 声明（成员=条目 id 引用，可跨分类）；UI 渲染为「合集槽」，形态差异（横幅/横排/大卡/竖排两条+左右切换）= 卡片变体 `layout` 字段区别（→ 05 §四）。
- **合集上下与上限（2026-11-19 澄清）**：卡片「上去」＝目录仓 `items` 数组列入 pluginId → 收录发布 → 市场按 5min 缓存自动出现，**不需要更新市场插件本身**；**无硬上限**——声明多少张横排渲染多少张，超一屏靠左右箭头横滚承载，蓝图里的截断只是演示；运营建议单个合集 6~12 张（策展习惯，非代码限制）；引用不存在的 id **静默跳过**；策展人现阶段＝目录维护者人工编辑，将来接服务器可换自动排序数据源（槽位 UI 不动）。
- **榜单**：同一目录换排序键（下载量——`downloadCounts.ts` 已在抓 01 §二；将来 star/收藏同路），零维护，不进数据文件。
- **推荐位（英雄横幅）＝广告卡（2026-11-19 拍板）**：官方目录声明 3~5 张封顶（精选制，绝不流水全部插件）；现在官方手写，将来接服务器＝广告竞价（谁付费谁上去＋「广告」标识，付费裁决走 05 §三·4 壳层）。⛔ 第三方目录永不进 hero。
- **多源边界（2026-11-19 拍板，官方槽＋作者域两级）**：① **首页运营位（装机必备/主题专区/编辑精选/广告位）只吃官方目录**——第三方源插件只出现在分类页/搜索/榜单（带作者来源标注）；② **作者卡片区（首页第一槽，hero 之后）＝源板块**：每添加一个市场源＝一张**作者卡**（头像／名／简介／仓数／插件数——**显示作者本人与其源，而非插件流水**），点卡进作者主页；位置极高——用户原话「位置必须要很高很高……立即能发现第三方插件作者」（⛔ 旧「作者精选插件横排塞在深处」形态已废弃）；③ **作者主页**：点进后是该源的门面视图（作者头＋其 collections 合集条＋其全量网格），rail 首页返回——第三方作者「什么都不搞也有完整门面」；④ **分类分级强制**：官方收录**强制**带分类（没分类不收录），第三方源**不强制**（缺分类统一落**全局「其他」桶**）。
- 🔴 **单一统一池（2026-11-19 用户确认的架构基线）**：多源合并后所有插件进**同一个池**——分类页（开发/文档/硬件…）按分类**混合展示所有来源**，不分来源、不分作者；「其他」桶也是**全局唯一一个**（A/B/C 作者＋官方未声明的一起混排）；**作者域（首页作者精选板块＋作者主页）只是首页的附加门面＋同一份统一池按作者过滤后的视图**，不产生第二套分类体系、不从池中抽走任何插件。来源仅以徽标形式标注（详情/榜单行等）。
- **作者域基建（2026-11-19 拍板）**：① **一个作者可有多仓多源**——authorId **去中心化聚合**（作者在自己每个仓声明同一 id，无需中心注册），作者卡/作者主页聚合名下所有仓；**🔴 身份正典＝GitHub**（2026-11-19 拍板）：authorId 推荐＝作者 GitHub 用户名，头像/名字/简介从其 GitHub 主页取——全源一张脸，作者在 GitHub 改即全源同步；⛔ 主仓制已否决（人不随源顺序变脸）；仓介绍/仓图＝仓级内容（仅显示于店内仓卡）；非 GitHub 作者兜底＝作者块声明＋多源冲突源列表顺序回落；② **布局继承**：「咱们的布局是怎么样，理论上他们的布局也是怎么样的，他们填哪个就显示哪个」——作者主页＝官方 Store 同款骨架声明填槽，组件归一复用；③ **板块 API 全量**：作者主页每板块（大屏/装机必备/主题专区/编辑精选/榜单…）均有声明指令，作者自定内容、数量、板块标题**与卡片原型**；**按分类浏览固定存在不可删**（渲染器硬保留）——「固定」指**结构**：板块恒在，内容＝**只列出有插件的分类**；**官方店与作者店同一规则**（2026-11-19 统一拍板，推翻原 B 方案「官方全分类恒显」——两店同构，规则不许分叉）；空分类不进瓷片区，但 **rail 仍是全分类注册表**（0 计数灰显、点入诚实空态）；④ **门店切换卡：官方卡恒排第一位＋店内仓库切换**：作者店内 ⛔ 第四方（作者不希望别人插在自己店里）——**每个店面大屏轮播置顶，门店卡（官方第一＋作者自有仓）排其下**，官方卡即返回官方的入口；店内可在作者自己的多个仓之间切换；⑤ 升级涉及面见任务 00「软件涉及面与任务清单」（SDK/目录仓/插件仓/作者文档/AI 文档联动，**不可孤零任务**）。

## 七、页面映射（拍板；细节随 R2 布局定）

- **首页 = 槽位流**：英雄横幅槽（推荐）→ 合集横排槽（可多个）→ 榜单槽 → 分类入口网格。
- **分类页 = 页头 ＋ 工具行 ＋ chips ＋ 内容区（v3.23 深化定稿）**：页头＝大标题＋「N 个插件 · 分类描述 · 统一混排」副行；工具行＝**排序组**（最多下载／最近更新／字母 A→Z／按作者／按仓库——按作者·按仓库为**分组排序**：同组挨一起、组间 A→Z，组头随内容渲染）＋**显示方式切换**（平铺＝grid 网格卡／详细＝row 详细行——同页两种卡片形态，切换即时、滚动位保持）；chips 照三门槛机制过滤；排序/视图选择跨分类**会话记忆**。**作者跳转字落页＝authorId 预过滤＋「显示全部」切换**（过滤一次性：rail 重入即全量；过滤标识「作者名·计数·✕」常驻，清除就地生效——09 §二 2026-11-19 拍板）。内容＝**单一统一池**（官方＋第三方混排，来源徽标随卡）。窄窗响应式照旧（单列堆叠）。**分类 rail＝三段式**：顶部固定「**首页＝品牌块**」（强调色底＋图标块＋副标题，视觉最重）／中部滚动「浏览」（分类＋排行榜）／底部固定「库＋作者＋来源」（紧凑行，库带已装数量、作者带作者数）——**固定项高度减半**，滚动区最大化（窄栏 110px：分类为竖排瓷片，固定项为横向 icon+文字；窄窗整体变横向 wrap）。
- **侧栏不变**：继续承担快速操作（02 §三·1），不复制分类页。

## 八、拓展性推演（回答「分类了会怎么样」）

| 将来的变化 | 要动什么 | 不用动什么 |
|---|---|---|
| 上架一批同类新插件（如 5 个烧录工具） | 各自 manifest 声明 `category: hardware` ＋ `categories:[flash]`——「烧录」chip 有货即显（≥1） | 注册表、任何代码 |
| 开辟新品类／新增小类（如 AI 专区） | §5.1 名单加一行（值表数据）＋条目补 slug | 分类页 UI、首页网格（自动多一个入口） |
| 接服务器做推荐/热度 | 合集数据源换服务端；榜单排序键换真实统计 | 槽位 UI、卡片组件 |
| 收费插件上线 | 动作槽加一种动作声明（→ 05 §三） | 分类/合集机制一根不动 |
| 市场插件被第三方替换 | ——（见 05 §三·硬约束：分类值在目录数据里，不随市场 UI 死亡） | slug 声明照旧有效 |
| 侧栏退位（02 §五剧本） | 删侧栏视图薄壳 | 数据面、分类注册表、Store 全部功能 |

每行的「不用动什么」就是验收标准——**任何一格出现「要改代码」，说明实施违反机制，当场纠正**。
