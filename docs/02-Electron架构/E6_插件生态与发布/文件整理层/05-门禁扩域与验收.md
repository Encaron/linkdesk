> **对应任务：E6#88（第 3.6.5 轮）——本层的收官轮，也是「整理」这件事**不再退化**的保证。**

## 〇、病根先摆出来

`scripts/check-file-size.mjs:53`：

```js
/**
 * E6#0.6c 门开关——marketplace per-scope 档仅在 #30.11 拆完 MarketplaceSidebar.css
 * （377 > 300，12 档 styles 阈值）后翻转 true。翻早 → 肇事文件被列出红灯（行为正确，
 * 失败自解释）；翻晚 = 该档休眠。编辑器/file-tree/settings 等插件同界不扩域（清单未授权）。
 */
const SCAN_MARKETPLACE = false;
```

**这段话本身是对的。** 出问题的是**它挂靠的对象**：开关的翻转条件写成了「**#30.11 拆完**」——而 #30.11 在清单里是**已完成的 ✅**，它从未产出 `MarketplaceSidebar.css` 的拆分。

于是：**开关等一个永远不会再发生的信号，休眠了整整一个月。**

| 时间 | `MarketplaceSidebar.css` | `DetailView.tsx` | `marketplaceShared.ts` |
|:--|--:|--:|--:|
| 2026-09-04（开关设计日） | 377 | 0（未诞生） | 180 |
| 2026-09-11（今天） | **680** | **1258** | **779** |

**这是 00 号档案 §四 第 ③ 类的第二个实例**（第一个是 E6#81④）：**判定挂在别人的一次性产物上**。
**本轮的修法**：让「翻开关」成为**一个自己的任务（E6#88），带自己的判据，自己的验证**——不再挂靠任何别的任务。

## 一、现行门禁的三个缺口

| # | 缺口 | 后果 |
|:--|:--|:--|
| **G1** | `SCAN_MARKETPLACE = false` | marketplace 的 10 处超限**无人看管** |
| **G2** | 扫描域只有 `src/` + `electron/`（`DEFAULT_SCOPE_DIRS`） | file-tree 9 处 / serial-monitor 7 处 / settings 5 处 / editor 3 处 —— **共 24 处无人看管** |
| **G3** | `ROLE_LIMITS` 表不全 | 补上扫描域后，门禁会对**合法目录抛错**而非放行：<br>· `hooks/`（serial-monitor `useSerialSessions.ts`）<br>· `utils/`（serial-monitor `useSendData.ts`）<br>· `services/*.tsx`（serial-monitor `SerialContext.tsx`）<br>· `views/*.css`（settings `SettingsView.css`） |

**G1 + G2 合起来 = 34 处超限。** 这就是 [03](03-市场插件整理.md) / [04](04-其余插件整理.md) 两轮要拆的总量。

## 二、目标规则（**唯一权威，写完照抄**）

### 2.1 三档制

| 档 | 范围 | 阈值 | 豁免 |
|:--|:--|--:|:--|
| **A** | `src/**` + `electron/**` | **800** | ✅ allowlist（`@E6#0.6b` 拍板制，现状不变） |
| **B** | `plugins/*/src/**` | **按角色表**（见 2.2） | ❌ **无豁免通道**——拆分是正解 |
| **C** | `plugins/*/src/index.tsx`（entry） | **120** | ❌ 同上 |

### 2.2 角色表（**按扩展名与首段目录定，不看更深层级**）

```
.css                                  → 300      （放在哪都算样式，含 co-located 的 views/*.css）
plugins/*/src/index.tsx               → 120      （entry = 薄门面）
plugins/*/src/<role>/**.{ts,tsx}      → ROLE_LIMITS[role]
```

```js
const ROLE_LIMITS = {
  views: 150,      components: 150,
  hooks: 150,      utils: 150,          // ← 新增（G3）
  services: 200,
};
```

**三条判定细则：**

1. **`.css` 恒走 300**——不看目录。这样 settings 的 `views/SettingsView.css`（630）与 marketplace 的 `styles/*.css` 用同一把尺。
2. **未知 role 夹 → `throw`（保持现状的 fail-loud）**——新增一个顶层目录（如 `src/store/`）时门禁**报错逼显式上档**，不允许静默落进 800 兜底。
3. **同名夹聚合器 → role 档 ×2**（见 2.3）。

### 2.3 聚合器档（**新增**）

**判定条件（纯机械，零内容分析）**：

> 文件 `X.ts(x)` 的**同级目录下存在同名夹 `X/`** → 该文件按 **role 档 ×2** 计。

仓库现有 **10 对**同名夹（`App.tsx`+`App/`、`KeybindingRegistry.ts`+`KeybindingRegistry/`、`useTabManager.ts`+`useTabManager/` …），**这个信号本来就是 0d.10 feature-folder 拆法的产物**——用它当聚合器判据，既准确又零额外约定。

| role | 常规 | 聚合器 |
|:--|--:|--:|
| views / components / hooks / utils | 150 | **300** |
| services | 200 | **400** |

> 🔴 **决策点（[00 §五](00-整理档案.md) 第 1 条）**：**推荐采纳**。
> 理由：本层拆完的 marketplace `DetailView.tsx` / `marketplaceShared.ts` **本来就是聚合门面**——不给它们一档，下一轮拆的人会为了「凑 150」把门面拆成更碎的碎片（正是 12 档明令禁止的「禁止拆同 domain 平铺多文件」）。
> **注意**：这是**上限放宽**，不是**目标值**。门面仍应尽量薄；300 是「不许超过」，不是「应该做到」。

## 三、代码改动（`scripts/check-file-size.mjs`）

**改动面：常量 + `marketLimit()` + 扫描循环。逻辑框架不动。**

```js
// ① 常量：改名 + 扩域（名字要跟语义走，别留着 MARKETPLACE 的旧壳）
const SCAN_PLUGINS   = true;                 // ← E6#88 翻开关（#30.11 挂靠已废除）
const PLUGINS_ROOT   = "plugins";            // 只扫 <plugin>/src/**
const MARKET_ENTRY_LIMIT = 120;              // ← 重命名 ENTRY_LIMIT（语义已是「所有插件 entry」）

// ② 角色表：去扩展名维度，补 hooks/utils
const ROLE_LIMITS = {
  views: 150, components: 150, hooks: 150, utils: 150, services: 200,
};
const CSS_LIMIT = 300;

// ③ marketLimit() 重写
function pluginLimit(relPath) {
  const seg  = relPath.split("/");
  const base = seg[seg.length - 1];
  if (base.endsWith(".css")) return CSS_LIMIT;              // 扩展名优先
  const dirs = seg.slice(seg.indexOf("src") + 1, -1);
  const limit = dirs.length === 0
    ? (base === "index.tsx"
        ? MARKET_ENTRY_LIMIT
        : (() => { throw new Error(`根级入口未上档（仅 index.tsx → ${MARKET_ENTRY_LIMIT}）：${base}`); })())
    : (() => {
        const role = dirs[0];
        if (ROLE_LIMITS[role] === undefined)
          throw new Error(`未知 role 夹「${role}」未上档——需在 ROLE_LIMITS 显式登记（E6#88）`);
        return ROLE_LIMITS[role];
      })();
  return hasSameNameFolder(relPath) ? limit * 2 : limit;     // 聚合器档
}

/** 聚合器判据：同目录下存在去扩展名同名的文件夹 */
function hasSameNameFolder(relPath) {
  const abs = resolve(ROOT, relPath);
  const d   = dirname(abs);
  const n   = basename(abs).replace(/\.(ts|tsx|css)$/, "");
  return existsSync(join(d, n)) && statSync(join(d, n)).isDirectory();
}

// ④ 扫描循环：plugins/*/src 逐个插件走
if (SCAN_PLUGINS) {
  for (const e of readdirSync(resolve(ROOT, PLUGINS_ROOT), { withFileTypes: true })) {
    if (!e.isDirectory()) continue;
    const src = resolve(ROOT, PLUGINS_ROOT, e.name, "src");
    if (!existsSync(src)) continue;                          // theme-*/lang-* 无 src，自然跳过
    for (const f of walk(src)) scanned.push({ rel: rel(f), full: f, plugin: true });
  }
}
```

**同时更新的注释**（脚本头 §1/§4、`SCAN_*` 处的门开关说明）——**把「翻开关」的历史写进去**，下一个读代码的人才知道为什么它曾经休眠。

**`EXEMPT_FILES` 守卫**：`!f.market` → `!f.plugin`（字段改名，语义一致：allowlist 只管 A 档）。

## 四、🔴 顺序——**必须先拆完，再翻开关**

```
E6#85 主软件  →  E6#86 marketplace  →  E6#87 四插件  →  E6#88 翻开关
                                                        ↑ 这里有 0 处红才成立
```

**翻早了会怎样**：门禁当场列出 **34 条红灯**——**行为正确**（它就该报），但你会被淹没在一屏错误里，失去「哪一条是我刚拆坏的」这个信号。

**先拆后翻的好处**：翻之前 `npm run check` 绿；翻之后仍绿；**中间任何一次变红都精确指向刚改的那一块**。

## 五、🔴 翻开关的验收——**必须包含一次人造红灯**

> memory `snapshot-shadows-truth-bug-class` 的硬要求：**回归测试必须证明在旧行为上会红**。
> 门禁的「旧行为」就是**休眠**——**不证明它能红，就不知道它是否真的醒了。**

**四步验收（机械可复现，做完删干净）：**

1. **绿**：`node scripts/check-file-size.mjs` → ✅ 通过，且 **pass log 的 Top-5 里出现插件文件**（证明插件域**真的被扫到了**，不是跳过）
2. **人造红灯 A（体积）**：临时往 `plugins/marketplace/src/services/` 塞一个 250 行的 `.ts` → 跑门禁 → **必须列出该文件并 exit 1** → 删除
3. **人造红灯 B（角色）**：临时建 `plugins/marketplace/src/store/x.ts`（未登记 role）→ 跑门禁 → **必须 `throw`「未知 role 夹」** → 删除
4. **人造红灯 C（聚合器档）**：
   - 临时在 `plugins/marketplace/src/services/` 建 `foo.ts`（180 行）+ 同名夹 `foo/` → 应**通过**（180 ≤ 200×2）
   - 把 `foo.ts` 涨到 450 行 → 应**报红**（> 400）
   - 删掉 `foo/` 夹 → 应**报红**（180 > 200 才对……即 180 ≤ 200 通过；把文件改到 250 验证）
   - 删除

> ⚠️ **第 4 条要按顺序做**——它同时验证「同名夹在 → 放宽」与「同名夹不在 → 收紧」**两个方向**。只验一个方向 = 聚合器档可能永远放宽（漏网）。

**收尾自查**：`git status` 必须干净（三个临时文件全删）；`npm run check` 全绿。

## 六、`npm run check` 的挂载确认

`check-file-size.mjs` 已挂在 `npm run check`（`package.json`，audit-i18n 之后、eslint 之前）。**本轮不改挂载序**，只改脚本本身。

**确认这条链没断**（「以为它跑了其实没跑」是同一个病根）：

- [ ] `npm run check` 输出里能看到 `✅ 文件体积门禁通过——N 个生产文件零超限` 这行
- [ ] `N` 的值**比翻开关前显著变大**（插件文件计入）——这是「真的扫到了」的外部证据
- [ ] `git diff` 里 `package.json` **无改动**（证明没顺手改挂载序）

**外加一条防「静默休眠」回潮**（class ④ 的对策——`SCAN_MARKETPLACE = false` 当年**不在任何地方报「我睡着了」**，一个月的静默就是这么来的）：

- [ ] **pass log 打出当前生效的档位**，例如：
  `✅ 文件体积门禁通过——618 个文件零超限（档 A src/+electron/ ≤800 · 档 B plugins/*/src ≤角色表 · 档 C entry ≤120）`
  （当前单档口径 = 508 个文件；翻开关后应显著变大）
  这样**任何一个档被关掉，输出行里就少一段**——休眠是可见的，不是隐形的。
- [ ] 门禁脚本**收尾不再有 `SCAN_* = false` 的开关**（本层之后不存在合法的关闭态；若未来要关，必须在 pass log 里打出「⚠️ 插件档已关闭」）。
