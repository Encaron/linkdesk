## 一、Context——为什么要有真机环

**动机源（Encaron，2026-09-07 讨论）：**
1. 万物皆可插件 + 目标 = 插件作者能制作**任意插件**（文件树 / Eclipse、Monaco 类编辑器 / CAN-bus / 示波器 / 愤怒的小鸟游戏），并享受**便利 ≥ 内部开发便利**——内部改 serial-monitor 只需重启 `npm run electron:dev` 即可验证。
2. WPF serial-monitor v2 创伤：只靠每次 AI 生成可执行 exe 双击——慢、后期 150MB、git 膨胀 15GB。**绝不给 LinkDesk 插件作者封死快捷调试通路**——作者不应被逼每次完整封包才能看效果。
3. E4 体量级 bug（见下）证明：**没有便利的真实调试，不可能顺利**；作者端还想要像内部一样的 **CDP/AI 全自动调试**（"pcd"）。
4. 纯浏览器 mock dev 对「需要真 IPC 的插件类」**不够**——这类插件必须真有壳 + 真 IPC 才能显形其 bug。

**为什么浏览器 mock 替代不了真机（E4 bug 家族实证，memory e4-complete / e5.5-7-editor-multi-webview-bugs / monaco-addcommand-global-trap）：**
- Monaco R17 = 5 失败 → 1 正确路径（standalone `monaco.editor.create()`，非 monaco-vscode-api）；worker 初始化时序 / IPC channel 碰撞 / singleton 跨 JS heap 隔离 / `addCommand` 全局动态键绑定陷阱（→ `editor.addAction`）——**只在真壳 + 真 IPC 下复现**。
- 文件树 sticky（E4V#57 弃）、monaco 字体/不启动——无便利真机调试不可能趟平。
- 结论：**真机环是必需，不是可选**（第三方作者尤其——没有内部壳源码/构建）。

## 六、A 的实现要点（执行期参考，非本轮代码）

1. **watch** 作者源码（`dev --real` 复用 vite dev server 之外的第二态，或独立 chokidar）→ 变更触发**隔离单插件 build**（复用 #25/#15 已建：vite-config `defineLinkdeskPluginConfig` → index.bundle.js + css/i18n 资源）。
2. **直写** `{userData}/plugins/<id>`（平台 %APPDATA%/linkdesk；`LINKDESK_USER_PLUGINS_DIR` 可覆盖）——产物 = 完整物化目录（plugin.json + bundle + 资源 + i18n），不经 `plugins:extract`（存在即拒）、不碰 #15n boot 门禁。
3. **reload**：作者以 `--remote-debugging-port=9222` 启动 LinkDesk（Chromium 原生 switch）→ SDK 经 CDP `Page.reload` 刷池窗口（目标 "LinkDesk Pool"）→ renderer 重 import 生效。CDP/AI 调试 = 同一 9222 入口。
4. **sourcemap**（执行期细化）：build 产物带 sourcemap 供 CDP 源级断点，非阻塞。

**风险与边界：** 直写覆盖不备份原插件（真机环针对作者自研 dev 插件，非用户市场已装插件——文档要写明作用域）；多插件工程并行 dev 需各自独立（一个 `dev --real` = 一个 dev 插件目录）；CSS 热更走整窗口 reload（秒级，非亚秒 HMR——那是 B 的卖点，B 门控后定）。

## 七、便利度账本——#62 dev 源码特快轨退役会降便利吗（2026-09-07 定论）

> 用户质询「#62 退役源码特快轨，未来是否便利度下降」→ 分群/分轴拆解定论。护栏已落 E6#62c 验收子项；本表每轮审视复用，不重新辩论。

### 7.1 受影响面分三群（#62 只打一群）

| 作者群 | dev 循环 | #62 影响 |
|:--|:--|:--|
| 第三方 UI 插件（无真 IPC） | SDK 浏览器 dev-host（#24 + #27 mock）——Vite HMR 亚秒 | **零**——#62 只动壳内置插件源码 glob |

### 7.2 壳团队三轴拆解——真降只有半截轴

| 轴 | 今天 | #62 后 | 判定 |
|:--|:--|:--|:--|
| ① 改 UI 看效果（最快内环） | 真壳内亚秒 HMR | dist 消费（插件级 reload ~1s + 视图重挂载） | **唯一真降**——但浏览器 dev-host 有亚秒替身（内置插件也是插件）；真降面 =「真壳内免挂载逐字改 UI」= 恰好隐藏生产 bug 的路（#17d serial 状态栏缺口 993daf80f：dev 源码 glob 正常、打包态才现形；E4 bug 家族同源） |
| ② 改真机/协议逻辑验证（串口/IPC/LSP） | 本就需真设备 + 重载 | watcher 秒级 | 不劣于基线（内部 `electron:dev` 重启 = 数秒~十几秒） |
| ③ 改壳主进程 | 必须重启 electron | 同 | 与 #62 无关 |

**#62 本质**：用「改完能信 dev==prod」（#15f/#17d 单一路径贯彻到底）换「真壳内亚秒微迭代」这一小块便利。

### 7.3 会不会回 WPF v2 创伤——判据 = 有没有手动封包

WPF 创伤痛点 = **手动**完整重打包 + 重装 + 重启（分钟级 + git 膨胀）。dist+watcher 三反：

- **零手动封包**——watcher 自动触发隔离单插件 build（~1s）
- **零重装**——直写 dist，非 zip 重物化
- **插件改动不碰主进程**——renderer 侧 reload，不重启 electron

**防创伤靠自动化，不靠源码特快轨。** 三条护栏 → E6#62c 验收子项。

### 7.4 亚秒真窗 HMR 没被堵死——逃生门 = B（#28.7）

#62 退役的是**生产相邻 loader 上的源码特快轨**，不预判独立 dev 实例机制（extensionDevelopmentPath 类比）未来经 #28.7 成本化再拍板成立。真机环（A）与壳侧 dev（#28b）同走 dist 消费族引擎（见 §四 四形态表）。
