## 二、① 搬家——1:1 映射，零解释成本

### 2.1 映射规则（机械，不用判断）

```jsonc
// 搬前：plugin.json
"changelog": [
  { "version": "1.0.7", "date": "2026-09-11", "changes": ["内部整理（E6#87b…）：…"] },
  { "version": "1.0.6", "date": "2026-09-10", "changes": ["README 展示区封面随包…"] }
]
```

```markdown
<!-- 搬后：CHANGELOG.md（版本已倒序，与源同序，不重排） -->
# 更新日志

## v1.0.7（2026-09-11）

- 内部整理（E6#87b 文件整理层）：1642 行主视图按 12 档拆为 24 件同名夹 + …

## v1.0.6（2026-09-10）

- README 展示区封面随包（E6#70a）：说明区静态图经 assetBase 解析 linkdesk:// 包内资产真加载
```

- `version` → 段标题 `## v{version}`（**带 `v` 前缀**——[09 规范](01-规范文档对齐.md) 的示例形态）
- `date` → 段标题括号 `（{date}）`（**全角括号**，与既有 README 文风一致）
- `changes[]` → 段正文**逐条一行 bullet**（`- ` 前缀）。**多条 = 多行**，不合并、不改写、不缩写
- **数组顺序原样保留**（源已是最新在前）
- 文件头固定 `# 更新日志` 一行 + 空行

## 四、③ settings 的 i18n——**初判是缺口，实测不是；真东西是两处键错位**

### 4.1 🔴 先纠正一个判断（**这是本档案里最容易抄错的一段**）

**初判**：settings 有 **54 处 `t()` 调用 / 46 条去重文案**，却**没有自己的 `i18n/` 目录** ⇒ 判「缺 46 条译文，要补 `i18n/en.json`」。

**这个判断是错的。** 错在**把 i18n 字典当成了「插件私有财产」**。

> **LinkDesk 的 `t()` 走的是壳提供的同一个 react-i18next 实例**——各插件 `contributes.i18n` 声明的字典**汇进同一个全局 bundle**。所以 **settings 的文案可以由任何插件的字典提供**，不需要自己有目录。

**实测（2026-09-11）**：settings 的 46 个去重 key 里，**44 个已在 [`plugins/lang-defaults/en.json`](../../../plugins/lang-defaults/en.json)（443 key）**里——那是**随壳发货的默认语言包**（`lang-defaults` 是一只普通插件，`en.json` + `zh.json` 都在）。

**⇒ settings 不需要补 `i18n/`。** 佐证：`npm run check` 里的 `audit-i18n.mjs --strict` **本来就报「缺翻译 0」**——**门禁一直是绿的，是我一开始没用门禁判。**

> 🔴 **教训（写给下一个 AI）**：判「某插件缺不缺译文」**不要**数它有没有自己的 `i18n/` 目录——**跑 `node scripts/audit-i18n.mjs`，那是唯一权威**。
> 🔴 **python 也同理**：它**0 处 `t()`**（没有 UI 文案），没 i18n 目录是对的。**两只都不是缺口。**

### 4.2 但顺着这条线抓出**两个真 bug**

#### B-i18n-1｜`t("newPattern")`——把「数据标识符」错当「UI 文案」翻 🔴

[ObjectEditor.tsx:39](../../../plugins/settings/src/views/SettingsView/ObjectEditor.tsx)：

```ts
const baseKey = t("newPattern");     // ← 这是「点 + 新增一行」时给新行起的默认键名
```

**三条问题，任一条都够立案：**

1. **它根本不是 UI 文案**，是**用户配置里的一个键名**（`newPattern` / `newPattern1` / `newPattern2`…）——**数据标识符不过翻译**。
2. **全仓任何字典都没有这个 key** ⇒ 靠 `parseMissingKeyHandler` 回落成字面量 `"newPattern"`。**它现在能用纯属巧合。**
3. 🔴 **陷阱**：**只要有人真的补一条 `"newPattern": "新条目"`，新增行的键名就变成「新条目」并写进用户配置**——**「补翻译」= 制造数据损坏。**

**修法**：`const baseKey = "newPattern";`（去 `t()`）+ 一行注释说明「这是数据键名，不是文案」。

**顺带暴露一个门禁盲区**：`audit-i18n.mjs` **只扫中文**（设计如此，作者可用任意语言当 key）⇒ 这种**标识符形态的 `t()` key 它完全看不见**。扩域候选见 [06 号档案](06-门禁扩域与验收.md)。

#### B-i18n-2｜`t("加载中...")`——3 个 ASCII 点 vs 1 个省略号字符 🟡

[SettingsView.tsx:195](../../../plugins/settings/src/views/SettingsView.tsx)：`t("加载中...")` 用的是**三个英文句点**；而字典里的 key 是 **`加载中…`（U+2026 单字符省略号）**。**两者不是同一个字符串。**

- **现在之所以英文能显示**，是因为 `plugins/marketplace/i18n/en.json` 里**恰好有一条三点版本** ⇒ **settings 的这句文案在靠 marketplace 的字典活着**。
- **marketplace 若被卸载** ⇒ 英文模式下 settings 显示中文「加载中...」。
- `audit-i18n.mjs` **也没报**——它比对的是**全插件字典的并集**，marketplace 那条把它盖过去了。

**修法（推荐 (a)）**：**(a)** 调用方改成 `t("加载中…")`——字典已有，**改一处**；**(b)** 在 `lang-defaults/en.json` 再补一条三点 key（**不推荐**：三点写法本来就是笔误，补它 = 把笔误固化）。

### 4.3 结论

- **不补 `i18n/`**，**只修上面两个键**。
- **版本**：B-1 零行为变化（键名字面量不变），**B-2 是用户可见**（英文模式显示中文）⇒ 取最高 ⇒ settings **`1.0.4 → 1.0.5`（`fix:`）**。

## 六、版本轴判定（🔴 逐只算，别一刀切）

**判据**：`version` 表示「插件对用户变了吗」。本轮的变更是**元数据存放位置 + 补缺失资产**——用户装上后**看到的东西变了**（更改日志页签从「未附带」变成有内容；marketplace 详情页从空变成有 README）。

⇒ **补了内容的插件 = 用户可见变化 = bump**；**只搬位置的**……

| 插件 | 用户可见变化 | 判定 |
|:--|:--|:--|
| **marketplace** | 详情页「详情」页签从空 → 有内容；「更改日志」页签 27 条从无 → 有 | **bump**（`1.0.27` → `1.0.28`，`fix:`） |
| **settings** | 英文模式下「加载中...」从中文 → 英文（B-i18n-2）；B-i18n-1 零行为变化 | **bump**（`1.0.4` → `1.0.5`，`fix:`） |
| editor / file-tree / python / serial-monitor / lang-defaults / theme-aurora-glass / theme-terminal | 更改日志页签从「未附带」→ 有内容 | **bump**（各 +1 patch，`fix:`） |
| 11 只空插件（若做 ④） | 同上 | **bump**（各 +1 patch） |
| **软件轴** | 无变化 | **不动**（0.1.47 保持） |

> ⚠️ **不打包上新版本来做这件事的例外**：若某只插件的 `CHANGELOG.md` 内容**完全等于**它 `plugin.json` 里原有的 49 条、且该插件**本来就是 bundled 随壳发货**——bump 的后果是「bundled 版本号变了但 zip 内容也变了」，**是应该 bump 的**（承 [12-插件目录与UI细节 §一·五](../03-插件市场/12-插件目录与UI细节.md)「plugin.json 同步铁律」）。
> **判定现算**：`node scripts/check-bundled-version-bump.mjs` 三档（`identical` / …）——**产物真值说了算，不是这条笔记说了算**。
