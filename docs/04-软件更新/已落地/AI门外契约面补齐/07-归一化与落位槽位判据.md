## 一、六条判据 → 本档的机械形态

| 判据 | 抽象要求 | 本档的具体落点 | 可机械判定 |
|:--|:--|:--|:--:|
| **归一化** | 同一个概念只有一个定义；一个 bug 不会在多处出现 | 描述面一份声明（manifest）· 解包一份 `unwrap` · 错误信封一份构造 · op 表一份 · 方向/解码各一处 · `activation` 一个真相源 | ✅ 部分 |
| **AI 友好化** | 可读 · 可操作 · 可查 | `describe` 带 `activation/risk/returns/example` · 失败带码＋hint · 异步带 `opId` · 规模大能筛 | ✅ 部分 |
| **无硬编码** | 行为由声明驱动，不写字面量 | ⛔ 插件 id / 命令 id / 编码列表副本 / 风险词表 / 手填 apiVersion | ✅ |
| **无死代码** | 不留只打日志的桩、不留无人走的分支 | `placeholder` → 真懒激活入口 · 删 `_cmdMap.size <= 1` · 删「整片摘＋补注册」· `--brief` 不做就⛔ 留半成品 | ⚠️ 人工＋审计 |
| **高内聚低耦合** | 壳不认识业务；插件不感知壳内部 | 壳只认 `activation/scope/risk/schema` 四个通用标记 | ⚠️ 人工审查 |
| **文件禁止平铺** | 一模块一职责；⛔ 巨型平铺文件 | 文档一主线一档（00 只索引）；代码按层拆（policy / registry / preload / sdk 各司其职） | ⚠️ 人工＋行数 |

> 🔴 **「归一化」不是「抽公共函数」**：抽的是**语义与行为**（判据 A）。两个地方长得像但意义不同（如描述面游标 vs 串口 `readSince` 游标），**不共享**——共享了才是错。

## 三、槽位预留规则（新字段怎么加，才不变成下一笔债）

三条硬规则，适用于本档所有 schema 变更：

1. **字段增删按阶段**：
   - **内测期（当前，决策 #10）**：允许**直接破坏**——旧字段该删就删、签名该改就改，⛔ 留兼容分支（兼容层＝死代码）；
   - **对外开放后**：回到「只加可选字段（`?`）、缺省行为 = 当时行为；破坏性变更 ⇒ 先加新字段并行、下个大版本删旧字段」。
2. **一个字段只能有一个真相源**。声明面与运行期都能提供时，必须写明「谁是真值、谁是提示」——
   - `activation`：运行期真、声明是提示；
   - `risk`：声明真、壳表只对壳命令；
   - `returns`：声明真、`doctor` 负责抓漂移。
3. **契约版本 ≠ 软件版本**。`apiVersion` 由壳统一生成；命令面结构变化才 bump；⛔ 作者手填。

> 判据：新增字段时问一句「**第二个作者不看第一个人源码，能不能填对**？」——填不对 ⇒ 槽位没开好。

## 四、无硬编码清单（进代码前逐条排除）

- ⛔ 壳内出现第三方/官方插件 id 字面量（硬约束 10 的同族）。
- ⛔ 壳内出现插件命令 id 字面量（`serial-monitor.send` 这类）；需要引用走声明/常量表。
- ⛔ 风险按动词词表猜（`send`/`write`）；风险只能声明或保守兜底。
- ⛔ 编码列表在壳/插件各存一份；「自动」是值不是列表。
- ⛔ `apiVersion` 手填、`activation` 按插件名判。
- ⛔ 为 doctor 另写一套 HTTP/JSON 客户端（复用 `bridge-client`）。
- ⛔ 测试 fixture 用真实插件名/真实文案（硬约束 21）。

## 五、无死代码清单（本档要清掉的既有死代码）

| 位置 | 现状 | 处置 |
|:--|:--|:--|
| 壳注册表的 `placeholder` handler | 只打诊断 warn，不可执行 | 变成「懒激活入口」——声明仍可见，调用触发 import |
| `useViewCommands.ts` 的「整片 unregister ＋ 补注册」 | 为绕开「分区缺失」写的适配层 | 分区后整段删除 |
| `_cmdMap.size <= 1` | 依赖跨 hook cleanup 顺序的脆弱判断 | 删除（作用域天然按实例） |
| `quickSendEdit/Delete` 双注册 | 同一 id 两个作用域 | 收敛为一个作用域 |
| `--brief` | 被降为低优后悬着 | 要么不做（删开关），要么到触发线再做 |
| 裸字符串错误（「未在池内注册」） | 门外不可判读 | 换 `EVIEWREQUIRED`/`ENOTACTIVE` |

## 六、文件组织判据（「禁止平铺」的具体含义）

- **文档**：一主线一档；`00` 只做索引/决策/待办，⛔ 不复制各档正文；数字带即分组（**00–07 方案** / **08–12 施工与连锁**），同类⛔ 再开新档；单档 > 250 行时按子主题拆；⛔ 多层级嵌套目录（保持单层）。
- **代码**：一模块一职责——`policy/` 只管判定，`registry/` 只管注册表，`preload-pool/` 只管桥接，`sdk` 只管作者面；⛔ 把「判定＋注册＋映射」揉进一个文件。
- **判据**：一个文件能不能用一句话说清它负责什么？说不清 ⇒ 拆。

## 八、准入流程（每笔改动前，30 秒过一遍）

```
1. 查 §二 落位表：这个概念唯一的家在哪？我这笔是不是在造第二个家？
2. 查 §三：新字段是可选的？真值写明了？第二个作者能填对？
3. 查 §四/§五：有没有写字面量？有没有留下桩？
4. 查 §六：文件是否一职责？文档是否在往 00 里堆正文？
5. 查 §七：这笔该由哪条腿守？没有腿 ⇒ 先补腿还是先写人工审查理由？
6. 最后对 [10 条判据](../../../开发管理/新能力设计流程.md)：不符合的写理由，⛔ 沉默略过。
```

## 九、跨档引用规则（防「第二份真相」）

本档与相邻档（[底盘](../../待抉择池/通用能力底盘/00-提案.md) · [权限系统](../../待抉择池/插件权限系统/00-提案.md) · [表现层可替换化](../../待抉择池/万物皆可插件-表现层可替换化/00-提案.md)）的共存纪律：

1. **一个概念只在一个档定义**；其他档**只引用**，⛔ 复制正文（复制＝未来必然漂移）。
2. **冲突写法**：先按 [12 §一](12-相邻任务关系与边界.md) 的优先级裁；裁完把结论写进 [12 §六 冲突登记表](12-相邻任务关系与边界.md)，⛔ 只改一处文档了事。
3. **名词不造同义**：`capabilities`（能力）与 `risk`（风险）、`activation`（可达性）与 `when`（可见性）——各自有明确所指，⛔ 互相替代或改叫法。
4. **门禁可共用、判据必须分开**：一条脚本腿可以查两件事，但每件事要有独立的断言与报错文案。
5. **新增/修改任何字段**，同笔检查：manifest schema · SDK 类型 · 03 中英文档 · AI 手册生成区 · 相邻档的根引用——**五处缺一即视为未完成**。
