> 2026-07-28 Encaron。此任务汇集了从 E3f 到 E3j 反复出现、反复修、反复回退的双份渲染问题。
> **这是 E3 真正的最后一个任务——前面的修修补补都是止血。这里动根基。**

---

## 一、什么是双份渲染

LinkDesk 的插件同时存在于两个地方：

| 实例 | 位置 | 目的 |
|------|------|------|
| WebView 实例 | 独立 WebContentsView | 多 WebView 架构——进程隔离 |
| React fallback | 壳主窗口 DOM | 安全网——WebView 崩了/没加载完时有 UI 兜底 |

历史原因：E3a 建了多 WebView 基础设施，但不敢立即关掉壳里的旧渲染——怕 WebView 没就绪用户看到空白。于是留了"渐进增强"：WebView 覆盖在 React fallback 上面，用户看到 WebView；WebView 失败时 fallback 可见。

**设计意图是好的——渐进增强不是断崖切换。但实现有缝。**

## 二、完整历史——这个问题捅了 5 次

### 第 1 次：#58d MainContent 集成（E3f）

```

d1c8685 revert: #58d MainContent 回退 🔙
```

**做了什么：** MainContent 里把 React 组件换成空 div，只靠 WebView 渲染。
**为什么回退：** 多 WebView 还没激活（registerPlugin 从未被调用），所有插件回到壳渲染。空 div = 空白。

### 第 2 次：#58e 关 React fallback（E3f）

```

```

**做了什么：** 有 WebView 的插件 → React 不渲染组件，返回空 div。
**为什么回退：** ref 异步更新 → 第二帧切空 div → WebView 未就绪 → 空白。改成 useState 也不行——时序窗口依然存在。**用 git checkout 逐 commit 二分定位**找到根因后决定回退。

### 第 3 次：#58e 信号驱动（E3f，当前方案）

```
a52085f fix: #58e 正确实现——WebView ready 信号驱动切换
fffac1c fix: ErrorBoundary + requestAnimationFrame 保底
```

**做了什么：** 6 文件信号链——WebView 渲染完 `notifyReady` → `plugin-view:ready` IPC → 壳收到 `onReady` → `setReadyWebViewIds` → re-render 切空 `<div>`。
**效果：** ready 后壳切空 div、WebView 覆盖。ready 前 React fallback 保底。比前两次好——**渐进增强**，但 temporally 有一段窗口。
**遗留问题：** `SerialContext._initIPC()` 是模块级的，ready 前就跑了一次，初始化后永不清理。webContents 的 `ipcRenderer.on` 监听器在切空 div 后仍然活着。

### 第 4 次：E3j #77 数据上桌（崩溃）

```
d2a4a13 E3j #77: 终端推送原始串口数据到大厅
→ 壳崩（events.emit 不存在）
d14bfe4 fix: 壳 preload 加 events.on/emit（临时止血）
825f7ce fix: 删了发给壳的 plugin:push（后来补回 99e680f）
```

**做了什么：** SerialContext 收到串口数据→`events.emit('serial:rawData', ...)`。
**为什么崩：** 壳 fallback 的 SerialContext 调了 `events.emit`，但壳 preload 没有这个方法。
**为什么以前不崩：** 以前 `_initIPC` 只做数据接收（写 ringBuffer），不做发射。加了 emit 才暴露出来。

### 第 5 次：E3j #77a-77b（归一化 + 错误假设）

```
b32f1e2 E3j #77a: events 归一化——提取 event-system.ts
c74159d E3j #77b: 双份渲染无害共存——fallback 只渲染不发射
3eea884 fix: #77b 回退——数据只到一个地方，守卫堵了唯一管道
```

**#77a 做了什么：** `preload-plugin.ts` 和 `preload-shell.ts` 的 events 系统提取到 `electron/event-system.ts` 共享。**这部分是对的。**

**#77b 做了什么：** 加 `isPluginWebView` 守卫——检查 `pluginViews.notifyReady` 存在性，只在 WebView 实例里 emit。

**实测推翻：** 串口数据只到打开端口的 webContents，不是两处。守卫把唯一管道堵了。已回退。

## 三、三条根因

### 根因 1：双份渲染同时存在

SerialContext（和其它插件模块）在两个 JS 上下文各跑一份。它们互不知情，各自注册 IPC 监听器、各自写 ringBuffer、各自发事件。

**为什么不直接关掉一份：** 试了 3 次（#58d、#58e×2），每次都失败。因为 WebView 加载是异步的，不能保证"关 React 的时候 WebView 已经就绪"。

### 根因 2：`_initIPC()` 是模块级的，永不清理

```typescript
let _initialized = false;
function _initIPC() {
  if (_initialized) return;
  _initialized = true;
  // 注册 ipcRenderer.on('serial:data', ...)
  // 这些监听器永远不会被 removeListener
}
```

模块级初始化 = 导入就执行一次 = 永远不清理。即使壳切到空 div、组件 unmount，IPC 监听器还在。以后新加数据管道、新加事件发射都用这个模式 = 新 bug 温床。

### 根因 3：串口数据的路由不确定

串口数据到哪取决于谁调了 `openPort`——是壳的 fallback 还是 WebView。
这不是代码能控制的——取决于用户操作时序和应用启动状态。
所以同样的代码、同样的测试环境，有时数据到壳、有时到 WebView——现象不稳定。

## 四、之前所有尝试为什么失败

| 尝试 | 思路 | 失败原因 |
|------|------|---------|
| #58d | 删 React 渲染 | WebView 还没激活 |
| #58e 第一版 | ref/state 异步关 | 时序窗口：关 React 时 WebView 未就绪 |
| #58e 第二版 | ready 信号驱动 | ready 前模块级代码已初始化，清不掉 |
| #77b | 守卫区分身份 | 数据路由不确定→假设错误 |

**共性问题：试图从外部"关掉"一份渲染，而不是从内部让模块知道自己该做什么。**

## 五、建议的修复方向

以下是给新 AI 的出发点，不要求照做——自己分析后决定。

### 方向 A：让 SerialContext 感知自己的运行环境

在 `_initIPC` 或类似初始化代码中，判断自己是在 WebView 还是 fallback 中运行。Fallback 实例只做最小安全工作（渲染 UI 壳），不做数据处理和事件发射。

**判别方法候选：**
- `window.linkdesk.pluginViews.notifyReady` 存在 → WebView（当前 preload 差异）
- WebView 的 `plugin-view.html` URL 参数
- 更彻底的新机制：传递环境标识

### 方向 B：把 IPC 初始化从模块级改为组件级

`_initIPC` 注册的监听器应该有对应的清理机制。改为 React effect 或提供 `dispose()` 函数，在组件 unmount 或 WebView ready 后调用。

**挑战：** `SerialContext` 是模块级共享状态——多个组件读同一份 state。改为组件级可能需要重构共享状态管理。

### 方向 C：接受双份渲染，让双方协作而不是冲突

两个实例都跑，但用某种机制（如互斥锁、主从选举）保证只有一个做"主动"工作（emit 事件、写持久化），另一个只做"被动"显示。

7. **设置页正常：** 配置读写
