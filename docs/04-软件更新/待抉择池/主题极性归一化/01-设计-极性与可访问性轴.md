# 主题极性归一化 · 设计正文

> 配套：[00-README.md](00-README.md)（根因、市场对照、范围与验收）· [polarity-preview.html](polarity-preview.html)（可交互稿）。
> 状态：设计稿待看；未动代码。

## 一、数据模型

### 1.1 主题配方（recipe）

```jsonc
{
  "id": "theme-x",
  "name": "X",
  "type": "light",        // 可选；降级为 hint（解析不出 token 时兜底）
  "appearance": { ... },  // 材质轴：glass / background（已有）
  "colorways": [
    {
      "id": "theme-x.a",
      "name": "A",
      "traits": { "contrast": "high", "colorVision": "deuteranopia" }, // 新增、可选
      "colors": { ... }
    }
  ]
}
```

- `type` 不再决定 `data-theme`；只作为“作者意图提示”和 token 解析失败时的兜底。
- `traits` 只加不删；未知值按 standard 处理（前向兼容）。
- 材质（flat / glass / panorama）继续走 `appearance`，不塞进 type。

### 1.2 派生结果

```ts
interface ResolvedAppearance {
  polarity: "light" | "dark";
  material: "flat" | "glass" | "panorama";
  contrast: "standard" | "high";
  colorVision: "default" | "deuteranopia" | "protanopia" | "tritanopia";
  source: "declared-hint" | "derived"; // 便于调试与作者提示
}
```

## 二、极性判据

### 2.1 算法

1. 取**生效** `text-primary` 与 `bg-window-solid`（无则 `bg-card-solid`，再无则 `bg-window`）。
2. 用 `ThemeEngine/color.ts` 的 `colorLuminance`（WCAG 相对亮度）；解析不出（`color-mix` / `var`）→ 用 `type` hint；hint 也无 → 按 `text-primary` 是否存在回退。
3. `textLum >= surfaceLum` → `dark`（亮字压暗面）；否则 `light`。（相等按 `light` 处理，避免黑底纯黑字被误判。）
4. 结果写 `data-theme`，并进 `theme:changed` 的 `polarity` 字段。

### 2.2 边界

| 情况 | 行为 |
|:--|:--|
| 玻璃 + 亮图，表面实质很暗但 token 是亮主题 | 以 `text-primary` 为准；若作者写反，主题审计报“正文与表面同极” |
| 跨明暗 colorway（暗配方 + 亮配色） | 派生按 colorway 生效 token 算 → 自动变 `light`；UI 标签同步 |
| 自定义 tint / 背景遮罩改变明暗 | `-solid` 基色已吸收 tint；图片极端亮部由 `maskColor` 收敛 |
| token 是 `var()` / `color-mix()` | 先求值（引擎已有 resolve）再算；求不出才用 hint |
| 第三方旧主题无 `traits` | `contrast=standard`、`colorVision=default`，行为零变化 |

## 三、广播与快照

- `theme:changed` 载荷增加 `polarity`；`themeType` 保留同值（兼容旧插件）。
- `preload-pool` 的 `data-theme` 从 `polarity` 写；旧池代码无需改。
- `ThemeSnapshot` 升 `v`，存 `polarity`；旧快照直接丢弃重算（首帧由快照铺，避免闪）。
- 壳内 `:root` 的 light/dark 默认块继续存在，`data-theme` 只用于 CSS 选择器，不用来表达“作者 type”。

## 四、UI

- **主题选择器**：平铺 + 徽标（`亮/暗（派生）`、`高对比`、`色觉友好`），不按声明 type 分组。
- **跨明暗警告**：改为“base 与 colorway 的派生 polarity 是否一致”，不再看配方 type。
- **DynamicSelect**：括号标签取派生 polarity。
- **开发者信息**（可选）：主题详情显示 `声明: light · 派生: dark · material: glass`，便于排查。
- 高对比：用户级开关（standard / high）优先于 colorway traits；两者都是“选择哪组 token”，不改引擎公式。

## 五、编辑器插件（`editor`）

现状：`theme-sync.ts` / `buildMonacoOptions.ts` 读 `data-theme`，只切 `vs` / `vs-dark`。

### 5.1 第一阶段（随极性归一化自动正确）

- 壳广播 `polarity` 后，`data-theme` 已是派生值；编辑器**零代码改动**即可在“暗配方亮配色”等场景选对 vs/vs-dark。
- 仍有两套固定 Monaco 主题，玻璃/彩色主题只影响外壳，不影响代码区。

### 5.2 第二阶段（大改，随本任务一起做）

- 订阅 `theme:changed` 的 tokens，`defineTheme` 生成当前主题的 Monaco 主题：
  - `editor.background` = `bg-window-solid`（**不透明近似**）
  - `editor.foreground` = `text-primary`
  - 行高亮/选区/边框 = `bg-selection` / `border` / `accent`
  - token 色：关键字用 `accent`，字符串/注释用主题状态色（缺省由引擎派生）
- **透明度取舍**：Monaco 正文区不承诺真透明；玻璃主题下只让外围 UI 透明，代码区保持可读。若未来 Monaco 支持可靠 alpha，再评估。
- 兼容：主题缺 token 时回落到内置规则；`polarity` 仍决定 `base: vs | vs-dark`。

## 七、测试

- 纯函数：`resolvePolarity` 的 light/dark、跨色、玻璃、`var()`、缺失键、相等亮度。
- 引擎：`applyTheme` / `applyRecipe` / 混搭 / 自定义 tint 后 `data-theme` 与 `polarity` 一致。
- 快照：旧版本丢弃、新版本回读一致。
- 广播：`theme:changed` 含 `polarity`，不含 accent 组键（已有约定）。
- 编辑器：四组主题下 Monaco 主题名与 `polarity` 一致；token 主题颜色生效。
- UI：选择器徽标、跨明暗警告、DynamicSelect 标签随派生值变化。

## 八、风险

1. **图片主题**的派生极性可能仍与视觉有偏差——用 `maskColor` / 阅读面收敛；作者数据审计兜底。
2. **第三方插件**若把 `themeType` 当渲染真相，会继续工作（同值兼容），但拿不到新语义；文档标注 deprecated。
3. **Monaco 透明度**不可承诺；提前在任务里写清取舍，避免“玻璃编辑器”预期落空。
4. **快照升级**会让首帧短暂使用默认主题；用 `v` 版本丢弃 + 重算，避免旧快照污染。

## 九、Monaco 旧 bug 防线（必读：本次改动最容易碰响的地雷）

编辑器历史上有过一组**高度相关**的实机 bug，改主题同步前必须逐条对照，否则会原样复发：

| 历史 bug | 根因 | 现有防线（不能拆） |
|:--|:--|:--|
| **B4 暗色字体黑**（`StandaloneWorkbenchThemeService` 异步竞态） | `loadThemes:false` ⇒ `vs-dark` 根本没注册；`setTheme()` 走异步 `getColorThemes()`，窗口期内用错主题 | `monacoBootstrap` 保持 `loadThemes:true`；`create({theme})` ＋ `editor.updateOptions({theme})` 双设；`theme-sync` 不走纯全局 setTheme |
| **DiffEditor 先于编辑器 mount 即黑字**（latent E5.6#2） | DiffEditor 缺补丁前置 / 初始主题未双设 | `monacoBootstrap` 单门收敛顺序；DiffEditor 也走同一 bootstrap ＋ 实例 updateOptions |
| **主题切换后 Monaco 仍是另一种颜色**（多 WebView） | 用了隔离的 `CoreEvents.onDidChangeTheme`，壳广播到不了插件 WebView | 只走 `window.linkdesk.events.on("theme:changed")`（`plugin:push` → `IpcBridge.broadcast`） |
| **React 竞态：初始 options 与 mount 后主题不一致** | `optionsRef` 未桥接 / EditorTab 初始 options 未主动 apply | 保留 `optionsRef` 桥接 ＋ 初始 options 主动 apply（`427217c` / `a129288` 的治本路径） |
| **生产 `file://` 主题扩展加载失败 ⇒ token 色错**（E5#114d） | `@codingame` 主题扩展在打包环境解析失败，CSS 规则不生成 | `defineTheme` 纯 Monaco 原生兜底，先于 `setTheme` |
| **静态 import Monaco 抢在补丁前** | 原生主题系统先初始化，`StandaloneWorkbenchThemeService` CSS 注入用部分固化状态 | 禁止静态 `import * as monaco`；只经 `monacoBootstrap` 动态加载 |

### 9.1 本次新增的风险点（token 化 Monaco 主题）

1. **动态主题名**：token 主题会按“主题 × 对比度”生成名字（如 `ldk-<hash>`）。`defineTheme` 必须**幂等**：同名只定义一次；定义失败立即回落 `vs` / `vs-dark`。
2. **自定义主题名可能不在 `getColorThemes()`**：`setTheme` 仍可能走异步 service；必须保留**双路径**（`defineTheme` → `setTheme` → 每个 editor `updateOptions`），不能只调全局 `setTheme`。
3. **token 色必须是 Monaco 可解析的字面值**：`var()` / `color-mix()` 先经引擎求值成 hex；求不出就回落静态 `DARK_TOKEN_RULES` / `LIGHT_TOKEN_RULES`，⛔ 不能把 `var(--x)` 直接塞给 `defineTheme`。
4. **base 必须跟 polarity**：`base: polarity === "dark" ? "vs-dark" : "vs"`。派生错 = 黑字压黑底；这是 B4 的翻版。
5. **DiffEditor 必须同批更新**：`getEditors()` 只返回 standalone code editor；DiffEditor 的两个 editor 要单独 `updateOptions`，否则分屏/对比页会留旧主题。
6. **字体不是主题**：`editor.fontSize` / `fontFamily` 仍走 `editor.*` 配置与双轴正交（E5.8#179），⛔ 不要把字体塞进 token 主题，否则“切主题字体变黑/变大”的老症状会回来。
7. **首帧**：编辑器 create 时的初始 theme 必须来自**当前快照/广播**，不能等 `theme:changed` 事件；否则先黑后白闪一下。

### 9.2 验收（按老 bug 的诊断签名反测）

- 暗色下**首次打开**编辑器：字体不是黑色；Ctrl+滚轮缩放正常；**不靠“随便改个设置”才恢复**。
- 亮 ↔ 暗快速切换 10 次：Monaco 与外壳同步，无残留旧色。
- 先开 DiffEditor 再切主题；先切主题再开 DiffEditor：两边都对。
- 无编辑器时切主题 → 再开编辑器：初始 theme 正确（不闪黑）。
- 高对比切换：token 主题重建且 `base` 不变；字体大小不变。
- 关闭主题插件/主题加载失败：回落 `vs` / `vs-dark`，不白屏、不黑字。
- 静态 import 门禁：编辑器入口无 `import * as monaco`；`loadThemes:true` 有测试钉住。

> 结论：**极性归一化本身不碰 Monaco 的初始化管线**；风险在“把固定 vs/vs-dark 换成 token 主题”这一步。只要保留上述六条防线、并把动态主题当“可回落的增强”而不是唯一路径，旧 bug 不会因本次改动复发。
