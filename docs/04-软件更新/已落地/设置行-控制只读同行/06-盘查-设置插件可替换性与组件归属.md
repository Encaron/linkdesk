## 二、换套那一天，逐步会发生什么

1. **声明照旧**：宿主 `getConfigurationContributions()` 全量喂给新插件；`group` 名随声明来（`appearance.ts` 里 `group: t("背景")` 等）⇒ **分组名不丢**。
2. **渲染换了人**：新插件自己的 `renderControl`。**它没实现的 `uiHint` 不报错**——作者面 schema 明写「未知 hint 回落到该 type 的默认渲染，不抛错；`uiHint` 是**开放字符串**，第三方可自定义 hint 名」（[plugin.schema.json](../../../../public/schemas/plugin.schema.json):374–375）。设置仓真实降级是**两级**：hint 未命中 → 按 `type` 渲染 → `type` 也未命中 → `<span>{String(val)}</span>`（设置仓 `renderControl.tsx` 两处 default）。
   - 具体例：`app.backgroundImage` ＝ `type:"string"` ＋ `uiHint:"image"`（[appearance.ts](../../../../src/App/config/appearance.ts):327–335）⇒ 在别家设置插件里会退化成一个**文本框**，里面是路径、或者字面量 `__none__`。
   - 同族：`fontTone` / `accentSource` / `fontSize` / `stringList` / `themePicker`… 各自的专属控件**全部失去**。
3. **语义各自重算**：「来源徽标」（theme/user/mix）与行尾**「生效：」徽标**都由**旧插件的本地纯函数**算出（设置仓 `deriveSourceBadge.ts` / `effectiveBadge.ts` ＋ `formatEffectiveValue`），宿主只给原始集（`userOverrides`/`baselineSeeds`/`effectiveTokens` 原始 map）。⇒ 新插件算得不一样＝**同一个键在两台设置插件里读数不同**。
4. **值域靠字面量**：`__none__` 是跨仓**字面量契约**，今天**不在 `@linkdesk/contracts`（grep 0 命中）**，散在至少四处：`ThemeEngine/constants.ts:174`、`FontFamilySelect.tsx:139`（自述「本共享组件不得引 @src/core」）、设置仓 `imagePicker.tsx:13`、`deriveSourceBadge.ts:23`。
5. **页面编排随插件走**（**本来就该是它的**）：i18n 文案表（设置仓 `i18n/en.json`，`plugin.json:23–25` 声明）、分组树/搜索/齿轮菜单/`dependsOn` 显隐流程。
6. 附注（不算缺口）：设置行**标题就是原始键名**（`SettingRow.tsx:65` `{configKey}`），宿主声明的人话 `description` 渲染成**下一行说明**（`SettingRow.tsx:78`）。声明层没有 per-key label 字段 ⇒ **换插件也变不出更好的标题**。

## 三、为什么会长成今天这个形状（用户第 10 问 · 根因）

- **出生史（你的判断被证据坐实）**：设置插件**出生在壳仓**（`f55d8b36e E4 #86a: 插件目录分离——9 个插件移入 builtin/(6)+user/(3)`），**到 `c1737620f E6#99 L7 第 7.2 轮「18 只发货插件源码外移各自独立仓」才离开**；它自己的 git 史里还留着壳仓时代的提交（`ed04fc7 E2c #19e: FactorySlots`、`73c0c12 E2c #19j-structure-b: 文件移入 src/`）。⇒ 写它的时候，「第二台设置插件」**不存在**。
- **当年的自设戒律**：设置仓 `package.json` description 自述「设置（内置）……**插件代码零 @src**」。于是「不耦合」被执行成「**不许 import，那就本地复制一份**」——`ReadOnlyStatus`、`BackgroundImagePicker`、`toneControls`、两套徽标算法都是这么长出来的。
- **精确表述**：当年缺的不是「解耦意识」，是**归属判据**。解耦管住了 import 方向，**没管住「这份能力该住哪一层」**；没有第二个实现者，就没有人问「换一台插件谁来画」。

## 四、判据（本案与后续一切「这个控件/这段语义归谁」的裁定规则）

- **判据 A · 声明对等律**：若某控件存在的意义是**消费宿主声明**（`uiHint`/`statusCommand`/`actionCommand`/`unit`/`effectiveToken`/`enum`…），它必须住在**任何声明者与其渲染者都取得到的层**（今日＝`@linkdesk/ui` 共享件：有 npm 版本、有 `check-api-surface-additive` 门禁）。住在一台**可替换**插件里 ⇒ 该声明的**解释权被一家垄断**——与滑杆案已判定的「能力住在第一个使用者手里」同族。
- **判据 B · 词表正典律**：`uiHint` 是宿主与渲染层之间的**词表**；词表必须有唯一真相源（`hint → 语义 → 控件 → 降级` 一览），且「声明了一个没人实现的 hint」必须有**可见后果**（今天是**静默降级**）。
- **判据 C · 语义不住插件律**：由宿主数据推导的**读数语义**（来源＝theme/user/mix、生效值＝哪个 token）属于**声明层的解释**，应与数据同时提供（宿主给解好的值，或共享纯函数），否则同键在不同插件下可显示不同答案——那是**一致性缺陷**，不是外观差异。

### §五·补 · 「生效：」徽标的落地状（判据 C 的具象 · **建议**，随 D5/D8 拍板）

现状一句话：宿主给**原始集**（`effectiveTokens` 原始 map ＋ `userOverrides`/`baselineSeeds`），设置插件本地三件套（`resolveEffectiveBadge`／`formatEffectiveValue`／SettingRow 手写 span）算出并画出行尾徽标——「谁算、谁能用、长什么样」三件事全在同一台可替换插件里。

落地状＝三层各归其位：

| 层 | 落地后 | 现状 |
|:--|:--|:--|
| **声明层** | **零新增**——`effectiveToken` 已是声明；任何键声明即得（含第三方键；token 解析不出＝无徽标，优雅降级） | 已有 ✓ |
| **宿主** | 配置读出面从「给原始集」升级为**给解好的语义**：每键 `{ source, effective?: { value, color? } }`——宿主本来就把生效值应用到 CSS 变量上，最有资格说「生效成什么」；⛔ 插件不再自算 | 给原始集，插件自算 |
| **共享层** `@linkdesk/ui` | ① `formatEffectiveValue`（字体栈截首族／色值配 swatch／未知形状原样）进共享；② **`EffectiveBadge` 呈现件**：props `{ label, value, color?, mode? }`——`mode` 缺省＝「跟随主题态才现」（＝今天），可覆写 `always`；颜色跟主题 token 走 | 无（span 手写在 SettingRow:89-101） |
| **设置插件** | SettingRow 控制区一行 `<EffectiveBadge …/>`；本地三件套退场；「生效：」措辞作为 `label` prop 传入（插件保留改文案的自由） | 本地三件套 |

**对内置设置页的观感：一个像素不变**（同位置——控件容器内、齿轮左；同「跟随主题态才现」；同措辞；同色块）。变的只有三件：

1. **谁算**——宿主＋共享函数，插件不再自算（判据 C）；
2. **谁能用**——任何设置插件声明即得**同一个答案**，换插件后「同键两答案」不可能再发生；
3. **哪里可调**——`label`／`mode`／formatter 都是显式 prop：**通用性＝声明即得，灵活性＝prop 可覆写**，两者都以「一份实现」为前提，不以「各家私算」为代价。

同一形状平移到**来源徽标**（theme/user/mix，判据 C 同款）与 **ReadOnlyStatus**（轮询进共享 `ReadOnlyText`，判据 A 同款）。与滑杆案 E1 的交界照旧：滑杆键若同屏「值标签＋生效徽标」，宽度与取舍按[滑杆案 00 §四·4.3](../../已落地/滑杆件-Slider能力扩展/00-README.md) ＋ 本案 [00 §四·补](00-README.md) 处理。

## 六·补 · 你复问后的四点厘清（2026-10-03 第二轮）

### ① 「组件内部并排」≠「声明层组合」——分界线

BackgroundImagePicker 的三按钮是**一个控件的内部实现**：一个 `uiHint:"image"` → 一个组件，按钮显隐由它自己看当前值决定（`color` hint 同理：色块 div ＋ 文本 input 两件并排）。声明层限制的只是**多个有独立语义身份的控件**——伴生件会进入「键」的语义面（来源徽标／生效徽标／齿轮菜单都以单键为粒度），所以才要「一主可编辑 ＋ 非编辑伴」的边界。⇒ **控件内部爱并几个就并几个**，无人看见内部结构；本案的组合自由度说的是声明面。
推论：把 BackgroundImagePicker 整件搬进 `@linkdesk/ui` **不需要任何新的声明表达力**——它本来就是一个控件。另注意区分两个面：**插件自己的 UI 面**想怎么排就怎么排（三个滑杆并排在任何插件自己的面板里都是小事），「多键一行」的限制只存在于**声明驱动的设置页**。

### ② AccentSourceControl / FontToneControl 不是重复造轮——底座已归一，不归一的是「预览原子」

两者都是**共享 `SegmentedRadio`** 的薄绑定（段值／预览／aria 从 hint 与 description 来）⇒ 你要的「自由度高的组件」**已经存在**。真正没归一的是**预览原子**（`Aa` 文字样本、纯色块样本、分半色块）被写死在两个 hint 专属控件里。⇒ 收归壳时的正确动作不是搬两个整件，而是**把「分段预览原子」抽进共享层**（纯展示、零宿主耦合，天然该共享），两个 handler 退化成数据绑定。

### ③ 轮询件的定性与规模化护栏

- **为什么是轮询不是推送**：`statusCommand` 是**命令**（一次性求值），命令没有订阅语义；要推送就得给每条命令配一条变更事件通道（新 API 面，契约成本高），而状态的变化源五花八门（进程死活／端口／文件），统一拉取最便宜。⇒ **当前契约下的合理解，不是终局**；升级路径＝可选 `onDidChange` 订阅 ＋ 轮询兜底，本轮不做。
- **现状体量**：宿主今天声明 **5 个** `statusCommand`（全在 `aiBridge.ts`）⇒ 打开设置页 ＝ 5 个 3s 定时器（`readonlyStatus.tsx:31`），可忽略。
- **规模化护栏**（搬共享层时**顺带**做，不另立项）：① **只在可见时轮询**（滚出视口／页签隐藏即停——设置页大部分时间在后台，这是最大头）；② **同命令去重**（多行同一 `statusCommand` 共享一个定时器）；③ 作者面 schema 补一句契约「`statusCommand` 必须便宜、幂等、无副作用」（今天没写）。「上百个轮询」的假想场景靠 ①＋② 压回个位数每 3s。
- **对既有 ai 组的影响＝零**：轮询能力进共享 `ReadOnlyText` 是**加可选 prop**，3s 节奏、alive 守卫、空值不占位原样保留；验收判据就一条——「ai 五行读数行为与节奏与今天逐格一致」。⛔ 不要在搬的同一笔里顺手改节奏（比如加隐藏暂停）——那是行为变更，须单独拍板。

### ④ 「只读文本」不是被实现两遍，是四种语义共享一个视觉原子

| 件 | 回答的问题 | 现状 | **落地后** |
|:--|:--|:--|:--|
| `ReadOnlyText`（共享） | 纯展示原子 | `@linkdesk/ui` ✓ | **原地升级**：获得**可选**轮询能力（`statusCommand`/`interval` props，缺省不轮询＝今天零变化）；执行命令的句柄由插件**传入**（共享件不引宿主内核——沿 `FontFamilySelect.tsx:139`「不得引 @src/core」同款纪律）；护栏三条（可见才轮询／同命令去重／作者面写明「要便宜」）随搬迁同笔做 |
| `ReadOnlyStatus`（本地） | 「这条命令**现在**什么状态」（轮询；值不来自配置存储） | 本地件（判据 A 该搬） | **退场**。设置仓 readonly 分支直接渲染升级后的共享 `ReadOnlyText`；3s 节奏／alive 守卫／空值不占位原样 ⇒ ai 五行读数逐格一致 |
| 「生效：」徽标（本地） | 「这个键**最终生效**的是什么值」（`effectiveToken` → 首族名／rgba＋色块） | 本地三件套（判据 C 该搬） | **退场**（详 §五·补）：宿主给解好的 `{ source, effective?: { value, color? } }`；共享 `EffectiveBadge`（`label`／`mode`／formatter 都是显式 prop）；插件一行 `<EffectiveBadge …/>` |
| 来源徽标（本地） | 「这个值是**谁**定的」（theme/user/mix） | 本地纯函数（判据 C 该搬） | **退场**：同形状——宿主解 `source`，共享纯函数＋呈现件；与 `EffectiveBadge` 合不合一个组件，留拍板 |

四件落地后的共同点：**设置插件在这四处只剩「摆不摆、摆哪」**——语义与画法一份实现，谁渲染都同一个答案；`ReadOnlyText` 是唯一「原地升级」的（它本来就是共享件），其余三件全部退场。

四个东西今天一半在共享层、一半在插件里，**没有成文的归口规则**——这才是它「看起来不归一」的真正原因。判据 A/C 落地后：原子共享、状态语义共享（轮询）、生效与来源语义共享（纯函数），设置插件只剩编排。
