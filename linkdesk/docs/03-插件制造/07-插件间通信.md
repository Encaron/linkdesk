# 07 — 插件间通信

> 2026-07-28。**插件之间怎么传数据？** 不是"终端开个门给协议"——所有通信走核心提供的管道。插件只负责用，不需要建。

---

## 一、核心原则

```
❌ 插件 ⇄ 插件    （直接握手——LinkDesk 不允许）

✅ 插件 → 核心 → 插件  （核心提供管道，插件只是用）
```

**只有核心建 API。插件不建 API。** 插件做的事：调核心给的函数，往管道里读写数据。

---

## 二、两套管道——核心提供，插件选用

| | 大厅 `events` | 后门 `p2p` |
|------|------|------|
| API | `linkdesk.events.emit(channel, data)` | `linkdesk.p2p.send(target, channel, data)` |
| 收到方 | `linkdesk.events.on(channel, callback)` | `linkdesk.p2p.on(channel, callback)` |
| 给谁 | 所有人——谁订阅谁收到 | 一个人——指定 pluginId |
| 生产者知道消费者吗 | 不知道 | 知道 |
| 消费者知道生产者吗 | 不知道频道名背后的插件是谁 | 知道是直连——但不一定知道是谁发的 |
| 目标不在线 | 无所谓——没人听就没人听 | 报错——"目标未运行" |
| 适合 | 事件广播、状态变更、数据共享 | 高频推流、大块数据、一对一 |
| 比喻 | 广场上的喇叭 | 包间里的电话 |
| 状态 | 🆕 #77 补 `emit`（`on` 已有） | ⬜ 还没建——等高频场景逼出 |

**两套可同时使用。** 终端收到一串数据，可以同时：
- 走大厅广播给日志插件（谁都该知道）
- 走后门推给协议插件（高频、低延迟、指定消费者）

---

## 三、大厅 `events`——广场上的喇叭

```
终端                          协议                        日志插件
  │                            │                            │
  │ events.emit(               │                            │
  │   'serial:rawData',        │                            │
  │   { portName, text }       │                            │
  │ )                          │                            │
  │         ↓                  │                            │
  │      核心广播               │                            │
  │         ↓                  ↓                            ↓
  │                     events.on(                   events.on(
  │                       'serial:rawData',            'serial:rawData',
  │                       callback                     callback
  │                     )                            )
  │                       解析字节                    记录日志
```

**终端不知道谁在听。** 0 个人、1 个人、10 个人——都一样，`emit` 完就走。

**频道名是字符串。** 核心不知道 `'serial:rawData'` 是什么意思。频道名约定：`<发出数据的插件id>:<数据名>`。

**代码：**
```typescript
// ── 发出数据（插件 A）──
await linkdesk.events.emit('serial:rawData', {
  portName: 'COM3',
  text: '\xAA\x01\x02'
})

// ── 接收数据（插件 B）──
const unsub = linkdesk.events.on('serial:rawData', (data) => {
  console.log(data.portName, data.text)  // COM3, \xAA\x01\x02
})

// 组件卸载时清理
// unsub()
```

## 四、后门 `p2p`——包间里的电话

```
终端                          协议
  │                            │
  │ p2p.send(                  │
  │   'sbq-protocol',     ← 指定收件人
  │   'serial:raw',            │
  │   data                     │
  │ )                          │
  │         ↓                  │
  │      核心验证：             │
  │      sbq-protocol 存在吗？  │
  │      在运行吗？             │
  │         ↓ 存在              │
  │         ↓                  │
  │                     p2p.on('serial:raw', callback)
  │                       只给这一个人——不广播
```

**终端知道收件人是谁。** 多了一个参数——`target`。

**核心做验证。** 目标不在线 → 报错。不需要两端先握手——核心就是中间人，知道所有插件的存活状态。

**代码（计划——还没建）：**
```typescript
// ── 发出数据（插件 A——指定收件人）──
await linkdesk.p2p.send('sbq-protocol', 'serial:raw', data)

// ── 接收数据（插件 B——只收直连数据）──
const unsub = linkdesk.p2p.on('serial:raw', (data) => {
  // 处理
})
```

## 五、终端——第一个交出数据的插件（E3j #77-#79）

当前终端是唯一的数据源，但数据全在自己房间内——协议插件拿不到。E3j 让它把三样东西交到大厅：

| # | 做什么 | 用哪个 API | 谁受益 |
|---|--------|-----------|--------|
| #77 | 推原始串口数据 | `events.emit('serial:rawData', data)` | 协议插件订阅后解析 |
| #78 | 广播连接状态 | `events.emit('serial:connected', {...})` | 状态栏/其他插件 |
| #79 | 接收发送命令 | `registerCommand('serial-monitor.send', handler)` | 工作台卡片发数据回 MCU |

**终端没有建任何 API。** 它只调了核心已有的函数：`events.emit`、`registerCommand`。

## 六、以后每个插件怎么做

新插件进场，回答两个问题：

**1. 我有什么数据别人可能需要？**
→ 调 `linkdesk.events.emit('频道名', 数据)`。频道名按约定起。往 API 文档的频道表里加一行。

**2. 我有什么能力别人可能需要调用？**
→ 调 `registerCommand('命令名', handler)`。命令名自己起。`handler` 是自己写的处理函数。

两个问题答完，该插件没有额外工作要做。**桌子是核心的，管道是核心的，函数是核心的。插件只是用。**

---

## 七、为什么这么说

> "终端建 API，协议连接终端的 API"

**这不是 LinkDesk 的模式。** 这是"开门"模式——每加一个插件，N 个插件之间开 N×(N-1) 扇门。

LinkDesk 的模式：

- **管道 = 核心建一次。** `events.emit`、`events.on`、`p2p.send`、`p2p.on`、`registerCommand`——这些函数是核心的，不是任何插件的。
- **频道名 = 插件自己起。** `'serial:rawData'`、`'sbq-protocol:parsed'`——字符串而已，核心不知道意思。
- **新数据源 = 不需要改核心。** 新插件调同一行 `events.emit('新频道名', 数据)`，核心代码零改动。

**核心的工作量是 O(1)，不是 O(N)。** 这就是插件自由化。

## 🔥 九、AI 开发者必读——新插件需要新通信时怎么改

> 2026-08-04。**E5#10 React Fallback 退役后发现的模式。**
> 这也是 LinkDesk 插件自由化的核心循环——不是 bug，是正常开发流程。

### 9.1 场景

你正在开发一个新插件。它需要接收某种外部指令（壳或其他插件发来的数据），但现有 `ShellEvents` 里没有对应的事件类型。

**示例：** editor 插件在 WebView 模式下，需要知道打开了哪个文件。但当前没有 `editor:openFile` 事件——editor 的 `sourceId` 是靠 React props `<EditorView sourceId="xxx" />` 传的。

### 9.2 正确做法——加事件，不改壳架构

```
步骤 1：在 ShellEvents.ts 的类型表中加一行
        editor:openFile: { filePath: string }

步骤 2：发送方（壳 MainContent.tsx）emit
        shellEvents.emit("editor:openFile", { filePath: "xxx" })

步骤 3：接收方（editor/src/index.tsx）监听
        linkdesk.events.on("editor:openFile", ({ filePath }) => { ... })
```

**三步改完。壳代码只多了 1 个 emit 调用——没有任何架构改动。**

### 9.3 什么情况需要加 ShellEvents

| 场景 | 需要加事件？ | 示例 |
|:--|:--:|:--|
| 新插件需要接收壳指令 | ✅ 是 | editor 接收 filePath |
| 新插件推送数据给其他插件 | ✅ 是 | LSP 推送诊断结果 |
| 新插件只在内部管理状态 | ❌ 不用 | 串口监视器连接/断开 |
| 新插件需要读取配置 | ❌ 不用 | 用 `linkdesk.config.get()` |
| 新插件需要操作文件 | ❌ 不用 | 用 `linkdesk.fileService` |

### 9.4 关键原则

- **ShellEvents.ts 是通信契约——单一真相源。** 新 AI 只需要读这一个文件就知道全部通信事件。
- **加事件是正常的，不是 hack。** LinkDesk 的设计就是"壳是空的，API 在事件表里长"。VS Code 从 10 个 API 长到 1000+，LinkDesk 同理——事件表会持续增长。
- **不要在壳里为插件写分支代码。** 壳只负责 `emit`/`on` 转发——插件自己处理业务逻辑。
