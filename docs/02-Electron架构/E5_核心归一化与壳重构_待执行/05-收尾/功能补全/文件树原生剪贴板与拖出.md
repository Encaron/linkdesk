# 文件树原生剪贴板与拖出桌面

> 2026-08-06。E5#17 建好了 ClipboardProvider 路由框架，Ctrl+C/V/X/A/Delete/F2 已在壳内正确分发。剩余缺口：**文件复制粘贴到操作系统**（跨进程剪贴板）和**拖出到桌面**需要 Electron 原生 API——网页沙箱 API 做不了。

---

## 一、前因

E5#15-#17 完成了剪贴板 Provider 归一化：
- `ClipboardProviderRegistry`——register/resolve/unregisterAll
- 壳 6 个快捷键 Ctrl+C/V/X/A/Delete/F2 → handler → `dispatchClipboard` → Provider
- 文件树注册了 Provider（onCopy/Cut/Paste/Delete），内部走文件系统操作

**已知局限（来自 E5 进度记忆）：** 文件 Ctrl+C 复制内容到系统剪贴板的是**纯文本路径**（如 `E:/_testfiles/touch_800x480.c`）。Windows 资源管理器 Ctrl+V 需要 `CF_HDROP` 格式（文件引用），纯文本不认。文件拖出同理——HTML5 drag-and-drop 不支持设置原生文件引用。

---

## 二、问题

### 问题 1：文件树 Ctrl+C → 桌面 Ctrl+V 无反应

**现状：** 文件树 `Ctrl+C` 走 `document.execCommand("copy")`，写入系统剪贴板的是纯文本路径。Windows 资源管理器粘贴不认纯文本路径。

**需要：** Electron `clipboard.writeBuffer("CF_HDROP", ...)` 或 `clipboard.write()` 原生 API 写文件引用格式。网页 API（`navigator.clipboard` / `execCommand`）做不了。

### 问题 2：文件树拖出到桌面无反应

**现状：** HTML5 drag-and-drop 支持内部拖放（文件树内重排）和外部拖入（从桌面到文件树）。拖出到桌面需要 `dataTransfer` 设置原生文件引用——HTML5 API 不支持。

**需要：** Electron 原生 drag-and-drop API（`event.sender.startDrag({ file: path, icon: ... })`）。

---

## 三、修复方案

两个问题根因相同：网页沙箱 API 无法访问 OS 级文件剪贴板/拖放。需要 Electron 主进程 API。

### Ctrl+C/ Ctrl+X → 系统剪贴板

```
renderer (Provider.onCopy) → IPC → main process
  → clipboard.writeBuffer("CF_HDROP", fileListBuffer)
```

`CF_HDROP` 是 Windows 文件拖放剪贴板格式——一个包含文件路径列表的结构体。Electron 的 `clipboard.writeBuffer()` 可以直接写原生格式。

### 拖出到桌面

```
renderer (dragstart handler) → IPC → main process
  → event.sender.startDrag({ file: filePath, icon: iconPath })
```

`startDrag` 是 Electron 的原生拖放 API——文件拖到资源管理器时，Windows 识别为文件操作（移动/复制）。

### 不改架构

E5#17 建好的 ClipboardProvider 路由框架正确——Ctrl+C 已经正确分发到文件树 Provider 的 `onCopy`。只需在 Provider 层替换写入逻辑：

| 组件 | 改动 |
|:--|:--|
| Provider 接口 | **不动**——`onCopy`/`onCut` 签名不变 |
| `onCopy` 实现 | 内部加 `ipcRenderer.invoke("clipboard:writeFileList", paths)` |
| `onCut` 实现 | 同上，额外设置 cut 标记 |
| dragstart handler | 内部加 `ipcRenderer.invoke("shell:startDrag", { file, icon })` |
| main process | 新建 handler——`clipboard.writeBuffer("CF_HDROP", ...)` + `startDrag` |

---

## 四、可能遇到的问题

### 1. CF_HDROP 格式编码

**风险：** `CF_HDROP` 是 Windows 专有格式（`DROPFILES` 结构体），需要按二进制格式编码文件路径列表（双 null 终止的宽字符路径 + 结构头）。

**缓解：** Electron 内置的 `clipboard.writeBuffer()` 接受原始 `Buffer`。参考 Chromium/Electron 源码中的 `ui/base/clipboard/clipboard_win.cc` 对 `CF_HDROP` 的处理。可用 `iconv` 或手动构造 `DROPFILES` 结构。

### 2. macOS/Linux 兼容

**风险：** `CF_HDROP` 是 Windows 专有格式。macOS 用 `NSFilenamesPboardType`，Linux 用 `text/uri-list`。

**缓解：** 在 main process handler 中按平台分叉——`process.platform === "win32"` → `CF_HDROP`，`"darwin"` → `NSFilenamesPboardType`，`"linux"` → `text/uri-list`。

### 3. 大文件/多文件拖出

**风险：** 拖出大量文件（100+）时 `startDrag` 可能慢。

**缓解：** Electron `startDrag` 只传文件路径引用，不传文件内容——文件数量不影响性能。但图标生成立即完成。

### 4. 非文件节点拖出

**风险：** 用户可能拖出目录节点的 twistie 或空白区域——此时应有合理的反馈。

**缓解：** 只有选中了文件/目录节点时才设置 drag data。空白区域拖拽由现有 `useDragReorder` 处理（标签页重排），不冲突。
