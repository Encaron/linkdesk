# 长远发展审视——结合网页 AI 对话，看 LinkDesk 路线图

> 2026-07-24。Encaron 与网页 AI 进行了一次关于"Electron + 多 WebView 隔离 + 万物皆插件"的长远发展讨论。此文档将那次讨论的洞察与 LinkDesk 实际路线图进行逐条对照——哪些已有、哪些缺失、哪些是对方没看懂的。

---

## 一、网页 AI 的核心论点速览

网页 AI 的讨论分四层递进：

| 层次 | 核心观点 |
|---|---|
| 技术可行性 | 独立 WebContentsView per 插件是正确选择——比共享 ExtHost 隔离性高一个等级 |
| 长久发展 | 软件死于三种"诅咒"：单体诅咒、生态崩塌诅咒、锁定诅咒。隔离本身不够——需要交互机制、性能预算、API 演化 |
| 长远战略 | 从"隔离容器"到"细胞组合"——插件不是孤岛，需要受控的跨插件通信、资源配额、API 版本化 |
| 落地建议 | 三种插件类型（UI/Theme/Service）、事件总线通信、资源休眠、AI 不仅是代码生成器更是插件编排者 |

## 三、网页 AI 指出但 LinkDesk 路线图中的真空白

> **以下是真正的盲区——在 LinkDesk 现有文档中找不到对应设计。**

### 🔴 盲区 1：资源配额与插件休眠（严重度：🔥🔥🔥🔥）

**网页 AI 的观点：** 50 个插件各一个 WebContentsView = 内存爆炸。必须有资源监控 + 自动休眠 + 状态保存/恢复。**"不解决这个问题，壳会在第 50 个插件安装后被用户卸载。"**

**LinkDesk 现状：** E3a 讨论了多 WebView 的内存代价（每个 ~60MB），但**没有设计资源配额和休眠机制**。当前设计假设所有 WebContentsView 一直存活。

**为什么是盲区：** Tauri 时代只有一个 WebView——没有"太多进程"的问题。Electron 多 WebView 是新领域，很容易被忽视。

**建议补入 E3a：**

```
新增任务：WebContentsView 休眠管理（~80 行）
  - webContents.getProcessMemoryInfo() 定时采样
  - 不可见插件 >30s → setBackgroundThrottling(true)
  - 不可见插件 >5min → 保存关键状态 → close() → 下次需要时 recreate
  - manifest.json 加 "sleepPolicy": "manual" | "auto"
  - 用户可手动"休眠插件"释放内存
```

### 🔴 盲区 2：插件间通信协议（严重度：🔥🔥🔥🔥）

**网页 AI 的观点：** 插件之间不是孤岛。需要壳作为路由器，提供 pub/sub + request/response。manifest 声明"输入"和"输出"的 type schema。壳校验、路由、记录。

**LinkDesk 现状：** CoreEvents 有 Emitter（`onDidChangeConfiguration` 等 5 个），但**零订阅**（G18 死代码）。插件之间没有正式的通信机制。当前 terminal 插件通过模块级变量共享数据——这在多 WebView 下不可用。

**为什么是盲区：** Tauri 时代插件都在同一个 JS context——直接 import 就行。E3a 后每个插件独立进程——必须走 IPC。

**建议补入 E3a/E3g：**

```
新增能力：PluginEventBus——壳级 pub/sub 路由（~100 行）
  - plugin A emit("highlight-request", { code, lang })
  - 壳根据 manifest 声明路由到 plugin B
  - plugin B on("highlight-request") → 处理 → emit("highlight-result", ...)
  - 壳校验 payload schema、记录调用链、超时告警
  - manifest.json 新增 "consumes" 和 "provides" 字段
```

### 🔴 盲区 3：API 版本化（严重度：🔥🔥🔥）

**网页 AI 的观点：** "一旦发布 API，就永远不能删除，只能增加。" API 分域独立版本号，保留旧版适配层，废弃有警告期。

**LinkDesk 现状：** plugin.json 有 `version` 字段（semver），但**没有 API 版本概念**。`window.linkdesk.*` 的 API 没有版本号——改了就是改了，旧插件直接坏。

**为什么是盲区：** 当前只有 4 个插件（terminal/marketplace/settings/workspace），都是自己写的。API 变更直接改插件代码就行。但插件市场开放给第三方后——**API 变更 = 破坏所有第三方插件**。

**建议补入 E3g：**

```
新增设计：API 版本化策略
  - window.linkdesk.* 加版本号：window.linkdesk.apiVersion = "1.0"
  - manifest.json 声明 "apiVersion": ">=1.0 <2.0"
  - 壳检测不兼容 → 提示"插件需要 API v1.2，当前壳支持 v1.0"
  - API 分域：filesystem / serial / config / events / ui
  - 每个域独立版本，deprecation 警告期 ≥ 6 个月
```

### 🟡 盲区 4：AI 作为插件编排者而非仅代码生成器（严重度：🔥🔥）

**网页 AI 的观点：** AI 友好的真正金矿不是"让 AI 写插件"，而是**让 AI 调用插件**。插件暴露 function 接口（JSON-in/JSON-out），AI 像 Function Calling 一样操控它们。

**LinkDesk 现状：** AI 友好原则聚焦于代码可读性、声明式设计、注释写"为什么"。但没有设计"AI 代理调用插件"的接口。

**为什么半盲区：** 这是 Phase 5+ 的远期功能，不需要现在就做。但**接口预留**现在就该想——如果每个插件在 `contributes` 里声明 `"aiFunctions"` 数组，壳就能自动生成 AI 可调用的 function list。

```
plugin.json 预留字段：
{
  "contributes": {
    "aiFunctions": [
      {
        "name": "sendSerialCommand",
        "description": "发送串口指令并返回响应",
        "parameters": {
          "command": { "type": "string", "description": "AT 指令" },
          "port": { "type": "string", "description": "COM 口名称" }
        },
        "returns": { "type": "string", "description": "设备响应文本" }
      }
    ]
  }
}
```

### 🟡 盲区 5：壳的平台抽象——不绑死 Electron（严重度：🔥🔥）

**网页 AI 的观点：** "抽象出一个平台无关的壳内核，将 Electron 仅视为一种渲染宿主实现。插件契约应基于 Web 标准。"

**LinkDesk 现状：** E1 设计把 `invoke()` → `window.linkdesk.*` 作为 API 边界——**这本身就是一个抽象层**。但 `window.linkdesk.*` 的实现直接依赖 Electron 的 `ipcRenderer` + Node.js `fs`/`serialport`——没有平台抽象。

**为什么半盲区：** Electron 是当前唯一目标平台。但如果 5 年后想跑在浏览器（Web Serial API）或 Tauri 3.0 上——`window.linkdesk.*` 的后端需要重写，但**前端插件代码可以不变**（这是 `window.linkdesk.*` 设计的好处）。

**当前够用。** 只需在代码注释中标注："`window.linkdesk.*` 是平台无关 API——换 Electron→Tauri→Browser 时只改后端实现，不改插件代码。"

## 四、网页 AI 没看懂的——LinkDesk 独有的优势

### 优势 1：三栏布局 + 标签页分屏 = 插件的"物理存在感"

网页 AI 讨论的是一般性的"多 WebView 壳"，但 LinkDesk 有 **图标栏/侧栏/主区三栏布局 + 递归分屏**。这意味着：

- **每个插件在图标栏有物理位置**——用户可以拖拽排序、固定位置
- **侧栏提供持久化上下文**——terminal 的 session 列表、文件树的目录树——不随标签页切换消失
- **分屏让多插件同时可见**——不像浏览器标签页一次只能看一个
- **对标 VS Code 的交互模型**——用户不需要学习新范式

这是网页 AI 没有触及的维度——他讨论的"壳"是抽象的，LinkDesk 的壳有**空间设计**。

### 优势 2：数据管道——插件不只是"被调用"，而是"被喂数据"

网页 AI 的插件模型是 request/response——AI 调插件，插件返回结果。LinkDesk 有 **RingBuffer → ProtocolParser → DataDispatch → 卡片** 的流式数据管道。

- 串口数据**主动推**给订阅的插件（terminal、workbench 卡片、逻辑分析仪）
- 不是"请求-响应"，是**持续的数据流**
- 多个消费者各自从 RingBuffer 读——天然支持一个数据源喂多个插件

这对应网页 AI 说的"循环系统（共享数据通道）获取营养"——LinkDesk 已经有了。

### 优势 3：plugin.json 声明驱动——比网页 AI 的 manifest 更成熟

网页 AI 提议 `manifest.json` 包含 `type`/`entry`/`permissions`/`version`。LinkDesk 的 `plugin.json` 已有：

- `viewRole`（sidebarPrimary / tabOnly / tabPrimary）
- `tabBehavior`（singleton / isFallback / confirmOnClose / invokeBeforeClose）
- `iconLocation`（top / bottom）
- `contributes`（commands / menus / keybindings / configurations / views / cards / protocols / themes / languages / fileAssociations / statusBar / icons / aiFunctions(预留)）
- `core: true`（不可卸载标识）

**11 个 contributes 类型、4 个声明字段——已经比网页 AI 的通用建议深入得多。**

### 优势 4：核心无知原则——比"壳永不变成超级插件"更彻底

网页 AI 说"壳就是壳，永不变成超级插件"。LinkDesk 把这个原则推到了极致：

> 核心不知道软件是干什么的。只定义"怎么接"，不定义"接什么"。往核心加东西前先问：加了之后核心变得更"知道自己是干什么的"了吗？是 → 别加，做成插件。

这不是防御性规则——是**架构基因**。核心无知 = 核心永远不会因为"现在主要用 terminal，以后主要用地图"而需要重构。

## 六、最后的判断——网页 AI 对了什么、错了什么

### 他对的：

1. **独立 WebContentsView 优于共享 ExtHost**——LinkDesk 已定，且隔离模型文档论证充分
2. **混合插件类型**——LinkDesk 六类插件早就覆盖了
3. **资源管理是长期存亡关键**——这是真盲区，需要补
4. **API 版本化从第一天开始**——LinkDesk 确实没做
5. **AI 不只是代码生成器，更是插件编排者**——远期正确，近期预留接口即可

### 他漏了的：

1. **三栏交互模型**——他讨论的"壳"没有空间设计，LinkDesk 的图标栏/侧栏/主区 + 分屏是独特优势
2. **流式数据管道**——他只有 request/response 思维，LinkDesk 的 RingBuffer 数据流是完全不同的范式
3. **核心无知原则**——他说的"壳不变成超级插件"是防御性的，LinkDesk 的版本是**进攻性的**——不是"克制"，是"设计上就不可能"
4. **对标 VS Code**——他的参照系是浏览器扩展和 Figma 插件，LinkDesk 对标的是 VS Code——交互标准高得多
5. **terminal 作为验证载体**——他假设需要先选赛道（笔记/工作台/AI 桌面），但 LinkDesk 已经有第一个功能完整的插件来验证架构。terminal（串口收发）= LinkDesk 的"Hello World 但真实可用"

### 他过度乐观的：

1. **"5 年成为通用运行时，向 W3C 提案"**——太远了。先让 10 个插件稳定运行再说
2. **"插件就像细胞，壳是生物体"**——比喻漂亮但无助于写代码
3. **"软件界的浏览器"**——LinkDesk 不是浏览器，是**通用容器**。浏览器是"打开网页"，LinkDesk 是"挂插件"。对标不同
