## 二、🔬 现状事实（读码 + 远端目录实测，file:line 证据）

### F1 更新失败归因系统性缺口 —— 「更新失败：未知错误」黑洞（真缺陷）

**现象**：更新失败 toast 永远只给「更新失败：未知错误，请重试」，不说真正原因。

**根因链（两截，都读码实证）**：
1. 归类字典是**照「安装」域报错文案**写的（[marketplaceShared.ts:346-360](../../../../plugins/marketplace/src/services/marketplaceShared.ts#L346-L360)）：`NET_RE = 下载中断|下载失败|HTTP|超时|网络|fetch|socket…`、`INT_RE = checksum|校验|哈希|大小不符…`、`ENV_RE = 磁盘|空间不足|权限…`、`PKG_RE = 解压|zip|损坏|plugin.json…`、`CON_RE = 已存在安装目录|覆盖…`。
2. 引擎**「更新」域**报错是另一套词（[update.ts:84-173](../../../../src/pluginLoader/lifecycle/update.ts#L84-L173)）：`插件 XX 未找到安装目录` / `插件 XX 不在用户安装区` / `缺少更新包来源` / `包内版本与当前版本相同 XX——无需更新` / `新版本需高于当前版本 XX——降级需在版本下拉显式选择旧版` / `替换失败，已恢复旧版: …`。**一个 token 都不在字典里** → `classifyInstallError` 全落 `unknown` → `updateFailLabelKey` 默认「更新失败：未知错误，请重试」（[marketplaceShared.ts:380-395](../../../../plugins/marketplace/src/services/marketplaceShared.ts#L380-L395)）。

**附带缺口**：`updateFailLabelKey` 连 conflict 分支都没写（:380-381 注释自认「conflict 对更新不适用 → 归 unknown 兜底」）；失败原始 error 只在 title 悬停留一注，用户实际只看到笼统 toast，无从判断是下载/目录/替换/版本方向哪一环。

<a id="f1-bua-71b"></a>
> **补案（E6#71b 闭，2026-09-09）**：此缺口已修——见 §三 71b ✅ 行。要点：不做「扩更新域词入安装类目」（会把「不在用户安装区」误标成「插件包损坏」，误导 > 笼统），改 **unknown 时直显引擎原文**（更新域报错本就是完整可读句）+ conflict 分支防御性补上 + default 撤「未知错误」谎 → 「更新失败，请重试」。实机喂出的证据③ 串（`插件 "…" 不在用户安装区…`）现在是 toast 终局文案，不再黑洞。

### F2 安装确认弹窗偏离已定设计 —— 左上角 + 无遮罩（真 bug）

**现象**：点「确认安装」弹出的富确认卡片贴窗口左上角、背后不变暗、与一般弹窗观感差异大；代码注释自称「居中卡片」。

**根因链**：
1. **为什么自绘是对的**：壳 `dialog.confirm` 契约只收一句纯文字（[preload-shell.ts:275-276](../../../../electron/preload-shell.ts#L275-L276) `confirm: (message: string)`），DialogHost 只渲染 title + message。安装确认要展示来源/发布者/许可证/版本/大小/官方徽标，壳给不了富内容 → 市场自绘。**此步合理**。
2. **错在没按已定设计走壳 Dialog 容器**：设计 [10-市场UI拥有权.md §四·三](10-市场UI拥有权.md) 写的是「壳 Dialog 容器 + 市场自绘内容」——壳 DialogHost 自带居中 + 全屏遮罩（[DialogHost.css](../../../../src/pool/floating/dialog/DialogHost.css)：panel `fixed; top:50%; left:50%; translate(-50%,-50%)`、backdrop `inset:0; rgba(0,0,0,.5)`）。实现却绕用它，改用 [OverlayPortal.tsx](../../../../src/components/shared/overlay-portal/OverlayPortal.tsx)——这组件**只做 portal + 外点关 + Esc 关，不管定位不管遮罩**（[OverlayPortal.tsx:116](../../../../src/components/shared/overlay-portal/OverlayPortal.tsx#L116) wrapper 仅 `position:relative`）。
3. **自绘又漏了定位**：卡片 CSS [MarketplaceDetail.css:837-847](../../../../plugins/marketplace/src/styles/MarketplaceDetail.css#L837-L847) 只有 width/bg/圆角/阴影，**无一条定位规则** → 普通块级落浮层根部 = 窗口左上角；无遮罩平面 → 背后不压暗。代码注释「居中卡片」（[DetailView.tsx:1094-1096](../../../../plugins/marketplace/src/views/DetailView.tsx#L1094-L1096) + [MarketplaceDetail.css:836](../../../../plugins/marketplace/src/styles/MarketplaceDetail.css#L836)）与实现**直接矛盾**。

**连锁副作用**（对应用户 Q3 的「行为怪」）：卡片顶部压着窗口顶部 30px 拖拽区（硬约束 18 老坑）那条不可点；无遮罩 = 无「点旁即关」的可感知提示；OverlayPortal 外点判定用整层 wrapper（块级横贯整行）→ 点卡片同一排空白区不算「框外」不关。

<a id="f2-bua-71c"></a>
> **补案（E6#71c 闭，2026-09-09）**：此缺口已修——见 §三 71c ✅ 行。要点：**壳 DialogHost 补富内容槽 `content:{pluginId, renderPath, payload}`**（[poolDialog.ts](../../../../src/core/types/pool/poolDialog.ts)）——present 时替代 title/message/默认按钮渲染，弹窗机制（居中/遮罩/Esc/Tab 焦点锁/点遮罩取消）由壳给（[DialogHost.tsx](../../../../src/pool/floating/dialog/DialogHost.tsx)）；富内容 = 插件视图经 `PluginComponent` 挂载（仿 FloatingPanel 声明寻址范式，壳零持渲染器、核心无知）。**三确认归一终态**：装 = `linkdesk.dialog.confirmContent({pluginId, viewId, payload})` 富内容卡（市场 ConfirmInstall 视图自画排版/按钮，§四·三「排版、按钮市场自由画」兑现）；卸 + 降级 = 同容器纯文字 `dialog.confirm` 原语不变——装/卸/降级共用同一 DialogHost 容器。**payload 不透明序列化载荷**随打开参数过壳→回池结构克隆（无跨 bundle 会话 store——prod 各视图独立 surface bundle、无模块单例，detailview 与 confirm 视图跨 bundle 共享内存是 dev-only 假象）。**viewId→renderPath 解析**走 `ViewContainerService.getView` 读 loader 运行时附挂 `_pluginId/_renderPath`（仿 floatingPanelReveal `resolveFloatingPanelView`）；解析失败防御回落纯文字 message 确认（弹窗仍出、不静默死）。**Enter 防双触发**：富内容模式 DialogHost 不注册面板 Enter→confirm（内容自带按钮/链接，聚焦其上 Enter 冒泡会与原生 click 双 settle）——`handleKeyDown` 遇 content 早退。老坑根因（壳 `dialog.confirm` 只收纯文字）仍在但被富内容槽绕开——无需扩纯文字契约收富内容（不把排版收归壳模板，保住 §四·三自由画）。

**证据**：[ExploreView.tsx:110-127](../../../../plugins/marketplace/src/views/ExploreView.tsx#L110-L127) `handleInstall` 直装（无任何确认）；[DetailView.tsx:551-555](../../../../plugins/marketplace/src/views/DetailView.tsx#L551-L555) `handleInstallClick` → `setConfirming(true)` → 富确认。

**设计背景**：mockup 02 状态总表把「探索插件组 + 行内『安装』」也归到「点安装先弹确认（帧 8）」同一行——即设计意图两入口都确认。但 08 §四 / 任务行只写了详情入口，实现便漏了侧栏。

<a id="f3-bua-71d"></a>
> **补案（E6#71d 闭，2026-09-10）**：此缺口已修——见 §三 71d ✅ 行。要点：**用户点名定「两处都先确认」（待定点② 落定）**——侧栏「探索插件」行内安装对齐详情页，**不引入「列表快装」差异档**（mockup 02 两入口都确认本意完整落地）。改动 = [ExploreView.tsx handleInstall](../../../../plugins/marketplace/src/views/ExploreView.tsx) 在 `startMarketInstall` 前加详情页同款富内容确认：`linkdesk.dialog.confirmContent({pluginId:"marketplace", viewId:"marketplace-install-confirm", payload: installConfirmPayload(entry)})`——`confirmContent`/`ConfirmInstall` 视图/`installConfirmPayload` 全复用 71c 现成机制（零新壳能力、零新视图声明、零新 i18n key），市场只加一个 import + 一段确认闸。**版本诚实**：payload 缺省 installVer → version = `entry.version`，正等于探索行所显 `v{version}`、所装 `entry.downloadUrl` 对应版本——确认卡不撒谎。确认闸落在既有三门禁（离线/缺下载地址/缺安装面）之后、`startMarketInstall` 之前；`confirmContent` 面缺失保守 no-op（与详情页同款，老 preload 防御）。**类属**：marketplace 插件 1.0.4→1.0.5 + changelog + 随包 zip 重建；软件零改动（confirmContent 71c 已在壳）→ 0.1.25 不 bump。实机 CDP 9222 五证据闭：侧栏点「安装」→ content 模式富确认卡正中 442×388 + 全屏遮罩显（非直装）/ 取消 → 卡关未装行仍「安装」/ 再点确认安装 → 真装成功行翻「已安装」/ 装回 Hello 与测试前备份字节级一致 / 备份清理零残留。

### F4 官方样板目录条目缺 readmeUrl —— 预览态只显一句话（发布侧缺口）

**现象**：Hello LinkDesk 未安装时，详情页只显示一句 description；装完才显示完整 README。

### F5.1 实机取证结果（E6#71a，2026-09-09）—— 更新失败真因 = 下载腿 github 间歇断 + 10s 桥遮蔽 + 域消息归因黑洞

**复现方式**：dev 实机（CDP 9222）经 `window.linkdesk.pluginManager.update('hello-linkdesk', { url: v0.1.0 资产, allowOlder:true })` —— 与详情「更新」按钮同一引擎入口（`plugins:call 'update'` → 壳 updatePlugin）。顺带②远端可达性当日已验：两资产曾有 HTTP 200。

**证据① —— 下载腿失败 + 10s 桥遮蔽（时间戳主进程日志）**：
- `13:40:23.595 [main] [ipc:plugins:stage-update] → 入 "hello-linkdesk", …v0.1.0 资产, "0.1.1", true`
- `13:40:43.442 [main] [ipc:plugins:stage-update] ✕ 错 19847ms TypeError: fetch failed`（cause `read ECONNRESET`）

fetch 卡 **19.8s** 才 ECONNRESET，落点 [plugin-download.ts:64](../../../../electron/services/plugin-download.ts#L64)（`downloadPackage` 内 `fetch(url,{redirect:"follow"})`）→ 主进程 stage-update handler 抛（下载分支 [plugin-install-handlers.ts:175-178](../../../../electron/ipc/handlers/plugin-install-handlers.ts#L175-L178)）→ 壳 [update.ts:113](../../../../src/pluginLoader/lifecycle/update.ts#L113) stage await 拒 → [update.ts:169-172](../../../../src/pluginLoader/lifecycle/update.ts#L169-L172) catch 包 `{success:false,error}`。

但池侧**先**收到 10s 桥超时：main↔壳 IpcBridge 请求超时 = **10 秒**（[ipc-bridge.ts:195-198](../../../../electron/ipc/ipc-bridge.ts#L195-L198)）。19.8s 下载 > 10s → 池 `pm().update` **reject** `[IpcBridge] 请求超时: plugins:call (requestId=bridge-285-…)`（非 resolve `{success:false}`）→ [DetailView.tsx:455-457](../../../../plugins/marketplace/src/views/DetailView.tsx#L455-L457) catch → classify 命中 NET「超时」→ network → toast「更新失败：网络连接不可用」。**真错误晚 ~10s 落在无人接听的桥后**。

**推论①'（比遮蔽更重）**：`update` 全流程 >10s 即桥超时（下载一腿常态 >10s）——**即便下载最终成功、磁盘已原子换新，池仍判失败 → 成功更新被误报失败 + 用户无感知磁盘已变**。结构性成因：pool `pluginManager.update` 走 request-response 桥裸 invoke 无进度 keepalive（[namespaces-plugin.ts:32](../../../../electron/preload-pool/namespaces-plugin.ts#L32)），与下载秒级~十秒级时长不匹配。治本方向另立（71b 非本注范围）。

**证据② —— 网络根因（下载腿为何断）**：取证当下两 release 资产 curl 全 HTTP 000（~20-21s 卡死；v0.1.0 连试 5 次全败、v0.1.1 亦 000）——当日早些时候两资产均有 200 → **github 间歇性限流/重置（本机网络）**，正是用户报的「v0.1.0 反复 HTTP 000」症状。Q2.4「更新失败」大概率即此下载腿。

**证据③ —— 「未知错误」真产生者 = 域消息（已实机喂出一条，零网络 2ms）**：池端 `pm().update('zzz-no-such-plugin',{url})` resolve `{success:false, error:"插件 "zzz-no-such-plugin" 不在用户安装区——仅安装包可更新（app 树插件走重新构建）"}` = [update.ts:47](../../../../src/pluginLoader/lifecycle/update.ts#L47) throw。该串无 NET/INT/ENV/PKG/CON 任一 token → classify unknown → [updateFailLabelKey:392-394](../../../../plugins/marketplace/src/services/marketplaceShared.ts#L392-L394) 默认「更新失败：未知错误，请重试」。update.ts 域 throw 全集：`:44 未找到安装目录` / `:47 不在用户安装区` / `:87 壳缺三段 handler` / `:105-107 缺少来源·市场未提供下载地址` / `:127 commit 替换失败 rethrow` + main stage 校验 [plugin-install-handlers.ts:196-200](../../../../electron/ipc/handlers/plugin-install-handlers.ts#L196-L200)（同版/降级拒）。

**收口**：用户 Q2.4 历史精确串无用户会话不可逆推，但 UI 可显两条路均已实机闭环——(a) 下载腿失败 → bridge reject「请求超时」或 resolve「fetch failed」→ 均已归 network（非黑洞）；(b) 域消息（update.ts/install-handlers stage 校验段）→ unknown → 「未知错误」。F5 原「特定场景路径（降级后升回/文件占用）」假设：**非下载环失败若发生（如 commit 遇 Windows 文件占用 → 替换失败已复原）确走 (b) 黑洞**；机制本身未瘫痪，证伪 F5 悲观假设。

### F11 失败 toast 长驻 —— 手动关才消失 / 成功几秒自动关（用户点名 #4）

### F14 补案：71k **反向**记录（2026-09-10 闭，E6#71k 最终形态）—— 改回「每次都问」，信任机制整体删除

> **本补案覆盖 F12/F13。E6#71k 以本节为最终形态。**

**触发**：F13 落地后（marketplace 1.0.7），用户当场改口——**原话**：「**暂时都问吧**，等未来的版本更新时代，这个作为一个更新点来作为安全更新的点来更新吧，咱们先不在这个地方纠结了。到时候可能会发花上一个季度半个月之类的甚至一个月，去专门研究这个安全问题，现在咱们这个先一步一步进行下去，先把这些东西都搞定了，然后那么关于这个点不能被卡住，所以就是先多问吧」。

**决定（三条）**：

1. **安装/更新确认一律弹卡——官方目录也不例外**。不再有「官方源预信任」豁免。
2. **E6#71k「每来源一次」整体作废**。`installTrust.ts`（纯判定）+ `MarketplaceTrust.css`（撤销 UI 样式）+ 对应测试文件**删除**；市场源弹窗的「已信任的来源」撤销列表**移除**。两个配置键 `marketplace.trustedSources` / `marketplace.installedFrom` 可能有残留在磁盘上，但**零读取方**（惰性孤儿，**不得复活**；`window.linkdesk.configuration` 面本就无 delete）。
3. **自动更新停摆**。自动更新发生在用户**不在场**时，弹不出确认卡就不能装——二者不可兼得，用户已知悉并接受。

**做法**（`services/installGate.ts` 新建，取代 `installTrust.ts`）：

| 件 | 内容 |
|:--|:--|
| **门** | `confirmMarketInstall(entry, mode, installVer?, fallbackName?)` —— **恒判「要问」**，无任何记忆 |
| **降级梯** | 有条目 + 壳有 `confirmContent` → 富内容卡；无条目 → 回落**纯文字** `dialog.confirm`（**仍然要问，绝不静默放行**）；连对话框都没有 → 返回 `false`（**问不了就不装**） |
| **四入口归一** | 详情页安装 / 详情页手动更新 / 侧栏「探索插件」行内安装 / **失败重试** —— 全部过同一道门。**重试不是免问券** |
| **载荷** | `ConfirmMode = "install" \| "update"` 取代原 `trustGrant`；`plaintext`（由 `isHttpSourceUrl` 派生）驱动 http 明文提示句 |
