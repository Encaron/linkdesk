## 一、架构澄清——两种齿轮，两个归属（✅ 正确）

LinkDesk 有两种齿轮菜单，归属不同：

| | 全局左下齿轮 | 插件卡片齿轮 |
|---|---|---|
| `MenuId` | `ExtensionGear` | `MarketplaceItemGear` |
| 位置 | 图标栏底部（`iconLocation: "bottom"`） | 插件卡片右侧 ⚙ 按钮 |
| 消费方 | `IconBar.tsx`（壳） | `marketplace/sidebar.tsx`（插件） |
| **菜单项由谁注册** | **核心** (`coreCommands.ts` + `APP_PLUGIN_ID`) | **marketplace 插件** (`ensureMarketplaceCommands()`) |
| 设计依据 | — | `gear-menu-normalization.md`——Encaron 定的机械规则 |
| 换 marketplace 插件后 | 全局齿轮不受影响 | 新 marketplace 自己注册 per-plugin 菜单项 |

**大厅模型的正确理解：**

```
MenuRegistry = 大厅里的"菜单本"桌子
ContextKeyService = 大厅里的"条件本"桌子

全局齿轮 (ExtensionGear)
  → 核心把"设置/命令面板/主题选择器"登记到菜单本的 ExtensionGear 分区

插件卡片齿轮 (MarketplaceItemGear)  
  → marketplace 插件把"设置/主题选择/启用/禁用/卸载"登记到菜单本的 MarketplaceItemGear 分区
  → marketplace 插件在打开齿轮前，把当前插件的 contributes 声明映射到条件本的 context keys
  → ContextMenu 渲染时，用 when 条件过滤——有 contributes.configuration → 显示"设置"，没有 → 不显示
```

**这是 Encaron 的设计，不是违规。** `applyExtensionContextKeys` 在 marketplace 插件里是**对的**——它是 marketplace 在管理自己的齿轮。`gear-menu-normalization.md` 第 29 行明确写：**加插件卡片齿轮菜单项时，唯一改动文件 = `plugins/marketplace/src/sidebar.tsx`。**

## 一.五、当前状态验证——什么已经对了、什么还没对

> 逐链路追踪实际代码，区分自动化骨架（✅ 不修）和边角漏洞（🔴🟡 在 #36f/#36g 里修）。

### 已验证——声明驱动的齿轮菜单（✅ 不改）

**场景：终端插件齿轮 → "设置"出现，theme-defaults 插件齿轮 → 不出现"设置"。**

终端 `plugin.json` 声明了 `contributes.configuration`：

```
plugins/terminal/plugin.json:20-35
  contributes.configuration.title = "串口监视器"
  contributes.configuration.properties = { serial-monitor.statusBar.txrx, serial-monitor.statusBar.connection }
```

theme-defaults `plugin.json` 声明了 `contributes.themes`，**没有** `contributes.configuration`：

```
plugins/theme-defaults/plugin.json:7-22
  contributes.themes = [{ id: "dark", ... }, { id: "light", ... }]
  // 没有 contributes.configuration
```

**齿轮菜单解析链路（纯数据驱动，零硬编码 `pluginId`）：**

```
点击终端齿轮
  → applyExtensionContextKeys(终端manifest, disabled)
    → c.configuration 存在 → extensionHasConfiguration = true    // ✅ 终端
    → c.themes 不存在       → extensionHasThemes = false
  → ContextMenu 渲染菜单项：
    → "core.openSettings" when: "extensionHasConfiguration" → true → 显示 ✅
    → "workbench.action.selectTheme" when: "extensionHasThemes" → false → 隐藏 ✅

点击 theme-defaults 齿轮
  → applyExtensionContextKeys(theme manifest, disabled)
    → c.configuration 不存在 → extensionHasConfiguration = false
    → c.themes 存在         → extensionHasThemes = true           // ✅ theme
  → ContextMenu 渲染菜单项：
    → "core.openSettings" when: "extensionHasConfiguration" → false → 隐藏 ✅
    → "workbench.action.selectTheme" when: "extensionHasThemes" → true → 显示 ✅
```

**没有一行代码是 `if (pluginId === "terminal")`。** 分辨逻辑唯一来源 = `plugin.json` 的 `contributes` 块。

### 已验证——齿轮"设置"跳转到插件配置子类（✅ 首次，🔴 设置已打开时）

```
齿轮"设置" → core.openSettings({ pluginId: "terminal" })
  → requestSettingsGroup("terminal")          // 写模块变量
  → factorySlots.getPluginId("settings")      // 查找设置插件
  → openTab("settings")                        // 打开/聚焦设置标签页
  → SettingsView mount → consumeSettingsGroup() // 读模块变量 → "terminal"
  → setSelectedGroup("terminal")              // 选中"串口监视器"分组 ✅
```

**场景区别：**
- 设置**未打开** → mount → `consumeSettingsGroup` 执行 → 跳转 ✅
- 设置**已打开**（singleton） → 不 mount → `consumeSettingsGroup` 不执行 → **不跳转** 🔴（M1）

### 已验证——新插件自动在设置中出现子类（✅ 即时生效）

```
新插件安装 → loadPlugin/LoadPluginRuntime
  → parseContributions(manifest.contributes)
    → registerConfiguration(pluginId, { title, properties })  // 写入 _contributions Map
  → PluginLifecycle.onDidInstall.fire()
    → notifyPluginViews()
      → SettingsView: setVersion(v + 1)
        → useMemo 重算 → getConfigurationContributions()
          → 返回包含新插件的 Map → 左侧导航新增分组 ✅
```

运行时安装也即时生效——不需要重启。

### 已验证——左下角全局齿轮 vs 插件卡片齿轮（✅ 正确）

| 入口 | pluginId context | `requestSettingsGroup` | SettingsView 行为 |
|---|---|---|---|
| 终端齿轮"设置" | `"terminal"` | ✅ 调用 | 跳到"串口监视器"分组 |
| 左下角齿轮"设置" | `undefined`（空 context） | ❌ 不调用 | 默认选中第一个分组（"通用"） |

**这就是"直接进入子类"和"默认从通用开始"的区别来源。** 不是硬编码——是 `ctx?.pluginId` 有没有值。

### 已验证——一个插件同时有 configuration + themes（✅ 两个菜单项都出现）

```json
{
  "contributes": {
    "configuration": { "title": "我的插件", "properties": {...} },
    "themes": [{ "id": "my-dark", ... }]
  }
}
```

→ `extensionHasConfiguration = true` + `extensionHasThemes = true`
→ 齿轮同时出现"设置"和"选择颜色主题" ✅

## 二、对标 VS Code——功能完整性审计

### VS Code per-plugin 齿轮菜单结构

VS Code 的 per-plugin 齿轮菜单分三层，用分隔线隔开：

```
┌─────────────────────────────┐
│ 设置颜色主题    ← contributes.themes                │  ← 贡献特有（顶部）
│ 设置           ← contributes.configuration          │
│ 键盘快捷方式    ← contributes.keybindings            │
├─────────────────────────────┤
│ 启用 / 禁用     ← 管理操作                          │  ← 管理（中部）
│ 自动更新       ← 管理操作                          │
│ 卸载           ← 管理操作（危险，标红）                │
├─────────────────────────────┤
│ 复制 / 复制 ID  ← 辅助操作                          │  ← 辅助（底部）
└─────────────────────────────┘
```

### LinkDesk 对照

`applyExtensionContextKeys()` 当前设 5 个 context key，`ensureMarketplaceCommands()` 当前消费 2 个：

| contributes 声明 | VS Code 齿轮出现 | LinkDesk context key | LinkDesk 菜单项 | 状态 |
|---|---|---|---|---|
| `contributes.configuration` | "设置" | `extensionHasConfiguration` | `core.openSettings` | ✅ |
| `contributes.themes` | "设置颜色主题" | `extensionHasThemes` | `workbench.action.selectTheme` | ✅ |
| `contributes.keybindings` | "键盘快捷方式" | ❌ **未设** | ❌ **未注册** | ❌ |
| `contributes.languages` | 语言相关 | ✅ 设了 | ❌ **未注册** | ❌ key 设了但零消费 |
| `contributes.iconThemes` | 图标主题 | ✅ 设了 | ❌ **未注册** | ❌ key 设了但零消费 |

**结论：** `applyExtensionContextKeys` 设了 5 个 key，`ensureMarketplaceCommands` 只消费了 2 个（`extensionHasConfiguration` + `extensionHasThemes`）。缺的是覆盖范围，不是架构。

## 三、运行时健壮性——13 漏洞审计

> 敌对审计方法：假设每次 async 都有竞态、每个模块变量都是陈旧的、每次清理都漏了。

### 🔴 高严重度（3 个）

#### H1. FactorySlots 不支持运行时热换

**文件：** `src/core/FactorySlots.ts` + `App.tsx:261`

**问题：** `initialize()` 只在启动时调用一次。类没有 `remove()`/`update()` 方法。卸载旧设置插件 → slot 仍指死 ID → `Ctrl+,` 打开不存在的东西。**换设置插件必须重启。**

**修复：**
- FactorySlots 加 `refreshFromPlugins(plugins)` 方法——重新扫描已加载插件，更新 slot 映射
- lifecycle.ts 的 `onDidInstall`/`onDidUninstall` 消费端调用
- 优先级保持：`core: true` > 第一个声明者

#### H2. revertThemeIfCurrent 漏掉旧格式主题

**文件：** `src/pluginLoader/loader.ts:1022-1035` + `src/core/ThemeRegistry.ts`

**问题：** `revertThemeIfCurrent` 用 `ThemeRegistry.get()` 查当前主题的归属插件——但 `ThemeRegistry` 只存新格式 `contributes.themes`（由 `parseContributions` 注册）。旧格式 `manifest.themes` 的主题调了 `registerTheme()`（写入 ThemeEngine）但**没调** `ThemeRegistry.register()`。卸载旧格式主题插件 → 当前主题不回退 → 用户 UI 退到 `index.css :root` 裸 CSS。

**修复：** `loadThemePlugin()` 中也调 `ThemeRegistry.register()`——归一化到 ThemeRegistry 单入口。旧格式字段映射：`t.id`→`id`，`t.name`→`label`，`themeType`→`uiTheme`，`t.file`→`path`。

#### H3. loadPluginRuntime /@fs/ 端点在生产环境不可用

**文件：** `src/pluginLoader/loader.ts:536`

**问题：** `import(/@fs/${absPath}/${manifest.entry})` 是 Vite dev server 专有端点。Electron 生产构建中无 Vite → 动态 import 失败 → toast "可能未构建"。

**修复：** 生产环境用 `linkdesk://plugins/${pluginId}/${manifest.entry}` 加载；dev 环境保护 `/@fs/`。

> **⚠️ 需先确认：** 生产打包后插件文件路径（`process.resourcesPath/plugins/`）及 `linkdesk://` 协议是否正确路由。

### 🟠 中严重度（5 个）

#### M1. SettingsView consumeSettingsGroup 空依赖——设置已打开时不跳转

**文件：** `src/components/views/SettingsView.tsx:66-72`

**问题：** `useEffect(() => { consumeSettingsGroup(); }, [])` 只在 mount 时执行一次。设置标签页 singleton 已打开时，齿轮"设置"→`requestSettingsGroup()` 写模块变量 → 无人消费。

**修复：**
- `ConfigurationRegistry` 加 `Emitter<string>`——`requestSettingsGroup` 既写变量也 fire 事件
- `SettingsView` mount 时消费变量 + 订阅事件（双通道，向后兼容）

#### M2. 没有内置 "Dark"/"Light" 兜底注册

**文件：** `src/pluginLoader/loader.ts:1015-1019` + `src/core/ThemeEngine.ts`

**问题：** `syncAppThemeEnum()` → `getAvailableThemes()` 返回 `pluginThemes` Map keys。启动时 Map 为空。第一个主题插件加载后枚举被替换。卸载唯一主题插件 → Map 空 → `if (available.length === 0) return` 跳过更新 → 下拉框残留死条目。

**修复：** App 启动时注册 2 个内置 fallback 主题——`"Dark"` 和 `"Light"`。颜色值从 `index.css :root` / `[data-theme="light"]` 读取。`getAvailableThemes()` 永远至少有 2 个主题。

#### M3. setConfigurationValue 不做枚举验证

**文件：** `src/core/ConfigurationService.ts:107-127`

**问题：** 写入 `app.theme` 不检查值是否在 `enum` 中。选到已卸载主题 → 死值写入 `settings.json` → 重启后 `loadTheme()` 抛异常 → UI 退到裸 CSS。

**修复：** `setConfigurationValue` 写入前查 `getMergedSchema()[key].enum`。值不在枚举中 → 拒绝写入 + console.warn（不抛硬错误——用户可能手动编辑了 settings.json）。

#### M4. 旧+新格式 themes 共存时双重注册

**文件：** `src/pluginLoader/loader.ts:427-441` + `loader.ts:466-473`

**问题：** `loadPlugin` 先处理 `manifest.themes`（旧格式→`loadThemePlugin()`→`registerTheme()`），再处理 `manifest.contributes`（→`parseContributions()`→`registerTheme()`）。同时声明两个格式 → 同一主题注册两次 → console.warn "重复注册"。

**修复：** `contributes.themes` 存在时跳过旧格式 `manifest.themes` 的 `loadThemePlugin()` 调用。

#### M5. 注册机制双轨——merge vs mutate 竞争

**文件：** `src/core/ConfigurationRegistry.ts:68` + `loader.ts:1018` + `App.tsx:242`

**问题：** `App.tsx:242` 的 `registerConfiguration(APP_PLUGIN_ID, {..., enum: getAvailableThemes()})`（Object.assign 替换引用）和 `loader.ts:1018` 的 `updateConfigurationEnum("app.theme", ...)`（原地 mutate enum 数组）是两个独立机制。如果 `syncAppThemeEnum` 在两次 `registerConfiguration` 之间执行，mutation 被后续 merge 覆盖。

**修复：** 删掉 `App.tsx:240-258` 的二次 `registerConfiguration("app.theme", ...)`。在 `initPluginLoader()` 完成后统一调 `syncAppThemeEnum()`。所有枚举更新走 `updateConfigurationEnum` 一个入口。

### 🟡 低严重度（5 个）

#### L1. Context keys 不清理

**文件：** `plugins/marketplace/src/sidebar.tsx:78-85` + `sidebar.tsx:528`

**问题：** `applyExtensionContextKeys` 设置 5 个全局 context key。`onClose` 只 `setGearMenuAnchor(null)`，不清理 key。当前无其他消费者（只在 ContextMenu 的 when 求值中读），但未来可能读到残留值。

**修复：** `onClose` 中重置全部 key 为 false。

#### L2. 枚举原地突变依赖 React 批处理

**文件：** `src/core/ConfigurationRegistry.ts:89-98`

**问题：** `updateConfigurationEnum` 原地 mutate `contrib.properties[key].enum`。SettingsView 的 `useMemo` 依赖 `version` 状态，不依赖数据本身。当前正确是因为 `syncAppThemeEnum` 同步执行 + React setState 批处理——mutation 总在 render 之前完成。但如果未来异步化，枚举就陈旧。

**修复：** 不修改代码，加 `// #36f11` 注释标记时序依赖——`syncAppThemeEnum()` 必须在 `onDidInstall`/`onDidUninstall` fire 之后（同步）调用。

#### L3. ThemeBrowser 打开时不订阅生命周期

**文件：** `src/components/ThemeBrowser.tsx:69`

**问题：** `getAvailableThemes()` 每次 render 调用，但 ThemeBrowser 不订阅生命周期。卸载主题时不重渲染 → QuickPick 列表残留死条目。用户选到死值 → 触发 M3 场景。

**修复：** ThemeBrowser 订阅 `onPluginLifecycleChange` → 强制重渲染。

#### L4. revertThemeIfCurrent 未被 await

**文件：** `src/pluginLoader/loader.ts:813` + `loader.ts:901-902`

**问题：** `revertThemeIfCurrent` 是 async（内部调 `setConfigurationValue`），两处调用点未 await。功能上不影响（revert 修改独立 key），但违反语义清晰。

**修复：** 加 `await`。

#### L5. 旧格式 theme/language 互斥

**文件：** `src/pluginLoader/loader.ts:575-579` + `loader.ts:427-446`

**问题：** `if (manifest.themes) {...} else if (manifest.languages) {...}`——`else if` 使旧格式插件不能同时声明 theme 和 language。新格式 `contributes.themes` + `contributes.languages`（走 `parseContributions` 独立处理）无此问题。

**修复：** `else if` → 独立 `if`。

### 6.3 🟠 注册/注销不对称（数据泄漏 + 崩溃风险）

#### M9. 终端命令注册无清理

**文件：** `plugins/terminal/src/index.tsx`

**问题：** `TerminalView` 在 `useEffect([], [])` 中注册 12 个命令。无对应清理。卸载后 handler 保留在 `CommandRegistry` 中——handler 调 `getActiveCmd()!`（non-null assertion），组件卸载后通过命令面板 invoke → **crash**。

**根因：** `_cmdMap` 有清理（`useEffect` 返回 `() => { _cmdMap.delete(sourceId) }`），但 command handler 未注销——handler 的生命周期长于 `_cmdMap` 条目。

**修复：** `useEffect` 返回清理函数——调 `unregisterPluginCommands("terminal")`，或逐个 `CommandRegistry` 注销。

#### M10. `loadThemePlugin` 不调 `ThemeRegistry.register()`

**文件：** `src/pluginLoader/loader.ts:658-712`

**问题：** `parseContributions()`（第 344-363 行）同时调 `ThemeRegistry.register()` 和 `registerTheme()`。但 `loadThemePlugin()` 只调 `registerTheme()`——不调 `ThemeRegistry.register()`。旧格式 `manifest.themes` 注册的主题对 `ThemeRegistry.get()` 不可见——`revertThemeIfCurrent()` 靠它查找归属插件。卸载旧格式主题插件 → 主题回退静默跳过。

**与 #36f1 (H2) 的关系：** #36f1 修 `loadThemePlugin` 写入 ThemeRegistry 的问题。本条目覆盖修复后仍需验证 `get()` 返回正确的连锁路径。
