## 一、用户看到什么

设置页「主题 → 整体配方」是一排卡片。用户那台机器上排在最前两张的是：

| 卡片名 | 徽标 | 预览区 |
|:--|:--|:--|
| `Dark` | `Dark` | 三条中性灰条（无色） |
| `Light` | `2 配色` | 真彩色（白底 + 蓝条） |

他把这两张读成「同一套的深浅两搭子」——壳那张**没有**插件归属、**没有**颜色、名字是个颜色词，而旁边那张叫 `Light` 的才是插件给的。**归属与名字对不上人话**。

## 二、根因（三条机制叠加，缺一条都不会这么误导）

| # | 机制 | 落点 |
|:--:|:--|:--|
| ① | **名字都用颜色词**：壳兜底卡 `Dark`／插件配方 `Light` —— 读者自然默认「同一套的深浅」 | 壳兜底名写死在 `src/core/services/ui/ThemeEngine/registry.ts:130-146`；插件配方名来自 `themes/defaults.json` 的 `name` |
| ② | **排位被钉死成相邻**：`recipes` 是 Map，兜底 `dark`/`light` 在插件加载**之前**登记，`theme-defaults` 覆盖的是**同一个 `light` 键**（Map 对已存在键 `set` 不改插入位置）⇒ 这两张卡**永远是最前两张、永远挨着** | 同上 ＋ `ThemeRegistry.registerRecipe` |
| ③ | 🔴 **UI 里压根没有「提供方」这个位**：契约 `RecipeMeta` 只有 `id/name/type/colorways/domains` —— **没有来源字段**；壳里明明知道（`ThemeRegistry.getRecipeOwner()`，`undefined` = 宿主兜底）却没进契约、没渲染 ⇒ 用户只能靠名字猜，**而名字恰好是唯一会撞车的东西** | `src/core/api/linkdesk-api/types.ts`（旧）· `src/core/registry/appearance/ThemeRegistry.ts:316-319` |

**加重一层**：`theme-defaults` 那只配方内部，第二个配色名字就叫 **`Dark`**（`theme-defaults.dark`）——于是屏幕上同时有三种 Dark/Light：壳的兜底卡 `Dark`、插件配方卡 `Light`（里面装着配色 `Dark`）、以及插件本体「官方主题」（说明写「出厂暗色/亮色主题」）。「官方黑白的那个」在界面上一次都没这么介绍自己。

## 三、设计前置（8 维度）

| 维度 | 结论 |
|:--|:--|
| ① 能力边界 | **壳能力**（登记本 ＋ 契约面）。保底不变：兜底配方仍在插件加载前登记，插件全缺席时卡片有名可读。 |
| ② API | `RecipeMeta` **只加**一个只读字段 `source`（`{kind:"host"}` / `{kind:"plugin",pluginId,name}`）。不新增方法。契约落 `src/core/api/linkdesk-api/types.ts` → `npm run contracts:gen` 同步 `contracts/linkdesk.d.ts`；`check-api-surface-additive` 过只加不删。 |
| ③ 通信 | 零新通道：`recipeOwners` → `toRecipeMeta` → 既有 `theme.listRecipes` 桥 → 池渲染。 |
| ④ 壳侧 | 新增**单一权威** `src/core/services/ui/ThemeEngine/source.ts`（`isHostRecipe` / `recipeSourceOf` / `recipeDisplayName` / `colorwayDisplayName` ＋ `setPluginNameResolver` 装配槽）。消费点 = `IpcBridgeHandler/theme.ts`（契约载荷）＋ `ThemeBrowser.tsx`（`theme.pick` 命令面）。🔴 解析器走装配槽：`pluginLoader/**` 反向 import `ThemeEngine` ⇒ 直接 import 会成环；装配点 = `src/App/config/appearanceApplier.ts`（与 `setAppearanceIdResolvers` 同一范式）。 |
| ⑤ 插件侧 | `theme-defaults` 只改 `themes/defaults.json` 的 `name`（配方 ＋ 两个配色）⇒ **id 一字不动、零迁移**；`lang-defaults` 补 4 条壳核心文字译名。 |
| ⑥ 显示 | 卡片加**来源行**（「壳自带」／「来自 X」）；`theme.pick` 第一段 detail 在「明暗类别 · 配色数」后追加来源。改的是壳共享组件 ⇒ 先调 `ui-ux-pro-max` 取设计系统，再动 CSS（字号走既有 `--font-size-2xs` 不新造类型阶；颜色用 `--text-secondary` 而非 `--text-muted`——深底 muted 只有 ≈3.4:1，小字号正文需 ≥4.5:1）。改完 `npm run ui:build`。 |
| ⑦ 配置 | **零新配置键**；`app.theme` 的取值空间 / 默认值 / 枚举一字不动（改的只是显示名，不进 enum）。 |
| ⑧ 验收 | `npm run check` ＋ 单测（来源两态 / 缺省不标注 / 宿主名走 t() / 兜底名不再是颜色词）＋ dev 实机看卡片与 `theme.pick` ＋ 用户视觉验收。 |

## 七、残余边界与「不做」

1. **来源行只覆盖壳自家两个消费面**（设置页卡片 ＋ `theme.pick`）：第三方自建主题 UI 要自己读 `RecipeMeta.source` 才知道归属——契约给了数据，渲染不强制。
2. **名字与 `id` 是两件事**：本次只动显示名，`dark`/`light` 等 id 一字不动（用户 `settings.json` 零迁移）。「壳兜底卡显得空」（`colors:{}` ⇒ 中性灰条）**本次不动**——那是「空兜底配方 = 回落 `index.css` 硬兜底」的既有设计，动它属另一条轴（把 `dark` 也交给插件实现）。
3. **配色名的中文/英文混排在插件数据里**（官方主题仓惯例 `中文 English`）：theme JSON 的 `name` 不在 manifest 渲染字段表内，不过 `own-dict-coverage` 判据，故照官方既有惯例写。
4. **`app.iconTheme` 的选项文字仍是 id 原文**（E6#111f 判定⑦的既有边界）——与本次无关，仅登记以免误读为同类问题。
5. 🔴 **「05-插件更新」轴本件不另建档案（有意）**：本件动了两个插件仓（`lang-defaults` 译名、`theme-defaults` 改名），但两只都是**纯声明式仓**——05 README §五 的结论是**那类仓走 pack 通道（目录整树打包），放 `docs/` 会被打进包**，所以插件侧档案的长期家仍留壳仓；且本件是**一个用户可见修复**，插件侧动作只是它的两半，落两份档案 = 造两个真相源 ⇒ 统一记在本档（§五）。判据与先例见 [05-插件更新/00-README.md §五](../../05-插件更新/00-README.md)。
