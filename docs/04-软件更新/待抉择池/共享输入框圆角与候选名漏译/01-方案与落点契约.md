## 一、落地位置判据走查（判据 A 三问，2026-10-06）

### 轴一 · 输入框圆角

```
Q1 谁在生产/声明它？      → 共享件 `InlineInput` 自己（.ldk-inline-input 是它自绘的 <input>）
Q2 谁是消费者？           → 四处：壳管理器（normal）· 设置插件设置页（normal）
                            · file-tree 行内重命名（compact）· serial-monitor 会话行（compact）
Q3 消费的是谁的面？       → 消费者用的是**控件自己的呈现契约**（高度/内距/底色/边框/圆角），
                            不是宿主声明面 ⇒ 落位问题在**共享件内部**，与消费方无关
```
**结论**：补在 `InlineInput` 自己身上，**一处改、四处受益**（⛔ 不许在四个消费位各补一次 —— 那是「先放插件」的反向用法）。

### 轴二 · 候选名漏译

```
Q1 谁在生产「插件显示名的中文原文」？ → 宿主面 `HandlerSnapshot.title` ＋ 清单 `manifest.name`
                                        （聚合层被规定为**只搬运不翻译**）
Q2 谁是消费者？                      → 管理器视图（卡头/下拉/胶囊/触发条）＋ 第三方设置渲染方
Q3 消费的是谁的面？                  → 呈现（文案）⇒ **翻译归视图**（`types.ts:37` 已写死：
                                        「i18n 原文，渲染前由视图 t()」）
```
**结论**：**落点是对的，缺的是执行**——四处消费位里只有卡头那处调了 `t()`。收口要在「视图层谁负责翻」上加一道**机械可见性**（[§六 D2/D3](#六门禁空档与替代判据轴二的正式登记)），⛔ 不是把翻译塞进聚合层（模型是纯函数、无 `t`，塞进去还要把 i18n 依赖拖进共享聚合——契约污染）。

## 三、方案落点一览

### 轴一（唯一的新增行 · 位置对齐 `.ldk-input` 的声明次序）

```css
/* src/components/shared/inline-input/InlineInput.css —— .ldk-inline-input 基类 */
   border: 1px solid var(--border);
+  border-radius: var(--radius-sm);   /* ← 本次唯一新增行：接上圆角标尺（与 .ldk-input index.css:258 同源） */
   background: var(--bg-input);
```

**为什么是基类（而不是 `--normal`／`--compact` 各写一条）**：圆角是「输入框」这条契约的属性，与高度／字号无关；写在基类上等于**一个真源**，两档自动一致（[D1](04-任务清单.md) 只决定要不要给 22px 那档换 2px）。

**为什么是 `--radius-sm`**（🔴 **不是**「4px 写死」——这一档今天值多少，由 `app.surfaceRadius` 滑杆／主题说了算）：

| 候选 | 依据 | 判定 |
|:--|:--|:--|
| `--radius-sm` | ① 仓内输入框契约 `.ldk-input` 就是它（`src/index.css:258`）② **22px 高配圆角已有生产先例**：file-tree 的 22px 筛选框（`SearchView.css:109`，1.0.24 修的同一个病）③ `SelectBox` 面板用 `--radius-sm` | ✅ **推荐（两档统一）** |
| 其余四档 `md`/`lg`/`xl`/`2xl` | 滑杆**拉过**的机器六档同值 ⇒ 与 `sm` **完全等价**（拉不动的地方今天都一样）；只有**未覆盖态**才有差（静态兜底 `md6`/`lg8`/`2xl16`） | ⬜ 等价但不选——与仓内契约**不同源**，将来主题若按档位分层就会岔开 |
| `--radius-xs` | 只有 `SelectBox` 的**触发器**用它（`SelectBox.css:24`） | 备选（若拍板认为 22px 小档该更收——但会与 file-tree 同高度先例不一致） |
| 硬编码 `4px` | — | ⛔ **双重失效**：主题覆盖失效（不跟主题）＋ **滑杆拉不动它**（用户拉圆角时这一件纹丝不动） |

⚠️ 写哪一档**都不断滑杆**（六档同写），所以 D1 之争实际只影响「**没拉过滑杆**的机器」；真正的红线只有一条：**必须消费 token，不许写字面量 px**。

## 四、反论与连带重审

| 反论 | 回应 |
|:--|:--|
| 「共享控件自己 `t()` 不就行了？一步到位」 | ⛔ **否决**。`SelectBox` 是通用控件：它的 `label: string` 收的是**任意文本**（排序项「按字母序」是 `t()` 后的字符串、第三方可能传纯文本／用户数据）。控件内 `t(label)` 会对**本来就该原样显示**的文本做二次查表——词条撞车就是错翻（例如某插件名恰好等于某个 UI 词条的中文）。**翻译职责必须在「知道这是 i18n 原文」的那一层**（视图／模型类型），控件只画 |
| 「模型里直接翻，视图零负担」 | ⛔ 否决：聚合纯函数无 `t` 依赖（`deriveModel.ts` 是纯函数，进 `@linkdesk/ui`），拖进 i18n 会污染共享聚合面，且把「文案」职责塞给「判定」层（`types.ts` 头注明写「判定归壳，管理器只聚合」） |
| 「那就维持现状吧，肉眼注意」 | ⛔ 否决：本次漏译的**成因**恰恰是「靠注意」（`818e910` → `afb4c637e` 两代都没人翻）。不改机制＝可复发 |
| 「圆角是不是该做成共享件的可配属性（`radius` prop）」 | ⛔ 否决：**零消费者**。四处消费位外观应当一致（同契约）——加 prop 等于「先造抽象、等消费者」，与判据 A「一次到位（不做超前抽象）」相反 |
| 连带重审：`InlineInput` 是否还有其他「契约声明缺失」 | 已复查：`bg-input`／`border`／`color`／`outline`（自绘 focus）／`font-family: inherit`／`width: 100%` 均在；**唯一缺的就是圆角**。⛔ 不顺手改别的（外科式） |

## 五、核心理念对照

| 理念 | 本案体现 |
|:--|:--|
| **一次到位 / 不做超前抽象** | 圆角写进基类一处（⛔ 不加 `radius` prop）；翻译收口做在**已有**四个位点（⛔ 不预造第三方渲染方抽象） |
| **契约要有真源** | 输入框契约＝`.ldk-input`（`index.css:258`）；**圆角值的真源＝`app.surfaceRadius` 滑杆／主题**（输入框只**消费** token，不定义值）。本次让唯一脱队的共享件归队 |
| **机械兜底优于人眼** | 轴二不能靠注意 ⇒ 见 §六（命名可见化 ＋ 门禁腿 ＋ 英文环境行为断言）；图本身也有机械门（`校验-拟真度.cjs`） |
| **外科式最小改动** | 轴一 = 1 行；轴二 = 调用点收口（⛔ 不动数据面/contracts/词典） |
| **搬运的可验证性** | 轴一验收可**逐字节**比对：除新声明外几何/颜色零变化；轴二验收 = 中文态渲染**逐字节不变**（译名只在非中文态生效） |

## 六、门禁空档与替代判据（轴二的正式登记）

**空档定义（一句话）**：`值是运行时变量（模型字段）、本该翻译、但调用点从未调用 t()` —— 现有**三道**相关腿原理上全部照不到：

| 腿 | 能力边界（实读实现） | 对本案 |
|:--|:--|:--|
| 壳 `linkdesk/no-hardcoded-chinese`（`eslint-local-rules.js:920-988`） | 只查 **JSXText ／字符串字面量／单准模板串**，且跳过已包 `t()` 的 | 位点源码**零汉字** ⇒ 无字可查 |
| 插件 SDK `linkdesk/no-hardcoded-zh`（`rules.js:211`，注明「同逻辑」） | 同上 | 同上（本漏点在**壳侧视图**，插件仓腿也够不着） |
| `scripts/audit-i18n.mjs --strict`（键覆盖率） | 只查 `t("…")` **用到的键有没有词条** | 该位点没用 `t()` ⇒ 无键可查；且词典**本来就全**（编辑器插件自带 `"编辑器": "Editor"`） |

**替代判据（三层，D2/D3 拍板）**：

1. **可见化（可选，有摩擦）**：把模型的原文标签**更名**，让「这是未翻译原文」在**每个调用点字面上看得见**（`RowOption.label` → `labelRaw` 之类）。⚠️ **摩擦**：`RowOption` 在 `@linkdesk/ui` 的**导出面**上，而壳对作者有三条承诺「**只加不删** ／ 行为改走新名字 ／ 样式跟着壳走」（见 CHANGELOG `v0.2.13` 段，机械门 `check-ui-surface-additive`）⇒ **直接更名 = 破坏第三方设置渲染方**。故更名只能走**追加式**（新增 `labelRaw` 并存、旧字段保留并标弃用），成本与收益值得拍板（[D3](04-任务清单.md)）。
2. **机械腿（待议，须走立法流程）**：三种形状，成本差别很大——
   - **甲 命名约定腿**：新增 ESLint 局部规则「名字标了原文的标识符（`*Raw`／`labelRaw`）⛔ 不得直接进 JSX，须被 `t()` 包住」——纯语法判定（无数据流分析）。**前提是第 1 条**（不更名就没有标记可判）。
   - **乙 入参收窄**：给共享件的 `label` 换成品牌类型（只有 `t()` 产出的值可赋值）——编译期真挡得住，但类型体操会传染到**所有**消费方（含第三方渲染方），成本高。
   - **丙 不加腿**：只靠下面第 3 条的行为断言 ＋ 文档纪律（「新增渲染插件显示名的地方必须 `t()`」写进作者面）。
   ⚠️ 立法纪律：照 [05-防复发-机械准入原则](../../已落地/文件打开方式与贡献点/10-纠正案-共享件转正与归一/05-防复发-机械准入原则.md) 走——⛔ 不许为凑绿加白名单；⛔ 不许只加尺不给「怎么改才对」的指路。**本案不预判结论**，等 [D3](04-任务清单.md) 拍板。
3. **行为断言（必做）**：夹具灌入中英两套词典，断言**英文环境**下卡头／下拉项／胶囊／触发条四处文字 = **译名**。这是唯一能覆盖「运行时值」语义的红灯，也是本案的**主验收**。
   ⚠️ 现状：`ManagerView.test.tsx` 只断言了筛选框的 `aria-label`，**没有一处**断言下拉项文字 ⇒ 现在改成什么样都不会红（所以本轮是「从零加钉子」）。

**空档要不要进纠正台账**：建议在 [09-待纠正-能力托管与共享件缺口台账](../../已落地/文件打开方式与贡献点/09-待纠正-能力托管与共享件缺口台账.md) **补一条 `P10`**（该档现为 P1–P9，新增挂 §二「待纠正清单」末尾），指向本夹——理由：它不是本夹独有的病，是**共享化搬运**时按「渲染逐字节不变」验收所必然继承的既有缺口；登记后**下一轮任何搬运**都能查到这个先例（[04 D4](04-任务清单.md) 决定）。
