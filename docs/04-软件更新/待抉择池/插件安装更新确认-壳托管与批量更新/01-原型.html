确认与执行逻辑

一句话：市场只发起；壳决定要不要问、问什么、能不能执行；执行必须带一次性 token。

① 入口

首装 / 单项更新 / Update all / 自动更新。市场只传结构化请求。

→

② 壳判定

首装？来源/发布者变？降级？minApp？哈希？→ 决定问/免问/直接拒。

→

③ 确认

壳画富卡 / 批量汇总卡 / 来源变更卡；市场不能传 HTML/CSS。

→

④ token

确认后签发一次性 token，绑定 pluginId + version + source + sha256 + 60s。

→

⑤ job

3 并发槽 → 下载/校验/解压/原子替换；进度走 plugin:installJobs。

动作确认？形态 / 理由
新装插件（任何来源）是壳富卡：来源/发布者/版本/大小/哈希；第一次信任决定不能省。
同源更新 · 官方源（official-silent）否直接入队；行内进度 + 完成 toast。用户装它时已做过信任决定。
同源更新 · 第三方（按源信任）按设置首次按源确认；信任后免问；来源/发布者变更自动失效。
批量 Update all一张汇总N 个、旧→新、来源、大小、风险标记；确认后全部入队。
来源 / 仓库 / 发布者变更是（硬确认）按新装处理，展示旧→新；不能当普通更新。
降级 / 选旧版是显式意图 + 数据/schema 风险；确认卡明示。
minAppVersion 不满足直接拦装了也跑不了；不进入确认。
哈希 / ID / zip-slip 失败直接拒技术攻击/损坏；征求同意没有意义；清理暂存。
自动更新（opt-in）否开关本身即授权；结束后汇总通知；默认只对官方源开。
内置 core（市场自身）单更不进批量；更新后提示重启，避免队列中途重启。
关键不变量：原始 pluginManager.install/update 没有一次性 token 一律拒绝；任何市场（含第三方）都必须走壳的 requestInstall / requestUpdateBatch。这样「不调 API 就不能成为插件市场」才是真的，而不是一句契约口号。

状态机

Queued → Downloading → Verifying → Extracting → Committing → Done；任一步失败 → Failed / 回滚；目录占用 → Deferred（重启补提交）；用户取消 → Cancelled。

Queued

等 3 个并发槽之一；可取消。

→

Downloading

HTTPS；进度/大小；可取消。

→

Verifying

sha256 + id + 版本方向；不符直接拒。

→

Committing

原子 rename；失败回滚旧版。

→

Done

账本更新；提示重启；不自动开详情。

更新完成

一条汇总，不逐项弹；失败项保留重试；不自动打开详情页。
