# 01 · 方案与落点契约（草案 —— 拍板前底稿）

> ⚠️ **状态：草案**。体例照范本 [已落地/兜底打开链与二进制文本选项/01-方案与落点契约.md](../../已落地/兜底打开链与二进制文本选项/01-方案与落点契约.md)；拍板冲突处**先改本档再立任务**。

> **愿想（贯穿本档的北极星）**：用户通过 LPM 管理内置内容物，同时通过第三方插件替换任何 GUI——**皮是第三方的，内容是官方的；更新不碰皮，替换不碰内容**。

## 一、概念层：内容物（Content Item）是什么

**四条边界（与插件划清）**：

| 维度 | 内容物 | 插件 |
|---|---|---|
| 形态 | **纯数据**（文档/资源包），零代码执行 | 代码 ＋ 声明 |
| 分发 | LPM 内容物轴（官方目录 channel 复用） | 插件市场（收录两步） |
| 卸载 | ⛔ 不可卸载，只可更新/回基线 | 可装可卸 |
| 身份 | 唯一来源 = 内容物 manifest | 唯一来源 = plugin.json（硬约束 11 同法） |

**两层模型（读序唯一真相源）**：

- 基线层：`resources/<contentRoot>/`（随包只读）——离线保底（用户要点 9）；
- 覆盖层：`%APPDATA%/linkdesk/content-overrides/<itemId>/`（LPM 更新写入）——🔴 **落点先登记用户机落点规范再写码**（硬约束 27）；
- 读序：覆盖层存在且校验通过 → 覆盖层；否则基线。**回滚 = 删覆盖层目录**——原子性天然，不造第二套回滚逻辑。

**内容物 manifest（schema 字段草案）**：

| 字段 | 型 | 说明 |
|---|---|---|
| `itemId` | string | 永不可变（对齐 pluginId 纪律） |
| `label` / `description` | string | 官方内容物，双语直填（面人档纪律） |
| `version` | semver | 独立于壳版本 |
| `appliesTo` | range | 适用壳版本（错配标注用，见 03-X5） |
| `dataCommand` | commandId | **消费方唯一取数通路**——门禁验证在册（防遗忘核心，§五） |
| `entry` | path | 资源包内入口 |
| `integrity` | sha256 | 校验 |
| `channel` | stable\|… | 对齐官方目录 channel |

- schema 落位：`packages/plugin-sdk/schemas/content-item.schema.json`（对齐 theme.schema 先例，三处下发副本同笔）；类型进 `@linkdesk/contracts`。
- ⭐ 命名待拍板：`content-item.json`（放内容根目录根部）。

**注册总账 = 扫描生成，零手工清单**：LPM 列表 = 扫描内容根目录的 manifest ＋ 官方目录最新版查询缓存。**没有手工登记表可漏**——新内容物 = 新建 manifest；忘建 = 门禁红 ＋ LPM 不显示（§五）。

## 二、API 层（命令面 ＋ 数据面）

**管理面 `lpm.*`（面向用户/AI）**：

| 命令 | params | 返回 | 说明 |
|---|---|---|---|
| `lpm.listItems` | — | 内容物 DTO[]（基线/覆盖/active 三版本、appliesTo、可更新否） | 结构化，AI 可读 |
| `lpm.checkUpdates` | — | 更新集 | 查官方目录；结果经**唯一通知面**提示 |
| `lpm.updateItem` | itemId | 结构化结果（from/to/校验态） | 下载→sha256→临时目录→原子 rename |
| `lpm.updateAll` | — | 逐项结果[] | 逐项独立，无事务耦合（03-X9） |
| `lpm.getItemDetail` | itemId | 详情（版本历史/更新说明） | |
| `lpm.rollback` | itemId | 结果 | = 删覆盖层 |

**数据面 `content.*`（面向消费方——壳视图与第三方替换 UI 走同一扇门）**：

| 命令 | 说明 |
|---|---|
| `content.read {itemId, path?}` | 读内容（读序内聚在 service）——姊妹档铁律 A 的内容轴实例 |
| `content.getVersion {itemId}` | `{baseline, override, active}` |

- ⭐ 域名拆分理由：管理面（谁更新）与数据面（谁消费）受众不同；是否合并单域待拍板。
- 全命令 meta 带 `description`＋`params`（硬约束 26②）；注册进壳命令注册表 → ai-bridge/linkdeskctl/MCP 自动可达（⚠️ ai-bridge 白名单需补 `lpm` 组——实施项）。
- 事件：`content:updated {itemId, from, to}` → 状态栏提示 ＋ UI 刷新（订阅走 IPC generation counter，硬约束 5）。

## 三、代码层落点（每块住哪、为什么是这层）

**判据 A 三问（照范本格式）**：

| 新增物 | 三问结论 | 落位 |
|---|---|---|
| 内容物管道（读序/校验/落盘/回滚/目录缓存） | 多提供方（N 个内容物）× 多消费方（LPM UI/壳视图/第三方替换 UI）→ 核心准入三标准全中 | **主进程 service**：`electron/services/content/`（写盘＋网络必须主进程；形态对齐 ai-bridge 服务） |
| LPM 整套 UI | 消费宿主声明面（manifest/目录数据）的呈现层——**设置页同律** | **`factoryRole:"lpm"` 官方插件**（bundled，`core:true`；渲染控件走 `@linkdesk/ui`，G1/R6 照守） |
| manifest schema | 宿主声明面本体 | SDK schema ＋ contracts（声明面归契约层） |
| 门禁腿 | 机械兜底 | `scripts/check-content-ledger.mjs`（新）＋ R8 词表扩展 |

**管道七步（`lpm.updateItem` 内部，全部在主进程 service，单实现）**：

1. 查目录最新版（channel 匹配）→ 2. 下载到临时目录 → 3. sha256 对 `manifest.integrity` → 4. 写覆盖层临时名 → 5. 原子 rename → 6. 版本推进 ＋ 发事件 → 7. 任一步失败 = 丢弃临时物 ＋ 读序自动回基线 ＋ 一条通知。
- ⛔ 步骤不拆分到别处；⛔ 池侧零下载零写盘零清单逻辑（哑渲染器）。

## 五、防 2028 遗忘：新内容物机械链（用户点名的场景）

**场景复述**：今天（2026-11-05）定案、两天后实现 LPM；2028 年某 AI 做用户操作手册时忘了两件事——「要进 LPM 统一管理」「要可被第三方替换」——把它写成第二个硬编码 AI 手册。

**四层锁（层层独立，漏一层还有下一层）**：

1. **孤儿门禁**：内容根目录无 manifest = `npm run check` 红（check-content-ledger 扫描对账）→ 不建 manifest 过不了提交；
2. **dataCommand 义务**：manifest 必填 `dataCommand`，门禁验证该命令在册（R3 同法）→「内容物必须经数据命令被消费」机械化——第三方替换 UI 天然有路，壳视图硬编码直读资源无法过账；
3. **可替换性挂钩**：呈现该内容物的页面若是页面型 → 立档时即声明 factoryRole（设置页先例）；部件型 → renderers（姊妹档 §3.9 分类轴）；由姊妹档候选门禁「有槽位必有三命令」兜住；
4. **R8 词表扩展**：「内容物更新以后再说」「先硬编码以后 LPM 化」句式 = 红（check-no-deferred-placement 扩词表）。

⇒ 2028 年的 AI 想硬编码都过不了 check：没 manifest 进不了 LPM 也提交不了；有 manifest 没 dataCommand 红；dataCommand 指向不存在的命令红；自立第二更新面违反 00-§五 纪律。**门禁红的信息文案本身要指路**（写明「见 待抉择池/内置件独立更新与文档国际化分型」）——让报错当老师。

## 七、不变量（本件不许碰）

1. **池=哑渲染器**：池侧零下载、零写盘、零清单逻辑。
2. **单等级插件制**：LPM 是插件不是特权层；内容物不是「低级插件」——两种身份互不混。
3. **内容物零代码执行**：纯数据。哪天要代码 = 升级为插件走市场收录，⛔ 不给内容物开执行口子。
4. **硬约束 27**：覆盖层落点先登记再写码。
5. **官方目录收录纪律**：内容物 channel 复用收录链，⛔ 不给绕收录的口子。
6. **通知面唯一**：更新提示走状态栏，⛔ 不做弹窗第二面。

## 八、UI 面（🔴 仅标记，不设计——用户 2026-11-05 拍板「暂时不做」）

- 一句话草图（仅锚定范围，**非设计**）：清单视图 = 全局「检查更新」＋ 内容物行（名称/当前版本/最新版本/适用壳版本/更新按钮）＋ 每行可深链回对应消费面。
- ⛔ 届时动手前必走设计 skill 门禁（硬约束 16）＋ design-flow 流程；mockup 另立（照范本 mockups/ 惯例）。
- 第三方替换口径：factoryRole **整套替换**即可，官方不预留「部分换皮」接口（避免半替换态）。

## 九、主线一（文档分型与翻译锁）机械形态细化 —— 自审补强（2026-11-05）

> 自审发现：主线一在 00 §2.1 只有四条纲领，而 00 §六-8 排期却把它排最先——设计深度不对等。本节补到位（细节仍待拍板微调）。

1. **分型的机械抓手 = 文档出口总账**（对齐硬约束 27 立法法）：「面人档」的判定不靠猜目录意图，靠**出口**——文档凡要出仓到用户/第三方作者手里，必经构建产物管道（现状三条：plugin-docs npm 包、`resources/ai-manual/`、未来用户操作手册包）。总账登记每条出口及其源树；门禁验证：**在册出口的源树必须施锁**（双语篇篇对应＋内容级锁）；新增出口不登记 = 红。在册之外的 docs 树 = 维护者/任务档，不施翻译锁、照旧中文直行——用户第 11/12 点「区分本身机械化」的落点。
2. **内容级锁形态**：DSH 式 pair-hash——每对双语旁一份锁记录（两语 git blob 哈希；改任一边必须同笔带上另一边并重锁；`--check` 模式挂 check，负控自测 = 单边改哈希即红）。锁随 pair 走（⭐，DSH 同款）还是集中一份 → 拍板点。
3. **术语级锁形态**：术语总表（scripts 数据文件，中英一对一；从 factoryRole/槽位/收录/内容物 等核心词起步）＋ 门禁逐术语全文对账——起步**只报不拦**（照 audit:plugin-commands 先例），跑稳转拦。
4. **AI 手册英文化增量轨**：07 树逐篇 front-matter 标 `lang: zh | bilingual`；门禁只对已标 bilingual 的篇施对账锁——翻一篇锁一篇，不欠整树债；未标篇章现状照旧（只报）。
5. **锁的作用域（自审补明）**：锁守**仓库源**；LPM 分发**构建产物**（内含两语全量）——链路 = 源改 → 锁同步 → 构建 → 目录收录 → LPM 更新。锁不随包、产物不回锁（03-X18 钉死）。
