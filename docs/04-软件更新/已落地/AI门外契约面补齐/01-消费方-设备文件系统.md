# 消费方 · 设备文件系统（device-fs）

> **本档身份**：本系列总纲 [00-提案](00-提案.md) **D1（收发方向）**的**消费方章节**。
> **为什么在这里**：它自己零壳改动，但**交付必须等 D1**（数据面在壳）⇒ 按 04/05 分档判据整案归 04。
> **来源**：02 工程外部 AI（「为了放一张测试图，只能把 SD 卡拔下来插电脑，来回三次」）。
> **2026-11-25 用户裁定（T18 挂账）**：device-fs 仓当前不存在；⛔ 在本档新建；D1 先由 serial-monitor 的 T17 接入验收，仓出现后再补 T18。

## 一、它要壳给什么（即 D1 的验收对象）

`SerialDataPayload` 带 `dir:"rx"|"tx"`（或 `echo:true`）。

**为什么必须要**：本插件的应答与板子自己的日志混在一条流里。没有方向标记，只能靠"发出去的字符串一模一样地回来"去猜——不可靠，且协议一旦分块就失效。

## 二、插件自己做什么

1. **设备端**（用户固件里实现）：4 条命令的小 Agent —— `ls` / `get` / `put` / `rm`，带长度、CRC、分块；
2. **插件端**：发命令、收数据、拼文件、报进度；选文件走壳的 dialog 通道（⛔ 不在池里 `input.click()`，硬约束 25）。

> ⛔ 不做"调试器直读 SD 块"：那要存储布局知识、侵入性强；串口 Agent 只要固件配合，干净可移植。

## 三、命令面

| 命令 | 回执 |
|:--|:--|
| `devicefs.list <path>` | `{ok, entries:[{name,dir,size}], tookMs}` |
| `devicefs.get <remote> <localPath>` | `{ok, bytes, sha256, tookMs}` |
| `devicefs.put <localPath> <remote>` | `{ok, bytes, sha256, tookMs}` |
| `devicefs.remove <remote>` | `{ok, removed:true}` |

## 四、边界

- ⛔ 不做通用 shell（不暴露任意命令执行）；
- ⛔ 不做烧录 → [烧录器](../../待抉择池/通用能力底盘/02-消费方-烧录器.md)；
- 卸载即消失，壳零改动。

## 五、验收（同时是 D1 的验收）

1. D1 到位后：插着板子 `list` 看到 SD 根目录；`put` 一张图板子上能打开；`get` 回来 sha256 一致；
2. 断线/不响应 → 明确报错（有码、有 hint），⛔ 不挂起；
3. 大文件（>1MB）分块不卡死，进度可查；
4. 卸载 → 壳无残留。
