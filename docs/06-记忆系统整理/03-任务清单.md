## 🚫 第零条铁律 · 审议门（最高优先级，覆盖其余一切）

> ### **严禁「自己审计 → 自己执行 → 自己删」。**
>
> **每一批次的固定节奏：**

```
① 通读全文 → 出处置表
② 向用户报告分析（在对话里讲清楚，不是只写进文件）
③ ★ 审议门：与用户探讨 → 用户明确放行 ★   ← 停在这里，不许往下走
④ 写折入内容 → 核对 → 执行删除
⑤ 校验 → 写档案 → git 提交
```

**审议门细则：**

1. **审计结束后必须停下报告**——逐份讲「我读了什么 / 判定删还是并 / 为什么 / 拿不准的是什么」。
   报告在**对话中呈现**，不许只落文件让用户自己去翻。
2. **等用户表态**——用户可能推翻、修改、或要求再看某几份。**未得到明确放行前，一个字都不许删。**
3. **"AI 自己觉得没问题"不是放行**。沉默不是放行。
4. **允许用户逐份裁**——用户说"这份留着"就留着，不辩论。
5. **审议结论写进批次档案**——记清哪些是用户拍板改的判定，避免后来者以为 AI 自作主张。
6. **拿不准的必须进"待用户裁"清单**——不许 AI 自行消化。

**违反本条的后果：** 删除不可逆（虽有三重备份），且破坏用户对整理过程的信任。**宁可多问一轮，不可先斩后奏。**

## 🚨 执行时铁律（除第零条外）

1. **逐份通读** —— 打开每一份候选文件读**全文**，禁止凭文件名、frontmatter description、或本清单的摘要下判。
   > 本清单写作时**并未逐份精读**，候选名单是基于描述与结构推断的**待审清单**。
2. **写出判定理由** —— 每份文件在处置表里写一行：`文件 / 判定(删·并·留) / 理由一句话 / 折进哪个文件`。**没写理由的不许动。**
3. **白名单禁碰** —— `00-整理总纲.md` §三 的 **16 份绝对不删**；压缩也须原意不变。
4. **先写后删** —— 合并文件**写完并核对无遗漏**，原文才可删。禁止"先删后写"。
5. **每批一次提交** —— 批次开始前工作区必须干净；批次结束后立刻 git 提交，形成独立回滚点。
6. **「须确认」项专项处理** —— 清单中标记 ⚠️ 的文件，执行时须**读全文 + 查工程现状**（grep 代码 / 查清单）再定。
7. **拿不准就保守** —— 判定存疑 → **保留**，并写进「待用户裁」区。
8. **不许跨批混合** —— 上一批未放行，绝不开始下一批。
