确认与执行逻辑

市场只发起；壳决定谁要问、能不能执行；确认 UI 是可替换渲染槽；完成态复用通知面板。

流程

① 入口

首装 / 单项更新 / Update all / 自动更新。市场只传结构化请求。

→

② 壳计划

policy 计算 silent / ask：首装、来源变更、降级、minApp、哈希全在这里裁决。

→

③ 确认渲染槽

默认壳渲染器；第三方可整套替换。渲染体只吃 DTO，⛔ 不碰 token/策略。

→

④ token

一次性绑定 pluginId + version + source + sha256 + 60s；原始 API 无 token 即拒。

→

⑤ job

3 并发槽 → 下载/校验/解压/原子替换；进度走 plugin:installJobs。

→

⑥ 通知面板

轻 toast 即时汇总 + 铃铛通知面板（现有 notificationPanel 槽）留结果/重试；完成不新开页面、不弹新模态。

确认策略矩阵

动作确认？形态 / 理由
新装插件（任何来源）是壳富卡：来源/发布者/版本/大小/哈希；第一次信任决定不能省。
同源更新 · 官方（silentOfficial 开）否直接入队；通知面板行内进度。用户装它时已做过信任决定。
同源更新 · 信任来源（silentTrustedSources 开）否只对信任清单里的来源；首装仍确认；来源变更自动失效。
同源更新 · 未信任第三方是一张确认卡；确认后可选记住此来源（只影响更新）。
批量 Update all · 混合来源只对 ask一张汇总卡只列需确认项；silent 项摘要；取消 = 整批取消。
来源 / 仓库 / 发布者变更是（硬确认）按新装处理，展示旧→新；信任开关不豁免。
降级 / 选旧版是显式意图 + 数据/schema 风险；确认卡明示。
minAppVersion 不满足直接拦装了也跑不了；不进入确认。
哈希 / ID / zip-slip 失败直接拒技术攻击/损坏；征求同意没有意义；清理暂存。
自动更新（opt-in）否开关本身即授权；结束后汇总通知；默认只对官方源开。
完成反馈不新开轻 Toast（TransientToast，底部居中）即时汇总 + 铃铛通知面板留结果/重试；同一 store 双呈现；⛔ 无新完成页、无第三面。
内置 core（市场自身）单更不进批量；更新后提示重启，避免队列中途重启。
关键不变量：原始 pluginManager.install/update 没有一次性 token 一律拒绝；任何市场（含第三方）都必须走壳的 requestInstall / requestUpdateBatch。确认 UI 可被第三方渲染器替换，但 token、策略、来源身份、队列永远在壳。
