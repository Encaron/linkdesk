# 命名规范——七种名字，一条身份

> 2026-09-14 ·。**读者 = 插件作者。** 读完能回答四问：**id 怎么起？能不能改？显示名怎么改？仓库叫什么？**
> 决策论证与 VS Code 实测依据住 [插件源码外移层/09-命名规范.md](https://github.com/Encaron/linkdesk/blob/electron/docs/02-Electron架构/E6_插件生态与发布/插件源码外移层/09-命名规范.md)——本篇是作者面落点，两处**只维护一处**：改规则先改本篇并回指，别造第二份。

---

## 一、七种名字一张表

| 名字 | 真源在哪 | 谁在用 | 能不能改 |
|:--|:--|:--|:--|
| **插件身份 id** | `plugin.json`（显式声明 `pluginId`；未声明时**临时**兜底 = 工程目录名——兜底不推荐，显式声明才是正路） | 安装目录、卸载记录、更新对账、catalog 去重 | 🔴 **发布后永不可变** |
| **显示名** `name` | `plugin.json` | 界面、市场卡片 | ✅ 随便改（改完 bump 重发） |
| **版本** | `plugin.json` 的 `version` | 更新比对、Release tag、catalog | 每次发布必变 |
| **分发件名** | `<id>.linkdesk-plugin`（SDK 自动生成） | zip 安装裁决、Release 资产 | 跟随 id，**不许手改** |
| **Release tag** | `v<version>`（publish 自动打） | 更新检查 | 跟随版本，**不许手打** |
| **GitHub 仓库名** | 无规则 | `downloadUrl` / `readmeUrl` / 详情页「仓库」 | ✅ 自由（改名代价见 §四） |
| **本地目录名** | 无规则 | 只有构建工具 | ✅ 自由（⚠️ 现状红线见 §五） |

**混为一谈是命名问题的总根源**：身份是给机器对的账，显示名是给人看的，仓库名和目录名只是工程住址——三者互不相干，改其中一个不该牵动其他。

---

## 二、四条字符集/格式约束（机械执行，写错当场被拒）

| 约束 | 规则 | 出处 |
|:--|:--|:--|
| 插件 id | `^[A-Za-z0-9][A-Za-z0-9._-]*$`（首字符须字母或数字） | `@linkdesk/plugin-sdk` 的 `SAFE_PLUGIN_ID`（validate） |
| 版本号 | `^\d+\.\d+\.\d+$`——**不许 `-beta` 之类预发布后缀**（schema 直接拒；想表达预发布目前没有语法，这是现状不是遗漏） | `plugin.schema.json` |
| 视图容器 ID | `^[a-z][a-z0-9-]*$` | schema / [03-插件contributes规范](03-插件contributes规范.md) |
| 分发件基名 | = 插件 id | SDK `assetNameForId` |

**id 建议小写连字符**（如 `file-tree`）——规则允许大写与点，但小写连字符最省事，官方插件全这么做。

## 三、三问直答

- **id 怎么起？** 字符集见上表；**发布后永不可变**——它 = 安装目录名 ＋ 卸载记录键 ＋ 更新对账键，换了 id 等于换了一只插件（旧数据看似丢失、更新链静默断）。**在 `plugin.json` 里显式写 `"pluginId"`**，别依赖目录名兜底。
- **能不能改 id？** 不能。想换名字改的是显示名。
- **显示名怎么改？** `plugin.json` 的 `name` 随便改，改完 **bump 版本重发一版**（已装用户副本按版本固化，不重发别人看不到新名）。
- **仓库叫什么？** 完全自由，不强制前缀。官方插件建议统一 `linkdesk-plugin-<id>`（惯例条文住 [插件源码外移层/09-命名规范.md §五](https://github.com/Encaron/linkdesk/blob/electron/docs/02-Electron架构/E6_插件生态与发布/插件源码外移层/09-命名规范.md)，拍板后只那处维护）；第三方随意。

---

## 四、改仓库名的代价

已发布 catalog 条目里的 `downloadUrl` / `readmeUrl` 内嵌 `owner/repo`——**改名会断旧版本的下载与 README 链接**（源码不受影响）。重发一版新条目可自愈，但旧版本条目仍指旧链。**能不改就不改，要改趁早。**

---

## 五、本地目录名与插件身份无关

**插件 id = 顶层 `pluginId` 字段**（必须显式声明；发布后不可改），**不是目录名**。⇒ 本地工程目录名**随便改**，身份不受影响。

反过来，**改 `pluginId` 才是危险动作——那等于换一个插件**：安装目录并存两份、卸载记录对不上、catalog 出现两条、更新链静默断、插件数据看似丢失，**五条后果全不报错**。真要换 id，等于发布一个新插件（见 [15-多仓开发与本地工作区 §五](15-多仓开发与本地工作区.md)）。

---

## 六、版本号——四处同源

版本号有**四个落点，必须同源**，改一处即四处同改：

```
① CHANGELOG.md 段标题的版本号   ## v<version>
② plugin.json.version           ← 唯一真源（schema 级必填）
③ 目录条目 versions[].version    ← publish 自动写
④ package.json.version          ← 必须与 ② 相等
```

- ①②③ 的既有规则（段标题解析、诚实留空、倒序）→ [09-插件目录规范 §CHANGELOG.md 的格式约定](09-插件目录规范.md)。
- ④ 是第四处锚：`package.json` 是独立仓里新人（和 AI）**打开仓库第一眼看到的东西**——两个版本号并存且不一致，必然有人 bump 错那一个；而 `publish` 与内容指纹门禁读的都是 ② ⇒ **改错的那个 = 静默无效**。
- 什么时候 bump（MAJOR/MINOR/PATCH 判据）→ `.claude/skills/version-bump/SKILL.md`——那里是唯一权威，本篇不另立一套。

## 七、宿主保留的名字——不许占，也别指望「借用」

**一句话规则（不用查表就能记住）：宿主保留的名字不许占；插件自己写的名字必须带 `<pluginId>` 前缀。**

要防的是同一件事：**公共花名册**——一张全局名字表，**谁都能往里写、没有人查归属、撞了不报错**，
结果总有一方**静默失效**。落在不同家族上就是不同的坏法：

- **命令 id** 撞了 ⇒ 同一条命令有两个人声明，谁生效看注册顺序；
- **设置键** 撞了 ⇒ 你的值把宿主的设置顶掉（用户会觉得「我的设置自己变了 / 丢了」）；
- **外观 id**（配方 / 配色 / 图标主题）撞了 ⇒ 主题下拉里出现两条同 id 的条目，选中态看着乱；
- **上下文旗子** 撞了 ⇒ 别人的 `when` 表达式判到你的状态上（菜单/快捷键时隐时现）。

### 7.1 名单在哪、谁说的算

这份名单是**生成式**的：壳仓扫描自己的源码产出 `scripts/host-reserved.json`，
并往 `@linkdesk/plugin-sdk` 里发一份**逐字节相同**的副本。⇒ **你本地就有**：

```
node_modules/@linkdesk/plugin-sdk/schemas/host-reserved.json
```

下面这张表与它**逐名对账**（门禁 `scripts/check-reserved-names-doc-sync.mjs`，跑在 `npm run check` 里）——

| 家族 | 保留的名字 | 你会撞上什么 |
|:--|:--|:--|
| 宿主命令前缀 | `app.`、`core.`、`theme.`、`update.`、`view.`、`workbench.` | 你的命令 id 落进宿主自己的段——命令面板、快捷键设置页里它看起来像宿主的功能 |
| 宿主协议 id | `bracket` | 与宿主的括号匹配协议处理器同名 ⇒ 有一方不生效（不报错） |
| 宿主伪 pluginId | `app`、`appearance`、`update` | 宿主自己也以「插件」身份注册（壳通用 / 外观 / 更新）⇒ 用这些 id 会被当成宿主自己 |
| 宿主配置键 | `app.schemaVersion` | 配置的**内部版本标志**（设置界面里看不到、也没有注册过）——占它会让迁移记账错乱，用户数据看着丢 |
| 宿主配置键 | `app.theme`、`app.themeColor`、`app.themeColorMode`、`app.iconTheme` | 主题与配色——占它 = 直接顶掉用户当前选的主题 |
| 宿主配置键 | `app.appearanceMode`、`app.accentColor`、`app.accentMode`、`app.accentSource`、`app.menuStyle` | 亮暗模式、强调色、菜单样式 |
| 宿主配置键 | `app.backgroundImage`、`app.backgroundMask`、`app.backgroundOpacity`、`app.zoneBackgroundImage` | 背景与区域背景 |
| 宿主配置键 | `app.glassBlur`、`app.glassOpacity`、`app.glassSaturate`、`app.glassTint` | 玻璃材质四参 |
| 宿主配置键 | `app.surfaceRadius`、`app.zoneRadius`、`app.zoneRadiusScale` | 圆角 |
| 宿主配置键 | `app.fontFamily`、`app.fontFamilyMono`、`app.fontTone`、`app.uiFontScale` | 字体与字号 |
| 宿主配置键 | `app.mixMode`、`app.mixFont`、`app.mixBackground`、`app.mixReset` | 混搭来源 |
| 宿主配置键 | `app.language` | 界面语言 |
| 宿主配置键 | `app.osIntegration.dirMenu`、`app.osIntegration.fileAssoc`、`app.osIntegration.fileMenu` | 系统集成（右键菜单、文件关联） |
| 宿主配置键 | `app.update.mode`、`app.update.showReleaseNotes` | 更新通道 |
| 宿主配方 id | `dark`、`light` | `app.theme` 的**兜底取值**。⚠️ `light` 另有一张**证照**：官方 `theme-defaults` 是宿主亮兜底的官方实现者，只有它有权声明这个 id |
| 宿主配色 id | `dark-fallback`、`light` | `app.themeColor` 与配色来源空间的兜底取值 |
| 宿主图标主题 id | `default` | `app.iconTheme` 的保底取值 |
| 宿主外观哨兵值 | `followTheme` | 混搭来源的「跟随主题」哨兵——**它不是 id**，别拿一个插件 id 去顶它 |
| 宿主专用旗子（插件**禁设**） | `activeEditor`、`editorCount`、`editorHasSelection`、`inputFocus`、`sidebarPosition`、`updateActionable`、`updateButtonLabel` | 你在运行时经 IPC 设它，宿主会 `console.error` **点名你**（值照写：旗子是状态不是注册，运行时拿不到「谁是先者」） |
| 宿主公开约定旗子（插件**可设**） | `settingKey`、`settingFollowTheme`、`settingModified`、`settingResetsToDefault` | 这 4 个是**公开约定面**：官方 `settings` 插件写、宿主命令的 `when` 读——照约定用，别改语义 |

**怎么自查**（你自己的仓里就能跑）：装上 `@linkdesk/plugin-sdk` 后，你仓里的 `verify` 会跑四条归属腿
（命令 id / 配置键 / 外观 id / 上下文旗子）；哪条犯了会直接报点并给出**「应以 `<pluginId>.` 开头」**的改法。

### 7.2 三类「全局概念名」为什么不需要前缀

有三种名字，看着「没主」，其实**本就不该有主**——给它们加前缀是**语义错误**，不是规范化：

| 名字 | 例子 | 为什么不能加前缀 |
|:--|:--|:--|
| **文件关联扩展名** | `.md`、`.json`、`.ts` | 它对的是**操作系统与文件系统**的通用概念——加前缀等于让系统认不出这个文件类型 |
| **语言定义扩展名** | `langDefs[].extensions` | 同上：这个字段要能和外部工具、编辑器对上同一个语言 |
| **语言包语言码** | `zh` / `en` / `ja`（`langDefs[].id`、`contributes.i18n` 的键） | 它是 **BCP 47 语言标签**，全世界的语言码就这些写法——`my-plugin.zh` 不是一门语言 |

⇒ 判据上它们**恒空转**（既不判红也不登记）：不是漏网，是明确划出去。

### 7.3 i18n 字典键——**建议**带归属，但不是强制

翻译文件是**平铺的一层键**，所有插件的键、宿主的键都住在同一本字典里。**建议**你把键写成
`<pluginId>.<原文>`（如 `serial-monitor.打开端口`）；但它是**建议不是规则**——理由与今天真实的重合
统计写在 [03-插件contributes规范 §3.9 桶键命名建议](03-插件contributes规范.md)（**那里是唯一落点**，本篇不重复）。

### 7.4 迁移说明——改过名的东西，你的值不会被丢

宿主自己这一侧的改名**都带迁移**，用户不用重调、你也不用替用户兜：

- **外观 id**（配方 / 配色 / 图标主题）：今天一律是 `<pluginId>.<词干>` 形状（如
  `theme-aurora-glass.aurora-glass`）。用户 `settings.json` 里的旧值由**壳侧迁移 v12** 搬过去
  （五个键：`app.theme` / `app.themeColor` / `app.mixFont` / `app.mixBackground` / `app.iconTheme`）；
- **命令 id / 设置键 / 用户自定义快捷键**：改名轮同样带迁移（键搬家、快捷键 id 跟着搬）；
- ⚠️ **迁移只在「插件已就位」时才搬得动**：外观 id 的新名必须**先由插件注册出来**，壳才认得出旧名该映到哪 ——
  这正是「先更新软件、后更新插件」会出现空窗的原因，壳侧为此多了一道**每次启动都跑的补跑通道**
  （它不写版本号，所以不会像普通迁移那样「跑过一次就再也不跑」）。

对你（插件作者）的影响只有一条：**别自己发明宿主的旧名做兼容**——旧名映射是壳的事，你声明**新形状**的名字即可。
