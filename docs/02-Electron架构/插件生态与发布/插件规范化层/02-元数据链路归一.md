### 2.2 🔴 schema 侧的两个陷阱（实测发现的，不是推演）

**陷阱 A：顶层 `additionalProperties: true`（实测 [plugin.schema.json](../../../03-插件制造/plugin.schema.json)）。**

⇒ **删掉 `properties` 里的定义，不等于作者写它会报错——只会被静默忽略。** 作者写了 27 条更新日志、页签显示「未附带更改日志」，他**永远查不出为什么**。

## 三、接通 `readmeUrl`——publish 自动写

### 3.1 现状：设计在、读取方在、就差写入方

未装插件时，详情页「详情」页签的回落链（[useDetailPackage.ts](../../../../plugins/marketplace/src/views/detail/DetailView/useDetailPackage.ts) 文件头注释）：

```
已装读包 README.md  →  缺失/未装走 readmeUrl 远端  →  再空降级 description
```

**中间那截空着**——`readmeUrl` 没有任何写入方。

### 3.2 写什么

`publish` 已经知道三件事：`remote.owner` / `remote.repo` / `tag`（= `v<version>`）。构造：

```
https://raw.githubusercontent.com/{owner}/{repo}/{tag}/README.md
```

**为什么用 `tag` 而不是 `defaultBranch`**：这条 URL 与**该版本打进 zip 的 README** 同源（同一个 commit）——用 `main` 会让「未装看到的」和「装上后看到的」是两份不同内容。

**为什么这个形态是安全的**：[sourceUrl.ts](../../../../plugins/marketplace/src/services/marketCatalog/sourceUrl.ts) 已经从 `readmeUrl` 反推 GitHub owner/repo（文件头注释原文「`raw.githubusercontent.com/…`（readmeUrl）」）——**用的就是同一形态**，不引入新解析分支。

### 3.3 边界（不猜，诚实留空）

| 情况 | 行为 |
|:--|:--|
| 插件工程根**没有 `README.md`** | **不写 `readmeUrl`**（写了必 404） |
| README.md 存在但**没随该 tag 推上 GitHub** | 照样写 → 未装时 fetch 404 → 现有代码回落 `null` → 降级 description（**已设计好的优雅降级，不需要新增处理**） |

## 四、接通 `versions[].changelog`——publish 从 `CHANGELOG.md` 切段

### 4.1 目标

`upsertCatalogEntry` 合并时，让 `versions[]` 每一行带上「那一版的变更说明」——**未装插件的「更改日志」页签第一次真正有内容**。

### 4.2 数据流（**只填当前版**，历史拼接是既有逻辑）

```
publish 读工程根 CHANGELOG.md
   → 按版本段标题切段
   → 取出「版本号 === manifest.version」那一段正文
   → buildCatalogEntry 的 versions[0].changelog = 该段
   → upsertCatalogEntry 拼进 versions[]（既有逻辑，不动）
```

**为什么只切当前版**：`buildCatalogEntry` 本来就只发**当前一版**（[publish.ts:268](../../../../packages/plugin-sdk/src/publish.ts)），历史是 `upsertCatalogEntry` 从既有目录里拼的——**一次发布只知道这一版**，这是对的，别改成「全量重写目录」。

### 4.3 🔴 切段算法（纯函数，必须可单测）

```ts
/** 从 CHANGELOG.md 原文切出指定版本的正文。零 IO、纯函数——publish.ts 内可 vitest 直测。 */
export function sliceChangelogSection(text: string, version: string): string | undefined
```

**算法（六条，逐条都有理由）：**

1. **BOM 剥离** —— `text.replace(/^\uFEFF/, "")`。Windows 上作者用记事本存过就会带 BOM，不剥会让第一行匹配位移。
2. **按行切，`\r?\n`** —— CRLF 兼容（本仓在 Windows 上开发，实测多个文档是 CRLF）。
3. **跳过围栏代码块** —— **` ``` ` 到 ` ``` ` 之间的行一律不看**。理由：README/CHANGELOG 里贴示例日志是常态，里面的 `## v1.0.0` 不是真段标题，误判会把示例文本当成更新说明。
4. **段标题正则**：
   ```
   /^#{2,4}\s+[vV]?(\d+\.\d+\.\d+(?:[-+][0-9A-Za-z.-]+)?)(?![0-9A-Za-z.-])/
   ```
   - `#{2,4}` —— `##` 常规；容忍 `###`（作者多写一级）与 `####`；**`#`（一级）不算**（那是文档标题 `# 更新日志`）。
   - `[vV]?` —— `v1.0.0` / `1.0.0` 都认。
   - 版本段**带 prerelease/build 后缀**（`1.0.0-beta.1`）——**必须整段捕获**。若只捕获 `\d+\.\d+\.\d+`，`1.0.0-beta.1` 会被截成 `1.0.0`，与同文件里真有的 `1.0.0` 段**撞号**。
   - 尾部 `(?![0-9A-Za-z.-])` —— 防 `1.0.0` 吃掉 `1.0.01` 的前缀。
   - **中文全角括号不拦截**（`## v1.0.0（2026-09-11）`）——`（` 不在否定类里，天然通过。
5. **正文 = 到下一个段标题为止**（或 EOF），`trim()` 后**空串 → 返回 `undefined`**（诚实留空；不返回 `""`、不返回 `"无"`——渲染层已有「此版本未提供变更说明」的兜底，见 [ChangelogTab.tsx:62](../../../../plugins/marketplace/src/views/detail/DetailView/ChangelogTab.tsx)）。
6. **同版本出现多次 → 取第一个**（「最新在最上」是格式约定，取首个即最新那一段）。

**版本相等判据**：`stripLeadingV(section.version) === stripLeadingV(manifest.version)`——**字符串严格相等**，不做 semver 松弛匹配（`1.0.0` ≠ `1.0`——**目录条目的版本号与 `plugin.json.version` 本就该逐字相同**，松弛匹配只会掩盖作者写错）。

### 4.4 🔴 可能的 bug（逐条排查，开工时按此清单写测试）

| # | 场景 | 症状 | 对策 |
|:--|:--|:--|:--|
| B1 | CHANGELOG.md **不存在** | — | 不写 `changelog` 字段（**不是填空串**——字段缺省与空串在渲染层走同一条兜底，但字段缺省更诚实） |
| B2 | 版本**切不到**（作者忘了写这一段 / 版本号写错） | 该版显示「此版本未提供变更说明」 | 返回 `undefined`。**不要回落到「取第一段」**——那会把上一版的说明挂到新版本上，是**发错信息**（同 [select.ts](../../../../plugins/marketplace/src/services/marketCatalog/select.ts) 里「不发错包」的既有纪律） |
| B3 | 段标题下**直接跟下一个标题**（空正文） | 空块 | `trim()` 后为空 → `undefined`（同 B2） |
| B4 | **代码块内的假标题** | 把示例文本当更新说明 | 规则 3 跳过围栏块 |
| B5 | **CRLF** | 段正文尾部带 `\r` | 按 `\r?\n` 切；正文 `trim()` |
| B6 | **BOM** | 第一行匹配位移 | 规则 1 |
| B7 | **prerelease 后缀** | 与正式版段撞号 | 规则 4 的完整捕获 |
| B8 | `# 更新日志`（一级标题）被当段标题 | 把「更新日志」当版本号 | `#{2,4}` 不含 `#` |
| B9 | `## v1.0.0 后续补记`（标题后无括号日期） | 段落标题合法但样式不一 | ✅ **正常通过**（日期本就可选——格式约定只约束版本号可解析） |
| B10 | 作者把版本段写成 `## [1.0.0] - 2026-09-11`（Keep a Changelog 风格） | 段标题不匹配 → 切不到 | 🔴 **这是一个真风险**：Keep a Changelog 是最流行的 CHANGELOG 约定，方括号会挡在版本号前。**对策见下** |

**B10 的处置（开工前定，别边写边改）**：把规则 4 的正则前置扩成容忍**一对可选方括号**：

```
/^#{2,4}\s+\[?[vV]?(\d+\.\d+\.\d+(?:[-+][0-9A-Za-z.-]+)?)\]?(?![0-9A-Za-z.-])/
```

——`## [1.0.0] - 2026-09-11` 与 `## v1.0.0（2026-09-11）` **两种主流写法都认**。**理由**：作者不该为了适配我们的解析器去改他习惯的 changelog 风格；**解析器适配作者，不是反过来**（对齐 [09 规范](../../../03-插件制造/09-插件目录规范.md)「诚实做法是登记」的同一精神）。文档里**两种写法都写成合法示例**。

## 五、墓碑提示——删了字段，得让人知道去哪

### 5.1 落点：SDK `validate`（作者侧唯一能触达的地方）

[sdk/validate.ts](../../../../packages/plugin-sdk/src/validate.ts) 的 `validatePluginJson` 在 **schema 校验通过之后**，加一道「已移除字段」检查。

### 5.2 🔴 为什么这不违反「schema 是唯一真源」

本仓铁律（[validate.ts 文件头](../../../../packages/plugin-sdk/src/validate.ts) 原话）：

> **必填/contributes 以 plugin.schema.json 为唯一真源**——不手写第二份字段清单。

**墓碑名单不是「第二份字段清单」**——语义完全不同：

| | 字段清单（禁止第二份） | 墓碑名单（本条新增） |
|:--|:--|:--|
| 回答什么 | 「**什么字段是合法的**」 | 「**什么字段曾经合法、现在已移除、替代是什么**」 |
| 真源 | `plugin.schema.json` | **本层这次删除动作本身** |
| 会漂移吗 | 会（schema 改了名单没跟上 = bug） | 不会（移除了就是移除了，墓碑**只增不减**） |

**代码里必须把这句注释写进常量旁边**——否则下一个人看到「一份硬编码的字段名数组」会当成违例删掉。

### 5.3 形态

```ts
/** 已移除的 manifest 字段墓碑——**这不是第二份字段清单**（合法字段的真源仍是 plugin.schema.json）。
 *  回答的是另一个问题：「曾经合法、现已移除」→ 替代方案。只增不减，不与 schema 同步。
 *  schema 顶层 additionalProperties: true（实测），删掉 properties 定义**不会**让作者收到任何报错
 *  ——没有这道兜底，作者写 27 条更新日志却看到「未附带更改日志」，永远查不出原因。 */
const REMOVED_MANIFEST_FIELDS: Record<string, string> = {
  changelog: "改用插件根目录的 CHANGELOG.md（市场详情页「更改日志」页签的唯一真源）",
  readme: "改用插件根目录的 README.md（文件名固定，无需声明路径）",
};
```

**行为**：命中 → **警告，不是错误**（`valid` 仍为 `true`）。

> **为什么不判错**：① 存量第三方插件的 `plugin.json` 里可能有这两个字段，判错会让他们的 `npm run build` 突然炸——**为一个从无读取方的字段破坏构建不值**；② 警告已经足够——作者跑一次 `validate` 就看到；③ 本仓官方插件由 06 号档案的**仓库门禁**红灯兜底，**两处合起来覆盖完整**（作者侧软提醒 + 自有仓库侧硬拦截）。

### 5.4 `ValidationResult` 需要加 `warnings`

```ts
export interface ValidationResult {
  valid: boolean;
  errors: string[];
  warnings?: string[];   // 新增——可选字段，存量消费方零影响
}
```

`bin.ts` 的 `validate` 子命令把 warnings 打印成 `⚠` 行。**可选字段 = 现有调用方（`bin` / `defineLinkdeskPluginConfig` / `vite-config`）一行不用改。**

## 六、要不要新 API？——**逐条核过，结论：不要**

用户要求「如果有新 api 还要再 03-插件制造 中给出」。**本层核完的结论是不需要**，逐条留证免得下次重问：

| 可能被提议的新 API | 为什么不需要 |
|:--|:--|
| `window.linkdesk.plugins.readFile(id, path)` | **已有等价物**——marketplace 现用 `plugins.resolvePath(id)` + `filesystem.readTextFile(...)`（[packageFiles.ts](../../../../plugins/marketplace/src/services/packageFiles.ts)）读包内文件。再加一个 = **同一能力两个入口**（违归一） |
| `window.linkdesk.plugins.getChangelog(id)` | 需要的是**包内某个文件**，不是某个语义。为「更改日志」单开 API = 核心开始「知道插件长什么样」（违**核心无知原则**） |
| 新 contribute 类型（如 `contributes.readme`） | 贡献点是「插件对壳的声明」，而 README/CHANGELOG 是**包内文件**，由壳的通用文件通道读——**声明一层是多余的中介** |
| 壳侧新 IPC 通道 | 无跨进程新需求——读包已在插件 WebView 内完成（`filesystem.*` 走既有 IPC） |

⇒ **03-插件制造 目录无需新增 API 章节。** 本层的文档动作是**删两行、加一节**（[01 号档案](01-规范文档对齐.md)），不是加 API。

## 七、🔴 顺序铁律（本轮最容易踩的坑）

**§二 的墓碑警告（3.7.2）与 §三 的插件实例删字段（3.7.3）的先后关系：**

```
✅ 正确序：3.7.2 先落（schema/SDK 改完）→ 3.7.3 再删 9 只插件的字段
❌ 错误序：3.7.3 先删插件字段 → 3.7.2 才动 schema
```

**为什么**：反过来的话，中间会存在一个**窗口期**——插件 `plugin.json` 已无该字段，但 schema 里还写着它、文档还在教人写。下一个人在这个窗口进来，看到的是**一份自相矛盾的仓库**。

> **同源纪律**（[00 §五 ②](00-整理档案.md) 已拍「**不搬**」）：`first-run-setup` 源码在仓外，**本轮够不着它** ⇒ 它的 `plugin.json.changelog` **永远只能靠用户手工删**，落成**对用户的口头交接（E6#91h）**。
