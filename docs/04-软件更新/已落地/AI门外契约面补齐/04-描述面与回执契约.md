# 描述面与回执契约（S3b · S3a · S1 · S2）

> 归属：[00-提案](00-提案.md)。四条主线共用一个主题：**门外的「读」是否可信**——能不能不问就拼对请求（S3b/S3a），能不能一眼看出成没成、错在哪（S1/S2）。

---

## 一、S3b · `describe` 补 `returns` / `example` / `apiVersion`（🥈）

### 问题

B2-4 原话：「describe 只有参数名/类型，靠试错猜请求体」。现在 AI 知道「有 `sessionId` 这个参数」，不知道「一次调用长什么样」「回来是什么形状」。

### 设计

| 字段 | 住哪 | 形态 | 说明 |
|:--|:--|:--|:--|
| `params` | manifest（已有） | 数组 | 保持 |
| `returns` | manifest（**新增**） | **字段表**，⛔ 不要求完整 JSON Schema | `[{name,type,optional,description}]`；够 AI 拼判断即可 |
| `example` | manifest（**新增**） | 请求体示例（一个对象） | 只给请求侧；返回侧用 `returns` 表 |
| `apiVersion` | `describe` 顶层（**新增**） | 字符串 | 契约面版本；命令面结构变化时 bump |

### 归一化铁律

- **一份声明**：`returns`/`example` 与 `params` 同住 manifest，⛔ 不许在文档、SDK 注释、CLI help 里各写一份。
- **必填（内测免兼容）**：官方各仓同一批补齐后，schema 对 `returns`/`example` **拒绝缺失**；⛔ 不留「可选期」。补齐前不许开这个门禁（否则全仓红）。
- **可验证**：`doctor --blind`（见 05）抽样对比「声明 returns 的字段名」与「真实回执的键」——**声明与实现漂移要能被抓出来**。这是本档唯一让 `returns` 不变成第二份谎言的机制。
- `apiVersion` 由壳统一生成（壳版本 + contracts 版本），⛔ 作者手填。

### 不做

- ⛔ 不做完整 JSON Schema：AI 读字段表就够，全 Schema 会把 describe 撑爆（与 S3a 冲突）。
- ⛔ 不给返回的**每个嵌套层**做类型：只到第一层键 + 必要时一层嵌套。

## 二、S3a · 描述面规模治理（🥈，现在就做）

### 问题

B1-8 说「185 条吃光上下文」，B2 反证「3 分钟摸清 183 条，设计对了」。**两边都对**——差别在规模。

### 决策（2026-11-25 用户原则 · 决策 #15）

> ⛔ **不做「等命令变多再做」的触发线**。能力一次到位：**现在就实现** `filter`/`limit`/`cursor`，默认行为保持全量（对现有调用零影响）。
> 理由：这正是用户最反感的「等某某需求出现再做」；槽位后补的代价远大于现在做完。

**规模事实（用于验收，不作为开关）**：单插件 183 条全量可用（02 亲证）；多插件总量才是 `filter`/`limit` 的价值区。

### 设计（现在就实现）

```jsonc
// describe 请求（全部可选，缺省 = 现有全量行为，⛔ 破坏兼容）
{
  "filter": { "pluginId": "serial-monitor", "category": "serial", "query": "cursor" },
  "limit": 50,
  "cursor": "<opaque>"
}
```

- `filter.query`：对 id/title/description 做**子串**匹配（⛔ 不做模糊排序，AI 不需要「近似」）；
- `limit` + `cursor`：稳定分页，`cursor` 不透明、由壳生成；
- 响应带 `total` / `nextCursor`，AI 能判断「还有没有」；
- ⛔ 不引入向量检索/语义搜索：不可解释、不可测试，且与「结构化优先」冲突。

### 归一化

- 筛选在**壳侧命令面**做（`describe` 的唯一实现），⛔ CLI / MCP / 插件各写一份过滤。
- 分页游标与串口 `readSince` 的游标**同名不同义**——文档必须写明，⛔ 不许复用同一套帮助文案造成误解。

## 三、S1 · 回执封装归一（🥉，先复现）

### 问题

B1-6「回执嵌套 1 层 / 2 层不一致」，02 反证「`exec` 严格回传真结果」。⇒ 不排除是 **CLI 与 MCP 两条路各自解包**导致。

### 设计

1. **T-S1-0 复现**：同一条命令，CLI 与 MCP 各调一次，钉版本记录回执结构与深度。
2. 若复现 ⇒ **单一 `unwrap`**：住 `cli/linkdeskctl/lib/` 一份，CLI 与 MCP **共用**；⛔ 两份解包。
3. 负控用例：多包输入（命令本身返回里再嵌一个同名信封）必须仍只解一层。

### 归一化铁律

- 解包深度**恒等于 1**；任何「按命令特判深度」都是 bug，不是特性。
- 复现不了 ⇒ **销账并记「无法复现」**（决策 #4），但在 `doctor` 留一条「回执深度」哨兵 → 以后再漂移会被抓。

## 四、S2 · 插件命令错误码统一（🥉）

### 问题

插件自造码（如 `badArg("no-view", 中文)`），门外只能从中文猜。

### 设计

- **唯一构造**：SDK 提供 `pluginError({ code, message, hint?, details? })`，插件只能经它抛结构化错误；⛔ 插件自己拼 `throw new Error("...")`。`code` 必填非空（**`E` 开头是建议，不强制**）；`details` 原样透传（`--json` 可见，⛔ 进 CLI 人读输出）。
- **透传**：壳 / CLI 原样透传插件给的 `code`。
- **兜底**：没有 `code` ⇒ `EUNKNOWN`，⛔ 不许「猜语义」把它归到某个已有码。
- **与 S4 对齐**：`EVIEWREQUIRED` / `ENOTACTIVE` / `EUNKNOWNCOMMAND` 由**壳**产生（S4），插件不许自造这三个码的变体。

### 归一化

- 错误信封**只有一个构造函数**（SDK）；壳、CLI、MCP 都消费同一形状 `{ok:false, code, message, hint, details?}`。
- ⛔ 中文消息当码用；`message` 是给人读的，`code` 是给 AI 判的，两者分离。

## 五、判据（对着 07 过一遍）

| 判据 | 本条要求 |
|:--|:--|
| 归一化 | 描述面一份声明（manifest）· 解包一份实现 · 错误信封一份构造 |
| AI 友好化 | 不问就能拼请求（example/returns）；错了有码可判（code）；规模大能筛（filter） |
| 无硬编码 | ⛔ 命令特判深度；⛔ 中文当码；⛔ 手填 apiVersion |
| 无死代码 | `--brief` 若无人用则不做（原档已判低优），⛔ 留一个半成品开关 |
| 高内聚低耦合 | 壳只管「形状/深度/分页」，⛔ 不解释业务语义 |
| 文件禁止平铺 | 四条主线住本一档；各自验收分节，⛔ 混写 |

## 六、验收

1. **S3b**：任取 5 条命令，`describe` 给出的 `example` 可直接执行成功；`returns` 的键与真实回执一致（`doctor` 抽样断言）。
2. **S3a**：未到触发线时行为与现在**完全一致**（回归）；造 600 条模拟命令时 `limit`/`cursor` 能翻页且不漏不重。
3. **S1**：CLI 与 MCP 对同一命令返回**结构完全相同**；多包输入只解一层（负控）。
4. **S2**：插件抛结构化错误 ⇒ 门外收到原 `code`；插件抛裸 `Error` ⇒ `EUNKNOWN`（⛔ 猜成 `EINVAL` 之类）。
5. **跨领域**：以上四条用 file-tree 也跑一遍。
6. `npm run check` 全绿。
