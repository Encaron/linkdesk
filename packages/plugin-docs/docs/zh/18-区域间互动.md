# 18 — 区域间互动：侧栏选中 → 主区切换 → 状态栏更新

> **本页回答一个问题：** 我的插件横跨好几个区域（图标栏 / 侧栏 / 主区 / 底部面板 / 状态栏），**它们之间怎么对上**？
> 例："侧栏里选中一个会话 → 主区切到那个会话的标签页 → 状态栏显示当前会话名。"

| | |
|---|---|
| 读者 | 已经知道区域在哪（→ [17-区域地图](17-区域地图.md)），现在要让它们**联动**的作者 |
| 形态 | **配方集**——每个场景一段可抄的骨架 |
| 不是 | 通信机制字典（→ [07-插件间通信](07-插件间通信.md) 讲"有哪些机制"）· 数据管道命令命名（→ [14-数据管道命令约定](14-数据管道命令约定.md)） |

> **一句话分工：`07` 回答"插件之间怎么传数据"，本页回答"同一个插件的几个区域怎么对上"。** 前者是机制，后者是**组网**——先在本页选出手段，再去 `07` 看机制细节。

---

## 一、五种联动手段（先选手段，再写代码）

| 想达到的效果 | 用什么 | 方向 | 耦合 |
|:--|:--|:--|:--|
| **点一下 → 另一个区域做件事** | `window.linkdesk.commands.executeCommand("id", args)` | 定向（一对一） | 紧——调用方知道命令名 |
| **一个区域变了 → 谁关心谁自己刷新** | `window.linkdesk.events.emit(channel, payload)` ＋ `events.on` | 广播（一对多） | 松——发布方不知道谁在听 |
| **某个状态决定按钮/菜单/视图显不显示** | `window.linkdesk.contextKey.set(key, value)` ＋ 声明里的 `when` | 声明式（零代码联动） | 最松——壳读键，你不碰对方 |
| **跨区域的"导航"**（打开/聚焦别处） | `tabs.create` / `tabs.openOrFocus` / `tabs.focus` / `panel.reveal(viewId)` / `panel.revealFloating(viewId)` | 定向 | 紧——你在指定去哪 |
| **用户在设置页改了值 → 各区域跟随** | `window.linkdesk.configuration.onChange(key, cb)` | 广播（壳替你发） | 最松——零额外声明（→ [20-我的插件加一条配置项](20-我的插件加一条配置项.md)） |

**还有一条零代码的：** 颜色/字体/圆角/玻璃这些**外观**随主题自动变——你只要用 `var(--xxx)`，主题一切全区域跟着变，不需要任何订阅。

## 二、四个典型配方

### 配方 A —— 侧栏选中 → 主区打开/聚焦对应标签页

侧栏视图里选中一项，让主区出现/聚焦对应内容。这是**"命令 + 打开"**的组合：

```tsx
// 侧栏视图（src/views/SessionListView.tsx）
function onPick(id: string) {
  // ① 让主区把对应内容亮出来（幂等：已有就聚焦，没有就建）
  void window.linkdesk.tabs.openOrFocus("my-plugin", { sourceId: id, label: `会话 ${id}` });
}
```

```tsx
// 主区入口组件（src/index.tsx）——靠 sourceId 知道该显示哪一个
export default function MyView({ isActive, sourceId }: { isActive: boolean; sourceId?: string }) {
  // sourceId 变了 → 这是"同一个插件、不同标签页"，各自独立
  return <SessionDetail id={sourceId} />;
}
```

> **`openOrFocus` 比 `create` 更常用**——用户连点两次不该出现两个一样的标签页。
> 同一个插件的多个标签页靠 **`sourceId`** 区分（不是靠各自的 React state）——见 [17 §五 props 契约](17-区域地图.md)。

### 配方 B —— 选中与否 → 状态栏条目 / 标题栏按钮自动显隐

**想让"有选中时才出现的按钮"出现，不要用 React 往下传 prop——用 context key 让壳自己判：**

```tsx
// 侧栏视图：把状态写进 context key（键名建议带插件前缀，避免和别的插件撞）
useEffect(() => {
  void window.linkdesk.contextKey.set("my-plugin.hasSelection", !!selectedId);
}, [selectedId]);
```

```jsonc
// plugin.json —— 声明式消费这个键，两个区域各写各的 when
{
  "contributes": {
    "titleBar": { "right": [
      { "command": "my-plugin.rename", "icon": "codicon-edit", "when": "my-plugin.hasSelection" }
    ] },
    "menus": { "editor/context": [ { "command": "my-plugin.rename", "when": "my-plugin.hasSelection" } ] }
  }
}
```

> **这是"零代码联动"**：标题栏按钮、右键菜单项、快捷键、侧栏视图都能用同一个 `when` 条件——你在一个地方 `set`，壳在 N 个地方读。`when` 的语法（`&&` / `||` / `==` / `in` / `!` / `()`）与壳自带的 key 表 → [03-插件contributes规范 §四](03-插件contributes规范.md)。

#### 🔴 旗子保留表——**先看这张表再起名**（壳 1.38 起）

旗子是**全局名册的键**：你 `set` 的名字**全池可见**，宿主的内置命令/菜单也用同一张表读 `when`。所以名字不能乱起——分**两段**，各段规矩不同：

**① 宿主专用旗子（🔴 插件禁设）**——宿主内核/壳自己维护的状态。占用它 = 改写宿主菜单/命令面板的显隐条件，**两侧都不报错**，用户只看到"菜单项莫名其妙不见了"：

| 旗子名 | 它在管什么（宿主侧） |
|:--|:--|
| `activeEditor` | 当前编辑器类型（命令/菜单按它显隐） |
| `editorCount` | 打开的编辑器数量 |
| `editorHasSelection` | 当前编辑器是否有选中 |
| `inputFocus` | 输入框是否获焦（🔴 实测点：F2 重命名时**快捷键要让位**） |
| `sidebarPosition` | 侧栏停靠位置 |
| `updateActionable` | 是否有可安装的更新 |
| `updateButtonLabel` | 更新按钮的文字 |

**② 宿主公开约定旗子（🟠 可设，但只有宿主该设）**——宿主 `when` **读**、**写的人本该是宿主自己**：

| 旗子名 | 约定用途 | 谁能设 |
|:--|:--|:--|
| `settingKey` | 设置项右键齿轮菜单——**当前项的键名** | 只有 `settingItemGear` 齿轮菜单该设 |
| `settingValue` | 同上——当前值 | 同上 |
| `settingType` | 同上——控件类型 | 同上 |
| `settingScope` | 同上——作用域 | 同上 |

这四条**事实上**是"谁都能设、谁都能读"的（`MenuId` 是开放字符串 ⇒ 第三方**可以**往 `settingItemGear` 槽加项）——所以设它们**不判红**。但**写点本该只有齿轮菜单一处**：你从别处覆盖它，齿轮菜单就会对着**错误的项**开合。⇒ **别设它们**，除非你正是在实现那个槽的菜单。

**机器可读的真源**（随 SDK 包下发，别靠猜）：

```
node_modules/@linkdesk/plugin-sdk/schemas/host-reserved.json
  → "contextKeysHostOnly": ["activeEditor", "editorCount", ...]   ← 段① 禁设
    "contextKeysPublic":   ["settingKey", "settingValue", ...]     ← 段② 别设（除齿轮菜单）
```

**两级判定**（与设置键、外观 id 同形，别混着记）：

| 判据 | 分级 | 谁判 | 会发生什么 |
|:--|:--:|:--|:--|
| `set` 的名字 ∈ **段① 宿主专用** | 🔴 **红** | SDK 腿 `linkdesk/no-unowned-context-key` | 作者仓里 lint 报红点名；**运行时第二道网**在 `contextKey:set` 过桥处补一条 `console.error`，但 🔴 **值照写、不拒绝**（见下） |
| **新**旗子第一段不是本仓 `pluginId` | 🟡 黄（建议） | SDK 腿 | 报点带 `suggested` = 只换第一段的新名（`zzzFlag` → `my-plugin.zzzFlag`）。存量官方 18 仓有 23 个旗子不合此规，迁移由壳侧统一执行——**新旗子请照规矩写** |
| `set` 的名字 ∈ **段② 约定面** | 🟠 **不判** | 只登记 | 合法，但见上：那是齿轮菜单的位置，别去覆盖 |

> **为什么"占宿主专用"是红、"没带自己前缀"只是黄**：占专用旗子有**真害**（顶替宿主状态，两侧都不报错）；而"没带前缀"在存量里有 23 个反例，一刀切会把既有插件当场弄坏。分级不同 = 容忍度不同。

> 🔴 **运行时为什么"只出声、不拒绝"**（与设置键/外观 id 的"拒登"**不同**）：旗子是**状态写**不是**注册**——`contextKey.set(name, value)` 只是往一张表里写值，同名被两方先后写、后者覆盖前者是**正常运行时行为**；而"拒谁"要求运行时知道"谁是先者"，可 `contextKey:set` 过 IPC 时**只带 `[key, value]` 两个值、不带写入者身份** ⇒ 「先者保留」在这个面上**结构上做不到**。⇒ 唯一诚实的动作 = 出声点名 ＋ 值照写。**真正的保护在你那边的 lint 里**（带身份、编译期报点），运行时那道只是第二张网。

### 配方 C —— 一个区域变了，分散在几处的 UI 一起刷新

比如"串口断开"要同时影响：侧栏的连接行、主区的按钮、状态栏的计数。**发布一个事件，各处自己订阅：**

```tsx
// 发布方（比如侧栏视图里检测到端口掉了）
window.linkdesk.events.emit("my-plugin:connectionChanged", { portName, open: false });
```

```tsx
// 订阅方 1 —— 主区组件
useEffect(() => window.linkdesk.events.on<{ open: boolean }>("my-plugin:connectionChanged", (p) => setOpen(p.open)), []);

// 订阅方 2 —— 状态栏组件（另一个文件、另一个区域，互不知道对方存在）
useEffect(() => window.linkdesk.events.on<{ open: boolean }>("my-plugin:connectionChanged", (p) => setText(p.open ? "已连接" : "未连接")), []);
```

> 🔴 **频道名必须带插件前缀**（`<插件id>:<数据名>`）。所有插件共享同一个渲染进程，频道是**全池可见**的——叫 `changed` 会撞车。

### 配方 D —— 用户改了设置 → 各区域立刻跟随

```tsx
useEffect(() => {
  return window.linkdesk.configuration.onChange<number>("my-plugin.refreshInterval", (ms) => {
    restartTimer(ms);   // 侧栏、主区、状态栏各自订阅各自关心的键
  });
}, []);
```

设置项怎么声明、怎么出现在设置页 → [20-我的插件加一条配置项](20-我的插件加一条配置项.md)。

## 三、一个完整小例子（三个区域串起来）

目标：侧栏列表选中 → 主区切过去 → 状态栏显示当前项 → 没选中时标题栏按钮藏起来。

```tsx
// ① src/views/SessionListView.tsx —— 侧栏：唯一的"用户意图"产生地
export default function SessionListView() {
  const [sel, setSel] = useState<string | null>(null);

  const pick = (id: string) => {
    setSel(id);
    void window.linkdesk.contextKey.set("my-plugin.hasSelection", true);   // → 配方 B
    void window.linkdesk.tabs.openOrFocus("my-plugin", { sourceId: id });  // → 配方 A
    window.linkdesk.events.emit("my-plugin:selectionChanged", { id });     // → 配方 C
  };

  return <ul>{items.map((it) => <li key={it.id} onClick={() => pick(it.id)}>{it.name}</li>)}</ul>;
}
```

```tsx
// ② src/index.tsx —— 主区入口：只认 sourceId，自己的状态自己管
export default function MyView({ sourceId }: { sourceId?: string }) {
  return sourceId ? <Detail id={sourceId} /> : <Empty />;
}
```

```tsx
// ③ src/components/statusBar.tsx —— 状态栏：订阅事件而不问"谁选中的"
export default function StatusBar() {
  const [label, setLabel] = useState("");
  useEffect(
    () => window.linkdesk.events.on<{ id: string }>("my-plugin:selectionChanged", (p) => setLabel(`当前：${p.id}`)),
    [],
  );
  return <span>{label}</span>;
}
```

```jsonc
// ④ plugin.json —— 声明面：三个区域各就各位，按钮带 when
{
  "pluginId": "my-plugin",
  "appearsIn": { "iconBar": "top", "tabBar": true },
  "entry": "src/index.tsx",
  "contributes": {
    "viewsContainers": { "my-plugin": { "title": "会话", "location": "sidebar" } },
    "views": { "my-plugin": [ { "id": "sessions", "title": "", "render": "src/views/SessionListView.tsx", "order": 0 } ] },
    "titleBar": { "right": [ { "command": "my-plugin.rename", "icon": "codicon-edit", "when": "my-plugin.hasSelection" } ] }
  },
  "statusBar": [ { "id": "current", "label": "", "align": "left" } ]
}
```

## 四、铁律与反模式

| 别这么做 | 为什么 | 正确做法 |
|:--|:--|:--|
| 在**模块顶层**注册 `events.on` / IPC 监听 | 模块级 = 导入即执行 = 永不清理，卸载后变僵尸回调（硬约束 19，ESLint 机械拦截） | 放 `useEffect`，返回退订函数 |
| 用 `useRef` 存"跨区域传过来的状态" | ref 更新不触发重渲染 → UI 与实际状态脱节，下次别的事件触发时才"突然跳变"（硬约束 17） | 渲染相关的一律 `useState` |
| 用 `localStorage` / 全局变量当总线 | 绕过壳的统一通道，多窗口/卸载后行为不可预期 | `configuration`（要持久化）或 `events`（只要通知） |
| 频道名不带插件前缀 | 所有插件共用一个渲染进程，频道是全局可见的 | `<pluginId>:<数据名>` |
| 直接 `import` 别的插件 | 插件之间互不知道对方存在（圆形大厅模型） | 走命令 / 事件 / context key |
| 用 `isActive` 把内容整块 blank 掉 | keep-alive 下所有标签页始终挂载，条件渲染会丢状态 | `isActive` 只 gate 副作用 |
| 手写右键菜单来"串联"区域 | 硬约束：右键菜单走声明式（`contributes.menus` ＋ `<ContextMenu>`） | 见 [05-插件UI写法规约](05-插件UI写法规约.md) |
