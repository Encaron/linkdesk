# 01 · 事故复盘与真机实证

> 本件记录的是一次 **2026-10-05 在用户真机上实证的事故**——🔴 **不是"据代码推出"的**。所有读数都是当场跑出来的，命令与出处附在行内。

---

## 一、现象（用户原话）

> 「我现在的安装版本是 `0.2.41`：`D:\01link\linkdesk`，但是**已经彻底无法运行 v1.0.35 的设置插件了**，但是插件详情页**仍旧显示「正常」**……只有继续开 dev 版的 `v0.2.48`（才能用）。」

即：**同一次事故，插件侧崩了，界面侧说一切正常。**

## 二、断裂机制（真机取证）

### 2.1 插件入口对壳池 vendor 的组件做了**顶层静态具名导入**

设置插件 `v1.0.35` 的入口 bundle `SettingsView-C259Ubby.js` **第一行**即：

```js
import { ContextMenu as he, ..., SelectBox as ke, ..., PluginCard as Je, HintTip as Xe, InlineInput as Qe } from "@linkdesk/ui"
```

（实测：`grep` 该文件；`PluginCard` / `SelectBox` / `HintTip` 均在此句中。）

### 2.2 这些组件在 `0.2.41` 的壳池里**根本不存在**

- `@linkdesk/ui` 在 SDK 的 `DEFAULT_EXTERNAL` 里被 **external 化**（[vite-config.ts:77](../../../../packages/plugin-sdk/src/vite-config.ts)）⇒ 产物里留下**裸 `import`**，运行期由**真壳的 import map** 去解（壳池 vendor 单实例供给）。
- **`PluginCard` 是 `@linkdesk/ui 0.2.44` 才进 barrel 的**——出处：壳仓 commit `bde05c77d`（第 4 波 4A「插件卡共享件 PluginCard 落地」）。
- 实测导出面读数：

| 时点 | 读数 | 命令 |
|:--|:--|:--|
| **`v0.2.41`**（用户安装版对应 tag） | `components.count = 57`，**`'PluginCard' in components === false`** | `git show v0.2.41:scripts/ui-surface.json` |
| **当前 dev（`0.2.48`）** | `count = 62`；相对 `v0.2.41` **新增 = `['OpenWithPicker', 'PluginCard']`**，**零删除** | 对比 [scripts/ui-surface.json](../../../../scripts/ui-surface.json) |

### 2.3 ⇒ ESM **链接期**失败 ⇒ **整只插件死**，不是"某个功能不出现"

静态具名导入 + 模块不存在导出 ⇒ 浏览器 ESM 在**链接阶段**抛 `does not provide an export named 'PluginCard'` ⇒ **整个模块图求值失败** ⇒ 设置插件**整只起不来**。

> 🔴 **这就是 changelog 那句话的错处**：插件 `1.0.35` 的 changelog 写「更低的软件上**这一组不出现**……本插件**其余功能一字不变**」——**静态 `import` 没有"局部降级"能力**。作者对**运行时调用**做了防御（`typeof e.setDefaultBulk == "function"`、`if (m)`），但**导入本身没防御**，于是"这一组消失"变成了"整只消失"。

## 三、为什么现有门禁没拦住（逐条点名）

| 现有的腿 | 它检查什么 | 为什么在这里是**绿的** |
|:--|:--|:--|
| **SDK lint** `no-ui-without-min-app-version`（[ui-min-app-version.ts](../../../../packages/plugin-sdk/src/eslint/checks/ui-min-app-version.ts)） | 插件**消费了** `@linkdesk/ui` ⇒ `minAppVersion` 必须 **≥ `UI_REANCHOR_APP_VERSION = "0.2.13"`** | 设置插件声明 `0.2.32` > `0.2.13` ⇒ **过闸**。那个 `0.2.13` 是「vendor 机制存在的起点」这个**一次性历史常量**，**它不知道 `PluginCard` 是 `0.2.44` 才有的** |
| **加载器版本门**（[runtime.ts:203](../../../../src/pluginLoader/resolution/runtime.ts)） | `appVer < manifest.minAppVersion` ⇒ 拒载 + toast | `0.2.41 ≥ 0.2.32` ⇒ **放行** |
| **市场拒装腿** | catalog entry 的 `minAppVersion` vs 当前壳 | 同上 ⇒ **放行**（用户就是这样从市场把这版装到 `0.2.41` 上的） |
| **兼容读数**（[compatibility.ts](../../../../src/core/compat/compatibility.ts)） | 只读 `minAppVersion` ＋ 悬空扫描 ＋ 两个日期 | `minAppSatisfied = versionGte("0.2.41", "0.2.32") = true` ⇒ 落 `current/compatible` ⇒ **显示「正常」** |

**关键结论**：**兼容读数没有谎报**——它忠实读的是 `plugin.json`。**撒谎的是那个手写的数字。**

## 五、Blast radius（实测，不是估计）

拿 `v0.2.41` 的导出面逐个比对**出厂的 6 只官方插件**实际导入的 `@linkdesk/ui` 成分：

| 插件 | 导入的 ui 导出数 | 命中「`0.2.41` 没有」的 |
|:--|:--:|:--|
| **settings** | 22 | ⚠️ **`PluginCard`** |
| file-tree | 9 | 无 |
| marketplace | 11 | 无 |
| editor / lang-defaults / theme-defaults | 0 | — |

**⇒ 波及面 = 1 只（settings）**。`OpenWithPicker`（新增的另一只）**没有官方插件导入**（它是壳自己用的）。**所以"全部插件重发一版"是过度动作**；本件的 G2 落地后，"翻账"应当机械得出这份名单。

## 六、为什么**本地测不出来**（本件最该记住的一条）

对第三方作者而言，这个错**结构性地难以在本地看见**：

| 路径 | 跑的是什么 | 能看见这个错吗 |
|:--|:--|:--|
| `npm run dev`（**默认**） | **mock 宿主** ＋ 作者自己 `node_modules` 里的 **`@linkdesk/ui@latest`**（[dev-host/mock.ts](../../../../packages/plugin-sdk/dev-host/mock.ts) ／ [linkdesk-mock.generated.ts](../../../../packages/plugin-sdk/dev-host/linkdesk-mock.generated.ts)，mock 只替 **`window.linkdesk.*` API 树**，**不替组件面**） | ❌ **组件全在，渲染完全正常** |
| `npm run dev:real`（E6#28.5 真机环） | **真壳**（插件直写进已安装壳的插件目录） | ✅ **能**——但只在**你手上那个壳**上 |
| 装进真壳 / 用户安装 | 真壳 | ✅ 能（用户侧） |

**两条推论**：

1. 一个**只用默认 `dev`** 的作者，可以**全程看不到任何错**，然后把包装进市场、推给用户的旧壳 → 崩。⇒ **"靠作者自己测出来"这条不成立**。
2. 🔴 **`dev --real` 也答不了这个问题**——它是**单向**的：它回答「**在这个壳上、此刻、跑得起来吗**」，**永远不回答**「**我最老能在哪个壳上跑**」。作者若（很自然地）下**最新**壳来测，全绿，他对旧壳用户**一无所知**；而他若下**旧**壳来测，才会撞见——**而这恰恰是本件要替他回答的那个问题**。
