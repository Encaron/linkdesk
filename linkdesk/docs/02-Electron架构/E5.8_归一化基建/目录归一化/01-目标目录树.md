## 0. 判据（三方共识的尺子）

1. **文件夹 = 一种东西**（同性质）；**文件对 = 一个单位**（同名 .tsx + .css 相邻 = 你的 C 里 LCD_1_69/src+inc 的等价物）
2. **宽度阈值 ~15**：一个夹里超过约 15 个单位且性质混杂 → 按语义/职责分组
3. **问题在宽度不在层数**：前端惯例层深 3-4 层是健康的，不要为加深而加深
4. **不建冗余包装夹**：`IconBarZone/IconBarZone.tsx` 这种夹名=文件名的包装盒零信息量（除非该单位要长成多文件模块）
5. **一起改的文件放一起**（co-location）：界面+样式+测试同夹，不搞全局 src/css/tests 三类分离（Codex 强调，Claude/AI-2 同意）

## 8. 执行指南（零上下文可执行——2026-08-16 步 1 试跑教训入库）

> 2026-08-16 步 1 首次试跑：git mv + 内外 import 改写后跑 tsc，报 15 处相对路径深度错误（见 8.1 踩坑表），用户叫停——**先完善本文档档案，再执行迁移**。已回退至 commit `ef20bb66`，树干净。重做按本节执行。

### 8.0 总则

- 每步独立 commit；**纯移动零逻辑改动**；门禁 `npm run check` 全绿才 commit
- `git mv` 保留 rename 追踪；外部引用改写用 sed 循环（见 8.1 脚本全文，可直接复制）
- **踩坑铁律：文件下沉一层后，该文件内所有相对 import（不止 services 相关）都要 +1 层 `../`**——tsc 会报，但报错是隐式 any + Cannot find module 混着来，容易漏判
- **再细分授权（2026-08-17 用户拍板）**：执行中若某域仍超宽度阈值（~15）或性质混杂，可继续建子子夹细分，不必回炉拍板。判据 2/3 不变——新夹名 kebab-case，语义与父夹一致，层深 3-4 层内健康。预案中无需再分的夹（services/ui 6 文件、zones 8 夹各 1-2 文件、shared 13 域各 1 对）；若执行时发现遗漏（如 SettingsView 子节增多、某控件长成多文件模块），按此授权直接细分
- 回退：`git reset --hard HEAD && git clean -fd <新目录>`（git mv 已 staged 的 rename 会被 reset 连同新路径文件一起清掉，旧路径由 HEAD 恢复）
