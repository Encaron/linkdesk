## 6. ESLint no-core-import-in-plugin 规则缺口核对

规则：[eslint-local-rules.js:824-877](../../../../eslint-local-rules.js#L824) `noCoreImportInPlugin`。**两条豁免路径 = 为何 10 处全漏网**：

1. **测试文件整文件豁免**（[eslint-local-rules.js:848](../../../../eslint-local-rules.js#L848)）：`/__tests__|\.test\.|\.spec\./` 匹配 → 直接 `return {}`。理由：vitest 单进程与壳同 JS 堆，"多 WebView 静默失效"前提不成立 → 5.2 的 3 处测试 import 永不报。
2. **纯类型 import 豁免**（[eslint-local-rules.js:862-867](../../../../eslint-local-rules.js#L862)）：`node.importKind === "type" || 全部 specifier importKind === "type"` → return。理由：类型擦除后零运行时耦合（E5.7#80）。→ 5.1 的 7 处运行时文件 type import 永不报。

**缺口定性与处置建议**：两条豁免设计时只考虑"运行时副作用"维度——类型 import 确实零运行时耦合，多 WebView 火种理由不成立。但对**契约消费路径**（Phase 4 目标）而言，type import 恰恰是插件依赖 @src/core 源码树的证据：
- 插件作者拿不到独立契约文件，只能偷 core 源码类型 → 违反插件独立铁律；
- #20 迁移后（10 处全走 linkdesk.d.ts 消费路径），这两条豁免的适用面大幅收缩。
- **#18 设计时应拍板**：契约生成后是否收紧规则（type import 只允许从 linkdesk.d.ts / 契约入口导入；测试文件豁免是否保留）。
